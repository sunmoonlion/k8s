# Celery Worker 多后端任务处理方案

## 问题场景

当 Celery Worker 需要处理来自多个后端服务（如 `llmops-service`、`incubator-service`、`scrapy-service` 等）的任务时，需要解决代码提取和任务路由的问题。

## 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **方案1：多 Worker Deployment** | 隔离性好、配置简单、易于扩展 | 资源占用较多 | 不同后端任务差异大 |
| **方案2：多 Init Container** | 资源占用少、统一管理 | 代码合并复杂、冲突风险 | 后端任务相似、代码兼容 |
| **方案3：多队列 + 多 Worker** | 灵活、可独立扩展 | 配置复杂 | 需要按队列隔离 |
| **方案4：共享代码库** | 代码统一、维护简单 | 需要重构现有代码 | 新项目或可重构项目 |

---

## 方案1：多 Worker Deployment（推荐）

为每个后端创建独立的 Worker Deployment，每个 Worker 只处理对应后端的任务。

### 架构图

#### 方案1A：单个 RabbitMQ + 多个队列（推荐）

```
┌─────────────────┐
│ llmops-service  │ ──┐
└─────────────────┘   │
                       │
┌─────────────────┐   │    ┌──────────────────────┐
│incubator-service│ ──┼───>│   RabbitMQ (单个)    │
└─────────────────┘   │    │  ┌────────────────┐  │
                       │    │  │ llmops-queue   │  │
┌─────────────────┐   │    │  │ incubator-queue│  │
│ scrapy-service  │ ──┘    │  │ scrapy-queue   │  │
└─────────────────┘        │  └────────────────┘  │
                            └──────────────────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    │                 │                 │
                    ▼                 ▼                 ▼
        ┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
        │celeryworker-     │ │celeryworker-     │ │celeryworker-     │
        │llmops            │ │incubator         │ │scrapy            │
        │监听:             │ │监听:             │ │监听:             │
        │llmops-queue      │ │incubator-queue   │ │scrapy-queue      │
        └──────────────────┘ └──────────────────┘ └──────────────────┘
```

**特点**：
- ✅ **单个 RabbitMQ 实例**：资源占用少，管理简单
- ✅ **多个队列**：不同后端使用不同的队列名称
- ✅ **队列隔离**：每个队列独立，互不影响
- ✅ **易于扩展**：可以独立扩展某个队列的 Worker

#### 方案1B：多个 RabbitMQ（完全隔离）

```
┌─────────────────┐
│ llmops-service  │ ──> RabbitMQ-1 (llmops-queue)
└─────────────────┘

┌─────────────────┐
│incubator-service│ ──> RabbitMQ-2 (incubator-queue)
└─────────────────┘

┌─────────────────┐
│ scrapy-service  │ ──> RabbitMQ-3 (scrapy-queue)
└─────────────────┘

        ┌──────────────────┐
        │celeryworker-llmops│ ──> 连接 RabbitMQ-1
        └──────────────────┘

        ┌──────────────────┐
        │celeryworker-     │ ──> 连接 RabbitMQ-2
        │incubator         │
        └──────────────────┘

        ┌──────────────────┐
        │celeryworker-scrapy│ ──> 连接 RabbitMQ-3
        └──────────────────┘
```

**特点**：
- ✅ **完全隔离**：每个后端使用独立的 RabbitMQ
- ❌ **资源占用多**：需要多个 RabbitMQ 实例
- ❌ **管理复杂**：需要管理多个 RabbitMQ
- ✅ **高可用性**：一个 RabbitMQ 故障不影响其他

### RabbitMQ 部署建议

**推荐使用方案1A（单个 RabbitMQ + 多个队列）**，原因：

1. **资源效率**：单个 RabbitMQ 实例可以处理大量队列
2. **管理简单**：只需管理一个 RabbitMQ 实例
3. **队列隔离**：RabbitMQ 的队列机制天然隔离，不同队列互不影响
4. **易于监控**：统一监控和管理
5. **成本低**：减少资源占用

**何时使用方案1B（多个 RabbitMQ）**：
- 需要完全隔离（安全要求）
- 不同后端在不同集群/网络
- 需要独立的 RabbitMQ 配置（如不同的持久化策略）

### 实现步骤

#### 1. 创建多个 Worker 目录结构

```
celeryworker-app/
├── celeryworker-llmops/          # llmops-service 的 Worker
│   ├── deploy-celeryworker/
│   │   ├── deploy-celeryworker.conf
│   │   └── deploy-celeryworker.sh
│   └── resources/
│       └── celeryworker.yaml
├── celeryworker-incubator/       # incubator-service 的 Worker
│   ├── deploy-celeryworker/
│   │   ├── deploy-celeryworker.conf
│   │   └── deploy-celeryworker.sh
│   └── resources/
│       └── celeryworker.yaml
└── celeryworker-scrapy/           # scrapy-service 的 Worker
    ├── deploy-celeryworker/
    │   ├── deploy-celeryworker.conf
    │   └── deploy-celeryworker.sh
    └── resources/
        └── celeryworker.yaml
```

#### 2. 配置示例：llmops-service Worker

```bash
# celeryworker-llmops/deploy-celeryworker/deploy-celeryworker.conf
# 注意：如果使用方案1（多 Worker Deployment），每个 Worker 需要独立的配置文件
BACKEND_IMAGE="llmops-service"
BACKEND_TAG="1.0.0"
CELERY_QUEUE="llmops-queue"  # 使用独立的队列名称
CELERY_WORKER_IMAGE="celeryworker-llmops"
# 使用同一个 RabbitMQ（推荐）
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-sunmoonai.messaging-platform-dev:5672//"
```

#### 3. 配置示例：incubator-service Worker

```bash
# celeryworker-incubator/deploy-celeryworker/deploy-celeryworker.conf
# 注意：如果使用方案1（多 Worker Deployment），每个 Worker 需要独立的配置文件
BACKEND_IMAGE="incubator-service"
BACKEND_TAG="1.0.0"
CELERY_QUEUE="incubator-queue"  # 使用不同的队列名称
CELERY_WORKER_IMAGE="celeryworker-incubator"
# 使用同一个 RabbitMQ（推荐）
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-sunmoonai.messaging-platform-dev:5672//"
```

#### 4. RabbitMQ 配置说明

**方案1A（推荐）：单个 RabbitMQ + 多个队列**

所有 Worker 使用同一个 RabbitMQ，但使用不同的队列名称：

```bash
# 所有 Worker 使用相同的 RabbitMQ 地址
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-sunmoonai.messaging-platform-dev:5672//"

# 但使用不同的队列名称
# celeryworker-llmops:    CELERY_QUEUE="llmops-queue"
# celeryworker-incubator: CELERY_QUEUE="incubator-queue"
# celeryworker-scrapy:    CELERY_QUEUE="scrapy-queue"
```

**方案1B：多个 RabbitMQ（完全隔离）**

每个 Worker 使用不同的 RabbitMQ 实例：

```bash
# celeryworker-llmops
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-llmops.messaging-platform-dev:5672//"

# celeryworker-incubator
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-incubator.messaging-platform-dev:5672//"

# celeryworker-scrapy
CELERY_BROKER_URL="amqp://admin:admin123@rabbitmq-scrapy.messaging-platform-dev:5672//"
```

#### 5. 部署脚本（统一部署所有 Worker）

```bash
#!/bin/bash
# deploy-all-workers.sh
# 注意：如果使用方案1（多 Worker Deployment），需要为每个 Worker 创建独立的目录和配置文件
# 每个 Worker 需要自己的 deploy-celeryworker.sh 和 deploy-celeryworker.conf

WORKERS=("celeryworker-llmops" "celeryworker-incubator" "celeryworker-scrapy")

for worker in "${WORKERS[@]}"; do
    echo "部署 $worker..."
    cd "$worker/deploy-celeryworker"
    # 每个 Worker 使用自己的部署脚本（需要单独创建）
    ./deploy-celeryworker.sh deploy dev
    cd - > /dev/null
done
```

### 优点

- ✅ **隔离性好**：每个 Worker 独立，互不影响
- ✅ **配置简单**：每个 Worker 只需配置自己的后端和队列
- ✅ **易于扩展**：可以独立扩展某个 Worker 的副本数
- ✅ **故障隔离**：一个 Worker 故障不影响其他 Worker
- ✅ **队列隔离**：使用单个 RabbitMQ + 多个队列，队列之间天然隔离
- ✅ **资源高效**：单个 RabbitMQ 可以处理大量队列
- ✅ **独立提取**：每个 Worker 有自己独立的 Init Container，从对应的后端镜像提取代码

### 缺点

- ❌ **资源占用**：每个 Worker 需要独立的 Pod 资源（但 RabbitMQ 可以共享）
- ❌ **管理复杂**：需要管理多个 Deployment（但 RabbitMQ 只需一个）
- ❌ **Init Container 开销**：每个 Pod 启动时需要运行 Init Container 提取代码

### Init Container 工作机制

**每个 Worker 都有自己独立的 Init Container**：

- ✅ 每个 Worker Deployment 从对应的后端镜像提取代码
- ✅ 每个 Pod 使用独立的 emptyDir 卷存储提取的代码
- ✅ 不同 Worker 之间完全隔离
- ✅ Init Container 完成后自动退出，不占用资源

详细说明请参考：[InitContainer工作机制说明.md](InitContainer工作机制说明.md)

## 方案2：多 Init Container（一个 Worker 处理多个后端）

使用多个 Init Container 从不同后端镜像提取代码，合并到一个 Worker 中。

### 架构图

```
┌─────────────────┐
│ llmops-service  │ ──┐
└─────────────────┘   │
                       │
┌─────────────────┐   │    ┌──────────────────────┐
│incubator-service│ ──┼───>│  celeryworker        │
└─────────────────┘   │    │  ┌────────────────┐  │
                       │    │  │ Init Container │  │
┌─────────────────┐   │    │  │ 1: llmops     │  │
│ scrapy-service  │ ──┘    │  │ 2: incubator  │  │
└─────────────────┘        │  │ 3: scrapy     │  │
                            │  └────────────────┘  │
                            │  ┌────────────────┐  │
                            │  │ Worker 容器    │  │
                            │  │ 监听所有队列   │  │
                            │  └────────────────┘  │
                            └──────────────────────┘
```

### 实现步骤

#### 1. 配置格式（统一格式）

配置文件使用统一格式：`BACKEND_<name>_<property>`

```bash
# deploy-multi-celeryworker.conf
# 后端配置格式
BACKEND_llmops_IMAGE="llmops-service"
BACKEND_llmops_TAG="1.0.0"
BACKEND_llmops_CODE_EXTRACT_DIRS="worker core services db models"

BACKEND_incubator_IMAGE="incubator-service"
BACKEND_incubator_TAG="1.0.0"
BACKEND_incubator_CODE_EXTRACT_DIRS="worker core services db models"
```

**优点**：
- ✅ 统一格式，易于理解和扩展
- ✅ 支持默认值，减少重复配置
- ✅ 添加新后端只需添加对应的配置项

#### 2. YAML 文件（仍需硬编码）

由于 Kubernetes YAML 的限制，`multi-celeryworker.yaml` 中的 Init Container 仍然需要硬编码：

```yaml
initContainers:
  # Init Container 1: llmops
  - name: extract-llmops-code
    image: ${LLMOPS_IMAGE_REGISTRY}/${LLMOPS_IMAGE_PROJECT}/${LLMOPS_IMAGE}:${LLMOPS_TAG}
    ...
  
  # Init Container 2: incubator
  - name: extract-incubator-code
    image: ${INCUBATOR_IMAGE_REGISTRY}/${INCUBATOR_IMAGE_PROJECT}/${INCUBATOR_IMAGE}:${INCUBATOR_TAG}
    ...
```

**原因**：
- Kubernetes YAML 不支持动态生成资源
- 每个后端需要独立的 Init Container
- 合并逻辑需要知道所有后端名称

#### 3. 添加新后端步骤

**步骤1：编辑配置文件** `deploy-multi-celeryworker.conf`：

```bash
# 后端3: scrapy-service
BACKEND_scrapy_IMAGE="scrapy-service"
BACKEND_scrapy_TAG="1.0.0"
BACKEND_scrapy_IMAGE_REGISTRY="${DEFAULT_BACKEND_IMAGE_REGISTRY}"
BACKEND_scrapy_IMAGE_PROJECT="${DEFAULT_BACKEND_IMAGE_PROJECT}"
BACKEND_scrapy_CODE_EXTRACT_SOURCE_DIR="${DEFAULT_CODE_EXTRACT_SOURCE_DIR}"
BACKEND_scrapy_CODE_EXTRACT_DIRS="worker core services db models"
BACKEND_scrapy_CODE_EXTRACT_FILES="__init__.py"
```

**步骤2：修改 YAML 文件** `multi-celeryworker.yaml`：
- 添加新的 Init Container（extract-scrapy-code）
- 在合并逻辑中添加 `scrapy` 后端名称

**步骤3：更新队列配置**：

```bash
CELERY_QUEUES="llmops-queue,incubator-queue,scrapy-queue"
```

**步骤4：更新部署脚本** `deploy-multi-celeryworker.sh`：
- 添加 `SCrapy_*` 环境变量导出

### 优点

- ✅ **资源占用少**：只有一个 Worker Pod
- ✅ **统一管理**：所有任务在一个 Worker 中处理
- ✅ **配置格式统一**：易于扩展新后端

### 缺点

- ❌ **代码冲突风险**：不同后端的代码可能冲突（同名文件、同名任务）
- ❌ **配置复杂**：需要处理代码合并逻辑
- ❌ **调试困难**：问题定位困难
- ❌ **YAML 硬编码**：添加新后端需要修改 YAML 文件

### 未来扩展方案

#### 方案A：使用 Helm 模板（推荐用于多个后端）

**适用场景**：5+ 个后端，需要动态配置

**实现方式**：
1. 创建 Helm Chart
2. 使用 `values.yaml` 配置后端列表
3. 使用模板循环生成 Init Container

**示例 `values.yaml`**：
```yaml
backends:
  - name: llmops
    image: llmops-service
    tag: "1.0.0"
    extractDirs: "worker core services db models"
  - name: incubator
    image: incubator-service
    tag: "1.0.0"
    extractDirs: "worker core services db models"
```

**Helm 模板示例**：
```yaml
initContainers:
{{- range .Values.backends }}
  - name: extract-{{ .name }}-code
    image: {{ .image }}:{{ .tag }}
    ...
{{- end }}
```

**优点**：
- ✅ 完全动态，无需修改 YAML
- ✅ 配置集中管理
- ✅ 易于扩展

**缺点**：
- ❌ 需要引入 Helm
- ❌ 增加复杂度

#### 方案B：使用脚本生成 YAML

**适用场景**：需要完全控制生成过程

**实现方式**：
1. 创建 Python/Shell 脚本
2. 读取配置文件
3. 动态生成 YAML 文件

**优点**：
- ✅ 完全灵活
- ✅ 可以自定义生成逻辑

**缺点**：
- ❌ 需要维护生成脚本
- ❌ 增加构建步骤

## 方案3：多队列 + 多 Worker（混合方案）

不同后端使用不同队列，但可以共享部分 Worker。

### 架构图

```
后端服务 ──> RabbitMQ (多个队列)
              ├── llmops-queue
              ├── incubator-queue
              └── scrapy-queue

Worker 配置：
  - celeryworker-llmops: 监听 llmops-queue
  - celeryworker-incubator: 监听 incubator-queue
  - celeryworker-shared: 监听 shared-queue (通用任务)
```

### 实现

每个 Worker 配置不同的队列：

```bash
# celeryworker-llmops
CELERY_QUEUE="llmops-queue"

# celeryworker-incubator
CELERY_QUEUE="incubator-queue"

# celeryworker-shared (处理通用任务)
CELERY_QUEUES="shared-queue,common-queue"
```

## 方案4：共享代码库（长期方案）

将任务定义提取到独立的共享库，所有后端和 Worker 都使用这个库。

### 架构

```
共享代码库 (shared-tasks)
  ├── tasks/          # 任务定义
  ├── models/         # 数据模型
  └── utils/          # 工具函数

后端服务 ──> 引用 shared-tasks ──> 发送任务
                                    │
Worker ──> 引用 shared-tasks ──> 执行任务
```

### 实现

1. 创建共享任务库镜像
2. 后端和 Worker 都使用这个镜像
3. 通过 Python 包管理（pip install）引入

## RabbitMQ 和 Redis 部署说明

### RabbitMQ 部署

**推荐：单个 RabbitMQ + 多个队列**

- 所有 Worker 使用同一个 RabbitMQ 实例
- 每个 Worker 监听不同的队列（如 `llmops-queue`、`incubator-queue`）
- 队列之间天然隔离，互不影响
- 队列无需预先创建：RabbitMQ 会在 Worker 启动时自动创建

详细说明请参考：[RabbitMQ和Redis配置方案.md](../deploy-celeryworker-bff/RabbitMQ和Redis配置方案.md) 和 [RabbitMQ队列创建说明.md](RabbitMQ队列创建说明.md)

### Redis 部署

**推荐：单个 Redis + 结果键前缀**

- 所有 Worker 使用同一个 Redis 实例
- Celery 使用应用名称作为结果键前缀（如 `celery-task-meta-llmops-*`）
- 不同应用的结果键不会冲突

**可选：单个 Redis + 不同数据库**

- 使用同一个 Redis 的不同数据库（0, 1, 2...）
- 数据库之间完全隔离
- 注意：Redis 集群模式不支持数据库功能

详细说明请参考：[RabbitMQ和Redis配置方案.md](../deploy-celeryworker-bff/RabbitMQ和Redis配置方案.md)

## 推荐方案

### 场景1：后端任务差异大，需要隔离

**推荐：方案1（多 Worker Deployment）**

- 每个后端独立 Worker
- 配置简单，隔离性好
- 易于扩展和维护
- **RabbitMQ**：单个实例 + 多个队列
- **Redis**：单个实例 + 结果键前缀（或不同数据库）

### 场景2：后端任务相似，代码兼容

**推荐：方案2（多 Init Container）**

- 一个 Worker 处理多个后端
- 需要仔细处理代码合并
- 适合任务定义相似的后端
- 当前阶段（2-3 个后端）：使用硬编码方式
- 未来扩展（5+ 个后端）：迁移到 Helm 模板方案

### 场景3：需要灵活扩展

**推荐：方案3（多队列 + 多 Worker）**

- 按队列隔离
- 可以独立扩展某个队列的 Worker
- 配置相对复杂

### 场景4：新项目或可重构

**推荐：方案4（共享代码库）**

- 长期最佳方案
- 需要重构现有代码
- 适合新项目

# deploy-multi-celeryworker.conf

### YAML 硬编码说明

由于 Kubernetes YAML 的限制，`multi-celeryworker.yaml` 中的 Init Container 需要硬编码。这是当前阶段的折中方案，适合 2-5 个后端。

如果后端数量增加到 5+ 个，建议迁移到 Helm 模板方案。

### 添加新后端步骤

1. **编辑配置文件** `deploy-multi-celeryworker.conf`
2. **修改 YAML 文件** `multi-celeryworker.yaml`
3. **更新队列配置** `CELERY_QUEUES`
4. **更新部署脚本** `deploy-multi-celeryworker.sh`

详细步骤见方案2的实现步骤部分。

## 总结

- **推荐使用方案1**：多 Worker Deployment，简单可靠（适用于不同后端任务差异大的场景）
- **当前实现方案2**：多 Init Container，资源占用少（适用于后端任务相似、代码兼容的场景）
- **如果资源紧张**：考虑方案2，但需要仔细处理代码合并
- **长期规划**：考虑方案4，提取共享代码库
- **配置格式**：已改进为统一格式 `BACKEND_<name>_<property>`，易于扩展
- **YAML 文件**：由于 Kubernetes 限制，仍需硬编码，但结构清晰
- **未来方向**：如果后端数量增加，建议迁移到 Helm 模板方案

根据你的实际需求选择合适的方案。
