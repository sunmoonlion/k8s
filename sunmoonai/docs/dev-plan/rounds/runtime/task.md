## 0. 一句话

上一轮（`refact-fable`）把架构分成「开发 Profile / 产品 Profile」两层，**这是个假分叉**。
本轮要产出的方案里只有**一个产品运行时**，它对应唯一状态机；今天的开发是跑在它上面的
**一个 Task Profile**，特殊之处只在于我们正用现有 AI 助手开发这个运行时本身。

### 1.2 所有者的四条推翻性判断（2026-09-05）

上一轮的结构性错误**五家和裁决方都没抓到**，是所有者在冻结之后指出的。原话要点：

1. **没有「开发过程」和「产品运行时」两个 Profile。只能有一个产品运行时，它和唯一状态机对应。**
2. **我们之前所讲的开发，只是这个运行时的一个 Task Profile。**特殊仅仅特殊在：我们现在利用现存的
   AI 助手来开发产品运行时**本身**。运行时开发成功后，后续的产品开发工作也通过它直接进行——
   只不过是**由运行时调用现有 AI 助手**，而不是像现在这样由人手动调用。
3. **人的角色就是产品运行时中人的角色。**它特殊在：当组织者把规划、分发等提交人审核时，
   人可以**全部否定、部分否定，或让它采用人的方案**——这样就和现在的手工模式**完全等效**。
4. **一个一直没触及的问题**：产品运行时的 agent，其执行环境可能与现有 AI 助手不同，
   因而读写仓库文件以及展示方式也可能不同——前者可能**通过**沙箱，后者**内部是**沙箱，
   而产品运行时本身以 SDK 或 CLI 模式调用。

### 1.3 这一刀砍在哪：`refact-fable.md` 的自证

> 按场景另造同构 Profile 与按场景另造状态词是同一类膨胀。

A 与 B 差的也只是那五格的**取值**（持久层 git↔PG、执行者、通道、guard、状态判定），结构相同。

**更难看的是词的冲突**：内核 `working/request-lifecycle.md:103-104` 已经定义了两个 Profile——

| 词 | 内核定义 | `refact-fable.md` 用法 |
| --- | --- | --- |
| Task Profile | 某类用户 Task 的输入、输出、验收、证据和策略**契约** | 未使用 |

这正是 `refact-fable.md` §1.2 自己诊断的病（「supervisor 已有三套同名物」）在 `Profile` 这个词上复发，
且是它自造的第三个含义。而内核对此已有明文：

- `request-lifecycle.md:505`「新增领域应**新增 Task Profile 和相容 Agent Profile，不修改通用状态语义**」
- `:580` 反模式表「Profile 修改通用状态机 → 新领域产生第二套生命周期」

## 2. 立项理由与它的边界

本轮方案要服务的是这个项目本身的存在理由，所以先把它写清楚，各家的方案不得与之矛盾。

### 2.1 理由一：并行竞争（成立，但边界窄）

上一轮的实测收益（可复核，原文在 `rounds/refact-fable/reviews/`）：

- luna O-L1 抓出裁决方 F-EXEC-02 的改判与其自己那张三档表**自相矛盾**；
- qwen 用三条命令推翻裁决方的一处错误归属（D-Q6 → D-K8）；
- cursor D1 抓到 ⑥→⑦ 隐含 `WAITING → SUCCEEDED`——内核没有这条边，**只查词表抓不到**；
- 裁决方抓到 qwen 拿休眠代码 `profiles.py:36-41` 当能力证据，九份评审无一发现；
- 任务书里「RunBudget 引用数为 0」的错误无人抄袭，三家独立写对。

收益类型集中在**内部矛盾与假证据**——单个助手的结构性盲区（它跟自己不矛盾）。

**边界（§1.2 就是证据）**：竞争评比抓**框架内**的错，抓不了**框架本身**。cursor 离得最近
（杀掉第三个 Profile），但没把同一把刀转向 A/B。框架由目标持有者抓。

**所以并行竞争是 T2 档的工具，不是默认档。**档位体系已经把这件事说对了。

### 2.2 理由二：专业 agent（决定性）

通用助手是**封闭 harness**。用 `codex exec` 这类通道做不到四件事：

1. 给它一个按本项目口径查财务库的工具；
2. 把它约束在既定分析方法内；
3. 拦住数据流出边界；
4. 钉版本、可复现——审计场景的硬要求。

财务分析产品每一条都需要。所以对理由二而言，运行时不是优化，是**唯一通路**。

### 2.3 未写出但更强的一条：运行时的对象就是产品的对象

Task / Attempt / Interaction / Artifact / Event / Side Effect / Delivery——
一次长跑的财务分析、失败重试、把分析计划交人审批、证据留痕、结果交付，需要的是**同一套对象**。
所以建运行时不是「产品之前的开销」，它**就是产品的内核**；开发只是它第一个 Task Profile。

### 2.4 所有者补充的一条，本轮按**约束**处理，不按理由处理

所有者原话：**「鉴于我几乎所有工作都要 AI 帮忙，就这点来说，也会大大节省我的手工成本，
即使开发收益为零。」**

这条成立，但**不能写成立项理由就完了**——理由写进背景改变不了造出来的东西，约束会。原因是它有个陷阱：

**手工成本高的地方，不是任务多的地方。** 开终端敲一句给助手，成本约十秒。运行时若对这类任务
也收全套手续费（建工单、路由落账、供给工作区、分发、收集、记事件），**净成本高于手工**。

| 运行时省得多 | 省不到，甚至更贵 |
| --- | --- |
| 跨会话续接（现在每次重讲上下文） | 一次性提问 |
| 留痕（决定了什么、为什么，现在没记录） | 单文件改动 |
| 中途审批（现在人要盯着） | 一句话能说完的活 |
| 并行多家（T2） | |
| 同形状反复跑的活 | |

准确说法：**运行时省的不是「调用助手」的成本，是 orchestration + 记忆 + 留痕 + 审批的成本。**

**这里有个会杀死项目的失败模式**：T0 走运行时若比开终端贵，人就绕过它；一绕过账本就有洞；
账本有洞，运行时存在的理由就没了。**所以它不是顺带的好处，是生存条件。**
`refact-fable.md` §8 第 5 条（T0 的 `APPROVAL` 触点 = 0）只管住了审批一项，没管总开销。

配套一个观察值（不是判据）：**绕过率**——哪类任务实际被绕过，说明运行时在那一类上开销超过价值。
按既有纪律登记进 `rulings.md`，不自动触发任何动作。

### 2.5 三条已登记的风险（方案不得回避）

1. **范围会漂**：失败模式是做成通用 agent 平台。差异化在**领域对象 + 人的权力模型**，不在编排。
2. **拿开发当第一个 Task Profile 有陷阱**：开发的验收**机械且便宜**（测试、门禁、diff），
   财务分析的验收**判断且昂贵**。验收机制只对着开发设计，最难的一半没解决。
3. **现在这套很重**（回执仓、签名、权力表、三道边界）。单用户系统扛这个重量，
   只有当**审计链是产品需求**时才划算。

## 3. 本轮范围：三块 + 一个贯穿必答项

### 3.1 P1 — 只有一个运行时，开发是一个 Task Profile

要求方案给出：

- **对象层**：一个运行时 + 唯一状态机（`request-lifecycle.md @ 70a7dd50`，sha256[:16] `6fcd3973ede30b88`）；
  「开发」落为一个 **Task Profile**（给出 `profile_id`、输入、输出、验收、证据、策略契约）；
  五家助手落为五个 **Agent Profile**。
- **bootstrap 与目标态的关系**：今天的 orchestrator 是人 + shell 脚本，明天是运行时本身。
  这是**同一个 Task Profile 的两种 orchestrator 实现**，不是两层架构。
  git 载体那套是**脚手架，要拆的**——请明确说明拆除条件。
- **等效判据**（本轮的核心验收方式）：同一个 Task Profile 的一次执行，
  在手工模式与运行时模式下产生的**轨迹**逐条对应。

  ```text
  轨迹 = Task 状态序列
       + 每个 Attempt 的状态序列
       + Interaction 序列（含出向载荷与入向响应）
       + Artifact 版本序列（含每版作者）
  ```

  **允许不同**：载体（文件 ↔ 表）、orchestrator 实现（人+脚本 ↔ 服务）、执行者可观测粒度。
  **不允许不同**：状态、边、对象、Interaction 形状、谁在哪条边上有权。

  这把 `refact-fable.md:243` 那句方法论（「先在这一层跑通，再往下实现」）从口号变成可机械比对的东西。

### 3.2 P2 — Interaction 必须是双向且带载荷的

所有者第 3 条判断（人可全部否定 / 部分否定 / 以自己的方案替代）**内核现在装不下**。
`request-lifecycle.md:257` 的 Interaction 绑定字段是：

```text
task_id, interaction_id, expected_state_version
question_or_action, audience, expires_at
resume_token_hash, idempotency_key, consumed_at
resume_target
```

**没有响应载荷**——响应只有「消费令牌」一个动作，是布尔的。缺的是两个方向：

| 方向 | 现有 | 缺的 |
| --- | --- | --- |
| 出向 | `question_or_action`（一句话） | 展示**哪个 Artifact 的哪个版本**、以什么**渲染形式**（diff / 全文 / 结构化摘要）、人**可编辑的范围** |
| 入向 | `resume_token_hash` + `consumed_at`（布尔） | `approve / reject / amend` 三值 + amend 载荷；该载荷成为一个新 Artifact 版本（作者 = principal），并成为**下一次 Attempt 的输入** |

两点必须在方案里说清：

- **不能绕成「建新 Task」**：`:297` 规定建新 Task 的条件是「修改目标、口径、授权范围或 Profile 版本」，
  而部分否定一份分发方案时目标没变。
- **这不是开发期特有的**：财务分析 agent 交一份分析计划给人审、人改两条让它照改，形状完全相同。
  所以这是**内核缺口**，按 `request-lifecycle.md:627` 的修订纪律走**规范修订工作单元**，
  方案须给出该工作单元的边界、影响分析与迁移方案。

**并请注意**：这三件事今天在手工模式里**全是隐式的**——「看哪个」靠 worktree 路径、
「怎么看」靠人跑 `git diff`、「能做什么」靠通知里的自然语言。所以手工模式**看起来**在跑，
实际上没有可搬运的形状。这正是等效判据逼出来的东西。

### 3.3 P3 — 执行者的可观测粒度进 Agent Profile，及其对证据权威性的后果

所有者第 4 条判断的展开。真正的差别不是「有没有沙箱」，是**运行时能看见多细的粒度**：

| | 运行时自己的 agent（SDK 腿） | 现有 CLI 助手 |
| --- | --- | --- |
| 沙箱由谁提供 | **运行时提供**，运行时定策略 | **助手自带**，运行时管不着内部 |
| 运行时能看见 | 每一次工具调用 | argv / stdin / stdout / 退出码 / 事后的文件系统 |
| 读写记账 | 逐次落 Event | 只能事后 diff |
| `F-EXEC-01`（只用 Agent Profile 允许的工具，`:381`） | 可执行 | **执行不了**，只能事后审计 |
| 副作用拦截 | 事中，在工具层 | 事中拦不住，只剩外层边界 |

方案必须处理由此产生的三个后果：

1. **可观测粒度是 Agent Profile 的登记字段，且决定证据的权威性。**
   进程粒度的执行者，自报一律不采信，证据必须由运行时从工作区**重新推导**（diff、复跑命令）。
   `refact-fable.md:238`「`RUNNING` 目前判不了」现被归因为 git 载体的缺陷——**归因错了**：
   换成 PostgreSQL 一样判不了，因为看不见的不是账本，是进程内部。这是**执行者属性**。
2. **`refact-fable.md` §3.13 的三道边界不是 bootstrap 期的临时安全措施，是架构组件。**
   CLI 助手内部 push、内部出网，事中拦不住，只剩外层：进程能看见文件系统哪个子树、
   env 里有没有凭据、出网走不走。产品运行时调 CLI 助手时**一样需要**。
   现在它被归在「bootstrap 威胁模型」里，会随脚手架一起被拆掉。
3. **`refact-fable.md` §3.7 的「独占工作区」在 CLI 腿上是约定，不是隔离。**
   provision 函数两边一样，但 SDK 腿是挂进沙箱（真隔离），CLI 腿是在宿主建目录再把路径传给进程——
   那个进程看得见整个文件系统。方案须如实声明，不得让两边看起来强度相同。

### 3.4 必答 Q（贯穿三块，每家单独成节回答）

**不答或答成表态，判交付不完整。**

运行时相对手工直接调用助手，存在一条**开销盈亏线**。请给出：

1. **分类规则**：具备哪些特征的任务，走运行时净成本更低；哪些更高。
   至少一条规则必须**机械可判**（由工单字段或任务特征直接判定，不靠「读起来对」）。
2. **反例**：至少举一类**你认为走运行时反而更贵**的任务，并说明贵在哪一步。
   **不接受「都值得走」——给不出反例的回答按未回答处理。**
3. **T0 开销上界判据**：提出一个使 T0 不被绕过的可判上界。

4. **绕过的可观测性**：绕过发生在运行时之外，账本天然看不见。你的方案怎么让它可观测？
