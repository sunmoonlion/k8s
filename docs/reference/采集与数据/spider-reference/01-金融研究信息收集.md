## 1. Scrapling 是什么定位？

Scrapling 官方定位是一个 adaptive Web Scraping framework，从单次请求到全规模 crawl 都可以处理。它强调几个特点：选择器能适应网页结构变化、支持类似 Scrapy 的 Spider API、支持并发、限速、暂停恢复、多 session、代理轮换、动态页面抓取，以及 MCP/AI 辅助抽取。

它目前热度很高。GitHub 页面显示约 58.1k stars、5.6k forks、1,447 commits；PyPI 显示最新版本为 0.4.8，发布时间是 2026 年 5 月 11 日，许可证为 BSD 3-Clause，要求 Python >=3.10。

所以从项目活跃度、文档、许可证、现代爬虫能力来看，它值得关注。

## 2. 它对你的金融研究项目有什么价值？

我认为 Scrapling 对你最有价值的地方有 4 个。

### 第一，适合“页面经常改版”的资讯网站

金融资讯网站、公司 IR 页面、地方监管网站、政策页面经常改版。Scrapling 的核心卖点之一是 adaptive scraping，也就是通过相似度算法在页面结构变化后重新定位元素。官方文档提到它支持 smart element tracking、flexible selection、find similar elements 等能力。

这对你很重要，因为金融资讯采集最怕的问题不是第一次抓不到，而是：

今天能抓，三周后页面结构一变，标题、时间、正文全错。

Scrapling 可以作为这类场景的备选工具。

### 第二，适合复杂动态页面

它内置 Fetcher、StealthyFetcher、DynamicFetcher 等抓取方式，动态页面抓取基于 Playwright 的 Chromium / Google Chrome。

所以对于一些普通 requests 抓不到、必须渲染 JS 的页面，它比单独写 Playwright 可能更省事。

### 第三，适合 AI/Agent 辅助采集

Scrapling 支持 MCP server，用于 AI-assisted Web Scraping，把目标内容先抽取出来再交给 Claude/Cursor 等工具，从而减少 token 成本。

这和你的方向比较匹配：你后面大概率会做“爬取 + 清洗 + 入库 + RAG + 智能体分析”。Scrapling 的 MCP 思路值得观察。

### 第四，开发体验比纯 Playwright 轻一些

Scrapling 有类似 Scrapy/Parsel 的 CSS、XPath、伪元素选择方式，也有 Spider API、JSON/JSONL 导出、交互式 shell、CLI。

所以它不只是一个浏览器自动化工具，而是介于 Scrapy + Playwright + 自适应选择器 之间的现代采集框架。

## 3. 但它不适合作为你的主框架

我的判断是：纳入，但不能替代 Scrapy。

原因有几个。

### 第一，Scrapy 仍然更适合长期工程化

Scrapy 是成熟的高层级网页抓取框架，GitHub 页面显示约 62.1k stars、11.6k forks、11,117 commits，官方说明它用于从网站抽取结构化数据，跨平台，要求 Python 3.10+，由 Zyte 和社区维护。

你的金融研究项目需要长期跑任务、做调度、增量、去重、失败重试、pipeline、日志、存储，这些场景 Scrapy 生态更成熟。

### 第二，Scrapling 不是金融资讯专用项目

它没有内置东方财富、财联社、证券时报、巨潮、交易所、公司 IR、券商研报等金融源。它是一个通用爬虫框架，不是金融数据源库。

所以你仍然需要自己维护：

公司表、来源表、栏目表、列表页规则、详情页规则、发布时间规则、正文规则、是否需要 JS、是否进入 RAG、版权/合规备注。

### 第三，它的“反检测/绕过”定位有合规风险

Scrapling 官方文档和 README 都强调 stealth、fingerprint spoofing、Cloudflare Turnstile 等能力。 另外，WIRED 近期报道也提到，Scrapling 被一些用户用于绕过反机器人系统，Cloudflare 也在持续针对相关行为做防护更新。

对你的金融研究项目，尤其是未来如果要公司内部或商业化使用，我建议明确一条红线：

>
Scrapling 只用于公开、授权、合规的信息源；不要把它作为绕过登录、付费墙、验证码、反爬限制的工具。

金融研究资料涉及版权、账号授权、交易所条款、研报版权，合规风险比普通网页爬虫更高。

### 第四，它当前仍显示 Beta 状态

PyPI 分类里标注 Development Status 为 4 - Beta。 这不代表不能用，但说明在生产主链路里要谨慎，最好先做小范围验证。

## 4. 我建议你这样纳入技术栈

你原来的技术栈可以调整成这样：

| 层级 | 工具 | 角色

| 数据 API 层 | AkShare、TuShare、SEC API、yfinance、Alpha Vantage | 行情、财务、事件、基础数据

| 主爬虫层 | Scrapy | 公告列表、新闻列表、IR 页面、政策栏目

| 动态页面层 | Playwright | JS 渲染、交互页面

| RAG 友好抓取层 | Crawl4AI | 网页转 Markdown、结构化抽取、Agent/RAG 数据

| 正文抽取层 | Trafilatura | 新闻正文、标题、作者、发布时间抽取

| 增强采集层 | Scrapling | 页面频繁变化、复杂动态页面、快速原型、AI/MCP 辅助采集

| 监控层 | changedetection.io | 公司官网、交易所栏目、政策页变更监控

| 存储层 | PostgreSQL/MySQL + MinIO + OpenSearch/Elasticsearch + RAGFlow/WeKnora | 元数据、原文、全文检索、知识问答

也就是说，Scrapling 的定位不是“替代 Scrapy”，而是：

>
Scrapy 的增强插件式工具 / Playwright 的封装替代方案 / Crawl4AI 之外的复杂网页采集补充。

## 5. 适合优先测试的场景

# 金融研究项目信息收集体系研究与落地方案

## 一、总体判断：金融研究的信息收集，核心已经不是“爬网页”，而是“可信数据资产建设”

金融研究项目真正需要的不是简单抓网页，而是建立一套长期可维护的资料体系：

>
信息源发现 → 数据采集 → 原文留存 → 结构化元数据 → 正文/表格解析 → 全文检索 → 向量化 → RAG/智能体分析 → 证据回溯。

现在主流金融研究系统越来越重视三件事：

第一，来源可信。官方披露、交易所、监管机构、公司公告、授权数据源的优先级高于普通新闻网页。比如 SEC EDGAR 已经提供 filings history 与 XBRL 财务数据的 REST JSON API，不需要 API key，并且 filings 与 XBRL 数据会持续更新；这类官方接口应优先于网页硬爬。

第二，数据可追溯。RAG 不是只要把 PDF 丢进去，而是要能追到：这句话来自哪家公司、哪份公告、哪个日期、哪一页、哪个表格、哪个段落。

第三，结构化与非结构化并重。行情、财务指标、估值、宏观数据适合结构化数据库；年报、公告、研报、新闻、电话会纪要适合全文检索 + 向量检索；事件、观点、风险、催化剂则适合抽取成结构化事件表。

所以，金融研究信息收集的最终目标不是“爬取成功”，而是形成：

公司资料库 + 公告库 + 研报库 + 新闻库 + 事件库 + 财务指标库 + 原文证据库。

# 二、金融研究应收集哪些信息：建议分成 10 大类

## 1. 公司基础信息

这是所有数据关联的底座。没有公司主数据，后面新闻、公告、研报、行情都会乱。

应收集字段包括：证券代码、公司简称、公司全称、英文名、市场、交易所、行业分类、上市日期、主营业务、控股股东、实际控制人、注册地址、办公地址、官网、IR 页面、董秘联系方式、历史简称、退市/暂停上市状态等。

用途是做实体统一。比如“贵州茅台”“茅台”“600519”“Kweichow Moutai”要映射到同一个公司实体。

优先来源：交易所、巨潮、Wind/iFinD/聚源、AkShare、TuShare、公司官网、SEC submissions API。AkShare 目前 GitHub 显示约 20.5k stars，定位为开源财经数据接口库，适合作为 A 股数据 MVP 的重要来源。

## 2. 公告与监管披露

这是金融研究最核心、最可信的信息。

应收集内容包括：年报、半年报、季报、招股书、上市公告书、重大资产重组、并购、股权激励、回购、减持、质押、诉讼仲裁、担保、关联交易、监管问询、处罚、交易所函件、澄清公告等。

这一类资料要保留原始 PDF/HTML，同时抽取标题、发布时间、公告类型、公司代码、附件、正文、表格、页码、章节。

美股方向，SEC EDGAR API 是标准主源，它提供 company submissions、company facts、company concept、frames 等接口，并且有 nightly bulk ZIP 文件，适合大规模同步。 A 股方向，巨潮资讯、沪深北交易所公告、公司 IR 页面是主线。

## 3. 财务报表与基本面数据

包括三张表、财务指标、杜邦分析、盈利质量、现金流、偿债能力、成长性、营运能力、分红、资本开支、应收账款、存货、商誉、合同负债、研发费用等。

这类数据应该尽量结构化入库。原因是：RAG 很适合解释文本，但不适合稳定做跨公司、跨年度、跨指标计算。

建议把财务数据分成三层：

第一层是原始披露值，如营业收入、归母净利润、经营现金流、资产负债率。

第二层是衍生指标，如毛利率、净利率、ROE、周转率、现金收入比。

第三层是研究标签，如“收入增长但现金流恶化”“商誉占净资产较高”“存货增速高于收入增速”。

TuShare GitHub 页面将其定位为中国股票历史数据抓取工具，适合作为 A 股历史数据和基础指标补充，但正式项目里最好与公告原文或授权数据库交叉校验。

## 4. 行情、估值与交易数据

包括日线、分钟线、复权价、成交量、成交额、换手率、市值、市盈率、市净率、指数成分、行业指数、ETF、北向资金、龙虎榜、融资融券、期权、期货等。

这类信息主要服务于：

公司表现跟踪、事件前后股价反应、估值比较、量化因子、新闻情绪与市场反应分析。

A 股可考虑 AkShare、TuShare、交易所公开数据；海外市场可用 yfinance、Alpha Vantage、Polygon、Nasdaq Data Link 等。yfinance 适合研究验证和快速原型，但其 GitHub 页面说明它是下载 Yahoo Finance 数据的库，不应把它当成正式商业项目的唯一主数据源。

## 5. 新闻与财经资讯

包括财经媒体新闻、公司新闻、行业新闻、政策新闻、突发事件、管理层变动、产品动态、诉讼、监管、舆情等。

这是金融研究里最容易“看起来有用、实际很乱”的部分。新闻采集不能只追求数量，而要关注：

发布时间是否准确、是否重复转载、是否有原始来源、是否能关联公司、是否能识别事件、是否能判断影响方向。

中文财经资讯可重点关注：财联社、证券时报、中国证券报、上海证券报、经济参考报、第一财经、每日经济新闻、21 财经、界面新闻、澎湃财经、东方财富、同花顺财经、雪球、交易所新闻、监管机构新闻等。

但要注意，很多财经资讯存在版权和反爬限制。建议新闻只作为辅助证据，核心研究结论仍以公告、财报、研报、监管披露为主。

## 6. 研报与机构观点

包括券商公司深度、行业深度、点评报告、盈利预测、评级调整、目标价、调研纪要、电话会纪要等。

这类资料价值很高，但合规风险也最高。很多研报受版权、账号授权、机构数据库条款限制。技术上可以解析 PDF，业务上必须明确来源是否合法。

建议不要一开始做“全网研报爬虫”，而是优先做：

公司内部已有研报上传库、合法授权研报库、公开可下载研报、公司公告里的投资者交流材料、交易所互动问答、电话会公开材料。

研报入库时应抽取：报告标题、机构、分析师、发布日期、公司、行业、评级、目标价、盈利预测表、核心观点、风险提示、关键假设、可比公司、估值方法。

## 7. 宏观、政策与产业信息

包括宏观经济、货币政策、财政政策、产业政策、医保/药品政策、房地产政策、出口管制、关税、利率、汇率、商品价格、PMI、CPI、PPI、社融、就业等。

这类数据对行业研究和策略研究很重要。尤其你如果关注医药、A 股、政策周期，那么政策信息要单独建库。

建议把政策类信息拆成：

政策原文、政策解读、影响行业、影响公司、发布时间、发文机构、政策级别、执行时间、废止/修订状态。

## 8. 投资者交流与问答

包括互动易、上证 e 互动、公司 IR 会议纪要、业绩说明会、电话会 Q&A、投资者调研记录、股东大会问答等。

这类数据很适合做“管理层表述变化分析”。比如同一家公司过去 8 个季度对“产能”“价格”“库存”“订单”的表述是否发生变化。

这类信息不要只做全文 RAG，还应抽取成：

问题、回答、回答人、日期、关键词、涉及业务、管理层态度、是否首次提及、是否与公告矛盾。

## 9. 舆情与社交数据

包括雪球、东方财富股吧、Reddit、X/Twitter、知乎、公众号、论坛等。

这类信息噪声大、合规复杂，但可以用于：

短期情绪、事件发酵、谣言追踪、投资者关注点、风险预警。

建议只作为弱信号，不作为正式研究结论来源。并且要避免抓取需要登录、付费、违反平台条款的数据。

## 10. 事件与知识图谱数据

最终真正有价值的不是“文章数量”，而是能抽取出结构化事件：

公司 A 发布年报、收入增长 20%、毛利率下降 5pct、原因是原材料涨价。

公司 B 被监管问询，问题涉及收入确认、关联交易、存货跌价。

公司 C 获批新药，预计影响未来收入。

公司 D 管理层在业绩会上首次提到海外扩张放缓。

这类事件可以形成：

公司—事件—时间—来源—影响方向—证据原文—置信度—后续跟踪。

这是金融研究智能体的关键资产。

# 三、主流信息收集方式：建议做“六层采集架构”

## 第一层：官方 API / 授权数据源

优先级最高。适合采集公告、财务、行情、监管、宏观等稳定数据。

典型来源包括 SEC EDGAR API、交易所、监管机构、Wind、iFinD、聚源、Bloomberg、FactSet、Refinitiv、Alpha Vantage、Nasdaq Data Link 等。

这类数据的优点是稳定、可追溯、结构化程度高。缺点是覆盖范围有限或成本较高。

你的项目如果要做 MVP，可以用开源接口先跑通；如果未来用于正式研究、内部生产或商业化，关键数据最好切换到授权数据源。

## 第二层：开源金融数据接口

适合快速搭建研究原型。

A 股方向：AkShare、TuShare。

海外方向：yfinance、Alpha Vantage、SEC API。

量化方向：Qlib、FinRL-Meta、backtrader、vn.py 等可作为后续扩展。

这类工具的定位是“研究加速器”，不是“最终可信源”。也就是说，它们适合帮你快速验证分析逻辑，但重要结论仍要回到公告、财报、交易所或授权数据源确认。

## 第三层：通用爬虫框架

这是你项目的采集主干。

我建议主框架仍然选 Scrapy。Scrapy 官方 GitHub 页面说明它是用于从网站抽取结构化数据的跨平台 web scraping 框架，Python 3.10+，由 Zyte 和社区维护；目前 GitHub 显示约 62.3k stars 和 11.7k forks，成熟度和生态仍然非常强。

Scrapy 适合做：

公告列表页、新闻列表页、公司 IR 页面、监管栏目、政策栏目、分页抓取、增量抓取、失败重试、Pipeline 入库、日志、任务调度。

它不是最“AI 新潮”的工具，但它最适合长期工程化。

## 第四层：动态页面与复杂页面采集

金融网站经常使用 JS 渲染、动态接口、反爬策略、分页接口、异步加载。这类页面单靠 requests 或 Scrapy 不一定够。

可以使用：

Playwright：处理 JS 渲染、点击、滚动、登录态内页面。

Crawl4AI：把页面转为 LLM/RAG 友好的 Markdown。

Scrapling：处理页面结构频繁变化、自适应选择器、复杂页面快速原型。

Firecrawl：适合 API 化搜索、抓取、网页转 Markdown/结构化数据。

Crawl4AI 的 GitHub 页面显示约 68.9k stars，定位为 open-source LLM friendly web crawler & scraper，比较契合你后续 RAG/智能体方向。

Scrapling 我建议纳入，但定位为“增强组件”，不是替代 Scrapy。它官方 GitHub 页面将其定位为 adaptive web scraping framework，适合从单次请求到 full-scale crawl 的场景；但它不是金融资讯专用项目，也不应被用于绕过付费墙、验证码或平台限制。

## 第五层：正文抽取与文档解析

网页抓下来后，不等于可用。你还需要抽取：

标题、正文、作者、发布时间、来源、栏目、标签、图片、表格、附件、PDF 链接。

Trafilatura 很适合做网页正文与元数据抽取。它的 GitHub 页面定位为 Python/命令行工具，可用于 web 文本和元数据收集，支持 crawling、scraping、extraction，并可输出 CSV、JSON、HTML、Markdown、TXT、XML。

PDF/研报/公告解析建议单独处理。可考虑：

PyMuPDF / pdfplumber：PDF 文字和表格。

MinerU / Marker / Unstructured：复杂文档解析。

PaddleOCR：扫描件 OCR。

Camelot / Tabula：表格抽取。

自定义规则：年报章节、财务表、风险提示、管理层讨论。

## 第六层：变更监控与触发式采集

金融信息并不是所有页面都需要每天全量抓。很多重要信息来自页面变化。

changedetection.io 适合监控：

公司官网 IR 页面、交易所公告栏目、监管政策页面、医保政策页面、行业协会通知、产品价格页面、招标采购页面。

它的 GitHub 页面定位为网页变化检测、网页监控和变化提醒工具，适合做“哨兵系统”。

建议做法是：

changedetection.io 发现页面变化 → 触发 Scrapy/Crawl4AI 抓取 → 入库 → 生成事件 → 推送给研究员或进入 RAG。

# 四、GitHub 项目重新分级：哪些应纳入，哪些只做参考

## A 级：建议纳入主技术栈

| 项目 | 定位 | 纳入理由 | 项目角色

| Scrapy | 主爬虫框架 | 成熟、稳定、生态强、适合长期工程化 | 主采集框架

| AkShare | A 股财经数据接口 | 快速获取行情、宏观、市场数据 | A 股数据补充

| TuShare | 中国股票历史数据 | 股票/期货数据补充 | 基础金融数据补充

| Trafilatura | 网页正文抽取 | 新闻正文、标题、时间、元数据抽取 | 文本清洗层

| Crawl4AI | LLM/RAG 友好网页抓取 | 输出 Markdown，适合 RAG/Agent | RAG 网页采集层

| Playwright | 动态页面处理 | JS 页面、滚动、点击、异步加载 | 动态页面工具

| changedetection.io | 页面变化监控 | 监控官网、政策页、公告页变化 | 触发器/哨兵

| PostgreSQL/MySQL | 元数据主库 | 存公司、来源、任务、文档目录、事件 | 业务主库

| MinIO | 原文对象存储 | 存 PDF、HTML、截图、附件 | 原文库

| OpenSearch/Elasticsearch | 全文检索 | 标题、正文、公告、研报检索 | 搜索层

| RAGFlow/WeKnora | 知识问答 | 面向文档问答和研究辅助 | RAG 层

## B 级：建议纳入增强组件

| 项目 | 定位 | 适合场景 | 是否纳入

| Scrapling | 自适应网页采集 | 页面频繁改版、复杂详情页、快速原型 | 纳入增强层

| Firecrawl | API 化网页抓取 | 快速网页转 Markdown/JSON，低代码 | 看许可证和部署要求后纳入

| Newspaper3k | 新闻抽取 | 快速原型、简单新闻站 | 可备选

| Fundus | 新闻抽取框架 | 英文/部分预定义新闻源 | 可参考，不适合作中文财经主力

| OpenEDGAR | SEC 研究数据库框架 | 美股 EDGAR 数据库建设参考 | 美股方向纳入参考

OpenEDGAR 虽然较老，但其论文明确说它可以基于 SEC EDGAR 构建研究数据库，包括抓取 index/filing、构建 form type 和 filer 元数据、CIK/ticker/industry 映射、抽取 filing 内容和元数据、搜索 filing 文档内容；如果你做美股公告研究，它的设计思路很值得参考。

## C 级：暂不作为核心，但可关注

| 项目 | 原因

| ScrapeGraphAI | 偏 LLM 网页结构化抽取，适合后期实验

| FinRL-Meta | 偏量化强化学习，不是资讯采集主干

| Qlib | 偏量化研究平台，不是新闻/公告采集主干

| LangChain / LangGraph | 用于后续智能体编排，不是采集层

| RPA 工具 | 可处理少量网页，但不适合大规模稳定采集

# 五、建议的系统架构

可以设计成 8 个模块。

## 1. Source Registry：信息源注册中心

这是非常关键的一张表。不要把采集规则写死在代码里。

建议字段：

source_id、source_name、source_type、country、market、website、section_url、data_category、priority、update_frequency、need_js、need_login、allowed_by_terms、robots_policy、copyright_note、parser_type、enabled、last_checked_at。

示例：

东方财富-公司新闻、证券时报-公告解读、巨潮-公告、沪深交易所-监管函、公司官网-IR 页面、国家医保局-政策通知、SEC EDGAR-submissions。

## 2. Company Master：公司主数据

字段：

company_id、ticker、exchange、market、short_name、full_name、english_name、industry、sub_industry、listed_date、status、website、ir_url、cik、isin、lei、aliases。

重点是 aliases。中文财经资讯里公司别名特别多，必须建别名表。

## 3. Crawler Task：采集任务表

字段：

task_id、source_id、task_type、url、method、params、headers_profile、schedule_cron、priority、status、retry_count、last_run_at、next_run_at、error_message。

## 4. Raw Archive：原文归档

原文不要丢。建议 MinIO 存：

HTML、PDF、图片、附件、截图、原始 JSON、解析前文本。

同时在数据库里保存：

raw_id、url、source_id、fetch_time、content_hash、storage_path、mime_type、status_code、encoding、file_size。

## 5. Document Metadata：文档元数据

字段：

doc_id、raw_id、title、source、publish_time、crawl_time、author、company_id、tickers、category、subcategory、language、url、canonical_url、attachment_url、doc_type、period、fiscal_year、report_type、valid_time、version、hash。

## 6. Parsed Content：解析内容

字段：

doc_id、plain_text、markdown_text、html_cleaned、tables_json、images_json、sections_json、page_map、quality_score、parser_version。

这里要注意：RAG 最好用 Markdown + section，而不是一整篇长文直接入库。

## 7. Event Extraction：事件抽取

字段：

event_id、company_id、event_type、event_time、doc_id、source_sentence、impact_direction、impact_area、confidence、entities、metrics、follow_up_required。

事件类型可以包括：

业绩增长、业绩下滑、毛利率变化、订单变化、产品获批、监管问询、处罚、回购、减持、并购、股权激励、产能建设、政策利好、政策利空、行业价格变化、诉讼、管理层变动。

## 8. Search & RAG Index：检索与问答层

建议双检索：

OpenSearch/Elasticsearch：用于关键词、标题、公司、日期、公告类型检索。

向量数据库/RAGFlow/WeKnora：用于语义问答、跨文档总结、研究报告生成。

不要只依赖向量库。金融研究里“精确检索”非常重要，比如要查“2024 年年报”“商誉减值”“问询函”“某公司 2023 年收入”。

# 六、采集策略：不要全网乱抓，要按优先级推进

## 第一优先级：公告与年报

原因：可信度最高、对研究结论最关键。

目标：

A 股：巨潮、沪深北交易所、公司官网 IR。

美股：SEC EDGAR API。

产出：

公告目录库、PDF 原文库、公告正文库、财务表格库、事件库。

## 第二优先级：公司新闻与行业新闻

原因：用于跟踪事件、舆情和催化剂。

目标：

先选 10–20 个高质量中文财经源，不要一上来抓 200 个网站。

产出：

新闻库、事件库、舆情标签、公司关联表。

## 第三优先级：研报与机构观点

原因：研究价值高，但合规复杂。

目标：

先处理内部已有研报、合法授权研报、公开可下载材料。

产出：

研报观点库、盈利预测表、评级变化表、风险提示库。

## 第四优先级：政策与宏观

原因：用于行业研究和策略研究。

目标：

国家部委、交易所、监管机构、行业协会、地方政府政策。

产出：

政策库、行业影响标签、政策事件表。

## 第五优先级：投资者交流与问答

原因：适合做管理层表述变化分析。

目标：

互动易、上证 e 互动、业绩说明会、公司调研纪要。

产出：

Q&A 库、管理层表述库、关键词变化趋势。

# 七、工具组合建议：给你一个最终版

## 版本一：低成本 MVP

适合你现在先跑起来。

动态页面： Playwright
正文抽取： Trafilatura
RAG 友好网页： Crawl4AI
变更监控： changedetection.io

检索： OpenSearch / Elasticsearch

这个版本最务实。

## 版本二：增强型 MVP

这个版本更适合团队化项目。

# 八、一个非常实用的落地路线图

## 第 1 阶段：先做“资料目录库”

目标不是马上智能问答，而是先把资料管理起来。

完成内容：

公司主数据表、信息源表、文档表、原文存储、采集任务表、基础爬虫。

优先采集：

公告、年报、公司官网 IR、少量财经新闻。

阶段成果：

可以按公司、日期、资料类型、来源检索所有资料。

## 第 2 阶段：做“正文解析与全文检索”

完成内容：

HTML 清洗、PDF 解析、正文抽取、标题/时间/来源抽取、OpenSearch 入库。

阶段成果：

可以搜索“某公司 + 商誉减值”“某行业 + 政策利好”“某公司 + 监管问询”。

## 第 3 阶段：做“RAG 问答”

完成内容：

文档切分、向量化、RAGFlow/WeKnora 入库、引用回溯。

阶段成果：

可以问：

“这家公司最近三年收入增长质量如何？”

“最近有哪些公告涉及股权激励？”

“把这家公司年报中的风险因素总结一下。”

“比较两家公司在产能规划上的差异。”

## 第 4 阶段：做“事件抽取”

完成内容：

从公告、新闻、研报中抽取事件，建立事件表。

阶段成果：

可以问：

“最近 30 天医药行业有哪些政策事件？”

“哪些公司被监管问询？”

“哪些公司业绩预告超预期？”

“哪些公司出现现金流恶化信号？”

## 第 5 阶段：做“研究智能体”

完成内容：

自动生成公司跟踪报告、行业日报、政策点评、风险预警。

阶段成果：

系统不只是“查资料”，而是能辅助研究判断。

# 九、几个关键判断

## 判断 1：Scrapy 仍然是主干

不要因为 Crawl4AI、Scrapling、Firecrawl 很新，就放弃 Scrapy。Scrapy 的价值在于长期任务、稳定调度、Pipeline、去重、重试、日志和生态。

## 判断 2：Crawl4AI 很适合你的 RAG 方向

它解决的是“网页怎么变成 LLM 能吃的内容”。如果你的目标是 RAG/智能体，而不是单纯做数据库，Crawl4AI 值得纳入。

## 判断 3：Scrapling 可以纳入，但不是主力

Scrapling 适合复杂页面和页面结构变化，但不要把它作为绕过限制的工具。金融项目一定要保持合规边界。

## 判断 4：Fundus 不适合作中文财经主力

Fundus 有新闻抽取思路，但中文财经源覆盖不够。中文财经更适合 Scrapy + Trafilatura + Crawl4AI + 自定义规则。

## 判断 5：RAGFlow/WeKnora 不是业务主库

RAGFlow 或 WeKnora 可以做知识问答，但你的资料目录、公司信息、事件表、来源配置、采集状态，必须独立建在 PostgreSQL/MySQL 中。

# 十、最终推荐方案

如果你现在要启动这个金融研究信息收集项目，我建议你的最终方案写成：

>
本项目采用“官方/授权数据优先、开源金融接口补充、网页采集增强、文档解析入库、全文检索与 RAG 并行”的技术路线。

以 PostgreSQL/MySQL 建立公司主数据、信息源、文档目录、采集任务和事件表；以 MinIO 保存原始 PDF/HTML/附件；以 OpenSearch/Elasticsearch 支撑全文检索；以 RAGFlow/WeKnora 支撑文档问答。采集层以 Scrapy 为主框架，Playwright 处理动态页面，Trafilatura 负责正文抽取，Crawl4AI 负责 RAG 友好 Markdown 输出，changedetection.io 负责重点页面变化监控，Scrapling 作为复杂页面和自适应采集的增强组件纳入。

我认为这是最适合你的方向：不追求炫技，追求可持续、可追溯、可扩展、能真正服务金融研究。
