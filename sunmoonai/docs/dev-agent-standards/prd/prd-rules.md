# PRD：产品需求（Product Requirements Document）

`PRD/` 是 PRD 段的定稿目录：**要什么、做到什么算满足**，不写怎么实现。SDD 段拿它当输入。

```text
PRD/
├── architecture/             模块之间的结构与关系（入口 README.md）
└── modules/<四位号>-<短名>/  每个模块要满足什么
```

## 这一段该问什么

**没有模板，也没有必填栏**，下面是这一段该落在哪些问题上；一问只谈一件事，一段话说清就够。

| 问什么 | 说明 |
| --- | --- |
| 以什么为底 | 哪一份 `PRD/` 定稿、哪一段讨论、哪个 ADR；给链接与提交 |
| 谁用、什么场景、要什么结果 | 需求的三件事。写结果，不写实现 |
| **正向场景** | 做对了是什么样，能演示、能验 |
| **反向场景** | 做错了、输入不对、外部不可用时该是什么样 |
| **非目标** | 这次明确不做什么、以后再说什么 |
| 约束 | 合规、平台、成本、时间、既有系统；不能动的东西 |
| 非功能 | 性能、容量、安全、可用性上的要求 |
| **什么算满足** | 验收口径该是什么——**这是要它答的**，不是你先写好的判据 |
| 允许的不确定性 | 哪些可以先不定，以及不定会影响什么 |
| 要不要拆模块 | 只定需求，还是同时给模块划分 |

**不把验收标准写成条目塞进这一问**：写成条目就把答案空间提前封死；合不合格看它能不能定稿成 `PRD/`，判据是本规则。
写多严见 [任务的生命周期](../lifecycle.md)「用户消息写多严」。

## `architecture/` 写什么

| 部分 | 写什么 |
| --- | --- |
| 目标与范围 | 这个任务要达成什么；包含什么、不包含什么、不包含的归谁 |
| 模块划分 | 分成哪几个模块、各自承担什么、为什么这样分 |
| 模块之间 | 依赖、边界、谁向谁提供什么；跨模块的共同约束 |
| 约束 | 必须遵守的规则、不能动的东西、外部限制 |
| 未决 | 还没定的事，以及定不下来会影响什么 |

## `modules/<模块>/` 写什么

| 部分 | 写什么 |
| --- | --- |
| 职责 | 这个模块要满足什么，一句话说清 |
| 输入与输出 | 从谁拿什么、给谁什么 |
| 验收 | 可判定的条件，做完能一条条对着勾 |
| 约束 | 只对这个模块成立的限制 |

- 模块的号与短名在同一父目录内从 `0001` 起连续编号，并与 `SDD/modules/` 下的同名目录、实现时 worktree 里的模块目录**一一对应**。
- **以定稿为准**：模块要拆、要合、要改名，先改这里，再改设计与代码。

## 纪律

- **只写要什么，不写怎么做**：技术方案属于 SDD。
- **`PRD/` 里写的验收条件可判定**：写「响应时间小于 2 秒」，不写「响应要快」。
- **不给倾向性结论**：把要求写清楚，把方案留给设计。
- 改 `PRD/` 要写明改了什么、为什么；已据它派出去的任务按 [改判](../detailed-rules/approvals.md) 处理。
