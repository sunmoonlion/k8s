# ADR-0014：智能体分通用与专用两部分，执行层租用、纪律与账自建

- 状态：已接受
- 日期：2026-08-28

## 背景

投资管理分析系统要以智能体承载后端任务。此前的施工基线是
`mooc-manus-langgraph-longterm-plan-v5.md` 与其实施计划，但在 2026-07-29
`P0-008C` 处标记为 `PAUSED_FOR_ARCHITECTURE_REVIEW`，未恢复。

重新审视这两份文档后发现：**v5 的主体是前后端对接，不是智能体架构。**
这不是评价其质量，而是对其覆盖范围的事实认定，依据可数：

| 事实 | 数值 |
| --- | --- |
| v5 §10「消息、事件、投影与流式输出」 | 200 行，全文最长，11 个子节中 8 个讲前端 |
| v5 §14「多智能体架构」 | **23 行** |
| v5 的 12 条 ADR 中前端相关（013–018） | **6 条**，占一半 |
| 实施计划中前端任务 / Research Runtime 任务 | **17 个 / 14 个** |
| 实施计划中多智能体任务 | **1 个**（`V5-M1-702` Subagent 薄切），且在 M1a 之后、状态 `NOT_STARTED` |

且 §14 的形态是**声明清单**——"每次 AgentInvocation 明确：输入上下文选择器、
可见 memory、允许工具、独立预算、输出 schema、合并策略、失败传播"。
它规定要填哪些字段，不规定怎么运作。

另有一处退化：v4 §20「智能体形态与多智能体架构」有 **102 行**，含 `AgentProfile`
完整结构与"AgentProfile 可切换 ≠ 多智能体协作"的分界，v5 收缩时压成 23 行，该分界丢失。

与此同时，本项目在 2026-08 的多助手协作实践中产出了
[`../multi-assistant-workflow.md`](../multi-assistant-workflow.md)——
它表面写"AI 助手怎么协作"，实质是**多智能体系统的运作纪律**，且每一条都来自真实发生过的失败
（隔离被破坏导致产出趋同、评审未声明覆盖范围导致误报、吸收方自判误报等）。

## 决策

### 1. 智能体分通用与专用两部分

| | 通用部分 | 专用部分 |
| --- | --- | --- |
| 内容 | 执行编排：轮次、隔离、中断恢复、审批、工具协议 | 领域：提示、工具绑定、权限、memory policy、领域约束 |
| 载体 | 执行运行时 | `AgentProfile`（沿用 v4 §20 的结构） |

新增一个业务智能体，**优先是新增一份 Profile，而不是 fork 一套代码**（继承 v4 §20）。

### 2. 纪律不是中间层，是两部分各自的性质

通用部分的纪律：隔离原则、三阶段可见性、提案包构造规则、评审须声明提交号与覆盖范围、
吸收须留处置记录、重叠与分歧作为覆盖率信号——见
[`../multi-assistant-workflow.md`](../multi-assistant-workflow.md)。

专用部分的纪律：零证据即失败、citation 只回同源、结论可复现、预算按研究任务分配。

**两部分都必须有纪律，不存在"通用部分不需要约束"。**

### 3. 四本账是两部分共用的地基，必须落在本项目的存储

预算、幂等、副作用、证据四本账
（见 [`../request-lifecycle.md`](../request-lifecycle.md) §7）
不随分层归属任何一侧，且**必须落 PostgreSQL**。

理由是既有判据：**跨 run、或跨进程死亡仍须正确的不变量，必须由存储承担。**
任何把账放在执行进程本地的方案（含外部 harness 自带的存储）都不满足该判据——
investment-app 是多 worker、进程可被杀。

### 4. 通用部分的执行层采用外部 harness，跟随其更新

选定 Codex 的 Python SDK（`openai-codex`，Apache 2.0）作为执行层，
不自建轮次生命周期、隔离进程、中断恢复、审批协议、工具与沙箱。

**依赖边界严格限定在 SDK，不得直接依赖其 app-server 裸协议。**依据实测：

| 层 | 近 3 个月提交 | 破坏性变更 |
| --- | --- | --- |
| `app-server-protocol`（裸协议） | 280 次 | 12 处 |
| `sdk/python`（门面） | **10 次** | **0** |

SDK 是稳定门面，吸收了协议的剧烈变动；跟随它的代价是常规依赖升级。

**执行层通过 Port 隔离**，理由不是"将来可能要换"，而是：有该接口才能用 fake 执行器
测试纪律层（隔离是否生效、吸收有没有留处置记录），否则每次测试都要真起 harness 并需凭据。

### 5. 外部 harness 只提供执行原语，不提供运作纪律

| 能力 | harness | 自建 |
| --- | --- | --- |
| N 路隔离并发、轮次、中断恢复、审批、工具、沙箱 | ✓ | |
| 三阶段可见性、提案包构造、评审协议、吸收处置记录、重叠分歧判据 | | ✓ |
| 四本账 | | ✓（§3） |

### 6. 结构化数据问答（Text-to-SQL）归专用，先做最小实现

理由是范围控制，不是能力归属：定位为通用会诱导第一版支持任意数据源与 schema，
在跑通一条真实链路之前先铺抽象，违反 v5 §3 原则 8「真实竖线优先」。

**抽象推迟到第二个领域需要时再做**——不到第二个用例，不知道通用的边界在哪；
提前抽出的"通用"多半是投资的形状套了通用的名字，比不抽更糟。

前提约束：**领域概念不得进入 Port 签名**（`run(sql, limit)` 可以，
`run_portfolio_query(持仓ID)` 不可以），提示词、语义层定义、数据源配置走 Profile。
满足这两条则随时可抽，否则会锁死。

## 后果

- `mooc-manus-langgraph-longterm-plan-v5.md` 及其实施计划**从施工基线降级为历史设计输入**，
  其前后端对接部分仍然有效，可在相应工作启动时引用；其 §14 不作为智能体架构依据。
- v4 §20 的 `AgentProfile` 结构重新生效，作为专用部分的载体。
- [`../multi-assistant-workflow.md`](../multi-assistant-workflow.md) 的地位改变：
  它不只是助手协作流程，同时是通用部分的行为规范。
- 引入对外部 harness 的依赖，须锁定 SDK 版本并纳入升级流程。
- 具体实施按 [`../request-lifecycle.md`](../request-lifecycle.md) 立请求承载，
  本 ADR 只记决策。
