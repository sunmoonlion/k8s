> 远程 Fable 应所有者「全盘分析，理出一个非常清晰的架构用来指导开发」起草。读了三代代码与文档：旧体系 `sunmoonai/`（2025-12 起：`infrastructure/`、`cicd-platform/`、`data-platform/`、`messaging-platform/`、`ingress-platform/`、`ops-platform/`、`app-platform/` 并列），新体系（2026-09 luna 重写：`infrastructure/` 加 `gitops/`），以及 2026-10-16 Opus 重写后的 `project-guide/`。代码事实见 [`平台代码地图.md`](../dev-investment-agent/tree-build/平台代码地图.md)。

## 一、为什么现在没有一条贯穿始终的架构

三段历史各留下一层叫法，没人把它们对齐：

| 时期 | 代码怎么分 | 「infrastructure」指什么 | CI/CD 在哪 | 文档在哪 |
| --- | --- | --- | --- | --- |
| 旧体系（2025-12 至 2026-09） | `sunmoonai/` 下七个并列目录：`infrastructure`（建 kind）、`cicd-platform`（Harbor、Jenkins）、`data/messaging/ingress/ops-platform`、`app-platform`（auth、info、investment、knowledge 四个应用） | **建集群那一层** | 集群里的 `cicd-platform` | `sunmoonai/docs/`、`app-platform/docs/` |
| 新体系（2026-09 至今） | `infrastructure/`（宿主上的 Ansible：Harbor、入口、建群、Flux、渲染发布链）加 `gitops/components/<平台>/`（集群内声明） | **宿主上、集群外的一切** | Harbor 成了宿主模块 `registry/`；Jenkins 刚成为宿主模块 `jenkins/`；CD 是 `flux/`，D 段换 Argo | `docs/platform/`（已删，并入 `constraints.md` C-R13–19）、`project-guide/`、`dev-investment-agent/` |
| 产品改向（2026-10-16 起） | 应用从四个变六个，专家线横跨 knowlab → knowmart → knowbench | 没变 | 没变 | `dev-investment-agent/`（名字还是「开发 investment 那个 agent」）装了六个应用的全部设计 |

结果是四个具体的错位：

1. 「infrastructure」一词换了意思，旧文档里的「infrastructure → application」分层在新代码里找不到对应目录。
2. 旧的 `cicd-platform` 被拆成宿主上的 Harbor、宿主上的 Jenkins、集群里的 Flux（将来 Argo），三处各有名字，没有一个词把它们合起来叫。
3. `project-guide/overall-architecture.md` 10-15 版还有 `infrastructure/` 与各平台目录两张表，10-16 重写时被收成一段话和一条发布链，平台层的架构描述移进了 `repos/k8s.md` 和 `constraints.md` 的发布规则里，读总览看不到分层。
4. `dev-investment-agent/` 的名字和它现在装的东西不符：里面既有跨项目通用的 `turn/`，也有本项目六个应用的 PRD、SDD、规则、决策，还有平台线的设计（0010、0013、0022、0033、0034）。

## 二、一套层次（自下而上）

每样东西只属于一层；跨层只经本页第三节写的那几种关系。

```text
┌─ 7 产品线 ─────────────────────────────────────────────────────────────────┐
│  数据线：knowfeed → knowbase            专家线：knowlab → knowmart → knowbench │
├─ 6 应用层（app-platform = 全部应用）───────────────────────────────────────┤
│  auth（Casdoor） tpl knowfeed knowbase knowbench knowlab knowmart              │
│  每个应用 = 后端一个镜像多角色 + 网页端 + 管理端；跨应用只经版本化契约        │
├─ 5 平台层（集群内的共享能力）──────────────────────────────────────────────┤
│  foundations · data · messaging · ingress · ops · relay · sandbox             │
├─ 4 集群层 ──────────────────────────────────────────────────────────────────┤
│  一个 Kubernetes 集群，建法可换：开发期 kind，生产期 kubeadm 或云托管；上层只认身份  │
├─ 3 宿主层（集群外、站点内的服务）─────────────────────────────────────────┤
│  数据盘与开机 · Harbor · 入口 HAProxy · Jenkins · （边缘机上的）Traefik+frps   │
├─ 2 站点层（三个地方）─────────────────────────────────────────────────────┤
│  用户电脑（浏览器、本地 link）· 公网边缘（东京 VM）· 内网站点（所有者机器 WSL）│
└─ 1 物料层 ──────────────────────────────────────────────────────────────────┘
   一切外来字节的锁与搬运：工具、镜像、包、chart、模型；Harbor 是它们的本地家
横切 A 交付链（CI/CD）：源码钉版 → 构建 → 渲染 → 发布 → 晋级 → 部署 → 检查；今天由人照卡跑，B 段 Jenkins 跑，D 段 Argo 调和
横切 B 身份与秘密：平台 CA、SOPS 身份、共享口令、组件与应用私有输入、人工账号预设；主备两份、丢了不再生成
横切 C 环境参数：站点名、集群名、命名空间、域名、端口、路径；C 段把它们从代码里拆出来
```

| 层 | 一句话 | 现在在哪 | 不变量来源 |
| --- | --- | --- | --- |
| 1 物料 | 版本与摘要只有一个来源，不追 latest | `infrastructure/artifacts/`、`tools/`、Harbor | `C-R3`、`C-R16` |
| 2 站点 | 深处只出站，边缘无状态 | `docs/运行拓扑.md` 第一部分、`SDD/architecture/topology.md` | `C-T7`、`C-T8`、`C-T9` |
| 3 宿主 | 集群外的服务一种形状：config + 剧本 + 模板 + 手册，systemd 单元并入 `sunmoon-platform.target` | `infrastructure/{host,registry,entry,jenkins,edge}` | `C-R13`、`C-R14` |
| 4 集群 | **一个 Kubernetes 集群，建法可换**：开发期是 kind（`sunmoon-kind`，D 段 `sunmoonai-kind`），线上生产是 kubeadm 自建或云托管；上面各层只认集群身份回执与 kubeconfig，不认建法；集群是可重建的，重建后数据从保留卷与备份回来 | `infrastructure/cluster/`（今天只有 kind 一种建法，生产建法是另一个模块） | 冷建即验证（D 段）；生产建法的验收另定 |
| 5 平台 | 组件按平台归目录，一个组件一个 `stage.yaml`；共享对象只由 foundations 声明 | `gitops/components/<平台>/` | `C-R15` |
| 6 应用 | 领域划 App，一个 App 一个后端、一条迁移链、一个逻辑库；模板优先 | 六个应用仓 + `gitops/components/app-platform/` | `C-T1`–`C-T3`、`C-D2`、`C-R6` |
| 7 产品线 | 逻辑和数据都是用户的；每件事只在一个应用里办；跨应用只经契约 | `tree-build/PRD/`、`SDD/modules/0026+` | `C-L1`–`C-L5`、`C-C*` |
| 横切 A | 一次发布 = 钉住的源码 + 由它构建的摘要 + 由它渲染的声明 + 匹配的迁移头 | `applications/`、`components/`、`flux/`、`jenkins/`（将来 `build/`、`argocd/`） | `C-R1`–`C-R5`、`C-R11` |
| 横切 B | 身份只在私有目录与密文里 | 各模块 `prepare`、`host/accounts.*` | `C-R12`、`C-I*` |
| 横切 C | 一套声明，站点只差参数 | `environments/kind/site.yaml`（现在只有一个站点，很多值还写死在断言里） | 10-06 决定「parity」 |

两个旧词的归宿：**旧 `infrastructure`（建 kind）= 第 4 层集群层**；**旧 `cicd-platform` = 横切 A 交付链**，它的三个部分按「跑在哪」各归其层：Harbor 和 Jenkins 在宿主层（它们要在集群被删掉时还活着），Argo 在平台层（它调和的是集群内声明）。

## 三、层与层之间只有这几种关系

| 关系 | 方向 | 怎么做 | 禁止 |
| --- | --- | --- | --- |
| 应用 → 平台 | 上用下 | 后端经集群内 Service 与私有输入里的身份用 PostgreSQL、Redis、RabbitMQ、对象存储、Casdoor、relay、provisioner | 应用声明里直接写平台的口令；应用按公网名连平台 |
| 应用 ↔ 应用 | 平级 | 版本化 HTTP 契约（提供方放 schema、调用方持锁）、Outbox 投递、普通链接带人过去 | 直接读写对方的库、桶、Redis 键；在调用方另建 schema 副本 |
| 平台 → 集群 | 上用下 | 阶段图 `dependsOn`、保留卷绑定节点目录 | 组件自己建节点目录 |
| 集群 → 宿主 | 上用下 | 节点只信 registry 的 CA、拉 Harbor；入口把域名直通到集群 NodePort | 集群里的东西依赖宿主上除 Harbor、入口之外的任何服务 |
| 宿主 → 物料 | 上用下 | 一切镜像、工具、包按锁校验后才用 | 运行时从公网直拉 |
| 交付链 → 各层 | 横切 | 只调各层的公开入口（`platform-*`、模块五个动作），自己不渲染、不部署、不存秘密 | 流水线里写第二套发布逻辑 |
| 身份 → 各层 | 横切 | 每层的身份由那一层的 prepare 首次生成并备份；跨层只传公钥或令牌 | 复用口令；重新生成已有身份 |
| 环境参数 → 各层 | 横切 | 每个字段一个来源；模块 config 引用站点参数，不复制常量 | 把集群名、命名空间写进断言或模板常量 |

## 四、新东西往哪放（决策表）

| 要加的是 | 放哪 | 怎么接 |
| --- | --- | --- |
| 一个集群外的服务（像 Harbor、Jenkins） | `infrastructure/<名>/`，形状同 registry、entry | 物料进锁；systemd 单元 `WantedBy=sunmoon-platform.target`；入口加 SNI 路由；账号进 `host/accounts.yaml`；模块进 `host/deployment.yaml` 的 modules |
| 一个集群内的共享能力（数据库、消息、检索、控制台） | `gitops/components/<所属平台>/<名>/`，带 `stage.yaml`、`config.yaml`、模板、`prepare.yaml`、README | 镜像进上游锁与 `service_image_ids`；保留卷进 `layout.yaml`；命名空间用站点参数 |
| 一个新应用 | 由 `tpl-app/init.sh` 实例化一个父仓三子仓；`gitops/components/app-platform/<名>-app/` 三个子对象 | 钉进 `applications/sources.yaml`；`application_names` 加名字；域名进入口路由与（若对公网）边缘名单 |
| 一个应用的新进程角色（像 knowbench-runner） | 同一镜像、同一后端目录；`config.yaml` 开关 + `common/backend/runtime/workload.yaml.j2` 一段 | 不新建应用、不新建镜像 |
| 一条跨应用关系 | 提供方 `contracts/<名>/v<N>/`，调用方锁文件；服务身份走 `common/backend/service-client` | 不开新的身份机制 |
| 一个产品线的功能 | 先答「在哪个应用里办」；设计写 `SDD/modules/00NN`；决定进 `decisions.md` | 不跨应用各做一份 |
| 一个自研的非应用镜像（像会合点） | 源码在 `infrastructure/applications/component-images/`（将来 `build/`），钉进 `component-images.yaml` | 走同一条构建链 |
| 一个站点（第二个内网站点、生产） | `environments/<站点>/site.yaml` 加对应私有目录；集群建法按站点选（kind / kubeadm / 云托管），平台层以上的声明同一套 | C 段之后才做得到；生产建法是 `infrastructure/` 里 `cluster/` 旁边的另一个模块，不改 `cluster/` 去迁就 |
| 一条规则 | `tree-build/rules/constraints.md` 对应节 | 架构页只引用不复制 |
