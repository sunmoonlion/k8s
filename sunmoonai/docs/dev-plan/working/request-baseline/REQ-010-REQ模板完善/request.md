# REQ-010：REQ 模板完善

> 状态：PROPOSED ｜ 提出日期：2026-08-16 ｜ 评审日期：—

> 类型：**决策型 REQ**（AGENTS.md §5）。不产生代码。
> 产出物为 `TEMPLATE.md` 的替换提案，**本 REQ 不修改 `TEMPLATE.md` 本身**——
> 它是治理文件，按 §7 功能分支禁改（见 ③ 的路径说明）。

## ① 原始需求

> 2，你觉得@k8s/sunmoonai/docs/sunmoonai-architecture/requests/TEMPLATE.md 这个结构是否要完善？

> 然后把结论写进去

## ② 架构评审

- 结论：**采纳**。现结构需要完善，缺陷有七处，每处均可追到一个已发生的实际后果。

- 理由：

  现模板四段（原始需求 / 架构评审 / 落地去向 / 状态流转）中三段的设计是对的，本提案不改：
  ① 一字不改作为意图证据（本轮多次回读 ① 并从中发现与后续改判的张力，该设计已被验证有用）、
  ② 的四选一结论与代价对比、以及「目标态事实写进 baseline，request 只留引用」的不复述约定。

  需要补的是**七处缺栏，且每一处都已经造成了后果**，不是预防性设计：

  | # | 缺什么 | 已发生的后果 |
  | --- | --- | --- |
  | 1 | 验收标准 | 无此栏时「IMPLEMENTED」不可证伪。REQ-008 有验收标准仅因撰写时临时加了一节；REQ-001 至 REQ-003 均无，故其完成度无法判定 |
  | 2 | 边界（含 / 不含 / 不含的归谁） | REQ-005 与 REQ-006 长期互相渗透，两次修正都在重划边界；REQ-003 整体被 REQ-004 吸收 |
  | 3 | 决策点作为一等栏位 | REQ-005 与 REQ-006 的 D 组是事后临时加的，却成为全文最常被跨文件引用的部分（本目录现有 20+ 处 `Dn` 引用）。模板不设此栏，等于让最高频的引用目标处于「看作者习惯」状态 |
  | 4 | 依赖与关联（取代关系双向登记） | **REQ-001 因此成为僵尸**：状态 ADOPTED，声明的六份产出物一件未出，目标已由 REQ-004 + REQ-008 从另一路径达成，但 REQ-001 一侧无任何记录。REQ-003 → REQ-004 是双向登记的，所以没出问题——对照即证明该栏有效 |
  | 5 | 「改判不覆写」的显式约定 | 本轮两次修正（`RunBudget` 误判、技能/底座重划）都是临时决定加「YYYY-MM-DD 修正」小节。约定不成文，下一位就可能直接覆写，从而丢掉「当时为什么那样判」 |
  | 6 | 状态流转的「说明」列写什么 | 现模板示例只有「用户提出」。实践中该列真正的价值是**改判依据**——改了什么 diff 里有，为什么改只有此处有。不写明会退化为复述 diff |
  | 7 | 事实性断言的取证要求 | REQ-008 逐条读码时发现旧文档含三处错误断言。取证要求应是模板级全局约定，而非每个 REQ 各自发挥 |

  两项不采纳的候选，一并记录以免重复讨论：

  - **不加「风险」栏**。风险与 ② 的代价对比重合，会产生两处内容漂移。
  - **不加「工作量估算」栏**。本目录无排期机制，该栏会长期为空或长期失准。

- 边界：

  - **含**：`TEMPLATE.md` 的替换提案、决策点的 ID 式引用约定、REQ-001 僵尸状态的暴露。
  - **不含**：REQ-001 的处置（是结案、改判不采纳、还是保留残余范围），见 D3。
  - **不含**：已有 REQ 按新结构的回溯补栏，见 D4。
  - **不含**：`AGENTS.md` §5 §7 的相应措辞调整——同属治理文件，与本提案同批处理。

- 冲突与代价对比：

  | | 采纳新结构 | 维持四段 |
  | --- | --- | --- |
  | 一次性成本 | 治理文件改动须走共享分支批准（§7）；D2 若采纳，需改 20+ 处 `④ Dn` 引用为 `Dn` | 0 |
  | 持续成本 | 每个 REQ 多填三栏（边界、验收、关联） | 僵尸 REQ 随数量线性增长；边界靠事后重划；决策点格式因人而异 |
  | 风险 | 栏位增多可能产生「长期空栏」腐烂 —— 由 ⑤ 要求「不适用也须显式写出」缓解 | 无新增 |
