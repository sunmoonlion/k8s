# 竞品比较分析

更新日期：2026-10-18（按 2026-10-16 至 10-18 的决定整篇重写；2026-10-14 的旧版在 Git 历史里）。对象：腾讯 WorkBuddy（含开放平台与金融版）、Meta Muse。比较基准：SunMoonAI 的 knowlab（孵化专家）、knowmart（专家目录）、knowbench（工作台）。专家市场的机制与界面另见[专家市场：架构对比与借鉴](专家市场架构对比分析和借鉴.md)。

证据分四类：官方披露、已读代码、已定设计、分析建议。竞品没有登录后同题实测；不对三方的准确率、稳定性、速度或费用作无依据的排名。我方能力以 2026-10-18 的代码与决定记录为准，「已实现」指代码已提交，是否已部署单独说明。

## 一、现在的判断

我们的定位在 2026-10-16 至 10-18 定清楚了：**投资逻辑与数据只来自用户，我们负责把用户的方法孵化成专家、测好、再在工作台上按步骤监理执行**（决定记录「产品的核心价值是怎么孵化」「都叫专家」；约束 `C-L1`–`C-L5`）。所以和竞品比，不再比「谁的专家更懂投资」，而是比三件事：

1. **孵化**：用户的想法变成一个能跑、测得出对错的专家，要多少功夫、准不准、守不守得住「没有用户出处的规则不放行」。
2. **监理**：执行时对不对由程序判（分步验收、数由平台算），还是由模型自觉。
3. **合规**：专家只归用户自用；公开售卖要发布主体持证，平台按类目审资质（对标 WorkBuddy 开放平台）。

WorkBuddy 值得学的是把上下文、外部服务、执行和成果组织成连续的办公流程，以及开放平台的入驻与资质框架；Muse 值得学的是围绕目标持续委托、只在有价值的变化或需要决定时回来找人。

## 四、和 WorkBuddy 的根本差别

| | WorkBuddy | 我们 |
| --- | --- | --- |
| 专家的方法从哪来 | 开发者（持证机构或个人）自己写 | 用户自己的想法；我们只做孵化与工程化，每条规则要有用户出处 |
| 专家是什么 | 一份提示词文件，专家强弱约等于这份说明写得好不好 | 方法包：分步、每步有交底、交回格式和验收 |
| 对不对谁来判 | 主要靠用户审阅产物 | 每步程序验收（结构与数值），数由平台算 |
| 先测后用 | 没有公开的先测机制 | 交付前在测试电脑上按用户给的用例测 |
| 数据 | 平台或机构提供金融数据源 | 平台不提供；专家只读用户自己上传、绑定的数据 |
| 投资类专家的公开 | 只对持证非个人主体开放 | 同样的框架（knowmart 照它建骨架）；现在没有资格，全部自用 |

用施工比方说：WorkBuddy 的工头也是一个工人，手里拿着一份写得很细的交代单；我们的监理是一套制度，做得对不对由仪器量、按规程验。这套制度是我们的本钱，但它也意味着我们只适合「能写成步骤」的工作，临时、探索性的任务要靠受理关口和普通工作对话兜住。

## 五、值得借鉴的地方

标「待验证」的是本轮没取得完整证据的，不能直接写成现网缺陷。

### 5.1 让用户第一次就知道交什么进来

**问题：** 「财务分析与预测」这样的名字很大，一版专家实际支持的数据和方法要说清楚。

**借鉴：** WorkBuddy 把能力放进具体场景，给任务样例。

**我们的落点：** knowmart 专家详情页的「能做什么、需要的数据、交回什么」三个页签（0032 已实现）；下一步加样例成果和一两个可直接改对象、改时间的问题样例。受理关口已能挡住明显无关的问题。

**验证：** 新用户不求助能否选对专家、问对问题；不适用的问题是否在花钱前被说明。

### 5.2 研究背景要准，不只是多

**问题：** 用户偏好、项目事实、分析假设、过期的判断不能混成一段背景。

**借鉴：** WorkBuddy 可更正的记忆；Muse 的持续背景加独立话题。

**我们的落点：** 已有长期记忆与跨对话读取。先把三类内容分开：用户偏好、项目事实（带对象与数据日期）、待验证假设（不自动升级成事实）；换公司、换期间、换数据版本时提示重新确认。

**验证：** 第二次任务少说多少重复的话；跨公司会不会串背景。

### 5.3 成果能接着用

**问题：** 拿到文件不等于干完了：还要查某个数的来源、改一条假设、和上次比。

**借鉴：** WorkBuddy 预览与修改在同一工作区；Muse 按用途选产物形式。

**我们的落点：** 文件交付与 Word、Excel、PDF 导出已有（0031）。下一步：从成稿里的数跳到计算记录与格子地址（0030 已有记录，缺入口）；和上一版成稿比较；基于成稿继续问（待办账 130 的「追问」）。

**验证：** 找到一个数的来源要多久；改一条假设要不要重说整件事。

### 5.4 持续跟踪靠事件，不靠定时重问

**借鉴：** WorkBuddy 的周期任务；Muse 的目标与事件推进。

**我们的落点：** 让用户在一次完成的研究上选「数据更新时按此口径再做一次」：记下目标、触发条件、停止条件、允许动作；先比数据版本，有变化才跑，跑完说清相较上次变了什么。用户电脑离线时等着，不偷偷改到云端执行。现在不做，等第一条实测之后。

### 5.5 用户的数据要看得懂够不够

**问题：** 平台不提供数据之后，「这个问题现在能不能做」取决于用户传了什么。

**借鉴：** WorkBuddy 按任务引入连接器；Muse 小企业版围绕用户现有业务资料。

**我们的落点：** 专家开工前给一段材料摘要：用了哪几份数据、覆盖哪些期间与科目、缺什么、建议补传什么。knowlab「我的数据」已提示「数字类尽量传表格」（K17）。

### 5.6 用户看得懂进度与下一步

**借鉴：** Muse 的活动与目标视图；WorkBuddy 把结果和待确认的事带回工作入口。

**我们的落点：** 工作台已有每步的白话说明、「现在在做什么」、审查面上「每个选项选了会怎样」。保持三种入口（聊天、工作、专家），不把每个内部事件都推给用户处理。

### 5.7 专家方法要证明值得

**问题：** 步骤多不等于质量高；模型越强，普通工作对话能做的越多。

**我们的落点：** 选一个边界清楚的场景，同模型、同数据比较普通工作对话与专家执行：专业正确性、出处、费用、人工复核时间。冗余的步骤由孵化出新版本去掉，不在执行中静默改。

### 5.8 市场与资质

**借鉴：** WorkBuddy 开放平台的主体、类目、证照框架（2026-10-18 所有者定照它建 knowmart）。

**我们的落点：** knowmart 已有发布主体与资质的数据结构和公开开关（0032）；入驻、证照审核、收费等有持证合作方或拿到资格再做。照搬框架不等于照搬合规：平台自己那一层的证照、孵化时我们算不算共同作者，要单独问律师（0026 第五节第 6、8 问）。

## 七、公平的验证方法

| 测试 | 保持相同 | 回答的问题 |
| --- | --- | --- |
| 三方产品同题 | 任务、可提供的数据、时间和费用范围 | 用户用完整产品的实际体验 |
| 我方普通工作与专家对照 | 模型、数据版本、工具、输入 | 方法与验收贡献多少 |
| 孵化质量 | 同一份想法，不同孵化方式（手工、辅助） | 规则出处是否守住、测试通过率、用户改了几轮 |
| 连续任务 | 同一项目，第二次新增一项数据或修正 | 背景与成果复用是否有效 |

竞品不能用相同模型时，说明这是产品整体比较，不归因于编排架构。竞品接不了某个数据源时记为条件差异，不混进准确率。

首批场景：首次使用（从目标到选对专家）、跨对话续做、假设变更、新旧资料冲突、成果复核、更新跟踪、成果交接。指标：专业正确性、首次有效成果时间、人工复核时间、重复说明次数、不必要的取数与执行、总费用、第二次任务节省多少。每类可先做少量重复试验找问题，不据此发布总体成功率。
