# UAT：用户验收测试（User Acceptance Testing）

由**验收 agent** 交付；验收 agent 不是交付 SDP 的执行 agent。
多个验收 agent 各自验收、需要比对时，按 [`../../protocol/`](../../protocol/round-rules.md) 的轮次协议进行。

## 判据与完成

- **验收依据是派工时的任务文本**：其中写明的验收标准；没写的，以任务说清的要求和本规范为准。派工后不改，出题的人与答题的人分开，实现者完工后不能改验收题。
- **任务没有可判定依据的地方，写「不可判」**，交给人，不自己发明标准来判通过。
- **验收不能外推。**在一类任务上跑通的便宜验收（可用测试、diff 机械复算），不能证明判断昂贵的另一类任务也过关。
- **完成条件逐条满足才叫完成。**缺项时只能称相应的中间状态（已受理、候选完成、待验收……），不能笼统说完成。
- **先核前提。**比较方案之前，先顺着真实调用链核实：要控制的动作是否一定经过所说的强制点；查不到就标假设。

## 证据采信

- 自述只是待验证的主张；结论由验证方从冻结的产物独立重算。
- 采信程度取各项中最低的一项（来源、可见范围、隔离强度、验收独立性、覆盖），任一项未知就降级，不取平均。
- 覆盖声明同时写查了什么、没查什么；零命中只有在输入集合被完整枚举时才算通过，否则是「不可判」。

## 检查本身也必须接受检查

每个检查都输出「通过 / 失败 / 不可判」三种结论，并写明查了什么、没查什么。
缺输入、权限不足、枚举失败不能被吸收为通过；聚合前先判输入集合是否完整、是否允许为空。
**不让空集合、空 diff、吞掉的退出码或「0 个文件通过」代替完成条件。**

新增或修改检查时至少核查适用的边界用例：正常通过、真正失败、输入缺失、命令失败、
空集合、引用对象不可达、否定句与历史引用。误报要区分是解析问题还是内容问题，
不能为了消掉一个红字删掉失败标准；假失败偏安全，也不是长期保留误报的理由。

文档复核分四层：链接可达；标题有对应；对应正文真正承载原主张及其边界；证据本身支持该主张。
**空标题、只有结论没有证据、映射到同名异义的段落，都不算吸收。**链接和表格一类的机械检查
不能替代正文层与证据层。

机械状态校验从明确的状态表取词与边，不对全文盲搜：历史反例、否定句和属性值不应被误认成状态。
覆盖声明和不可判的输入与结果并列，不让下游把窄范围的通过外推成完整正确。

## 覆盖声明：查了、没查、不能排除

覆盖声明要能装下「不确定」，不是只有「查了」「没查」两档。凡「不能排除某事发生过」，
就如实写进来，不要因为难看就压成「没查」：

| 写法 | 含义 |
| --- | --- |
| 查了 | 有观测，有结论 |
| 没查 | 没有观测，**明知自己不知道** |
| **不能排除** | **有观测但不足以定论**，或存在自己控制不到的路径 |

「没查」还要按类别分列，不能混成一段：

| 类别 | 例 | 性质 |
| --- | --- | --- |
| **环境事实** | 主机名、身份、命名空间映射 | **可当场复跑**；没查是因为没跑，跑了就有结论 |
| **远端与授权** | 远端分支、分支保护、部署密钥 | 部分可读，**写授权不能只靠读取来验证** |
| **执行者内部** | 界面里选的模型、沙箱内的工具调用 | **结构上够不着**，换接入方式才可能有结论 |

第三类是唯一「不改变接入方式就永远查不了」的；把它和前两类并排写成「没查」，
会让人以为再跑几条命令就能补上。

**如实写「不能排除」不扣分，隐瞒才扣。**


## 验证分层

| 层 | 谁 | 判什么 |
| --- | --- | --- |
| L0 | 自动检查（CI、提交钩子、校验器） | 链接、schema、冻结区、摘要、diff、测试、角色冲突等机械条 |
| L1 | 独立验收方 | 任务要求中机器判不了的内容；**作者自检不能代替独立验收**，验收方只按派工时的要求判，不为通过而静默改标准 |
| L2 | 被处置主张的原作者 | 是否被误读；异议必须带处置条目与可复跑证据 |
| L3 | principal | 意图是否正确、不可逆项、抽样复算证据的真实性；抽样规则事先写进任务，否则抽检会退化成「翻一翻」 |

顺序不可倒：L0 未过不进 L1，L1、L2 未过不请求最终批准。新增的机器判据，首跑必须与人工结论对照；
锚点存在但不支持断言，比没有锚点更危险。

## 证据账按流程分级

| 流程 | 最小留证 |
| --- | --- |
| 单路实施 | 固定最终提交、验收方、门禁命令及原始输出位置 |
| 定向审核 | 任务链接、评审、处置、最终提交与验证结果 |
| 最小选优 | 任务链接、参与者清单、候选提交映射、决策、处置与验证结果 |
| 完整选优 | 请求、清单、候选、评审、决策、改进、处置、最终提交上的回归结果 |

载体可以分散，但必须由一个稳定的主记录串起全部链接，并能由第三方读取。**任何流程都不得只在聊天中宣称测试通过**；
别人不能恢复和复核的内容视为未持久化。候选提交必须来自该候选自己的分支。

## 先裁决事实，再谈偏好

- 评审分两阶段：先只读原始请求、匿名提交和统一标准**独立审**；冻结后再读候选自评、盲区与验证记录**对照审**。
  评审写明提交、覆盖范围、阻断问题、证据，以及哪些结论真的运行过。
- 每条主张判为「证实 / 证伪 / 未决」并附证据。测试失败、违反硬约束或范围、有阻断风险、提交或证据不可取、隔离不可恢复的候选，
  **不进入偏好评分**；全体一致不是免检理由。偏好维度与权重在候选产出前冻结；结果称「本轮选定」，不称「已证明正确」。
- 整合：选定提交冻结为只读基线；**一条独立主张一个提交**，整体重写作为新候选重开；逐项记录接受、部分接受或拒绝及证据；
  冲突按原始请求、约束和证据解决，不按票数、作者或提交时间。**所有有效门禁必须在最终提交上重跑**——候选的绿色不能证明整合结果正确。

## 完成判据

同时满足才叫闭环：受理幂等，原始请求可追溯；工作区与清单可复现；任务里说清的范围、验收、权限、预算、批准点在派工时就已定下，基线已固定；
执行者接单核对过工作区、指令、租约与输入；按风险执行，角色冲突已处理；每个产出有归属、命名空间、状态、来源和唯一的发布目标与整合者；
候选没有直接写共享路径；发布经预期版本的原子条件更新；并行结果绑定提交，迟到、失败、取消已处置；最终提交上门禁与验收逐条通过；
结果、证据、副作用、盲区和风险已持久化；终态唯一，请求方可重取结果；提交与产物可达、血缘可追溯且无活跃引用后才清理工作区。

**缺项时只能称「已受理」「候选完成」「本轮选定」「待验收」「交付待重试」或「清理待处理」，不能笼统宣称完成。**

## 能力状态只用四级

| 级 | 含义 |
| --- | --- |
| `defined` | 有类、DTO、迁移或测试夹具**存在** |
| `wired` | 生产链**已接线**，会被真实请求走到 |
| `deployable` | 部署面（打包、网络、凭据、配额）**已就位** |
| `runtime-verified` | 在目标环境**实跑验证过** |

类、DTO、迁移或测试夹具存在，都不等于生产链已经接线。历史记录、候选与聊天只作线索；当前实现的断言必须回到代码、测试或运行结果取证。

## 载体各能证明什么

| 载体 | 覆盖会怎样 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 未提交工作区文件 | 后写直接覆盖先写：无冲突、无历史、无作者归属 | 磁盘此刻的内容 | 谁写的、谁先写完、被覆盖前是什么 |
| 提交 | 新提交不摧毁旧对象，旧对象需有引用才找得到 | 一组文件内容及父历史不可变 | 谁批准、测试是否通过、外部副作用状态 |
| 分支 | 指针可被快进、重置、强推 | 当前指向哪个提交 | 稳定的评审对象 |
| 工作区 | 一条分支只能被一个工作区检出 | 某执行者当前可写目录 | 长期证据 |
| 标签 / 引用 | 可被移动或删除，所指对象仍在 | 使对象可达、表达冻结点 | 不自动构成验收或发布 |
| 补丁 | 应用到不同基线结果不同 | 可传输的差异 | 完整父基线与外部状态 |
| 共享发布面 | 未授权写入等于闯入他人发布面 | 只有整合后的最终提交算交付 | 任何未经整合的内容 |

**交卷 = 自己分支上的可达提交。**候选和评审一律引用完整提交 ID 与基线；冻结后禁止改写历史，需要变基时形成新候选并保留新旧映射；
删除分支或工作区前确认要保留的提交已由持久引用保持可达——「对象暂时还在 reflog」不是保留策略。
Git 不能证明跨记录的事务提交、租约或写入隔离，也不能证明执行器内部发生过哪些工具调用。

## 证据分三级

- **已核对事实**：证据当前仍可独立取得并复核（提交、文件、可重跑命令）；
- **事故报告**：确实发生过，但现场已灭失，只能按当事方陈述记录；
- **设计风险**：机制上成立，但尚未实际踩到，或原始出处已不可取得。

三级**不可互相升格**，尤其不得把「机制上必然如此」当成「此处已核对」。用不可复核的叙述去加强一条本来就成立的规则，只会削弱整份文档的证据标准。

## 检查给出假答案的边界案例

| 边界案例 | 错误结论怎样产生 | 怎样核 |
| --- | --- | --- |
| 验收方集合为空 | `all([])` 为真，被当成完成 | 先验证应有参与方或产物数量，再聚合；未指定不是通过 |
| 身份命令在仓外运行 | 失败被管道吞掉，从错误文本生成假名字 | 每个依赖命令检查退出码；取不到仓库根就停止 |
| 身份判别失败后按产品猜人 | 「运行在某产品」被推成「属于某参与方」 | 对照登记的工作区与任务身份 |
| 机械检查读到否定句 | 「没有这条边」被误判为声明了非法边 | 从规范定义块或 schema 取状态 |
| 两层调用各吞一个错误 | 内层失败被外层成功掩盖 | 原始退出码逐层传递 |
| 文档门禁只查链接 | 被纯文本「文件:行」引用的文件删了，门禁仍绿 | 并查纯文本锚点与可重取来源 |
| 标题保留而正文被切掉 | 空节不产生坏链接 | 对照源段的主张、条件、反例与未验证项 |

假通过会成为下游继续执行的依据，比一次明确的失败更危险；判不了时停在「不可判」。假失败也要靠修正解析来消除，不能长期靠人工忽略。

## 评审的收益与盲区

评审能发现局部矛盾、非法状态边、归属错误和证据不足；但共同的前提错误、被任务书封死的答案空间，可能经多轮评审仍不被发现——
「必须包含某机制」一旦冻成标准，「其实不需要它」就无法作为合格答案提交，增加候选数也修不了这种出题错误。
所以任务越重，出题越要给硬约束与发展方向、可复核的问题、客观的完成判据与完整的源集，允许用证据质疑机制的必要性，不给出题方的倾向。
来源方异议检查整合是否忠实，独立验收检查产物是否满足标准，两者不可互代。通过只意味着按所述范围完成了一次检视，不能估计未发现缺陷为零。

## 历史证据怎样用

使用证据前固定：仓库或 SDK 版本、配置或策略版本、主机、身份、沙箱或容器上下文、命令、退出码、原始输出引用及时间；敏感字段去敏。
沙箱内观测不能直接外推宿主，受限环境不能代替同身份的生产测试。文档里的「曾经通过」只说明那个版本的那个用例；
原记录不得改成新日期。原作者的数字与读数可作回归线索，没有独立重取证据时引用为「原作者记录」。

其余规范尚未编写。
