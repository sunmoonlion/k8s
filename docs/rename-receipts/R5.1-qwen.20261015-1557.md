### 根因诊断（只读取证，未动磁盘）

`windows-capacity.ps1` 是构建前的 **Windows C 盘容量守卫**，本次判定 `passes:false` → `rc=2`。守卫逻辑（保守）：`c_free − future_data_growth − planned ≥ minimum_free`，其中 `future_data_growth = 配置的 VHDX 上限 − 当前已分配`。实测数值换算：

| 量 | 字节 | GiB |
|---|---|---|
| `c_free_bytes`（C 盘可用）| 83355537408 | 77.63 |
| `configured_data_maximum_bytes`（VHDX 上限，`-DataMaximumGiB 230`）| 246960619520 | 230.0 |
| `data_vhd_allocated_bytes`（VHDX 现占用）| 180459929600 | 168.07 |
| `future_data_growth_bytes`（上限−现占用）| 66500689920 | 61.93 |
| `planned_bytes`（本次构建预估）| 6442450944 | 6.0 |
| `remaining_after_growth_and_plan_bytes` | 10412396544 | **9.70** |
| `minimum_free_bytes`（`-MinimumFreeGiB 10`）| 10737418240 | **10.0** |

即 9.70 GiB < 10.0 GiB，**差约 0.3 GiB 没过**。守卫假设数据 VHDX 可能一路长满到 230 GiB 上限，届时 C 盘余量将低于 10 GiB 安全线。前两个对象（tpl、knowfeed）能过、到第三个（knowbase admin）不过，是因为构建过程本身在往数据盘写、C 盘余量随之下降，到 knowbase 时越过了阈值。**这不是改名/正则/脚本问题**（第 1、2 步 python exit=0、锁值全对；tpl/knowfeed 构建 exit=0 可证），是本机 Windows C 盘余量触到守卫。

### R5.0 磁盘核对的盲区（供 Opus 参考，非本次失败主因）

R5.0 的 `df -h /` 看的是 WSL Linux 根（599G 可用），而构建守卫查的是 **Windows C 盘**（77.6 GiB 可用）与数据 VHDX 上限。两者不是一回事，所以 R5.0「磁盘够」通过、第 3 步仍被 C 盘守卫拦。是否要在 R5.0 增加一条 Windows C 盘容量核对，交 Opus 定。
