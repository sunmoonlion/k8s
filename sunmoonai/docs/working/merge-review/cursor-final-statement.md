## 1. 若按现稿收口，实际会发生什么

[`disposition.md`](disposition.md) 文末写：

> 未完成：无。四份评审的 A 组与 B 组已逐条处置完毕。

按 `agent-discipline.md` §5.3–§5.4，这句话的效果是：后续评审方（尤其是
被点名重跑 A1 的 kimi）只核处置表里有的行；表外的条目不再有「必须给去向」
的位置。`merge-review/` 的删除条件第 2 条也会被读成已满足。

因此：**写「无」不等于做完，等于把没入表的东西从循环里拿掉。**

复核（本声明所审的就是这份现稿，不是某个已推送提交）：

```bash
grep -n '未完成\|四份评审\|qoder.md' \
  k8s/sunmoonai/docs/working/merge-review/disposition.md
```

## 3. 但有两样东西会被「未完成：无」顺带盖掉，它们不是措辞问题

### 3.1 处置记录声称已执行的 luna A1，在 tree 上仍成立

luna A1 的核心是：**总览与仓页对同一事实结论相反**。处置表写「采纳」，
理由是「总览旧风险条已随修复移除」。现稿不是这样。

```bash
sed -n '/### 9.3/,/### 9.4/p' \
  k8s/sunmoonai/docs/project-guide/overall-architecture.md
#   knowledge 行仍写：CANCEL 终态被当作成功（只有 FAIL 抛错）

sed -n '/CANCEL 必须抛错/,/pytest/p' \
  k8s/sunmoonai/docs/project-guide/repos/knowledge-app.md
#   仓页仍写：CANCEL 必须抛错，并给 cancelled 回归测试
```

两条不能同时代表当前事实。无论代码在 `origin/opus` 上已经修没修：

- 已修 → 总览 §9.3 必须改到与仓页一致（这正是处置记录声称做过、但没做的）；
- 未修 → 仓页必须改回风险，kimi A1 的证伪也要重写。

**现状是第三态：处置记录说做了，正文没做。** 这比「漏记一条 B 组」重——
它让 luna 的阻塞项带着「已采纳」标签活着。收口前必须先让三处对齐：
代码、仓页、总览。只改处置表不够。

同型、仍活着的还有 **luna A1.3**（处置表未列）：

```bash

grep -n '^## ' k8s/sunmoonai/docs/project-guide/governance.md
```

写作约定实际在 `working/doc-conventions.md` §3 / §4。这是语义坏链，
luna 验收标准第 3 条仍红。改指针即可，成本低于再辩一次。
