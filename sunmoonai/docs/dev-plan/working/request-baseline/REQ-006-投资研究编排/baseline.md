## 2. 设计原则

### 2.1 子 Agent 即 Run（理由已改，结论不变）

子智能体是一个带 `parent_run_id` 的 Run，父子关系用**物化路径**表达，
既支持路径寻址，也支持库内子树查询。

**2026-08-16 修正：结论保留，但理由换了。**原理由是「免费继承状态机、事件流、检查点、cancel」。
智能体那半改为租用之后，这些继承大部分由 SDK 侧提供（其 run 有自己的状态、流式与 cancel），
不再是本仓建 Run 行的动机。

真正的动机是**记账归属**：四本台账都需要一个可归属的行——预算要有节点才能树形累计，
副作用要有 `run_id` 才能定位重复来源，证据要有行才能挂模型标识与时点。
即：**Run 行的存在理由从「继承机制」变为「作为账户」。**

推论一：本仓 Run 与 SDK 侧 run 是两个对象，须记录后者的标识以便对账。
推论二：`RunBudget` 不在任何继承清单内——它当前未被任何生产链调用（见 §1），
须先接线，见 §2.2。

### 2.2 预算预扣，不用共享池

**前置条件：先让单 Run 预算真正生效。**当前两条生产链都不调 `budget.check()`，
父 Run 自身没有有效余额，因此预扣与退回都无从测起。次序必须是「单 Run 接线 → 父子语义」，
不可颠倒（归属见 REQ-006 ④ D7）。

接线之后：派生子 Run 时从父 Run 的四维余额中**划走**一份，子 Run 完成时将未用部分退回。

共享池的两个问题：并行消费有竞态；无法保证任何单个子 Run 能跑到完成（可能全部中途
`budget_exceeded`）。预扣制保证「派出去的每个子 Run 都有确定的完成能力」。

推论：`spawn` 时必须显式给出子预算，父余额不足则派生失败而非降级。

### 2.3 ~~等待语义做全，不留给调用方~~（2026-08-16 作废）

原文主张把 wait-any / wait-all / quorum 做成一等原语，理由是不要复制参考实现
「只给 wait-any、调用方自写循环、单批八目标上限」的缺陷。

**作废理由**：等待多个租用调用就是 `asyncio.gather` 与 `as_completed`，
quorum 是在 `as_completed` 上数到 k 即停。标准库既无八目标上限也无需调用方写循环，
原缺陷不存在，故无题可设计。原 REQ-006 ④ D5 随之作废。

保留一条要求：并发上限须可配置且默认保守——它约束的不是等待语义，而是预算账（§2.2）。

### 2.4 Registry 独立于会话

编排状态（节点、边、状态、产物指针）单独存储，不塞进 `session_events`。
依据参考实现的教训：会话记录存的是对话，业务 DAG 是另一个状态容器，
靠翻会话记录还原「工作流跑到第几步」迟早出问题。

`tool_side_effects` 已是独立记账表，说明该分离直觉在本仓已有先例。

### 2.5 复核者拿不到父上下文

复核子 Run 不继承父 Run 的消息历史，只接收产物与验收标准，结论用契约 DTO 回，
不退回自然语言摘要。

两条依据：REQ-002 中 C7 由「错误」被人工改判为「含糊」，说明产出方不能自验；
参考实现亦有同一结论（刚写完代码的会话倾向确认自己的判断）。

### 2.6 副作用与 cancel 的多智能体语义

- 副作用：并行分支可能重复触发同一副作用。语义（exactly-once 或 at-least-once + 幂等键）
  必须在写第一行编排代码前定死，见 REQ-006 ④ D3。
- cancel：须沿父子树传播。参考实现中「能掐子 Agent、掐不掉另一个持久任务」的不对称性
  是其历史遗留，不予继承。

### 2.7 证据账：结论必须可复现

第四本台账，为 2026-08-16 新识别的缺口。每条落库结论须同时落：依据（来源指针）、
执行者标识（模型或版本）、时点。

理由不是审计偏好，而是**外部行为可在本仓无任何提交的情况下改变**：
模型列表会演进，`auto` 档由服务端选型。不记执行者标识时，同一份代码在两个月后
给出不同结论且无从归因——这对投资研究结论是不可接受的。

推论：不接受智能体自报其模型标识（自报无审计效力），由调用方写入。

### 2.8 「未派出去」与「跑了但挂了」按原因码分流

调用未发出（配置、鉴权、网络）与调用发出后失败是两件事：前者该直接重试，
后者重试可能重复副作用，须先查副作用账。

**区分能力本仓已有**：`pilot_service.py:52-53` 写 `error="dispatch_failed"`、
同文件 `147-148` 写 `resume_dispatch_failed`，两者 status 同为 `failed`。
不新增终态，理由见 REQ-006 ④ D10。

待补的是消费侧：重试须按 `error` 码分流，当前无此分流。

## 3. 验收标准

1. 子 Run 复用 Run 状态机，无新增并行状态机（可代码审查判定）。
2. **单 Run 预算已生效**：两条生产链均调 `budget.check()`，超限时 run 进入 `budget_exceeded`
   且该状态在生产中可达（当前唯一写入方是非生产图 `first_m1_graph.py:36`）。
3. 预算预扣可测：父余额不足时派生失败；子 Run 未用额度在终态时退回父。
4. ~~wait-any 与 wait-all 均为一等原语~~（随 §2.3 作废）。改为：并发上限可配置，
   且该上限的超出由预算账拦截而非由调用方自律。
5. Registry 与 `session_events` 分离存储；从 Registry 单独可答「当前哪些节点 ready」。
6. 复核子 Run 的上下文不含父 Run 消息历史（可测）；复核结论为契约 DTO。
7. cancel 父 Run 后，全部子孙 Run 在有界时间内进入 `cancelled`。
8. 副作用语义有明确文档与测试：同一副作用在并行重试下不产生重复业务效果。
9. **台账层不含投资研究领域概念**（`grep` 可判定），投资研究是其首个消费者而非定义域。
10. 每条落库结论均带来源指针、执行者标识与时点；缺任一项者写入失败而非降级。
11. 「未派出去」与「执行后失败」在库内可区分；前者的重试路径不触碰副作用账。
12. 进程在任一步被杀后重启，四本账均不出现「已发生但未记」或「已记但未发生」
    （须有针对性的杀进程测试，非仅单元测试）。
