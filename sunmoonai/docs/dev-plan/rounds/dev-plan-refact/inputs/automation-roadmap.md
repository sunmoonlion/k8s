## 1. 背景：结论是怎么得出来的

### 1.1 起点

项目要建一个全栈 agent 平台（含专业财务分析），**开发工作全部由 AI 助手承担**。
为此本仓有两份同构文档：`working/development-lifecycle-agent.md`（1161 行）
与 `working/development-lifecycle-human.md`（823 行），合计约 1984 行重复内容，
2026-09-04 的 refact 轮里 cursor 与 qwen 的评审都指认过这个重复。

### 1.2 三步推导

**第一步：四家助手全部有非交互 CLI。**

| 家 | 命令 | 非交互 | 装了吗 |
| --- | --- | --- | --- |
| cursor | `agent`（旧名 `cursor-agent`） | `-p` / `--print`，写文件需 `--force` | ❌ |
| qoder（qwen） | `qoder` | `-p` / `--print`，写文件需 `--permission-mode` 或 `--yolo` | ❌ |
| kimi | `~/.kimi-code/bin/kimi` | `-p, --prompt` | ✅ |
| luna | `codex exec` | 子命令即非交互 | ✅ |

**第二步：CLI 化之后，人与 agent 的入口差异消失。**

两份文档的差异原本主要在入口：agent 路径是「前端 → FastAPI 受理 → sandbox 物化 → 交给 Agent」，
human 路径是「人自己建仓、自己开 worktree」。全部 CLI 化之后，两者变成同一条：

```text
收到固定指令 → 跑 round-status 定位 → 读落盘通知 → 在自己 worktree 干活
   → 按同一命名交付 → 按 commit 冻结
```

`round-protocol.md`（改造版，见 §2）从头到尾**没有分人和 agent 两套**——这不是巧合，
是「落盘通知 + 从产物反推状态」这个设计的必然结果。

**第三步：但权力差异不消失，也不该消失。**

以下五条只有人能做，与装多少 CLI 无关：冻结题目与验收标准、⑥ 确认、
省事方向裁定的确认、推翻任一裁定、承担最终责任。

**所以结论不是「删掉 human 版」，而是：**

> **一份流程文档（人机共用）+ 一节「人独有的权力与责任」。**

human 版 §10–§18 自己标着「以下各节对人和 agent 同样成立」——那部分是重复，该删；
§2–§9（人的三个角色、人独有的权力及其义务、改判三要素、终审与责任归属）不是流程，
是授权模型，**要并进统一文档的一节**。说成「删掉 human 版」会丢掉这一半。

### 1.3 一个更大的结构发现

把这套东西看全，它本身就是一个 agent 系统：

| round-protocol 里的 | `development-lifecycle-agent.md` §6 里的 |
| --- | --- |
| 轮次组织者（现在是人，将来是编排器） | Agent 作为 supervisor |
| 四家助手 | Work Unit 的执行者 |
| ① 提案 N 家并行 | fan-out 派工 |
| ② 互评 + ③ 裁决 | 收候选、选优、整合 |
| ⑤ 验收、停止规则 | §6.4–6.8 候选隔离、角色分离、评审裁决、停止规则 |

**用 dsh 建的财务 agent，在这个结构里与 kimi/luna/cursor/qwen 地位相同——都是 subagent。**
这反过来验证了裁决稿 §4.7 的 `AgentExecutorPort` 不区分「租来的通用助手」与
「我们组装的专业 agent」是对的：在 supervisor 眼里它们是同一种东西。

**一处差异不能抹平**：跨厂商 subagent 的独立性是真的（不同训练、不同失败模式），
同 runtime 派生执行者的独立性要靠机制造出来。这影响「多家一致但都没取证，
输给一家带 `file:line` 的」这条规则的含金量——同源 subagent 的「一致」信息量低得多。

### 1.4 难度地图被修正了

原来的隐含排序是「先建判据与回路，再谈组织多个 AI 协作」。**反了**：

| | 性质 | 状态 |
| --- | --- | --- |
| 怎么组织一群不确定的执行体 | **设计难**——没有现成答案，买不到抄不来，失败模式隐蔽 | **已跑通** |
| 怎么判断执行体做得对不对 | **工程难**——方法已知，费钱费时但路清楚 | 未做 |

详见 [`readiness.md`](readiness.md) 文末「难度地图（2026-09-04 修正）」。

## 2. 现状：什么跑通了，什么没有

**跑通的是 §6（supervisor 那一层）**——2026-09-04 用四家助手实跑了一整轮完整流程
（提案 → 互评 → 裁决 → 异议 → 验收），并在过程中从零建出改造版 `round-protocol.md`。

**没跑通的是 §5（执行内核）与 §9（权限、预算、副作用）**——而恰恰是这两块在生产里
引用数为 0（`ToolExecutionPort`、`SandboxPort`、`RunBudget` 全部 `defined` 未 `wired`）。

`round-protocol` 能跑通，**前提是它假定每个 subagent 已经是能自己干完活、自己提交、
自己守纪律的成熟主体**；而 investment-app 要建的正是那个「能自己干完活」的部分。

## 3. 处理顺序

**每一步都有前置，跳过任何一步的代价写在右列。**

| # | 步骤 | 前置 | 跳过的代价 |
| ---: | --- | --- | --- |
| 1 | **走完 refact 轮**（⑤ 验收 → ⑥ 人确认 → ⑦ 清理发布） | 无 | 中途改题；协议自己规定「任务书冻结后不得中途修改」 |
| 2 | **装 `agent` 与 `qoder`，各自登录** | — | 分发无通道，四家里只覆盖一到两家 |
| 3 | **分发脚本先只做「生成待发指令」**：输出该发给谁 + 可直接粘贴的文字，人粘贴一轮 | 1、2 | 判定错、措辞错会在第一次全自动时同时暴露，且无人在场 |
| 4 | **全自动跑一个可丢弃的小题目** | 3 验证通过 | 见 §4.1 |
| 5 | **补「验收稿要点名三处」进协议** | 4 | 见 §4.2 |
| 6 | **U1 合并轮**：两份 lifecycle → 一份流程 + 一节人的权力（**T2**） | 1–5 全部 | 拿本仓最贵的两份文档做首次全自动试验 |
| 7 | **U2**：supervisor 第四套定名，`round-protocol` 与 agent §6 共用规则骨架 | 6 | — |

第 3、4 两步看着多余，但它们把「第一次全自动出错」的代价限制在一个可丢弃的题目上，
而不是本仓最贵的两份文档上。

**与执行内核并行**：以上是协作层的路线；执行内核（§5/§9）的验证路径是另一条，
即裁决稿 §4.5 的 Gate 0 三条可证伪硬条件，目前**全部标 ⚠ 未实证**。
两条线互不阻塞，但**不要把协作层跑通误读成执行内核已验证**。

## 4. 两个已知风险

### 4.1 第一次全自动别拿权威层文档做题目

「CLI 跑通 → 直接全自动」这一步本身，按协议的档位判据属于**不可逆性未知**：
第一次全自动的失败形态我们没见过——可能是四家同时被叫起来干错的环节；
可能是分发脚本把某家的内容串进别家 prompt，**隔离当场破**；
可能是无人值守时卡在某处而没人发现。

所以第 4 步的题目要满足：**做砸了可以直接丢掉**。合并 lifecycle 是权威层 + 不可逆，
不适合当首次试验。

### 4.2 人不在场之后，「确认」会退化成盖章

现在人能确认 ⑥，是因为全程在旁边、知道每一步发生了什么。全自动之后，
人会在**流程末尾**看到一份一千多行的稿子和一句「请确认」——这时候点通过几乎是必然的。

协议已经挡住一半（⑥ 不设逾期默认、人不确认就不发布、确认前必须有检视面），
但**挡不住「看了但没真看」**。

补法（第 5 步）：**验收稿必须点名「最该看的三处」**——本轮改动最大的、
争议最多的、以及验收方自己最不确定的。让人的注意力有落点，而不是面对全文。
