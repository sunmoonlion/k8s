# App Platform 集成规范

## 1. 目标

本文定义 App Platform 各 App 之间的同步 API、异步事件、文件交换和失败处理规范。

跨 App 集成只能使用公开契约，禁止直接读取或修改其他 App 的数据库、Bucket、缓存和内部队列。

## 2. 集成方式

### 2.1 同步 API

适用于：

- 用户正在等待结果的查询或命令。
- 需要立即校验的业务操作。
- 数据量可控的点查询。

要求：

- API 路径包含主版本，例如 `/api/v1/...`。
- 定义请求超时，不允许无限等待。
- 查询与命令接口语义分离。
- 错误响应包含稳定错误码和 `trace_id`。
- 列表接口使用稳定分页和排序。
- 非幂等命令支持 `Idempotency-Key`。

### 2.2 领域事件

适用于：

- 领域事实已经发生后的通知。
- 多个下游独立消费。
- 不要求调用方同步等待。

事件命名：

```text
<domain>.<aggregate>.<event-name>.v<major>
```

示例：

```text
info.information.version-created.v1
investment.decision.approved.v1
auth.user.disabled.v1
```

标准事件信封：

```json
{
  "event_id": "uuid",
  "event_type": "info.information.version-created.v1",
  "occurred_at": "2026-06-11T08:00:00Z",
  "producer": "info-app",
  "aggregate_id": "uuid",
  "aggregate_version": 3,
  "correlation_id": "uuid",
  "trace_id": "string",
  "data": {}
}
```

事件携带稳定标识和必要摘要。大文件、完整正文和敏感数据不直接放入消息，由消费者通过授权 API 获取。

### 2.3 任务消息

任务消息表达“请求执行”，与“事实已发生”的领域事件分开。

要求：

- 明确任务所有者。
- 包含幂等键、最大重试次数和过期时间。
- 失败进入死信队列。
- 管理端能够重试、取消和查看错误。

### 2.4 文件和对象交换

- 文件主档保存在所属 App 的对象存储。
- 跨 App 默认传递短期授权地址、对象引用和内容哈希。
- 接收方需要长期处理时，创建受控副本并记录来源。
- 不允许共享宿主机目录作为正式集成协议。

## 3. 一致性与事务

跨 App 不使用分布式数据库事务，采用：

- 本地数据库事务。
- Transactional Outbox 发布事件。
- 消费端 Inbox 或幂等记录。
- 必要时使用补偿流程和状态机。

事件发布失败不能导致业务事实永久无法传播。消费者重复收到同一消息不得产生重复业务结果。

## 4. 重试与失败处理

- 只对可恢复错误自动重试。
- 使用指数退避和随机抖动。
- 同步调用限制重试次数，避免放大故障。
- 写操作重试必须具备幂等条件。
- 达到重试上限后进入死信或人工处理状态。
- 业务失败和基础设施失败使用不同错误码。

每个集成都必须定义：

```text
timeout
retry policy
idempotency key
dead-letter behavior
reconciliation method
```

## 5. 契约演进

- 同一主版本内只能做向后兼容变更。
- 新增可选字段通常属于兼容变更。
- 删除字段、改变含义或类型必须发布新主版本。
- 生产者在约定迁移期内同时支持旧版和新版。
- 消费者忽略未知字段。
- API 和事件契约进入版本库并接受评审。

## 6. 服务身份与授权

- 用户身份由 `auth-app` 统一提供。
- 服务间调用使用独立服务身份，不复用管理员账号。
- Token 只授予完成操作所需的最小权限。
- App 在本领域内执行资源级授权。
- 日志不得记录密码、完整 Token 或来源密钥。

## 7. 可观测性

同步 API、事件和任务必须传播：

```text
trace_id
correlation_id
actor_id or service_id
```

至少记录：

- 请求量、延迟和错误率。
- 消息积压、消费延迟和死信数量。
- 外部依赖健康状态。
- 对账差异和补偿结果。

## 8. 对账

事件不能作为唯一恢复手段。关键集成必须提供周期性对账：

- 根据业务版本或更新时间查找遗漏。
- 比较记录数、稳定标识、版本和内容哈希。
- 自动补发或进入人工处理。
- 保存对账批次和处理结果。

`info-app` 到 RAGFlow 的同步必须支持全量重建和增量对账。

## 9. 禁止事项

- 跨 App 直接访问数据库表。
- 以 Redis、搜索索引或消息队列作为主数据。
- 在消息中传输未受控的大文件。
- 无超时的同步调用。
- 无幂等保护地重试写操作。
- 以部署优先级替代运行时容错。
