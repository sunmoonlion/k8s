# PRD：用户消息怎么写

PRD 这一类问的是**要什么、做到什么算满足**，不问怎么实现。定稿怎么把关见 [PRD 定稿](finalize.md)。

**规范不规定答。**要让答符合某种形式、走某条路、带某些东西，**就在这一问里提出来**——
规范里不替你规定，模型也不会自己知道。写进问里的才算数。

## 这一类该问什么

**没有模板，也没有必填栏**，下面是这一类该落在哪些问题上；一问只谈一件事，一段话说清就够。

| 问什么 | 说明 |
| --- | --- |
| 以什么为底 | 哪一份 `PRD/` 定稿、哪一段讨论；给链接与提交 |
| 谁用、什么场景、要什么结果 | 需求的三件事。写结果，不写实现 |
| **正向场景** | 做对了是什么样，能演示、能验 |
| **反向场景** | 做错了、输入不对、外部不可用时该是什么样 |
| **非目标** | 这次明确不做什么、以后再说什么 |
| 约束 | 合规、平台、成本、时间、既有系统；不能动的东西 |
| 非功能 | 性能、容量、安全、可用性上的要求 |
| **什么算满足** | 验收口径该是什么——**这是要它答的**，不是你先写好的判据 |
| 允许的不确定性 | 哪些可以先不定，以及不定会影响什么 |

**不把验收标准写成条目塞进这一问**：写成条目就把答案空间提前封死；合不合格看它能不能定稿成 `PRD/`，判据是本规则。
写多严见 [turn 的投影](../turn-project.md)「用户消息写多严」。

## 问到什么程度算够

**正向场景、反向场景、非目标、什么算满足都有答案，而且每条可判定**，就可以定稿成 `PRD/`。
**不要求知道怎么实现**：为了把需求写下去而先去定技术方案，就是已经在替 SDD 干活——那部分挪进 SDD 的用户消息，不留在这一类。

## 出题的人自己要守的

- **不给倾向性结论**：把要求写清楚，把方案留给设计。写出倾向，答就向你的结论收敛。
- **不把验收标准写成条目**：一旦冻成条目，「其实不需要这个机制」就再也交不上来。
