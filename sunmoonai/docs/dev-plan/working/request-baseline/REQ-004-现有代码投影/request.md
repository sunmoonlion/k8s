# REQ-004：现有代码投影

> 状态：PROPOSED ｜ 提出日期：2026-08-15 ｜ 评审日期：—

> 类型：**总壳/决策型 REQ**（AGENTS.md §5）。本请求定义投影的定位、结构与验证机制；
> 逐仓逐平台的投影撰写由实施 REQ 承担（见 ③）。

## ① 原始需求

> 我有很多问题没有理清：1，baseline开始我想当作投影，后来又想当作目标goal起到约束代码开发。
> 其实，这两件事都需要做，只不过把它混到一起了；2，另外，我还想为以后的代码开发特别是通过
> ai助手开发搭建一套成熟的工作流。这个想法也混迹其中，导致现在混乱。这些问题都要慢慢理清，
> 你看能否现在再立两个request：1，真正的就是为助手人了解现有的代码，也就是原来的baseline
> 确定作为代码投影，功能纯粹！为此，要重新考虑为实现这个目的而进行结构安排，比如你说的两轴等，
> 总之，这部分功能就是我们上面一直在想实现的功能2，再起一个request专门讨论如何开发一个agent
> 集群来进行代码开发。这个功能要从上面的讨论中彻底抽离出来。并且它要与request更紧密结合讨论。
> 特别要注意的是：其实第一个问题从根本上来说，只是一个大的request而已：对现有代码进行投影

## ② 架构评审

- 结论：**采纳（立项为总壳/决策型 REQ）**。定位与边界即刻生效；结构与实施范围待
  ④ 决策点拍板后转 ADOPTED。

- 理由：

  **用户自陈的「三事混一」与文档内可定位的证据一致。**`AGENTS.md` 第 22 行称 baseline
  「定位是现行有效事实（代码现状的镜子），**从不描述将来**」，第 175 行却要求
  「request 采纳后**目标态事实必须写进基线**」，第 25 行给出的调和机制是「**吸收进** `baseline/`」。
  吸收 = 搬运当初写的目标态文字，而非回读代码重写投影。这条通道使「意图」得以以「事实」的
  身份进入 baseline。

  **该通道已产生实测后果。**REQ-002 核出的 14 条偏差重新归类：真正的「代码改了文档没跟」
  只有 2–3 条（C14 Secret 拆分、C6 selector 改名）；读码精度问题 4 条（C5 C7 C8 C12）；
  **其余 7 条（宽算含 C9 为 8 条）属「意图被当成事实写下」**——C1 部署顺序写的是合乎逻辑的
  设计顺序而非 `deploy.py` 的实际顺序、C2「前置应含网络策略」、C3「应有统一门禁脚本」、
  C4「应有 cert-manager」、C10「Web 面应走 Pilot 链」、C11「红线应在 CLAUDE.md」、
  C13「应有 Attempt/Invocation 表」。成因不是维护不及时，而是**入口未拦住设计话语**。

  **定位澄清（本 REQ 的核心结论）**：baseline 定位为**纯投影**，功能单一。
  三项排除、一项承诺，详见 `baseline.md` §1。

  **结构服从目的**：寿命轴与归属轴（原 REQ-003 提案）是达成纯投影的手段，不是目的本身。
  按纯投影前提重新推导后，`facts/` 由「组织方案」升格为**定位的必然推论**（投影不得包含
  代码的即时状态），验证机制由「附属检查」升格为**投影的核心质量指标**。这是 REQ-003
  须并入本 REQ 而非平行推进的原因。

  **「只是一个大的 request」这一判断成立，且有简化收益**：投影是**交付物**，不是治理规则。
  因此 `AGENTS.md` 中关于 baseline 内容的规定可大幅收缩为几条纯度约束，baseline 的产出与
  维护改由本 REQ 及后续实施 REQ 承担。治理与交付物分离，`AGENTS.md` 随之瘦身。

- 冲突与代价对比：

  | | 确立纯投影 | 维持现状 |
  | --- | --- | --- |
  | 一次性成本 | 重审全部 baseline 条文并剔除不可对代码证伪的设计话语；结构迁移（15 条链接重算、文件 rename 后 `git blame` 需 `--follow`）；`AGENTS.md` §2 §5 §175 等条文须在共享分支修订（§7） | 0 |
  | 持续成本 | 维护 `facts/` 采集与可重复验证扫描 | 每轮请求闭环经「吸收」通道注入新的意图-事实混淆（本轮实测 7–8 条）；投影可信度持续下降 |
  | 风险 | 迁移期新旧路径并存易产生第二真源；须一次搬完不留旧址 | 投影退化至「读了也不敢信」，等同放弃 §1 将 baseline 定位为代码缓存的整个设计 |

- 边界（明确排除，不在本 REQ 内解决）：

  - **B｜目标约束**（用户 ①-1 中「当作目标 goal 起到约束代码开发」）：确认需要做，但
    **不得以 baseline 承载**。载体待定，见 ④ D3。
  - **C｜智能体开发工作流**（用户 ①-2）：整体移出，见 ③ 与 REQ-005。
