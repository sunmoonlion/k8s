# 一次 turn 的九站

**一问从发出到拿到可用的答的完整往返。**这是主干:
[`turn/`](turn/README.md) 讲每一站怎么走,[`tree-build/`](tree-build/README.md) 讲这个项目
怎么把每一站建出来,两边都指这一份。

## 只有一条流程,区别是每一站谁做

**没有「人版」和「agent 版」两套流程。**只有同一条九站,每一站「谁做」是一个变量,
取值是**人**或**脚本**。所谓人版,是多数格子取「人」;所谓 agent 版,是除第一格外全取「脚本」。

**我们正在做的事,就是把这些格子一个一个从「人」改成「脚本」。**

⚠ **「谁做(现在)」那一列是现状投影,随实现更新。**每把一格改成脚本,这一列就要改一格;
本仓其余文档不另记人机分工(`project-guide/` 也不记)。

| # | 站 | 这一步做什么 | **谁做(现在)** | **脚本化后是什么** |
| --- | --- | --- | --- | --- |
| 1 | **写 message** | 把这一问要什么、边界、交回哪一种写清楚 | **人** | **永远是人**。产品侧由桌面应用承载,类别预填经 ③ 由 runtime 算 |
| 2 | **提交** | 把这一问交出去 | 人贴进助手窗口——**没有载体,所以这一步看不见** | 提交信封 + 幂等键,经通道 ④ |
| 3 | **受理** | 认下这一问、把契约定死 | 人心里那一下 | 建单、首事件、拒绝也形成可审计的 `REJECTED` |
| 4 | **派发** | 决定给谁、送过去 | 人投喂:手工粘,或脚本投给交互会话 | 路由、排队、带签名投递、租约与 fencing |
| 5 | **执行** | 干活 | **AI 助手——这一格已经自动化了** | 沙箱里的执行体 + key 隔离 + 独立工作区 |
| 6 | **中断** | 中途要人拍板 | 人当面说行 | Interaction:绑版本、有期限、**只能消费一次** |
| 7 | **封装** | 把产出收起来 | 人自己去看分支 | 本地内容检查 → 加密 → 上报密文 |
| 8 | **验收** | 判做对没有 | 人读,或另一方 agent 验 | 确定性验收 + 终态原子提交 |
| 9 | **交付** | 送到手里,且以后还能取 | 人读完取舍、整理成定稿 | 事件按 cursor 续传;密文在本机解开、渲染出来 |

**第 5 格已经改完了**——这正是为什么现在能用「其余格子还是人」的方式往下做:最贵的那一格先自动化了。

**第 1 格永远不改。**message 是人的意图,没有它这条链没有输入。

## 每一站算走完了没有

| 站 | 人做时 | 脚本做时 | 条款 |
| --- | --- | --- | --- |
| 写 message | 边界写清了:含什么、不含什么、不含的归谁。**模型只知道这里写了的东西** | 未经用户确认的类别预填不算数;没有可用的模型 key 不得提交;资料正文、文件名及派生特征不发往本平台后端与知识服务 | `F-INTAKE-05/06/07` |
| 提交 | 这一问存进 turn 目录,**发出即冻结** | 幂等键在「租户 + 请求方 + Profile」作用域内唯一;同键同摘要返回原 `task_id`,同键异摘要返回冲突,**不静默复用也不另建** | `F-INTAKE-01` |
| 受理 | ——(人版没有独立载体) | 身份从认证上下文确定,**不信任客户端自报**;一旦分配 `task_id` 并写首个事件,后续拒绝也必须形成可审计的 `REJECTED` | `F-ADMIT-*` |
| 派发 | 执行者知道交什么、交到哪;并行时各家隔离,不泄露别家方案 | 派发内容带签名;租约与 fencing 随派发下发;设备离线则等待,不丢 | `F-DISPATCH-*` |
| 执行 | 在自己的 worktree、自己的分支上;不碰别人未提交的改动 | 在独立工作区里跑;key 只在本机;本地资料不上传 | `F-EXEC-*`、`I16` |
| 中断 | 需要批准的动作**没批准就不做**;批准绑定这一版、这一项、有有效期 | 工具级在本机闭环,Task 级经后端 Interaction **原子消费**;两条提交逻辑**不得共用** | `F-APPROVE-*`、`F-REVIEW-*` |
| 封装 | 交的是**分支与提交**或 `response.md`;报路径不报提交不算交回 | 先本地内容检查,再加密;后端只拿到密文与元数据 | `F-CRYPTO-*` |
| 验收 | 每条判定有 `pass` / `fail` / `undecidable`;判不了停在 `undecidable` | 确定性验收与回执核对通过;终态、结果、预算结算**原子提交** | `F-ACCEPT-*` |
| 交付 | 写明以哪个 turn 为底、改了什么。**定稿不等于批准动代码** | 事件按 cursor 续传、重复幂等;**密文在本机解开、渲染出来** | `F-DELIVERY-*` |

## 差别只在有没有传递面

人当面说、当面给、当面批,所以第 2、3 两格没有独立载体,看起来像「少了两站」——
实际是**同一套九站,人版有两个关节没关节化**。

一旦这条链要交给程序,信封、签名、租约、一次性令牌就全都得有。
**这不是把人版翻译一遍,是同一条意图在有传递面时必须落成的机制。**

## 横穿所有站的不摊进任何一站

状态与账、进度与「下一步是什么」——这两样横穿全部九站,**不属于任何一格**。
摊进去,同一事实就会有多个写入面(`P1`)。后端把它们单列成两块,见
[后端的七块](tree-build/SDD/submodules/0001-backend/SDD/architecture/blocks.md)。

⚠ 横穿的东西**必须不朝外**:一旦有外部面,它就成了绕过站序的第二个入口。

## 自举:用这条链造这条链

改每一格的办法,是把它当成一次委托,走 PRD → SDD → IMP → UAT 四问;
**而这四问本身,仍然用「其余格子还是人」的状态来完成。**

```text
一次 turn 怎么走      ← turn/：跨项目通用的规矩
   ↓ 用它，每格 4 次 turn
把某一格改成脚本      ← tree-build/：这个项目的任务树
   ↓ 九格改完
这条链自己就能跑一次 turn
```

**改完一格,下一次委托就少一格人工——它自己给自己加速。**

⚠ 两条硬规矩:

- **不得假设还不存在的自动化。**写用户消息时不能写「系统会自动验收」——
  验收那一格现在是人。这是 `P6`(未核前提只能标假设)在流程上的对应。
- **改完一格,后续 turn 的写法要跟着变。**派发自动化之后,再写 turn 就不用交代投喂了。

## 投喂可以脚本化,批准不可以

**派发**那一格的**传输**可以自动化,**中断**那一格不可以。

| 形态 | 能不能用 |
| --- | --- |
| 手工投喂:人把话粘进助手窗口 | **现在唯一跑通的** |
| 脚本投喂:脚本把话投给**交互会话** | 可以——消息由脚本发出,审批照样浮到人面前 |
| 非交互一次性(`codex exec` / `agent -p` / `qoder -p`) | **不可用**:权限开关把审批预先答掉 |
| 走产品通道派发 | 待开发 |

**自动化的是传输,不是决定。**细则见 [操作闭环](turn/protocol/competition-operations.md)「投喂」,
批准点见 [人的批准点](turn/approvals.md)。

## 多方竞争挂在第 4 格

多方竞争不是另一条流程,它**从派发那一格分出去,到验收重新合流**:同一问发给几家,
多出互评、裁决、异议三个环节。因为横穿两站,产品侧单列成一块
（[`0008-competition`](tree-build/SDD/submodules/0001-backend/SDD/modules/0008-competition.md)）。

规则见 [多方竞争](turn/competition.md);**这一格现在由人做**时的操作细则见
[protocol/](turn/protocol/README.md)——那几份随这一格被脚本化而退役。

## 终点在哪

终点不是「模型返回了文字」,也不是「一条事件推送成功」,而是四条同时成立:

1. 最终结果、验收、证据和副作用状态已经可靠持久化;
2. Task 已以唯一合法终态提交;
3. 有权的人在断线、重启或换设备后仍能重新取得结果;
4. 通知失败可以独立重试,**不改变结果本身**。

## 交给程序驱动之前,两条已知风险

**一、人不在场之后,「确认」会退化成盖章。**现在人能确认,是因为全程在旁边。
自动化之后,人会在流程末尾看到一份一千多行的稿子和一句「请确认」——这时点通过几乎是必然。

已经挡住一半:不设逾期默认、人不确认就不发布、确认前必须有检视面。
**挡不住的是「看了但没真看」**。补法是让人的注意力有落点——
验收结论必须点名最该看的三处,见 [UAT 把关](turn/uat/finalize.md)。

**二、难度地图和直觉是反的。**

| | 性质 | 状态 |
| --- | --- | --- |
| 怎么组织一群不确定的执行体 | **设计难**——没有现成答案,买不到抄不来,失败模式隐蔽 | 人版已跑通 |
| 怎么判断执行体做得对不对 | **工程难**——方法已知,费钱费时但路清楚 | 未做 |

所以不要按「先建判据与回路,再谈组织多个执行体」排期。
**也不要把协作层跑通误读成执行内核已验证**:那是另一条线,另有它自己的可证伪条件。
