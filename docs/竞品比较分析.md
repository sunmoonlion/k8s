# 竞品比较分析

更新日期：2026-10-14（二次查证修订）。对象：腾讯 WorkBuddy、Meta Muse；比较基准：SunMoonAI 的 investment 工作台及 knowfeed、knowbase、规划中的 knowmart-app（2026-10-14 改名：info → knowfeed、knowledge → knowbase、advisor → knowmart）。

**本次修订口径：** 用户已明确，前次排查的问题正在完善代码、尚未发布，预计很快解决。因此，目录准备、登录提示、专家版本绑定和 Windows 写文件等问题，仅视为修复中的工程事项，不再作为产品竞争力的主要论据，也不写成已经上线解决。本轮重点是：这些问题解决之后，我们还应向竞品学习什么，哪些现有能力需要继续深化。

证据分为官方披露、已读代码、设计方向和分析建议。竞品未做登录后同题实测，本次也不进行我方新版本发布验收；不对三方准确率、稳定性、速度或费用作无依据排名。代码检查是当前本地工作区快照，不代表正在其他工作区开发的全部内容。

## 一、修订后的判断

WorkBuddy 值得借鉴的是把上下文、外部服务、执行和成果组织成连续的办公流程；Muse 值得借鉴的是让用户围绕目标持续委托，并只在有价值的变化或需要决定时回来参与。我们的长期机会，是把这些使用体验与专业数据、明确方法和可复核交付结合起来。

我们已经具备聊天、工作、专家、项目记录、本地文件访问、长期记忆管理和分步验收等基础，不能继续用“有没有这些按钮”作为比较重点。需要验证的是这些能力是否让用户少重复说明、少查找材料、少手工复核，并能在下次研究时复用已有成果。

建议优先探索三个方向：

1. **研究上下文的连续性：** 换对话、换专家或更新数据后，仍清楚研究对象、口径、已确认事实和待验证假设。
2. **成果的后续使用：** 不止交回一个文件，还能定位依据、进行修订、比较新旧变化，并将结果用于下一次任务。
3. **可控的持续跟踪：** 从已完成任务转成用户明确授权的跟踪工作，有新信息才更新，有重要变化才提醒。

以上是产品建议，不自动改变已有账号、文件归属、审批和专家方法的决定。

## 四、我们还应关注的产品问题与借鉴方式

本节讨论的是修复完成后仍值得研究的产品问题。标为“待验证”的内容是本次未取得完整证据，不能直接列为现网缺陷。

### 4.1 用户为什么选择我们：需要更具体的任务承诺

**问题：** “聊天、工作、专家”解释了使用方式，还没有充分解释用户第一次应该把什么任务交进来。“财务分析与预测”这样的大名称，也可能超出某一版专家实际支持的数据与方法。

当前财务预测方案以 Olist 演示和评测数据起步，文档明确其缺少成本数据，A 股财务预测不在该方案首期范围。这个范围事实与上午的实现故障无关，应通过产品介绍清楚呈现。[0023 财务预测方案](dev-investment-agent/tree-build/SDD/modules/0023-fin-forecast.md)

**借鉴：** 学习竞品把能力放进具体场景的表达方式，为每位专家提供少量任务样例、所需数据、样例成果和适用限制。选择样例后保留原问题，让用户替换对象和时间，不要求先理解内部步骤。

**最小改进：** 在既有专家详情和输入框提供“输入示例—需要哪些资料—交回什么”的说明，并明确演示数据与用户实际业务数据的区别。

**验证：** 新用户能否在不求助的情况下选对任务；首次取得有用结果需要多少时间；不适用的问题是否在消耗大量资源前被说明。

### 4.2 记忆已经有了，下一步是让研究背景保持准确

**问题：** 用户偏好、项目事实、分析假设和已经过期的判断不能混在一段背景文字里。保存过一条信息，也不代表每次任务都该引用它。

**现有基础：** 我们已有用户事实记忆和项目对话读取。`memory_note` 目前将启用条目组装为有限长度的背景；它不是针对研究对象管理事实、假设与时效的完整系统。

**借鉴：** WorkBuddy 提供可更正的记忆，Muse 将持续背景与不同话题结合。我们应优先发展用户可检查、可修正的研究背景，而非自动记住所有聊天。

**最小改进：** 在现有机制上先明确三类内容及来源：用户偏好、项目事实、待验证假设。项目事实记录对象与数据日期；假设不自动升级为事实。换公司、换期间或换数据版本时，提示需要重新确认的相关内容。具体保存位置沿用各自既有真源。

**验证：** 第二次任务是否减少重复说明；跨公司是否串用背景；撤回或过期的信息是否仍被引用。这里的成功标准是准确复用，而非记忆条目数量。

### 4.3 让专家主动选取相关上下文，而非每次重读全部材料

**问题：** 同一项目会积累多段对话、多份底稿和用户改动。工具能够读取这些内容，是基础；能否正确找到这次需要的材料、识别前后矛盾，还需要验证。

**借鉴：** WorkBuddy 用项目组织共享背景，Muse 在连续对话之外保留话题分隔。我们可以保留本地项目定义，把关注点放在“这次用了哪些背景、为什么”。

**最小改进：** 为当前研究维护可检查的材料索引：研究对象、已选数据版本、相关底稿、用户确认的约束和未决问题。开始任务时按相关性选取，完整材料通过已有工具读取。索引引用原文件和对话，不另存一套独立结论。

**验证：** 追问时是否重新取了不必要的数据；变更一项假设后是否只重算受影响部分；旧底稿与新数据冲突时是否明确说明。

### 4.4 从“文件已交付”深化到“成果可以继续使用”

**问题：** 用户拿到 Markdown 不一定意味着已经完成工作。还可能要检查某个数字、修改一条假设、与上次结果比较，或形成可交给同事的表格。

**现有基础：** 已有文件树、预览、改动和底稿面板。应在这些组件上完善体验，而不是重新创建独立结果页。

**借鉴：** WorkBuddy 把预览与修改放在同一工作区，Muse 根据任务选择产物形式。我们可以针对研究任务增加更具体的操作。

**最小改进：** 给交付文件提供清晰的摘要和入口：打开文件、查看相关依据、与上次交付比较、基于此继续研究。随后评估选择一行数据或一段文字发起追问。数值任务优先提供可复算表格；交互图表只在有助于探索假设时使用。

**约束：** 项目文件继续作为用户成果真源。分析视图引用文件及执行证据，避免用户编辑文件后，另一个页面仍显示旧结论。

**验证：** 用户找到一个数字的来源需要多久；完成一次修订是否必须重新描述整项任务；离开对话后成果是否仍可正常使用。

### 4.5 持续研究需要事件与变化管理，不只是定时重复提问

**问题：** 分析经常围绕新数据反复进行。即使每次都能完成，用户仍可能要人工检查数据是否更新、重新发起、比较变化。

**现有基础：** 0019 已提出个人信息采集及周期重取。不能重复建议“从零做采集”；应评估从采集完成到研究更新之间还缺哪些环节。

**借鉴：** WorkBuddy 的周期任务适合固定重复工作；Muse 的目标与事件推进启发我们围绕研究目标组织后续行动。

**最小改进：** 从一次完成的研究中，让用户明确选择“下次同一数据源更新时，按此口径再做一次”。记录目标、触发条件、停止条件和允许动作。先比较数据版本，有变化才决定是否运行；完成后重点说明相较上次改变了什么。

**约束：** 这只是未来产品能力建议，本次不创建后台任务。用户电脑离线时，涉及本地文件的操作保持等待或按已定恢复策略处理；不得静默改到云端执行。通知与结果独立，通知失败不重复整项任务。

**验证：** 重复触发是否造成重复任务；无数据变化时的无效执行比例；变化提醒是否有用；用户能否看懂并停止持续工作。

### 4.6 数据能力应变成用户可理解的研究覆盖

**问题：** 有数据集目录、口径工具，不等于用户知道某个问题现在能不能做。覆盖不足、资料过期、指标不可计算，是专业产品长期需要管理的边界。

**借鉴：** WorkBuddy 将连接器按任务需要引入，Muse 小企业版围绕用户现有业务资料开展工作。我们可以把自己的数据覆盖与外部依赖显示为完成任务的条件，而不是要求用户自己浏览多个服务。

**最小改进：** 在研究范围确定后展示简短材料摘要：对象、时间范围、可用指标、缺失项、数据截至日期及出处。缺失时指出具体补充路径；已有数据满足时直接推进。连接器建设从目标用户最常遇到的材料来源开始，不追求数量。

**延伸方向：** 区分公开数据、专家资料与用户项目材料的作用，支持追问“这个结果来自哪一层资料”。自动选择数据仍需受对象、时间和口径约束。

**验证：** 用户为提供材料切换多少页面；选择正确数据所需时间；覆盖说明与实际结果是否一致；接入一个新数据源是否提升了目标任务完成率。

### 4.7 用户应看懂自主程度与下一步，不必理解内部状态机

**问题：** 长任务的使用成本包含等待与不确定性。用户需要知道已经完成什么、还缺什么、哪些行动会来问自己，以及此时是否值得继续。

**借鉴：** Muse 用活动与目标视图说明后台工作，权限决定则使用明确控件；WorkBuddy 会把任务结果和待确认信息带回工作入口。可以借鉴信息组织，保留我们现有聊天、工作和专家三种入口。

**最小改进：** 任务顶部用简短摘要呈现当前目标、已完成成果、阻塞原因、下一步及费用。审批沿用现有权限规则，说明具体对象与后果；已有授权的常规步骤顺畅执行。不要把每个内部工具事件都当作需要用户处理的消息。

**持续授权另行讨论：** 若未来支持周期任务，新增授权必须限定对象、时间与动作范围；不能把一次写文件批准泛化为长期对外发布权限。

**验证：** 用户是否知道下一步由谁处理；无意义中断次数；读进度花费的时间；重要审批是否容易被识别。

### 4.8 专家方法需要证明增益，也要适应模型进步

**问题：** 拆成更多步骤不自动带来更高质量。能力较强的模型可能在普通工作模式下就能完成简单任务；固定流程带来的等待和费用必须有理由。

**现有基础：** 项目早已设计“数据—方法—评测”的价值检验，且有相关实现。应深化这套机制，不把建设评测描述成尚未开始。[价值检验设计](dev-investment-agent/tree-build/PRD/value.md)

**借鉴：** 通用代理和专家生态都在扩展任务覆盖。对我们的启示是，把方法效果作为可测量产品属性，而不是仅通过“专家”称呼表达。

**最小改进：** 选一个边界清楚的场景，用相同模型、相同数据比较普通工作与专家执行。记录专业正确性、引用、费用和人工复核时间。对证据表明冗余的步骤，由作者发布方法新版本调整，保留必要检查，不在执行中静默改变契约。

**进一步判断：** 多专家并行适合可独立拆分的任务，但不能用专家团数量证明质量。先用单专家建立基线，确有收益再评估并行。

**验证：** 专家相对“同样工具和数据的普通代理”带来多大提升；模型更新后优势是否仍在；提升是否值得额外费用。

### 4.9 市场、分享和协作应服务于真实复用

**问题：** 作者能够上架，不等于用户能选对专家；用户能打开一份成果，也不等于同事能理解和复核。供给和使用之间仍要建立信任。

**借鉴：** WorkBuddy 的市场、项目与产物分享降低了能力被发现和传递的成本。我们可先学习能力表达与成果交接，不必立刻把本地项目改成团队云空间。

**最小改进：** 专家页展示适用任务、样例交付、必要条件及有范围说明的评测结果。成果交接先使用用户可主动导出的文件组合，包含正文、数据说明及必要依据；不默认上传私有资料。

**后续方向：** 如果用户确有团队复核需求，再评估评论、授权分享、交接和共同维护。专家市场的版本与评价机制见[专家市场架构对比分析和借鉴](专家市场架构对比分析和借鉴.md)，不在本文复制其架构。

**验证：** 用户能否正确选择专家；接收成果的人是否能独立理解；合格交付后是否复用；作者是否能依据质量反馈持续改进。

## 五、怎样借鉴：建议顺序与投入边界

以下顺序是研究建议，实施前仍需结合当前正在开发的范围与真实用户反馈。上午问题的修复继续按原工程安排完成，不占用本节的长期产品排序。

| 优先顺序 | 建议 | 原有基础 | 最小可评估成果 | 不急于扩展的部分 |
| --- | --- | --- | --- | --- |
| 第一组 | 场景表达与专家能力边界 | 专家卡、六问、现有样例 | 新用户能选对一项任务并知道需要什么资料 | 大量专家或复杂推荐算法 |
| 第一组 | 研究上下文与依据复用 | 记忆、项目对话和本地文件读取 | 连续两次任务少重复说明，事实与假设不混用 | 自动记住所有会话 |
| 第一组 | 成果复核与后续修改 | 文件树、底稿及改动面板 | 找到依据、比较两版、基于成果继续做 | 独立结果数据库或通用在线编辑器 |
| 第一组 | 专家价值对照 | 既有评测及数据服务 | 一类任务质量、复核时间和费用的对照报告 | 用历史小样本给全产品打分 |
| 第二组 | 有边界的持续研究 | 采集与任务机制 | 用户授权后的一种更新触发流程 | 大规模无人值守任务调度 |
| 第二组 | 少量高价值数据连接 | MCP、knowbase 与 knowfeed | 减少一个实际材料准备障碍 | 只追求连接器数量 |
| 按需求 | 移动处理与成果交接 | 网页、文件交付和审批 | 在支持的边界内查看状态、处理决定、取得成果 | 自动上传本地资料、完整团队协作 |
| 按证据 | 多专家、更多执行环境 | 市场和执行架构方向 | 对特定任务有可测量提升 | 全面复制竞品的所有形态 |

## 六、串起来看：一个值得验证的研究流程

以下是未来体验示例，不代表当前全部已经可用，也不承诺现有财务专家覆盖示例所需的全部数据和方法。

1. 用户选择一项边界明确的研究任务，系统说明适用数据与交付形式。
2. 沿用项目中已确认的对象和口径；只问本次新增的不确定信息。
3. 使用带版本的材料完成研究，展示简明进度，按既有授权推进。
4. 交付到项目文件；用户可以打开表格、查看出处、选择一处发起修改。
5. 用户主动选择持续跟踪，并明确触发条件、范围和停止方式。
6. 后续数据更新时，比较与上次的变化，按约定决定是否重做及通知。
7. 下一次研究引用确认过的背景和已有成果，保留出处与有效期。

这条流程结合了 WorkBuddy 的工作组织与 Muse 的持续目标体验，同时可以保留我们的专业数据、方法验收和本地文件定位。价值应以用户少做了多少重复工作、成果更容易复核多少来判断。

## 七、公平的验证方法

### 7.1 将能力贡献与产品体验分开测试

| 测试 | 保持相同 | 回答的问题 |
| --- | --- | --- |
| 三方产品同题 | 任务、可提供的数据、时间和费用范围 | 用户用完整产品时实际体验如何 |
| 我方普通工作与专家对照 | 模型、数据版本、工具、输入 | 专家方法和验收贡献多少 |
| 静态文件与原生数据服务对照 | 问题、期望输出、核验口径 | 数据准备与专业服务贡献多少 |
| 连续任务测试 | 同一项目，第二次新增一项数据或修正 | 上下文与成果复用是否有效 |

竞品不能使用相同模型时，明确这是产品整体比较，不归因于编排架构。竞品无法接入某个数据源时，将这一点记录为条件差异，不在准确率里混算。

### 7.2 首批场景

| 场景 | 观察重点 |
| --- | --- |
| 首次使用 | 从目标到正确选择专家，是否理解资料要求和成果 |
| 跨对话续做 | 换对话后能否沿用已确认背景，并明确引用来源 |
| 假设变更 | 修改一项假设，能否指出受影响范围并正确更新 |
| 新旧资料冲突 | 能否识别版本差异，而不是顺着旧记忆作答 |
| 成果复核 | 用户能否快速定位数字来源、计算过程与局限 |
| 更新跟踪 | 是否只对有效变化执行和通知，能否停止 |
| 成果交接 | 另一人仅凭交付材料能否理解和复核 |

指标包括：专业正确性、首次有效成果时间、人工复核时间、重复说明次数、不必要的取数与执行、通知有用程度、总费用，以及第二次任务的节省幅度。

可以先每类做少量重复试验找问题，但不能据此发布总体成功率或胜率。旧故障回归属于发布验证；竞品测试关注用户价值，两类记录分别保存。
