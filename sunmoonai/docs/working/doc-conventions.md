# 文档写作与维护约定

> 最后更新：2026-08-29
>
> **本文件管的是「怎么写这套文档」，不是项目本身。**项目现状见
> [`../project-guide/`](../project-guide/)；代码要遵守的约束见
> [`../dev-plan/constraints.md`](../dev-plan/constraints.md)。

## 1. 漂移：什么时候必须更新文档

不经请求流程的直接开发是自由的，**不设强制标记义务**——约定无法保证执行。
义务只加在**能保证执行的一方**：**智能体读到代码与本文档集矛盾时，
必须主动指出并提出更新建议**，是否更新由用户决定。

### 判断尺子

该改动是否改变了"另一个仓的开发者或新来者也需要遵守"的事实？命中即构成漂移：

1. **跨仓边界**：新增或修改跨 App 的 API、事件、契约、服务身份
2. **拓扑与组件**：增删拆分 backend / admin / web / worker，改仓库组成、发布单元、版本语义
3. **身份与认证**：改 Casdoor application、audience / cookie / 表面配对、鉴权分区
4. **模板与实例**：动模板导致实例需同步，或改门禁规则
5. **先例性变更**：做了"以后每个 App 都会照抄"的事——第一个实现就是事实基线
6. **与文档矛盾**：改动推翻本文档集的任何一句——代码赢，文档必须跟上

**不构成漂移**（纯仓内、不影响跨仓认知）：单仓内部实现（算法 / UI / 单库表结构 /
bugfix / 性能）、不改发布单元的依赖微调、不改门禁语义的测试与 CI 细节。

## 2. 三条维护约定

1. **每个事实只有一个权威位置。**跨仓事实进 `topics/`；仓内事实进 `repos/<仓>.md`。
   判断标准是"这个事实将来变了，应该在哪一处改"。**两处都写 = 必然漂移。**
2. **每份文档带时点。**头部写"取证时点"（对代码取证的日期）或"最后更新"。
   没有时点的断言无法判断该不该信。
3. **引用而非复制。**写"见 §X"加一句话结论，不抄全文，更不抄参数值。

## 3. 写作约定

1. **每条断言可落到位置或可执行命令。**给不出取证的句子应删除，不靠推测补全。
2. **易腐值不进正文。**镜像 digest、schema sha256、commit、迁移 head、副本数，
   变化比文档维护快，写进来必然先于文档失效。只写规则并指向真源。
   - **验证命令禁用行号**（`sed -n '12,34p'`）——代码一动就静默产出错误输出。
     用模式锚定：`sed -n '/<起始模式>/,/<结束模式>/p'`。
   - 正文里的 `file:line` 作为**近似指针**可以保留，但不得作为验证手段。
3. **主动写「已知未实现」。**"静态占位页""未接线"是合法且必要的事实陈述——
   这是文档主动暴露缺口的地方，通常也是读者最需要先知道的一节。
4. **不写历史演进叙事。**"原来是…""已改为…"一类由 git 承担；正文只写现状。

## 4. 编辑自检

任何一次新增或修改本文档集，**必须同时完成**，缺一项视为未完成：

1. 更新该文档头部的时点；
2. 确认新写入的事实**没有第二处复述**（有则改为引用）；
3. 检查被改动章节在其它文档中的引用是否仍成立——**改结构时链接最容易断**；
4. 断言若能落成测试，就落成测试；落不成的，在
   [`../dev-plan/constraints.md`](../dev-plan/constraints.md) 里老实标 ⚠。
   **不要靠"记得跑某个脚本"来把关**——那和写在文档里的规矩没有区别。

## 5. 请求完成后怎么更新文档

**禁止「吸收」。**请求实施完成后，其长期有效事实进入本文档集的方式是
**回读代码重新取证重写**，**不得搬运请求文件里的文字**。

重写投影时**只读代码，不读本文档集的旧版本**——否则产出会退化为对旧文本的改写，
与代码是否一致完全靠运气。这条是整套方法里最要紧的一句。

配套的四条：每条断言必须给出位置或可执行命令，给不出的一律删除，不靠推测补全；
**实际跑测试**，不满足于静态读码；强制产出「已知未实现」一节，主动找占位、
未接线、TODO、空实现、被 flag 关掉的东西；**产出方不自验**，高影响断言由另一方复核。

理由有实测依据，两条：

1. 一次核对核出 14 条偏差，其中 7–8 条不是"代码改了文档没跟"，
   而是**目标态文字被原样搬进现状文档，从此以"事实"身份流传**。
2. 2026-08 有三份独立写成的架构基线，**都读过同一批文件，都漏了同一处版本矛盾**
   （见 [`overall-architecture.md`](../project-guide/overall-architecture.md) §9.1）。
   这是"**不能靠拼接现有文档做整合**"的直接证据——三份文档叠加，
   漏的还是同一处；只有回代码才能补上。

这条规则不增加工作量，只要求"重写"而不是"复制粘贴"。
