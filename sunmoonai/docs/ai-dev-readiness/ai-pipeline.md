# AI 执行开发时，pipeline 要怎么改

> 起草：2026-09-04 ｜ 前提：**开发工作全部由 AI 助手承担**，人只提需求、拍板、验收
>
> 本文是 [`standard-pipeline.md`](standard-pipeline.md) 加上这个前提之后的**改法**。
> 那份写的是行业通用实践（横轴：流程该有哪些格子），
> [`readiness.md`](readiness.md) 写的是每格判据由谁执行（纵轴：机器还是纪律），
> **本文是两者的交点**。
>
> 三份都**不承担规范效力**，是讨论材料。落地去向见
> [`README.md`](README.md)。

---

## 1. 为什么这不是微调

加上"由 AI 执行"这个条件，改变的不是流程的某几步，而是**三个成本结构同时翻转**：

| 成本 | 人类团队 | AI 执行时 |
| --- | --- | --- |
| **产出**（写代码、写文档、写测试） | 高，是瓶颈 | **趋近 0** |
| **验证**（读、判断对不对） | 中，靠评审 + 常识兜底 | **不变**——人的时间是唯一没变便宜的东西 |
| **上下文延续** | 靠记忆、口头传承、坐在旁边 | **归零**，每次冷启动 |

于是：

- 瓶颈从**产出**搬到**可信度**；
- 稀缺资源从**工时**变成**人的注意力**。

经典 pipeline 的不少设计——控制 PR 大小、批量式阶段交接、估点排期——
是为**产出昂贵**优化的。前提没了，那些设计就不再是最优，有的甚至有害。

还有一条比成本更要命的：**AI 产出的东西"看起来对"的概率极高，而且错得通顺。**
人类开发者不懂时会卡住、会问；AI 不懂时会流畅地编，语气与正确时无异。
**这直接摧毁了经典流程里最大的一道防线——"评审人一看就知道不对"。**

## 2. 八条改法

每条给出：改什么、为什么、以及**本项目现在有没有一半**。

### 2.1 判据前移并机器化

**改什么**：每个阶段的准出判据，必须在**阶段开始前**就写成可执行的检查，
而不是事后靠人看。

**为什么**：人眼那道防线的有效性大幅下降（见上节末段）。
一个只能靠"读起来对不对"判断的准出判据，在 AI 流程里等于没有判据。

**直接后果**：**TDD 从"最佳实践"变成结构性必需。**
测试是需求的可执行形式，必须先于实现存在——
否则实现方会写出"恰好能通过自己所写测试"的东西，而且那些测试也读起来很像样。

**本项目已有的一半**：L1–L7 测试层次已分好，任务模板有"测试"栏且**缺栏视为未定义、不开工**。
缺的是"测试先于实现"的强制，以及产品契约的 47 个编号与测试之间的对应
（`readiness.md` 议题一）。

### 2.2 新增人类专属阶段：意图确认

**改什么**：在需求与实现之间插一次廉价往返——

```
AI 复述需求（用自己的话）
  + 列出它将要做的决策点
  + 标出它认为有歧义的地方
→ 人确认或纠正
→ 才允许开工
```

**为什么**：人类团队里需求偏差靠日常交流不断校正；AI 执行时，
人写的需求被解释一次，**偏差要到交付才暴露**，返工成本最高。

这一步很便宜（几分钟），挡掉的是最贵的错误。**它是整套改法里投入产出比最高的一条。**

**本项目已有的一半**：REQ 模板的「①原始需求（一字不改）②架构评审」
已经是这个形状的一半——①保住了意图证据不被改写。
缺的是"AI 复述 + 决策点清单 + 人确认"这一步，
现在评审直接从原始需求跳到结论。

### 2.3 阶段变少、门变多、门变自动

**改什么**：合并阶段、允许高频循环，但每一圈都过门，且"进入代码库"那道门必须硬。

**为什么**：人类流程的阶段划分，部分原因是**批量传递成本高**
（设计交给开发、开发交给测试，每次切换都贵，所以要攒够一批再交）。
AI 切换成本近乎 0，攒批毫无收益——设计、实现、测试可以在一次会话里转好几圈。

净效果：**流程图变短，门禁数量变多，且几乎全部自动化。**

**本项目已有的一半**：`doc-gate.py` 是"随提交自动跑"那层的样板，已经证明可行。
缺的是代码侧的同类门（测试没有挂进 `.githooks`，也没有 CI）。

### 2.4 评审改成「机器全审 + 人抽检三样」

**改什么**：

| 层 | 谁做 | 审什么 |
| --- | --- | --- |
| 机器 | CI / 门禁 | 全部机械判据：格式、lint、类型、测试、契约一致、文档门禁 |
| 人 | 人，**只审三样** | ① 意图是否被正确理解 ② 不可逆的部分 ③ **抽样复算证据的真实性** |

**为什么**："控制 PR 大小"这条纪律在 AI 面前撑不住——它一次就能产出巨大的 diff，
且拆小的成本对它几乎为零、对人的评审带宽却没帮助（总量不变）。
人逐行读 AI 的 diff 是低效且不可靠的。

**第三项是新增的，也最容易被忽略**：AI 报告"测试全绿"**不可信**，
不是因为它撒谎，而是因为它可能跑的不是那件事、或者环境不对而它没意识到。
证据必须是 CI 产出的，或是人能自己重跑的可复跑命令。

**本项目已有的一半**：`evidence/` 目录 + "可复跑命令锚点"的取证纪律已经在做这件事。
它在人类流程里是加分项，**在 AI 流程里是必需项**。

### 2.5 文档三分法要加第四类：上下文包

**改什么**：在决策 / 规格 / 状态之外，新增一类：

| 类 | 写给谁 | 判据 |
| --- | --- | --- |
| **上下文包** | 冷启动的 AI | **短**（占上下文预算）、**准**（错了比没有更糟）、**自动注入**（进目录就带上） |

**为什么**：经典三分法的隐含前提是**人有隐性知识**——知道去问谁、知道哪份文档过期了、
知道这个目录名骗人。AI 的隐性知识为零。

这类文档的判据很特殊：**它是唯一一类"越短越好"的文档**，
因为每一行都在挤占助手干活的上下文预算。写长了不是更周到，是更差。

它也不属于原来三类中的任何一类：不是决策（会变）、不是规格（不随代码同步）、
不是状态（不每天变），**它随项目结构变**。

**本项目已有的一半**：五仓根 `AGENTS.md` + 八个组件 `CLAUDE.md`，
`constraints.md` 三层表里明确标了"进目录自动注入"。
缺的是把它当成一类文档来管——现在没人定它该多短、该多久校一次准。

### 2.6 出题方与答题方必须分离

**改什么**：切开三处——

| 环节 | 要求 |
| --- | --- |
| 验收标准 | 由需求阶段产生，**不由实现方产生** |
| 测试 | 不能在实现写完之后由同一会话补 |
| 验收 | 由独立方执行 |

**为什么**：人类团队里开发者写自己的单测是可接受的，因为有同事评审兜底。
AI 流程里，**自己写实现 + 自己写测试 + 自己报告通过 = 三位一体的自证**，
等于没有验证。而且这种自证产物的表面质量往往很高，更难被发现。

同理适用于任何"AI 给 AI 打分"的场合：金标准不能由答题的模型出题，
评审方与被评审方不能是同一次会话。

**本项目已有的一半**：[`round-protocol.md`](../dev-plan/round-protocol.md)
的角色分离（提案 / 评优 / 裁决 / 验收 / 确认）已经把这条想透了，
2026-09-03 那次失败整合也反证了它的必要——五条毛病全部源于角色不分。
**缺的是把它从大轮次下沉到日常任务。**

### 2.7 拆分粒度换标准

**改什么**：

| | 拆分标准 |
| --- | --- |
| 人类 | 控制在**评审人读得动**的量（几百行） |
| AI | 这个单元有没有**独立的、机器可判的验收**？有 → 可以很大；没有 → 再小也不该开工 |

**为什么**：评审带宽不再是约束（人已经不逐行读了），可验证性才是。
一个没有独立验收的小改动，和一个有独立验收的大改动，后者安全得多。

**本项目已有的一半**：`development-lifecycle-agent.md` 已有一条形状正确的判据——
**「把当前会话杀掉，另一个执行者只读持久载体能否接着做」**。
建议把它从 checkpoint 的判据提升为**派工的准入条件**：
通不过说明还没拆到可以交给 AI 的粒度，**不是助手的问题**。

### 2.8 不可逆动作靠门禁，不靠纪律

**改什么**：显式列出不可逆动作清单，每条配硬门禁（权限、审批、沙箱），
而不是写在文档里提醒。

**为什么**：人在执行破坏性操作前会本能犹豫；AI 不会，除非被挡住。
更麻烦的是**它执行破坏性操作时的语气和执行安全操作时完全一样**，
所以"看着点"这种人工兜底也不成立。

**本项目已有的一半**：`readiness.md` 议题四已经立了通用规则——
**凡是"忘了做"与"故意做"在代码里长得一样的地方，都要显式化**。
那里给的实证是 Codex SDK 的默认审批处理器自动 accept，且兜底发生在构造函数里。

## 3. 改完之后的 pipeline

| # | 阶段 | 谁做 | 准出判据 |
| --- | --- | --- | --- |
| 1 | 需求 + **意图确认** | 人提，AI 复述并列决策点 | 人确认复述无偏差 |
| 2 | **验收标准先行** | AI 起草，人拍板 | 每条验收都指向一个未来的测试标识 |
| 3 | 设计与契约 | AI 起草，人只评审不可逆部分 | 契约可被机器校验；ADR 记清代价 |
| 4 | **测试先行** | AI，**与实现分离的角色** | 测试为红，且红的原因正确 |
| 5 | 实现 | AI | 测试转绿 + 质量门全绿 |
| 6 | 机器评审 | CI / 门禁 | 全绿，**不许例外** |
| 7 | **人类抽检** | 人 | 意图 / 不可逆 / 证据抽样，三项通过 |
| 8 | 发布 | AI 执行，人授权 | 回滚路径已验证 |
| 9 | 反馈 | AI 起草复盘，人确认 | 改进项进待办 |

与经典九阶段对比：

| 变化 | 说明 |
| --- | --- |
| **没变** | 交互设计（它本来就该人主导）、发布与反馈的形状 |
| **基本消失** | 拆解排期——估点与批量排期在这里没有意义 |
| **新增三格** | 1 的意图确认、2 的验收先行、7 的人类抽检 |

**三个新增全部是人的动作。** 这不是巧合：

> AI 承担执行之后，人的工作从"做"整体迁移到**"定义"和"验证"**两端，
> 中间交给机器守门。

## 4. 什么加重、什么可以删

| 加重 | 为什么 |
| --- | --- |
| 需求与验收标准的精确度 | 没人会"凭常识补全"，写多含糊就执行多含糊 |
| 证据链与可复算性 | 不能信自述 |
| 上下文入口文档 | 每次冷启动 |
| 不可逆动作的门禁 | AI 不会犹豫，语气也不会变 |
| 角色分离 | 防自证 |

| 可删或轻化 | 为什么 |
| --- | --- |
| 工时估点、燃尽图 | 比在人类团队里更没意义 |
| 控制 PR 大小 | 换成"可验证性"标准 |
| 批量式阶段交接 | 切换成本没了 |
| 多级人工评审 | 换成机器全审 + 人抽检三样 |

## 5. 一个反直觉的结论

流程**总量**不一定变多，但**分布**完全变了：

```
人类流程：  轻前期  →  重实现  →  重评审  →  轻交付
AI  流程：  重前期  →  轻实现  →  重门禁  →  重抽检
```

很多人的直觉是"AI 快，流程可以更轻"。**恰恰相反**——
正因为实现变得几乎免费，**前期定义和后期验证的相对重量必须加大**，
否则产出量会淹没验证能力，形成"生成得越多、可信的越少"的负向循环。

`readiness.md` 里那句"AI 会 100% 声称满足一条无法被证伪的规则"，
在 pipeline 语境下的等价表述是：

> **判据跟不上产能，流程就退化成产出垃圾的加速器。**
