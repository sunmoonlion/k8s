## 0. 结论一览

1. **生成式模型调用只在用户电脑上发生，费用由用户承担。**本地 runtime 内置原版 Codex，用用户自己的 key 直连模型厂商；后端需要模型判断时，也经推理请求交给本地 runtime、用用户的模型去做（1.5）。后端不持有用户 key，不中转模型请求；只在知识检索（embedding、rerank）和长期记忆上使用自有模型，与用户的模型调用无关。
2. **后端是 supervisor：以 workflow 为主的控制面。**Task、Attempt、Interaction、四本账都在后端的 PostgreSQL；路由与编排按规则和 workflow 确定性地推进，少量需要模型判断的环节发推理请求到本地；需要执行的工作作为 Attempt 派给本地 Codex。
3. **不再分别建设通用 agent 与专业 agent。**执行体只有一个（Codex），任务之间的区别只在 Profile 与 workflow：supervisor 按「规则 → 本地推理分类 → 拿不准交用户选」路由，通用任务用收紧能力的通用 Profile 直接派发，专业任务按 workflow 拆步派发；执行中 Codex 发现需要领域能力时调 `escalate` 工具兜底，由 supervisor 裁决（1.5）。
4. **资料分两处：用户的留在本地，我们的按上下文下发。**用户自己的资料、Codex 从公开渠道取回的资料（公告等由 Codex 自己去查，我们不提供）放在用户电脑上的本地知识库；我们的自有数据（info-app 采集、knowledge-app 建库）经 MCP 按查询以上下文形式下发，不整批同步（1.9）。
5. **主要工作界面是 Electron 桌面应用，网页端作为辅助端。**按投资经理开发，能自己开通和配置模型 key 的散户同样适用；两类用户都不是开发者、都在电脑桌面上工作，按商业因素选桌面应用（第 2 节）；网页端承担 Task 级审查、账号、计费与报告；手机不作为工作端。只做下载即用，不做私有部署；平台 Windows 优先、macOS 其次（1.1）。
6. **执行层租用、不自建（A4）。**本地 runtime 建议做成 Python 后台进程，经 Codex Python SDK 驱动 Codex，并替换 SDK 默认的"自动同意"审批处理；审批策略要把所有命令与文件修改都送进回调。
7. **审批分两层。**工具级审批由本地 runtime 执行并上报；Task 级审批按合同在后端落 Interaction、原子消费。审批分层挡不住"被攻破的后端派发恶意 Attempt"，另需派发签名、本地确认与收紧自动放行范围（1.7）。
8. **断线即暂停。**失去租约时中断正在跑的运行时 turn，不产生新的副作用；重连后按 fencing 对账，再决定恢复原运行时 thread 还是开新 Attempt（1.12）。
9. **每个 Attempt 在自己的独立工作区里执行；副作用记账粒度（D6）是本方案能否成立的前置决策。**独立工作区内的写入按运行时 turn 批量记账，改动经 Task 级批准后才合进用户的工作区；不可逆动作逐条记账（1.12）。
10. **核心价值是自有数据与编排。**编排逻辑留在后端、按步下发，核心计算在 MCP 工具内部执行（1.5、1.9）。用户拿原版 Codex 自己就能做到的，不算卖点；每项功能都要过这道检验，并用"原版 Codex 对比本产品"的领域评测给出证据（1.15）。
11. **定位是 AI 研究能力与数据，类似 Wind，不做投资咨询。**分析在用户电脑上、由用户发起和主导，判断由用户下；我们提供数据、编排与 AI 能力。边界有模糊地带，由律师定夺（1.1、D25）。

## 1. 总体设计

### 1.1 目标用户与前提

**目标用户**：按**投资经理**开发。能自己开通和配置模型 key 的散户同样适用，不另做面向大众散户的简化——连 key 都配不了的用户不在服务范围内。两类用户都不是开发者，以**电脑桌面**为主要工作场所；手机不作为工作端，至多查看状态与结果（D23）。

**范围**：只做**下载即用**，不做私有部署，有私有化客户时再说；平台 Windows 优先、macOS 其次。以下后置，文中相关内容保留作后续参考：私有化部署、企业网关、团队协作与共享（先按个人使用开发）、统一分发、Linux 与信创平台。

**产品定位**：我们提供 **AI 研究能力与数据**，类似 Wind，不做投资咨询：用户用自己的资料、在自己的电脑上、借助我们的数据与编排做研究，判断由用户自己下。这一定位对投资经理与散户相同，客户类型只影响产品配置。它在架构上有实在的支撑：

| 事实 | 落到哪里 |
| --- | --- |
| 用户的资料与研究成果在用户电脑上 | 本地知识库（1.9）；结果的存放见 D30 |
| 执行在用户电脑上，由用户发起和主导 | 本地 runtime 与 Codex（1.6） |
| 模型由用户自选、开通、付费 | 1.8 |
| 我们提供的是数据，不是观点：自有数据只装事实与数据，不装评级、目标价、景气判断 | knowledge-app（1.9） |
| 我们的编排与方法库只写方法，不写判断规则 | workflow 与 skills 的评审（1.5） |
| 系统不替用户下判断 | validator 的输出检查（1.5） |

边界上有模糊地带，最后由律师定夺（D25）。建议从现在起有意识地留存证据：数据流图、「后端不存哪些东西」的清单、日志策略、skills 评审记录。

**目标**：用户在桌面应用里提交 Task；后端受理、编排并验收；Agent 在用户电脑上执行，读写本地工作区、调用模型、调用知识服务；结果可靠持久化并可重新取得。完整语义以 `request-lifecycle.md` 为准。

**前提**：

- 执行端（本地 runtime 与 Codex）在用户电脑上，与桌面应用同机；网页端可以在任何能登录的地方使用，只承担不需要本机的事（2.8）；后端一般在另一台机器（私有化部署时也可以同机）。
- 生成式模型调用只由本地 runtime 负责；模型选择与配置在桌面应用里做（runtime 由我们随应用分发）。
- 桌面应用与 runtime 之间走本机进程通信，不开端口；网页端只连后端，与本机没有通道。

**目标用户对前提的检查**：下面几条前提原本按开发者的习惯定，对目标用户要重新落实：

| 前提 | 对目标用户的问题 | 待定 |
| --- | --- | --- |
| 用户自带 key、模型费用由用户承担 | 目标用户能自己开通与配置 key；保留基本引导与粘贴后当场测可用与余额；提交前显示预估费用，可设单任务与每月上限，完成后显示实际花费（自报，只作展示） | D22 |
| 工具级审批（命令、diff） | 投资经理也不是开发者，判断不了一条 shell 命令安不安全。审批要翻译成业务语言（「将读取你的持仓表」「将生成一份报告」），能按策略定的尽量不打扰用户 | D24 |
| 工作区、独立工作区、合并改动 | 这些是开发者概念。界面上要换成用户能理解的「文件夹」「文件」「报告」，独立工作区与合并对用户隐藏为「生成结果 → 确认后保存」 | D24 |
| 本地安装 runtime、Python、Codex | 一个安装包装齐、一次到位，之后增量更新 | — |
| ⚠ 定性、备案与数据授权 | 定位为 AI 研究能力与数据、不做投资咨询，边界由律师定夺；是否需要信息技术系统服务备案等手续，须法务确认；自有数据的来源干净（info-app），按上下文下发 | D25（关键路径） |
| 本地知识库 | 投资经理要接入自己的研究资料（研报、纪要、Excel、内部数据），检索能力要下放到 runtime | D26 |
| 用户电脑以 Windows 为主 | Codex 官方原生支持 Windows，默认用原生沙箱，不需要 Linux 或 WSL2；Windows 11 推荐，较新的 Windows 10 只是尽力支持；首选的沙箱模式要在安装时批准一次管理员授权（1.11）。个人电脑更易有恶意软件，钥匙串与 runtime 配置被窃取、篡改的风险更高 | D33、第 5 节 |

**必须满足的现行规则**：

| 规则 | 在本设计中的落点 |
| --- | --- |
| A1 通用/专用分离，新增业务 Agent 优先新增 Profile | 执行体只有一个，通用与专业只在 Profile 与 workflow 上区分；领域差异在 Task Profile / Agent Profile、workflow、skills、MCP 工具。A1 的措辞要按修订程序改写（3.1） |
| A2 两边都要有纪律 | 多方竞争协议照旧适用；本地 runtime 的策略层是执行侧纪律的强制点 |
| A3 四本账必须落 PostgreSQL | 四本账只在后端；本地 runtime 只执行与上报，不持有任何账的权威副本（1.12） |
| A4 执行层租用，只依赖 SDK | 本地 runtime 经 Codex Python SDK 驱动 Codex，不直接依赖 app-server 裸协议（1.6） |
| A5 领域概念不进 Port 签名 | `AgentExecutorPort` 保持中性；派往本地的 DTO 只含引用与通用字段 |
| R6 模板优先 | 桌面客户端与网页端的框架、共享包按 2.11 的路线处理，不单独改实例 |
| I4、I6（按浏览器写的会话与 CSRF 条款） | 网页端照旧；桌面端用 token 会话，要补相应条款（3.1） |
| `request-lifecycle` 全文 | 状态机、七阶段、I1–I15、AT-01–AT-22 不变；本设计只决定它们落在哪个部分（1.4），合同需小修处见 3.1 |

│   本地 runtime（Python 后台进程，常驻）                            │

| 部分 | 职责 | 不做什么 |
| --- | --- | --- |
| **桌面应用** | 用户的主要工作界面：提交 Task、进度与结果、任务历史、Task 级审查窗口、工具级审批与本地确认、key 与模型配置、工作区授权、本地结果预览；拉起并监管 runtime；托盘、通知、开机启动 | 不持有领域事实；不自己调用模型；审查窗口不挂本机能力 |
| **本地 runtime** | 主动连后端；接收 Attempt 并驱动 Codex；代后端执行推理请求；向 Codex 提供本地 `escalate` 工具；工具级审批的强制点；key 保管；工作区与沙箱策略；本地知识库（用户资料与取回的公开资料，经本地 MCP 提供给 Codex）与公开资料取数工具；上报事件、用量、副作用意图与回执 | 不持有四本账权威副本；不自行决定 Task 状态 |
| **Codex** | agent loop：规划、调用工具、读写文件、执行命令、调用模型与 MCP | 不直接连后端控制面；不开网络端口 |
| **后端（supervisor）** | 身份与登录会话（网页 cookie、桌面 token）、设备注册；Task/Attempt/Interaction/Event/Delivery；四本账；router、orchestrator、validator 与 workflow；skills 库；派发网关；推理请求的发起与限额；审计 | 自己不调用生成式模型；不中转模型请求；不接触用户 key |
| **网页端** | 辅助端：Task 级审查、账号与计费、报告与任务历史、设备管理 | 不连本机；不输入 key；不做工具级审批 |
| **info-app / knowledge-app** | 我们的自有数据：info-app 采集，knowledge-app 建库、检索、领域工具，经 MCP 按查询以上下文下发；用自有模型做 embedding/rerank | 不接触用户 key；不装观点类内容；不整批下发（1.9） |
| **模型厂商** | 推理 | — |

### 1.3 通道

| # | 两端 | 协议 | 内容 | 安全要点 |
| --- | --- | --- | --- | --- |
| ① | runtime ⇄ 后端 | WSS，runtime 主动向外连 | 派发 Attempt（带签名，1.7）、取消、续约、事件与进度回传、副作用意图与回执、审批结论上报、用量上报、厂商预设下发、推理请求与结果、`escalate` 转交 | 设备私钥认证；协议里不设 key 字段；推理请求只接受允许的用途，受限额约束（1.5） |
| ② | runtime ⇄ Codex | Codex Python SDK（底层是子进程 stdio） | 启动/恢复 thread、下发 turn、事件、审批请求、中断 | 仅本机；Codex 不开端口 |
| ③ | 桌面应用 ⇄ runtime | 渲染进程 → preload → 主进程 → 本机管道（stdio 或仅本用户可访问的本地套接字） | 工具级审批、本地确认、key 与模型配置、工作区授权、本地结果预览、runtime 状态 | 不开 TCP 端口；只有随应用打包的本地页面挂这类 preload（2.4） |
| ④ | 桌面应用 ⇄ 后端 | HTTPS + 事件流（cursor 续传） | 提交 Task、查询、Task 级审查、取消、结果、"有待审查"提醒 | 桌面端 token（2.5）；每次读取重新授权（F-DELIVERY-09） |
| ⑤ | Codex ⇄ knowledge-app | HTTPS（MCP） | 检索、领域工具、按需取 skill | 按设备发 token、可吊销、限流 |
| ⑥ | Codex、runtime ⇄ 模型厂商 | HTTPS | 推理（含推理请求） | 用户自己的 key，只在本机 |
| ⑦ | 网页端 ⇄ 后端 | HTTPS + 事件流 | Task 级审查、账号、计费、报告、设备管理 | 现有 cookie 会话 + CSRF（I6） |

**网页端与本机之间不设通道。**网页端不需要本地端口、Origin 校验或与 runtime 配对，也不受浏览器对 localhost 访问的限制。

### 1.4 生命周期七阶段的落位

| 阶段（`request-lifecycle` §5） | 在哪里执行 | 说明 |
| --- | --- | --- |
| 5.1 提交 | 桌面应用 | 幂等键生成与复用、`task_id` 与 event cursor 持久化在应用本地存储 |
| 5.2 受理与校验 | 后端 | 身份来自桌面端 token 会话（网页端来自 cookie 会话），两者共享同一 application use case；router 选执行设备，选不到在线设备时按 5.3 等待 |
| 5.3 排队与可靠投递 | 后端 → ① → runtime | outbox 投递到派发网关；设备离线时 Task 保持 `QUEUED`（或 `WAITING(RESOURCE)`），界面显示"等设备上线" |
| 5.4 Agent 执行 | 本地 runtime + Codex | Attempt 的租约与 fencing 由后端签发，runtime 持有；工具、证据、副作用经 ① 关联到 Attempt |
| 5.5 中断、批准与恢复 | 两层（1.7） | Task 级 Interaction 在后端，于审查窗口或网页端处理；工具级审批在桌面应用的本地页面 |
| 5.6 验收与完成提交 | 后端 validator（确定性）+ 本地验收 Attempt（需要语义判断时） | 结果、验收、预算结算与终态在后端原子提交 |
| 5.7 返回前端 | 后端 → ④ → 桌面应用（网页端经 ⑦） | 先持久化后通知；断线、应用重启后按 cursor 回放 |

**设备绑定**：进行中的 Attempt 绑定在一台设备上。这台电脑离线，Task 就停住，不能换一台设备接着跑。合同只保证有权用户换设备后能取回结果（§1 第 3 条），没有要求换设备继续执行，所以不违约，但影响体验；是否支持换设备续跑（在另一台设备上开新 Attempt）由 Profile 决定，前提是工作区在那台设备上也可用。

### 1.5 后端控制面

后端是 supervisor：以 workflow 为主，按规则确定性地推进；少量需要模型判断的环节不在后端调用模型，而是发推理请求到本地（见下文）。角色沿用 `agent-dev-guide` 的词：

| 角色 | 做什么 |
| --- | --- |
| router | 形成 RouteDecision：选 Task Profile、Agent Profile、执行设备。顺序是规则优先（入口、用户所选）→ 规则判不了时发推理请求分类 → 拿不准时创建 Interaction 交用户选；命中规则、分类结果（含模型、提示词版本、置信度、理由）与拒绝原因入账 |
| orchestrator | 创建并推进 Attempt；按流程模板拆步骤；需要临时规划时，先派一个"出计划"的 Attempt，计划作为 Artifact 经批准后再执行 |
| validator | 按固定 Task Profile 版本做确定性验收：schema、规则、测试结果、MCP 领域校验；**系统替用户下判断的输出检查**：对具体证券给出评级、目标价、买卖建议、承诺收益等，命中即打回或拦截，不只靠提示词约束（1.1） |
| acceptor | 需要语义判断的验收，作为独立的验收 Attempt 派给本地（不同 Agent Profile、不同运行时 thread），结论回到后端 |
| publisher | 不可逆副作用经 Task 级批准后执行，Delivery 可重取 |

**控制面承担的领域方法**：

- **流程模板**：按领域流程把需求拆成步骤，逐步派发；
- **结果校验**：规则、测试、MCP 工具优先；Codex 对自身产出的自评可靠性低，不能单独作为验收依据；
- **上下文管理**：跨 Task 记住项目背景、偏好、历史决定（长期记忆的 embedding 在后端，用自有模型）；
- **审计**：全部 Task、Attempt、审批结论、副作用摘要。

**一个执行体，按 Profile 与 workflow 区分任务**：不再分别建设通用 agent 与专业 agent。

| 任务 | 怎么派 | 用什么 Profile |
| --- | --- | --- |
| 通用 | 直接派一个 Attempt 给 Codex | 通用 Profile：能力收紧（只读与独立工作区内写入可自动放行，不开领域工具） |
| 专业 | 按 workflow 拆步骤，逐步派 Attempt，经 validator / acceptor 验收 | 对应的专业 Profile：领域工具、skills、验收规则 |

- 分类的难点不在模型，在清单：「专业」定义为命中某个已有 workflow，分类就是在有限清单里挑一项，外加「都不是」「拿不准」。清单边界要写清楚，并用标注集评测，重点看**专业误判为通用**的比例——这会绕过 workflow 与验收，阈值要偏向升级。
- **`escalate` 兜底**：runtime 以本地 MCP 工具的形式向 Codex 提供 `escalate(原因, 建议类别)`，经 ① 转交 supervisor；Codex 不直接连后端。调用后当前 Attempt 以「已升级」结束，supervisor 决定是否改走 workflow，改判入账。转交用结构化参数，不用自由文本。
- 不让 Codex 在开工前自判类别再转回：那样路由取决于用户所选模型，还要为分类白跑一轮运行时 turn，且可能在判断前就已动手。

**推理请求：后端的模型判断也在本地做**。supervisor 需要模型判断时（分类、workflow 里的少量判断），经 ① 发推理请求；runtime 用用户配置的模型直接发一次请求（不启动 Codex 的 agent loop，不带工具），把结构化结果交回。

- **费用由用户承担**，key 不离开本机，数据只到用户所选的厂商；
- **只看任务文本与摘要**：不把检索文档、产出物、完整 diff 喂给推理请求；需要读大量内容的判断（如语义验收）派 Attempt 给 Codex；
- **限额与用途**：① 的协议写明允许的用途、单次 token 上限、每个 Task 的调用次数上限（沿用 `RunBudget` 的 `max_llm_calls`）；runtime 按此执行并在本地留日志，用户随时可查——防止被攻破的后端把 runtime 当成花用户钱的模型代理；
- **结果是自报**：结果来自用户电脑，证据等级标「自报」，只决定这个用户自己的任务怎么走；团队策略、企业合规、计费相关的约束由后端按规则强制，不依赖推理结果；
- **设备离线时不可用**：执行本来就要等设备上线；后端在设备离线时需要的判断一律按规则走；
- runtime 为此带一个直连用户厂商的单次调用客户端，不借用 Codex（Codex 只支持 Responses API，且为此开一轮运行时 turn 太重）。

**编排引擎要重新评估**：后端现有 LangGraph 原本服务于"后端调用模型的 agent 图"。控制面自己不再调用生成式模型（判断经推理请求在本地做）后，LangGraph 剩下的价值是带检查点的持久化流程编排；它是否仍比"Task/Attempt 状态机 + outbox + 普通任务队列"更合适，要单独评估（D16）。

**skills 收在后端，不落地到用户电脑**：

- 好处：方法库不分发；改一个 skill 所有用户立即生效；可按客户、行业定制并做灰度和 A/B；由 router/orchestrator 按任务类型和检索结果挑选，比让 Codex 按描述自行匹配更可控。
- 下发方式，可并用：
  - **随 Attempt 注入**：派发时把选定 skill 拼进指令，适合开工时就能确定方法的场景；
  - **经 MCP 按需取**：提供 `get_skill(name)` 一类工具，适合长任务中途才需要某套方法的情况。
- 边界：
  - 注入的文本会进入本地运行时 thread 的记录，也会发给模型厂商，不是完全保密。skill 只写"怎么做"的指引，核心规则、算法、数据留在 MCP 工具内部执行，只返回结果；
  - skill 与 workflow 只写方法，不写判断规则（如买卖标准、打分阈值），评审记录留存（1.1）；
  - **编排逻辑留在后端**：supervisor 按 workflow 一步一步派发，每步只下发这一步需要的指令，完整流程不下发；核心计算与规则放在 MCP 工具内部执行，只返回结果——编排是核心价值，不让它整份留在用户本地的记录里；
  - 一次别注入太多，否则挤占 Codex 的工作上下文；
  - skill 是提示词资产，要版本化、签名（1.7）并配评测，改动后做回归。

下发给 Codex 的指令质量直接决定结果，领域评测集要尽早建：用来调流程模板、skills、验收规则，也用来对比用户所选模型的效果（1.15）。

### 1.6 本地 runtime 与 Codex

**Codex 的 agent loop 本来就在本地**：Codex CLI、IDE 插件、桌面 app 都是规划、工具、读写文件、执行命令在用户电脑上完成，只有推理请求发往模型厂商。（Codex Web 是另一种形态：agent 在 OpenAI 云端沙箱里跑，与本设计无关。）所以本地 runtime 不是干活的主体，而是一层壳。

**完整打包，不做部分打包**：

| | 部分打包：本地只放 Codex 的执行层 | 完整打包：整个 Codex 放进 runtime |
| --- | --- | --- |
| agent loop | 在后端，要自建或 fork Codex 改工具层，跟进频繁的上游更新 | 不改代码 |
| 模型调用 | 必须从后端发出，违背前提 | 从本地发出 |
| 延迟 | 每一次工具调用（包括只读的查找、运行测试）都要后端⇄本地往返，一个任务几十上百次 | 工具调用本地完成；只有需要记账的写动作按 1.12 的粒度与后端往返 |
| 工具格式 | 必须与 Codex 的 shell、apply_patch 一致，效果才不打折 | 原样 |
| 沙箱、审批 | 要自建（Codex 很依赖执行 shell 命令，只做文件读写不够） | 用 Codex 自带的 |
| 升级 | 跟上游改代码 | 换钉版二进制 |
| 代价 | — | agent 行为由 Codex 决定，只能经配置、AGENTS.md、MCP 工具、派发的指令影响 |

**runtime 要补 Codex 缺的**：

- 主动连后端（Codex 的 app-server 只等别人连进来）；
- 随安装包带上 Codex、锁定版本、负责升级；
- 与用户自己安装的 Codex 完全隔开：使用自己的二进制路径与独立的 `CODEX_HOME`，不读取、不改写用户自己的 Codex 配置与记录；
- 设备身份与配对（1.10）；
- 模型配置与 key 保管（1.8）；
- 工具级审批的强制点与副作用记账的拦截点（1.7、1.12）；
- 每个 Attempt 的独立工作区，以及经批准后把改动合进用户工作区（1.12）；
- 把需要云端决定的工具级请求升级为 Task 级审批（1.7）；
- 与桌面应用主进程的本机通信（③，2.3）；
- 策略：限定工作区、禁止关闭沙箱、危险操作必须审批、并发上限、只接受签名的派发内容。

**用哪个 SDK（A4）**：

| 选项 | 审批 | 与 A4 | 代价 |
| --- | --- | --- | --- |
| **Codex Python SDK（`openai-codex`）** | 有审批回调；⚠ 默认对命令执行与文件修改一律返回 accept，必须替换 | 符合 | 安装包里要带 Python 运行环境 |
| Codex TypeScript SDK（`@openai/codex-sdk`） | 包装的是 `codex exec`，只有 `approvalPolicy`（`never`/`on-request`/`on-failure`/`untrusted`），没有审批回调，做不了逐条交人审批，也拦不到写动作 | 符合 | 可在 Node 进程里用 |
| 直接用 app-server 协议 | 可以 | **违反** | 裸协议变化快（`0002-agent-execution` §2.7 实测） |

**建议**：runtime 做成独立的 Python 后台进程，经 Python SDK 驱动 Codex。理由：满足 A4；审批回调可用，既是审批强制点又是记账拦截点；DeepSeek Harness 那条腿也是 Python；后端已有的 `AgentExecutorPort`、Adapter 与 Fake 执行器代码可以复用。

**驱动 Codex 的要求**：

- 不解析终端输出；
- 钉住 Codex 与 SDK 版本，升级钉版必须重跑锚点；
- 连接时带 `clientInfo.name` 标识本产品（OpenAI 合规日志用它区分客户端；面向企业客户时，官方建议联系 OpenAI 加入已知客户端列表）；
- SDK 侧的 thread id 不是 Task 的真源：`ExecutionBinding` 经 ① 写回后端（I13）。

**这是官方支持的嵌入方式**：OpenAI 的 VS Code 插件和桌面 app 在发布包里带对应平台的 Codex 二进制、锁定版本，作为长驻子进程经 stdio 走 JSON-RPC；JetBrains、Xcode 也嵌入同一套 harness；官方文档把 app-server 定位为产品深度集成接口，自动化与 CI 用 SDK。社区已有 20 多个基于或包装 Codex 的项目。"打包进自家产品、用户完全无感"有多普遍，没有可靠数据。

### 1.7 审批：两层

| 层 | 例子 | 发起 | 处理界面 | 决定与记录 |
| --- | --- | --- | --- | --- |
| **工具级** | 执行某条命令、修改某个文件、联网 | Codex → SDK 审批回调 → runtime | 桌面应用的本地页面（经 ③） | runtime 按策略自动放行、拒绝或交用户在本地页面决定（以业务语言呈现，D24）；结论经 ① 上报后端存档 |
| **Task 级** | `WAITING(INPUT/APPROVAL)`、计划批准、不可逆副作用（发布、推送、对外动作）、预算追加、待审文档 | 后端 | 桌面应用的审查窗口（经 ④）或网页端（经 ⑦） | 后端落 Interaction，按 `request-lifecycle` §4.2 原子消费（F-INTERACT-*） |

**拦截点**：审批策略必须让所有命令执行与文件修改都进入 SDK 审批回调，哪怕 runtime 随后自动放行。否则 runtime 既拦不到高风险动作，也无法在写动作之前记账（1.12）。⚠ 全量进回调的性能与可行性要实测。

**强制点**：

- 审批结论只由 runtime 执行，Codex 进程改不了 runtime 的判定。⚠ 但 runtime 与 Codex 以同一个用户身份运行，两个进程之间没有操作系统级隔离；runtime 的策略与配置不被 Codex 改动，全靠 Codex 沙箱把写权限限制在工作区（1.11）。
- 本地页面随应用打包、签名，后端改不了；工具级审批结论只从本地页面来，后端不能替用户点"同意"。

**被攻破的后端仍能下指令**：后端派发的 Attempt 本身就是给 agent 的指令。在工具级"自动放行"的范围内，被攻破的后端可以借一个 Attempt 让本机执行命令；审批页不被篡改挡不住这一点。所以还要：

- **派发内容签名**：Attempt 的 Profile、流程模板、skills 由不在在线派发服务里的密钥签名，runtime 只接受签名有效、且在本地登记过的 Profile 版本；
- **本地确认**：桌面应用在本地页面显示将要执行的内容摘要（Task、Profile、工作区、能力范围），未经本地确认不开始执行。只确认新 Task 时，同一 Task 之后追加的 Attempt 不再经过确认，这是一个缺口；确认粒度（按 Task 还是按 Attempt）与哪些 Profile 可免确认，由 D14 决定，用户在本地设置；
- **收紧自动放行**：只自动放行只读动作和独立工作区内的写入；网络访问、独立工作区外的写入、任何不可逆动作一律交本地确认或升级为 Task 级。

**签名管住的是能力，管不住指令。**Profile、流程模板、skills 可以在发布时签名；但每个 Task 的输入文本、orchestrator 逐步下发的指令、检索注入的内容都是运行中生成的，无法预先签名。被攻破的后端仍能在一个签名有效的 Profile 里下达恶意指令。所以真正的防线是**按 Profile 限定能力与自动放行范围**：Profile 没授权的工具、目录、网络，指令写什么都用不上；签名与本地确认只是缩小暴露面。

**工具级请求升级为 Task 级**：不可逆命令（如 `git push`、对外发布）、需要云端授权的网络访问等，执行上仍是 Codex 发出的一条审批请求，但结论要由云端给出：

1. runtime 在审批回调里按 D3 的清单识别出这类请求，暂不回答 Codex，让该请求挂起；
2. runtime 经 ① 登记副作用意图，并请后端为它创建 Interaction；Task 进入 `WAITING(APPROVAL)`；
3. 用户在审查窗口或网页端批准或拒绝，后端落 Interaction 并原子消费，经 ① 把结论与幂等键下发给 runtime；
4. runtime 核对结论对应的正是挂起的那条请求（请求摘要一致、租约与 fencing 有效），再回答 Codex；拒绝时回答 decline；
5. 等待期间 runtime 照常续约，不开始新的工具调用；等待超时或断线，按「断线即暂停」处理，挂起的请求作废，恢复后由 Codex 重新发起。

⚠ SDK 能否容忍审批请求长时间挂起（几十分钟到几小时）要实测；不能时，改为先中断运行时 turn，批准后在同一运行时 thread 里开新的运行时 turn 继续。

**审批内容尽量不上传**：命令原文、diff、文件路径在本地页面展示；上报只带摘要与结论。

**两层的具体划分**是待定决策（D3）。建议：所有不可逆、对外可见的动作归 Task 级（按上文「升级」的流程处理）；独立工作区内的读写和命令归工具级，其中只读与独立工作区内的写入可自动放行。D3 同时要给出「需要升级」的命令清单。

#### Task 级审查：把待审文档做成页面给用户审

需要人审查时（设计、计划、报告、diff、验收结论等 Artifact），桌面应用弹出审查窗口，把这些文档渲染成页面供用户逐份审查（窗口设计见 2.6，网页端复用同一套页面）。按 `components/0002-frontend/composition/agent-dev-guide.md` §4.12「人的收件箱」：

| 页面必须表达 | 说明 |
| --- | --- |
| 问询定位 | Interaction id、Task、适用的权力与合法转换、被询问的主体 |
| 待决内容 | 具体要决定什么、各选项的后果、证据等级与未知项 |
| 决定对象 | 每份文档的版本与摘要值（digest）、实际 diff 摘要；有验收条时附冻结的验收条及结论 |
| 时效 | 截止时间与目标状态版本；过期不等于拒绝，也不等于默认同意 |
| 决定记录 | 经鉴别的主体、响应、实际生效值、原建议与改动 |

- **内容与结论都以后端为准**：页面按 Interaction 从后端取 Artifact，结论经 ④ 提交，后端落 Interaction 并原子消费（F-INTERACT-01）。
- **批准绑定具体版本**：任何一份文档的版本或摘要变化，旧批准自动失效，须重新审查。
- **不预填"同意"**：可以展示建议，结论只能来自审批人明确的操作。
- **多份文档逐份表态**：每份各有批准记录；只有审批策略明确允许时才可批量批准。
- **不要求在本机**：Task 级审查只依赖后端数据，用户在桌面应用或任何能登录网页端的地方都能处理；工具级审批仍只在本地。
- 每次记录响应耗时、相对建议的修改项数、各类触点次数，供人判断流程摩擦；这些只是观察值，不自动放宽审批。

**复核**：Task 级审批也可以指派给提交人以外的人，例如投资总监复核研究员的产出（合同要求 Interaction 向正确受众投影）。同样绑定版本、不预填同意、全程留痕。团队协作后置，先支持个人自审。

### 1.8 模型调用与 key

**配置在桌面应用的本地页面里做**：

- key 只在桌面应用的本地页面输入，经 ③ 交给 runtime，存进系统钥匙串（macOS Keychain、Windows 凭据管理器、Linux libsecret），不写进配置文件；
- **网页永远不索要 key**：这是产品规则，在网页端和桌面应用上都明确告诉用户，网页上出现要求输入 key 的地方即可视为被篡改；
- runtime 启动 Codex 时用环境变量把 key 只传给 Codex 子进程，`config.toml` 里只写环境变量名（`env_key`）；
- runtime 内置厂商预设（OpenAI、各家国产模型、企业自建网关），只含接口地址、模型名等不涉密字段；后端可经 ① 推送更新这份列表（带签名）；
- 企业客户把 `base_url` 指向自己的网关，可自行审计每次调用；
- 只用 API key，不提供"用 ChatGPT 账号登录"（第三方产品能否这样用，OpenAI 未明确答复）；
- ① 的协议里没有 key 字段；上报的日志、报错过滤请求头与环境变量。

**计费**：模型费用由用户直接付给厂商；我们收控制面、知识服务与领域数据的服务费。runtime 上报的用量只用于展示，不作计费依据。建议用户为本产品单独建 key、按项目隔离、在厂商控制台设用量上限和预算提醒。

**接国产模型**（不需要 cc-switch，runtime 自己生成配置）：国内用户大多用不了 OpenAI，主力是国产模型。

- Codex 只支持 Responses API（`wire_api="chat"` 明确报错）。Kimi 已提供 OpenAI 兼容接口，Codex 可直接连接，本项目正在实测；推荐清单里的厂商以能直连为准，runtime 只生成配置，不带转换层。只支持 Chat Completions 的厂商暂不纳入；
- ⚠ 运行时 thread 自动压缩上下文后，记录里会带 OpenAI 私有的 compaction 条目，第三方接口可能不认，导致该运行时 thread 无法继续，续接长任务会受影响——以 Kimi 为第一个样本实测；
- ⚠ 有报告称经第三方接口时，配置的 reasoning effort 可能没有真正发出——同样实测；
- ⚠ 工具调用（shell、apply_patch、MCP）在第三方模型上的格式稳定性与失败率要实测；
- 第三方模式下官方插件、图片生成、远程功能等不保证可用；
- "能接上"不等于"效果好"：Codex 的提示词与工具格式按 OpenAI 模型调优，换模型要用领域评测集实测，结果直接决定推荐清单与应用内默认推荐哪一家。

### 1.9 知识服务与 MCP

**资料分两处**：

| 资料 | 放在哪 | 怎么给 Codex |
| --- | --- | --- |
| 用户自己的资料（研报、纪要、Excel、内部数据） | 用户电脑上的本地知识库 | runtime 提供本地 MCP |
| 公开资料（公告等） | 由 Codex 从官方渠道取回，存进本地知识库；我们不提供 | runtime 提供取数与解析工具；联网按白名单放行（D31） |
| 我们的自有数据 | 我们的云：info-app 采集（来源干净），knowledge-app 建库 | knowledge-app 的远程 MCP，按查询以上下文下发，不整批同步 |

**本地优先的理由**：不做私有部署，机构仍能放心，靠的是资料根本不出用户电脑；用户订阅数据的授权问题不涉及我们；持仓等敏感信息我们不收；也与「用户用自己的数据做研究」的定位一致。代价是团队共享与换电脑要另想办法，有团队客户时再做。本地知识库的向量化可调用户自选厂商的 embedding 接口，或在本地跑小模型。

**公开资料取数**：网页结构会变，不让 Codex 临时写爬虫；由我们提供本地取数与解析工具（按公司、日期、类型下载公告，解析 PDF 表格），工具更新随 runtime 分发。runtime 限速，遵守站点访问规则。

**自有数据只装数据**：结构化财务数据、产业链关系、另类数据、标签与指标可以；评级、目标价、景气判断这类观点不装（1.1）。

**按上下文下发的要求**：每次只给最相关的片段并设上限，避免挤占 Codex 的上下文、增加用户的 token 费用；每个片段带来源、时点与我们的数据版本，进证据账；片段会留在用户本地的运行时 thread 记录里，这可以接受。我们能看到查询内容（等于知道用户在研究哪家公司），查询日志少记，并明确告知用户。

**RAG 接给 Codex 的两种方式**，可并用：派发时由 orchestrator 预先检索并注入（简单可控，但执行中途拿不到新资料）；做成 MCP 工具由 Codex 按需调用（更灵活，Codex 原生支持）。

**核心逻辑留在工具内部**：检索、行业数据查询、业务系统对接都做成 MCP 工具；需要严格步骤的领域流程封装成一个工具，内部用固定逻辑执行，而不是让 Codex 逐步执行。

**防批量抓取**：MCP 调用凭据存在用户本地，拿到它就能绕过 Codex 直接调用。"数据留在后端"只在一定程度上成立，所以要：

- 按设备单独发 token，可吊销，随设备配对签发；
- 限流，监控异常调用模式；
- 只返回所需的字段与片段，不返回原文全文；
- 必要时给返回内容加水印，便于追查。

### 1.10 连接、设备身份与首次安装

**runtime 主动向外建立 WSS**：

- 用户电脑不需要开放入站端口，易穿越 NAT 和家庭/企业防火墙；
- 后端能维护设备在线状态，直接经已有连接派发；
- 断线自动重连，重连后先对账（1.12）。

**常驻**：runtime 注册为用户级后台服务（Windows 用户态后台程序、macOS LaunchAgent、Linux systemd user service），登录后启动并连后端，由桌面应用在托盘显示状态；关闭窗口是否停止接收派发由设置决定。

**首次安装**：WSS 解决不了"机器上还没有 runtime"，首次仍要引导：官网或网页端引导下载桌面应用（内含 runtime 与 Codex）→ 下载安装包（Windows `.exe`/`.msi`，macOS `.pkg`/`.dmg`；Linux `.deb`/`.rpm`/AppImage 延后）→ 用户确认安装（Windows 上同时批准一次管理员授权，用于完成 Codex elevated 沙箱的设置，见 1.11）→ 注册后台服务 → 登录并配对 → 连接。安装包必须签名：Windows 代码签名（否则会被 SmartScreen 拦截），macOS 公证。

**绑定账号：一次性配对**。不把浏览器 Cookie、密码或长期 token 塞进 runtime：

- 配对记录含 `enrollment_id`、一次性 secret、5 分钟有效期、所属用户；
- 后端校验 secret 是否正确、是否过期、是否已用、属于谁；
- 成功后立即标记已用，secret 失效。

**配对在桌面应用里完成**：用户在应用里登录（2.5）后，应用用桌面端 token 向后端申请一次性配对记录，经 ③ 交给 runtime；runtime 用设备私钥签名提交，后端把设备公钥绑定到账号。配对 secret 只在本机进程之间传递，不经浏览器。以后做统一分发、应用尚未登录的场景时，可用 Device Code 流程（RFC 8628 那一类）作备选。不建议把 token 写进安装包参数：会与代码签名冲突。

**长期身份：设备密钥**。runtime 首次启动生成密钥对，私钥只留本机（存系统钥匙串），公钥在配对时上传；之后建立 WSS 时用私钥证明身份，后端用公钥验证。设备可在网页端或桌面应用里吊销。

**一个用户多台设备**：router 选设备时只考虑在线且已授权该工作区的设备；Task 与设备的绑定写入 RouteDecision；提交 Task 时可指定设备。

### 1.11 执行隔离与权限

**权限的来源**：本地进程的权限继承其运行用户（UID）。Agent 是逻辑执行主体，不是操作系统用户；Codex 调 shell 时 `whoami` 看到的是运行它的用户。能否做管理员操作取决于 sudo、ACL、SELinux/AppArmor 等系统策略。

**沙箱与非 root 各管一件事**：沙箱限制 Agent 能看到和接触哪些资源（外层边界）；非 root 限制它在边界内的权限（内层最小权限）。两者同时需要，非 root 也是纵深防御的一部分。

**桌面场景的取舍**：

- 依靠 Codex 自带的操作系统级沙箱：macOS 用 Seatbelt；Windows 用原生沙箱（见下文）；Linux 用 bubblewrap，依赖非特权用户命名空间，部分发行版默认限制它（Linux 后置）。均以钉版实测为准；
- runtime 只把用户授权的工作区暴露给 Codex，禁止关闭沙箱，网络访问按策略开关；
- ⚠ runtime 与 Codex 同一用户身份：runtime 的配置、策略、已登记 Profile 放在工作区之外，并做签名或完整性校验，启动与派发前核对；key 与设备私钥只放系统钥匙串。沙箱一旦失效，这些措施只能发现篡改，不能阻止；
- 不另用 Docker 容器或由我们创建专用 UID：Windows/macOS 需要 Docker Desktop（较大企业要付费），写出的文件属主不是用户本人会造成权限混乱。Windows 上 Codex 的 elevated 模式自带低权限沙箱用户，由 Codex 管理，不属于此列；
- 企业或服务器部署可选加固：Codex 以非 root 专用 UID 运行（容器内用镜像的 `USER` 或运行时 `--user`，由容器运行时直接以该 UID 启动进程，不需要先以 root 启动再切换），挂载 `/workspace` 可写、参考资料只读、生产数据不可见。这样 runtime 与 Codex 之间也有了操作系统级隔离。

**Windows**（主平台）：Codex 官方原生支持 Windows，默认使用原生 Windows 沙箱，**不需要 Linux 或 WSL2**；WSL 只在需要 Linux 原生工具、或两种原生模式都不满足时才用。依据是 OpenAI 官方 Windows 文档（`https://learn.chatgpt.com/docs/windows/windows-sandbox.md`，2026-09-17 查阅）与钉版源码 `codex-rs/windows-sandbox-rs`；钉版源码里 `docs/install.md` 仍写着「Windows 11 via WSL2」，已过时，不作依据。

| 项 | 官方说明 | 我们的做法 |
| --- | --- | --- |
| 支持的版本 | Windows 11 推荐；Windows 10 1809 及以上尽力支持，稳定性不如 11；更老的 Windows 10 不推荐 | 支持范围待定（D33） |
| elevated 模式（官方首选） | 使用专门的低权限沙箱用户，加文件权限边界与防火墙规则；需要管理员批准的设置；会创建本地沙箱用户 | 默认使用；安装时一并完成管理员授权 |
| unelevated 模式（备选） | 用当前用户的受限令牌，靠 ACL 划文件边界；不需要管理员权限；隔离较弱 | 拿不到管理员授权时退回使用，并收紧自动放行范围（只放行只读动作），在界面上告知用户 |
| 两种模式共同的限制 | 限制在工作目录以外写入；未经批准不能联网；只有「完全访问」模式会关掉这些保护 | 禁止使用完全访问模式 |

⚠ 创建本地沙箱用户、修改 ACL 与防火墙规则，可能被杀毒软件告警，公司电脑的 IT 策略也可能不允许——要实测，必要时向主流杀毒厂商报备（2.2）。

**权限链**：

```text
后端控制面：RouteDecision、Task 级批准、签名的派发内容（逻辑控制）
    ↓ ①
本地 runtime：签名校验、本地确认、工作区白名单、工具级审批、并发与预算上限（执行侧强制点）
    ↓ ②
Codex 沙箱
    ↓
运行用户的 UID（企业部署可为非 root 专用 UID）
    ↓
本地工作区
    ↓
操作系统内核（最终边界）
```

### 1.12 与合同、四本账的衔接

**Port 不变**：后端的 `AgentExecutorPort`（start/resume/cancel/events/inspect/close/submit_result）增加一个"经 ① 派往本地 runtime"的 Adapter；纪律层继续用 Fake 执行器测试。runtime 内部再用 Codex Python SDK 实现执行。

**独立工作区**：每个 Attempt 在自己的工作区里执行（版本库用 git worktree，其他用副本），不直接改用户正在用的目录。否则补偿时回滚会把用户同一时间的改动一起抹掉，「可回退」也就不成立。Attempt 的改动在 Task 级批准后才合进用户的工作区；这一步是独立工作区之外的写入，按下表逐条记账。补偿就是丢弃这份独立工作区。

**副作用账（I9）与往返开销**：I9 要求每个外部副作用有幂等键、状态、回执和补偿信息；若每一次本地写入都先到后端记账，就把"本地执行免往返"的好处抵消了。所以记账粒度（D6）是本方案能否成立的前置决策。建议：

| 动作类别 | 记账方式 | 往返 |
| --- | --- | --- |
| 只读（查找、读文件、运行不写工作区的测试） | 不是副作用，不记账，只作为工具调用事件上报 | 无 |
| 独立工作区内的写入 | **按运行时 turn 批量记账**：运行时 turn 开始前，runtime 在后端登记一条"工作区写入"意图（一个幂等键 + 独立工作区的起点引用）；运行时 turn 内的写入不再逐条往返；结束后上报变更摘要（文件清单与内容摘要）作为回执；补偿是丢弃独立工作区 | 每个运行时 turn 两次 |
| 独立工作区外的写入（含合进用户工作区）、网络请求、不可逆或对外动作 | **逐条记账**：先登记意图拿到幂等键，执行后上报回执；多数同时需要 Task 级批准（F-EXEC-03 的授权重校验在这一步做） | 每个动作一次，这类动作少 |

批量记账仍满足 I9：每个批次有稳定幂等键（同一运行时 turn 重跑时按键判重）、状态、回执（变更摘要）和补偿信息（丢弃独立工作区）。前提是拦截点成立：所有写动作都进入审批回调（1.7），runtime 才能判断它属于哪一类、是否已登记。

**补偿信息的可靠性要写明**：独立工作区与它的内容只在用户电脑上，后端只存引用和变更摘要，不存代码本身。本地工作区丢了，后端仍知道改了哪些文件、改前改后的摘要，但无法替用户恢复内容。这是「代码不经过后端」的直接代价，副作用账里对这类记录标注「补偿依赖本地」。⚠ 独立工作区的实现方式（worktree、副本、写时复制）与大工作区的开销要实测。

**租约与 fencing（I14）**：Attempt 的租约由后端签发，runtime 持有并按固定间隔经 ① 续约；续约失败即视为失去租约，此后不得提交结果、不得登记或执行新的副作用；迟到写入由后端按 fencing 拒绝。

**断线即暂停的机制**：

1. 续约失败（断网、休眠、后端不可用）时，runtime 调 SDK 的 turn 中断，停止当前运行时 turn；
2. 正在执行的那条工具调用：⚠ 中断能否终止已启动的命令进程要实测；不能终止的，runtime 自己终止其进程组。该调用的结果记为"未知"，runtime 在本地暂存独立工作区相对起点的差异，作为待上报的回执（本地暂存不是账的权威副本）；
3. 暂停期间不开始新的运行时 turn、不执行新的工具调用；本地页面里未决的工具级审批、挂起待云端决定的请求都作废，不因断线自动通过；
4. 重连后先对账：上报暂存回执；后端核对租约与 fencing。租约仍有效且 fencing 未变，runtime 用 SDK 恢复原运行时 thread 继续；否则按合同开新 Attempt，从后端持久的 Artifact 与独立工作区引用恢复，原运行时 thread 只作参考，不作真源；
5. 不允许"离线先在本地记账、之后同步成权威记录"（违反 A3）。

**预算账（F-EXEC-04）**：步骤数、耗时、派发次数、推理请求次数由后端控制；token 与费用（含推理请求）由 runtime 上报，证据等级标"自报"。花的是用户自己的钱，这不构成信任问题，但要写明。

**证据账**：citation、来源、时点经 ① 上报后端落表，不只留在事件流里。

**结果存放（D30，已定）：端到端加密后存后端，密钥只在用户手里。**合同要求结果可靠持久化、换设备后能重新取得；明文存到后端又会削弱「我们只提供能力」的定位。端到端加密两者兼顾：后端保存密文，看不到内容。随之而来的要求：

- **内容检查下放到本地**：validator 对结果内容的检查（包括替用户下判断的拦截）在 runtime 里、加密之前执行；后端只能检查元数据与结构（状态、版本、摘要值、大小、检查结果的签名回执）；
- **后端仍可见的只有元数据**：任务状态、时间、用量、审计摘要、密文的摘要值；审计与四本账照常记账，但不含结果正文；
- **密钥管理**：密钥在用户设备上生成，存系统钥匙串；换设备时要能把密钥带过去（如恢复码，或已登录设备之间的迁移），这是满足合同「换设备后重新取得」的前提；
- **密钥丢失即无法恢复**：要明确告知用户，并引导保存恢复码；我们没有后门；
- **后端做不了基于内容的功能**：结果的全文搜索、服务端预览都做不了，只能在用户设备上解密后本地完成；网页端要看结果，就得在浏览器里解密（D32）；
- **复核**：指派给他人复核时，要把该结果的密钥用对方的公钥加密后分享（团队协作后置时一并设计）。

**可恢复现场**：本地运行时 thread 的记录不是真源；需要跨 Attempt 恢复时，以后端持久的 Artifact 与独立工作区引用为准。

**多方竞争**：N 路并行 Attempt 都在用户电脑上跑，按机器资源限制并发数，派发前由 router 查询设备容量；各路本来就在各自的独立工作区里。dev.change 类 Task 天然适合本地：仓库本来就在用户电脑上。

### 1.13 信任与数据流

| 数据 | 流向 |
| --- | --- |
| 用户 key | 只在用户电脑，只发给用户选的模型厂商 |
| 代码与文件 | 由 Codex 发给用户选的模型厂商；发往后端的只有 MCP 检索与工具调用需要的内容、结果、审批摘要、变更摘要 |
| 工具级审批细节 | 只在桌面应用的本地页面展示 |
| 用户自己的资料、取回的公开资料 | 只在用户电脑上的本地知识库 |
| 我们的自有数据 | 按查询以片段形式下发到用户电脑 |
| 查询内容 | 发到 knowledge-app，日志少记并告知用户 |
| 研究结果 | 端到端加密后存后端，我方无法读取；内容检查在本地加密前完成 |

**让用户能验证，而不只靠承诺**（key 就在 runtime 里，用户会担心它被偷偷发走）：

- 开源本地 runtime（Codex 本身是 Apache-2.0）；开源 runtime + 闭源后端是这类产品常见的平衡点；
- 签名二进制，最好可复现构建；
- 公开 runtime 与 Codex 会连接的全部域名，用户可用防火墙或抓包工具（Little Snitch、mitmproxy 等）核对；
- 公开 ① 与 ⑤ 的协议文档，证明没有上传 key 的途径。

**后端不滥用的约束**（后端仍会看到 MCP 检索内容和结果）：服务条款、隐私政策、数据处理协议（DPA）；GDPR、《个人信息保护法》等法规；企业单独合同；SOC 2、ISO 27001 等第三方审计；必要时机密计算（Intel TDX、AMD SEV、NVIDIA 机密 GPU）加远程证明，思路同 Apple Private Cloud Compute。上游同理：提示词最终发给模型厂商，依赖其条款与零数据保留（ZDR）协议。通行做法是缩小需要信任的范围，而不是消灭信任。

### 1.15 价值、风险与应对

**价值在哪里**：agent loop 正在变成通用基础设施，差异化在"给它什么能力"（知识服务）和"让它干什么、怎么验收"（控制面）。真正的价值是它们装的东西：

- 独家或精心整理的领域数据，以及打通客户内部系统的能力（RAG 的价值在数据：专业性、持续更新、针对行业的切分与标注、检索准确率评测）；
- 流程模板与验收标准里的领域经验；
- 能证明"比直接用 Codex 强多少"的评测体系；
- 国产模型适配、资料与 key 不经过后端；私有化部署、团队权限（后置）；
- 开箱即用（不用自己装 Codex、拼流程），这是体验价值，容易被追上，不宜作主卖点。

**价值检验：去掉知识服务与控制面，用户还能不能得到同样的结果？**用户随时可以直接试原版 Codex，所以每项功能在设计与验收时都要过这道检验；答案是"能"的，不作为卖点投入。原版 Codex 给不了、本产品要给的：

| 类别 | 内容 | 由谁提供 |
| --- | --- | --- |
| 领域数据与工具 | 自有数据（info-app、knowledge-app）、持续更新、封装成工具的计算、用户本地资料的接入与检索 | 知识服务（MCP）+ 本地知识库 |
| 领域流程与验收 | 按行业规矩拆步骤、按标准验收并打回重做、规定何时必须停下问人与哪些动作要批准、跨 Task 记住项目背景 | 控制面 |
| 可靠性与可追溯 | Task/Attempt 断点恢复、审批记录、证据与引用可追溯、多方竞争择优、全程审计 | 控制面 + 四本账 |
| 团队与企业能力（后置） | 共享知识库、权限、私有化部署、国产模型适配、代码不经过后端 | 后端 + 本地 runtime |

**对比评测是价值的证据**：同一批领域任务，原版 Codex（同一模型、同一用户配置）做一遍，本产品做一遍，比较准确率、验收通过率、返工次数、引用完整度与耗时。要求：

- 任务集、金标准、指标与预算在跑之前冻结，两边用同一模型与 key；
- 结果按 Task Profile 分别报告，不合并成一个总分；
- 控制面、skills、MCP 工具的改动都要重跑回归，确认优势没有退化；
- 同一套数据用于推荐模型清单（见下表）。

它既是调优依据，也是销售时的核心材料；评测集要在第一个 Task Profile 开发时一并建立。

**两处容易被绕开的地方**：

- **知识服务可以被单独接走**：用户可以在自己装的 Codex 里直接配置 MCP 地址（1.16），绕过控制面。因此控制面的价值要让用户直接看到（验收结论、返工记录、可追溯的证据），知识服务是否单独售卖、如何定价要单独决定（D9）。
- **下发的指令会被看到**：skills 与派发的提示词会进入本地运行时 thread 的记录。方法里真正的核心（规则、算法、数据）留在 MCP 工具内部执行，只返回结果（1.5、1.9）。

**风险与应对**：

| 风险 | 应对 |
| --- | --- |
| 后端被攻破后借派发的 Attempt 在用户电脑上执行命令 | 按 Profile 限定能力与自动放行范围（主防线）；派发内容签名、本地确认（缩小暴露面，挡不住动态指令）（1.7） |
| 补偿回滚误伤用户自己的改动 | 每个 Attempt 在独立工作区执行，经 Task 级批准后才合进用户工作区（1.12） |
| 钓鱼：被篡改的网页或推送的链接骗用户输入 key | 网页永远不索要 key；桌面应用只放行产品域名下的外部链接（1.8、2.3） |
| runtime 与 Codex 同一用户身份，策略保护依赖沙箱 | 配置与策略放工作区外并校验完整性；Windows 默认用 elevated 沙箱，拿不到管理员授权时退回 unelevated 并收紧自动放行；实测通过才上线（1.11） |
| Windows 沙箱设置被杀毒软件或公司 IT 策略拦截 | 实测主流杀毒软件；代码签名与厂商报备；拦截时退回 unelevated 模式（1.11、2.2） |
| 与用户自己安装的 Codex 互相干扰 | 独立的二进制路径与 `CODEX_HOME`，不读写用户自己的配置（1.6） |
| 个人电脑恶意软件窃取 key、篡改 runtime | key 只放系统钥匙串；runtime 配置与策略做完整性校验；建议用户为本产品单独建 key 并设用量上限（1.8） |
| 副作用逐条记账抵消本地执行的好处 | 独立工作区内按运行时 turn 批量记账，不可逆动作逐条（1.12，D6） |
| 强依赖 Codex：协议变化快；OpenAI 在往上做 skills、插件、编排，可能覆盖通用部分 | 控制面与知识服务不绑定 Codex，换执行引擎只改 runtime 里的 Adapter；控制面越贴近行业流程越稳 |
| 用户自选模型，质量不受控，售后压力落到我们身上 | 维护经评测的推荐模型清单，清单外标"未验证"；公布各模型在领域任务上的评测数据 |
| 开通 key 多出几步、费用不透明 | 应用内图文引导、当场测 key；预估费用、上限与实际花费展示（1.1、D22） |
| 维护面：桌面应用、runtime、Codex、两个平台、签名、更新 | 只支持能直连 Codex 的厂商，不带转换层；runtime 与应用一起签名、一起更新；页面与网页端共享代码（2.2） |
| 控制面没有生成式模型，自评式验收可靠性低 | 优先确定性验收（测试、规则、MCP 校验）；语义验收用独立 Agent Profile |
| 分类把专业任务判成通用，绕过 workflow 与验收 | 规则优先；阈值偏向升级；拿不准交用户选；执行中 `escalate` 兜底；标注集评测误判率（1.5） |
| 分类质量取决于用户所选模型 | 提示词与输出格式由我们定；推荐模型清单加入分类评测，清单外标「未验证」 |
| 被攻破的后端把推理请求当成花用户钱的模型代理 | 用途白名单、单次与每 Task 限额、本地日志可查（1.5） |
| 推理结果在用户电脑上可被改动 | 标「自报」，只影响用户自己的任务；团队与企业约束由后端规则强制 |
| 多方竞争的并行压在用户电脑上 | runtime 按机器资源设并发上限，派发前由 router 查询设备容量 |
| Task 绑定单台设备，离线即停 | 界面显示"等设备上线"；Profile 允许时在其他设备开新 Attempt（1.4） |
| 开发者概念（命令、diff、工作区）让目标用户困惑 | 界面一律用业务语言呈现，能按策略定的不打扰用户（1.1、D24） |
| 被认定为提供投资分析（大模型输出易带观点） | 自有数据只装数据、方法库只写方法、validator 拦截替用户下判断的输出；留存数据流与评审证据；律师定夺（1.1、D25） |
| 自有数据经查询被整库拿走 | 只按查询给片段；按设备发 token、限流、监控异常调用、必要时加水印（1.9） |
| 编排逻辑被看光 | 后端按步下发，核心计算在 MCP 工具内部（1.5） |
| 本地知识库受用户电脑性能限制，换电脑要迁移 | 向量化可调用户厂商接口；迁移与共享后置（1.9） |

### 1.16 备选：只做远程 MCP

接受用户自己安装 Codex 时，可以不要本地 runtime：用户在 Codex 里配置我们的 MCP 地址，skills 经 MCP 下发。代价是控制面无法主动派发 Attempt，只能由用户在 Codex 里发起；流程与验收要改成 MCP 工具由 Codex 调用，对流程的掌控弱很多，Task/Attempt 合同也难以完整落实。适合面向开发者、先快速验证领域价值；完整产品仍走本设计。两者可以先后做。

## 2. 界面形态：Electron 桌面应用

### 2.1 结论与理由

**主要工作界面用 Electron 桌面应用，网页端作为辅助端。**这是按商业因素定的，不是按开发方便：目标用户是投资经理与能自己配 key 的散户（1.1），都不是开发者，在电脑桌面上工作。

界面有三种形态：

| 形态 | 做法 | 结论 |
| --- | --- | --- |
| 浏览器直连 runtime | 网页经 localhost 访问本地 runtime，审批、配置都在网页里 | 不采用：本地端口、Origin 校验、浏览器配对、浏览器对 localhost 的限制、后端下发的网页代码不可信，难题全在「网页直连本机」 |
| 网页 + runtime 自带的本地窗口 | 网页只连后端；本机的事在托盘小窗口里做 | 不采用：安全上成立、前端改动最小，但非技术用户要在两个界面之间切换，伤转化与留存——这是商业成本，不因工程省事而抵消 |
| **Electron 桌面应用** | 界面与 runtime 打包成一个应用 | **采用** |

**商业因素对比**（网页 + 本地窗口 对 Electron）：

| 因素 | 网页 + 本地窗口 | Electron |
| --- | --- | --- |
| 竞品对照 | 弱：Codex、Claude、Cursor、ChatGPT 都有桌面应用；底层就是 Codex，界面不如 Codex 桌面版时，「为什么不直接用 Codex」更难回答 | 与它们同档 |
| 非技术用户 | 两个界面、托盘小窗口，容易困惑 | 一个应用，符合一般认知 |
| 黏性 | 浏览器标签页容易被关 | 常驻 Dock、托盘，发通知，打开频次高 |
| 本地交互（本地文件、报告、结果预览） | 挤在小窗口里 | 原生支持 |
| 品牌与定价 | 像工具的配套组件 | 像完整产品，按席位或订阅收费更自然 |
| 迭代速度 | 网页即时发布、灰度、A/B | 靠发版（应对见 2.2） |
| 安全软件与系统拦截 | 小代理同样要过 SmartScreen、杀毒软件 | 新发布的应用易被 SmartScreen、杀毒软件拦截或误报，用户会直接放弃安装（应对见 2.2） |
| 国产化环境 ⚠ | 浏览器处处可用 | 对 LoongArch 等架构支持有限，统信 UOS、麒麟要实测 |
| 团队成本 | 网页 + 小窗口 | 网页端 + 桌面客户端两套界面长期维护（应对见 2.2） |

网页端仍然需要：用户不在自己电脑前时处理 Task 级审查、看报告；账号与计费也在网页上（2.8）。

### 2.2 代价与应对

| 代价 | 应对 |
| --- | --- |
| 迭代慢于网页 | 应用内自动更新（增量包）；服务端功能开关控制新功能的开放范围；不靠「从后端加载主界面」来换取即时发布（2.4） |
| 安全软件与系统拦截 | Windows 代码签名（优先 EV 证书，尽快积累 SmartScreen 信誉）、macOS 公证；向主流杀毒厂商报备白名单；跟进 Chromium 安全更新；更新包签名与完整性校验 |
| 国产化环境 | 暂不覆盖（1.1） |
| 两套界面的维护 | 页面都按「纯客户端 React + 调后端接口」写，契约、交互客户端、通用组件抽成共享包，网页端与桌面端复用（2.11） |
| 安装包体积（Electron + Python + Codex） | 实测 Windows、macOS 的体积；首装一次到位，之后增量更新 |

### 2.3 应用的组成

- **主进程**：窗口管理；拉起并监管 runtime（应用启动时连接已在运行的 runtime，而不是再起一个）；托盘、系统通知、开机启动；自定义协议（登录回调、唤起应用）；打开外部链接只交给系统浏览器，且只放行产品域名（域名随应用签名分发，不由后端下发）。
- **主窗口**：提交 Task、进度与结果、任务历史、"等设备上线"状态；经 ④ 调后端。
- **本地页面**（随应用打包，挂具体函数的 preload）：工具级审批、本地确认（1.7）、key 与模型配置（1.8）、工作区授权、本地结果预览、runtime 状态与日志摘要、推理请求日志。
- **审查窗口**：Task 级审查（2.6），不挂本机能力的 preload。
- **runtime**：独立的 Python 后台进程，同时注册为用户级后台服务，关闭窗口后是否继续接收派发由设置决定；与应用一起签名、一起更新。

界面文字面向非技术用户：命令、diff、工作区、合并这些开发概念不直接出现，按 D24 翻译成业务语言。

### 2.4 形态与安全

- **界面随应用打包**，不把后端网址塞进 Electron（`loadURL`）：那样得到的仍是浏览器方案；若再给远程页面挂上能调用本地能力的 preload，比浏览器更危险。
- **安全配置**：开启 `contextIsolation`、`sandbox`，关闭 `nodeIntegration`；禁止窗口导航到外部网址（`will-navigate`、`setWindowOpenHandler`）；preload 只经 `contextBridge` 暴露具体函数（如 `approve(id, ok)`、`saveKey(provider, key)`），不暴露"执行任意命令"类通用接口；设置 CSP。这几项没配好，Electron 比浏览器更危险。
- **本机能力分窗口授予**：只有本地页面挂能调用 runtime 的 preload；主窗口只挂读取 runtime 状态等只读能力；审查窗口不挂任何本机能力。
- **本地通信**：页面与 runtime 的交互集中在 `runtimeClient` 模块，走 preload → 主进程 → runtime 本机管道；不开 localhost 端口。
- **应用本身**：代码签名、公证、自动更新（如 electron-updater），更新包校验完整性。
- **Electron 与 Tauri**：优先 Electron（自带 Chromium，行为一致，VS Code、Cursor 同路线）；在意包大小时可选 Tauri，但它用系统自带网页引擎，三平台差异要多测，Linux 上尤其明显。

### 2.5 登录与会话

- 系统浏览器打开 Casdoor 登录页，走 OAuth PKCE，经自定义协议链接回到应用；
- token 存系统钥匙串，刷新由应用负责；
- 后端新增桌面端 token 发放与刷新；网页端的 cookie 会话保留；
- 设备配对复用同一登录态：应用登录后引导 runtime 完成配对（1.10）；
- 于是 U1 定为"后端持有会话与投影"；`request-lifecycle` F-ADMIT-04 的"浏览器入口"改为"客户端入口"，AT-16/AT-17 补"断线 / 应用重启"场景（3.1）。

### 2.6 Task 级审查窗口

Task 级审查（1.7）用独立窗口弹出：浏览器只能在自己的标签页里弹窗，Electron 可以开独立窗口、置顶、配合系统通知。

- **弹出**：由主进程创建。必须先处理才能继续的，做成主窗口的模态子窗口；需要与主界面对照着看的，做成普通窗口。应用在后台时发系统通知，点击后打开或聚焦审查窗口。同一 Interaction 只开一个窗口。
- **多份文档**：同一窗口内用标签页或左侧列表切换，每份文档旁显示版本、摘要值和各自的表态状态；不为每份文档各开一个窗口。
- **渲染**：按 Artifact 类型选择渲染器：Markdown、表格、图表、报告、引用来源。页面内的弹窗、确认框、遮罩层用 React 组件实现；不用 `window.alert()` / `window.confirm()`。
- **数据**：用桌面端 token 直接调后端接口取 Artifact、提交结论；不经本地 runtime。
- **安全**：文档是 agent 生成的，按不可信内容渲染——过滤脚本和内嵌 HTML，不加载远程资源；文档内链接交给系统浏览器打开，窗口禁止导航；不挂本机能力的 preload。
- **复用**：审查页是普通 React 页面，网页端原样复用（2.8）。

### 2.7 本地触发与云端触发分开实现

两类弹出都由主进程开窗口，外观可以统一，但数据来源、提交通道和权限完全分开：

| | 本地触发（工具级审批、本地确认） | 云端触发（Task 级审查） |
| --- | --- | --- |
| 审什么 | 单条命令、单个文件修改、联网等（以业务语言呈现）；待本地确认的新内容 | 设计、计划、报告、验收结论等文档，以及不可逆动作 |
| 谁发起 | Codex → SDK 审批回调 → runtime → 主进程；或 runtime 收到新 Attempt | 后端创建 Interaction → ④ 提醒 → 主进程 |
| 内容从哪来 | runtime 经 ③ 给出 | 桌面端 token 从后端接口取的 Artifact |
| 谁做决定 | 只在本地；结论交 runtime 执行 | 后端落 Interaction 并原子消费 |
| 结论走哪条路 | 本地页面 → preload → 主进程 → runtime；runtime 再经 ① 上报摘要 | 审查窗口经 ④ 直接调后端接口 |
| 本机能力 | 有，preload 只暴露"批准 / 拒绝"这类具体函数 | 无 |
| 能否在别的电脑上处理 | 不能 | 能（网页端） |
| 断网时 | 未决项作废，runtime 已暂停执行，不产生新的副作用（1.12） | 打不开，待网络恢复后处理 |
| 页面载体 | 随应用打包的本地页面 | 审查窗口；网页端共用同一套页面 |

两类界面不得共用一套提交逻辑：否则后端提供的内容可能借道本机通道批准本地操作，破坏 1.7 的"工具级审批结论只从本地来"。

### 2.8 网页端

保留一个网页端，给不在执行端电脑前、或不装 runtime 的人用：

- Task 级审查（复用 2.6 的页面）；
- 账号、计费、报告、任务历史；
- 设备列表与吊销（团队与权限后置）；
- 首次引导：下载桌面应用。

不做任何本地操作，不输入 key，不做工具级审批；网页上出现要求输入 key 的地方即可视为被篡改（1.8）。登录仍是现有 cookie 会话 + CSRF。是否允许从网页端提交 Task（执行仍在用户电脑上），待定（D23）。

### 2.9 前端要动的地方（以现有代码为准）

**可以复用**：`components/`、`contracts/`（zod 校验）、`lib/interaction/`、React Query、zustand、next-intl 文案、shadcn/Tailwind 组件、Vitest；Playwright 也能驱动 Electron。

**在 Next.js 上改成桌面客户端时必须改**：

| 现状 | 为什么在 Electron 里不行 | 改为 |
| --- | --- | --- |
| `next.config.ts` 为 `output: 'standalone'`，依赖 Next 服务器 | Electron 里没有 Next 服务器 | `output: 'export'` 静态导出，经自定义协议（如 `app://`）加载；不用 `file://` |
| 工作台页面在服务端用 cookie 调 `/api/auth/web/me` 检查登录（`lib/server/auth-session.ts`），页面 `force-dynamic` | 静态导出不支持服务端读 cookie、动态渲染 | 登录检查挪到客户端 |
| `proxy.ts` 在服务端生成 CSP nonce 并做多语言路由 | 静态导出没有中间件 | CSP 由 Electron 设置响应头；多语言改为不依赖中间件的路由 |
| `lib/common/api-client.ts` 强制同源 `/api/...`、`credentials: 'same-origin'`，cookie + CSRF | 应用来源不是后端域名 | 后端绝对地址 + `Bearer` token；后端 CORS 放行应用来源 |
| 登录跳转后端 `/auth/web/login`（Casdoor），用 `return_to` 回到网页 | 桌面应用不能靠网页回跳 | 见 2.5 |

也可以在 Electron 里跑 Next standalone 服务器，改动最少，但重新引入本地端口、应用更重，不建议。

### 2.10 框架选择

- **框架都能用**：Electron 的界面是 Chromium 在跑网页，React、Next.js（静态导出）、Vite + React Router、Vue、Svelte、Angular 以及 shadcn/ui、Tailwind、Ant Design、MUI 都能用；工程工具有 electron-vite、Electron Forge、electron-builder，Nextron 是 Next.js 与 Electron 的现成组合模板。唯一的限制是框架里依赖服务器运行的功能（服务端渲染、API 路由、Server Actions、中间件）不能用。
- **Next.js 运行时不重**：静态导出后 Next 客户端路由多出的 JS 在几十 KB 量级，与 Vite + React 相当；**开发与配置有摩擦**：动态路由要预生成或用查询参数（工作台现用 `?run=<id>`，不受影响）、须用自定义协议加载、`next/image` 优化要关、next-intl 中间件不能用、开发时要协调 `next dev` 与 Electron、构建较慢。
- **Vite + React Router 是 Electron 里最省事的组合**：天然是纯客户端静态产物，动态路径直接可用。页面少时选型或迁移成本最低；组件与业务代码两种框架下基本不用动，迁移成本在路由、布局、多语言这一层。

### 2.11 模板约束与两条路线

- **R6 模板优先**：`investment-web-frontend` 是 `tpl-web-frontend` 的实例，`tpl-app/frontend-capability-matrix.json` 登记了各前端共用的能力。单独改它的框架或运行方式（包括只改成 Next 静态导出）属于违规漂移。
- **I4**（Next.js 可承担浏览器同源 BFF / session 边界）与 **I6**（非安全方法须同时满足 Origin 与 CSRF）是按浏览器写的；桌面客户端的 token 会话要补相应条款。

**路线 A：保留网页前端，新建桌面客户端（建议）。**网页前端保持 Next.js、与模板一致，承担 2.8 的网页端；新建桌面客户端（如 `investment-desktop`），一开始就用 Electron + Vite + React Router，不存在迁移；共享的 `contracts/`、交互客户端、通用组件抽成共享包，不靠复制；info、knowledge 不受影响。待定：桌面客户端作为 investment 的领域扩展登记在模板对齐报告里，还是先在模板里加一类"桌面端"再同步（D12）。

**路线 B：模板与全部实例统一改为 Vite + React Router。**按 R6 先改 `tpl-app` 的 admin 与 web 两个前端、过门禁，再依次同步 Info → Knowledge → Investment，共八个前端（现均为 Next.js 16）。影响：

| 方面 | 变化 |
| --- | --- |
| 部署 | 不再运行 Next standalone 的 Node 服务，改为静态文件（nginx 或对象存储）；K8s 部署模板跟着改 |
| 登录与会话 | 服务端组件里的登录检查改为客户端检查；cookie 会话与 CSRF 仍由后端负责（I6 本来就在后端中间件执行） |
| I4 | 不再有 Next BFF，这条要改写 |
| CSP | `proxy.ts` 按请求生成 nonce 的做法不可用，改为网关设响应头或基于哈希的 CSP |
| 多语言 | next-intl 换成 react-i18next 一类方案，文案文件可沿用 |
| 公开页面 | web 前端的公开首页、`sitemap`、`robots`：纯客户端渲染不利于搜索引擎收录；需要收录时单独做静态官网 |
| 能力矩阵 | 登记的公共能力要在新框架下逐项重新实现并测试 |
| 可复用 | 组件、shadcn、Tailwind、React Query、zustand、zod、契约、测试基本不动 |

好处：所有前端与桌面客户端技术栈一致；代价：改动面覆盖四个仓的前端与部署。**建议先走 A**：桌面客户端从零起步没有迁移成本，网页端不动，R6 的影响限于共享包与登记；两条路线都要求页面按纯客户端写，以后要统一仍可走 B。决策见 D10–D12。
