# 核心价值与价值检验

> 卖点是什么、凭什么说它成立。定位与范围见 [需求](requirement.md)。

核心价值是**自有数据**与**编排**：

| 类别 | 内容 | 由谁提供 |
| --- | --- | --- |
| 领域数据与工具 | 自有数据、持续更新、封装成工具的计算、用户本地资料的接入与检索 | 知识服务与本地知识库 |
| 领域流程与验收 | 按领域流程拆步骤、按标准验收并打回重做、规定何时停下问人与哪些动作要批准、跨 Task 记住项目背景 | 后端 supervisor |
| 可靠性与可追溯 | 断点恢复、审批记录、证据与引用可追溯、多方竞争择优、全程审计 | 后端 supervisor 与持久化账 |

**价值检验**：去掉知识服务与编排，用户用原版 Codex 能否得到同样的结果？答案为「能」的功能不作为卖点投入。

⚠ **卖点与入口是两套指标，不要用一套判两件事。**通用问题的回答原版 Codex 也给得出，
按上面这条判据它**不是卖点**——但它是**入口**：用户带着任何问题来都不落空，
然后被引到专业能力上（见 [`routing.md`](../SDD/architecture/routing.md)「判成通用之后」）。

| | 判什么 | 指标 |
| --- | --- | --- |
| **卖点** | 比原版 Codex 强多少 | 下面的对比评测：准确率、验收通过率、返工次数、引用完整度、耗时 |
| **入口** | 通用问题能不能把人引到专业能力上 | 领域识别命中率、提示的点击率、**重跑后专业结果的验收通过率**、关掉提示的比例 |

⚠ 入口指标**不得用来给卖点背书**：转化率高不证明专业能力强，只证明引导有效。

**对比评测**必须作为价值证据：同一批领域任务，由原版 Codex（同一模型、同一用户配置）与本产品各做一遍，比较准确率、验收通过率、返工次数、引用完整度与耗时。任务集、金标准、指标与预算在运行前冻结；结果按 Task Profile 分别报告；编排、方法库、知识服务的改动都必须重跑回归。评测集在第一个 Task Profile 开发时一并建立，同一套数据用于推荐模型清单（[`0003-runtime/PRD/models-and-keys.md`](../SDD/submodules/0003-runtime/PRD/models-and-keys.md)）。

**评测集的最小形状**（做到这一步时再实现）：

| 层 | 至少要有 |
| --- | --- |
| 每道题 | 题目、数据时点、这一问要覆盖什么（目标、指标、维度、时间范围、对比）、**真值查询**（查询语句、期望列、键列与值列、容差）与其结果指纹、必须引用哪几条证据、必须给出哪几条结论 |
| 每次运行 | 按步骤分段判定，每段分机器检查与语义检查；第一个失败的步骤、端到端结论、真值指纹、事件数、模型请求数、用量是否可观测 |
| 每次发布 | 质量、安全、可靠性、成本四道门取与；**任何一道判不了（`undecidable`）也关闭发布**，不折成通过 |

关键在于**真值定在查询层，不定在文字答案层**：结论依赖的数值必须能机械比对，
「这条结论引没引对证据」要靠规则绑定证据来判，不靠人读。口径（指标怎么算、按什么时间基准）
另立一张表，随数据一起版本化——没有它，结论无法复核（I11）。
