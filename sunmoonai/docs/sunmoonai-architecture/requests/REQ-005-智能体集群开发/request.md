  ---

  ### 2026-08-16 修正：第三阶段取消，改由租用 + 底座

  **触发**：通用智能体已可从命令行与 SDK 非交互调用（`Agent.prompt` 一发即走、
  `Agent.create`/`send` 带流式与 cancel、`Agent.resume` 跨进程续跑、按 ID 观测他人启动的 run、
  异步客户端并发编排、cloud runtime 跑长任务）。「无人值守、定时、可恢复、可并发」
  不再构成自建智能体的理由。

  **结论**：三层演进的第三阶段（自研代码开发智能体）**取消**，不是推迟。
  租用按次计费且能力随模型迭代自动提升，自建在该维度上被严格支配。
  本 REQ 的论域收缩为**技能层**——第二阶段即终态。

  #### 判据：什么能技能化，什么必须落到底座

  技能是**给智能体的指令**，其执行机制是智能体选择遵守。因此决定性的问题不是
  「这条规则重不重要」，而是**「不遵守时会怎样」**。三问依次执行：

  | 问 | 答「是」则 |
  | --- | --- |
  | 1｜违规能否从产出中机械检出？ | 技能 + 校验脚本足够 |
  | 2｜违规重跑一遍是否无害？ | 技能足够 |
  | 3｜不变量是否跨越多个 run，或跨越进程死亡？ | **技能永远不够，必须底座** |

  第三问是分界线，理由是结构性的而非能力性的：**技能只在 run 内有运行时。**
  进程在「已下单」与「已记下下过单」之间被杀掉时，run 内的任何指令都无法补救；
  cron 重复触发时有两个各自完美遵守技能的智能体，彼此不知道对方存在——
  合规是逐 run 的，而不变量是跨 run 的。

  **该判据与本项目既有元规则一致。**`AGENTS.md` §1.1「义务放在能保证执行的一方」
  正是同一条。把预算限额写进技能，等于把义务放在受约束方自己身上，且该方是非确定性的；
  按元规则这种写法本就不成立（另见 ④ D7）。

  #### 按判据重算：技能能替代的比原先设想的多

  | 原先当作需自建的能力 | 判据结论 | 实际替代物 |
  | --- | --- | --- |
  | 任务分解 | 技能 | 智能体自己做 |
  | 上下文供给与切片 | 技能 | prompt 构造 |
  | 证据取证纪律（`file:line`） | 技能 + 校验 | **本项目已实证**：REQ-008 的「禁读旧文档 + 每条断言带 `file:line`」即技能形态，产出可 grep 复核 |
  | 产出格式与 schema 合规 | 技能 + 校验 | 校验脚本拒收即可，重跑无害 |
  | 独立复核 | **调用方式，非底座** | 用只带产物与判据的新一次 `Agent.prompt`，约五行调用代码 |
  | 子 Agent 派生 | 不必自建 | 循环调 `Agent.prompt` |
  | 等待语义 wait-any / wait-all | 不必自建 | `asyncio.gather` / `as_completed`；**不需要设计成一等原语**（原 REQ-006 ④ D5 按设计题处理，判据下它是标准库） |
  | 运行中追加方向（steering） | 不必自建 | `agent.send` 追加轮次 |

  #### 不可技能化的剩余部分：四本账

  过完判据后剩下的全部是**跨 run 或跨进程死亡的不变量**，且全部是记账，无一是智能：

  | 账 | 为什么技能做不到 |
  | --- | --- |
  | **预算账**（树形累计、成本上限） | 逐 run 自律无法约束树：二十路各守「20 步」= 400 步。SDK 全面无任何限额原语 |
  | **幂等账**（此任务是否已做过） | 重复触发时两个 run 互不可见。SDK 生产实践第 4 条自陈「盲目重试会导致重复的 cloud run」，并不提供防它的原语 |
  | **副作用账**（此外部动作是否已发生） | 失败发生在两条指令**之间**，run 内指令无法覆盖 |
  | **证据账**（结论依据什么、哪个模型、哪天） | 智能体自报模型版本不具审计效力；且模型列表会演进、`auto` 由服务端选，**行为可在仓内无任何提交的情况下改变** |

  四本账都是**预写台账**：要求在进程死亡时依然正确。这恰是 LLM 结构上做不到、
  而记账系统本职就做的事。规模上是四张表加一个 supervisor 循环，不是一个框架。

  #### 长远配置原则

  | 资产 | 随模型变强会 | 结论 |
  | --- | --- | --- |
  | 技能 / SOP | **增值**（同一份规则被更强的执行者读） | 长期投入在此 |
  | 四本账 | **不受影响**（更强的模型不会让重试变幂等） | 该造，且只造这些 |
  | 编排框架（拓扑、调度、等待原语） | **贬值**（模型自己会规划；厂商也在出功能） | 两头夹击，尽量不造 |

  即：**投入该放在会增值的一端（技能）或与模型无关的一端（台账），避开中间层（编排）。**
  REQ-005 与 REQ-006 当前的设计篇幅大量落在中间层，是本次修正要纠的主要偏差。

  #### 技能层自身的失效模式

  技能**在构造上不被强制执行**，因此技能质量只能由产出校验来度量。
  推论：**每份技能必须随附它的校验器，否则它是装饰品。**
  这使 REQ-007 ④ D2「取证命令随结论一并产出」不是可选优化，而是「技能成立」的定义。

  第二个失效模式是厂商漂移：SDK 是单厂商专有的，技能若不定期在两种以上工具上实跑，
  「工具中立」会静默腐烂。REQ-007 验收标准 2 已是此意，应作为常态而非一次性验收。

  **由此得到本 REQ 的定位：`AGENTS.md` §2 §5 §7 就是自研代码开发智能体的需求文档，
  只是当前写成了给人看的散文。**对照即明：§2 请求闭环七步 = 主循环；§5 粒度拆分与依赖图
  与四类硬依赖 = 任务分解器与调度器；§3「handoff 是唯一游标」= Registry；§7 分支纪律与
  编号撞车处置 = 并发控制；§6 里程碑收口与接手演练 = 验收标准；§1.1 漂移尺子 = 更新投影的
  触发器。这些条文不是「另一件事」，而是本 REQ 需求的现有形态。

  **技能层是工具中立的那个桥。**hook、`.codex/agents/*.toml` 一类是单一工具专有的，
  而「技能」概念各家工具均有。规则落在技能层，`AGENTS.md` 标题上的「工具中立」才保得住。
  技能的验收标准应定为一句可测的话：**换一个助手照样能跑出同格式产物**——这是工具中立
  唯一的可测形式。

  **本 REQ 与投资研究编排（REQ-006）是生产关系，不是并列关系**：本 REQ 的产物（代码开发
  智能体）生产 REQ-006 的代码。两者共用领域无关的编排内核，工具面与 SOP 分开，
  自举隔离见 ④ D8。

  ---

  **抽离的必要性有文档内证据，不止是主观感受。**现行 `AGENTS.md` 名义上是「文档协作总入口」，
  但其中大部分篇幅讲的是「智能体如何协作产出代码」，而非「如何读写投影」：
  §2 请求闭环七步、§3 进度单面、§5 请求粒度与总盘/模块关系、§5 实施顺序与并行依赖图、
  §5 任务 ID 分配、§6 里程碑收口与接手演练、§7 多助手分支协作与 REQ 编号撞车处置、
  §8 启动流程与指针注入机制。**这些条文属本 REQ 的论域，寄居在文档治理文件中**——
  这正是用户所述「混迹其中」的具体形态。

  按 263 行统计，与投影读写直接相关的约 60–80 行（§0 §1 §1.1 §4），其余约三分之二属本 REQ。

  **与 request 机制的接口已经存在，只是未被识别为集群调度设计。**现行条文中可直接复用为
  调度语义的部分：

  | 现行条文 | 作为集群机制的含义 |
  | --- | --- |
  | REQ 文件夹（§5） | 工作分配的最小闭环单元 |
  | `plan-<模块>.md` 按模块分文件、各助手认领（§7） | 任务队列与认领隔离 |
  | 任务 ID 请求内全局编号、一次性分配不复用（§7） | 工作项唯一标识，防重复领取 |
  | `handoff.md` 单面、主驾驶维护（§3 §7） | 单一调度游标，防多头 |
  | 实施顺序 = 依赖图，无依赖边可并行（§5） | 调度输入 |
  | 四类硬依赖：契约、模板→实例、部署序、身份（§5） | 调度约束 |
  | 分支天然隔离、编号撞车改号（§7） | 并发冲突处置策略 |

  即：request 机制已经是一个**人工执行的调度器规格**。本 REQ 的任务是把它显式化、
  补齐缺口（验收责任、上下文供给、失败处理），而非另起一套。

  **已有一次真实实证可作首个案例数据。**REQ-002 的核对是一次五智能体并行作业：按仓切分
  （天然无依赖边，全并行），每单元读定的投影文件、逐条断言回代码取证、产出带 `file:line`
  的四类结论。可观测到的结果包括：产出可交叉复核（本人复核了 C1 C2 C6 C10 C11 C12 数条，
  均成立）；亦暴露出需要设计的问题——个别结论需人工重新归类（C7 由「错误」改判为「含糊」），
  说明**验收责任不能落在产出方自身**。

  **与 REQ-004 的接缝是清晰的**：REQ-004 产出投影，投影即本集群的上下文供给；
  本 REQ 消费之。两者不再互相污染。

- 冲突与代价对比：

  本 REQ 与现有架构无冲突，但与 `AGENTS.md` 现行边界有**归属冲突**：约三分之二条文需从
  `AGENTS.md` 迁出。代价对比：

  | | 抽离 | 维持现状 |
  | --- | --- | --- |
  | 一次性成本 | `AGENTS.md` 条文迁移，属治理文件，须共享分支经批准（§7）；五仓 10 个指针文件不受影响（路径不变，见 REQ-004 `baseline.md` §4） | 0 |

- 边界：

  - **不含**投影的定位与结构（属 REQ-004）。
  - **不含**四本账的实现（属 REQ-006，其论域按本次修正已改为任务无关的执行底座）。
  - **不含**自研通用智能体——按 2026-08-16 修正，该项取消，不在任何 REQ 内。
  - **含**技能层：SOP 的技能化、技能与其校验器的配对、工具中立的维持。
  - **含**上述「技能 / 底座」判据本身，它是跨 REQ 的划分依据。
  - 首个可独立验收的实施为 REQ-007。

## ④ 讨论点

| 编号 | 议题 | 备选 | 现有倾向 |
| --- | --- | --- | --- |
| D1 | 集群形态 | 并行同质（每单元一个同质智能体）/ 角色分工（规划-实施-复核）/ 混合 | 混合：切分后同质并行，另设独立复核角色（依据 REQ-002 中 C7 需人工改判的观察） |
| D2 | 隔离单元 | git 分支 / worktree / 独立仓 / 容器 | 待议；现行 §7 用分支，但同一请求多助手时靠 `plan-*.md` 分文件隔离，未验证过真并发写 |
| D3 | 验收责任归属 | 人工 / 专职复核智能体 / 自动门禁 / 三者分层 | 分层：可脚本判的入门禁，判断类由复核角色，最终由人 |
| D4 | 上下文供给 | 全量投影 / 按归属轴切片 / 按需检索 | 按归属轴切片——REQ-004 的 `platform/`、`cross-cutting/`、`repos/` 三分正好是切片边界 |
| D5 | 失败与冲突处理 | 未定 | 需覆盖：产出冲突、部分失败、**证据幻觉**（声称的 `file:line` 不存在） |
| D6 | C 类条文的迁移目标 | 新建 `workflow.md` / 本 REQ 产出独立文档集 / 留在 `AGENTS.md` 但分节 | `workflow.md`，与 `AGENTS.md` 同级；`AGENTS.md` 末尾一行指向它 |
| D7 | 与 D3 的义务归属 | — | 按 §1.1 元规则「义务放在能保证执行的一方」校验每条新规则；无法保证执行的不写成强制 |
| D8 | 与 REQ-006 的分工 | 完全独立两套 / 共用编排内核 / **技能层与台账层分离** | **技能层与台账层分离**（原「共用编排内核」已作废：按修正，派生与等待不再自建）。本 REQ 管技能，REQ-006 管四本账。台账的测试须人写并钉死为智能体不可改 |
| D9 | 技能化的对象排序 | 见 REQ-007 ② | 判据「执行过 ≥1 次 + 产出可机械校验 + 预期高频重复」，据此核对流程优先 |
| D10 | 技能与校验器的绑定强度 | 建议配对 / 无校验器的技能不得入库 | **不得入库**。技能不被强制执行，无校验器则无法度量，等于装饰品（见 ② 失效模式） |
| D11 | 工具中立的检验频率 | 一次性验收 / 每次技能变更 / 定期（如每季） | 每次技能变更时在第二种工具上实跑一次。定期检验会让漂移积累到无法归因 |

D5 的「证据幻觉」是本论域特有风险：智能体产出的 `file:line` 可能不存在或不含所述内容。
REQ-002 的应对是人工抽样复核，成本随规模线性上升，需要机械化方案（如取证命令随结论一并
产出、可重跑）。
