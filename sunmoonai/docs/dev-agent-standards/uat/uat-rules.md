# UAT：用户验收测试（User Acceptance Testing）

UAT 阶段验证做出来的东西是否满足用户消息。由验收 agent 交回，它不是实现这份 IMP 的那一个。

逐条判定与证据写在 `test/` 里，结论写进那条提交。多个验收者各自验收再比对时，按
[多方竞争协议](../detailed-rules/protocol/competition-rules.md) 进行。

## 这一段该问什么

**没有模板**，但和 IMP 一样：验收者是另一个进程，只知道消息里写了的东西。
YAML 头里填 `verifies`（验收哪个 turn）。下面这些不说清就判不了：

| 问什么 | 说明 |
| --- | --- |
| **验收对象** | 哪个 turn、哪条分支上的哪个提交——**写完整提交号**，分支是会被快进、重置、强推的指针 |
| **按哪几条判** | 照抄被验 turn 里已冻结的完成条件，不在这里改、不在这里加 |
| **真实路径** | 要走哪几条用户路径；哪些恢复与降级场景也要验 |
| **观察窗** | 看多久、看哪些可观测的量；不是裸的时钟时间 |
| 哪些能机器判、哪些只能靠纪律 | 不分档，答会把纪律条目写成「已验证」（见下面「门的三档」） |
| **可用的证据** | 能跑的命令、测试入口、日志与产物位置；够不着的路径要点明 |
| 在哪开 worktree | 在被验的 worktree 之上再开一个，不得修改被验的产物 |
| 残余风险谁接收 | 验完还剩什么没盖住、谁来决定接不接 |

执行者不能是实现这一段 IMP 的那一个。这一段不交 `response.md`。
写多严见 [任务的生命周期](../lifecycle.md)「用户消息写多严」。

## 判据与结论

- **依据是被验 turn 派工时的完成条件**：照抄过来，派工后不改、不加。用户消息没写的部分，以本规则和各阶段规则为准。
  出题的人与答题的 agent 分开，实现者完工后不能改验收题。
- **验收对象是提交，不是分支**：分支是会被快进、重置、强推的指针；判定写明验的是哪个完整提交号。
- **每条判定只有三种结论**：`pass`、`fail`、`undecidable`。没有可判定依据的地方判 `undecidable` 交给人，**不自己发明标准来判通过**。
- **整份验收的结论**是逐条汇总后的那一个——**有任何一条不通过就是不通过，没有不通过但有不可判就是不可判**。
  逐条判定与证据写在 `test/` 里，那是真源；提交说明把结论说清楚，回执不记结论。
- **不外推**：在一类上跑通的便宜验收（可用测试、diff 机械复算），不能证明判断昂贵的另一类也过关。
- **先核前提**：比较之前先顺着真实调用链核实——要控制的动作是否一定经过所说的强制点；查不到就标假设。
- **完成条件逐条满足才叫完成**：缺项时只能称相应的中间状态，不能笼统说完成。

## 怎么验

不是把测试跑绿就完事。三样都要走到：

| 要验什么 | 说明 |
| --- | --- |
| **真实路径** | 按用户真正会走的路走一遍，不只跑单元测试。接口通了不等于那条路通了 |
| **恢复与降级** | 依赖不可用、输入不合法、中途中断时的行为；这些路径最少被测，也最容易出事 |
| **观察窗** | 跑起来之后看一段时间，看**可观测的量**（错误率、延迟、队列、资源），不是裸的时钟时间。数据不足记 `undecidable`，不自行宣布通过 |

## 门的三档

判据的执行归属分三档，**不混进同一张「已保证」清单**：

| 档 | 含义 | 要求 |
| --- | --- | --- |
| 机器已能判 | 有一条能跑出非平凡结果的命令 | **必须能写出这条命令**；不能是空列表恒真，也不能是「脚本文件存在」 |
| 当前靠纪律、将来可机器化 | 有办法做成检查，只是还没做 | 登记为欠账 |
| 本质上只能靠纪律 | 做不成机器检查（例如「语义覆盖了原问题」） | 一直标 ⚠ |

第三档必须单列：只分两档会诱导把「暂时靠纪律」和「本质靠纪律」混同，进而假装后者将来会自动化。

## 谁来判

| 层 | 谁 | 判什么 |
| --- | --- | --- |
| 机器 | 自动检查（测试、门禁脚本、校验器） | 能跑出非平凡结果的那些条 |
| 独立验收者 | 这一段的执行者 | 机器判不了的；**作者自检不能代替独立验收**，只按派工时的完成条件判，不为通过而静默改标准 |
| 人 | — | 意图是否正确、不可逆项、抽样复算证据的真实性；抽样规则事先写进用户消息，否则抽检会退化成「翻一翻」 |

顺序不可倒：机器这层没过不进独立验收，独立验收没过不请求人的最终批准。
新增的机器判据，首跑必须与人工结论对照；**锚点存在但不支持断言，比没有锚点更危险**。

## 证据采信

- 自述只是待验证的主张；结论由验收者从冻结的产物独立重算。
- 采信程度取各项中**最低**的一项（来源、可见范围、隔离强度、独立性、覆盖），任一项未知就降级，不取平均。
- 证据分三级，**不可互相升格**，尤其不得把「机制上必然如此」当成「此处已核对」：

| 级 | 含义 |
| --- | --- |
| 已核对事实 | 证据当前仍可独立取得并复核（提交、文件、可重跑命令） |
| 事故报告 | 确实发生过，但现场已灭失，只能按当事方陈述记录 |
| 设计风险 | 机制上成立，但尚未实际踩到，或原始出处已不可取得 |

- 用证据前固定：仓库或 SDK 版本、配置版本、主机、身份、沙箱上下文、命令、退出码、原始输出引用及时间；敏感字段去敏。
  沙箱内观测不能外推宿主；文档里的「曾经通过」只说明那个版本的那个用例。

## 覆盖声明：查了、没查、不能排除

覆盖声明要能装下「不确定」，不是只有两档。凡「不能排除某事发生过」，就如实写进来：

| 写法 | 含义 |
| --- | --- |
| 查了 | 有观测，有结论 |
| 没查 | 没有观测，**明知自己不知道** |
| **不能排除** | **有观测但不足以定论**，或存在自己控制不到的路径 |

「没查」还要按类别分列，不能混成一段：

| 类别 | 例 | 性质 |
| --- | --- | --- |
| **环境事实** | 主机名、身份、命名空间映射 | **可当场复跑**；跑了就有结论 |
| **远端与授权** | 远端分支、分支保护、部署密钥 | 部分可读，**写授权不能只靠读取来验证** |
| **执行者内部** | 界面里选的模型、沙箱内的工具调用 | **结构上够不着**，换接入方式才可能有结论 |

第三类是唯一「不改变接入方式就永远查不了」的；和前两类并排写成「没查」，会让人以为再跑几条命令就能补上。

**如实写「不能排除」不扣分，隐瞒才扣。**这与 [人的批准点](../detailed-rules/approvals.md)「人这一侧的义务」里
「执行者说没查过某处时当作真话对待」是同一条规则的两侧。

## 检查本身也必须接受检查

每个检查都输出 `pass` / `fail` / `undecidable`，并写明查了什么、没查什么。
缺输入、权限不足、枚举失败不能被吸收为通过；聚合前先判输入集合是否完整、是否允许为空。
**不让空集合、空 diff、吞掉的退出码或「0 个文件通过」代替完成条件。**

新增或修改检查时至少核查这些边界：

| 边界案例 | 错误结论怎样产生 | 怎样核 |
| --- | --- | --- |
| 应有的对象集合为空 | `all([])` 为真，被当成完成 | 先验证应有数量，再聚合；未指定不是通过 |
| 命令在预期之外的目录运行 | 失败被管道吞掉，从错误文本生成假结论 | 每个依赖命令检查退出码；取不到仓库根就停止 |
| 机械检查读到否定句 | 「没有这条边」被误判为声明了非法边 | 从规范定义块或 schema 取状态 |
| 两层调用各吞一个错误 | 内层失败被外层成功掩盖 | 原始退出码逐层传递 |
| 门禁只查链接 | 被纯文本「文件:行」引用的文件删了，门禁仍绿 | 并查纯文本锚点与可重取来源 |
| 标题保留而正文被切掉 | 空节不产生坏链接 | 对照源段的主张、条件、反例与未验证项 |

**假通过比一次明确的失败更危险**——它会成为下游继续执行的依据；判不了时停在 `undecidable`。
假失败也要靠修正解析来消除，不能长期靠人工忽略。

文档类的复核分四层：链接可达；标题有对应；对应正文真正承载原主张及其边界；证据本身支持该主张。
**空标题、只有结论没有证据、映射到同名异义的段落，都不算吸收。**

## 能力状态只用四级

| 级 | 含义 |
| --- | --- |
| `defined` | 有类、DTO、迁移或测试夹具**存在** |
| `wired` | 生产链**已接线**，会被真实请求走到 |
| `deployable` | 部署面（打包、网络、凭据、配额）**已就位** |
| `runtime-verified` | 在目标环境**实跑验证过** |

类、DTO、迁移或测试夹具存在，都不等于生产链已经接线。当前实现的断言必须回到代码、测试或运行结果取证。

## 结论里还要写什么

除了三种结论本身：

- **残余风险**：验完还剩什么没盖住、影响多大、谁来决定接不接；
- **未决与交接**：后续要做的事、下一个接手的人需要知道什么；
- **覆盖**：查了什么、没查什么、不能排除什么（照上面的三档写）。

**通过只意味着按所述范围完成了一次检视**，不构成「已验证」的背书，也不能估计未发现缺陷为零；
发布说明与记录一律照此措辞。

## 验收发现不了什么

验收能发现局部矛盾、非法状态边、归属错误和证据不足；但**共同的前提错误、被完成条件封死的答案空间**，
验几遍也不会冒出来——「必须包含某机制」一旦冻成判据，「其实不需要它」就无法作为合格结果提交。

所以出题越重，越要给硬约束与方向、可复核的问题、客观的完成判据与完整的源集，允许用证据质疑机制的必要性，
不给出题方的倾向。
