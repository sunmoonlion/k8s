## F-1 ｜ `dispatch` 字段把两件事混成了一个值

**提出**：所有者 2026-09-07，在讨论本轮怎么投喂时。

### 观察

`agent-dev-guide.md` §2.3 的 Agent Profile 里，`dispatch` 只有两个值：`argv` / `manual`。
今天的实测证明这个粒度不够：

| 事实 | 取证 |
| --- | --- |
| `claude` **有** `-p` 非交互入口，故 `dispatch = argv` | `/home/zym/.local/bin/claude` 2.1.263；`--help` 有 `-p, --print` |
| 但所有者**特意不用它**，改开交互会话 | 「如果用脚本就和你用脚本一样，没办法处理了啊」 |
| 理由是能力差异，不是偏好 | `agent -p`（一次性）写出产物**从不提交**（②④ 共三次）；`agent`（交互，所有者跑）**读、写、自己提交**——`O-7` 记的**全程唯一端到端跑通的一次** |
| `codex exec`（一次性）不关 stdin 则**永久挂起**，CPU 恒 0 | 实测 17 分 29 秒 |

⚠ **同一个 harness、同一句指令，一次性调用与交互会话的能力完全不同。**
而 `dispatch = argv` 对两者**给出同一个值**。

### 结论

`dispatch` 现在混了两件互相独立的事：

1. **有没有程序入口**——能不能被非人调起；
2. **以什么形态被调起**——一次性 / 会话持续 / 双向。

所有者给出的完整谱系（**比本仓此前的「投喂 vs SDK」二分多三档**）：

| 入口 | 中途能否介入 | 决策通道 | 会话 | 本项目现状 |
| --- | --- | --- | --- | --- |
| **CLI 交互** | ✅ 人在终端 | 终端 stdin/stdout，人眼人手 | 持续 | ⚠ **本轮五家全走这条** |
| **CLI 一次性/脚本** | ❌ | 无，只有**事前授权**（`--permission-mode` / `-s`） | 单次 | 前几轮走这条，三次零提交 |
| **SDK** | ✅ approval handler | 双向 RPC | 由调用方管 | **一次都没跑过**（`executor-adapter` 轮的题） |
| **IDE 扩展** | ✅ 人在编辑器 | 编辑器 UI | 持续 | fable 走这条（Cursor 桌面应用） |
| **ACP / A2A** | 取决于协议 | agent 间协议 | 取决于协议 | 未涉及 |

⚠ **这五档各自背后还有不同的「多道环节」**——输入在到达 agent 之前经过几次变形，
每档不同。这正是 `O-7` 指出的 `I1` 漏洞：`I1` 保护的是「**后端受理到的东西**」，
不是「**人打出来的东西**」；变形若发生在受理之前，`I1` 忠实地保护了一个已被解释过的输入。

⚠⚠ **最要紧的一条**：本项目**产品要开发的是 SDK 入口**，而**开发过程本身跑在 CLI 入口上**。
`agent-dev-guide.md` §1.4 已立「开发验收不可外推」，但那说的是**验收成本**；
**这里是入口形态的不可外推**——⚠ **用 CLI 入口跑通的协作纪律，
不证明 SDK 入口下同一套纪律成立**，因为决策通道、会话语义、变形环节三者都不同。

### 落点建议（**待裁定，本轮不改**）

1. `dispatch` 拆为两个字段：`entry ∈ {cli, sdk, ide, acp, none}` 与
   `mode ∈ {oneshot, session, bidi}`。今天的五家是 `entry=cli, mode=session`；
   前几轮是 `entry=cli, mode=oneshot`；fable 是 `entry=ide, mode=session`。
   ⚠ 现行的 `argv`/`manual` 二值**无法表达今天这次改变**，而这次改变是有能力后果的。
2. `agent-dev-guide.md` §2.7 的「两个官方 SDK」表与 §5.6 的双腿矩阵，
   ⚠ **其结论的适用范围应显式限定到 `entry=sdk`**——现在读起来像是对所有入口成立。
3. `O-7` 的入口链分析应与本条合并，成为一节正文（现在只是一条待处置观察）。
4. `executor-adapter` 轮的 Q1「投喂 vs SDK 是字段还是结构」——
   ⚠ **本条倾向于「结构」**，因为它改变的是决策通道是否存在，而不是某个字段的取值。
   但该轮尚未取证，**不在此裁**。

## F-2 ｜ 投影的**必要性**由受众的展示环境决定，而 agent 与人在这点上结构性不同

**提出**：所有者 2026-09-07。

> artifact 的展示，其实也不同：对于 agent，它不需 worktree 就能看分支，
> 但是，对于人则需要。所以，这点在人和 agent 当 arbiter 时就会体现，
> 比如你现在就必须给我开 worktree 控制面。

### 观察

同一个 Artifact（某家分支上的候选），两类受众的读法**不是偏好差异，是能力差异**：

| | agent | 人 |
| --- | --- | --- |
| 读一个分支上的文件 | `git show <ref>:<路径>` —— **不物化，直接读** | ⚠ **必须物化**：要一个真实目录才能浏览、开编辑器、看 diff |
| 展示环境 | 文本流 | 文件系统 + 编辑器 |
| 投影会不会陈旧 | ⚠ **不会**——`ref` 在读的那一刻解析 | ⚠ **会**——worktree detach 在开的时候那个 commit 上，之后该家再提交，**这里还是旧内容而看起来一切正常** |
| 生命周期 | 无——用完即散 | **有**：建 → 刷新 → 删，三步都要管 |

⚠ **本轮就是活证据。**前三轮 arbiter 是 opus（agent），**一次检视面都没开过**——
`git show` 就够了。本轮 arbiter 换成所有者（人），起草者**必须**新写
`protocol/round-review.py` 才能让裁决方读到五份候选。
**同一个流程、同一批产物，只因受众换了，就多出一整套物化设施。**

⚠ **那个「会陈旧」的性质也是本轮撞出来的**：`round-review.py` 首版开完就不管了，
各家后续提交它不跟进——**而看起来一切正常**。补了刷新才对。
**这个 bug 在 agent 受众下根本不存在**，因为 `git show ref:path` 每次都重新解析 ref。

### 结论

1. **「要不要投影」不是可选项，是受众属性推导出来的。**
   内核现有的 `client_context`（locale、时区、**展示能力**）方向是对的，
   但它只服务「最终用户」一类受众；⚠ **supervisor、另一个 agent、裁决方**这三类没有位置。
2. **物化投影带生命周期，非物化投影不带。**协议 §7.2 那三条规矩
   （`--detach` 不占分支 / 不是产物落点 / 用完删）**只对人这一侧成立**——
   它们不是通用纪律，是**人这类受众的物化代价**。此前它们写在通用位置，读起来像通用规矩。
3. ⚠ **流程的物质成本随 arbiter 是人还是 agent 而变。**这一点目前**完全没有登记**：
   `round.md` 记了 `arbiter` 是谁，但没有任何字段表达「因此需要 N 个物化投影」。
   本轮五个检视面是起草者临时想起来才开的，**而且是所有者提醒后才开的**——
   ⚠ **这不是第一次**：所有者此前就提过「所有者读不到我分支，报告前先开检视面」。
   **同一个缺口犯两次，说明它不该靠记性，该进机制。**

### 落点建议（**待裁定，本轮不改**）

1. `agent-dev-guide.md` §3.2 的 `provision(...)` 已有 `review_needed` 参数，
   但正文只用一句「人需通读时临时开 review worktree，用完删除」带过。
   ⚠ **建议把它提升为「受众投影」的一个实例**：`review_needed` 的真实含义是
   **「本 Task 有人类受众」**，而不是「有人想看看」。
2. 与 `O-6` 合并：`O-6` 说「投影缺一个概念」，本条给出该概念的**第一条可判规则**——
   **受众的展示环境决定投影是否需要物化，物化的投影必须管生命周期**。
3. `round.md` 增一个派生字段（如 `human_audience = true|false`），
   由 `arbiter`/`acceptor` 是不是 principal 推导；为真时 ⑤ 之前必须已开检视面。
   ⚠ 协议 §7.3 已写「裁决方在请求确认前必须已经把检视面开好并给出路径」——
   **但它只约束了「裁决方是 agent、要请人确认」那一种情形**，
   没约束「裁决方本人就是人」的情形，而后者恰恰是本轮。

## F-3 ｜ 还有两个独立架构轴：**执行侧**与**执行环境**；本项目全部证据落在同一个格子里

**提出**：所有者 2026-09-07。

> agent 的运行环境也是一个重要变量：① 如果 agent 在用户侧和开发者侧（provider 侧），
> 那么很多会不一样——input 和 response 的路径会迥然不同；
> ② 如果执行环境在宿主机和 docker 容器，架构也有很大变化。

### 轴一：执行侧 —— 用户侧 vs provider 侧

**这不是部署细节，它改变的是「谁能对谁设强制点」。**

| | **用户侧**（agent 跑在用户的机器/账号下） | **provider 侧**（跑在服务方基础设施里） |
| --- | --- | --- |
| **input 路径** | 本地文件系统**直接读**，零变形 | ⚠ 工作区必须**先送过去**（上传 / 挂载 / clone）——**这是一道变形环节**（`F-1`、`O-7` 的「多道环节」） |
| **response 路径** | 直接写本地 | 产物要**回传**，而回传本身是一次**副作用**，要幂等键和回执 |
| **凭据边界** | ⚠ agent 与人**共享凭据域**——本项目实测：`sudo -n -l` 返回 `(ALL) NOPASSWD: ALL`（§4.4） | 凭据由 provider 发放，**可以做到 agent 够不着人的凭据** |
| **强制点可行性** | ⚠ **本机一切本地判定都不是边界**（§4.4 原文）；只能靠托管方 key 作用域与账户端点 | 服务端身份、工具网关、出网网关**都在 provider 手里**，§4.4 要求的「落在 executor 够不着的地方」**天然可满足** |
| **可观测粒度上限** | `outer-only` —— 拦截点在进程内，运行时够不着 | ⚠ **可达 `tool.enforced`**——运行时**拥有**工具层 |

⚠ **由此更正 §5.1 的一句话。**该处写「**目前没有一家是 `tool.enforced`——那是 SDK 腿
建成之后才会出现的取值**」。**归因不完整**：`tool.enforced` 的前提**不只是 SDK**，
而是**运行时拥有工具层**，那要求执行发生在 provider 侧。
⚠ **用户侧即使接了 SDK，运行时仍然拦不住进程内的工具调用**——
SDK 给的是 approval callback（能问），不是工具网关（能拦）。**两件事，§2.7 的表里也混了。**

### 轴二：执行环境 —— 宿主机 vs 容器

| | **宿主机** | **容器** |
| --- | --- | --- |
| `workspace_isolation` | ⚠ 只能是 `convention`——本项目**六家全是**（§2.12） | 可以是 `enforced`：namespace / mount / 凭据裁剪 / 出网网关 |
| 文件可见面 | ⚠ **整个文件系统**（同 OS 用户） | 挂载了什么就看得见什么 |
| 新增的失败面 | —— | 挂载点、凭据注入、出网策略、进程生命周期、**取证被 namespace 骗** |

⚠ **「取证被 namespace 骗」在本项目已经发生过一次**，代价是一整节写错：
在助手自带沙箱内跑取证命令，`/proc/self/uid_map` 为 `0 1003 1`，
于是**沙箱内一切看起来都是 root**，据此写出「本机所有进程都是 root」（§12）。
**容器不只是更安全，它同时是一个新的取证不可靠来源。**

⚠ 产品侧的容器约束**已经在 §2.10 记着**（root filesystem 只读、worker 内存上限 768Mi、
无模型 API egress），但那里是当作**部署阻断**记的，**没有被识别为架构轴**。

### 结论：三个轴正交，而我们的证据是三维空间里的**一个点**

| 轴 | 本项目**全部实测**所在 | 产品**要去**的位置 |
| --- | --- | --- |
| **入口**（`F-1`） | CLI 交互 | **SDK** |
| **执行侧**（本条轴一） | 用户侧 | **provider 侧** |
| **执行环境**（本条轴二） | 宿主机 | **容器** |

⚠⚠ **三个轴各自都改变协作纪律是否成立，而我们在每个轴上都只有一个取值的证据。**
`agent-dev-guide.md` §1.4 立了「开发验收不可外推」，说的是**验收成本**；
`F-1` 加了**入口形态不可外推**；本条再加两条：**执行侧不可外推、执行环境不可外推**。

⚠ **最该警惕的具体后果**：guide 里凡是形如「**强制点必须落在 executor 够不着的地方**」
「**本机一切本地判定都不是边界**」「**六家全 `convention`**」的结论，
**都是「用户侧 × 宿主机」这个格子里的事实**，而它们现在读起来像**平台事实**。
§4.4 已经立过同形的纪律——「取证结论的措辞必须限定到**这台宿主、这个身份、这个时刻**」——
⚠ **本条要求把同一条纪律扩到执行侧与执行环境两个维度**。

### 落点建议（**待裁定，本轮不改**）

1. Agent Profile 增两个字段：`side ∈ {user, provider}`、`env ∈ {host, container, vm}`；
   与 `F-1` 的 `entry × mode` 合起来，**四个字段才描述得清一个执行者**。
   现有的 `sandbox ∈ {runtime, self, none}` 只覆盖了「谁提供沙箱」，**没覆盖「跑在哪一侧」**。
2. §5.1 那句 `tool.enforced` 的归因改为：**前提是运行时拥有工具层，即执行发生在
   provider 侧**；SDK 是必要条件不是充分条件。
3. §2.7 的表把「交互批准」与「工具网关」**分成两行**——前者是 SDK 能力（能问），
   后者是执行侧能力（能拦），现在混在一起。
4. 凡「用户侧 × 宿主机」得出的安全结论，逐条加上适用范围限定（同 §4.4 的写法）。
5. §2.10 的四条部署阻断**重新归类**：它们不是「待补的门禁」，是**容器这一轴的固有约束**。

## F-4 ｜ 「Harness 不得声称原生 HITL」把包级约束写成了产品级结论

**提出**：起草者 2026-09-07，在为 `executor-adapter` 轮整理 ACP/A2A 时实测发现。
⚠ **本条晚于本轮基线 `f1d5f8f4`**，五家树内看不到；登记供所有者与后续轮次用。

### 观察

`agent-dev-guide.md` §2.7「交互批准」行判 Harness 为
「**server→client request 是死能力**」，§5.6 `F-EXEC-03` 行据此判 `explicit_unsupported`，
结论写成「**Harness 不得声称原生 HITL**」。依据是
`~/repo/deepseek-harness/packages/sdk/protocol/README.md:116`。

**那句 README 本身没错。**但实测同一个仓有**三个协议面**：

| 面 | 证据 | server→client 请求 |
| --- | --- | --- |
| Python SDK wire | `packages/sdk/protocol/README.md:116` 自述 | **死能力** |
| **ACP 服务端** | 握手 `agentInfo.name = "deepseek-harness-acp"`（`snapshots/acp/handshake/stdout.expected.jsonl`） | ⚠ **可用**：`session/request_permission` 带 `options[]`，**有 `escalation-approved` / `escalation-rejected` 两组快照** |
| ACP 客户端 | `packages/subagent/subagent-acp/src/index.ts` | 它是调用方 |

### 结论

⚠ **正确表述**：「**Harness 的 Python SDK wire 上没有 server→client 请求**」。
现有写法把**包级约束**说成了**产品级结论**。

⚠ **这与 §2.7 表格自己立的那条限定纪律同形**——该表已经要求「结论固定在核对提交，
升级钉版必须重跑」，那是**时间维度**的限定；**本条缺的是范围维度的限定**：
**结论固定在哪个协议面。**

### 落点建议（**待裁定**）

1. §2.7「交互批准」行的 Harness 侧改为「**该 SDK wire 上不发**」，并**另列 ACP 面**；
2. §5.6 `F-EXEC-03` 的 `explicit_unsupported` **加范围限定**：对 SDK wire 成立，
   ⚠ **对 ACP 面未判**——`rounds/executor-adapter/port-design-notes.md` §8.2 已注明
   「harness 的 ACP 服务端怎么起没查到」，**查清前不得反向声称「走 ACP 就有 HITL」**；
3. 立一条通则：**凡「某执行者不支持 X」的结论，必须写明是在哪个协议面上不支持**——
   一个 harness 可以同时有多个面。

## F-5 ｜ 「SDK 能接审批」把**某一个 SDK** 的能力写成了 **SDK 这一类**的能力

**提出**：起草者 2026-09-08，为 `executor-adapter` 轮枚举 codex 接入面时实测发现。
⚠ **本条晚于本轮基线 `f1d5f8f4`**，五家树内看不到。

### 观察

Codex 有**两个官方 SDK，走两个不同的子命令**：

```
Python SDK     → codex app-server --listen stdio://   （sdk/python/src/openai_codex/client.py:252）
TypeScript SDK → codex exec --experimental-json       （sdk/typescript/src/exec.ts:92）
```

复核：`rg 'app-server' sdk/typescript/src/` **零命中**；`rg '"exec"' sdk/python/src/` **零命中**。

| | Python SDK | TypeScript SDK |
| --- | --- | --- |
| 线路 | JSON-RPC，**双向** | JSONL 事件流，**单向** |
| 能收审批请求 | ⚠ **能**（九种 server→client 请求） | ⚠ **不能** |

### 结论

⚠ `agent-dev-guide.md` §2.7「交互批准」行的 Codex 侧写「可由 approval handler 接请求，
但默认自动接受」——**该行未指明是哪个 SDK / 哪个子命令**。
若有人按 TypeScript SDK 实施，会发现**接不到**，而文档看起来是支持的。

⚠ **这是 `F-4` 的同形第二例。**F-4：把包级约束写成产品级结论；
本条：把**某一个 SDK** 的能力写成 **SDK 这一类**的能力。

### 落点建议（**待裁定**）

1. §2.7「交互批准」行的 Codex 侧注明 **`app-server` 面 / Python SDK**；
2. **立通则**（与 F-4 的建议合并）：⚠ **凡「某执行者支持/不支持 X」的结论，
   必须写明是在哪个接入面上**——一个产品可以同时有多个面，能力不同。
   现已知 codex 至少七个面（见 `rounds/executor-adapter/port-design-notes.md` §9.1）；
3. Agent Profile 的字段随之要能表达「**用的是哪个面**」——
   这与 `F-1` 的 `entry × mode`、`F-3` 的 `side × env` 是同一组扩展。
   ⚠ **四个字段可能仍不够，因为「面」比「入口」更细**：
   同一个 `entry=cli`，`exec` 与 `app-server` 的能力天差地别。
