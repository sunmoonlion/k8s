# 研究：结构化数据放在哪——SQLite 文件还是我们的基础设施

日期：2026-09-28。状态：**研究稿，没有动任何代码**。
起因：所有者提出「我们现在好像是用 SQLite，但应该用我们的基础设施」。

## 一句话结论

| 问题 | 结论 |
| --- | --- |
| 现在 SQLite 用在哪 | 只用作**数据集文件的格式**。采集批次、原文、登记表已经在 PostgreSQL 和对象存储里 |
| 真正的缺口是什么 | 抽出来的财务数字**没有主档**：它们只存在于生成的文件里，数据库里查不到任何一个数 |
| 建议 | 数字的主档放进 info 自己的 PostgreSQL；对外仍然发布不可变的快照；专家查询先继续用现在的方式 |

## 一、现状：哪些已经在基础设施上，哪些不在

| 东西 | 现在放在哪 | 是不是我们的基础设施 |
| --- | --- | --- |
| 采集批次、每个请求的记录 | info 的 PostgreSQL | 是 |
| 原始响应、年报 PDF | 对象存储 | 是 |
| 数据集的登记（版本、校验值、质量检查结果） | info 的 PostgreSQL、知识服务的 PostgreSQL | 是 |
| 数据集文件本身 | 对象存储里的一个 SQLite 文件 | 存放位置是，**格式不是** |
| **每一个财务数字** | **只在那个 SQLite 文件里** | **不是** |
| 专家查询时 | 知识服务把文件取到本地，转成 DuckDB 再查 | 不是 |

用到 SQLite 的代码位置：

| 仓库 | 位置 | 做什么 |
| --- | --- | --- |
| info 后端 | `application/securities/dataset/sqlite_writer.py` | 把解析结果写成 SQLite 文件 |
| 知识后端 | `application/services/dataset_query.py` | 旧路：直接查 SQLite 文件 |
| 知识后端 | `infrastructure/semantic/` | 新路：读 SQLite、转成 DuckDB、查 DuckDB |
| 投资后端 | `eval/truth.py` | 评测时重跑 SQL |

## 二、当初为什么用文件

| 原因 | 说明 |
| --- | --- |
| 沿用最小实例 | 第 23 课的零售库就是一个 SQLite 文件，问数二十题的真值冻结在它上面 |
| 版本天然不可变 | 文件有校验值，内容变了校验值就变。评测要求真值引用固定的数据版本（`F-KNOW-07`、`F-EVAL-01`） |
| 隔离 | 专家写的 SQL 是模型生成的。让它只能碰一个只读文件，碰不到任何业务库 |
| 跨 App 交接 | 规则 `C-D2` 禁止跨 App 直接读表。文件加登记接口是一种合规的交接方式 |

这些理由现在仍然成立。问题不在「用了文件」，在于**只有文件**。

## 三、只有文件带来的问题

这些是 2026-09-28 扩大样本之后看清楚的：

| # | 问题 | 例子 |
| --- | --- | --- |
| 1 | 数字没有主档，数据库里查不到 | 想知道「哪些公司的 2021 年数据被重述过」，得把每个文件打开 |
| 2 | 一家公司一个文件，跨公司的问题答不了 | 「比较茅台和五粮液的毛利率」要专家分别查两个数据集再自己拼 |
| 3 | 口径只能标到整行 | 探针发现第三方数据里，同一行不同科目的口径不一样。宽表标不出来 |
| 4 | 出处只能记到文件 | 每个数来自哪份年报、第几页、哪条附注，宽表里没处放 |
| 5 | 改一个数要重建整个文件 | 新披露一份季报，整家公司的文件重新生成、重新登记、重新下载 |
| 6 | 金额是浮点数 | SQLite 的 REAL、DuckDB 的 DOUBLE 都是浮点。金额应该用精确的十进制 |
| 7 | 同一份数据三种方言 | SQLite（文件）、DuckDB（查询）、PostgreSQL（别的一切） |

第 2 条要说明：这是「一家公司一个文件」这个做法造成的，不是 SQLite 本身的限制。一个文件里放多家公司也可以。

## 四、规则怎么说

| 规则 | 内容 | 对这件事的含义 |
| --- | --- | --- |
| `C-D1` | 每类业务数据只有一个权威主档，其余存储只保存引用、快照或可重建副本 | 财务数字要有主档；文件应该是快照，不是主档 |
| `C-D2` | 每个 App 一个逻辑数据库；禁止跨 App 直接读表 | 知识服务**不能**直接查 info 的表。info 的数据要经过契约交给知识服务 |
| `C-D3` | 物理资源可共享，但必须独立逻辑库、角色、Secret | 同一个 PostgreSQL 集群可以，库和账号要分开 |
| `C-D5` | RAGFlow 是可重建的派生系统 | 同理，给专家查的那份数据也应该是可重建的派生品 |

所以「用我们的基础设施」不能做成「知识服务直接连 info 的库」。

## 五、三种做法

| | 甲：保持现状 | 乙：全部搬进 PostgreSQL | 丙：主档进库，对外发快照 |
| --- | --- | --- | --- |
| 数字的主档 | 没有 | info 的 PostgreSQL | info 的 PostgreSQL |
| 交给知识服务 | 文件加登记 | 文件加登记，知识服务导入自己的库 | 文件加登记 |
| 专家查询落在哪 | 本地 DuckDB 文件 | 知识服务的 PostgreSQL | 本地 DuckDB 文件（以后可换） |
| 解决第三节的问题 | 都没解决 | 全部 | 1、3、4、5、6 在主档里解决；2 靠发布多公司的数据集；7 减为两种 |
| 要改的量 | 无 | 大 | 中 |
| 新的风险 | 无 | 模型写的 SQL 直接打在数据库服务器上 | 小 |

### 乙的风险要单独说

让专家（模型）写的 SQL 在 PostgreSQL 上执行，要解决这些：

| 风险 | 需要的措施 |
| --- | --- |
| 写操作 | 专用的只读账号 |
| 碰到别的库、别的模式 | 账号只对数据集的模式有读权限 |
| 读服务器上的文件、往外连 | 普通账号本来就做不了，但要核实没有被授予额外权限 |
| 一条慢查询拖垮数据库 | 语句超时、内存上限。CPU 限不住 |
| **拖累别的业务** | 物理集群是共享的，专家的重查询会和业务库抢资源。要么单独的实例，要么接受这个风险 |
| 数据版本 | 每个版本一个模式，旧版本何时清理要有规则；评测冻结的版本不能被清掉 |

现在的做法没有这些问题：引擎在知识服务自己的进程里，内存封顶，对外访问关闭，和任何数据库都不相干。

## 六、我的建议：丙

```text
原文（对象存储，已有）
   ↓ 解析
info 的 PostgreSQL：财务数字的主档        ← 这次要新建的
   一行一个数，带口径、出处、来源、采集时间
   ↓ 质量检查通过后，按版本导出
快照文件（对象存储）+ 登记（已有）
   ↓ 契约
知识服务：取快照，给专家查（已有）
```

| 层 | 放什么 | 在哪 | 状态 |
| --- | --- | --- | --- |
| 原文 | 年报 PDF、原始响应 | 对象存储 | 已有 |
| 主档 | 每一个财务数字，一行一个 | info 的 PostgreSQL | **新建** |
| 快照 | 某个时刻、通过质量检查的一组数 | 对象存储里的文件 | 已有，改为从主档导出 |
| 查询 | 专家用的那一份 | 知识服务本地 | 已有 |

理由：

1. **补上真正的缺口**。现在缺的是主档，不是查询引擎。
2. **符合规则**。主档在 info 自己的库里（`C-D1`、`C-D2`）；知识服务拿到的是快照。
3. **不引入新风险**。专家的 SQL 仍然碰不到任何数据库服务器。
4. **不浪费已经做的**。登记接口、多数据集、语义层、按口径名查询、评测都不用重做。
5. **以后可以换**。查询那一层是可重建的派生品，将来数据量大了要换成 PostgreSQL 或别的，只动知识服务。

## 七、主档大致长什么样

只是示意，不是设计稿。

| 表 | 一行是什么 | 主要的列 |
| --- | --- | --- |
| 证券 | 一家公司 | 代码、市场、简称、是否金融类 |
| 披露文档 | 一份年报或季报 | 公司、期间、报告类型、法定披露日、原件的校验值、是否更正版 |
| **财务事实** | **一个数** | 公司、期末日、报告类型、哪张表、科目、**数值（精确十进制）**、**口径**、来自哪份文档、**第几页**、**附注编号**、本期列还是上期列、抽取程序的版本 |
| 第三方事实 | 第三方网站给的一个数 | 同上，另有来源 |
| 质量检查结果 | 一次检查 | 规则、范围、是否通过、违例 |
| 数据集版本 | 一次发布 | 版本号、包含哪些公司和期间、文件的校验值、登记结果 |

「财务事实」一行一个数，所以：

- 口径可以标到每个科目（第三节问题 3）。
- 每个数都带出处（问题 4），也就能和文字连起来（附注编号）。
- 同一年同一个科目可以同时存「原始披露」和「追溯调整后」两个数，各自来自哪份年报一目了然。
- 新披露一份季报只是新增若干行（问题 5）。

量有多大：

| 范围 | 行数 |
| --- | --- |
| 关注清单十家，近九年，只算年报 | 约 3 万行 |
| 三百家，近十年，含季报 | 约 400 万行 |
| 全市场五千多家，二十年，含季报 | 约 1 到 2 亿行 |

前两档对 PostgreSQL 毫无压力；第三档要分区，但也是它能处理的量级。

## 八、快照的格式要不要换

| 选项 | 说明 |
| --- | --- |
| 继续用 SQLite | 不用改知识服务。缺点是金额仍是浮点 |
| 换成 Parquet | 支持精确十进制，DuckDB 直接能读，不用转换。要改 info 的导出和知识服务的读取 |

这是次要问题，可以在主档建好之后再定。如果要解决金额精度，就得换。

## 九、分阶段

| 阶段 | 内容 | 动哪里 |
| --- | --- | --- |
| 一 | info 建主档的表；解析结果先写主档，再从主档导出文件。文件内容与现在逐字节相同 | info |
| 二 | 年报抽取的结果进主档，与第三方数据并存，逐项比对 | info |
| 三 | 口径、出处、附注编号标到科目 | info，数据集自述 |
| 四 | 发布含多家公司的数据集，支持跨公司的问题 | info、知识服务、专家包 |
| 五 | 评估查询层要不要换 | 知识服务 |

第一阶段的验收很明确：**导出的文件与现在的逐字节相同**。这样能保证搬家没有改变任何数。

## 十、验证过的与没验证的

| 项 | 状态 |
| --- | --- |
| 语义层的引擎能不能为 PostgreSQL 做规划 | **验证过**：试了四条查询，两条正常规划出了 PostgreSQL 方言的 SQL，查系统表和读服务器文件的两条被拒绝 |
