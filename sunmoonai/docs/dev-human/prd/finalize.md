# PRD：怎么定稿

定稿的通则（定稿、批准、验收是三件事；审读→取舍→整理；不满意怎么办）见 [定稿](../finalize.md)。
本文只写 PRD 这一类特有的。这一问怎么写见 [PRD 用户消息怎么写](message-rules.md)。

`PRD/` 是 PRD 类的定稿目录：**要什么、做到什么算满足**，不写怎么实现。SDD 拿它当输入。

```text
PRD/
└── requirement.md            入口；长了按主题再拆几份，由它索引
```

**`PRD/` 不分模块**：分成哪几个模块是怎样满足，属于 [SDD](../sdd/finalize.md)，`architecture/` 与 `modules/` 只在 `SDD/` 下。
需求真要分块，按**场景或能力域**分成几份文件——不按模块分，因为模块是设计切出来的，需求不该先认那个切法。

## 定稿时对照看什么

下面这张表是**人在审核定稿时**对照用的：看有没有明显的空当。
**不写进用户消息，也不作为判 response 合不合格的条目**——写成条目发出去，答案空间就被提前封死。
缺了哪一项，是开新 turn 去问，不是让模型照着填。

| 部分 | 定稿里通常会有 |
| --- | --- |
| 目标与范围 | 这个任务要达成什么；包含什么、不包含什么、不包含的归谁 |
| 场景 | 正向：做对了是什么样；反向：做错了、输入不对、外部不可用时该是什么样 |
| 非目标 | 这次明确不做什么 |
| 约束 | 必须遵守的规则、不能动的东西、外部限制 |
| 非功能 | 性能、容量、安全、可用性上的要求 |
| 什么算满足 | 可判定的验收口径 |
| 未决 | 还没定的事，以及定不下来会影响什么 |
## 定稿本身要守的

- **只写要什么，不写怎么做**：技术方案属于 SDD。
- **写进 `PRD/` 的验收条件必须可判定**：写「响应时间小于 2 秒」，不写「响应要快」。
- 改 `PRD/` 要写明改了什么、为什么；已据它派出去的任务按 [改判](../approvals.md) 处理。
