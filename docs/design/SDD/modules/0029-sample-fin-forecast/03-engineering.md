# 样本 · 第 3 步：工程化（我们定的部分）

> 这些不碰投资逻辑，由我们定、不问用户：步骤怎么切、每步交回什么、验收怎么写成机器能核的规则、用哪些工具、每步额度、停下来交人的条件、成稿落在哪。凡是落到「怎么判断」的，都引用 [`01-idea.md`](01-idea.md) 的出处或 [`02-gaps.md`](02-gaps.md) 的缺口号，答复前那条规则在清单里的出处写 `pending_user`（knowlab 建草稿会拒收，这正是要的：没有用户出处的规则过不了）。

## 平台规矩（不是用户的方法，所有分身都带，不进 `rule_sources`）

- 不给买入、卖出、持有建议，不给评级、目标价、估值结论（成稿验收 `no_positioning_advice`；合规 `C-L1`–`C-L5`）。
- 数只能来自本次读到的用户数据或上游交回物，不回忆、不编（第 2 版 `_FIN_NUMBERS` 的同一条，属于工程上的诚实要求）。
- 只回一个 JSON 对象；成稿写进项目文件；工具与审批不比平台默认更松（分身清单的硬约束，`knowbots.py`）。
- 分身只读用户自己的数据：工具只有 `list_my_data`、`read_my_data`，不接平台的数据线（`C-L2`，0027 §3.5）。

## 写的过程中发现的平台空白（交给设计 0029）

1. **没有被允许的计算工具。** 第 2 版的规矩是「所有计算都在 SQL 里做，不心算」，靠的是 knowbase 的 `run_sql`。分身不能用数据线，`read_my_data` 只给文字；剩下的路是模型自己算（容易错），或在用户电脑上跑命令（每条都要人批准，测试里就是运营一条条批）。**单季换算、比率、同比、回测都要算**——没有可靠的计算手段，这个分身做不准。需要平台提供一个确定性的计算工具（对用户数据只读、返回结果和算式），或者给分身开一个受限的计算沙箱。
2. **验收只能核结构。** 现有规则只有「是不是 JSON、有没有某个键、列表够不够长、有没有买卖措辞」（`AcceptanceRule`），核不了「这个比率是不是由这两个数算出来的」「恒等式真平还是假平」「累计减出的单季对不对」。要有数值类的确定性验收：按交回物里给的分子分母重算、核恒等式、核单季加总等于年报。
3. **读数据是分页文字。** Excel 每张表转成 CSV、PDF 逐页抽字；年报 PDF 很长，要模型翻页找「主要会计数据」表，慢且容易漏。可以让用户给结构化的表（G1 提议的格式），PDF 只用来对照少数几项。
4. **验收用例的期望值要来自用户。** 「2024 年营业收入」这类期望值只能由用户从年报里填（G10），起草的人不能代填——否则就是我们给的真值。

这四条里前两条决定这个样本能不能真跑出可信的结果，应在第一条实测之前或同时解决（见 0029 第五节）。
