# SDD：用户消息怎么写

SDD 这一类问的是**怎样满足需求**。定稿怎么把关见 [SDD 定稿](finalize.md)。

**规范不规定答。**要让答符合某种形式、走某条路、带某些东西，**就在这一问里提出来**——
规范里不替你规定，模型也不会自己知道。写进问里的才算数。

## 这一类该问什么

**没有模板，也没有必填栏**，下面是这一类该落在哪些问题上；一问只做一层，别把结构层和模块内部混在一起。

| 问什么 | 说明 |
| --- | --- |
| 以什么为底 | 哪一份 `PRD/` 定稿的哪几节、哪一份 `SDD/`；给链接与提交 |
| 设计到哪一层 | 结构层（模块之间）还是模块内部 |
| **责任边界** | 这件事归谁做、不归谁做；跨模块时谁向谁提供什么 |
| **接口与数据** | 调用、数据、协议的形状；错误与版本规则 |
| **状态与不变量** | 哪些账跨运行、跨进程死亡仍须正确（预算、幂等、副作用、证据） |
| **失败与恢复** | 会怎样失败、失败后回到哪个状态、谁负责补偿 |
| **威胁与越权** | 被攻破、越权、伪造时会怎样，强制点落在哪 |
| 有哪几条路 | 各自代价，为什么选这条；拿不准时要不要先做个有预算和退出条件的 spike |
| 哪些契约已冻结 | 不许动的状态词、合法边、终态、接口签名、数据格式 |
| 要不要往下拆 | 拆出的模块将在 `SDD/modules/` 下各得一份说明，并在 `SDD/submodules/` 下各成一个子任务 |

**不把验收标准写成条目塞进这一问**，也不复述本规则的栏目与设计原则：合不合格看它能不能定稿成 `SDD/`。
写多严见 [turn 的投影](../turn-project.md)「用户消息写多严」。

## 问到什么程度算够

出口判据只有一条：**另一个人不再问你就能开工**——模块划分、责任边界、接口与数据、失败与恢复、冻结了哪些契约都定了。
做不到就是还没问完，接着追问。

做得到还继续往下写——具体函数、目录结构、伪代码、用哪个库的哪个调用——就是已经在替 IMP 干活。
那些由执行者在自己的 worktree 里定：**设计定的是约束，不是写法**。
