# 请求生命周期

**一条 message 从用户发出到用户看到 response 的完整往返**，以及它穿过的那些部件。
起点和终点都在用户电脑上，后端只占中间。

> 组成部分、通道、数据流与工程落点由产品合同搬入（合同「去向」表登记）。
> 本文答「系统长什么样、一条请求怎么走完」；各模块**自己是什么**见 [`../modules/`](../modules/)，
> 模块之间的接口与约束见同目录的 [通道](channels.md)、[信任边界](trust.md)、[共同约束](engineering.md)。

别和这两个混：**状态机**管纵向（这个 Task 现在算什么），**七阶段产品功能**是按段分组的功能义务；
本文管的是横向那一条线。

## 本轮建哪几块

按**运行位置、信任域、发布方式**切——三者都不同就单列：

| 模块 | 是上图的哪一部分 | 跑在哪 | 各自是什么 | 子任务 |
| --- | --- | --- | --- | --- |
| `0001-backend` | 后端（supervisor） | 服务器 | [说明](../modules/0001-backend.md) | [子任务](../submodules/0001-backend/PRD/requirement.md) |
| `0002-desktop` | 桌面应用 | 用户电脑 | [说明](../modules/0002-desktop.md) | [子任务](../submodules/0002-desktop/PRD/requirement.md) |
| `0003-runtime` | 本地 runtime 与 Codex | 用户电脑 | [说明](../modules/0003-runtime.md) | [子任务](../submodules/0003-runtime/PRD/requirement.md) |

`0002` 与 `0003` 都在用户电脑上，**信任域不同**：runtime 碰得到 key 与结果正文，桌面应用碰不到。
这是它们分开的唯一理由，也是不能合并的理由。

## 九站

一条请求依次经过这九站。**顺序由行序表达**；走哪条通道见 [通道](channels.md)。

| 站 | 在哪 | 走完的判据 | 条款 |
| --- | --- | --- | --- |
| **写 message** | 桌面应用（类别预填经 ③ 由 runtime 算） | **未经用户确认的类别预填不算数**；没有可用的模型 key 不得提交；资料正文、文件名及其派生特征不出本机 | `F-INTAKE-05/06/07` |
| **提交** | 桌面应用 → 后端 | 幂等键在「租户 + 请求方 + Profile」作用域内唯一；同键同摘要返回原 `task_id`，同键异摘要返回幂等冲突，**不静默复用也不另建** | `F-INTAKE-01`、提交信封 |
| **受理** | 后端 | 身份从认证上下文确定，**不信任客户端自报**；一旦分配 `task_id` 并写首个事件，后续拒绝也必须形成可审计的 `REJECTED` Task | `F-ADMIT-*` |
| **派发** | 后端 → 执行端 | 派发内容带签名；租约与 fencing 随派发下发；设备离线则等待，不丢 | `F-DISPATCH-*` |
| **执行** | 执行端 | 在独立工作区里跑；key 只在本机；本地资料不上传 | `F-EXEC-*`、`I16` |
| **中断** | 本地窗口 / 后端 | 工具级在本机闭环，Task 级经后端 Interaction **原子消费**；两条提交逻辑**不得共用** | `F-APPROVE-*`、`F-REVIEW-*` |
| **封装** | 执行端 | 先本地内容检查，再加密；后端只拿到密文与元数据 | `F-CRYPTO-*` |
| **验收** | 后端 | 确定性验收与回执核对通过；终态、结果、预算结算**原子提交** | `F-ACCEPT-*` |
| **交付** | 后端 → 桌面应用 | 事件按 cursor 续传、重复幂等；**密文在本机解开、渲染出来** | `F-DELIVERY-*` |

### 中断那一站跨三个模块

工具级审批的界面在 `0002-desktop` 的本地窗口，拦截点在 `0003-runtime`；
Task 级审查的界面在 `0002-desktop` 的审查窗口，原子消费在 `0001-backend`。
这是三方交界处，最容易出错。

## 终点在哪

终点不是「模型返回了文字」，也不是「一条事件推送成功」，而是四条同时成立：

1. 最终结果（密文）、验收、证据和副作用状态已经可靠持久化；
2. Task 已以唯一合法终态提交；
3. 有权用户在断线、应用重启或换设备后，凭结果密钥可以重新取得结果；
4. 通知失败可以独立重试，不改变 Task 结果。

**起点同理在用户电脑上**：类别预填与资料选择都发生在提交之前。两头都在本机，这不是实现细节，
是信任边界的直接结果——后端读得到问题，读不到资料，也读不到结果。
