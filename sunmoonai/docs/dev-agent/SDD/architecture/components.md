# 组成部分与本轮范围

> 由产品合同搬入（合同「去向」表登记）。时间上怎么走见 [请求生命周期](lifecycle.md)。


```text
用户电脑
┌──────────────────────────────────────────────────────────────────┐
│ 桌面应用（Electron）　三扇独立窗口，能力按窗口授予                 │
│   主窗口：提交 Task · 进度与结果 · 任务历史 · 本地知识库管理        │
│   审查窗口：Task 级审查（不挂本机能力）                            │
│   本地窗口：工具级审批 · 本地确认 · key 与模型配置 · 工作区授权    │
│                    主进程 ⇅ ③ 本机管道                             │
│ 本地 runtime（Python 后台服务，常驻；关掉窗口仍在跑）              │
│   连接 · 策略 · 工具级审批拦截 · key 保管 · 本地知识库 · 执行适配   │
│   ──② Codex Python SDK（stdio）──▶ Codex（随应用打包）            │
│                                └── 沙箱 ── 独立工作区              │
└──────┬───────────────────┬──────────────────┬──────────────────┘
       │ ④ HTTPS/事件流     │ ① WSS（runtime    │ ⑤ HTTPS(MCP)      │ ⑥ HTTPS
       │   （桌面应用）     │   主动外连）      │   （Codex）       │  （Codex）
       ▼                   ▼                  ▼                   ▼
  ┌──────────── 后端（supervisor）────────────────┐   知识服务        模型厂商
  │ 身份与会话 · 设备 · 派发网关 · 路由与编排      │   info-app 采集   用户自选
  │ Task/Attempt/Interaction/持久化账（PostgreSQL）│   knowledge-app   用户自付
  │ 方法库 · 审计 · 结果密文                       │   建库与 MCP
  └───────────────────────▲────────────────────────┘
                          │ ⑦ HTTPS（内部人员）
                     管理后台：运营 · 客服 · 审计查询（另有官网与下载页）
```

| 部分 | 职责 | 不做什么 |
| --- | --- | --- |
| **桌面应用** | 用户唯一的工作界面：提交 Task（含本地预填、用户确认的任务类别）、进度与结果、任务历史、研究底稿查看与编辑、本地知识库管理、Task 级审查、工具级审批与本地确认、key 与模型配置、工作区授权、设备与计费；拉起 runtime 并确保它在跑；托盘、通知、开机启动 | 不持有领域事实；不自己调用模型；审查窗口不挂本机能力 |
| **本地 runtime** | 主动连后端；接收 Attempt 并驱动 Codex；向 Codex 提供本地 MCP（本地知识库、`escalate`）与公开资料取数工具；工具级审批与副作用记账的拦截点；key 保管；工作区与沙箱策略；本地内容检查与结果加密；上报事件、用量、副作用意图与回执 | 不持有任何持久化账的权威副本；不自行决定 Task 状态 |
| **Codex** | agent loop：规划、调用工具、读写文件、执行命令、调用模型与 MCP | 不直接连后端；不开网络端口 |
| **后端（supervisor）** | 身份与会话、设备注册；Task、Attempt、Interaction、Event、Delivery；持久化账；受理判定与路由、编排、验收与发布；方法库；派发网关；结果密文与元数据；审计 | 不调用生成式模型；不中转模型请求；不接触用户 key；看不到本地资料、文件名与结果正文 |
| **知识服务** | info-app 从合法来源采集；knowledge-app 建库、检索、领域工具，经 MCP 按查询下发；embedding 与 rerank 用自有模型 | 不接触用户 key；不装观点类内容；不整批下发 |
| **官网与管理后台** | 官网：产品介绍与下载页；管理后台：内部人员的运营、客服、审计查询 | 管理后台只见元数据，不见研究结果正文 |
| **模型厂商** | 推理，由用户选择并付费 | — |


## 本轮建哪几块


按**运行位置、信任域、发布方式**切——三者都不同就单列：

| 模块 | 对应上表的哪一部分 | 跑在哪 | 各自是什么 | 子任务 |
| --- | --- | --- | --- | --- |
| `0001-backend` | 后端（supervisor） | 服务器 | [说明](../modules/0001-backend.md) | [子任务](../submodules/0001-backend/PRD/requirement.md) |
| `0002-desktop` | 桌面应用 | 用户电脑 | [说明](../modules/0002-desktop.md) | [子任务](../submodules/0002-desktop/PRD/requirement.md) |
| `0003-runtime` | 本地 runtime 与 Codex | 用户电脑 | [说明](../modules/0003-runtime.md) | [子任务](../submodules/0003-runtime/PRD/requirement.md) |

**各模块承担什么、不承担什么，写在 [`SDD/modules/`](../modules/) 下各自那一份**，本表不复述。

`0002` 与 `0003` 都在用户电脑上，**信任域不同**：runtime 碰得到 key 与结果正文，桌面应用碰不到。
这是它们分开的唯一理由，也是不能合并的理由。

上表其余部分**本轮不开发，沿用现状**，所以不占模块：

| 范围外 | 现在在哪 |
| --- | --- |
| 八个既有 Next.js 前端 | 四个 app 仓各一对：`tpl-`、`info-`、`knowledge-`、`investment-` 的 `*-web-frontend/` 与 `*-admin-frontend/` |
| 官网与下载页 | 上述 `*-web-frontend/` |
| 内部管理后台 | 上述 `*-admin-frontend/`，沿用平台模板 |
| 知识服务 | `info-app` 采集、`knowledge-app` 建库与 MCP；Codex 经通道 ⑤ 直接调它 |

这几块的要求（由合同搬入）：注册与登录经认证服务的页面，支付经支付渠道的页面；官网只做产品介绍与下载；管理后台供内部人员使用，只见元数据。官网与桌面应用都必须写明「key 只在桌面应用里输入」。


## 未决


知识服务与八个既有前端何时进入建设范围，未定；进入时按同一把尺子（运行位置、信任域、发布方式）判断要不要单列模块。
