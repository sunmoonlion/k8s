### 我是怎么判错的：`||` 兜底从未触发

检查命令的形状是

```
git show <refA>:<文件> | grep … | head | cut | sed  ||  git show <refB>:<文件> | …
```

**管道的退出码取自最后一个 `sed`，它永远成功**，于是 `||` 的兜底分支**一次也没跑过**。
而 `luna` / `qwen` 的 ② 评审提交在**裸分支** `luna` / `qwen` 上（组织者代提交时用的是它们的当前分支），
第一个 ref `runtime-refact/<家>` 上没有该文件 → `git show` 失败 → 空输出 → **看起来就像「没声明」**。

**不需要为此立新规矩。**协议 §8.1 第 1 条早已写明：

> 零命中要能区分「**真的没有**」与「**没查到**」。

规则在，是执行者（我）没照做。**方向是危险的那一侧**：它不是漏报，是**冤枉了两个合规的参与方**——
与 ① 那次「判据只认一个 ref，把照指示做的那家判成没交」同一形态、同一天内第二次。

## O-4 ｜ 裁决方两处判错：`resume` 已接线；「验不了的三样」已在服务态验过

### O-4a ｜「抽象层 `resume` 是 `NotImplementedError`，故端到端未接线」——**错**

| 事实 | 取证 |
| --- | --- |
| `NotImplementedError` 在**抽象基类**里，是抽象方法的正确写法 | `graph_runtime_service.py:26-31` |
| **适配器已实现**：`Command(resume=user_input)` + 同 `thread_id` | `langgraph_runtime.py:13-21` |
| **有端到端测试且通过**：中断 → `resume("continue")` → 原地续跑并产生副作用 | `test_graph_runtime_service.py:18-35`，实跑 **2 passed** |

**怎么错的**：吸收 `C2` 时裁决方**确实打开了文件自验**——但只看了基类那 18 行就停了，
**没搜谁继承它、没搜谁调用它、没跑测试**。`cursor` 原话是

说的是**接口契约**，被读成了**功能缺失**。

⚠ **这是「打开文件自验」也会失败的一个实例**：验了，但**验的范围是自己划的**，
而范围划错了。与本轮其他几次同形态——**凭印象选检查点**。

### O-4b ｜「事务性 / 租约 / fencing 验不了」——**句子对，读法错**

原句「**git 载体**验不了这三样」成立。但整套文档只写了这一句，

| 项 | 测试 |
| --- | --- |

| 副作用恰好一次 | `test_interrupt_resume_executes_side_effect_once`、`test_retry_after_crash_after_commit_does_not_repeat_effect`、`test_tool_side_effect_service_records_once_by_tool_call_id` |
| 陈旧覆盖被拒 | `test_versioned_reducer_rejects_stale_plan_overwrite` |

## O-6 ｜ Artifact 的「面向对象的投影」缺一个概念，而我们一直在手工做它

所有者提出：**同一个 Artifact 在不同层级应有不同投影，服务于不同对象**——
比如 AI 助手的回复既要给 supervisor 看，有时也要给人看，
**同一个 Artifact 就要有不同投影，并连带不同的展示环境**。

### 现状：「投影」一词已被用于三件事，而这一件最弱

| 现有用法 | 指什么 | 定义状况 |
| --- | --- | --- |
| **状态投影** | Event 流 → Task / Attempt 状态 | 内核定义完整 |
| **投影 Π** | 比较两次跑动前丢掉私有事件与时间戳 | 等效判据定义完整 |
| **前端投影** | 后端事实 → 用户看到的东西 | 内核提及 4 次，**只说「由前端投影决定」，没有定义** |

内核**已预留位置**但只朝一个方向：`frontend_renderer_contract`（Task Profile 字段）、
`client_context`（locale、时区、**展示能力**）。二者都假定「投影 = 给最终用户看」，
**没有「给 supervisor 看」「给另一个 agent 看」这两类受众**。

检索结果：`render` 在设计文档与协议里 **0 次**（只在内核 4 次）；
`检视面` 有 10 次，但它只是「给人 + 编辑器环境」这一种投影的**既有实现**，未被抽象。

### 我们一直在手工做它，只是没有名字

| 同一个东西 | 给机器的投影 | 给人的投影 |
| --- | --- | --- |
| 一份候选稿 | `git show <ref>:<path>` 的 blob + sha256 | 编辑器里渲染的文本 |
| ④ 的四份异议 | `round-status.py` 判「✅ 交了」 | 组织者写的「四家立场」对照表 |
| 一次代提交 | `author` / `committer` 两字段 | commit message 里的人读解释 |

### ⚠ 必须先立的一条规矩，否则这个抽象会变危险

> **批准必须绑定在源对象上，不得绑定在投影上。**

理由：**投影是有损的**。渲染会丢字节，摘要会丢条件，
一张「四家立场表」丢掉了它们的全部论证。
若人看着投影批准、而机器认源对象，**批的与执行的就不是同一个东西**。

**我们其实已经在遵守这条，只是没说出来**——三处既有实例：
收件箱条目必须带 `target_commit` 与 `diff_stat`（§2.6）；
`R7` 代提交必须附 sha256；`luna` 自报哈希经裁决方逐位复核一致。
**这些都是「投影可以随便做，批准必须钉源对象」的实例。**

### 建议的形状（⚠ 不自决，待流程判）

- **一个 Artifact = 一个源（字节 + 哈希 + commit）+ N 个投影**；
- 每个投影声明三件事：**给谁看**（audience：human / supervisor / agent）、
  **在什么环境展示**（render target）、**丢了什么**（lossy 声明）；
- **投影不可作为批准对象**，批准一律指向源的 commit / hash；
- 「检视面」不是特例，是「human + 编辑器环境」这一种投影的既有实现。

### ⚠ 一处直接命中当下的推论

**组织者给所有者的每一条汇报，都是投影。**
「四家三条推翻我」「156 passed」——都是有损压缩。
所有者据此做的判断，**严格说是基于投影而非源对象**。

这不是说汇报有问题，是说**它应当被明确标成投影，而不是被当作事实本身**；
凡涉及批准的场合，汇报里必须同时给出源对象的引用（commit / 路径 / 哈希），
让所有者**能够**绕过投影去核。本轮各处代提交附 sha256 即此意，
但**汇报正文尚无此纪律**。

## O-7 ｜ 入口是一条链，不是一个点——而 `I1` 保护的是链**之后**的东西

所有者提出：**input 有多个入口（CLI、IDE 扩展、SDK 等），
每种主要方式背后还有不同的多道环节**，这在整个开发中都很重要。
本条是 `O-6`（输出侧的投影）的**对偶**，且**比 O-6 更早出问题**——
输入的变形发生在内核看到它**之前**。

### 内核的现状：入口被画成一个点

链路图起点是「前端用户 → ① 提交 Task」，**「前端」是一个没有内部结构的点**。
而不变量 `I1` 写的是：

> **原始输入、调用者、租户、受理时间和 Profile 版本可追溯，不被后续解释覆盖**——防「意图漂白」。

⚠ **`I1` 保护的是「后端受理到的东西」，不是「人打出来的东西」。**
若入口链已在受理前做过变形（注入编辑器上下文、展开配置、截断、加系统前缀），
那么 `I1` 忠实地保护了一个**已经被解释过的输入**，而它自称保护的是原始输入。
**「意图漂白」恰好可以发生在 `I1` 的保护范围之外。**

### 本轮实测：同一句文本，六种入口，六种行为

指令文本完全相同：`按 round-protocol 定位当前环节，做你该做的那一步。`

| 入口 | 实际行为 |
| --- | --- |
| `agent -p`（CLI 非交互） | 写出产物，**从不提交**（②④ 共三次） |
| `agent`（CLI 交互，所有者跑） | 读、写、**自己提交** ← **全程唯一端到端跑通的一次** |
| `codex exec`（CLI 非交互） | 能写不能提交；不关 stdin 则**永久挂起**（CPU 恒 0） |
| `qoder -p --permission-mode dont_ask` | 一切写入被拒，**打印请求后退出** |
| `qoder -p --permission-mode accept_edits` | 能写不能提交 |
| Cursor 桌面应用（`fable`） | **无命令行入口**，只能人工投喂 |

**同一段文本，经不同入口，得到的不是「同一件事的不同表现」，而是不同的事。**
其中最刺眼的一条：`agent` 交互 vs `agent -p`，**同一个二进制、同一个模型、同一句话，
一个提交一个不提交**——差别纯粹来自入口模式。

### 内核缺的字段

现有 `client_context` 只装 locale、timezone、展示能力，**是「客户端是什么」**；
缺的是**「这次输入经过了哪条链、链上每一道做了什么」**：

| 该记而未记 | 例 |
| --- | --- |
| 入口种类 | CLI / IDE 扩展 / SDK / 桌面应用 / 人工转述 |
| 入口模式 | 交互 vs 非交互；有无回话通道 |
| 链上的变形 | 是否注入工作区上下文、是否加系统前缀、是否截断 |
| 能力差异 | 能否接收审批请求、能否答复、能否原地续跑 |

⚠ 最后一行与 `executor-adapter` 工单的第二问**是同一件事**：
「投喂与 SDK 的差异是字段还是结构」——本条给出的答案倾向是
**它至少是「入口链」这个尚不存在的对象的属性**，而不是执行者的属性。
**但本条不裁定**，那是该轮的权力。

### 与 `O-6` 合起来看

| | 方向 | 现状 |
| --- | --- | --- |
| `O-6` | 一个 Artifact → N 个投影（按受众） | 内核只预留了「给最终用户看」一个方向 |
| **`O-7`** | N 个入口 → 一个 Task | 内核把入口画成一个点，`I1` 从链尾开始保护 |

**两条都指向同一个缺口：边界上的多态没有被建模。**
中间的状态机做得很细，两头各按一个点处理。

### 建议（⚠ 不自决）

- 提交信封增加**入口链声明**：入口种类、模式、链上变形、能力四项；
- `I1` 的表述明确其保护起点：**它保护的是受理时的输入**，
  若入口链有变形，**变形本身必须可追溯**，否则 `I1` 名不副实；
- 与 `O-6` 的「批准绑定源对象」对称，本条的规矩是：
  **`I1` 要能回答「人到底打了什么」，而不只是「后端收到了什么」。**

## O-8 ｜ 全部实测证据来自一条产品可能不会有的入口链

所有者指出：**或许我们最后只做浏览器入口，但事实上现在用的是 IDE 扩展和 CLI 入口，
而且是在本地。**

### 这是外部效度问题，不是措辞问题

| | 设计面向的 | 实测所在的 |
| --- | --- | --- |
| 入口 | **浏览器**（内核链路图：「前端用户 → ① 提交 Task」） | **CLI + IDE 扩展 / 桌面应用** |
| 部署 | 前后端分离、服务端受理 | **全在本地**，发布是本地 merge、不经网络 |
| 回话通道 | 前端用户响应 Interaction（图中 ⑤） | 非交互模式**没有通道**；交互模式靠终端 |

**推论：本轮及此前各轮积累的入口侧证据，对产品入口的有效性未知。**
沙箱行为、`-p` 与交互的差异、权限档位、stdin 阻塞、`--add-dir`——
**全部是 CLI/IDE 链上的事实**。若产品最终只有浏览器入口，这些**一条都不直接迁移**。

反过来同样成立且更值得警惕：**浏览器入口至今零次实测**。
内核链路图假定它，`frontend_renderer_contract` 为它预留字段，
`AT-*` 为它写验收——**而没有任何一次真实提交经过它**。

### 文档现状：这条边界从未被写下

检索：`agent-dev-refact.md` 里「本地」six 处全在**边界/安全**语境
（「本地验证不是边界」「发布是本地 merge」），
**没有一处承认「开发的入口链 ≠ 产品的入口链」**。

已有的 `§1.4 开发验收不可外推` 讲的是**验收**：
「开发的验收机械且便宜，财务分析的验收判断且昂贵，最难的一半没解决」。
**本条是它的平行条款，且更基础**——验收不可外推是**结论**层的限制，
入口不可外推是**证据**层的限制：它决定前者的证据算不算数。

### 对已有结论的具体影响

| 结论 | 是否受影响 |
| --- | --- |
| 对象形状、两层状态机、权力表、证据等级 | **不受影响**——它们不依赖入口 |
| 「投喂 ≠ 人在环」（`executor-adapter` §1.0） | **受影响**：证明的是 **CLI 投喂**≠人在环，不是「一切自动化」≠人在环 |
| 沙箱 / 权限 / `--add-dir` 全部结论 | **仅对 CLI 链成立** |
| `O-7` 的六条入口对照 | **仅覆盖 CLI/IDE**，浏览器与 SDK 两栏是空的 |
| 「一个运行时，开发是它的第一个 Task Profile」 | ⚠ **这条最需要复核**——若开发与产品**入口链不同、部署形态不同**，则「同一个运行时」在**入口侧**尚未被验证过 |

### 建议（⚠ 不自决）

1. **补一条与 `§1.4` 对称的边界**：**开发的入口链不可外推到产品的入口链**，
   凡引用入口侧实测证据的结论，必须注明它成立于哪条链；
2. `O-7` 建议的「入口链声明」四项，**至少要能区分本地 CLI 与服务端浏览器**；
3. ⚠ **在浏览器入口有过一次真实提交之前，不得声称产品入口已被本项目验证。**
   现在的状态是：**内核为它写了字段与验收，实测一次没有。**

## O-9 ｜ 协议能否泛化为「supervisor 分派 subagent」：一半已成立，一处硬冲突

所有者提出：现行 `protocol/` 只针对**评优、核查、吸收**，
能否进一步泛化为 **supervisor 分派 subagent 的协议**。

### 现状：内核支持子 Task，协议对它命中为 0

内核 §8 已完整规定子 Task：派生五条约束（父完成标准仍是业务目标、
父级预算覆盖全部子级、**授权只能收窄**、子级各有 Profile/Attempt/结果/验收、
汇总保留血缘），依赖图由有边界的 `COORDINATION` Task 管理。

检索：`subagent` / `子 Task` / `子任务` 在
`protocol/round-protocol.md` **0 次**、`agent-dev-refact.md` **0 次**。
**内核与流程各做各的，没接上。**

### 能泛化的一半：已经是参数问题

协议 §1.0 已把三种协作形态化为一套流程的三组参数。按同一套参数：

```
supervisor 派一个 subagent  =  proposers   = [该 subagent]
                               skip_stages = ②互评、④异议   ← N=1 时无对象
                               保留          ①派发、⑤验收、⑥确认、⑦清理
```

**这不是新流程，是 N=1 的退化。**`_fixups` 轮已实跑过近似形状
（`skip_stages = ①②④⑥`）。**泛化在参数层面成立。**

### 装不下的三处

| # | 缺口 | 说明 |
| --- | --- | --- |
| 1 | **递归** | 协议的一轮是**平的**，没有「轮中轮」；而 subagent 可再派 sub-subagent。内核有 `COORDINATION` Task 管依赖图，**协议无对应物** |
| 2 | **粒度与仪式成本** | 最轻档 T0 仍要工单 + 独立验收 + 人确认，其上界是「人的必需动作 ≤ 2」；对**秒级**派发仍过重。需要更轻的档，或明确「subagent 派发不是一轮」 |
| 3 | **硬冲突：产出方 ≠ 验收方** | 见下 |

### 第 3 条展开：这是「三条不能省」之一，不能绕

supervisor→subagent 最自然的设计是 **supervisor 验收 subagent 的活**。
但 **supervisor 对父 Task 的产出负责，因此它本身就是产出方**——
验收下属的活等于自验自己的一部分。

内核那句正是在防这件事：
**「父 Task 的完成标准仍是用户业务目标，不能以『已经拆出子 Task』冒充完成」**。

三种可能，代价不同（⚠ **不自决**，触及「三条不能省」，属权威层，命中 T2）：

| 方案 | 代价 |
| --- | --- |
| 另一个 subagent 验收 | 满足独立性，**成本翻倍** |
| 确定性 validator 验收 | 只能验机械条，**判断条无人管** |
| supervisor 自验子任务 + **父 Task 的验收方兜底且能穿透到子 Task** | 组织者倾向此案，但须证明「穿透」是可判定的 |

### ⚠ 与 `O-7` / `O-8` 的关系

**supervisor→subagent 的派发是又一种入口，而且是「内部入口」**——agent 派 agent，
**没有人在环**。而本项目全部入口侧证据来自 CLI / IDE 链（`O-8`），
**内部派发这条链一次都没跑过**。

因此本条**不得**在 `O-7` 的入口链模型落地前单独推进：
否则会为一条从未实测的链先定协议。
