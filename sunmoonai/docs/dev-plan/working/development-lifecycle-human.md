# 开发生命周期 · 人

> 最后更新：2026-08-31
>
> **本文是人在开发工作中的角色、权力和纪律。**它与
> [`development-lifecycle-agent.md`](development-lifecycle-agent.md) 是同一件事的两种执行者。
>
> **本文不是 [`request-lifecycle.md`](request-lifecycle.md) 的投影，也不复制产品状态机。**
> 那份是产品契约；实现它的是代码，不是本文。看到 Task、Attempt、Interaction、Delivery
> 这些词一律以那份为准，本文不重新定义，也不在正文使用产品状态名。
>
> **本文只写人独有的部分。**凡 agent 那份已有、对人同样成立的（上下文路由、
> 范围门禁、证据账、worktree 纪律），不在此重复——需要时读那一份。
>
> 人可以向多名助手派活，此时人扮演协调者；隔离、评审与选优规则不因“人当协调者”
> 而豁免，仍按 agent 文执行。

## 1. 为什么要单独一份

人和 agent 做的是同一类事——领受、实施、验收、交付。**但有四处是真实差异**，
不是同一条规则的两种说法：

| | 人 | agent |
| --- | --- | --- |
| 批准权 | **有**——放行门禁、取消、预算追加、验收终审 | 无，且不得自我批准 |
| 跨会话续接 | 可依赖记忆、经验与组织背景 | 每次冷启动，只能靠落盘 |
| 裁量权 | 可判断“这件事不值得走全流程” | 不得自行降级流程 |
| 责任归属 | 人承担后果 | agent 不承担，因此不能是最终判定方 |

这四处决定了：**把人的规则写进 agent 那份，会给 agent 松绑；
把 agent 的规则写进人这份，会给人加不必要的枷锁。**

## 2. 人的三个角色

1. **请求提出者**：提出有边界的开发工作，提供原始意图、范围和验收期望；
2. **执行者**：亲自实施部分工作，与助手交替推进；
3. **有权主体**：批准、取消、追加成本和终审验收的最终权力。第三种助手不能替代。

助手不得自我批准；人也不得把终审责任外包给助手后不再复核。

## 3. 人独有的权力，及其义务

权力越大，留痕义务越重。下表左边是只有人能做的动作，右边是做了必须留下什么。

| 动作 | 必须留下 |
| --- | --- |
| **批准**一个需要放行的门禁 | 批准了什么、依据什么、承担什么风险 |
| **取消**一个进行中的工作 | 取消原因；已产生的副作用是否需要补偿 |
| **追加预算 / 提高资源上限** | 为什么值得、上限是多少、什么条件下停 |
| **验收终审** | 逐条对着验收标准的结论；未通过项是缺陷还是标准过期 |
| **降级流程**（判定不必走完整选优） | 判定依据：为什么这件事的风险不足以支付那个成本 |
| **推翻 agent 的判定** | 推翻的是哪一条、原判断错在哪、新判断的依据 |

**“我看着行”不是依据。**依据要能被半年后的自己复核。

派活给多名助手时：人冻结任务包、指定角色、收回最终选择；不在候选互投上“凑独立”。
无法保留候选人与裁判分离时，决策留在人，不交回候选方。

## 4. 跨会话续接：靠文档，不靠记忆

人可以隔一周回来接着做——但**别人接不上**，包括未来的自己。

- 当前推进哪件事、卡在哪、下一动作，落在
  [`handoff.md`](../handoff.md)，不落在脑子里；
- **“不能倒退的输入”必须写下来。**已经定过的事，下次不重新讨论——
  这是 `handoff.md` 最有价值的一节；
- 覆盖与缺口 → 实现矩阵；产品目标 → [`request-lifecycle.md`](request-lifecycle.md)；
  仓库操作 → [`../working/collaboration.md`](../../working/collaboration.md)；
- 停下来之前，先让 `handoff.md` 能回答：“接手的人一分钟内要知道什么？”

交接投影不是第二真源，不得在 handoff 里复制整张覆盖矩阵。

判据与 agent 那份的 §1.5 相同，只是理由不同：
**agent 是记不住，人是记得但传不出去。**

## 5. 小请求的裁量权

人可以判断“这件事不值得走全流程”，agent 不可以。但裁量有底线——
下面五条不因规模而豁免：

1. **不篡改原始意图**；
2. **不越过权限与范围**；
3. **结论有与风险相称的证据**；
4. **“完成”可判定**；
5. **发生改判时，交代触发与变化**。

省略任何一步都必须**显式写出“不适用”及理由**。空着与“忘了”无法区分。

**什么时候不能简化**：涉及安全边界、数据迁移、跨 App 契约、不可逆外部动作、
生产发布——这几类无论多小都走完整流程（同 `development-lifecycle-agent.md` §2）。

## 6. 改判三要素

人比 agent 更容易改判——信息多、判断在变。改判本身不是问题，**装作没改过才是**。

每次改判必须写清三件事：

| | |
| --- | --- |
| **触发** | 什么新证据或什么情况变化 |
| **原判断错处** | 当初哪一句不再成立——不是“当时信息不全”，是具体哪一步推错了 |
| **新判断** | 现在以什么为准；能独立成立，不写“理由见上文” |

不得装作从未判过，也不得为了让检查变绿而静默删除旧标准。修改验收标准时保留原标准、
原始失败输出和改判理由。

把结论写进 project-guide 前回读代码或实物重新取证，不把目标态文字直接写成现状。
文字改对了、代码里还是旧的，比不改更糟。

## 7. 人与 agent 协作时，人的义务

不只是 agent 有纪律。人这边同样有，且被违反时后果更大——因为 agent 会照做。

| 人的义务 | 违反会怎样 |
| --- | --- |
| 请求写清**边界**：含什么、不含什么、不含的归谁 | agent 会自行扩大范围，或漏掉本该做的 |
| 给**可判定的验收标准**，不给倾向性结论 | agent 向你的结论收敛，等于白问 |
| 并行提案时**不泄露其他方案** | 独立信号退化成改写（`development-lifecycle-agent.md` §3.2） |
| 收到“我不确定”时**不追问到它给出确定答案** | 逼出的确定性是编的 |
| agent 说“没查过某处”时**当作真话对待** | 声明盲区的动力被消灭，下次它不说了 |

最后一条最容易被忽略：**盲区声明是自愿的，只要说了就受罚，很快就没人说了。**

## 8. 提出与委派一项开发工作

提出时至少给出：原始意图、边界（含什么 / 不含什么）、可判定验收、已知约束，以及需要
人工批准的动作。只有歧义会实质改变结果、权限、成本或不可逆风险时才必须先澄清；局部、
可撤销且惯例明确的细节可以作合理假设，但交付时必须说明影响结果的假设。

**委派转移的是执行，不是最终责任。**人向 Agent 或其他人派活时必须给出范围、权限、预算、
停止条件和可验收输出；对超范围、追加成本、不可逆动作和规范修改及时批准或拒绝；亲自验收，
或指定未参与实施的验收方。执行过程按
[`development-lifecycle-agent.md`](development-lifecycle-agent.md) §1；需要并行候选时按该文 §2–§3。

## 9. 终审与责任归属

终审针对最终固定版本，不针对计划、候选、作者总结或“所有 Agent 都返回”。人至少确认：
原始请求逐条满足；最终版本通过有效门禁；未验证项、副作用和残余风险已说明；多仓 commit
与 gitlink 可取得；必要的交接足以恢复。

| | 谁负责 |
| --- | --- |
| 决定做什么、不做什么 | **人** |
| 决定怎么做（在约束内） | 执行者 |
| 产出是否符合验收标准 | 未参与实施的一方判定；无人时由**人** |
| 上线后出问题 | **人**——agent 不承担后果，因此也不能是最终判定方 |

这张表解释了为什么 agent 不得自我批准：**不是不信任它的判断，是它不承担后果。**
