# 产品定位重构评审（2026-09-23）

> 评审对象：`k8s/sunmoonai/docs/dev-investment-agent/tree-build/human-ai-turn/prd/repositioning-discussion-2026-09-23.md`
>
> 评审者：Cursor 工位上的 AI 助手（Grok 4.6）。只读了讨论稿、`PRD/requirement.md`、`PRD/value.md`、`SDD/architecture/methods.md` 和 `decisions.md` 相关条目，没有改任何产品代码。
>
> 标记沿用原文：对【所有者决定】的反对会单独标明依据；对【Claude 观点】同意或反对也会说清。

一句话：两层决策权作为**内部设计语言**成立，作为**产品本质和第一期路线**不成立。Claude 六条担心里 1、2、4、6 我同意，3、5 同意但解法要补强。最大的问题不是「方法没有护城河」，而是**第一期客户、第一期可卖物、第一期要造的机器三者互相打架**。

---

## 0. 总评：三处同意、三处要推翻或收窄

**同意、建议保留**

1. 入口翻转（云端从必经变成求助路径）是对的。旧的「通用/专业路由 + 领域识别引导重跑」是在替用户做他没要求的分类，既重又容易判错。
2. 九站是「委托人让 AI 把一件事做对」的语法，不是「我们编排用户机器」的专属实现。所有者纠正 Claude 第二轮「tree-build 多数退役」，这一纠正成立。
3. 价值漏斗（第一层卖数据/MCP，第二层卖方法/编排）商业上干净。第一期只做第一层，也和这个漏斗一致。

**建议推翻或收窄的【所有者决定】**

1. **「同一个 Codex 实例」不应成为第一层的前提。** 它把「日常工具」和「求助通道」焊死了。同一实例作为最优路径可以留，作为第一期准入条件应拿掉。依据见问题 3。
2. **「方法是长期主体」应改成「可复核的口径 + 证据 + 评测是长期主体，方法是载体」。** 否则架构重量会压在一份会过时的说明书上。`methods.md` 自己已经写了：编排只提高复制成本，抄不走的是数据、服务端计算与口径、评测闭环。依据见问题 2。
3. **「第一期只做第一层」和「第一期就要 runtime 座舱」互相矛盾。** 第一层若是「所有人买数据」，可卖物是知识服务 MCP，不需要账房、派发、租约、桌面壳。若第一期把第二层的控制面也造出来，会在验证「数据卖不卖得出去」之前把 staging 里那 56–94 人周花掉。依据见问题 8、10。

Claude 的建议一（先人肉跑第二层）和建议五（控制面按最小可用切）方向对，但实验少了一条臂，架构表少了一列「终态保留 / 第一期建造」。下面按第五节十二问展开。

## 1. 两层决策权分配这个产品本质，成立吗？

**作为系统设计语言：成立。作为对外产品本质：不成立。**

比「通用/专业」好的地方很具体：

- 不需要分类器，也就没有 F-DISPATCH-06 那条「判错就绕过 workflow」的失败模式。
- 对应真实行为：先自己开，不行再求助。用户能理解「把方向盘交出去」，不能理解「你的问题被判成了通用」。
- 把「谁决定拆步、谁决定验收、谁付 token、谁下结论」拆开，F-POS-03（结论永远是用户的）在表里有落点。

它遮住了四件比「谁握方向盘」更致命的事：

1. **用户买的不是决策权，是更快、可引用、少胡说的研究。** 对内用「两层分配」设计交接面可以；对外若开始用这套词，销售、定价、评测都会漂。PRD 里「类金融数据终端、不做咨询」仍应是对外定位；两层是交付机制。
2. **表里只有「用户 vs 顾问」，把模型本身的能动性写没了。** 模型在变强，第一层里真正握方向盘的经常是 Codex 自己。顾问层的价值取决于「我们比模型更会拆步」还能持续多久，这是一个会贬值的差，不是一个稳定的产品本质。
3. **求助触发条件是「用户不满意」。** 投研里最危险的是用户对错误答案满意。旧设计的领域识别至少是一张质量网（不管你满不满意，专业路径都可能被提示）。新设计把这张网撤了，升级变成自愿。价值最高的时刻（抓住用户没看出来的错）反而进不来。U3 比讨论里呈现的更关键。
4. **第一层和第二层的买方、销路、成功指标不同，硬捏成一个「升级漏斗」会拖死第一层发货。** 买 MCP 数据的人，和会交出驾驶权的人，不是同一批；第一期只做第一层时，不要用第二层的对象模型去定义第一层。

建议把「产品本质」改成两句，不要合成一句：

- 对外：给 AI 助手用的投研数据与口径，需要时再提供可验收的研究流程。
- 对内：第一层用户自驾，第二层顾问驾驶；同一套九站语法，两套委托人。

## 2. 「方法（编排）是长期主体」同意吗？Claude 第一条担心成立吗？

**Claude 第一条担心成立。所有者「方法是长期主体」只在一个收窄定义下才成立，现在的写法过宽。**

同意 Claude 的部分：

- 纯流程文本没有授权壁垒，模型变强后会贬值，资深分析师付钱优先为数据和省时间。
- 文档里看不到谁来写第一个专家包。没有写包的人，方法是假设。
- 评测集不存在（decisions.md 已标 ⚠），「优于原版 Codex」目前只是目标。把尚未验证的东西定为长期主体，再先造最重的机器，顺序反了。

不同意把结论推到「所以方法不该做」。`methods.md` 已经把护城河写对了，讨论稿没有把这句话提升到定位层：

> 编排形态提高的是复制成本，不构成保密；真正抄不走的是数据、服务端的计算与口径、以及评测闭环。

所以「方法」要能守，必须同时具备四样，缺一就只是一份会泄漏的 skill：

| 要有 | 为什么这才算资产 |
| --- | --- |
| 服务端口径与计算（MCP 工具内部） | 模型只看到调用和结果，用户拼不出算法 |
| 按步契约 + 确定性验收 + 返工上限 | 不靠模型自觉，这是比 skill 文件强的那一截 |
| 评测集（真值在查询层，不在文字层） | 没有它，方法无法回归，也无法定价 |
| 写包的人与金标准来源 | 否则包是工程师的想象，不是投研方法 |

建议把【所有者决定】里的优先级改成：

1. 现在能卖、也相对能守的：数据、口径、引用、MCP 工具（第一层）。
2. 长期能加价的：带评测的编排（第二层）。它是主体的前提是上面四样齐，不是宣布它是主体它就会成为主体。
3. 合规与工程便利：起步要，但不要用它们代替 1 和 2 的验证。

一句话：不要赌「我们比用户更会写 prompt 流程」；要赌「同一口径下，数字和引用能机械核对，裸 Codex 做不到」。后者才是 value.md 已经写过的价值检验。

## 3. 同一个 Codex 实例、经我们的 runtime，用户会接受吗？

**作为第一层前提，多数目标用户不会接受。Claude 第二条担心成立，而且比讨论里写的更硬。**

依据：

- `requirement.md` 写明服务对象「都不是开发者」，以桌面为工作场所。同时又要求用户自备模型 key、自驾 Codex。这已经是窄客群。再要求日常切到「我们的壳 + 我们的 runtime + 钉死的 codex app-server」，是在窄客群里再砍一刀。
- 已经在用 Codex CLI、Claude Code、Cursor 的人，不会为了「有时要求助」而换日常工具。若只在求助时打开我们的壳，第一层上下文不在我们这里，「同一实例」的好处落空——这正是 Claude 说的矛盾。
- 第一期若只卖数据，用户的自然入口是「在自己的助手里加一个 MCP」。这和 D5/D6（轻方案先验证领域价值、知识服务能否脱离编排单卖）是同一条路。用 runtime 把第一层绑死，等于把已经标过的轻方案否决掉，但讨论里没有把 D5/D6 正式关掉。

同一实例真正值钱的是：工作目录、已读文件、对话、工具审批状态连续。要这 80%，不必焊死进程：

| 路径 | 做什么 | 第一期要不要 |
| --- | --- | --- |
| A. MCP 直连（引擎中立） | 用户留在自己的 Codex/Claude Code/Cursor，只加知识服务 | 要，这才是第一层 |
| B. 显式交接包 | 求助时导出：问题、试过的步骤清单、工具调用摘要、工作区句柄；顾问在新会话接手 | 要，这是第二层的退路 |
| C. 同一实例（经我们的 runtime 接管现有进程） | 上下文零损失 | 可选，第二层体验升级，不是准入 |

这与【所有者决定】「同一个实例」有张力。我的立场和 Claude 建议三相同，但更硬：**第一层默认走 A，不走 C。** C 可以留在路线图，不能挡第一层发货。否则「第一期只做第一层」会在分发上直接失败。

钉死 Codex 还有另一半市场问题（Claude 已写）。适配层本来就在风险表里（constraints.md：编排与知识服务不绑定 Codex）。第一层走 MCP，这件事自动成立；第一层走 runtime+app-server，这件事自动不成立。

## 4. token 激励错位怎么解？把费用写进评测与标价够吗？

**不够。标价和评测是信息披露，不是激励对齐。**

根因：方向盘在我们手里，账单在用户口袋。返工、独立验收 Attempt、竞争择优，全是用户的 token。我们没有让流程变省的压力，用户会把贵账算在顾问费上——Claude 这条成立。

只显示「顾问费 + 预期 token」会让诚实的包看起来更贵，不诚实的包继续少报。还需要把费用做成**契约失败条件**，不是说明书上的一行：

1. **每个专家包发布时冻结 token 包络**（分位数，按评测集跑出来，不是拍脑袋）。超包络视为包失败，和验收不通过同一类，计入 U4 的质量门。
2. **评测三列：质量、引用、费用。** 更贵但只好一点点的方法判负。这条 Claude 有了，必须是发布门，不是仪表盘。
3. **第一期禁止并行 Attempt / 竞争择优。** 这是 token 乘数最大的旋钮，也是激励错位最明显的地方。对象模型可以留 `Attempt`，调度策略不要上竞争。
4. **步骤级预算硬停，交回用户，而不是顾问自行加步。** 决策权表里「返工几次」已经写了超限交回；要落到 step_contract，不要只写在表里。
5. **真正的正向对齐：好方法应该省 token。** 口径计算放进 MCP，让模型少推一遍 DCF、少自己编勾稽。若方法让账单更贵，它就不是方法资产，是披着方法的更长 prompt。

结构性限制：只要我们坚持不垫付 token，「我们吃超支」做不到。能做的是（1）包络当成验收，（2）超支交回而不是继续烧，（3）用服务端计算把步数打下去。不要幻想靠展示费用解决。

## 5. 「先人肉跑第二层再建控制面」可行吗？

**可行，而且应该做；但要把它定义成杀假设实验，不是「跑赢就开工」的立项实验。两周、五到十题、两三个分析师，只够证伪，不够证实。**

实验设计上的漏洞（按杀伤力排）：

1. **少了一条臂。** 必须三臂，不能两臂：
   - 裸 Codex（同模型、同配置）
   - Codex + 仅 MCP 数据（第一层）
   - Codex + MCP + 人按方法驾驶（第二层人肉）
   
   两臂（裸 vs 人驾驶）分不出赢的是数据还是方法。若「仅 MCP」已经赢了大半，第一期更不该造控制面。这是整份讨论里对实验最重要的修正。

2. **顾问本人是领域专家会混杂。** 必须先把方法写成逐步说明书，再让**非作者**按说明书驾驶。否则赢的是人，不是包。

3. **金标准若由同一批分析师写方法又写答案，循环。** 金标准应来自已有底稿、已发生的勾稽差错、或第三方已复核的覆盖笔记；时点截死，防训练数据泄漏。

4. **5–10 题只能杀明显不成立的假设。** 若人肉方法没有稳定赢过「仅 MCP」，停止讨论第二层控制面。若有优势但不稳定，加题，不要立刻建账房。

5. **「愿不愿意付钱」是廉价口头。** 改问：现在为同一任务付给 Wind/Choice 多少、内部几个分析师几天、若按这个差距从现有数据预算里挪，挪多少。

6. **两周偏紧。** 写方法、找金标准、约分析师、跑三臂、冻结时点，更像三到四周。宁可题少（先 3 道已有金标准的旧题）也要把三臂和「非作者执行」做干净。

结论：U8 我建议拍板为**做**。但成功标准写成：「仅当第三臂在费用可接受的前提下，稳定优于第二臂，才进入第二层对象模型的最小实现。」不要写成「人肉赢了裸 Codex 就开始造九站脚本」。

## 6. 切口场景选哪个？

Claude 两个候选里，我选 **公告解读 + 财务勾稽异常筛查**，不选财报季快速覆盖。另外加一个更窄的第一包。

判据仍用：高频、可度量、离不开数据。再加三条讨论里没写的：金标准好不好造、离「投资咨询」远不远、是不是四季忙一阵。

| 候选 | 高频 | 可度量 | 离不开数据 | 金标准 | 法律距离 | 季节性 |
| --- | --- | --- | --- | --- | --- | --- |
| 财报季/预告快速覆盖 | 中 | 差（叙事） | 中 | 难 | 近（像研报） | 强 |
| 公告解读 + 勾稽异常 | 高 | 好（数字是否对得上） | 强 | 中 | 较远 | 弱 |
| **年报/半年报附注关键数字提取 + 与三大表勾稽**（建议作为第一包） | 中高 | 最好 | 强 | 最好 | 远 | 中 |

不选「快速覆盖」的原因：它像在写研报，D17 最难守；质检靠人读；和卖方、终端里已有的「一键纪要」抢同一感知，很难证明不是套壳。

勾稽筛查好在：错就是错，真值可以落在查询层（value.md 要求的那种），正好逼出第一个评测集。

第一包再收一档：不要一上来做「所有公告」。只做 **A 股非金融、年报/半年报，提取附注里的若干张表，和已入库三大表勾稽，输出差异清单 + 引用**。结论栏仍空着给用户。这能同时定死第一个专家包、第一套评测集、MCP 要暴露哪些查询。

## 7. 专家是什么（A/B/C）？B 是否被过早排除？

**所有者倾向（A + 真人只写包不答问题）对，B 作为「云端替用户跑 agent」排除得对，但 B 的一个子义被误杀了。**

- **A（固化的专业能力：数据、工具、方法，云端持有、本机取用）**：这就是第一层 MCP + 第二层包。合规上唯一走得通的主产品。
- **B（云端专家 agent）**：若指我们垫 token、在云端读用户资料代跑，应保持排除——和「不垫付、资料不经过我们」正面冲突。
- **B 的子义：云端 planner 只出下一步指令，不见用户文件。** 这不是第三种产品，这就是第二层的 supervisor。不要用「排除 B」把编排也排除掉。第一轮 Claude 把 A 和编排拆开了，第三轮已经收回；评审时不要再把 supervisor 叫成 B。
- **C（真人专家答问题）**：保持卡在 D17 之后，单独立项。写包的人不是 C。要预先立一条硬规则：本产品永远不出现「真人在线答这一问」，否则方法一弱，销售会把 C 从后门塞进来，那是持牌咨询。

还缺一个讨论里没命名的 **D：专家 = 仅数据与口径 MCP，没有编排。** 第一期只做第一层，卖的就是 D。不要把「专家」一词只留给第二层，否则第一层在话术上没有主体，U3（用户怎么知道有专家）会更糟。第一层应叫「数据/口径专家工具」，第二层才叫「专家包」。

## 8. 保留/退役/新增那张表，有没有判错？第一期要不要账房、派发、租约？

**终态保留大体对；第一期建造完全判错了。** 表把「第二层最终要有的机制」写成了「现在要留的机制」。请加一列。

| 机制 | 终态 | 第一期（只做第一层） | 理由 |
| --- | --- | --- | --- |
| 知识服务两个 App + MCP（⑤） | 保留 | **建造** | 这是第一层可卖物 |
| F-POS、本地内容检查 | 保留 | 建造（检查可先做规则子集） | 法律与信任 |
| 对比评测 | 保留 | **先有评测集和三臂实验，代码可以后写** | 资产前提 |
| runtime + 薄桌面壳 | 第二层需要 | **不做，或只做 MCP 配置说明** | 同一实例不是第一层前提 |
| 账房状态机 / 事件 / 幂等 | 第二层要 | 不做 | 第一层不建单 |
| 派发桥、租约、fencing | 第二层要（长任务、不可信执行端） | 不做 | 求助若是人在环上的短任务，先用请求-响应 |
| 中断 / Interaction 原子消费 | 第二层要 | 不做 | 工具级审批在用户自己的助手里已经有了 |
| 多方竞争 | 终态可选 | **不做，建议从「保留」挪到「默认关闭」** | token 激励错位 |
| 结果密文跨设备取回 | 可选 | 不做 | Claude 建议对；U11 建议拍板不做 |
| 三层类别判定与领域识别 | 退役 | 同意退役 | |
| 交接面 | 新增 | 第二层才设计；第一期最多留导出格式草案 | |
| 专家包作为一等公民 | 升格 | 先有一个包的人肉版和评测，再谈发布单元 | |

账房、派发、租约在**第二层无人值守长任务**时需要，在**第一期验证数据能不能卖**时不需要。所有者说九站语法仍在，不等于九站的脚本实现第一期全上。语法可以先由人走（这正是 turn/ 和人肉顾问在做的事）。

Claude 建议五「账房第一期只要状态机、事件、幂等」仍然偏重——那是「已经决定做第二层最小控制面」之后的切法。现在还没通过问题 5 的杀假设。更小的第一期是：**只发 MCP。**

退役那一行（三层判定、领域识别、D11/D12）我同意。漏掉的退役/降级：把桌面应用从「用户界面只有桌面」里，对第一层放宽为「第一层界面可以是用户已有的助手；桌面是第二层座舱」。否则 requirement.md 的「只有桌面应用」会把 MCP 入口直接判非法。

## 9. 上传三级，默认第二级，合理吗？「本机摘要」风险怎么看？

**不合理。默认第二级建议推翻。这是讨论里对 I20 /「不经过我们」伤害最大的一条，而且来自已被部分纠正的第一轮。**

风险：

- 「本机摘要」是资料的函数。对投资经理，摘要里的标的、仓位线索、未公开论点就是 alpha。发到云端，精神上已经「经过我们」，即使不是原文件。
- I20：用户资料、文件名、本地知识库内容不上传。摘要是灰区，必须先问 D17，不能用产品默认值抢跑。
- 摘要谁写都糟：Codex 写会夹带原文；用户写则交接摩擦大，求助路径死掉。
- 默认级决定 90% 的流量。默认第二级等于默认把研究过程送到服务器。

建议改成：

| 级 | 内容 | 何时 |
| --- | --- | --- |
| 0（默认） | 问题文本 + **结构化元数据**（用过哪些工具名、失败码、步数、耗时）。不含资料片段、不含文件名、不含引文原文 | 默认 |
| 1 | 用户**可见可改**的摘要，提交前 diff 出将离机的每一字段 | 用户显式勾选 |
| 2 | 用户勾选的文件/片段 | 等同更高法律风险，D17 点头前不要做；做了也要按件授权、按次过期 |

「顾问只见元数据与密文」和「默认送摘要」不能并存。决策权表里「什么可以离开本机」写的是用户授权范围——默认值必须落在授权的最小端（P3：默认值属于省事方向，朝省事须人确认）。默认送摘要是朝省事且无人确认。

## 10. 三层客户与「第一期只做第一层」：数据不独占，订阅能撑收入吗？

**不能按「终端数据订阅」来撑，只能按「给 AI 助手用的口径与引用接口」来撑；即便如此，也撑不起 56–94 人周的控制面，只撑得起一个 MCP。**

公开公告和研报没有独占。和 Wind/Choice/同花顺比数据覆盖，必输。第一层能收钱的唯一楔子是：

- 给编码助手用的 MCP 比传统终端好用一个数量级（现有终端几乎不是为 agent 设计的）；
- 口径稳定、查询层真值、引用可回源（这是 value.md 的卖点，不是「我们有公告」）；
- 也许有少量自有计算指标。

这要求先做 U6（数据盘点）：有什么、从哪来、和 Wind 差在哪、哪些能合法再分发。盘点没出来就谈「所有人买数据」，是在给空货架做定价。

客群还要收窄：第一层真正会付钱的，是已经在用 Codex/Claude Code、自己能配 key 的人。这不是 `requirement.md` 写的「投资经理（非开发者）」。两套人不能用同一张第一期故事：

- 若第一期要收入：卖给 AI 原生的研究员/量化/个人，MCP 订阅，小额。
- 若第一期要验证投资经理场景：不要谈订阅收入，做人肉顾问实验（问题 5），对象是 2–3 个认识的经理。

「第一期只做第一层」我同意，前提是第一层 = MCP + 盘点 + 评测集胚子，不是第一层 = runtime 座舱 + 薄桌面 + 半个账房。后一种会把「只做第一层」做成「为第二层打地基」，用第一层的故事花第二层的钱。

机构层（合规模式）对流程影响确实大（所有者说得对），现在不要设计；但有一个架构后果现在就要知道：整份设计是单人、单机、单 Codex。投研是团队工作。端到端加密 + 资料不出本机，会让「组内共享底稿」变成第三层的重写。不必现在做，但交接面和结果对象不要设计成「永远只有一把设备私钥能解开」。

## 11. turn 机制改造：看到什么问题？四条补充规则够不够？

方向同意：绝大多数问答不留痕；值得留的才建 `human-ai-turn`；状态从 git 反推。原 thread 机制确实在用目录模拟尚未存在的控制面。

四条补充规则**必要但不充分**，主要洞在「靠纪律」：

1. **AI 先提交、人再提交**——没有 hook 就会经常混成一次提交，作者信息丢了。至少约定 commit 标题前缀（`ai:` / `review:`），在含 `human-ai-turn/` 的变更上做检查；现在没有。
2. **追问追加在 `user-message.md` 末尾**——来龙去脉在，但「当前要做什么」会沉底。应固定文首一段「当前请求」，其下才是追加历史，或分节编号并在文首写当前节号。
3. **改正式文档的理由进提交说明**——这是定稿记忆的唯一载体，却无 hook。目录一删，工作区里理由消失，只剩 git log。这条比另外三条更需要强制。
4. **产生过正式文档修改的，提交后再删目录**——对。再补：删之前确认对应提交已能从 log 读到「以何为底、改了什么、为什么」。

「绝大多数问答不留痕」会丢掉的，不是日常 CLI 碎答，而是**当时觉得小、后来成为负载的口头决定**。不要因此退回全量 thread。加一个比 `human-ai-turn` 更轻的东西即可：仓库里一份 append-only 的 `decisions-log.md`（或沿用现有 `decisions.md` 的纪律），五到十行记一条。判据：改了已定稿行为，但不值得开目录。

这次评审本身暴露了新机制的一个缺口：多方 AI 评审往哪放。旧 competition 协议是为这个准备的；新机制只说「人可以随时建目录」。本次是「意见写在各自工位根目录」，能用，但回收、对比、定稿路径没有约定。若还要再问几家，应规定：各工位根目录一份、文件名含工位名、由人择一写入正式 PRD/SDD，并在提交说明引用各评审路径。不要把评审直接改正式文档。

另外：目标文件已存在就原地改，审 diff 比审全文好。风险是 AI 顺手改相邻段落。应写明：非问题点的「顺手清理」禁止。

协议目录（competition / 分支）没改，这是对的。imp/uat 答在分支上，也是对的。

与产品的关联（2.5）：「产物与历史归 git，状态与账归数据库」这句区分是对的。将来账房不要把研究结果只做成行；结果应内容寻址（提交哈希或 CAS），merge/采纳才是状态变化。不要等控制面建完再发现 git 用不上。

## 12. 最大的盲区是什么？

双方都没提到、但会决定成败的，按重要性：

1. **分发对象和设计对象不是同一群人。** 设计对象是非开发者投资经理 + 只有桌面应用；第一层能付钱的是会配 key、会用 Codex 的人。不先承认这个裂口，第一层没有真实用户。这是最大盲区。
2. **升级触发在「不满意」，错过「满意但错了」。** 见问题 1。投研产品若不能在用户觉得还行时提出证据缺口，价值大半不在。第一层 MCP 至少应能做廉价的本地提示：这条结论在我们数据里没有对应查询/引用——这不是旧的领域分类器，是证据网。
3. **谁写第一个包、金标准从哪来。** 没有具名领域专家、没有可引用的历史底稿，方法层全是空中楼阁。这比「团队会不会写代码」更先。
4. **数据授权与再分发，不只是「算不算投资咨询」。** D17 被当成咨询持牌问题。info-app 采集 + 经 MCP 卖出去，可能先撞上数据许可。U6 和 D17 应绑在一起，不要只看法条里的「投资建议」。
5. **Windows + 锁定的办公机。** 国内投研终端环境经常无管理员权限、不能随地装 Electron、Wind/Bloomberg 已经占桌面。staging 把桌面客户端写成 13–20 人周，没把「装得上」当成风险。第一层走 MCP 反而更适合这环境（若他们用网页或已有助手）；第一层走桌面壳更不适配。
6. **模型改进是倒计时。** 每季度裸模型会吃掉一层流程优势。评测基线必须按时间衰减来看，不能用一次 2026 年的人肉实验为 2028 年的编排机器背书。
7. **第二层失败时，第一层现场被毁掉。** 顾问烧了 token、改了工作区、交回一个半成品，用户比求助前更糟。交回必须包含：做了什么、什么已核实、什么仍未知、工作区如何恢复。决策权表有「超限交回」，没有「交回物契约」。
8. **求助是负向时刻，而且稀。** 等用户失败再出现的产品，转化天然差。U3 不能靠产品教育。MCP 工具里用**包的输入 schema 做本地匹配提示**（「这个问题像《年报勾稽》包」）比「请了解我们还有专家」有用，也不等于旧的通用/专业分类。

## 建议的实际顺序（把讨论里的顺序倒过来）

1. **本周不写代码的两页：** 数据盘点（U6）；D17 问题清单（咨询形式 + 数据再分发 + 摘要离机）。
2. **收窄第一包：** 年报勾稽，题目、时点、真值查询一起冻。
3. **三臂人肉实验（U8）。** 未通过则第二层控制面不立项；通过了再进入 5。
4. **第一期可卖物：** 知识服务 MCP（引擎中立）。runtime/桌面/账房不进第一期。
5. **仅当 3 通过：** 交接面（0 级默认）+ 最小控制面（单设备、单 Attempt、无竞争、无跨设备），专家包从那一份人肉方法升级。

这和 Claude 的收束句一致，只是把「先人肉、再收窄、再造机器」里的「机器」明确成两台：第一台机器是 MCP，第二台才是九站脚本。现在的风险是还没验证第一台，就要按第二台的零件清单采购。
