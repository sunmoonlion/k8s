# turn 的投影

一次一问一答是摸不着的：谁在答、答到哪、这一版算不算数、在等谁。
**本文写的是把它显给人看的最小办法，以及——更要紧的——什么时候根本不必显。**

## 默认：直接交互，不留痕

人在任何入口把话说给 AI 助手：命令行、IDE、脚本把话投给一个交互会话。AI 在那个入口里答；
要动文件就直接动，人看 diff、改、提交。

⚠ **绝大多数 turn 就是这样：不建目录、不编号、不写回执。**这不是简化版，这是常态。
一次问答留下的痕迹只有两样：改过的文件和它的 git 历史；人脑子里与 AI 那个会话里的上下文。
两样都够用的时候，什么都不用建。

直接交互仍然要守的只有纪律：[八条](#交给-agent-的活八条都成立)、[不给倾向性结论](#用户消息写多严)、[批准点](approvals.md)。
它们不需要文件。

## 什么时候值得留

**判据只有一句：这一问的问和答，将来有没有人要回来看。**命中任一条就建目录，都不命中就别建：

| 值得留 | 为什么 |
| --- | --- |
| 答会成为别的文档或代码的依据（权威层） | 半年后要能查「当时到底问的什么」 |
| 不可逆、已知对立、判据未定（[多方竞争](competition.md) 的 T2 判据） | 事后要能复核问法有没有倾向 |
| 要交给另一个执行者、另一个会话接着做 | 交接只能靠落盘，不能靠记忆 |
| 同一问要发给几家比较 | 各家要拿到一字不差的同一问 |
| 人自己想留着 | 这是人的裁量，不需要理由 |

一句话的澄清、改个措辞、跑个命令看结果、「把这段挪到那节」——**都不值得留**。

## `human-ai-turn/`：值得留的那一问长什么样

在工作区里**离目标最近的地方**建一个目录。名字约定为 `human-ai-turn`——叫别的也行，约定这个名只是为了讨论方便：

```text
<任务目录>/human-ai-turn/
├── user-message.md          这一问；追问接着往下写
│
│   或者按种类分子目录——同一个问题要问好几类时，各放各的：
├── prd/user-message.md
├── sdd/user-message.md
├── imp/user-message.md
└── uat/user-message.md
```

- **子目录可选**。一个问题只问一类，`user-message.md` 直接放在 `human-ai-turn/` 下；同一个问题先 PRD 再 SDD 再 IMP，就按种类分。种类只有四个，见下「四个种类」；
- **它是普通目录**。人随时建、随时删；在仓库里就和别的目录一样可提交、可推送、可删除。没有门禁盯着它的形状，只查里面的链接；
- **没有 thread、没有编号、没有回执。**同一问追问多少次都在同一个 `user-message.md` 里，目录总是最新状态；
- ⚠ **删之前看一眼**：这一问产生过对正式文档的修改（`PRD/`、`SDD/`、代码）吗，那些修改提交了没有。
  提交了，目录随便删——历史在 git 里；没提交，删目录等于这一问从没发生过。纯探讨、什么都没改的，随手删。

### 问：`user-message.md`

- 发出去的就是这个文件的内容。**模型只知道这里写了的东西**——要它交回什么、能改哪些文件、哪些动作先问人、有哪些背景，都得写进去；没有哪个机制会替它补上；
- **追问追加在末尾，不覆盖。**AI 再读时看到的是这一问的完整来龙去脉，能理解「上次你说 X，改成 Y」；目录仍是最新状态，只是最新状态带着来路。
  人想清空重写也可以——它是普通文件——只是从此历史只在 git 里；
- **没有 YAML 头。**谁答的看提交的 `Co-Authored-By`；验收哪个提交写在正文里；
- 模板见 [`user-message.md`](user-message.md)。

### 答：落在哪，按目标定

| 这一问的目标 | 答落在哪 |
| --- | --- |
| **已存在的文件**（某份 `PRD/`、`SDD/`、代码） | **直接改那个文件。**改完是工作区里的未提交 diff，那就是答 |
| **还不存在** | 在 `human-ai-turn/` 下新建。目标路径说得清时（「写 ledger 的需求」→ 它的 `PRD/requirement.md`）也可以直接在目标路径新建——未提交前同样是草稿 |
| **说不清目标路径**（「A 方案还是 B 方案」这类讨论） | 在 `human-ai-turn/` 下新建一份，名字自定 |
| **IMP、UAT** | 答在**分支与提交**上，目录里不放产物；见 [IMP 规则](imp/message-rules.md) |

**答和问分开放**：AI 不往 `user-message.md` 里写答。那个文件是人的话。

### 定稿：人怎么采纳

见 [定稿](finalize.md)。要点一条：**AI 答完先提交一次，人再改再提交。**
两次提交把「它答的」和「人改的」分开——这替代了上一版的「交回即冻结」。T0 级的小改可以合成一次。

## 状态从 git 读，不另写

⚠ **不另写记录或进度文件。**做到哪、谁在做、在等谁，从下面读：

| 看到什么 | 意思 |
| --- | --- |
| 有 `human-ai-turn/`，目标文件有未提交改动 | 问了，AI 答了，人还没审 |
| 目标文件已提交 | 人定稿了 |
| 目录被删 | 这一问结束 |

这是 `P2`（状态从产物反推，不从声明读取）在这套载体上的样子。

**载体可以换**——数据库、Issue、PR、事件流都行，但换了也不能丢这几样。上一版靠目录结构保住它们，现在靠：

| 不能丢的 | 现在在哪 |
| --- | --- |
| 原始请求与边界 | `user-message.md` |
| 以什么为底、改了什么、为什么改（含改判三要素） | **改 `PRD/`、`SDD/` 的那次提交说明** ⚠ 现在靠纪律，还没有钩子查形状 |
| 谁答的、谁改的 | 两次提交与 `Co-Authored-By` |
| 验收的对象与证据 | 完整提交号写在 UAT 的 `user-message.md`；逐条判定在 worktree 的 `test/` |
| 基线 | 提交号 |

交给程序驱动之后，真源移到控制面（[工作台后端的账房](../tree-build/SDD/modules/0001-workbench.md)），目录只剩投影。
**不得直接编辑投影**：改目录不改记录，等于同一事实有两个权威写入面（`P1`）。

## 四个种类

| 种类 | 问什么 | 答落在哪 | 定稿成什么 |
| --- | --- | --- | --- |
| **PRD** 产品需求 | 要什么、做到什么算满足 | `PRD/` 下的文件（改或新建） | `PRD/` 目录 |
| **SDD** 设计 | 怎样满足 | `SDD/` 下的文件（改或新建） | `SDD/` 目录 |
| **IMP** 实现 | 做出来 | 各自的 worktree | 审核通过后合并到 master |
| **UAT** 验收 | 验证是否满足 | worktree 的 `test/` | **结论写进那条提交的说明** |

**每一类的定稿就是它自己那份东西**：AI 改出来的 diff 是答，定稿是人读完取舍之后提交的那一版，不换成下一种文档。
后面的问拿前面的定稿当输入：SDD 拿 `PRD/`，IMP 拿 `SDD/`。**但这不是排队**——一个任务可以同时问几个 PRD 问题，
IMP 里发现设计不对要回 SDD，子任务各走各的。四类不是四个先后相接的阶段，是四种问法；不是每件事都要把四类都走一遍。

### 一问属于哪一类

归类只问一句：**这一问的答案定下来，跟着改的是上表「定稿成什么」里的哪一份？**
改 `PRD/` 就是 PRD，改 `SDD/` 就是 SDD，改代码就是 IMP，改「这一版满不满足」的结论与证据就是 UAT。
**四份都不改的问题，多半不属于这个任务**：过程与工具怎么定（候选由谁选、用哪套门禁）是规范的事，去改规范。

常混的几种：

| 这一问 | 属于哪一类 | 为什么 |
| --- | --- | --- |
| 后端能不能读客户任务的正文 | **PRD** | 信任边界是约束，属于「要什么」——明文读什么、加密什么，是需求对系统的限制 |
| 控制面用不用图执行框架 | **SDD** | 选型是怎样满足；否掉了哪几条、为什么，写进 `SDD/architecture/` 的「取舍」 |
| 并行候选取最先通过的一份，还是全交回再比较选定 | **SDD** | 两种都成立、要定死，定完 `SDD/` 才写得下去 |
| 状态机与 workflow 怎么分工 | **SDD** `architecture/` | 责任边界 |
| 步骤交回物要带哪些字段 | **SDD** | 接口与数据的形状 |
| 失败重试三次 | **SDD** | 除非这个次数客户要看得见、要进验收口径，那才是 PRD |
| 响应两秒内 | **PRD** | 非功能要求：要什么，不是怎么做 |
| 这一版为什么没通过 | **UAT** | 结论与证据。要改设计，写进结论并回 SDD 追问，不在验收里改 |

### 归错了怎么办

- **一问里混了两类**：拆成两问，各归各类——不在同一问里混着答。
- **答越界了**（PRD 的答里给了技术方案）：**不打回**。定稿只收本类的那部分，越界那部分挪进下游那一类的 `user-message.md` 当输入。
- **整问派错了类**：AI 停下来问（见下面八条的第二条），由人改派到正确的那一类，**不在原问里补**。

## 一个例子

1. 一开始只有一句话：「做一个 AI 投资研究工具」。这值得留：建 `human-ai-turn/prd/user-message.md`，人问、AI 直接写出 `PRD/requirement.md`、人改、追问几轮、提交。
2. 接着问怎么做（**SDD**）：`human-ai-turn/sdd/user-message.md`，AI 写 `SDD/architecture/`、`SDD/modules/<号>-<短名>.md`，人定稿提交。往下的子任务目录在 `SDD/submodules/<号>-<短名>/`。
3. 某个子任务在自己的目录里同样走 PRD、SDD 两类（需要哪类走哪类），再往下拆。
4. 要动代码时问 **IMP**：`human-ai-turn/imp/user-message.md` 写清工作区与完成条件，执行者在自己的 worktree 里做，交回分支与提交。
5. **UAT** 派给验收者：`human-ai-turn/uat/user-message.md` 写明验哪个提交，测试写在 worktree 的 `test/`，结论写进那条提交的说明。判定不通过，追问里写明理由重做。
6. 重做到什么时候不再重做，由驱动方定。
7. 中间任何一句「这段措辞改一下」——直接说，直接改，不进目录。

## 任务目录里放什么

```text
<任务目录>/
├── human-ai-turn/                可选：值得留的那一问；不值得留就没有这个目录
│   └── user-message.md           或 prd/ sdd/ imp/ uat/ 各一份
├── PRD/requirement.md            PRD 类的定稿：要什么。**不分模块**，长了按主题再拆几份
├── SDD/                          SDD 类的定稿
│   ├── architecture/                模块之间的关系
│   ├── modules/<四位号>-<短名>.md   每个模块本身是什么
│   └── submodules/<四位号>-<短名>/  子任务：内部是同样结构的任务目录
└── <约束目录>/                   可选：这一层的约束、纪律与开发提醒；名字自定
```

- **约束目录可选，名字自定**（本项目用 `rules/`）：装这一层必须守的和必须记得的——代码规则、开发指导。
  它不归哪一类，四类都要守，所以**与 `PRD/`、`SDD/` 平级**，不塞进某一段的定稿里。
- **模块只在 `SDD/` 下划**：分成哪几块是怎样满足，不是要什么。`architecture/` 是目录，入口文件 `README.md`，可以再拆多份。
- `SDD/modules/` 与 `SDD/submodules/` **同号同名一一对应**：前者是这一层对这块的说明，后者是它往下的子任务。
- 两者与实现时 worktree 里的模块目录**一一对应**；**以定稿为准**：代码结构要变，先改定稿。
- 子任务自己的 `PRD/` 写它要满足什么。
- 改动过的代码留在 worktree 与它的提交里，不拷进任务目录。
- **不另写记录或进度文件。**⚠ 禁的是**任务目录里的第二份进度**。IMP 在自己 worktree 的代码分支上写 `CHECKPOINT.md`
  不在此列——那装的是推不出来的工作材料，见 [IMP 规则](imp/message-rules.md)「跨运行时 thread 续接」。

## 用户消息写多严

**模型只知道用户消息里写了的东西**：要它交回什么、能改哪些文件、哪些动作必须先问人、有哪些背景和出处——
凡是要它知道、要它遵守的，都必须写进去。直接交互时这些话说在入口里；值得留时写进 `user-message.md`。

写多严按任务轻重。下面说的是要**表达出什么**，不是要用什么格式：一段自然语言说清了就算满足。

| 程度 | 适用 | 至少要说清 |
| --- | --- | --- |
| 一段话 | 可逆、局部、方向明确（T0） | 要什么、交回哪一种，以及要它遵守的任何限制 |
| 加边界 | 影响跨多个文件或多个仓（T1） | 要什么、交回哪一种、范围；IMP 类另加完成条件 |
| 按模板填全 | 命中任一条 T2 判据：不可逆、权威层、已知对立、判据未定 | 本类规则「这一类该问什么」里的每一栏；不适用的写「不适用」及理由 |

档位判据见 [多方竞争](competition.md)「要不要开」；各类要写清什么，见各自的规则。

- **用户消息由人写**；由上层定稿拆出的任务，用户消息来自定稿的相应一节，随定稿一起生效。
- **写清边界**：含什么、不含什么、不含的归谁——否则执行者会自行扩大范围，或漏掉本该做的。
- **不把内容判据写进 PRD 与 SDD 两类的用户消息**：一旦写成条目，答案空间就被提前封死，
  「其实不需要这个机制」这类答案再也交不上来。这两类合不合格按各类规则判。
  ⚠ 禁的是**内容判据**（什么答案算对），不是**形式判据**（交什么、要回答哪几个问题、边界、格式）——
  后者必须发，否则各家交的东西形状各异，没法逐项比。两类的完整矩阵见
  [多方竞争协议](protocol/competition-protocol.md)「工单发什么、不发什么」。
- **IMP 类必须写完成条件**：执行者不知道做到哪算完，就只能猜。UAT 类照抄被验那一问的完成条件，不另立。
- **不给倾向性结论**——否则产出向写用户消息的人的结论收敛，等于白问。
- **内容判据先冻结、密封，⑤ 验收才公开**；没发出去的判据只能用于排序或加分，**不得用于扣分或判不通过**。密封时记下 SHA-256，公开时可验它没被改过。
- **出题的人与答题的 agent 分开**。AI 不改用户消息，发现用户消息有问题时停下来问。
- 哪些动作需要人批准，见 [人的批准点](approvals.md)；写用户消息的人要把它们写进去。

## 交给 agent 的活，八条都成立

不论哪一类、不论单路还是并行、不论直接交互还是落了目录：

1. **不用计划覆盖原始需求**；
2. 只在范围、工具、数据、预算和副作用边界内行动；用户消息没说清边界、而越界会有影响时，先问；
3. **区分事实、推断、假设、缺失和未运行验证的结论**，不可混写；
4. 对可中断的工作持久化检查点；
5. 无法满足完成条件时请求输入或**明确失败**，不交半成品；
6. 在**最终固定版本**上运行与风险相称的验证；
7. 报告盲区、副作用和残余风险；
8. 未经授权不推送、合并、发布、删除远端资产或扩大外部影响。

第 3 条是 [UAT 怎么验](uat/verify-rules.md) 证据采信的前提：分不清事实与推断，采信分级就无从谈起。

## IMP 与 UAT 的 worktree

- 执行者在自己的 git worktree 里实现；验收者在 worktree 的 `test/` 里写测试。
- 交回的是分支与**完整提交号**；产物不拷进任务目录。
- 审核者在被审的 worktree 之上再开一个审核 worktree，逐层向上，最后合并到 master。
- **worktree 完成后才清理**；清理前分支或标签必须留下——工作区可以删，提交不能跟着消失。
- 审核发现问题：**不在审核 worktree 里替对方写**，追问让它重做；审核 worktree 只用来核对、跑测试、做最小修补。
- **人负责清理**：工作完成、合并进 master 之后再清 worktree；清理前确认分支或标签还在。

## 追问与返工

- **打回就是追问**：理由追加在 `user-message.md` 末尾——用户消息里的哪一条要求（或本规范的哪一条）没满足、证据在哪、要求改什么；
  用户消息本身没说清、无法判定的，写「不可判」并交给人，不自己发明标准。返工派回出问题的那一类——设计有问题回设计，实现有问题回实现。
- **标准或判断变了**，写清改判三要素：触发、原判断错在哪、新判断（见 [人的批准点「改判」](approvals.md)）。
  落点两处：追问里，以及改 `PRD/`、`SDD/` 的那次提交说明。
- **什么时候不再重做，由驱动方定**：现在驱动方是人，人自己判断——改问法、改判据、换做法还是换执行者。本规范不定次数。
- **多方竞争**：同一问发给几家，各家一条分支，从同一基线开；各家拿到一字不差的同一份 `user-message.md`。
  定稿写明以哪一家为底。规则见 [多方竞争](competition.md)；竞争内部的回退不计入本任务的返工次数。
