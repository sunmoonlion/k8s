# BRD 用户消息模板

复制成 turn 里的 `user-message.md`。

本阶段的用户消息要写清什么，见 [BRD 规则](brd-rules.md)「这一段的用户消息」；写多严见 [任务的生命周期](../lifecycle.md)「用户消息写多严」，字段的含义见同一份的「turn 的固定字段」。
这一段该问哪几件事，见 [BRD 规则](brd-rules.md)「这一段在问什么」；答要写成什么样，见同一份的「response 写什么」。

```markdown
---
executor: <派给谁；还没派出去写 unassigned>
verifies: 无
---
# turn <四位号>：<短名>

## 现在只有什么
<触发这一问的原话或现象；现在是怎么做的、卡在哪。分清事实、推断与假设>

## 要弄清楚的
1. **谁的问题**：<用户是谁、在什么场景下遇到>
2. **什么算解决**：<可判断的结果，不是「更好用」>
3. **边界**：<这次做什么、不做什么、以后再说什么>
4. **硬约束**：<资质、合规、平台、成本、时间上不能碰的>
5. **取舍**：<有哪几条路、各自代价>
6. **未知**：<现在答不了、要去查或去试的>

## 不要做的
- **不给方案**：技术选型、模块划分、接口都不在这一段——那是 PRD 与 SDD；
- **不替人下决定**：把选项和后果摆清楚，决定由人做；
- 涉及外部规则（资质、合规、平台限制）标明依据与出处，查不到写「未核实」。

## 约束
<必须遵守的规则、不能动的东西；例如只交文本、不改代码>

**交回：写成这个 turn 的 `response.md`，由 discussion agent 交，不改代码。人读完定稿成 `PRD/`。**
```

这一段不写验收标准：答得合不合格按 [BRD 规则](brd-rules.md)「response 写什么」判——写进用户消息只会把答案空间提前封死。

不适用的栏写「不适用」及理由——空着与「忘了」无法区分。命中 T2 判据的任务每一栏都要填。
