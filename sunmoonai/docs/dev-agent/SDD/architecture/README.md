## 轮廓

**先读它**——下面的组成、通道与约束都是那条线上的局部。

## 组成部分

```text
用户电脑
┌──────────────────────────────────────────────────────────────────┐
│ 桌面应用（Electron）　三扇独立窗口，能力按窗口授予                 │
│   主窗口：提交 Task · 进度与结果 · 任务历史 · 本地知识库管理        │
│   审查窗口：Task 级审查（不挂本机能力）                            │
│   本地窗口：工具级审批 · 本地确认 · key 与模型配置 · 工作区授权    │
│                    主进程 ⇅ ③ 本机管道                             │
│ 本地 runtime（Python 后台服务，常驻；关掉窗口仍在跑）              │
│   连接 · 策略 · 工具级审批拦截 · key 保管 · 本地知识库 · 执行适配   │
│   ──② Codex Python SDK（stdio）──▶ Codex（随应用打包）            │
│                                └── 沙箱 ── 独立工作区              │
└──────┬───────────────────┬──────────────────┬──────────────────┘
       │ ④ HTTPS/事件流     │ ① WSS（runtime    │ ⑤ HTTPS(MCP)      │ ⑥ HTTPS
       │   （桌面应用）     │   主动外连）      │   （Codex）       │  （Codex）
       ▼                   ▼                  ▼                   ▼
  ┌──────────── 后端（supervisor）────────────────┐   知识服务        模型厂商
  │ 身份与会话 · 设备 · 派发网关 · 路由与编排      │   info-app 采集   用户自选
  │ Task/Attempt/Interaction/持久化账（PostgreSQL）│   knowledge-app   用户自付
  │ 方法库 · 审计 · 结果密文                       │   建库与 MCP
  └───────────────────────▲────────────────────────┘
                          │ ⑦ HTTPS（内部人员）
                     管理后台：运营 · 客服 · 审计查询（另有官网与下载页）
```

| 部分 | 职责 | 不做什么 |
| --- | --- | --- |
| **桌面应用** | 用户唯一的工作界面：提交 Task（含本地预填、用户确认的任务类别）、进度与结果、任务历史、研究底稿查看与编辑、本地知识库管理、Task 级审查、工具级审批与本地确认、key 与模型配置、工作区授权、设备与计费；拉起 runtime 并确保它在跑；托盘、通知、开机启动 | 不持有领域事实；不自己调用模型；审查窗口不挂本机能力 |
| **本地 runtime** | 主动连后端；接收 Attempt 并驱动 Codex；向 Codex 提供本地 MCP（本地知识库、`escalate`）与公开资料取数工具；工具级审批与副作用记账的拦截点；key 保管；工作区与沙箱策略；本地内容检查与结果加密；上报事件、用量、副作用意图与回执 | 不持有任何持久化账的权威副本；不自行决定 Task 状态 |
| **Codex** | agent loop：规划、调用工具、读写文件、执行命令、调用模型与 MCP | 不直接连后端；不开网络端口 |
| **后端（supervisor）** | 身份与会话、设备注册；Task、Attempt、Interaction、Event、Delivery；持久化账；受理判定与路由、编排、验收与发布；方法库；派发网关；结果密文与元数据；审计 | 不调用生成式模型；不中转模型请求；不接触用户 key；看不到本地资料、文件名与结果正文 |
| **知识服务** | info-app 从合法来源采集；knowledge-app 建库、检索、领域工具，经 MCP 按查询下发；embedding 与 rerank 用自有模型 | 不接触用户 key；不装观点类内容；不整批下发 |
| **官网与管理后台** | 官网：产品介绍与下载页；管理后台：内部人员的运营、客服、审计查询 | 管理后台只见元数据，不见研究结果正文 |
| **模型厂商** | 推理，由用户选择并付费 | — |


## 本轮建哪几块

按**运行位置、信任域、发布方式**切——三者都不同就单列：

| 模块 | 对应上表的哪一部分 | 跑在哪 | 内部结构见 |
| --- | --- | --- | --- |
| [`0001-backend`](../modules/0001-backend/PRD/requirement.md) | 后端（supervisor） | 服务器 | [设计](../modules/0001-backend/SDD/architecture/README.md) |
| [`0002-desktop`](../modules/0002-desktop/PRD/requirement.md) | 桌面应用 | 用户电脑 | [设计](../modules/0002-desktop/SDD/architecture/README.md) |

`0002` 与 `0003` 都在用户电脑上，**信任域不同**：runtime 碰得到 key 与结果正文，桌面应用碰不到。
这是它们分开的唯一理由，也是不能合并的理由。

上表其余部分**本轮不开发，沿用现状**，所以不占模块：

| 范围外 | 现在在哪 |
| --- | --- |
| 八个既有 Next.js 前端 | 四个 app 仓各一对：`tpl-`、`info-`、`knowledge-`、`investment-` 的 `*-web-frontend/` 与 `*-admin-frontend/` |
| 官网与下载页 | 上述 `*-web-frontend/` |
| 内部管理后台 | 上述 `*-admin-frontend/`，沿用平台模板 |
| 知识服务 | `info-app` 采集、`knowledge-app` 建库与 MCP；Codex 经通道 ⑤ 直接调它 |

## 通道

| # | 两端 | 协议 | 内容 | 安全要点 |
| --- | --- | --- | --- | --- |
| ① | runtime ⇄ 后端 | WSS，runtime 主动外连 | 派发 Attempt（带签名）、取消、续约、事件与进度、副作用意图与回执、工具级审批结论摘要、用量、厂商预设（带签名）、`escalate` 转交 | 设备私钥认证；协议不设 key 字段、不设本地资料内容与文件名字段 |
| ② | runtime ⇄ Codex | Codex Python SDK（子进程 stdio） | 启动或恢复运行时 thread、下发运行时 turn、事件、审批请求、中断 | 仅本机；Codex 不开端口 |
| ③ | 桌面应用 ⇄ runtime | 渲染进程 → preload → 主进程 → 本机管道（stdio 或仅本用户可访问的本地套接字） | 工具级审批、本地确认、key 与模型配置、工作区授权、本地知识库、结果解密与预览、runtime 状态 | 不开 TCP 端口；只有随应用打包的本地窗口挂这类 preload（它是独立窗口，不与主窗口共用 webContents） |
| ④ | 桌面应用 ⇄ 后端 | HTTPS + 事件流（cursor 续传） | 提交、查询、取消、Task 级审查、结果密文、设备与计费、「有待审查」提醒 | 桌面端 token；每次读取重新授权 |
| ⑤ | Codex ⇄ 知识服务 | HTTPS（MCP） | 检索、领域工具、按需取方法 | 按设备发 token、可吊销、限流 |
| ⑥ | Codex ⇄ 模型厂商 | HTTPS | 推理 | 用户自己的 key，只在本机 |
| ⑦ | 管理后台 ⇄ 后端 | HTTPS | 运营、客服、审计查询 | cookie 会话 + CSRF；内部人员权限；只见元数据 |


用户侧没有网页端，网页与用户电脑之间不存在通道；本机的一切交互都在桌面应用里。

设计上还要落实这几件事：

| 交互 | 设计要点 |
| --- | --- |
| 提交 | 客户端生成幂等键，后端在可靠边界内建单并写首事件（`F-INTAKE-01`、`F-ADMIT-01`） |
| 事件与结果 | 先持久化后通知；客户端按 cursor 续传，重复事件幂等（`F-DELIVERY-02` 至 `F-DELIVERY-05`） |
| 审批与审查 | 工具级只在本机闭环，Task 级经后端 Interaction 原子消费；两条提交逻辑不得共用（`F-APPROVE-*`、`F-REVIEW-*`） |
| 结果 | 执行端本地检查后加密，后端只存密文与元数据，客户端本机解密（`F-CRYPTO-*`） |

谁对哪条要求负责，以合同「责任投影」为准，本文不复制第二份。

## 数据流与信任边界

| 数据 | 流向 |
| --- | --- |
| 用户 key | 只在用户电脑，只发给用户选择的模型厂商 |
| 用户提出的问题（任务文本、归一化目标、已确认的类别） | 明文发到后端，用于受理判定、路由与编排 |
| 用户自己的资料、文件名、Codex 取回的公开资料 | 只在用户电脑上的本地知识库；提交时只给句柄 |
| 文件与研究内容 | 由 Codex 发给用户选择的模型厂商；不上传后端 |
| 自有数据 | 按查询以片段形式下发到用户电脑 |
| 查询内容 | 发到知识服务；日志少记并告知用户 |
| 工具级审批细节（命令原文、改动、路径） | 只在本地窗口展示；后端只收摘要与结论 |
| 研究结果 | 本地检查后加密，后端只存密文与元数据，无法读取 |
| 任务元数据（状态、时间、用量、审计摘要、密文摘要值） | 后端 |


## 工程落点

- 桌面客户端新建，采用 **Electron + Vite + React Router**，是做研究工作的唯一界面；
- 现有网页前端本轮不开发、沿用现状，继续承担官网、下载页与内部管理后台；
- **界面不共享**：网页前端用 Next.js，桌面应用用 Vite + React Router，各按各自技术栈开发。
  两者运行模型不同（SSR 与 hydration／Electron 渲染进程与 preload），强行共享组件会让两边都被对方的约束绑住；
- **接口契约单一真源**：两端调的是同一个后端，接口形状以后端的 OpenAPI / schema 为准，
  两端各自生成客户端，**不手写第二份**——同一事实只能有一个权威写入面；
- 管理后台沿用平台模板的 admin 前端；
- **runtime 独立成仓**；后端的执行端口保持中性（领域概念不进签名），新增经 ① 派往 runtime 的适配器；
- 以上工程决定须符合 [`constraints.md`](../constraints.md)；需要改动其条款时按其修订程序进行。

同层的其他定稿：[`constraints.md`](../constraints.md) 是代码必须遵守的规则，
[`agent-dev-guide.md`](../agent-dev-guide.md) 是开发指导，
[`protocol/`](../../../dev-human/protocol/README.md) 是多方竞争在本平台的做法。

## 共同约束

- 状态机只有一套，场景差异只体现在 Profile 与 workflow（[SDD 规则](../../../dev-human/sdd/finalize.md) P0）；
- 同一事实只有一个权威写入面（P1）；
- 跨进程仍须正确的不变量由持久存储承担，不放在执行进程本地；
- 执行层租用不自建，领域概念不进执行端口的签名。

## 未决

知识服务与八个既有前端何时进入建设范围，未定；进入时按同一把尺子（运行位置、信任域、发布方式）判断要不要单列模块。
