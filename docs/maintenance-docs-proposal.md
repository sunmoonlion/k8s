## 5. 各层文档的职责和内容边界

### 5.0 阅读顺序

维护者先读`docs/README.md`选择任务，再进入责任模块的README，按它的配置和操作入口完成工作。需要理解取舍时读架构；需要判断能否交付时读验收边界。应用维护按“平台→应用概览→后端/Web/Admin组件”逐层定位。

日常手册中，关键任务采用“目的、输入位置、前置条件、预览副作用、执行入口、成功条件、停止条件、恢复办法”八项组织。短组件可合并相近项，不能留下没有实际内容的模板标题。

### 5.1 全局导航：docs/README.md

只回答“我要做什么，从哪里进去”。至少覆盖：查看环境、改配置、部署平台、构建/发布应用、入口切换、证书与密钥、仓库恢复、空间维护、故障定位、已验证/未完成。

每个导航项链接唯一的实际维护手册，并标明功能状态。整套一键安装、整套统一启停和统一空间管理尚未交付时，导航不能将其描述为可用；链接到相应缺项。

### 5.2 稳定架构：architecture.md

保留现有路径，减少上层引用变化。内容包括：宿主机/Harbor/入口/KIND/Flux/应用的责任；原生 Make→Ansible→声明→Flux 顺序；身份和秘密所有权；组件目录与运行命名空间的关系；网络与代理；存储与恢复约束；版本锁职责；本地单机环境的适用边界；云端未验证范围。

删除阶段性承诺和重复版本表。实际版本和摘要指向锁文件，最新已验证状态指向 `verification.md`。

### 5.3 验收边界：verification.md

每条记录字段：能力、证据日期、源码提交或声明来源、实际验证范围、未覆盖范围、证据定位。记录少量能够支持结论的信息，不把完整日志放入 Git。

例如：“2026-10-04，三节点实际应用日志与 kubectl 日志比对通过”可以保留；“目录正确，所以 WSL 重启和删群重建持久化已通过”不可采用。57 个 Ready Pod 等历史数量只在有日期的条目中出现，不作为实时运行承诺。

### 5.4 模块手册

一个模块承载一个维护责任，详细命令只在这个责任模块维护。基础设施 README 解释编排、依赖和操作顺序；组件 README 解释配置字段、账号归属、存储及组件专属故障。

长度较大的恢复或扫描流程拆成同目录专门手册，README 给出清晰入口。其他短模块保持单份说明，避免为每个组件机械建立一套目录。

### 6.2 用户名、密码和端口

- 用户名、数据库名、域名和资源参数在对应 `config.yaml` 中说明。凭据值由现有初始化流程生成并保存在配置指明的 root-only 私有目录及独立备份中，经过 SOPS 加密后进入 GitOps。
- 每个 README 明确“账号名在哪个字段、口令保存在哪个目录、谁消费这个身份、丢失时从哪里恢复”。只记录字段名、文件路径和权限，禁止文档嵌入真实口令或令牌。
- 初始化与轮换分开说明。已有声明后主输入和备份同时丢失，现有代码拒绝重新生成；改变配置中的用户名或编辑秘密文件，不代表服务端账号已经安全轮换。
- 应用API默认8000、前端默认3000、公共TLS入口30443和NodePort/宿主机端口各自标注职责，不能混称“服务端口”。PostgreSQL/Redis等目前配置未开放所有端口或资源字段，手册指向模板实现，不虚构用户开关。
- 现有 SOPS recipient 为公共加密身份；age私钥属于可恢复秘密，不能随着重建集群重新生成。组件TLS私钥、许可证与备份权限同样单独说明。

## 7. 每种操作必须写清副作用

| 操作类别 | 当前代码行为 | 文档处理 |
|---|---|---|
| `plan` | 校验配置、文件或现有环境身份，显示计划；不等于完全脱离环境的纯静态输出 | 各模块列出所需已有输入及读取对象 |
| `render` | 可能建立私有输入/备份、生成证书、准备数据目录/模型、写候选；ELK还涉及宿主机sysctl | 明确属于准备操作，有文件或宿主机变化 |
| `stage` | 更新工作树声明；应用stage先render；Knowledge provider准备可创建远端dataset | 不称作只读预览；写清API状态变化和失败恢复边界 |
| 发布镜像/声明 | 向Harbor写内容，校验独立puller摘要；声明发布生成候选来源 | 发布候选与晋级分开；不能声称发布就立即部署 |
| `bootstrap` | 编排已提交、已晋级的声明及检查 | 解释不自动批准工作树中的新配置；维护失败按阶段止损 |
| `check` | 可能创建临时Pod、队列、对象版本、图节点、dataset或应用记录，并按本次身份清理 | 标明写入与删除探针的范围；清理失败保留身份记录定位 |
| `start/stop` | Harbor和入口已有模块入口；整个集群/平台全链路启停尚缺统一入口 | 按实际功能说明，不把多个手工步骤描述为已交付一键启停 |
| 修改`enabled` | 影响声明/材料选择；不能概括为立即停止现有工作负载 | 区分停止、暂停同步、删除声明和删除数据；读实际Flux语义 |
| 删除Completed Job/Pod | 声明仍由Flux持有时可能被重新建立 | 初始化代次的维护另说明；不提供通配删除命令 |

## 8. 日常维护入口如何组织

所有示例统一从 `k8s` 工作树根目录执行 `make -C infrastructure ...`；模块内不再使用含糊的“先到某处”约定。保留 `SITE`、`APP`、`COMPONENT` 等现有参数，所有应用示例显式传 `APP`。

以下是现有入口的归属，供编写手册时对照；今晚不执行这些命令。

| 维护任务 | 现有入口 | 详情归属 |
|---|---|---|
| 看配置/主机挂载/物料身份 | `config`、`preflight`、`images`、`check-images` | 根README、host、artifacts |
| 物料准备/离线校验 | `plan-artifacts`、`fetch-artifacts`、`check-artifacts` | artifacts |
| Harbor安装启停/身份 | `registry-plan/deploy/start/stop/status`、`registry-accounts` | registry |
| 真实镜像推拉/扫描/隔离恢复 | `registry-publish-check`、`registry-scan-check`、`registry-recovery-plan/check` | registry及两份专门手册 |
| TLS入口管理 | `entry-plan/preview/deploy/start/stop/status` | entry |
| KIND建群、身份、私有镜像拉取 | `cluster-plan/deploy/status`、`cluster-pull-check` | cluster |
| Flux及秘密基础 | `flux-bootstrap/status/release/source-apply/source-status`、`secrets-*`、`foundations-*` | flux、secrets、foundations |
| 平台变更与部署 | `services-render/stage/validate-release/bootstrap/check` | services；参数在各组件 |
| 应用在线构建和发布 | `application-source-plan`、`application-build-backend/web/admin`、对应publish | applications |
| 应用声明与验收 | `application-deployment-plan/render/stage/validate-release/bootstrap/check/check-public` | applications和各应用 |

表中斜杠写法用于概括同组 Make target。实际操作卡必须展开为可复制的真实单个 target；例如 `make -C infrastructure application-check-public APP=info`，而不是复制 `application-check/check-public`。

### 8.1 常见修改的操作路线

1. **改应用副本/资源**：应用所属组件配置→deployment-plan→render候选→审阅差异→stage并提交→发布声明候选→显式晋级→bootstrap→check。指出render/stage有副作用，服务不会因仅编辑配置自动变更。
2. **改Web/Admin域名**：前端origin和公共身份关联→证书覆盖/回调地址/Ingress生成→声明部署验收→入口候选检查→维护切换→public check。注明会同时涉及身份和证书，不能只改一处HAProxy。
3. **构建网络失败**：默认国内直连→仅依赖下载类失败进入一次官方源+代理尝试→检测现有代理→成功则继续，代理不可用则退出→启用代理后重新运行。编译、摘要、证书、授权错误独立处理，禁止用切源掩盖。
4. **初始化失败**：对照Job代次、私有输入、依赖Ready和schema→修复输入或正确代次→重新生成声明→审阅/晋级。不得为了让Job“绿了”删库重建或用管理员代替运行账号。
5. **空间不足**：先看实际占用和峰值预算→对照保留资产→给出删除预览与批准范围。当前缺统一容量/GC/轮换入口，先标为缺项，不写自动执行不存在的命令。

## 10. 备份、恢复、持久化和空间管理的写法

### 10.1 备份对象

维护手册区分：Harbor全量目录/配置/加密密钥/数据库；各业务数据库；对象原文和版本；初始化身份/age私钥/TLS/许可证；可重建的模型、镜像物料、派生索引与日志。分类不等于批准删除任何资产。

同盘备份用于误删和升级失败恢复。数据VHDX和WSL系统VHDX同在C盘所在物理硬盘，不能防该硬盘损坏。机器外备份落点仍待确定；手册保留接口和待办，不写已实现异地备份。

### 10.2 已有与未有

已有仓库隔离恢复演练入口，需显式`BACKUP`及`BACKUP_SHA256`；其代码要求同版本、完整结构、文件与链接边界，候选服务隔离于生产入口。维护手册须解释输入来自哪里、包含哪些数据、空间峰值及如何检查隔离。

业务数据库/对象存储/Neo4j/MongoDB等没有完整统一备份轮换恢复交付，不能把私有凭据副本当作完整业务备份。完整Harbor重启/删群重建持久化验收也不能由卷挂载检查替代。

### 10.3 删除与自动化

已批准的Harbor容器日志轮转为每份20MiB、最多3份，以实际override模板为准。其他组件的日志/磁盘占用需要分别列出现有配置与缺项。

Harbor保留策略与GC、构建缓存回收、备份轮换和日志索引保留属于不同删除对象。统一查看/预览/执行入口尚待交付。删除方案必须保护在用镜像、回退版本、必要备份，并由所有者确认策略；今晚不启用任何新增定时删除。

禁止给出`docker system prune`、`docker volume prune`、`docker container prune`作为一般维护办法。旧kind节点/卷和新正式资产的保留约定继续有效。Windows系统盘压缩另有维护窗口要求，不能并入普通“清缓存”命令。
