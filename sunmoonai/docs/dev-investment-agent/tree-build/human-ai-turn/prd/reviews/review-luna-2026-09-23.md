# 产品定位重构评审意见（Luna，2026-09-23）

评审对象：`repositioning-discussion-2026-09-23.md`。本文基于该文及其附录，不把文中标为“事实”的源码现状视为已经独立复核；以下是产品与架构判断、待验证假设及建议，不是新的项目决定，也未修改正式 PRD、SDD 或代码。

**我的总体意见：支持从问题分类转向按需委托，支持把专业方法作为长期投入方向。眼下最需要补齐的是一个可验证的服务承诺：为谁、把哪一种工作做到什么程度、由谁验证、花费多少。两层决策权说明了协作方式，还不足以证明商业价值。**

Claude 提出的验证、收窄场景、计算总费用的方向值得采纳；但“方法没有壁垒”“同一实例必然要求桌面壳”“人肉不赢则自动化也不赢”“预算和副作用账可以晚做”都推得过远。此外，全量估算 56–94 人周与第一阶段 2–3 人、6–8 周可能对应不同范围，不能仅凭这两个数字判定估算矛盾。

**1. 两层决策权成立，但需把委托关系和购买关系分开。**

它比“通用/专业”好在：是否交出执行策略由用户决定，同一个问题也可以先自做、再委托、再收回，不需要分类器替用户决定服务级别。

不过，用户、顾问和执行体之间不是简单换驾驶员。用户始终保留目标、授权、预算和终止权；顾问获得限定范围内的策略权；执行体在策略范围内仍有实现选择。应按这些维度定义授权，避免“交出驾驶权”被理解成整台电脑或整个会话的控制权。

两层交互也不等于三层客户。“数据、专家包、机构能力”更像三个可组合的产品维度；同一个机构也可能只买数据，同一个个人也可能买委托服务。现有分层可以用于组织产品，但不宜直接拿来代替客户画像。

尤其要分清“第一层不建云端委托单”和“不经过云端”：第一层购买并调用 MCP 数据，依然会发生云端请求、鉴权和计量。建议正式表述为“日常对话不进入云端编排；数据调用按需访问云端；只有显式委托才建立顾问任务”。

也不宜把委托限定为“不满意后的补救”。用户可能为了节省时间，在任务开始前就愿意购买规范执行或独立复核。入口应允许直接委托、对已有结果复核、对卡住的步骤求助；第一期只需选择其中一个做实。

**2. 方法可以是长期主体，但应把“方法资产”定义为经过验证的专业生产过程。**

我同意 Claude 说目前没有证据证明方法能产生收费价值，不同意据此把方法本身排在数据与合规之后。文档同样没有证明数据独占性、机构留存或付费需求；三个来源都要验证。

一份流程文本容易复制，但完整的方法还包括：适用范围、关键输入、口径转换、失败识别、验收标准、例外处理，以及持续积累的真实任务评测。可能形成优势的是这些东西结合起来后的稳定效果。模型变强会淘汰补模型短板的步骤，也可能让同一套专业质量标准覆盖更多任务，不能预先推出方法必然贬值。

建议专家包至少能回答六个问题：解决什么、需要什么、不解决什么、何时算完成、何时应拒绝或交回、效果和成本如何。版本应绑定数据口径、方法与验收规则、兼容范围和评测结果。生产中出现的失败进入回归案例，另留未见过的评测任务，避免只优化已有题库。

按步下发可以提高复制成本，但不能替代价值验证。用户反复购买应当是因为完成质量与维护服务，而不是因为没能拼出完整提示词。

**3. 同一实例值得保留为当前约束，但先说清“同一”的含义。**

同一进程、同一会话历史、同一工作区、同一模型账户，是四个不同要求。用户真正需要的通常是不用重复解释、资料仍在原处、结果能继续使用，以及能够随时收回控制。应当先写清所有者要求的是哪些连续性，再判断实现代价。

Claude 指出的迁移摩擦是合理风险，但“用户一定不换工具”和“必须有桌面壳”都还没有得到证明。同一执行实例与独立桌面界面之间没有逻辑上的必然关系。

建议先做一条可演示的交接链：保留正在研究的工作区与必要上下文，暂停用户侧新执行，明确授权顾问，在原执行环境完成一个受限步骤，再归还控制。这里提出的是验收目标，不代表任何现有引擎接口已经支持；接口能力需单独做技术核验。

该链必须验证旧指令、在途工具调用与旧授权不会在交接后继续生效。用户和顾问不能同时改同一份产物；取消后也不能由迟到回包把任务重新推进。控制权轮次与交接回执，比“继续显示在同一个聊天窗口”更关键。

第一期可以只支持一个执行引擎，不必同时开发多个适配器。交接契约则可独立于引擎。若后续发现必须转交会话，应明确这是需要重新决策的退路，不能把它包装成已满足“同一实例”。

**4. 展示 token 费用不够，必须让顾问受到可执行的预算约束。**

如果产品控制重试、分支和验收次数，仅披露预估金额不能解决激励问题。建议按整个委托设预算，涵盖执行、验收、返工和工具费用；默认限制返工次数，不默认开启竞争执行；预算增加由用户明确批准。按次或订阅收费都应避免让顾问收入直接随着无效步骤增加。

用户应看到顾问费、预计模型费及其不确定范围、目前已用额度和继续执行的原因。无法取得及时精确账单时，只能承诺调用次数、输出额度、并发数等可执行限制，并采用保守估算；不能把估算上限说成供应商账单的绝对硬上限。

因此，我反对在真实付费委托里把预算放到以后。可以先做很简单的预算机制，但从第一次自动追加模型调用开始就要有停止条件。是否给失败服务退款或额度补偿可以另行试验，不宜在没有数据时先做成本兜底承诺。

**5. 先人肉验证可行，但五到十个任务只能用于发现问题。**

两周、两三个分析师足以检验流程是否能跑、评价标准是否清楚、是否出现有感知的改善；不足以证明普遍优越性、收入规模或长期留存。同一分析师的多个任务也不能当成相互独立的客户样本。

更大的实验漏洞是把更好的数据、更长的推理时间和专家现场发挥，全都算成“编排的价值”。建议至少分三组：

| 组别 | 条件 | 要回答的问题 |
| --- | --- | --- |
| A | 用户现有工具和数据，按通常方式做 | 新产品相对真实工作方式是否有价值 |
| B | 相同执行模型，加我们的数据，不加顾问流程 | 数据服务贡献多少 |
| C | 与 B 相同的数据和模型，加顾问流程 | 方法是否产生额外价值 |

先用少量任务打磨方法，再冻结版本用于未参与打磨的任务。B、C 对比控制预算或同时报告不同预算下的质量，记录提示、人工干预、失败和拒绝；评分人尽量不知道来源。除引用完整度、数值与口径错误外，要记录用户把结果改到可用所花的时间、总费用与耗时。拒绝率和任务覆盖率也要展示，避免只看成功样本。

人肉顾问知道完整资料，而未来云端看不到正文，会造成特别严重的实验偏差。应限制顾问只能接触未来产品允许看到的输入；若做不到，明确标为人工服务上限实验，不能据此证明目标架构可行。

付费验证要超过“愿不愿意买”的口头询问：给出具体服务和价格，观察是否愿意实际购买、在下一个真实任务再次使用。具体价格和验收门槛应在看结果之前确定。

“人肉不赢，自动化也不赢”不成立：自动化可能降低等待、人工成本和执行波动。反过来，人肉赢也不能说明可自动化。实验需要分别识别专业判断贡献与可复制流程贡献。

**6. 首个场景建议选“自选公司新财报的变化核对底稿”。**

范围收窄为：针对用户已关注的一家公司，将新披露报告与可比前期报告按一组固定指标核对，输出数值变化、口径变化、原文出处和待核实问题。先限定一种报告类型和一套可比口径，不做整个市场的泛化财报解读。

这个选择是待验证的产品假设。它便于形成明确交付物，数据层和方法层也能使用同一批任务验证。比起开放式“公告解读”，其字段、来源、单位、期间与计算更容易逐项核验。初期异常提示应呈现为需要核实的差异，不把任何差异直接写成问题结论。

它的弱点是单公司披露频率有限。应面向持续跟踪一组公司的研究者验证组合层面的使用频次，不能把财报季的集中需求外推成全年高频。没有相应历史数据、引用定位或版本支持时，先缩小承诺，不能靠生成内容补缺口。

**7. 专家的分类应拆成“能力从何而来”与“判断在哪里发生”。**

真人写包、规则编排、本地模型推理、云端模型推理，可以组合，不是互斥的三种产品。支持先做专家编制并验证的能力包，但一个包不是“写完即可出售”的文档，还需要维护人、适用范围和效果记录。

B 类云端 agent 可以保留为未来的技术选项：例如只处理公开数据、辅助规划、复核允许共享的结构化结果。不过它会改变“后端不调用生成式模型”的现行约束，并引入供应商、数据访问和成本承担的新决定；没有证据前不必纳入第一期。

“真人只是写包的人”不能作为 D17 已解决的依据。评审文档里的“合规守得住”等表达应降为待核验假设；以拟交付的真实样例、销售承诺和数据流另行评审。这不是本文能够代替的法律结论。

**8. 架构表需要区分“保留责任”和“本期实现”。**

九站可以继续用作完整委托的检查框架，但九种责任不意味着必须对应九个模块、九次网络往返或每次都人工审批。一个简单请求也能在一个调用里承担多项责任。

| 场景 | 本期应具备的能力 | 可推迟的能力 |
| --- | --- | --- |
| 仅销售数据服务 | 鉴权、权益与用量计量、来源与版本、查询质量、必要的隐私保护 | 顾问派发、长任务租约、竞争执行、结果跨设备取回 |
| 人工验证委托 | 明确任务范围、固定输入版本、记录成本与交付结果 | 完整自动化控制面 |
| 自动委托试点 | 最小持久任务账、幂等、授权与取消、预算、断线恢复规则、产物绑定与验收回执 | 多设备调度、冗余竞争、复杂编排平台 |

第一期只卖数据，不应以顾问终局架构作为上线前置条件。但一旦自动控制用户机器，就不能泛称“可靠性机制先不做”：单设备也会断线、重试、重启和重复执行。可以限制为单个活动委托、无并行、无外部写操作，缩小机制范围；若仍有远端派发与本地执行竞争，必须有拒绝过期指令的机制。实现形式可以简化，安全性质不能靠“第一期”省掉。

副作用账也应按能力决定：首版完全只读，就不需要预建全部写操作账；若允许写用户工作区或对外操作，相应幂等、授权和回执必须同时具备。正文在本机生成并不等于已可靠交付，还需明确本地持久化、丢失与重启恢复的承诺。

D11 的旧类别判断可以退出，但委托请求的受理、输入充分性和能力匹配仍存在。D12 的“通用/专业分类”可以退出，workflow 清单与专家能力边界仍必须定义。因此不建议把 D11、D12 整项直接标成消失。

**9. 不赞成默认上传本机摘要。**

问题本身也可能含保密信息，摘要更可能保留持仓、研究意图、未公开数字和来源片段。“经过摘要”既不等于脱敏，也不等于允许上传；它还可能把错误判断压缩成无来源的既定事实，污染顾问后续策略。

建议区分完整的本地交接包与明确的外发包。默认外发内容限于用户为求助确认提交的任务描述和必要参数，不自动附带本机会话。需要补充时，本机生成待发送内容，让用户看见实际文本、接收方和用途；资料片段另行选择。问题、摘要、资料三级可以作为界面简化，但权限最终应落到具体内容和目的。

原 I20 禁止资料、文件名和本地知识库内容上传；新方案若允许任何这些内容，应明确修订不变量和产品承诺。不能同时宣称“绝不经过我们”与“默认上传摘要”。本地运行也不意味着不出本机，文中已经说明模型厂商仍可能收到资料。

U1 不必二选一。建议按次批准一个有边界的服务契约，允许范围内的只读步骤自动执行；扩大数据外发范围、增加预算、产生外部副作用或改变目标时再次请求授权。这样既能委托，也能保住用户控制。

**10. 第一层可能有收入，但“所有人买数据”不能作为收入假设。**

数据不独占并不直接否定价值。需要验证的是用户是否愿意为可检索、可比、可追溯、及时更新且便于执行体使用的数据付费，以及这些能力相对于其当前获取方式节省了多少工作。MCP 是交付方式，本身不能证明购买理由。

建议第一层也聚焦到第 6 项的同一批研究者，给出明确覆盖清单和交付质量，而不是先做泛数据平台。先盘点实际可提供的数据、使用权、历史跨度、版本修订与出处定位，再承诺服务。

收入实验应同时记数据获取与维护成本、清洗纠错、计算、客服、获客和用户设置成本。用户自己付模型费并没有消除这些成本。观察按具体价格购买、重复使用与续费的行为，再决定订阅或按量组合。

第一层收费验证与第二层方法验证可以并行，但判据应分开：有人买数据，不代表愿意交出流程控制权；方法有提升，也不代表数据订阅能覆盖经营成本。

**11. turn 机制变轻是对的，但不要把 Git 操作解释成审批事实。**

“有未提交改动 = AI 答完待审”“已提交 = 定稿”“目录删了 = 结束”都不可靠：人也会修改草稿，AI 也会提交，目录也可能只是归档。Git 保存版本和变更，不自动证明谁批准了什么。

建议保留“普通交互不用留痕”，只在正式采纳或修改重要结论时，留下与具体版本绑定的审阅结论及理由。可以用已有 PR 审核、提交说明或简短的决策说明，不必重新造一套每轮回执。AI 先提交、人工后提交有助于分开差异，但如果人没有修改，也需要能表示“已审并接受”。

四条补充规则中，我建议调整两条：其一，“追问永远追加”会重新长成无限对话日志，可允许 user-message 保持当前问题，但生效的约束、反对意见与决策依据要进入正式产物或版本记录；其二，“提交后才删目录”不是充分条件，关键是有用结论与审阅依据已有可追溯去处，临时目录才可删除。

提交哈希可以绑定不可变候选，但“内容寻址即幂等”不成立：同一提交仍可能被触发执行两次，外部写入仍要幂等键。合并也只说明变更被纳入，只有明确规定审核流程时才代表业务采纳。Git 与任务账分工的方向正确，理由应改成各自适用的事实和并发约束。

**12. 最大的盲区：云端顾问不看正文，却被要求证明正文做对了。**

当前讨论默认“顾问拥有更强验收能力”，同时又保留“后端不调用生成式模型、看不到资料与正文、只收元数据和密文”。格式是否齐全、步骤是否结束，与论证是否充分、比较口径是否正确、证据是否支持结论，是不同层次的判断。后者不能仅凭执行体自报通过来成立。

需要尽早拿一个实际场景跑通以下闭环：

1. 哪些项目可以确定性检查，例如期间、单位、计算、来源定位和字段完整性；检查在哪里运行。
2. 哪些项目需要读取正文并做语义判断；是否由受限的本地校验步骤完成，费用如何纳入预算。
3. 云端能收到哪些回执；回执如何绑定任务、产物和验收规则版本，又能证明到什么程度。
4. 哪些结果只能标为“形式检查通过”或“仍需人工核实”，不能对用户宣称研究已经正确。

签名和哈希能够帮助确认回执来源与版本，不能证明分析本身正确。用户设备不可信时，本地回执还存在真实性边界。原版不看正文的云端要接受这一能力上限，或明确提出另一种数据授权方案，不能把矛盾藏在“验收”这个词里。

另一个相关盲区是：数据质量评测、方法包发布评测、单次结果验收，是三道不同的门。发布前平均表现较好，不代表当前这次交付合格。用户若本就缺乏专业能力，也未必能发现问题并主动求助；所以产品需要展示证据、未知项与完成范围，不能把质量控制寄托在“不满意再升级”上。

**建议下一轮讨论形成的最小成果。**

先写一页可对外解释的服务定义：具体客户、一个场景、输入、交付物、质量边界、收费试验与预算；同时明确第一期销售数据，顾问能力处于何种验证阶段。随后准备少量真实任务，分离数据价值与方法价值进行比较，并演示“同一执行环境交接 + 本地验收 + 云端可知范围”。

这三件事能分别回答“有人买吗”“方法有额外价值吗”“在约定信任边界内做得到吗”。据此选择要自动化的九站环节、修订冲突的约束，再安排工程范围。我支持保留完整框架作为方向，但不把所有机制是否建齐当成第一期产品是否成立的判断标准。
