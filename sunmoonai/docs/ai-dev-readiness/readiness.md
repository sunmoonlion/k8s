## 0. 为什么值得单独立项

要建的东西是：一个全栈 agent 平台，包含专业财务分析。要用的方式是：**开发工作全部由
AI 助手承担**。

这两件事叠在一起，改变的不是"开发速度"，而是**错误的形状**：

| | 人类开发者 | AI 助手 |
| --- | --- | --- |
| 不懂时 | 会卡住、会问 | **会流畅地编**，语气与正确时无异 |
| 记纪律 | 会忘，但忘了心里有数 | 每次冷启动，纪律不在上下文里就等于不存在 |
| 产出速度 | 受限于打字 | 一夜可产出几千行自洽的散文 |
| 交叉检查 | 同事读得出味道不对 | 评审方也是 AI，可能被同一种"看起来对"骗过 |

结论是一句话：**AI 会 100% 声称满足一条无法被证伪的规则。**
所以准备工作的主线不是"把规矩写清楚"——那件事本仓已经做得比多数项目好——
而是**把规矩变成会自己报错的东西**。

本仓已经在 [`constraints.md`](../dev-plan/constraints.md) 的「保证这些被遵守的三层」里
把这个道理写死了：

> **只有第一层不依赖人。**后两层是纪律，纪律会被忘——这份文件本身就出过两次
> "规则在眼前却没回头对照"。

**本立项就是把那句话贯彻到底。** 下面的议题全部是它的展开。

## 1. 现状盘点

### 1.1 已经做对的三件事（是资产，要沿用，不要重造）

| 资产 | 位置 | 为什么它是对的 |
| --- | --- | --- |
| 三层理论 | [`constraints.md`](../dev-plan/constraints.md)「保证这些被遵守的三层」 | 明确区分"随测试自动跑 / 随提交自动跑 / 纪律"，并断言只有第一层不依赖人 |
| 文档门禁 | [`doc-gate.py`](../dev-plan/doc-gate.py) + 版本化 `.githooks/pre-commit` | 两条设计约束正面避开了前两个被删脚本的坑：**不靠人记得跑**、**结论不取决于工作区状态**（对照 git 索引而非文件系统） |
| 休眠能力登记表 | `investment-backend/app/tests/test_dormant_capabilities.py` | 每条判据**两个方向都能失败**：`anchor_exists`（锚点还在吗）+ `still_dormant`（还休眠着吗）。文件头点破本项目反复踩的坑：**把"没找到"当成"不存在"** |

这三件事的共同形状值得单独提炼，因为后面每个议题都要用它：

> **一个检查如果只能证明"没找到问题"，它就不是检查。**
> 它必须同时能证明"我还找得到我要查的东西"。

`doc-gate.py` 用 git 索引解析链接是这个形状，`anchor_exists` 是这个形状，
"先清零再扩范围"也是这个形状（否则门禁上线当天就被 `--no-verify` 掉，退回纪律层）。

### 1.2 三个可量化的缺口

**缺口一：规则大多还在纪律层。**

```bash
cd sunmoonai/docs/dev-plan
grep -cE "^\| [ACDITR][0-9]+ \|" constraints.md          # 40 条规则
# 「谁在执行」列的分布：22 条是「⚠ 自检」
```

40 条规则中 **22 条的「谁在执行」是 ⚠ 自检**，即纯纪律层。按本仓自己的三层理论，
这 22 条对一个冷启动的 AI 助手**约等于不存在**。

**缺口二：产品契约的编号一个都没进测试。**

[`request-lifecycle.md`](../dev-plan/working/request-lifecycle.md) 定义了
15 条不变量 I1–I15、22 条验收 AT-01…AT-22、10 条功能项 F-EXEC-01…08 / F-INTERACT-01…02，
共 **47 个编号**。

```bash
cd investment-app/investment-backend/app
grep -rlnE "I1[0-5]|AT-[0-9]{2}" tests/     # 零命中
```

**没有任何一个测试按编号认领任何一条。** `tests/test_kernel_invariants.py` 确实在测
架构不变量（接口分面、依赖方向、迁移链单调），但它测的是另一套东西，且不带编号锚定。

后果很具体：AI 助手交付时说"满足 AT-07"，**没有任何机器能反驳它**。
refact 轮 §3 那次失败整合栽的正是这个——自编一套 8 条不变量与 I1–I15 并存，
还漏了 I12/I13/I15，而当时没有任何东西会因此变红。

**缺口三：回路在新工作区里跑不起来。**

2026-09-04 实测：`~/worktrees/opus` 下 `python -m pytest` → `No module named pytest`。
依赖声明是齐的（`app/pyproject.toml` 的 `[dependency-groups].dev` 有 pytest /
pytest-asyncio / pyright / ruff，且配了清华源），`uv` 也装了，但**每个新 worktree
需要先 `uv sync`，而这件事没写在任何一个助手会先读到的地方**。

仓内也没有 CI（无 `.github`，Jenkins 在平台侧，⚠ 未核它是否跑本仓测试）。

**每个新 worktree = 一个冷启动的 AI 助手。** 它如果不能在半分钟内跑通测试，
它就会开始猜；而它猜出来的东西和真的长得一样。**39 个测试文件对一个跑不动它们的
助手价值为零。**

### 1.3 一个已经埋下的坑：编号撞车

`I3` 在本仓有两个互不相干的含义：

| 出处 | I3 是什么 |
| --- | --- |
| [`constraints.md`](../dev-plan/constraints.md)（`:88`） | 浏览器身份与服务身份互不通用；凭据禁止复用 |
| [`request-lifecycle.md`](../dev-plan/working/request-lifecycle.md)（`:450`） | 每次读取、工具调用和写入重新校验当前授权 |

`I1`–`I8` 两边都有。人读上下文能分清，**AI 跨文档检索时会混**——而且混了以后
产出的文字仍然通顺。这条在议题六处理。

## 2. 议题

### 议题一 · 把判据从纪律层搬到测试层

**事实**：40 条规则 22 条 ⚠ 自检；47 个契约编号 0 个进测试（§1.2）。

**候选做法**：建一张 `编号 → 测试标识` 的映射，并让**映射表本身是个测试**——
表里点名的测试不存在就红。这样它同时具备 `anchor_exists` 与 `still_dormant` 两个方向。

分三类落地，不追求一次全覆盖：

| 类 | 处理 | 例 |
| --- | --- | --- |
| 可机械判定 | 写测试，认领编号 | 终态不可转出、迁移链单调、四本账写入必经某个出口 |
| 可判定但需环境 | 写成集成测试，标注前置 | 跨进程 checkpoint 恢复、预算耗尽转 `budget_exceeded` |
| 当前不可判定 | **显式标 ⚠ 并写明为什么** | 依赖尚不存在的业务数据的那些 |

第三类**必须显式列出**，否则"没测到"会被读成"测过了"——就是 1.1 那条形状。

**待决**：
- 映射表放哪？（候选：契约文档内加一列 / 单独一份 `invariant-map.md` / 直接落在测试代码里）
- 覆盖率要不要设门槛，还是只要求"每条都有明确归类"？
- 22 条 ⚠ 自检的规则里，哪些是**真的做不成**，哪些只是还没做？（需要逐条过一遍）

### 议题二 · 一条命令的回路

**事实**：见 §1.2 缺口三。

**候选做法**：
1. 一个 `make check`（或 `uv run` 脚本）把 `ruff` + `pyright` + `pytest` 串起来，退出码可信；
2. 把它写进**助手会自动读到的位置**的前十行——各仓根 `AGENTS.md` 与组件 `CLAUDE.md`
   （按 `constraints.md` 三层表，这两处是"进目录自动注入"的）；
3. 新 worktree 的 `uv sync` 要么写进同一处，要么做成幂等的引导脚本。

**为什么排在议题一前面执行**：判据写得再好，助手跑不动就等于没写。
这是本立项**投入最小、解锁最多**的一条。

**待决**：
- 要不要上 CI？本仓在 gitee，⚠ 未核 Jenkins 是否可挂本仓测试。
  没有 CI 的话，`pre-commit` 就是唯一防线——那要不要把 `pytest` 也挂进 `.githooks`？
  （代价：提交变慢；收益：跟 `doc-gate` 一样不依赖人记得跑）

### 议题三 · 金标准与数据源

**事实**：13 张表全是运行时基础设施，**业务数据 0 张表**：

```bash
grep -rn "create_table(" investment-backend/app/alembic/versions/ | wc -l   # 13
```

逐张点名：`agent_sessions`、`agent_runs`、`session_events`、`tool_side_effects`、
`checkpoints`、`checkpoint_blobs`、`checkpoint_writes`、`checkpoint_migrations`、
`auth_user`、`agent_pilot_requests`、`agent_pilot_controls`、`outbox_message`、
`inbox_message`。没有标的、行情、财报、基本面、持仓、研报。

`tests/golden/` 下只有三份 graph 快照，**没有一条财务金标准**。

**为什么这是 AI 开发的前置而不只是产品的前置**：财务分析的对错**不能靠读起来对不对
判断**。没有带来源、带期望的金标准，AI 写出来的分析器**无法被证伪**，
评审就退化成文风比拼——而评审方也是 AI。

**候选做法**：先建最小可用的数据源 + 一小批金标准（数量待定），再谈任何 Profile 设计。

**待决**：
- 数据从哪来（自采 / 采购 / 现有 mcp-huachuang 之类的通道）？
- 金标准由谁出题、谁定答案？**这件事 AI 不能自己给自己出题**——
  出题方和答题方是同一个模型时，金标准就不再是独立信号。
- 首批覆盖哪几类分析？

### 议题四 · 把纪律编译成错误

**事实（最硬的一个例子）**：Codex Python SDK 的
`sdk/python/src/openai_codex/client.py:773-779` 默认审批处理器对
`item/commandExecution/requestApproval` 和 `item/fileChange/requestApproval`
一律返回 `{"decision": "accept"}`；而 `:221` 那行
`self._approval_handler = approval_handler or self._default_approval_handler`
让这个兜底**发生在构造函数里，没有任何告警**。

于是：**"忘了传 handler"和"故意选自动批准"在代码里长得一模一样。**

**候选做法**（一条通用规则，不止用于这一处）：

> 凡是「忘了做」与「故意做」在代码里无法区分的地方，
> 都要改成**必须显式传参**、类型不通过、或有测试专门盯着。

同类已知位点：
- `AgentProfile` 现在是**审计字段，不是约束**——`effective_config` 到不了图里，
  两条生产图对 `allowed_tools` / `denied_tools` / `model_key` / `system_prompt_id` /
  `memory_policy` 的引用数均为 0（`tests/test_dormant_capabilities.py:240` 已登记）。
  意味着助手可以提交一个"支持 allowed_tools"的改动，**而没有机制能发现它没接线**。
- ⚠ 其余位点尚未系统排查，属本议题的第一项工作。

**待决**：这条要不要直接进 [`constraints.md`](../dev-plan/constraints.md) 成为新规则？
若进，归到哪个系列（看起来最接近 T 系列）？

### 议题五 · 任务粒度与交接判据

**事实**：AI 在"有明确契约和测试的窄单元"上接近熟练工程师；
在"跨五个文件的架构演进"上会编造，且编得通顺。

本仓已有一条形状正确的判据，在
[`development-lifecycle-agent.md`](../dev-plan/archive/development-lifecycle-agent.md) §5.5：

> 把当前会话杀掉，另一个执行者只读持久载体能否接着做？

**候选做法**：把它从"checkpoint 的判据"提升为**派工的准入条件**——
一个工作单元如果通不过这句话，说明它**还没被拆到可以交给 AI 的粒度**，
不是助手的问题。

**待决**：
- 谁负责拆？拆的动作本身要不要也由 AI 做、由人验？
- 单元的上限怎么定（改动文件数 / 是否跨层 / 是否引入新依赖）？

### 议题六 · 取证纪律与锚点腐烂

**事实**：本仓已经在用 `file:line` 锚点，效果实在。但 2026-09-04 一次复核就在
refact 轮任务书「已经查实、不必重新论证的事实」一节 抓到三处措辞漂移（其中一处
「引用数为 0」实为 2 处，`grep` 一次就能推翻）。**人写的文档尚且如此，AI 生成的漂移更快。**

**候选做法**：
1. 凡以 `grep` 计数为证据的断言，**必须同时给锚点存在性判据**——
   否则改个名字，证据就"假性通过"（`test_dormant_capabilities.py` 文件头点的正是这个坑）；
2. 编号撞车（§1.3 的 `I3`）：要么给两套编号加前缀区分，
   要么在两份文档头部各写一行交叉提示。**前者机器可查，后者只是纪律**——
   按本文主线应选前者，但改编号会波及大量既有引用，代价要评估。

**待决**：
- 编号改前缀的代价有多大？（需要先统计 `I1`–`I8` 在五仓的引用点）
- 锚点检查能不能并进 `doc-gate.py`？（它现在只查链接 / §引用 / 表格三件事，
  且明确"做不成的不硬做"——`file:line` 锚点跨仓，正是被删脚本的失败点，⚠ 需谨慎）

### 议题七 · 并行隔离流程的适用边界

**事实**：四家并行提案 + 互评 + 异议轮 + 独立验收，见
[`round-protocol.md`](../dev-plan/protocol/round-protocol.md)。这套流程确实有效——
现行的 lifecycle 基座就是它的产物，而 2026-09-03 那次**角色不分**的整合失败
（整合方即参赛方、无异议轮、无独立验收）反证了流程的每一环都在起作用。

但成本是 4–5 倍，且提案期各家互不可见会产生大量重复推导。

**候选做法**：按**可逆性**分流——

| 决策类型 | 流程 |
| --- | --- |
| 不可逆（选执行器、定契约、定门禁、改编号体系） | 走完整并行轮 |
| 可逆（日常实现、修 bug、加测试） | 单线开发 + 一次独立评审 |

**待决**：边界线画在哪？"可逆"的判据是什么——能不能也写成机器可判的？

## 4. 明确不做的

**不再增加散文文档。**

本仓文档层已经过量（`sunmoonai/docs/` 下 117 份已纳入门禁）。而 2026-09-03 那次失败
整合的产物形状很典型：1100 行、自洽、自编一套不变量与 I1–I15 并存、
锚点 ID 出现 0 次。**散文喂 AI 会放大而不是约束它**——文档越多，
它越容易在里面找到支持自己的段落。

本文自己也受这条约束：**它的产出应当是一批会报错的东西，不是它的续集。**

## 7. 难度地图（2026-09-04 修正）

**触发**：2026-09-04 用四家助手实跑了一整轮并行评优（refact 轮），
并在过程中从零建出 `round-protocol.md` 的完整流程。跑完之后，
本文原来的难度判断站不住了。

### 7.1 原判错在哪

本文（尤其 §3）隐含一个排序：**先把开发的判据与回路建好，再谈组织多个 AI 协作**——
把"协作组织"当成后面的、附带的事。

**这个顺序反了。**真实难度是：

| | 性质 | 状态 |
| --- | --- | --- |
| **怎么组织一群不确定的执行体** | **设计难**——没有现成答案，买不到、抄不来，失败模式隐蔽 | **✅ 已跑通** |
| 怎么判断执行体做得对不对 | **工程难**——方法已知（建评测集、定金标准、量化），费钱费时但路清楚 | ⬜ 未做 |

"设计难"不是形容词。本仓踩过的四条——整合方即参赛方、中途降档、逾期无判据、
裁量无留痕——每一条都是想不到就必然踩、踩了还不自知的那种。
而它们现在都有了成文的机制，且是在真实一轮里被逮出来的，不是想象的。

### 7.2 新判：三层，不是两层

| 层 | 结论 | 依据 |
| --- | --- | --- |
| **控制面（怎么组织）** | **可以定稿** | 实跑一轮，暴露的三个缺陷（无异议轮、无逾期判据、无裁量留痕）已全部补进协议 |
| **执行内核（一个执行体怎么被约束）** | **有明确路径，未验证** | 路径是 Gate 0 spike 的三条可证伪硬条件；生产里 `ToolExecutionPort`/`SandboxPort`/`RunBudget` 引用数仍为 0 |
| **判据体系（怎么判对错）** | **有方法，需投入** | 业务数据 0 张表、`tests/golden/` 无一条财务金标准 |

用 refact 轮的词汇说最准：**跑通的是 §6（supervisor 那一层），没跑通 §5（执行内核）与 §9（权限、预算、副作用）**——
而恰恰是 §5 和 §9 在生产里引用数为 0。

`round-protocol` 之所以能跑通，**是因为它假定每个 subagent 已经是能自己干完活、
自己提交、自己守纪律的成熟主体**；而 investment-app 要建的正是那个"能自己干完活"的部分。

### 7.3 一个此前没想到的连带结果

**已经建好的组织机制，恰好就是让判据体系不腐坏的前提。**
评测体系的经典失效，本轮全都已有对应机制：

| 评测体系的经典失效 | 已有的机制 |
| --- | --- |
| 出题的人就是答题的人 | 角色分离；写进不可裁量的下限 |
| 分数不好就改标准 | 验收方只能按冻结标准判定，不得为通过而静默改标准 |
| 被判错的一方没处说 | 异议轮 + 可复跑证据门槛 |
| 评委有既得利益 | 验收方由采纳条数最少算出，可计算、不可事后更换 |
| 判断无留痕，事后不可复核 | 裁定记录；未记录的裁定无效 |

**所以不是"先建评测再建 agent"，而是"评测体系本身要用这套机制来建"**——
否则金标准会被同一个模型出题又答题，建了也白建。

### 7.4 残留的真难点：判据的可判定性拆分

第二层里有一小块**不是工程难，是真的难**：

> **财务分析的「对」，常常没有唯一答案。**单元测试有对错，估值分析没有。

所以金标准不能照搬软件评测，要先做一次拆分：

| 可判定 | 不可判定 |
| --- | --- |
| 数字取对了没（来源、口径、期间） | 结论合不合理 |
| 引用的原文是否真实存在 | 判断有没有洞见 |
| 有没有编造事实 | 该不该买 |

**只对可判定的部分建金标准，不可判定的部分老实标 ⚠。**
这一步做不好，金标准会滑向"读起来对不对"，退回文风比拼。
成本很低，但顺序错了要返工——**应在建数据源之前先想清楚**。
