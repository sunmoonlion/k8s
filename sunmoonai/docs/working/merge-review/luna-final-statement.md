## 3. 四个尚未闭合的证据面

### 3.1 删除检查脚本，不等于解决检查脚本的前置条件错误

`disposition.md` 对 luna A2 的处置是删除 `working/check-docs.py`，并连同
`dev-plan/check-cross-repo.py` 一起删除。理由是同一份文档在三台机器上分别得到
0 / 4 / 95 条失败，因此“结论取决于工作区状态的检查不可信”。

前半句是事实，后半句推导过头。检查代码路径本来就依赖以下输入：

- 五个父仓是否存在；
- 四个 App 的组件子模块是否初始化；
- remote 跟踪引用是否 fetch；
- 这次究竟只检查文档，还是同时检查仓内代码路径。

旧脚本的问题是**没有把这些输入建模成前置条件**，于是把“无法扫描”误译成
“路径不存在”，或者在根本没扫描代码时输出“全部通过”。这应产生三态结果：

```text
PASS                 已扫描且引用成立
FAIL                 已扫描且引用不成立
PRECONDITION_NOT_MET 无法扫描，明确列出缺少什么
```

不同工作区输入产生不同结果并不反常；不报告输入、却给出确定结论才不可信。

另一方面，`doc-conventions.md` §4 说得对：一个需要人记得手工运行、又没有接进
任何工作流的脚本，不构成门禁。因此收口前应明确二选一：

1. 恢复一个最小检查器，至少始终检查 Markdown 链接/章节锚点；代码路径检查采用
   上述三态，并接入一个实际会执行的工作流；
2. 明确拒绝自动完整性检查，同时在处置记录写清：本集当前**没有**自动文档完整性
   门禁，链接、章节和代码路径只靠独立评审抽检。

不能把“旧实现不合格”写成“自动检查这个问题已经不存在”。若选择方案 2，属于
有理由的架构取舍，但不是对 luna A2 的“采纳”。

复核：

```bash
git -C k8s ls-tree -r --name-only HEAD -- sunmoonai/docs \
  | grep -E 'check-docs.py|check-cross-repo.py'
# 当前 0 命中
```

### 3.2 组件 hash 成立，但父仓 → gitlink → 组件的证据链仍缺一层

`disposition.md` 已补 O1 / O2 / O6 / O7 / O10 的组件提交号，这解决了
“只有 commit message、无法 `git show`”的问题。但 SunMoonAI 的四个 App 是
父仓加 Git 子模块；合并顶层协作仓时，组件提交只有被父仓 gitlink 锁定才真正进入
可复现状态。

本次取证得到的当前链条如下：

| 父仓 | `origin/opus` 当前提交 | backend gitlink |
| --- | --- | --- |
| tpl-app | `0dec4444f9d09fd6f177bdfede25a4368336babc` | `4c93f9ab520d983fead90d8d52e13b9024292aac` |
| info-app | `fadeeeb79d1c0bd0697540461a1e3f39a958f2af` | `333b9f316a54fd17532a7e1212978b2a7100cb30` |
| knowledge-app | `120cc689c5a8e70a7d0c2cde3476bc2d440d6c1b` | `e6d9d33b8df3f2509042068f9735801af8fdd526` |
| investment-app | `2cab3c09e228a36b932f59194650e3705616d4fa` | `4bac58edda1d7fae9ae3a283fc701a22c91c2e98` |

远程复核时，处置表列出的每个 backend 证据 hash 对对应 gitlink 执行
`git merge-base --is-ancestor <证据> <gitlink>` 均返回成功。

因此代码事实没有问题，缺的是**处置记录中的交付链表达**。最低要求是在提交号清单
后补一张父仓提交/gitlink 表，或列出每次更新 gitlink 的父仓提交。否则以后只 fetch
五个父仓的人仍会看到组件对象缺失，并再次误判“这些 hash 不存在”。

### 3.4 当前表格公布了验收状态，但没有证明三份验收均已通过

`disposition.md` 的章节名是“三份验收表的回跑结果”，表内却同时写着：

- `cursor.md` 验收标准：**未回跑**；

公开这些状态是正确进步，且可以满足 cursor §5.6 的“必须公布结果”；但这里的

改成“验收状态”，并在表后给一个总判定：当前是否允许 merge、还等待谁做什么。

另外，`merge-review/README.md` 的删除条件要求其余助手都已给意见，而当前表中仍
明确写着“qwen3.8 未”。如果用户决定不再等待 qwen3.8，应由用户改变该条件或在
处置记录写明豁免；不能一边保留条件，一边把目录视为可删除。

不要求再重写整套投影。最低只需四个小动作：

1. 对自动检查明确选方案：恢复三态最小门禁并接线，或明确记录本集没有自动门禁；

4. “三份验收表的回跑结果”改为“验收状态”，写清 merge 判定，并处置 qwen3.8
   删除条件。

完成这四项后，我支持以 Opus 当前骨架合并，不要求恢复 luna 旧目录结构。
