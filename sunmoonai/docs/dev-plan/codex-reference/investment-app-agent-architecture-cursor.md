## 1. 这一个 Agent 是什么

investment-app 的 Agent 不是「再做一个 Codex」，也不是「只做问数机器人」。它是
挂在投资产品上的执行体：人在网页上给目标，服务端调度，容器里干活，该留下的
数字、观点、PR、报告写回系统和 remote。

形态是 B-S：

```text
人 ──浏览器──► investment-app 服务端
                 │
                 │  建 / 派 / 等 / 读 / 中断 / 预算 / 事件
                 ▼
           持久 Task（Session / Run）
                 │
                 ▼
           Task 内 Subagent
                 │
                 ▼
           该用户的 Docker
              ├─ clone（Local）
              └─ worktree 或并行容器（隔离写）
```

人给目标、纠偏、拍板。服务端操作 Task / Turn，并把事件推回浏览器。模型推理、
改文件、跑命令发生在容器里，不发生在 API 进程里。

Codex 桌面 App 里，人对着会话说话，App Server 是给程序用的侧门。我们没有这道
缝：浏览器只打服务端，服务端就是唯一控制面。

**建设纪律（2026-08-22 确认，本篇最要紧的一条）：一套地基，两种形态，不建
两套系统。** 立项第一天就要守。等读到后面「生路怎么走」再写，人可能已经在
画第二个 Agent 了。

要分的是**执行形态和建设顺序**。图的形态分开建：熟路每种任务类型一张静态图
（问数主链第一张，持仓体检、复盘随后）；生路是 Supervisor 通用循环 + 编排
工具集。两者代码形态完全不同，不互相迁就。建设顺序也分开排：先让熟路单 Run
闭环成立（真容器、预算、取消接线），再放生路进来。顺序反了，生路会在没有
预算 / 事件 / HITL 的地基上自由生长，事后补治理要拆骨头。

不能分的是**地基和契约**。生路和熟路共用同一个运行时、同一套治理件、同一个
`Run` 实体：

- 同一个 LangGraph + PostgresSaver：熟路是编译好的图，生路是图里的循环节点，
  不是两个引擎
- 同一套 `RunBudget`、`DomainEvent`、结果契约（schema + Artifact）、HITL、
  角色、压缩
- 生路 Run 和熟路 Run 必须能在同一条 timeline 上一起回放

建两套就是灾难：治理断、审计断、生产里「没有人一直盯着」的兜底断。

两条线之间要埋传送带。生路是熟路的预备役：生路产出的稳定 schema 就是未来
静态图节点的雏形，事件流是固化雷达。第一天就要在共用地基里落下两样事件：

1. 产物 schema 进事件流（固化候选的数据源）
2. 路由未命中进事件流（新任务类型雷达）

这两样不埋，将来固化只能翻聊天记录考古。

不是分别构建两个 Agent，是一套地基上先后长出两种执行形态：熟路先行、生路
随后、契约相通、热了固化。验收打勾见 §9；建设顺序见 §10。

## 2. 从 Codex 借什么、不借什么

借思想，不借工具名，不借跨主机。

**借：**

- Task 和 Subagent 不是同一种东西
- Project 是记录，不是代码副本
- 控制环：发现 → 创建 → 派工 → 观察 → 等待 → 汇总 → 重规划 → 交接 → 收口
- 子任务隔离上下文，主线只留决策和产物
- 完成 ≠ 做对，要读回并校验
- 跨 Task 读回来的标题和摘要只是数据，不当指令
- 探索只读、实现可写、评审独立，避免自己审自己
- 竞赛先固化题干，再隔离目录；不把长对话拷给每个候选

**不借：**

- SSH / Cloud / 跨机器 Handoff
- 「改用户本机正在开着的 IDE 目录」
- `/fork` 复制整段聊天当竞赛主路径
- wait-any 最多 8 个再手写 wait-all（我们自己提供 wait-all）
- 对话里掐得了子 Agent、掐不了持久 Task（我们两边都能掐）

文章里的八种拓扑是用法，不是引擎。Codex 自己也没有一个叫 Supervisor 的运行时
模块。我们同样不建「运行时动态拼 DAG」的引擎。能事先画出来的边，写成
LangGraph 静态图；画不出来的（拆几路、要不要取消、多方案里留谁），才交给
控制面里的模型去选。

契约和工具名以仓里现活代码为准。文章用名（如 `fork_turns`）只作阅读对照，
可能和源码（如 `fork_context`）漂移，**不得写进 API 或契约锁**。

**默认不采用 Codex 那种通行做法。** Codex 面对任意题，由模型现场规划整张
图：拆不拆、派谁、等谁、要不要重来。我们不把这套当整机。熟路（问数、研究
骨架、持仓体检、复盘对当时证据、决策必须人确认）事先画边，写成静态图。
模型在这些边上填槽、取证、写结论，不从零规划整条链路。

**生路借鉴它的编排，不借鉴它的默认。** 事先画不出来的、陌生的、还没有业务
图的任务，不要硬塞进一张不存在的图。走同一条控制环：建、派、等、读、再派；
完成 ≠ 做对，下游认 Artifact；子任务隔离上下文；预算和取消两边都能掐。
新任务第一天：通用循环 + 已有工具 + 沙箱，带着预算、事件、无 schema 就停下
来问人。跑热了，把稳定边收成静态图。动态只发生在控制面允许的选择上：拆几
路、取消谁、竞赛留谁。

不是「不用 Codex」，是**默认不用它当整机，生路才用它的编排**。形态分、系统
不分：生路用的仍是 §1 那一套地基和同一个 `Run`，不是第二个 Agent。

## 3. 对象模型

仓里已经有 Session / Run / RunLineage / DomainEvent，不必另起一套名词。
下面是编排语义和现有实体怎么叠。

| 编排对象 | 它是什么 | 落在仓里 |
| --- | --- | --- |
| Project | 工作域记录：用户、数据域或仓库、容器内路径 | 新增记录即可，不是一份代码拷贝 |
| Host | 执行环境 | 该用户（或该 Run）的 Docker |
| Task / Thread | 持久会话 | `Session` + 其上的 Run 序列 |
| Turn | 一次输入及其后的全部工作 | `Run` / `RunAttempt` |
| Item | 最小可观察事件 | `DomainEvent`，经事件流推给浏览器 |
| Subagent | Task 内短工 | 子 Run；`RunLineage.parent_run_id` / `root_run_id` 已能表达树 |
| Worktree | 同一仓库另一棵真目录 | 容器内 `git worktree add` |
| Artifact | 固化题干、契约、报告、证据 | 对象存储引用；state 里只放 id |
| Automation | 到点叫醒 | celery beat，不挂在容器线程上 |

现有锚点（2026-08-22 读过）：

- `SessionStatus` / `RunStatus`：`domain/agent/models.py:9,18`
- `RunLineage`（session / run / root / parent）：`models.py:51`
- `CreateRunCommand` 带 `idempotency_key`：`domain/agent/commands.py:9`
- `CancelRunCommand` 已定义、尚未成为控制面主路径：`commands.py:31`
- `AgentRunService.create_run` 建 run 后丢给 celery：`application/agent/run_service.py:25`
- `RunBudget` 四维限额已建模：`domain/agent/runtime.py:62`
- `AgentProfile`：模型键 + 工具黑白名单：`domain/agent/profiles.py:14`
- `SandboxPort.run` 一次性执行抽象：`domain/agent/sandbox.py:39`；生产未见真实调用方

最要紧的两条：

1. **Session 是长期角色，Run 是一轮活。** 用户离开页面，Session 还可以在后台接着
   开 Run。容器跟 Session / 未收口的 Run 活，不跟浏览器 tab 活。
2. **Project 不是 clone。** clone 和 worktree 是 Host 磁盘上的真文件夹。

## 4. 执行环境

Host 只有 Docker。按用户建，用完删除——「用完」定义为产物已推走或已落库，
不是用户关了页。

三种目录用法，都是真文件夹，都在容器里，不回到宿主机用：

| 位置 | 何时用 |
| --- | --- |
| Local（主 clone） | 单线实现、复用依赖缓存、起一次性服务 |
| 同容器 Worktree | 同一 Session 里并行写、多方案竞赛、避免互相踩文件 |
| 另一容器 | 配额要独立、候选必须彻底隔离、或威胁模型要求一 Run 一沙箱 |

Worktree 和「一 Run 一容器」不打架。前者省、共享 `.git`；后者硬隔离。竞赛默认
先 worktree；候选要跑不可信代码或抢资源，再升成多容器。

长任务：后台保活**同一个**容器，历史和半成品还在。容器已经删了还要续：从
remote / 自有库恢复分支、Artifact、进度，再开新容器——这是新 Host 接上旧
Session，不是「目录还在」。

数据落 volume 或先 push 临时分支。只写容器可写层，删了就没。

## 5. 投资产品里这个 Agent 干什么

问数是感官。主战场是投资闭环：

```text
研究 → 观点 → 决策 → 持仓 → 监控 → 复盘 → 再研究
```

| 环节 | 典型活 | 怎么跑 |
| --- | --- | --- |
| 研究 | 公司 / 行业 / 取数 / 读公告 | 骨架固定，内部可 fan-out 取证 |
| 观点 | 写出带时点的 thesis | 独立评审；thesis 本身是 Artifact |
| 决策 | 买卖建议、备忘录 | **人拍板**。系统只给建议和证据 |
| 持仓 | 组合体检、敞口 | 尽量静态图，可周期跑 |
| 监控 | 公告、阈值、异动 | beat 叫醒；便宜角色盯，贵模型只在触发后上 |
| 复盘 | thesis 对时点验证 | 用**当时**的证据快照，不用今天重新检索 |

时间是一等公民。thesis、行情、财报都有 as-of。复盘对的是决策当时看见的世界。

问数走受管 SQL（Wren 一类语义层），任意代码走 Docker。两条威胁模型分开：
SQL 怕的是乱问和泄密，沙箱怕的是乱执行和出网。不要用同一条通道混过去。

评过 SQLBot（DataEase ChatBI：prompt 链 + RAG 校准）。机制可借，路线不换，
代码不搬。详评见同目录 `sqlbot-cursor.md`。可吸收：术语库、示例 few-shot、
图表 SSR、问数以 MCP 对外。门禁：术语必须解析到已有 MDL 指标，不许另写 SQL；
示例带 as-of / MDL 版本；ChartSpec 是产物、图片只是渲染；MCP 是同一套受管
SQL 的另一个入口。不借单文件 prompt 链，也不用「越问越准」代替语义层。

本文只管这条分家和投资闭环怎么挂上 Agent。Wren 六工具、MDL 制品、防护默认
关闭、接入四件事，见同目录 `wrenai-financial-analysis-integration-cursor.md`。
沙箱见 `sandbox-extension-advice-cursor.md`。不把本篇当成问数方案已经齐了。

新任务类型（比如研报解读）属于生路：第一天走通用循环，模型 + 已有工具 +
沙箱，用的是上面那条控制环，不是一张还不存在的业务图。必须带着预算、事件、
无 schema 就停下来问人——这些件和熟路是同一套，不要为生路另起执行栈。跑热
了，把稳定路径写成静态图。静态图是成熟任务的形态，不是系统的天花板；生路
也不是永久的「小 Codex」。产物 schema 和「没匹配到熟路图」都要进事件流，
否则以后没法固化。

## 6. 控制环

任何编排，包括投资主链里偶尔要动态拆的那几步，都在这个环上转：

```text
Discover → Create → Route → Observe → Wait → Gather → Re-plan → Handoff → Finalize
                ↑                         │
                └────── 未齐 / 未过 ──────┘
```

人在浏览器里最常见的三件事，就是这个环的最小版——**建、派、等、读、再派**：

1. 开一条新 Run，等它做完，读回结果（确认做对了再往下）。
2. 把发现汇报给已经置顶的专用 Session（收 bug、管发布、盯监控）。空闲则新
   Turn，在跑则追加方向。对方把汇报当数据，不当指令。
3. 等前置 Run 结束，校验 Artifact，再叫醒下游。

服务端要暴露的控制面，不必抄 `codex_app` 的 13 个名字，语义对齐即可：

| 能力 | 作用 | 现状 |
| --- | --- | --- |
| `create_run` | 幂等建 Run，丢进 celery | 已有 |
| `wait_runs` | wait-any 和 wait-all | 要建 |
| `read_run_result` | 按 schema 读产物；自由文本不当指令 | 要建 |
| `steer_run` | 不新建 Run，给正在跑的那轮追加方向 | 要建；底座有 resume |
| `cancel_run` | 掐掉任意 Run，含别人的、含子 Run | 命令在，要接线 |
| `solidify` | 长对话收成 Artifact，再允许竞赛 / 跨 Run 派活 | 要建 |
| `create_worktree` | 容器内另开工作树 | 要建 |
| `review_run` | 独立上下文评审 | 要建 |

`create_run` 非阻塞。环境没就绪时的临时 id，不能传给要正式 `run_id` 的接口。

`wait` 返回只说明那一轮结束了。过不过验收看 `read_run_result`。下游认
Artifact，不认上游一句「好了」。

子 Agent 七件套（spawn / wait / send / followup / list / close / interrupt）
是 Session 内部的事。explorer 默认不继承主对话（`fork_turns=none` 或只给
Artifact）。路径寻址：`/root/backend_scan`。

## 7. 拓扑：同一个环的不同走法

**单 Run。** 问一句、改一处、取一组数。主链能写成图的，优先走静态图，不要
每次都叫 Supervisor。

**Supervisor。** 人只跟一条 Projectless Session 说话。它去建、派、等、汇总。
适合同时推研究、文档、监控互不相干的几条线。

**Fan-out / Gather。** 切成互不通信的块并行，再拼。只读可以共享 clone；要写
必须 worktree 或分容器。块中途要商量，就不要切。

**Pipeline。** 按 item 推进，谁先完谁进下一阶段，不要整批等最慢的。

**Graph。** 依赖是网。状态放在服务端（LangGraph + Postgres 就是这张表），
不要靠翻聊天记录还原走到哪一步。这是问数主链、持仓体检该优先用的形态。

**Generator-Critic。** 干活的和挑毛病的不能共享实现上下文。`wren_dry_plan`
一类「只规划不执行」适合当 critic 的第一刀。

**Handoff。** 换人：打包 Artifact，交给另一条 Session，改负责人。换地方：
同一 Session 在 Local 和 worktree 之间搬 Git，不换机器。

**竞赛。** `solidify` → N 个 worktree（或 N 个容器）→ 各写各的 → 独立评审
比 diff / 回测 / 指标 → 留下胜者，掐掉其余。不 `/fork` 长对话。

**Race / Quorum。** 先到且通过验证的胜，或 K 个独立结果一致才采。候选必须
从同一份 Artifact 出发，不能从同一份被污染的聊天出发。落后的 `cancel_run`。

选型很短：

- 一两步明确动作 → 单 Run
- 大量阅读才得出短结论 → 子 Agent
- 跨项目、要长期角色 → 多 Session + Supervisor
- 多方案并行写 → 固化 + worktree
- 问一句怕脏主线 → 一次性侧边 Session，用完归档
- 固定投资流程 → 静态图，不要动态编排

## 8. 角色、沙箱、预算、事件

角色是配置，不是再写一套类。`AgentProfile` 已有 `model_key` 和工具名单，
补上指令和推理档即可。至少四种：

| 角色 | 干什么 | 沙箱 |
| --- | --- | --- |
| explorer | 读代码、读库、给 `file:line` / SQL 证据 | 只读 |
| worker | 实现、修、跑 | 只写授权的 clone / worktree |
| critic | 独立审 | 只读 |
| watcher | 盯长 job、监控、Heartbeat | 几乎不推理；只等待和报告，禁止「假装做完」 |

Docker 是外层沙箱。里层再按角色收一档，避免 explorer 在容器里写盘。交互式
写操作可以推到浏览器批；后台 Cron 需要新审批就失败，把错误抛回父 Run，
不要挂死等一个已经离开的页面。

`RunBudget` 已经有步数 / 工具 / LLM / token 四维。接线时按**一棵
`RunLineage` 树一本账**：根上总额，子 Run 共摊。否则 fan-out N 路就是 N 份
上限。跌到 80% / 50% / 20% 先提醒当前 Run 收敛，再硬停。提醒写入事件流成功
之后才标记已投递。

现有 `AgentMemory` 窗口大约是最近若干条，没有 Run 内压缩。财务 Run 会长。
要做阈值压缩：摘要必须保住数字、SQL、evidence_id，推理过程可丢。能拆成小
Run 就不在单 Run 里硬扛。压缩本身落 `DomainEvent`。

事件覆盖：Run 创建与状态、计划、diff、命令退出码、文件变更、派工、取消、
评审、token。人在浏览器里除了最终回答，还要看得到运行图。出了问题要能区分
「模型拆错了」还是「执行挂了」。

Hook 先做三件：按角色注入纪律（explorer 必须带证据）、子 Agent 结束时验证
不过就再跑一轮、工具调用前拦截写盘和出网。

## 9. 什么叫做好了

不看「像不像 Codex」，看这些能不能打勾：

1. 人只通过浏览器使用这一个 Agent，后台能续跑。
2. 画得出来的投资边在静态图里，动态只发生在控制面允许的选择上。
3. 子任务返回 schema 或 Artifact id，自由文本进不了下游决策。
4. 每个数字能指回 SQL / 数据源 / 时点。
5. 决策终态必须由人的确认触发。
6. 每次派、等、取消、重派能在 timeline 回放。
7. 超预算是事件，不是账单惊喜。
8. 出错能从 checkpoint 续，用户不用从头再讲一遍。
9. 有金标准题，改 prompt / 图 / 模型能回归。
10. 长 Run 要么被拆小，要么压缩后数字还在。
11. **熟路生路不建两套系统。** 任意 Run 都能指回同一套 LangGraph / Saver /
    预算 / 事件 / 契约 / HITL。生路产物 schema 与路由未命中都能在事件流里
    查到。timeline 上熟路和生路能一起回放。禁止为生路另建执行栈。

## 10. 建设顺序

现在的地基：能幂等建 Run、能丢进 celery、Pilot 链在，预算和取消是睡着的，
沙箱 port 还没有真实执行。屋顶（八种拓扑）不要画在这个上面。

两条轨并行，不要排成一条队。轨 A 和轨 B 都是在**同一套地基**上施工，不是
两个运行时。P0 先把这套地基接通（真容器、预算、取消、事件）；第一张熟路图
（问数）在合流后上；Supervisor 生路更后——顺序反了会在无治理的地基上长出
第二条系统。

**轨 A：Agent 执行闭环（不依赖财务库选完）**

1. **一个真容器跑通一次。** `DockerSandbox` 接上现有 `SandboxPort.run`，产物
   进对象存储，引用对得上。不先改 port 签名。
2. **预算和取消接线。** 超限有事件；人能从浏览器掐掉 Run。
3. **控制面四件套。** `create_run`（已有）+ `wait_runs` + `read_run_result` +
   `cancel_run`。到这里，「建、派、等、读」成立。这一步在轨 A 通了就能做，
   **不等**问数数据源。

**轨 B：问数上限（数据源未定，不画问数主链）**

4. **选定数据源 + 样例库 + 受管 SQL。** 20 道金标准题的准确率是**这条静态
   问数链的退出条件**，不是全项目排到第 4 步才准验数。

**合流之后才做的**

5. **第一张熟路图：问数静态主链**接到已通的问数能力和已通的控制面上。
   取数 → 校验 → 分析 → 人确认。持仓体检、复盘是随后的熟路图，不要一张
   图包打天下。这一步起，产物 schema 和路由未命中必须已经在事件流里（传送带
   第一天就埋，不是等固化时再补）。
6. **生路：Supervisor 通用循环 + 编排工具集。** 第一张熟路图通了才开。单 Run
   还没在真容器里拿出过 Artifact 之前，不开放 Supervisor **自由拆财务活**。
   控制面四件套已经在轨 A，不在这条禁令里。solidify + worktree（或第二容器）
   跟生路一起：Fan-out 和竞赛才允许上。
7. **独立评审、steer、压缩、watcher、beat 监控。**
8. **依赖成网的 Registry 流程**（发版检查、跨仓契约）最后做。

对应关系：P0 = 轨 A + 轨 B；P1 = 第一张熟路图；P2 = 生路 Supervisor。
每一步的退出条件对着上一节的勾。第 11 条（不建两套系统）从 P0 第一天就开始
打勾，不是 P2 才验。

## 11. 一句话

investment-app 只要一个 Agent：人在浏览器里用，服务端调度，Docker 里执行。
熟路走预定图，生路走控制环，跑热了再收成图。要分的是形态和顺序，不能分的
是地基和契约。一套地基上先后长出两种执行形态，不是两个 Agent。Codex 教
怎么拆、怎么等、怎么隔离；投资业务教哪些边必须写死、哪些数字必须可溯、
哪一步必须人拍板。两层进同一个 Run，不进第二套系统。
