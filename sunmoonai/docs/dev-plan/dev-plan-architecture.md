## 1. 归属判据（先于归属结果）

①a 从六阶段 + 三横切推出十一类文档。安置 260 节时，**每一节按下面的判据入槽，
不是按「它现在在哪个文件」入槽**。判据先行，结果在后（§8 才是结果）。

| 槽 | 名称 | 归属判据（什么样的内容属于这里） | 不属于这里的标志 |
| --- | --- | --- | --- |
| **A** | 需求合同 | 产品必须满足什么：对象、契约、状态语义、功能义务、不变量、验收矩阵 | 开发流程、现状快照、实现选型 |
| **B** | 工程手册 | 开发运行时的结构与一次开发 Task 怎么执行：怎么搭、怎么干、为什么 | 任务清单、进度、单轮裁定 |
| **C** | 协作协议 | 多家/多角色怎么一起干活、怎么做决定（不随轮次变的部分） | 某一轮的参数与产物 |
| **D** | 约束护栏 | 动代码前必须逐条勾的不可违反项，每条标「谁在执行」 | 现状、计划、论证 |
| **E** | 方向档 | 要建什么、为什么这么建（含架构取向：它回答的正是「为什么这么建」） | 进度、任务、现状 |
| **F** | 任务档 | 可派工的工作单元：目标、前置、测试、验收、回滚 | 状态叙述、架构论证 |
| **G** | 状态档 | 现在到哪、卡在哪、什么不能倒退 | 论证、实施步骤、未派工的待办（那是 F） |
| **H** | 目录入口 | 目录里有什么、各文档分工 | 任何实质内容 |
| **I** | 取证档案 | 单轮的裁定、处置、落点收据、审议过程——**只追加不修改** | 现行规范 |
| **J** | 原始需求档案 | 所有者原始输入（B7：位置已定死在 `working/`） | 现行合同 |
| **K** | 规格（随代码） | 与代码同 PR 演进的契约/模型/测试 | 目标态叙述 |

三条通用判据（处理跨界节）：

- **P-投影**：同一事实只有一个权威展开处；他处可投影（指针 + 结论），不算混写。
  投影节的落点随**它服务的读者所在槽**，不是随权威处。
- **P-自描**：文档关于自身的元信息（边界、章存在的理由、覆盖声明、修订纪律）随该文档入槽，
  不单独归类——拆了就没有读者找得到它。
- **P-轮属**：由某一具体轮次产生、只对该轮有意义的产物（裁定、处置、落点收据）入 **I**，
  即使它当前物理寄居在别的文档里（见 §3 拆并代价）。

## 3. 拆与并：主张与代价（J5）

### 3.1 拆：`agent-dev-guide.md` §8「本轮核查裁定」→ I（`rounds/` 对应轮目录）

- **为什么走**：§8 是 `runtime-refact` 轮的裁定与处置记录——由具体轮次产生、
  只对该轮有意义，P-轮属判据下入 I。它不是「怎么搭、怎么干」的知识，
  是「这一轮换掉了什么」的收据。
- **谁的引用会断**：`agent-dev-guide.md` §0.1「被撤销主张集中在 §8」、§0.2 章表
  「§8 核查裁定」行、§12.2 附近对 §8 的指认（以 `grep -n '§8' agent-dev-guide.md`
  枚举，迁移时逐处改指针）。
- **锚点怎么保全**：`doc-gate.py` 会抓到失效的 `§8` 引用（它查章节引用含跨文档解析），
  迁移与改指针必须同一提交完成；`anchor-gate.py` 复跑确认无 `file:line` 断锚。
- **读者检索路径变化**：想查「什么主张被撤了」的读者从「手册 §8」改为
  「手册 §0.1 的指针 → 轮档案」。多一跳，但读者意图本来就是考古，
  不是干活——干活路径不变短，可以接受。
- **⚠ 执行时机**：在 ⑦ 清理或其后一个工作单元里做，不在本候选内做（本轮只定架构）。

### 3.2 拆：`agent-dev-guide.md` §10「五份历史正文及目录说明的逐节处置」→ I（各吸收轮）

- **为什么走**：它是各次吸收的**落点收据**——逐节处置表属于产生它的那一轮的
  取证档案（P-轮属）。手册正文需要的是一个指针（「来源处置见某轮」），不是 322 行收据。
- **谁的引用会断**：`README.md`「§10 是四份源稿的逐节落点表（182 行）」、
  §0.2 章表「§10 逐节落点」行、`archive/README.md` 轨迹图。
- **锚点保全**：同 3.1，`doc-gate` + `anchor-gate` 双跑；收据本身按轮次拆分入各轮目录，
  行号级锚点（若有）随收据整体移动，引用处改指新路径。
- **检索路径**：「某历史节现在在哪」的查询从「手册 §10」改为「对应轮目录的落点表」，
  查询者本来就要先知道是哪一轮，路径不变长。

### 3.3 并：`handoff.md`「文档面待办」→ F（`implementation-plan.md` 任务条目）

- **为什么并**：D1/D2 是**未派工的任务**（有验收条件、无状态叙述），
  按判据属 F 不属 G；handoff 自己的页首都写「任何任务的实施步骤不写在这里」。
- **代价**：两处文件各改一处；`grep -rn 'D1\|D2' handoff.md` 无外部引用（⚠ 迁移时复跑核实）。
  检索路径：查待办的人从此只看任务档，少一处「既像状态又像任务」的格子。

### 3.4 明确不拆不并（论证）

| 主张 | 不做的理由 |
| --- | --- |
| 拆 `request-lifecycle.md` 为 PRD + 领域模型 + 规格三份 | 代价 prohibitive：71 个带行号外部锚点、40 份文档引用（B2）。收益为零：其内部各章已是类型化的（§2 对象 = 领域语言、§5 功能义务、§6 不变量、§11 验收），拆文件不改变读者读法，只断引用。详见 Q1（§6） |
| 并 `development-plan.md` 与 `implementation-plan.md` | 生命周期不同：方向随拍板变、任务随执行变。并了就是「方向里长进度」，v5 正是这个死法（`development-plan.md`「起点」节自述） |
| 并 `protocol/` 进 `agent-dev-guide.md` | 变更门槛不同（协议走 T2、手册走工作单元），读者时刻不同（开轮前 vs 干活中）。并了要么协议被随手改，要么手册改动被流程卡住 |
| 重排 `rounds/` 内部 | F4 禁止：破坏已归档轮次的可取件性 |

5. **本轮候选本身不触碰该文件**——①b 的全部安置对 A 槽是「原位确认」，

## 6. 不预设立场问题的回答（J7）

- **Q1**（`request-lifecycle.md` 落哪格）：**A 需求合同，整份不拆**。
  所有者起点 ≈PRD，本候选**维持**。起草者异议（PRD + 领域模型 + 规格三焊）在
  内容分析上成立，但结论不成立：领域模型（§2 对象）与验收（§11 AT 矩阵）不是
  外来物，是 PRD 的定义部件——没有共享词汇的 PRD 不可判，没有验收的 PRD 没有终点。
  「焊」在这里是类型化的**章**，不是杂烩；拆文件的代价（71 锚点 / 40 引用，§4）
  换不来任何读者收益（§3.4）。42 节逐节落点见 §8 表 1。
- **Q2**（`rounds/` 落哪格）：**I 取证档案**。所有者起点 ≈ADR **部分成立**：
  rounds 里确有决定记录（`rulings.md` 的裁定行），但 rounds 整体比 ADR 大——
  它含完整审议过程，而审议过程是**证据**不是决定。本候选的答案：决定不搬出档案，
  而是被**索引**（Q9）；档案只追加不重排（F4）。
- **Q3**（`protocol/` 落哪格）：**C 协作协议，不是实施计划的一部分**。
  对所有者起点提出异议，举证：① 生命周期不同——协议变走 T2，任务条目完成即失效；
  ② 读者时刻不同——开轮前读协议，干活时读任务；③ 内容种类不同——实施计划说
  「建什么、什么顺序」，`round-protocol.md` 说「怎么一起干活、怎么做决定」，
  后者里没有任何一行是任务。三条均可由通读两文复核。替代落点即 C 槽。
- **Q6**（类别数量）：**11 类**。每类的「为什么不能并进相邻类」：
  决定记录 vs 规格（一个只被取代、一个随代码同步）；状态 vs 任务（每天变 vs 完成即失效）；
  约束 vs 手册（变更门槛与读者时刻不同）；协议 vs 手册（同 Q3②）；方向 vs 任务
  （§5.5 反面：并了就是 v5 死法）；取证档案 vs 一切（冻结性互斥）；上下文包单列
  （①a §6.4：判据是越短越好，与所有类的判据冲突）。
- **Q8**（不走轮次的工作，取证放哪）：**`evidence/<task-id>/`**。
  该位置不空缺——`implementation-plan.md`「交付规则」已定义它
  （`result.md` + 测试输出 + 关键请求/响应 + revision/digest，去敏）。
  本候选正式化边界：**T0/T1 的取证落 `evidence/`，T2 的取证随轮落 `rounds/`**；
  两者同属证据，分置只是因为检索路径不同（按任务查 vs 按轮查）。
- **Q9**（决定如何可检索）：**新增 I 槽决定索引 `rounds/decisions-index.md`**。
  规则：① 决定 ID 全仓唯一，形如 `<round-id>/R<n>`（轮次前缀消除
  「R1 指三件事」的撞车）；② 索引每行 = ID + 一句话结论 + 状态（现行/被谁取代）+
  档案指针；③ 机器可判：脚本逐行核对档案中确有该 ID 的裁定行（锚点存在方向）
  且索引无重复 ID（另一方向）——两个方向都能失败才是检查（`constraints.md` 既有理论）。
  存量 26 条裁定的回填是一个工作单元，不在本轮。

## 7. 与 `project-guide/` 的边界（任务书 §4.2 要求）

`project-guide/` 记**现状投影**（代码已经长什么样），本架构任何槽都不装现状：
A 是目标合同、K 随代码但活在产品仓、G 只记开发状态不记系统现状。
边界判据一句话：**「改了代码它就要跟着变」的是 project-guide；「要它变必须先拍板」
的是本架构各槽。**当前缺口与接线状态按 `request-lifecycle.md` §12.1 的既有纪律
只进实现矩阵 / project-guide，不回写目标合同。
