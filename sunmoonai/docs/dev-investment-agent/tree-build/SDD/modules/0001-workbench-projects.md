## 三、三种功能落到 Codex 上

| 情形 | 执行环境 | 目录 | 沙箱策略 | 审批 |
| --- | --- | --- | --- | --- |
| 聊天，不在项目里；或者项目的机器不在线 | 空 | — | 只读 | 从不 |
| 聊天，在项目里 | 项目所在的机器 | 项目目录 | 只读 | 从不 |
| 工作 | 项目所在的机器 | 项目目录 | 只写项目目录 | 按用户的设置 |
| 专家 | 同上 | 同上 | 同上 | 按用户的设置；越出的按专家包的规矩处置 |

| 规则 | 说明 |
| --- | --- |
| 每一轮都带全这四样 | 不靠上一轮留下的。由账里的种类与方向盘决定，页面传来的设置一概不用 |
| 新的入口不收任何设置 | 新建对话、请专家的接口里带了设置就拒绝（422） |
| 旧入口建的会话 | 沿用它当时记下的设置，行为不变 |
| 设置页里的 `on-failure` | Codex 0.155.1 已经不认。按 `on-request` 发。设置页的选项留到第 7 步改 |

### 在真的 Codex 上发现并处理的四件事

| # | 发现 | 处理 |
| --- | --- | --- |
| 1 | 同一条线先聊天、后进项目：Codex 换了工具和权限，但不告诉模型。模型记得自己先前说过「没有执行命令的工具」，之后一直不用，连转成工作之后也不用。同样的步骤有时成、有时不成 | 换情形时往线里插一段说明（`thread/inject_items`，角色是 developer），写明现在在哪个目录、有没有执行命令的工具、能不能写。账里记一条 `session/mode_announced`，内容连同说明的原文。插不进去不拦这一轮 |
| 2 | 聊天里模型会起子代理。子代理是另一条线：事件不进账，费用不进预算 | 起线与重新装载线时都关掉 `multi_agent` 与 `goals`（后者会让线自己接着跑）。验过：模型答「没有这个工具」，沙箱里只有一条线的记录 |
| 3 | 推理摘要的增量事件被记进了账，一轮几十条。读事件的接口一次最多 500 条，几轮之后就取不全 | 凡是增量都不入账。成段的内容在 `item/completed` 里 |
| 4 | 被只读拦下的命令，Codex 不发事件。命令确实在用户机器上执行了、写被拒了（输出是「只读文件系统」），但账里没有这条命令 | **没有处理**，记在 [账本](../../structure-ledger.md) H29。联调脚本改为到沙箱里那条线的记录上去核对 |

## 四、接口

契约版本 2。都在 `/api/workbench` 之下，登录的用户，只碰得到自己的。

### 项目与对话（甲）

| 接口 | 作用 |
| --- | --- |
| `GET /workspaces` | 我的工作区：每台机器的每个根目录 |
| `GET /projects`、`POST /projects` | 列出、新建 |
| `GET /projects/{项目}`、`PATCH /projects/{项目}` | 一个项目连同它的对话与委托的摘要；改名、归档 |
| `POST /sessions` | 新建对话：`kind`、`project_id`（聊天可不给）、`title`（可不给）。旧的三个字段的写法还认 |
| `GET /sessions` | 可按项目筛；可只要不属于项目的 |
| `POST /sessions/{对话}/project` | 把不属于项目的聊天放进一个项目 |
| `POST /sessions/{对话}/kind` | 聊天转为工作 |
| `PATCH /sessions/{对话}` | 改名 |

### 专家（丙）

| 接口 | 作用 |
| --- | --- |
| `GET /packs`、`GET /packs/{专家}` | 有哪些专家：名字、一句话、解决什么、不解决什么、输入、输出、每一步的名字与一句白话、每条验收的名字、不通过时怎么办、走一遍至少要多少预算 |
| `POST /projects/{项目}/delegations` | 从专家入口请专家：新建一段工作对话并立刻交给专家 |
| `POST /sessions/{对话}/handover` | 在对话里请专家（已有）。加了两条检查：对话要属于项目；机器要在线 |
| `GET /tasks/{委托}/steps` | 委托单与步骤轨：每一步的状态、做了几次、几次没过、花了多少、用了哪些工具各几次 |
| `GET /tasks/{委托}/steps/{第几步}` | 一步的全部：每一次做的交回物、逐条的验收结果、过程的摘要 |
| `GET /interactions` | 跨对话的待办，摘要形态 |
| `GET /interactions/{待办}` | 审查面，五块齐全 |
| `GET /expert/overview` | 专家首页的三张清单：等我决定、进行中、最近交回的 |
| `GET /tasks/{委托}/dossier` | 底稿，按这位专家登记的排法排好 |
| `GET /tasks/{委托}/dossier/export` | 整份底稿导出成 Markdown |

| 规则 | 说明 |
| --- | --- |
| 方法的原文不出后端 | 上面任何接口的返回里都没有。有测试逐个专家、逐个步骤核对 |
| 状态由后端算 | 页面照着画，不自己从事件里推 |
| 机制烟测不在清单里 | 它只给我们自己测机制用。按编号去取也答没有 |
| 「不通过时怎么办」的说法由后端给 | 三种：「重做，最多 n 次」「退回第 k 步」「停下来问你」。按专家包里写的如实组合，例如「重做，最多 1 次；仍不过，退回第 2 步」 |
| 金额的写法 | 至少两位小数，多出来的零去掉。账里存的是六位小数 |
| 默认预算 | 接口里给的是空。所有者还没有定（`W4`） |

### 步骤的状态

| 状态 | 记号 | 什么时候 |
| --- | --- | --- |
| `pending` | ○ | 还没做 |
| `running` | ● | 正在做 |
| `accepted` | ✓ | 做完，验收通过 |
| `reworking` | ↻ | 验收没过，正在重做 |
| `went_back` | ↩ | 验收没过，退回到了前面的某一步 |
| `redo` | — | 做过并且通过了，但后面的步骤退回到了它之前，要重做。设计里没有这一种，做的时候发现少了 |
| `waiting` | ⏸ | 停下来等用户 |
| `failed`、`cancelled` | ✕ | 委托在这一步结束 |
| `not_reached` | — | 委托已经结束，没有做到这一步 |

### 审查面的五块

| 块 | 内容 |
| --- | --- |
| 在哪 | 项目、对话、委托（问题、专家）、第几步、问的是哪一类事 |
| 待决的是什么 | 标题、问题、为什么停下、没通过的验收（用验收自己的话）、每个选项连同「选了会怎样」、还不知道的 |
| 决定的对象 | 这一步交回的原样、命令与目录（工具审批）、预算（预算用完）、对象的摘要值、目标状态版本 |
| 时效 | 什么时候过期、还剩多少秒、过期之后会怎样 |
| 决定记录 | 谁、什么时候、选了什么、金额 |

答复用的令牌仍然只在开出这件事的那条事件里。审查面的接口只给出那条事件在哪（对话、游标），页面去那里取。

### 底稿

| 项 | 做法 |
| --- | --- |
| 怎么排 | 每个专家包登记自己的底稿：哪几块、每块取哪个交回物的哪一项、画成什么、表有哪几列叫什么。没登记的用通用的排法 |
| 表与数取哪里的 | 各步验过的交回物。**不取成稿里的表**：那是模型重抄的一份，可能抄错 |
| 专家验过什么 | 勾稽、对照官方各有一句小结（验了多少、过了多少），数的是交回物里写的 |
| 数的出处 | 每张数据表带上数据集、数据版本、数据时点；口径在各行里 |
| 没做到的块 | 写「没有做到这一步」 |
| 结论栏 | 只放用户自己存过的。没存过就是空的 |
| 各步写的数据版本不一样 | 如实列出来（`versions_seen`），由页面提醒。做的中途数据换了版本才会这样 |

## 五、专家读项目里别的对话（丁）

| 项 | 内容 |
| --- | --- |
| 地址 | `POST /api/mcp/workbench` |
| 工具 | `list_project_conversations`、`read_project_conversation`、`list_project_dossiers`、`read_project_dossier`。都是只读的 |
| 令牌 | 工作台签发、工作台自己验，绑定用户 |
| 能读哪个项目 | 每个工具都要带委托编号（专家每一步的说明里给）。每次调用按这个委托核对：是这个用户的、还没结束、方向盘在专家手里。能读的就是委托所在的那一个项目 |
| 读不到的 | 别的项目、别的用户的：和不存在一样答。当前这段对话：它就在线里，不经工具 |
| 记录里有什么 | 用户说的话、模型说的话、命令与改动与查询的摘要、专家每一步的结果、专家问过用户什么（只有标题） |
| 记录里没有什么 | 答复用的令牌、查询带回的内容、改动的内容、专家每一步发给模型的方法原文 |
| 分页 | 每页 40 条；一句话最长 2000 字；底稿最长 30000 字 |
| 留痕 | 专家读了什么，记在账里（`records/read`） |
| 限流 | 每个用户每分钟 60 次（可配） |

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `WORKBENCH_RECORDS_MCP_ENABLED` | 关 | 关着时这个地址不存在，专家每一步的说明里也不提这组工具 |
| `WORKBENCH_RECORDS_MCP_URL` | 空 | 开关开着、地址也配了，供给沙箱时才带上地址与令牌 |
| `WORKBENCH_RECORDS_MCP_RATE_PER_MINUTE` | 60 | 限流 |

## 六、「没有数据」（戊）

| 来源 | 什么时候记 | 内容 |
| --- | --- | --- |
| 查数据的工具 | 工具调用失败，答复是「没有这个数据集」，被查的数据集名认得出证券（市场加六位代码开头，例如 `sh600519-financials`） | 证券代码、市场、数据集名 |
| 专家的步骤 | 这一步的交回物说没有入库。专家包里写明哪一步会发现、怎么认（财报体检的数据摸底） | 证券代码 |

| 规则 | 说明 |
| --- | --- |
| 同一段对话同一个代码只记一次 | 先拿这段对话的锁，再查有没有 |
| 认不出代码 | 不记。对话里照常显示工具的答复 |
| 专家发现没有数据 | 不重做，直接问用户。原先是先重做一次再问：重做也不会有数据，只是白花钱 |

## 七、和设计不一样的地方

| 项 | 设计 | 实现 | 原因 |
| --- | --- | --- | --- |
| 读项目记录的令牌 | 绑定用户与项目 | 绑定用户；项目每次按委托核对 | 沙箱里的工具服务是拉起沙箱时配的，一个用户一个沙箱，那时还不知道是哪个项目。效果相同：只能读委托所在的那一个项目，只在专家处理期间 |
| 没有数据时的两个选项 | 「先停在这里，等数据入库后我再来」「停止」 | 「数据已经入库了，接着做」「停止」；也可以先不答 | 「先停在这里」一旦提交，这件待办就用掉了，委托却还在等，没有东西可等。不答就是停在这里：委托不花钱，72 小时内回来接着做 |
| 「没有数据」的来源 | 只有工具的答复 | 加了专家的步骤 | 模型通常先列出数据集、发现没有，就不再去查一个不存在的名字。只靠工具的答复，财报体检遇到没入库的公司时记不下来 |
| 底稿的表 | 成稿里的表 | 各步验过的交回物 | 见上 |
| 步骤的状态 | 七种 | 多了 `redo`、`not_reached` | 退回之后中间的步骤、委托结束时没做到的步骤，原来没有说法 |
| 验收的结果 | 通过、不通过 | 多了「没有验」 | 交回的格式不对时，后面的各条无从验起。记成通过或不通过都不对 |
| 专家清单里的默认预算 | 有 | 空 | 所有者还没有定 |
| 审查面的时效 | 样稿写 24 小时 | 72 小时 | 样稿只是示意。账里一直是 72 小时；工具审批是 1 小时 |

## 十、实时的花费与随时停止（2026-10-04）

所有者 2026-10-04 定：页面上实时显示花了多少（像 WorkBuddy 那样一个不断跳的数），加一个随时能点的停止；**不靠预算上限**。页面的设计在 [`PRD/apps/investment.md`](../../PRD/apps/investment.md) 5.12。

### 做了什么

| 项 | 做法 |
| --- | --- |
| 单价 | 放在配置 `WORKBENCH_MODEL_PRICES_JSON`，每百万 token、人民币。默认带 `kimi-k3` 一个：输入 20、命中缓存的输入 2、写缓存 20、输出 100（2026-10-04 查自 Kimi 开放平台公开价目）。不认识的模型不给金额，只给 token 数 |
| 每次调用的金额 | runner 收到 Codex 的用量通知，算好金额再进账。事件 `thread/tokenUsage/updated` 多一个 `cost`：这一次花的、这一轮到现在花的、对应的 token 数、币种、模型、「估算」 |
| 一段对话的合计 | `GET /api/workbench/sessions/{对话}/usage`：合计、按轮次、用的单价。金额用当时记下的，以后改单价不重算过去的 |
| 专家一步花多少 | 这一步里各次调用相加 |
| 专家正在做的那一步 | 步骤接口的 `budget` 多三项：`running`（正在做的这一步到现在花的）、`spent`（做完的加正在做的）、`estimated` |
| 预算上限 | 变成可不给。不给就没有上限：`limit` 与 `left` 是空，专家不会因为钱停下来。给了仍然和原来一样 |
| 停下自己的一轮 | `POST /sessions/{对话}/interrupt` 不用给轮次的编号：停的是这条线正在跑的那一轮。账里记一条 `turn/stop_requested` |
| 停下专家 | `POST /tasks/{委托}/cancel`：专家正在做某一步时，立刻把那一轮停下。那一步记为已取消，花了的照记，委托结束，方向盘交回 |

### 顺带查出并改掉的两个错

| # | 错在哪 | 后果 | 改法 |
| --- | --- | --- | --- |
| 1 | 专家一步的花费，拿的是 Codex 报的「这条线到现在的累计」，不是这一步的 | 越往后的步骤多算得越多。机制烟测两步原来记 1.02，实际是 0.19 到 0.27 | 按每次调用相加 |

### 在真的 Codex 上验过的（`workbench-chain.sh`，22 项全过）

| 项 | 结果 |
| --- | --- |
| 每条用量事件都带金额 | 是。模型 `kimi-k3`，人民币 |
| 专家各步记的花费 = 这几步里每次调用相加 = 账上的已花 | 是。两次分别是 0.193040 与 0.270824 |
| 不给上限，专家做到底 | 是 |
| 自己的一轮：不给轮次编号也停得下 | 是。按下到停下 0.3 到 0.4 秒，这一轮以 `interrupted` 结束 |
| 专家做到一半停下 | 是。按下到委托结束 2.5 秒；那一步记为已取消；方向盘交回 |
| 重新接线时重报的用量没有再记一遍 | 是 |

### 没有做到的，和要知道的

| 项 | 说明 |
| --- | --- |
| 被打断的那一次调用，花费记不到 | Codex 只在一次模型调用**做完**时才知道用量。调用做到一半被停下，Codex 不报，我们记的是 0；模型厂商那边大概率仍然按已经生成的部分收费。所以停下的那一刻，显示的数会比真实账单少一点（最多一次调用） |
| 金额是估算 | 用的是用户自己的模型 key，真正的账单在模型厂商那边。写缓存按 5 分钟档的单价算（Codex 不报是哪一档）；单价改了要人去改配置 |
| 金额每次调用跳一次，不是每个字跳一次 | Codex 不在生成过程中报用量。一次调用通常几秒到几十秒 |
| 没有硬性的花费上限 | 这是所有者的决定。没有人看着的时候，专家会一直做到做完、验收不过停下、或被停下。专家包里重做的次数有上限；「退回第 k 步」的次数还没有上限（`I7`） |
| 页面 | 没有做。第 7 步 |
