## ② 架构评审

- 结论：**采纳（立项为决策型 REQ）**。整体方向采纳，具体范围待用户在 §决策点 逐项拍板后
  转 ADOPTED。

- 理由：

  现结构有三项设计是正确的，本请求**不改动**：baseline 与 requests 的二分及其生命周期
  （AGENTS.md §0）、权威排序把 baseline 定位为「代码的缓存」而非真相（§1）、
  以及漂移义务只加在智能体一方的元规则（§1.1）。

  需要重组的是**分类轴**。现结构按物理位置组织（`baseline/app-platform/intra-apps/`），
  而实际承载的事实有两个更本质的维度：**寿命**（长期规则 vs 每次发布即变的值）与
  **归属主题**（平台 / 跨切面 / 仓）。轴选错导致四个持续性后果：

  1. `intra-apps/` 五项实为三类（3 领域 App + 1 模板仓 + 1 部署编排仓），k8s 与 tpl-app
     被归入「app-platform 的内部」名实不符；同时真正的 auth-app 缺位。每新增一个非 App
     的仓，分类异常加一。
  2. 九平台中仅 app-platform 有 baseline（6 份 1300+ 行），其余八平台合计只在
     `architecture.md` 251 行里带过。改 Harbor 保留策略或 RabbitMQ vhost 的人，
     在本文档集中无可读内容。
  3. **易腐事实与长寿命事实混居**。§0 承诺 baseline「一定时期内不变、手动更新」，
     该承诺对架构原则成立，对 digest / Alembic head / schema sha256 / release_id
     必然失效。REQ-002 核出的偏差中，相当一部分源于此机制而非疏忽。
  4. ADR 规定落 `baseline/sunmoonai/adr/`「随首条落地创建」，实际 13 条在
     `app-platform/docs/adr/`。且该位置本身语义冲突：baseline 覆盖式修改、ADR 追加不覆盖。
     结果 §2 要求的「任何事实向上能追到当初为什么」这条链是断的。

  另有一项非结构问题一并处理：`AGENTS.md` 263 行中混着「怎么读怎么写」与
  「REQ 方法论」两类内容，使动手前必读门槛与其自身「3 分钟必知」的精神相悖。
  按 §4 约定 3，应拆分而非精简掉。

- 冲突与代价对比：

  | | 重组 | 维持现状 |
  | --- | --- | --- |
  | 一次性成本 | 15 条内部相对链接重算；文件 rename 后 `git blame` 需 `--follow`；REQ-001/002 内路径引用需更新；治理文件改动须共享分支经批准（§7） | 0 |
  | 持续成本 | 迁移后需维护 `facts/` 生成脚本 | 每轮发布产生新的文档-代码偏差（本次一轮核出 14 条）；八平台盲区不消失；分类异常随新仓线性增长；ADR 追溯链持续断开 |
  | 风险 | 迁移期间新旧路径并存易产生第二真源 | 文档可信度继续下降，最终退化为「读了也不敢信」，等同于放弃 §1 的缓存定位 |

  **关于 `AGENTS.md` 的路径**：初拟方案曾建议移入 `governance/`。核查后否决——
  五仓共 10 个指针文件（各仓 `AGENTS.md` + `.cursor/rules/sunmoonai-architecture.mdc`）
  硬编码其绝对路径，且均在各仓 master 上（§8）。移动需同时改动五仓 master 的治理文件，
  代价远超收益。**结论：`AGENTS.md` 的路径视为稳定接口，只拆内容不迁位置。**

### 复审（2026-08-15）

- 结论修订：**不采纳，并入 REQ-004**。原分析不推翻，但前提有误。
- 理由：本请求把「结构重组」当作目的，而结构只是达成投影纯度的手段。用户于 2026-08-15
  澄清了三事混一（投影 / 目标约束 / 智能体工作流），确立 baseline 为**纯投影**后，
  本请求的两条主要提案性质发生变化——`facts/` 由组织方案升格为定位的必然推论，
  验证机制由附属检查升格为核心质量指标——须在新前提下重新推导，而非平行推进。
- 有效内容去向：目标结构、两轴、迁移映射、`AGENTS.md` 路径为稳定接口的核查结论，
  均已并入 `REQ-004-现有代码投影/baseline.md`。本文件夹 `baseline.md` 冻结为记录，
  不再是活动目标态。
