# 评审意见：对 refact-fable.md 的异议与建议

> 日期：2026-09-05 ｜ 评审者：kimi ｜ 对象：`refact-fable.md`（当日 11:30 修订版，§8 未冻结）
> 性质：评审意见稿，供 fable 处置；按 round-protocol 异议格式组织（条目 + 为什么 + 应当是什么 + 证据）。
> 总体判断：诊断（§1.2/1.4/1.6）与核心抽象（权力表驱动 interrupt、签名回执威胁模型）成立，**方向无异议**。
> 以下 10 条中，D1–D3 为阻断级（不处置则实施路线在中途卡死或自相矛盾），D4–D8 为设计级，D9–D10 为文字级。

## D1（阻断）：GitHub ruleset 可用性是 R1 的隐性前置，未列入任何判据

**为什么错**：A 档方案（§3.11.2 推荐）依赖 GitHub tag protection ruleset 来禁止非所有者账户创建
`confirm/*`、`frozen/*`。但 **ruleset 的 tag 保护在私有仓库上要求 GitHub Team 及以上计划**；
目标仓库 `sunmoonlion/k8s` 若是 free 私有仓库，A 档整体不成立。实施路线中 R3/R4/R5 全部以 R1 为前置，
R1 失败则整条路线停摆——而全方案没有任何一条机械判据验证"ruleset 真的建得起来"。

**应当是什么**：R1 验收增加第 ⓪ 条："在目标仓库实际创建 tag protection ruleset 成功，配置导出留痕"；
并在 §3.11.4 剩余风险表预先登记 fallback：① gitee protected tag 作第二锚（现文只列为"可选"，应升级）；
② 改用"受保护分支上只允许所有者推送的签名 commit"代替 tag。

**证据**：GitHub 官方文档 "About rulesets"——organization 私有仓库的 ruleset 执行需要 Team/Enterprise 计划；
free 私有仓库仅有 branch protection（不含 tag pattern 的推送者限制）。

## D2（阻断）：T0 档的 H1 与 H2 自相矛盾，"全自动小题目"在第一步卡死

**为什么错**：§3.3 权力表 H1（冻结题目）写明可否设默认 = **否**；§3.4 又写 H2 在 T0 且路由 decide 时
可按默认放行；§3.6 写"T0/T1 通常一签两用"。于是 T0 全自动场景下：H2 放行了，工单仍停在 DRAFT，
因为 H1 无人能默认。方案自己论证 R1 必要性的原话是"没有它，R3 的全自动跑不完最后一步"——
而 D2 意味着即使有 R1，T0 也跑不完**第一**步。

**应当是什么**：三选一，需所有者裁定后写入 §3.3/§3.6：
① T0 豁免 H1（题目琐碎、验收即测试，出题/答题同体的风险可承受），权力表加注；
② T0 的 H1 允许随 H2 默认一并放行，落账 `RouteDecision` 中注明；
③ 承认 T0 也需要一次人签，删去"T0 可为零次"（§8 第 5 条随之改）。

**证据**：§3.3 H1 行"可否设默认：否" × §3.4"H2 …只有 H2 在策略明确允许的 T0 场景可以按默认放行"
× §8 第 5 条"T0 可为零次且落账"，三处无法同时成立。

## D3（设计缺陷）：H2"每项已按默认填好，人只改不同意的项"与 P3 冲突，批量盖章风险高于三次 interrupt

**为什么错**：P3（方向不对称）明文"朝省事须人确认；默认值属于省事方向"。§3.6 的 H2 设计
"收件箱里每项都已按默认填好，人只改不同意的项"，等于把省事方向预设为阻力最小路径，
人点一次"无异议"即全部通过。方案批评三次 interrupt 会导致"确认退化成盖章"（§4 引 roadmap），
但单次预填式确认的盖章化门槛**更低**——一次都不用读。

**应当是什么**：H2 收件箱字段分级：
- **无默认、必须显式确认**：执行者名单（arbiter/acceptor）、验收标准逐条、档位；
- 可预填默认：工作区计划、预算窗。
判据化：开工确认的签名 tag 所指向的工单中，无默认字段不得为空（`round-status.py` 可机械判）。

**证据**：§2 P3 行；§3.6"人只改不同意的项"；§4 对原建议"supervisor 规划 list → interrupt"的处置理由
（"避免三次前置 interrupt 导致确认退化成盖章"）——同一理由反向适用于自身。

## D4（设计）："一个内核"需防双向耦合，建议内核按冻结版本引用

**为什么错**：§3.1 要求开发实例与产品实例共用 request-lifecycle.md 的对象名与状态名。
但 request-lifecycle.md 是**产品态**真源，会持续演化；开发实例的工单字段、对照表（§3.9）若跟随其 HEAD，
产品侧每次改内核都会反向冲击开发流程文档与脚本——正是 §1.1 批评的"两个真源"换了一种形态复活。

**应当是什么**：§3.1 补纪律一条：开发实例引用内核的**冻结版本**（如 `request-lifecycle.md @ <commit>` 或版本号），
内核对象名/状态名的修改一律 T2；§3.9 对照表注明所对照的内核版本。

**证据**：§1.1 对"两份同构文档即两个真源"的诊断逻辑，同样适用于"一份演化中文档被两套体系实时引用"。

## D5（设计）：§8 第 1 条禁 "supervisor" 一词，禁不住同义词再生

**为什么错**：判据是"supervisor 一词只出现在词汇对照与历史说明里"，机械可判，好；
但第四套同名物当初就是在"监督器/执行监督/组织者"三个名字之后再生的（§1.2），
coordinator / organizer / dispatcher / orchestrator 都是现成的复活通道。禁词不禁义，判据会空转。

**应当是什么**：改为**禁止词表**机械判定，词表（含 supervisor 及上述同义词）入仓入门禁；
§8 第 1 条改为"禁止词表中任一词不出现在规则句中，词表本身的修改按 T2"。

**证据**：§1.2"每加一层就加一个名字"——历史已证明换名成本为零。

## D6（设计）：`independence` 折算权重无操作定义，裁决仍会靠手感

**为什么错**：§3.2 提出"cross-vendor 一致算独立信号；same-runtime 一致只算一票"。
"只算一票"未定义：N 家 same-runtime 一致是否算 N 票折一？与一家 cross-vendor 带 `file:line` 证据相比谁重？
没有折算表，裁决方遇到"3 家 same-runtime 一致 vs 1 家 cross-vendor 带证据"仍只能拍脑袋，
评审规则的可执行性在最关键的一格断掉。

**应当是什么**：R5 验收增加一条：给出折算表雏形（哪怕粗糙），例如
"same-runtime 组内一致 → 计 1 个独立信号；每个独立信号带取证则权重 ×2；信号数相同则取证优先"。
允许首版粗糙，不允许缺席。

**证据**：§3.2 原文两个句子的语义间隙；`rounds/refact/round.md` U2 只指出问题未给出权重。

## D7（设计）：H 触点疲劳应有观测指标，否则"盖章化"无法被证伪

**为什么错**：方案多处用"确认退化成盖章"批评现状（§4、§3.6），但 A 档下每次 H 回执 =
切到 Windows + pinentry（TTL=0 每次弹）+ push，摩擦不小；人只剩 H1–H7 触点后，
每次触点的疲劳度与敷衍度恰恰是该被观测的。方案对自己不设此观测，"不盖章"就成了信仰而非判据。

**应当是什么**：`rulings.md` 每次 H 回执登记两个观察值：回执耗时（收件箱落盘 → tag 推送）、
回执相对预填值的改动幅度（改了哪几项 / 全未改）。⑦ 清理时汇总。与 §8 行数观察值同款待遇
（可判不代表对，但可观察趋势）。

**证据**：§7 风险表第 2 条已承认"参与感不足"是设计目标；本条要求把代价也量化登记。

## D8（文字级）：`ls-remote` 判 ⑥ 的网络失败语义应写入正文而非风险表

**为什么错**：§3.11.3 判据"受保护远端上是否存在该 tag"依赖网络与 VM 侧凭据；
§3.11.4 只把"GitHub 不可用"列为剩余风险。若 `round-status.py` 在网络失败时返回非零即视为"未确认"，
需要明写 fail-closed，否则实现者可能顺手写成 fail-open（查不到就当没确认的反面）。

**应当是什么**：§3.8 一般化表格的 ⑥ 行补一句："`ls-remote` 失败（网络/凭据/超时）一律判未确认，
退出码区分『查到不存在』与『查询失败』"。

**证据**：§3.11.2 A 档成立条件依赖远端可达；round-protocol 判据纪律要求区分"真的没有"与"没查到"（§3.8 已引用同一原则）。

## D9（文字级）："误签"防护应升格为收件箱必备字段

**为什么错**：§3.11.4 把"签名前收件箱必须列出 tag 将指向的 commit 与其 `git diff --stat`"写在剩余风险的处置列，
意味着它可以被忘掉。这是 A 档下人防误签的**唯一**手段，不应是可选项。

**应当是什么**：§3.4 收件箱格式定义中，凡 H1/H5 类条目，必备字段增加 `target_commit` 与 `diff_stat`；
`round-status.py` 可机械判收件箱条目字段齐全。

**证据**：§3.11.4 风险表第 1 行处置列自身。

## D10（文字级）：R1 验收第 ③ 条的 `rg` 范围应明确列出

**为什么错**："`rg` VM 上无所有者账户凭据"是好判据，但 `rg` 的路径与模式不定，执行者可能只查
`~/.config/gh` 漏掉 `~/.ssh/id_rsa` 之外的 `id_ed25519`、`~/.git-credentials`、环境变量持久化文件
（`~/.bashrc`、`~/.zshrc` 中的 token export）、vscode-server 的凭据存储。

**应当是什么**：R1 验收第 ③ 条改为指向一份入仓的检查清单/脚本（如 `scripts/check-no-owner-creds.sh`），
清单本身按 T2 修改。

**证据**：§3.11.3 第 3 条已枚举部分位置（`~/.config/gh`、`id_rsa`），枚举不全即 P4 所谓"覆盖不全比没有更危险"。
