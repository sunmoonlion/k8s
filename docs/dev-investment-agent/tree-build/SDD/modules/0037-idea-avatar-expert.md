## 二、叫法：三样东西，两个动作

| 叫法 | 是什么 | 能不能改 | 代码里（不改名） |
| --- | --- | --- | --- |
| **创意** | 用户交来的：方法（六问或 skill）、验收用例、同意测试；之后写的补充方法也挂在它下面 | 用户可补充，不能改原文 | `knowbot_request` |
| **分身** | 照创意孵化出来、拿去测的那一个：从开始孵化起就有，一生四段——孵化、核出处、测试、交付；带孵化的产物（现在只有清单）、测试状态、测试中的问题、测试结果、成稿与交回物 | 孵出的清单定了不改；要改就孵化下一个分身 | 孵出后是 `knowbot_draft` 一行；孵化中的另建孵化记录（0029，本版不建表） |
| **专家** | 测试通过、交付到 knowmart 的版本；工作台「请」的就是它 | 只读 | `knowbot` |

- **流转**：创意 → 分身（孵化 → 核出处 → 测试 → 交付）→ 专家；没通过就孵化下一个分身。
- **孵化是分身的第一段，不单独占一栏**（所有者「孵化不需要这个名吧」），但在分身里有自己的一整块，**为将来留好位置**（所有者「建分身将来是一个很大的工程……我们要为将来考虑」）：
  - **现在**：只有「手工孵化」——清单在外面写好，选创意、贴清单、校验（规则出处、补充方法的关口照旧）、孵出。今天孵化一下就完，所以看不到「孵化中」的分身。
  - **将来**（0029）：选孵化方式（手工 / 辅助 / 自动）；出处表；缺口与用户的答复（缺口发到 web端「待我回答」）；清单候选各版（可比较）；工程记录；模型调用记录；状态「孵化中：起草中 → 等用户答 → 等运营核 → 已孵出」。都加进分身的「孵化」这一块，页面结构不再改。
  - **实现边界**：`knowbot_draft` 是孵出后定了不改的清单，孵化过程中的东西放不进去；将来另建「孵化记录」表，孵出时生成 `knowbot_draft` 那一行。本版只在页面、状态与接口形状上留好位置（分身列表与详情按「分身」而不是按「草稿行」组织，状态集合含「孵化中」），不建这张表。
- **为什么叫分身**：分身是用户的一个化身，按他的方法、用他的数据做出来，逻辑是他的（`C-L1`）；一个创意会建好几个去测，「分身」本来就可以有好几个。2026-10-16 至 10-18 文档里的「分身」指的是今天的专家（10-18「都叫专家」取代）；以 2026-10-19 为界，之后的「分身」指测试中的那一版。活文档改到哪份换哪份，历史记录与所有者原话不改。
- **编号**：专家按版本号 1、2、3；分身写「分身 版本号.第几个」，如「分身 1.3」= 第 1 版第 3 个分身（取代「第 1 版 · 第 3 稿」）。
- **代码、表名、接口路径不改名**（`knowbot_request`、`knowbot_draft`、`/knowbot-drafts`）：改名要迁移数据、动两个应用的契约，眼下不值得；词汇表写明对应。新加的页面路径用新叫法：`/ideas`、`/avatars`、`/experts`。
- 取代 `turn/glossary.md`「分身的生长阶段」那张表（种子、孵化、雏形、成品）；`decisions.md` 记一条，写明取代 2026-10-17 那条的叫法部分（孵化的三种方式与孵化记录不变，孵化从「阶段」改为分身的第一段）。
- 界面文字跟着换（两端）：「想法 / 提交一个想法」→「创意 / 提交一个创意」；「专家草稿」→ 三栏；「第 N 稿」→「分身 1.N」；「建草稿 / 建下一稿」→「孵化一个分身 / 孵化下一个分身」（手工孵化：贴清单）；补充的状态「已用进第 N 稿」→「已用进分身 1.N」；补充的提示「我们照着改出下一稿」→「我们照着孵化下一个分身」。「专家」不变。

## 四、web端：同一套外壳，按用户的事来排

和管理端用同一套外壳（左边一级导航、可收起、手机抽屉、右边折叠栏的组件），**但不照搬**：用户要做的事、看的东西、说的话都不同。

### 1. 用户在这里做什么

1. **交创意**：写方法（六问或 skill）、填验收用例、选用哪些数据、同意测试。
2. **答问题**：孵化时我们回问的缺口（将来）、测试中专家停下来问的（判断、开步前的提问）——**最急，要一眼看到**。
3. **看测试结果、读成稿**：验收依据（`C-L3`「结果给用户作验收依据」），不满意就写补充方法。
4. **管自己的数据**：上传、看版本、删；一份数据可被几个创意用。
5. **用专家**：交付了去 knowbench 工作台请。

### 2. 一级导航

```text

待我回答  (n)  全部要我答的问题，按创意分组；数字为 0 时灰

专家           做出来的专家，列表直接写专家名（不叫「我的专家」，所有者 2026-10-18）
```

- 平台的错不让用户背：用例「运行出错」显示为「这次是平台出了错，不是你方法的问题，我们会重测」；原因全文只在管理端。
- 手机：左栏是抽屉；右边折叠栏变成主栏顶上「我的方法与用例」按钮，打开全屏一层。

### 4. 数据从哪来（web 接口，knowlab 自己的，非跨应用契约）

现有 `GET /web/v1/knowbot-requests` 一次回所有创意及其每一稿，不带方法原文、用例、出处、成稿。加：

| 接口 | 回什么 | 鉴权 |
| --- | --- | --- |
| `GET /web/v1/knowbot-requests/{id}` | 这个创意：方法原文、用例、补充、它的分身列表（不带清单原文） | 只认创意的主人，不是就 404 |
| `GET /web/v1/knowbot-drafts/{id}` | 这个分身：状态、测试结果（白话化在前端做）、规则出处（只给 `rule` 与 `ref`，用户的话） | 同上 |
| `GET /web/v1/knowbot-drafts/{id}/outputs` | 每条用例的成稿与各步交回物（第五节） | 同上 |
| `GET /web/v1/knowbots` | 这个用户做出来的专家（由已交付的分身推出：名字、版本、knowmart 编号、交付时间） | 只回自己的 |

管理端另加两个（admin、operator）：`GET /admin/v1/knowbot-drafts/{id}/outputs`（产出，同上形状）、`GET /admin/v1/knowbot-drafts/{id}/manifest`（清单原文，对照材料里只读、可复制）；管理端分身列表加 `delivered_at`。交付时 knowlab 在交付记录里记下交付时间（`delivery.delivered_at`），之前交付的没有。

现有的提交、回答、补充、数据接口不动。

## 五、成稿与交回物带回测试结果

### 1. 谁、什么时候取

| 谁 | 做什么 |
| --- | --- |
| knowbench（测试推进器） | **每条用例跑完、记结果的那一刻**（`KnowbotTestConductor._record`，下一条用例开跑前、整次测试收尾删目录前）取这条用例的产出，存进 `workbench_test_cases.outputs` |
| knowbench 接口 | `GET /internal/v1/knowbot-runtime/test-runs/{run_id}/cases/{case_id}/outputs`（服务身份 `knowbench:testrun`，同现有测试接口） |
| knowlab | 刷新测试结果时，看到某条用例已有结论、本地还没存它的产出，就取一次，存进新表；以后不再取 |

成稿在 `_record` 时取：每条用例的底稿写在自己那一格（`底稿/对话-<编号>/<开始时间>-<专家名>/`，advisor 的 `run_folder`），不会被下一条盖掉；但隔离打开后整次测完目录就删，晚了取不到。（评审前这里写成「用例共用工作区、晚了被下一条盖掉」，不对，Astra 10-19 指出。）

### 2. 取什么

每条用例一份：

```text
{case_id,
 deliverable: {path, text, truncated} | null,   成稿（第 8 步写的 Markdown）
 deliverable_note: 为什么没有成稿 | null,
 steps: [{step_id, title, outcome: accepted | rejected | not_reached,
          artifact: 交回物 JSON | null,          通过的那一版
          returned_raw: 没过那次的交回原文 | null, 只有 rejected 才有
          checks: [{label, pass, detail}] }]}    验收逐条（管理端看；web 只用 pass 与白话原因）
```

- **成稿**：只读这条用例验收时记下了 `workspace_path` 的那份，经会合点请测试电脑上的代理 `fs/readFile` 读；**文件修改时间早于这条用例开始的不认**（同一格里返工、回退时留下的旧文件）。没写、没走到那步、读失败（代理离线、超过上限）都不读，`deliverable_note` 写原因。成稿带 `step_id`（哪一步写的）；超时收尾时取的，`deliverable_note` 写「超时收尾时取的，可能没写完」。
- **交回物**：从工作台的步骤视图（`ExpertDesk.steps(full=True)`，已有）取每步最后一次尝试：通过的取那一版交回物；没过的取最后一次交回的内容与原文（工作台已为排查存着）；没走到的记 `not_reached`。
- **上限**：成稿 20 万字（超了截断、`truncated: true`）；每步交回物序列化后 20 万字节，超了不带、注明原来多大（JSON 截半截没法看）；没过的原文 2 万字（现有 `RAW_CHARS`），超了只留前面；一条用例的产出合计不超过 2 MB（留 64 KB 余量）。合计超了**一级一级让，每级只走一遍**：拿掉最大的几步交回物 → 原文截到 2000 字 → 拿掉原文 → 只留没过的验收 → 成稿截到 2 万字 → 拿掉成稿 → 只留各步结局（评审前是「对半截成稿」的循环，成稿截空了还会转圈，Astra 10-19 第 1 条）。测试电脑上读文件的单次上限是 512 KiB（`MAX_READ_BYTES`），成稿超过就记「成稿太大没取」。
- 取产出出错**不影响**这条用例的结论：结果照记，`outputs` 记 `{error: …}`（白话，不带异常类名）。

### 3. 契约：`knowbot-test-run/v1` 只加不改

- 加一个接口与结果模式 `test-run-case-outputs.schema.json`，真源在 knowlab 的 pydantic（`domain/knowbots/test_run.py`，同 `RunResultV1`），由模型生成，knowbench 的锁 `contracts/knowlab-test-run-lock.json` 跟着更新；两边锁测试都要过。
- 现有 `RunResultV1`、`/test-runs/{id}` 一个字段不动：每次刷新拉的结果仍然小；产出每条用例只取一次。
- knowlab 取产出：运行方自己的 404（`code: not_found`）记「没有产出」；路由不存在的 404（旧版运行方）与不可达一样当暂时取不到，**这一轮就停**，下次刷新再取；回包不合契约、答错用例是确定的错，记下原因不再取。一次刷新最多取 10 条。knowbench 取单条只读那一格，常规列表不带 `outputs` 列。测完的分身在管理端产出那一块点「补取产出」再取（评审 10-19）。

### 4. 存在哪、留多久

| 哪里 | 存什么 | 留多久 |
| --- | --- | --- |
| knowbench `workbench_test_cases.outputs`（新列，JSONB，迁移） | 第 2 节那一份 | 整次测试收尾后 **30 天**清空这一列（测试结果本身照旧留着）；knowlab 一般几分钟内就取走，30 天是给「没人刷新」留的余量 |
| knowlab 新表 `knowbot_test_output`（迁移） | `draft_id`、`run_id`、`case_id`（主键）、`fetched_at`、成稿、各步 JSON | 这个分身**交付、或被下一个分身取代后 90 天**清掉正文、留一句原因（定时任务每小时；所有者 10-19「按建议」） |

knowlab 的新表单独存、不塞进 `knowbot_draft.report`：报告每次刷新整份重写，产出大、只取一次；分开存才好分开鉴权（web 只认主人）。

## 十一、代价

- knowbench：`_record` 里多一次读文件（经会合点，几百毫秒）和一次组装；一列、一个接口、一条清理。
- knowlab：一张表、一个外部调用、四个 web 接口；管理端拆成三页加折叠栏；web端加外壳、六页，是这次最大的一块。
