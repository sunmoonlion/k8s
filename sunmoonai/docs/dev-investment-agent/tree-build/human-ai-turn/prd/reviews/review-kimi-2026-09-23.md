## 一、总体判断（先给结论）

方案的形状我认可：**"两层决策权分配"比"通用/专业路由"更本质**，因为它把分类问题（机器猜你要什么）换成了主权问题（你决定谁来驾驶），后者不需要分类器、不会判错、且天然解释了定价（顾问费 = 替你握方向盘的劳动）。这是这次重构真正的收获。

但我和 Claude 一样认为：**文档把最大的赌注（方法可守）押在最没验证的假设上，又准备先把最重的机器（控制面）造出来**。顺序应该倒过来。在这个大方向上我基本站在 Claude 一边，下面只在几处与他有分歧，并补充他没有充分展开的点。

## 二、逐条回答第五节 12 个问题

### Q1. 两层决策权分配这个产品本质，成立吗？

**成立，且有一个文档没点破的好处：它把"产品的敌人"重新定义了。** 旧定位里敌人是"判错的分类器"；新定位里敌人是"裸 Codex 已经够好"。这更诚实——因为后者才是真实的竞争。value.md 里"去掉知识服务与编排，原版 Codex 能否得到同样结果"的检验，在新定位下自动成为整个产品的主检验，不再需要额外的路由设计来自圆其说。

它遮住的东西有一个：**第一层和第二层之间不是平滑过渡，而是一次信任跳跃**。用户交出驾驶权的那一刻，是他对"我们的顾问比自己开得好"建立信任的瞬间，这个信任只能由第一次求助的结果质量建立。所以**第二层第一次体验的成功率比任何架构指标都重要**，这应直接影响 U7 切口的选择（选最容易做对的场景，而不是最有代表性的）。

### Q2. "方法（编排）是长期主体"同意吗？

**我同意 Claude 的担心，但认为他和文档都漏了一个更关键的变量：方法资产可以守，但守的方式不是"藏起来"，而是"评测闭环"。**

推理：方法被抄走的门槛确实低（owner 自己在 methods.md 里承认了）。但方法论资产的持久性从来不靠保密，靠的是**它比对手更新得快且能证明自己更好**。文档 A12 里写"对比评测所需的领域评测集尚不存在"——这才是要害：**不是方法守不住，是"我们的方法更好"这句话今天没有任何证据载体**。如果评测集和金标准先建起来，方法库每次更新都有回归成绩，那"方法 + 评测"合起来是可守的（对手抄得走方法文本，抄不走持续校准的闭环）；如果评测集不建，方法库只是一堆没人能证伪的文本，确实是最没价值的一源。

**结论：把"方法是不是主体"的争论改写成"评测集什么时候建"。评测集不建，三源里没有一个站得住（数据的独占性也没盘点）；评测集建了，方法才有成为主体的资格。** 这也回答了 Q8 里"什么该留"——对比评测不是验收矩阵里的一条（AT-36），它是产品的地基，应该提到 PRD 第一节。

### Q3. 同一个 Codex 实例、经我们的 runtime 驱动，用户会接受吗？

**Claude 的担心成立，但有一个双方都没展开的中间态：同一实例可以是"同一个后端身份"而不是"同一个前台进程"。**

用户日常照常用他自己的 Codex CLI / Claude Code。我们的 runtime 不作为壳包在前面，而是作为一个**可被挂接的 MCP 服务 + 本机交接代理**：求助动作是用户在自己的 agent 里调一个 `ask_advisor` 工具（或拖一个交接包进我们的窗口）。这样：

- 第一层的上下文本来就在用户的 agent 里，不需要我们持有；
- 交接面（U2）从"接管一个已在跑的会话"简化为"接收一个结构化的求助包"，工程上小一个数量级；
- 引擎中立自动成立，钉死 codex app-server 的风险消失；
- 代价是失去"同一个实例无缝继续"的体验——但这个体验本来就是幻想：即便同一实例，求助时的上下文打包、授权、预算划定一样要做，一样会打断流。

所有者已定的"同一个实例"不必推翻：把它降级为**最优路径**（愿意装我们 runtime 的用户得到无缝交接），显式交接作为保底路径。两条路径共用同一个交接包格式。这正是 Claude 建议 3，我支持，且认为这不与所有者的决定冲突。

### Q4. token 激励错位怎么解？

Claude 的"费用写进评测与标价"是对的，但不够，因为它治的是**事后透明**，治不了**事前激励**。补三条：

1. **按结果计价而非按步骤计价**：专家包的顾问费与"验收通过"绑定，返工不另收费。这样返工的成本由我们内部消化（体现为毛利），我们天然有压力让 workflow 变短。token 仍用户付，但我们若按次包一个 token 上限预估、超出部分明示由谁承担，错位就大部分消除。
2. **workflow 的每一步都要有"省掉它"的弃权证**：编排系统应记录每步的边际贡献（这步删掉，验收成绩掉多少）。没有边际贡献的步骤定期淘汰。这把"变省的压力"变成机制而不是美德。
3. 预算硬顶（RunBudget 四维限额已定义）应该在第一期就接线——它是防止"我们的流程烧用户的钱"失控的唯一硬约束，比事后展示费用重要得多。这与 Claude 建议 5"预算可以晚"**直接冲突，我不同意他这条**：预算恰恰是 token 错位问题里唯一不能晚的部分。

### Q5. "先人肉跑第二层再建控制面"可行吗？

**方向对，但 Claude 的实验设计有两个漏洞，照原样跑会得出假阳性或假阴性：**

1. **幸存者偏差**：挑"两三个分析师给的真实问题"，很可能挑到分析师自己已经知道怎么做的问题——这时顾问驾驶当然赢。应该混入分析师**没做出来过**的问题，且裸 Codex 对照组要用同样的时间预算。判断标准不是"顾问赢不赢"，而是"**顾问赢在哪些子类上**"——大概率会发现赢面集中在数据接入与口径，而不是拆步骤。这个细分结论直接决定专家包第一版该写什么。
2. **扮演者不是真人**：一个人扮顾问驱动 Codex，他同时是方法的作者和执行者，能力被高估；而真实的第二层里方法是别人写的、supervisor 是脚本。缓解办法：方法**先写成文档，由另一个没参与写的人照文档驾驶**。这顺便验证了方法库的可传递性——如果换个人照做就失效，那这套方法脚本化之后也不会有效。

时间上两周偏乐观但数量级对。补充：**这个实验本身就应该用改造后的 human-ai-turn 流程来跑**（每一次求助 = 一个 human-ai-turn 目录），实验过程和实验产物就是 U12 专家包形状的第一手需求来源。造产品的过程和产品是同一条链——文档 2.5 自己说的，这里正好兑现。

### Q6. 切口场景选哪个？

两个候选里我选**财报季/业绩预告的快速覆盖**，理由三条：有天然 deadline（可度量"快"）、有标准答案雏形（一致预期与实际值的差，可度量"准"）、数据需求明确（公告正文 + 历史财务 + 一致预期，正好检验数据盘点）。公告勾稽筛查作为第二个包。

一个文档里没人提的候选：**"会议纪要/路演纪要的结构化入库与问答"**——更高频（每天都在发生）、强依赖私有资料（用户自己的录音/纪要，不出本机的卖点直接兑现）、质量好坏立刻可感。缺点是"专业度"门槛较低，可能撑不起专家包定价。可以作为第一层数据订阅的引流场景而非第二层。

### Q7. 专家是什么（A/B/C）？

同意"A + 真人写包"。但 **B（云端专家 agent）被排除的理由不成立，应该明说为什么缓，而不是排除**。文档里 B 被隐含地并入 A 的"编排"形态，但两者不同：A 是料，B 是脑。真正的顾虑是 B 需要云端调用模型 → token 谁付 → "不垫付 token"这条所有者决定被突破 → 且 B 看到问题正文，信任边界从"只见元数据"退到"看见问题"。所以 B 的准确位置是：**第二层 supervisor 的编排决策本身迟早要由模型做（人写 workflow 的覆盖速度永远不够），那就是 B；它应该被列为"token 模式改变"之后的第二阶段，而不是不存在**。把 B 写进路线图反而保护 A：让 A 的专家包现在就按"将来会被 agent 消费"来设计（结构化、带验收条目），避免以后返工。

### Q8. "保留/退役/新增"表有没有判错的？

三处：

1. **多方竞争（0008）应从"保留"降为"缓建"**。它是优化（择优/择快）不是验证，第一期单 Attempt 即可（Claude 建议 5 这点对）。对象模型留着，机制不做。
2. **预算（RunBudget）应从"可以晚"提前到第一期**，理由见 Q4——它是 token 错位的唯一硬约束。这是我与 Claude 建议 5 的主要分歧：他把"账房 = 状态机 + 事件 + 幂等"三样列为第一期，我改为四样：加预算。预算的实现在投资端已有雏形，成本远低于租约/fencing。
3. **"退役"那条线判得对，但漏了一处连带**：U3（用户怎么知道有专家可问）不是小 UX 问题，它是**旧路由设计退役后留下的获客空洞**。旧设计里每一问都是引流机会；新设计里满意的用户永远不来。这意味着第一层必须有自己的留存与转化设计（使用频率、数据消费深度、失败时刻的识别），建议补一句：第一层埋点记录"用户反复重试/明显不满意"的本地信号，在本机（不调云端）提示专家入口。这把旧路由的获客功能以隐私合规的方式救回来。

### Q9. 上传三级，默认第二级，合理吗？

默认合理，但**"本机摘要"是这份文档里最被低估的信任风险，双方都轻描淡写带过了**。摘要由谁生成？Codex（经用户自选的模型）——也就是说**摘要生成这个动作本身已经把资料内容发给了第三方模型厂商**，trust.md 的口径"不经过我们"在这里成立，但"资料不出本机"在用户的朴素理解里会被打破。二级默认必须在 UX 上说清两件事：摘要经过了你的模型厂商；摘要里可能含资料片段（用户可审阅后再发）。另外摘要一旦发出，后端应把它当"已出域资料"记账（事件留痕），否则 I12/I17 的审计故事在边界上有个洞。

### Q10. 第一层（所有人买数据）能撑起收入吗？

**在数据不独占的前提下，单靠数据撑不起订阅收入——但它不需要撑收入，它需要撑漏斗。** 第一层的正确财务定位是：定价压到"比 Wind 便宜一个数量级 + 与 AI 工作流原生集成（MCP）"的获客价，收入目标只要求覆盖数据成本与浅层毛利，利润指标全部押在第二层转化率（第一层用户 → 年度求助 N 次）和第三层机构。换言之：**第一层是第二层的获客渠道和评测数据来源，把它当利润中心会把它定价定死**。这也意味着数据盘点（U6）要回答的不是"我们的数据值多少钱"，而是"我们的数据能不能把目标人群从裸 Codex 拉进我们的面"——判据不同，盘点的内容也不同。

### Q11. turn 机制改造，有什么问题？

机制本身干净（状态从产物反推、git 即账本），四条补充规则方向对。三个具体问题：

1. **规则 1（AI 答完先提交、人改完再提交）是整个方案的承重墙，但目前只是纪律**。文档自己引用 P5"凡能落成代码的纪律必须落成"——这条可以落：pre-commit 钩子检查 human-ai-turn 目录内文件的 author 交替（AI 提交与人提交不得在目标文件上合并为一次提交）。落不了钩子的部分（人就是会顺手改掉）至少要在 finalize 文档里写明"混提即失去 AI/人分界，该 turn 作废"。
2. **"绝大多数问答不留痕"会丢一类东西：被否掉的方案。** git 记最终状态，不记"为什么没走另一条路"。原 thread 机制意外承担了这个功能。建议在判据表里加一条硬判据：**"凡是'做过选择'的 turn 必须留"**——两个以上可行方案、选了其一的，留。否则半年后同类问题会重新讨论一遍，这正是原机制要防的。
3. imp/uat 子目录"只放问题、答在分支上"与 prd/sdd"答在文件上"不对称，评审者读一个目录时要先知道它属于哪类才能找到答。建议在目录 README 或 user-message.md 头部用 `mode:` 字段明示，门禁可查。

### Q12. 这份讨论最大的盲区是什么？

**竞争面里完全缺席：整个文档没有一处分析"用户的第二层诉求正在被谁接住"。** 而这决定成败，因为第二层不是空白市场：

- 模型厂商自己在做：OpenAI/Anthropic 的 agent 产品每次升级都在内置"拆步骤、给料、验收"能力（今天叫 skills/plugins/projects），Claude 担心 1 的"明年输给裸模型"不是抽象风险，是对方 roadmap 上写着的事；
- 垂直投研 agent 已有人在卖（Hebbia、Rogo、AlphaSense 的 agent 层），它们的选择恰好与本方案**相反**：云端 agent + 云端数据 + 订阅。本方案"本机执行 + 用户 token"是差异化还是劣势，取决于目标客户对"资料不出本机"的支付意愿到底有多强——而文档里这个意愿是假设，没有任何一条访谈或意向证据；
- 因此 U7 之前其实还有 U0：**找 5 个目标用户，把"你的研究资料发给云端模型"和"资料不出本机但你付 token"两个选项放他们面前，听反应**。半天成本，直接检验整个定位的承重墙。D17 法务要看的是合规线，这个是市场线，两者都该在写任何代码之前。

次级盲区两个，一并记录：

- **第二层的服务水平没有定义**：顾问驾驶要多久交回？用户在第一层卡住时等得起吗？如果专家包是异步的（分钟级？小时级？），交接面的 UX 和九站的 deadline 语义（task-contract 已有 requested_deadline）要按这个设计；文档从未讨论时效。
- **专家包的供给端**：让领域专家写包（3.3）意味着要雇/合作真正的资深分析师，这是人力与商业模式问题不是工程问题，文档对"写包的人从哪来、怎么分钱"只字未提，而它决定 U12 的形状（包必须简单到一个非工程师分析师能写）。

## 三、给所有者的行动排序（综合以上）

1. **本周，零开发**：U0 用户访谈（Q12）+ 数据盘点一页纸（U6）+ D17 法务约谈。
2. **两周，零开发**：人肉第二层实验，按 Q5 的修正设计跑，用 human-ai-turn 留全程；产出第一份评测集雏形与专家包需求。
3. **实验结果出来之前，不建控制面**。要建也只建四样：状态机、事件、幂等、**预算**（与 Claude 建议 5 的唯一分歧，见 Q4/Q8）。
4. 交接面按 Q3 设计成"求助包"格式，同一实例为最优路径、显式交接为保底，两者共格式。
5. 把"对比评测 + 评测集"从验收矩阵的一条（AT-36）提升为 PRD 的一等公民（Q2）——**先有金标准，后有方法库，再有机器**。
