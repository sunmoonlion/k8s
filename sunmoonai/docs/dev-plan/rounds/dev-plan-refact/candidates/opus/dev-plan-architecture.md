## 1. 目标架构

### 1.1 推导，不是另立

①a §2.2 的九个阶段，每格产出一类文档；①a §4.3 给每类定了生命周期。
**目录形状由「生命周期规则相同的放一起」决定**——因为决定文档怎么被对待的是规则，不是主题。

```text
dev-plan/
├── README.md                    ENTRY      目录入口
├── handoff.md                   ENTRY      上下文包：AI 冷启动从这里进（§6.8）
├── pipeline.md                  RULE       ← ①a：流程定义本身
├── constraints.md               RULE       跨需求护栏
├── rules/                       RULE       从各处析出的护栏
│   ├── anti-patterns.md                    ← request-lifecycle §10 + agent-dev-guide §11
│   ├── failure-modes.md                    ← agent-dev-guide §12
│   └── delivery.md                         ← implementation-plan「测试层次 / 交付规则」
├── decisions/                              ⚠ 新增目录
│   ├── ADR-0001 … ADR-NNNN.md   ADR        全局单调编号，**只被取代不被修改**
│   └── DEC-0001 … DEC-NNNN.md   DEC        所有者拍板，**追加不改**（①a §4.4）
├── product/                                ⚠ 新增目录：A 线的产物
│   ├── functions.md             REQ        34 个 F-<域>-<号>
│   ├── acceptance.md            AT         AT-01 – AT-22
│   ├── contract/                CONTRACT   对象模型 / 状态机 / I1–I15 / Profile / 编排
│   └── design/                  TLD        运行时结构 / Task 执行 / 人介入 / 可观测性
├── plan/
│   └── implementation-plan.md   WU         阶段与任务条目
├── working/
│   └── request-baseline/        REQ        ⚠ **位置已由所有者定死，不动**（B7）
├── protocol/                    RULE(B)    B 线流程定义 ⚠ **本轮不动**
└── rounds/                      ROUND      轮次归档 ⚠ **本轮不动**（F4）
```

### 1.2 为什么是这几个目录，而不是别的划法

| 目录 | 装的类型 | 它们凭什么在一起 | 为什么不能并进相邻目录 |
| --- | --- | --- | --- |
| 根下四份 | ENTRY · RULE | 冷启动第一眼要看到的 | 埋进子目录就失去入口作用 |
| `rules/` | RULE | 只增不减，减要走 B 线 | 与 `product/` 分开：护栏跨需求长存，产品文档随需求消亡 |
| `decisions/` | ADR · DEC | **写完不改**（ADR 只被取代，DEC 只追加） | 与 `rules/` 分开：规则可修订，决定不可改。合并会让「当时为什么」被后来的修订抹掉 |
| `product/` | REQ · AT · CONTRACT · TLD | 都随某条产品需求生灭 | 与 `plan/` 分开：产品文档描述「是什么」，计划描述「什么时候做」 |
| `plan/` | WU | 每天变 | 与 `product/` 分开，理由同上 |
| `protocol/` | RULE(B) | B 线的流程定义 | ⚠ 与 `rules/` 分开：它约束**决策过程**，不约束产品代码。合并会让「改一条开发纪律」和「改一条决策程序」看起来同等重量，而后者是 T2 |
| `rounds/` | ROUND | 冻结归档 | 不可与任何活文档混放：冻结物的锚按成文时状态解析 |

⚠ **`decisions/` 与 `product/` 是新增的两个目录，其余全部沿用现状。**
新增的理由逐条在上表；沿用的理由在 §6 逐份给出——**不给理由的沿用等于没做这一部分**。

## 2. 归属判据（先于结果）

### 2.1 三问

照搬 ①a §4.2，此处只给可执行形式：

```text
问一  它记的是「人说过什么」，还是「我们算出什么」？
        人说过的 → REQ / DEC / AUDIT（追加不改类）        [终止]
        算出的   → 问二

问二  它会不会因为代码变而**必须**跟着变？
        会 → CONTRACT / 测试（随码类）                     [终止]
        不会 → 问三

问三  它记的是「现在是什么」，还是「当时为什么」？
        当时为什么 → ADR（只被取代不被修改）               [终止]
        现在是什么 → TLD（随需求消亡）/ RULE（跨需求长存）

三问都不终止的，只能是 WU（状态）/ ROUND（轮次产物）/ ENTRY（路标）。
```

## 4. 判据的三处边界（自己指出，不藏）

⚠ 一份声称机械可判的判据，必须自己说清它在哪里不可判。

### 4.1 `protocol/` 落 `RULE` 还是新立一类

三问对 `round-protocol.md` §8「环节判定」跑出的是 `RULE`（算出的→不随码变→现在是什么）。
但它约束的是**决策过程**，不是产品代码——与 `constraints.md` 的「数据/契约/身份/拓扑」不同种。

**本文的处理**：标为 `RULE(B)`，即 `RULE` 的 B 线子类，物理上留在 `protocol/`，不并进 `rules/`。
**代价**：类型表因此有一个带括号的子类，不够干净。
**为什么不新立第 12 类**：新立一类要能说出「它不能并进相邻类的理由」；
而 `RULE(B)` 与 `RULE` 的**生命周期规则完全相同**（只增不减，减要走 B 线），
按 ①a §4.3「生命周期由流程位置决定」，位置不同但规则相同时，子类比新类更诚实。

### 4.2 `development-plan.md` 落 `DEC` 是一个判断，不是计算

三问的问一是「人说过什么」。`development-plan.md` 的四节——不延续 v5、智能体分两部分、
三个阶段、有意留白的两处——**读起来像所有者拍板的方向**，但文中没有署名，
也没有「所有者于某日决定」的形式。

**本文按 `DEC` 处理**，理由：这四节都不是可推导的结论，也不随代码变，更不是「当时为什么」的记录；
它们是**方向选择**，而方向只能由人选。
⚠ **但这一步依赖我对文本语气的判断，不是纯机械。**若所有者认为其中某节是 AI 起草的分析
而非拍板，该节应改判 `TLD`。这是本表中**唯一一处需要所有者确认才能定案**的归属。

### 4.3 `handoff.md` 落 `ENTRY` 与「状态不进仓」冲突

①a §4.3 说 `WU`（状态）「每天变，不保留，**不进仓**」。
`handoff.md` 13 节全是状态：当前阶段、未决项、任务游标、进度。按此它不该在仓里。
