## ② 架构评审

- 结论：**采纳（立项为决策型 REQ）**。目标形态与设计原则即刻生效；能力边界与实施拆分待
  ④ 决策点拍板后转 ADOPTED。

- 理由：

  **investment-app 已有完整的单智能体运行时，缺的只是多智能体那一层。**据 REQ-008 的
  逐条读码取证，现有地基包括：LangGraph + `PostgresSaver` 检查点与 interrupt/resume、
  Run 状态机（七态、四终态不可转出）、`idempotency_key` 幂等建 run、`consume_resume`
  原子消费且永不复用、SSE 先订阅两个 Redis channel 再读 DB 快照回放（避免窗口丢事件）、
  七种 RunEvent 带 discriminator、`tool_side_effects` 副作用记账、
  契约 DTO frozen + extra=forbid + schema sha256 锁。

  **其中四处已强于成熟参考实现**（对照 `note/Codex编排能力完全指南.md` 所述 Codex 编排面）：
  结构化产出（契约锁 vs `outputSchema`）、幂等建任务、恢复令牌的原子消费、
  事件窗口安全性（参考实现无此层考虑；本仓 `agent_routes.py:182-184` 有注释明确记录了
  「先订阅后读快照」的理由）。**因此不照搬其模型**，只取其概念划分与已踩过的坑。

  **预算闸门是一处例外，须先补齐再谈继承。**（2026-08-15 修正）
  `RunBudget` 的四维限额、默认值与超限抛错均已实现于 `domain/agent/runtime.py:62-97`，
  但**两条生产链都不调用它**：全仓 `rg -l RunBudget` 只命中该定义文件与非生产图
  `infrastructure/graph/first_m1_graph.py`（后者仅被 `tests/` 与 `scripts/agent_golden.py` 使用）。
  `budget_exceeded` 这一 run 状态因此在生产中不可达——唯一写入方是 `first_m1_graph.py:36`。
  即：**预算是一个已设计未接线的能力**，不是既有强项。
  此前将其列为「强于参考实现」的判断源自旧 baseline 的错误陈述，已随 REQ-008 一并纠正。

  **缺口集中且可在现有地基上增补**：子 Agent 派生、上下文继承控制、等待语义
  （wait-any / wait-all / quorum）、独立复核、业务 DAG Registry、运行中追加方向（steering）、
  跨 Run 长期目标与验收判据。完整对照表与目标设计见 `baseline.md`。

  **与 REQ-005 是生产关系**：本 REQ 的代码由 REQ-005 的代码开发智能体产出。两者共用
  领域无关的编排内核，工具面与 SOP 分开；自举隔离的权威决策在 REQ-005 ④ D8，本 REQ 引用不复述。

- 冲突与代价对比：

  与现有架构无冲突——本 REQ 是在既有 Agent 域内增补能力，不改变领域所有权与契约边界。
  主要代价在于**多智能体会放大三处既有机制的语义压力**：

  | 机制 | 单智能体下 | 多智能体下 |
  | --- | --- | --- |
  | RunBudget | **当前未接线**，无预算即无上限 | 必须先在单 Run 内生效，再做可继承可分配；否则 fan-out 等于把「无限额」乘以并行度 |
  | `tool_side_effects` | 审计用途 | 成为正确性的一部分：并行分支可能重复触发同一副作用 |
  | cancel | 单 Run 内每步检查 | 须沿父子树传播，否则父终止而子继续 |

  RunBudget 那一行的次序有实际后果：**先接线单 Run 预算，再设计父子语义**。
  反过来做会得到一套无法验证的继承机制——父余额本身不生效时，预扣与退回都无从测起。
  这构成 ④ D2 的前置条件，见 D7。

  维持现状的代价：投资研究任务只能单线推进，无法并行检索、交叉验证、分头起草，
  也无法用独立复核提升结论可信度。

- 边界：本 REQ **不含**代码开发智能体（属 REQ-005），**不含**投影（属 REQ-004）。

## ④ 决策点（待用户拍板）

| 编号 | 决策 | 备选 | 建议 |
| --- | --- | --- | --- |
| D1 | 子 Agent 的承载形式 | 复用 Run（带 `parent_run_id`）/ 另建独立实体 | **复用 Run**：状态机、事件流与 SSE 回放、检查点、cancel 的每步检查全部免费继承（RunBudget 不在此列，它当前未接线，见 ② 修正）；父子关系用物化路径列以支持路径寻址与库内查询 |
| D2 | 预算的父子语义 | 共享池 / 预扣制（派子时从父余额划走，完成时退回） | **预扣制**：共享池在并行下有竞态，且无法保证任何单个子 Run 能跑完；预扣可保证「派出去的每个子 Run 都有确定的完成能力」。此语义在设计期几乎免费，事后改很贵 |
| D3 | 副作用投递语义 | exactly-once / at-least-once + 幂等键去重 | 待议；必须在写第一行编排代码前定死（见 ② 表第二行） |
| D4 | 实施拆分维度 | 按能力（派生 / 等待 / Registry / 复核）/ 按拓扑（先 fan-out 再 DAG） | 按能力，且顺序为：子 Run 派生 → 等待语义 → Registry → 独立复核 |
| D5 | 等待语义的一等原语范围 | 只做 wait-any / wait-any + wait-all / 再加 quorum | wait-any + wait-all 都做成一等原语。参考实现只给 wait-any，代价是调用方自写循环与八目标上限；从零设计无此包袱 |
| D6 | 复核者的上下文继承 | 继承父 Run 历史 / 只给产物与验收标准 | 只给产物与验收标准（等价于上下文不继承）。依据 REQ-002 中 C7 需人工改判的观察，以及「自己不审自己」原则 |
| D7 | 单 Run 预算接线的归属 | 并入本 REQ 的首个实施 / 另立独立实施 REQ / 归入 D4 的第一项 | **归入 D4 顺序之首**：它是 D2 的前置条件，且改动面小（在两条链的每步检查处调 `budget.check()`），不值得单开 REQ；但须在 D2 落地前完成并可测 |
