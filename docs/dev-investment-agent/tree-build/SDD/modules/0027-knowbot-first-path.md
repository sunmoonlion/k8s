## 一、这一项交付什么

一条走得通的最小通路，让「我们自己当普通用户做财务分析与预测分身」（staging 第 3 项）可以在它上面做：

```text
用户（knowlab 网页端）      提交想法（六问或 skill）＋上传数据文件＋验收用例，同意数据用于测试
knowlab 后端               创建专家草稿（调模型生成清单，投资判断的空缺回头问用户，每条规则记出处）—— 草稿存在 knowlab，「待测试」
我们（knowlab 管理端网页）  查看待测试的草稿，核每条规则的出处，核过把测试需求交给管理端后端
knowlab 管理端后端          草稿改「测试中」→ 调 knowbench 工作台按用例跑测试（我们的测试账号、有预算上限与超时）
                           → 通过：提交到 knowmart（用户即可请）；未通过：报告给用户和我们，改好出新草稿再测
用户（knowbench 工作台）   点「请专家」→ 跳到 knowmart「我的分身」选一位 → 跳回工作台，给输入，自己跑；
                           运行时只读他自己上传、绑定在这一版上的数据
```

所有者 2026-10-16 定的流程：knowlab 后端按网页端的请求创建专家；knowlab 管理端（网页＋后端）查看待测试的、交给后端，后端调 knowbench 工作台测试。所有者先说待测试的提交到 knowmart，听了 Opus 的意见后改为**草稿放 knowlab、测试通过才提交到 knowmart**（「同意，放 knowlab」）：草稿、测试、报告、改版都属于创建；knowmart 保持所有读写按所有者过滤、只存能用的版本，持牌后的对外市场里也只有正式发布的。

不在这一项里：工作台撤内置专家包与沙箱默认不接 knowbase（staging 第 4 项）；财务分析与预测专家本身（第 3 项）；knowmart 对外上架（持牌后）；可视化编辑专家。

## 三、契约与接口

### 3.1 专家清单 `knowbot-manifest` v1

- **形状 = 工作台现在的专家包**（`knowbench-backend` `app/domain/workbench/packs.py` 的 `ExpertPack`：六问、步骤契约、验收规则、底稿布局、工具策略），去掉内置专用字段（`internal`），加 `data_bindings`（这一版能读的用户数据：knowlab 的数据集 id + 版本 + sha256）和 `rule_sources`（每条判断规则出自用户原文还是用户确认过的改写，`C-L1`）。
- **schema 真源在 knowmart**（版本的提供方），knowbench 与 knowlab 各持锁文件，同 knowfeed→knowbase 的做法（`contracts/*-provider-lock.json`）。schema 变更走版本号，v1 冻结后只增可选字段。
- **运行方 `runtime`（所有者 2026-10-16：「不要把测试工作写死为investment，因为之后可能还有其它的bot」）**：清单外层必填，写明这个专家在哪个应用里运行（现在只有 `knowbench`）。knowmart 原样存放；「取清单」只给运行方是调用方自己的专家；用户「请专家」的入口在各运行方自己的界面里，从哪个运行方来就只能选运行方是它的专家。
- **P2 实现时细化（2026-10-16）**：清单分两层。外层（`schema: knowbot-manifest/v1`、名字与说明、版本、`data_bindings`、`rule_sources`）归 knowmart，严格校验；`pack`（专家包形状的可执行部分）归执行它的工作台，knowmart 只核骨架（`pack_id`、`version` 等于外层版本、非空 `workflow`），完整形状由工作台按自己的模型校验，免得两处各维护一份执行格式。外层 schema 由 knowmart 后端模型生成，放 `knowmart-app/contracts/knowbot/v1/`（摘要见 `contract-manifest.json`）；JSON Schema 表达不了的跨字段规则以 knowmart 交付时的校验为准。摘要写作 `sha256:<十六进制>`。
- 校验两处做：knowlab 上传时（不合格不让测）、knowmart 登记时（不合格不收）。knowbench 取到后按同一 schema 解析，失败拒绝运行。

### 3.2 接口

| 接口 | 谁调谁 | 身份 | 做什么 |
| --- | --- | --- | --- |
| knowlab → knowmart `POST /api/internal/v1/knowmart/deliveries` | knowlab 后端 | 服务身份 `knowmart:deliver` | 交付一个测试通过的版本：所有者、专家名与说明、清单原文、摘要。幂等键 = knowlab 的交付单 id；同一专家已有该版本号且摘要不同则拒绝 |
| 运行方 → knowmart `GET /api/internal/v1/knowmart/owners/{owner}/knowbots/{id}@{version}` | 运行方后端（现在是 knowbench） | 服务身份 `knowmart:summon`（每个运行方一个调用方，knowmart 认出是谁；只给运行方是它自己的专家） | 取清单原文 + 摘要。**owner 由 knowbench 从已认证的会话里取**，浏览器给不了；owner 不符一律 404（不区分「不存在」与「不是你的」） |
| knowlab 管理端后端 → 运行方 `POST /api/internal/v1/knowbot-runtime/test-runs` | knowlab 后端 | 服务身份 `<运行方>:testrun` | 按草稿的 `runtime` 找到登记的运行方（现在只有 knowbench）。契约 `knowbot-test-run/v1` 由 knowlab 定（真源 `knowlab-app/contracts/`）：请求是草稿清单、验收用例、数据绑定、预算上限、超时；回每条用例的结果（各步验收通过与否、出错处）。运行方在我们的测试账号上无人值守跑；测试跑出的分析内容不给用户，运行方只短期保留（7 天）供排查，到期删除。以后加运行方：实现这个契约、在 knowlab 配置里登记（名字、服务身份、集群内入口），knowlab 代码不改 |
| knowmart 网页端「我的分身」 | 用户 | 用户会话（sunmoonai，单点登录） | 只列本人的专家与版本、停用某一版；从工作台跳来时每位专家多一个「请这位」，点了按服务端登记的回跳目标跳回工作台，带 `knowbot=<id>@<version>` 与原 `ref`（不从链接接受回跳地址，[跨应用跳转规则](../architecture/cross-app-links.md)）；不出现上架、分享、导出、价格（`C-L4`） |
| knowbench 收回跳 | knowbench 后端 | 用户会话 | 拿 `knowbot` 用上一行接口按会话里的 owner 核一次，核过才显示「已选」并允许提交；伪造或别人的专家得到「找不到」 |
| 专家读用户数据（只读，P5 细化见 §3.5） | 沙箱里的专家 → 工作台的工具服务 `sunmoon-workbench` → knowlab `POST /api/internal/v1/knowlab/knowbot-data/{list,read}` | 沙箱到工作台：已有的读记录令牌（绑用户），每次带 `task`；工作台到 knowlab：服务身份 `knowlab:read` | `list_my_data`、`read_my_data`：只能读这件委托所用那一版的 `data_bindings`。工作台按委托核，knowlab 按自己的草稿与交付记录再核一次（契约 `knowbot-data/v1`，真源 `knowlab-app/contracts/`） |

- **跳转与单点登录**：工作台到 knowmart 用现成的 `CrossAppLink`（业务参数 + `from=knowbench` + `ref`）。sunmoonai 组织里 knowbench、knowlab、knowmart 三个网页端应用在 Casdoor 打开「保持登录会话」与「自动登录」，在一处登录后跳到另两处不再输密码；退出登录同时结束 Casdoor 会话（公用电脑上下一位不会以上一位身份进入）。2026-10-16 实验核实（[记录](../../../../../scripts/results/opus-0027-P1b-sso-lab.20261016-1753.md)）：两个开关**都开**才免登（授权请求服务端直接 302 回调）；退出用 `/api/logout` 结束会话并跳回（只跳回登记过的地址）；会话时长由 `app.conf` 的 `sessionCookieLifeTime` 定（默认 30 天；所有者 2026-10-16 定 **12 小时**，即 `43200`，全局生效，管理端登录也一样）；边缘放行清单加 `/api/logout`。退出不存任何令牌：带本面 `client_id` 即可（实验核实 Casdoor 结束会话且只跳回登记过的地址），会话记录里仍不出现 id_token。一处退出只结束 Casdoor 会话，已登录着的其他应用本地会话留到自己过期（最长 1 小时）；全局单点退出见待办账 114。以后对外市场沿用同一套跳转。
- **接收方按「关系 × 调用方」配置**：一种关系可以有多个调用方（「取清单」以后会有多个运行方），接收方的环境变量是 `SERVICE_AUTH_<关系>_<调用方>_*`，外加 `SERVICE_AUTH_<关系>_CALLERS` 列出调用方；校验器按令牌认出调用方，接口据此核运行方。
- **服务身份与内部入口（P1 已实现，未部署）**：knowmart 的内部接口统一在 `/api/internal/v1/knowmart` 下，经 traefik service-access 的内部入口 `knowmart-tls.<命名空间>.svc.cluster.local`（独立证书）。knowlab 的 `service_clients` 有 `knowmart:deliver`，knowbench 有 `knowmart:summon`，knowmart 的 `service_receivers` 接受这两种；应用代码读的环境变量见 `gitops/components/app-platform/common/backend/service-client/README.md`（调用方 `KNOWMART_INTERNAL_URL`、`KNOWMART_<关系>_SERVICE_*`；接收方 `SERVICE_AUTH_<关系>_*`）。knowlab 不持运行令牌公钥（P5 改为经工作台转读，§3.5）。
- **跨应用的用户标识用 Casdoor 用户 id（`sub`）**，三个应用各自的本地 actor id 不出应用（`C-D14`）。
- ~~运行令牌（`aud=knowlab`，knowlab 持 `workbench-signing` 公钥）~~：2026-10-17 P5 细化时改掉，不签运行令牌、knowlab 不持公钥，见 §3.5。

### 3.3 工作台的改动（knowbench）

- 现在 12 处同步调用 `find_pack(profile_id, version)`。改为一个**专家目录端口**：`resolve(owner, id, version)`（内置包另有本地列出）。实现两个来源：内置（只剩机制烟测 `SMOKE` 和过渡期的现有内置包）+ knowmart。
- **请的时候钉死并缓存**：建委托时从 knowmart 取 `id@version` 的清单，原文与摘要存进 knowbench 自己的库（版本不可改写，所以缓存不会过期）；之后编排、底稿、验收全读本地缓存。knowmart 暂时不可用只影响「列出」与「新请」，不影响在跑的委托。
- 委托记录加一列来源（内置 / knowmart）与清单摘要，便于复核。
- **P4 第一部分实现时细化（2026-10-16，已实现未部署）**：钉住发生在**跳回来时**（不是建委托时）：工作台首页收到 `knowbot=<专家>@<版本>`，后端按会话所有者向 knowmart 取清单、核摘要、按 ExpertPack 校验，存进钉表 `workbench_knowbot_pins`（只插不改）；建委托时再把这一版的**专家包快照**与清单摘要写进委托（`pack_source`/`pack_digest`/`pack_snapshot`，数据库约束三者同在），之后编排、底稿、验收、知识库都只读委托上的快照，原来 8 处 `find_pack` 改为同步的 `pack_for_task(task)`，不用把十几处改成异步。knowbot 的专家 id 写作 `knowbot:<专家>@<版本>`，专家列表里带上用户自己钉过的专家（`source=knowbot`），专家入口与会话里的「求助」都能请，别人的一律「没有这位专家」。工作台对 knowbot 的专家包的硬约束：工具与审批只能比平台默认更严、不许自带命令放行前缀、不许用数据线工具（`C-L2`；读用户数据的工具 P5 才有，所以现在专家不能 `requires_tools`）。包里六问的键沿用内置包的中文键（解决什么、不解决什么、输入、输出、谁做判断、失败怎么办），专家卡片才显示得出来。

### 3.4 运行方跑测试（knowbench 实现 `knowbot-test-run/v1`）：方案 A，有人值守

工作台现在的执行是「用户自己的电脑（本地代理，项目文件在那上面）+ 他自己的云端沙箱（Codex）+ 他自己的模型 key（`C-A9`）」，审批与反问都等人答。所有者 2026-10-16 定**方案 A**（真引擎），随后改为**有人值守**（原话：「好像要改成有人值守吧，用户的用例不可能给得那么细啊」）：测试跑到需要人决定的地方就停下等人，在 knowlab 答完接着跑；三条细则「按你的建议」。

| 项 | 定了什么 |
| --- | --- |
| 发起与把关 | 始终在 knowlab 管理端网页：我们的运营核出处、发起测试（预算上限、超时）、看报告；跑的过程不用人盯，只在有问题时回答 |
| 引擎 | 真引擎：同一个 runner、Advisor、验收，测的就是用户以后跑的那条路 |
| 账号与电脑 | 我们的一个**测试账号**；集群里常驻一台「测试电脑」（本地代理装在容器里跑，项目目录在它自己的卷上，只配对给测试账号） |
| 沙箱与 key | 测试账号自己的沙箱，用**kimi 的模型 key**（在本地机，P6 放私有目录与 SOPS；所有者：「kimi没有模型选择，它默认就是kimi3」，所以只配接入地址与 key、不配模型名，接入地址 P6 时在本地机用这把 key 实测确定）；每月测试费用上限 **1000 元**；每次测试的预算上限由 knowlab 发起时给，按用例平分，超了这条用例记 `error` |
| 一次测试怎么跑 | 每条用例在测试电脑上建一个临时项目，用草稿的专家包快照建委托（`pack_source=knowlab-test`，不进钉表、不进用户的专家清单），runner 照常驱动 |
| 遇到要人决定的地方 | 工作台照常生成「待人回答」的交互；测试模式下不等测试账号在工作台里答，而是把它作为**待回答的问题**报给 knowlab（状态 `waiting`）。开步前的提问（`ask_before`）先用用例里预给的答案，没有才问。验收不过、返工用完要交人的那种不问：这条用例记 `failed`（不能让人在测试里把不合格放过去） |
| 谁来答（`C-L1`） | **工具审批、跑法层面**的问题（能不能执行这条命令、读哪个文件）由我们的运营在**管理端网页**答；**投资判断**的问题转给**用户本人**，在 knowlab 网页端「我在做的分身」里答；归哪一类由运营判断，拿不准的一律转给用户 |
| 等人的时间 | 不计入测试超时；最长等 **3 天**，过了没人答，这条用例记 `needs_human` |
| 答过的记下来 | 答案记回这条用例的预设答案（标明用户答的还是运营答的），重测不再问；用户答的方法判断作为规则出处（`user_confirmed`）写进下一版草稿 |
| 结果 | 每步验收通过与否、没过的验收名；末尾按用例的期望（`Expectation`：交回物 + 点号路径 + 等于/约等于/包含）核最后的交回物；整次 `passed` 当且仅当每条用例都 `passed`；不回任何分析内容 |
| 读用户数据 | P5（§3.5）：测试的委托经工作台转读，knowlab 核这次测试正在跑、只开这一版 `data_bindings`（用户提交时已同意用于测试）。P5 之前先测不读数据的专家（所有者「要」） |
| 产出与保留 | 临时项目、委托、交回物 7 天后由定时任务删除（项目目录一起删）；只留测试结果（就是回给 knowlab 的那份） |
| 并发与超时 | 一次只跑一个测试（测试电脑一台）；knowlab 给的超时（不含等人的时间）到了 → `timeout`，停掉在跑的委托 |

契约 `knowbot-test-run/v1` 相应加：状态 `waiting`（非终态）与结果里的待回答问题（问题 id、用例、步骤、种类 `tool_approval`/`question`/`ask_before`、问题原文与选项、提出时间）；请求里的最长等待 `max_wait_seconds`（默认 3 天）；回答接口 `POST /api/internal/v1/knowbot-runtime/test-runs/{run_id}/answers`（同一个问题 id 重复回答：内容相同回原状态，不同则 409）。v1 还没部署，直接改 v1。

**实现到哪（2026-10-17 凌晨，已写未部署）**：

### 3.5 专家运行时读用户数据（P5，2026-10-17 细化）

原设计是沙箱另配一个 knowlab 的 MCP，凭工作台按委托签的运行令牌直接读。细化时改为**经工作台已有的工具服务转读**，理由有四条：
- **委托一结束就读不到**。工作台每次调用都按委托现查，比等令牌过期、或 knowlab 回头查工作台都更及时，也省了一条 knowlab → 工作台的服务关系。
- **沙箱不多开网络出口**，碰不到 knowlab。
- **不多一种令牌**，knowlab 也不用持工作台的公钥。
- **委托令牌没地方放**。沙箱的工具配置按用户、在拉起时就定了；按委托签的令牌只能塞进每步说明，那样会进模型上下文。

**怎么读**：
- 工具：工作台的工具服务 `sunmoon-workbench` 加两个工具，`list_my_data(task)` 与 `read_my_data(task, dataset, page)`。沙箱里已经配好这个服务，令牌绑用户。
- **工作台这道核**：委托属于令牌里的用户、没到终态、是会话当前在做的那件（同读项目记录）；委托的专家是 knowbot 或测试中的草稿。数据要在这一版清单的 `data_bindings` 里：专家看钉表里的清单，测试看测试请求里的清单。核过后，用服务身份 `knowlab:read`（调用方 knowbench）调 knowlab，用途写明是哪一种：
  - 专家：`{"kind": "knowbot", "owner": <Casdoor id>, "knowbot": <id>, "version": <版本>, "digest": <清单摘要>}`
  - 测试：`{"kind": "test", "run_id": <测试编号>}`
- **knowlab 这道核**：调用方必须是这份草稿登记的运行方。专家：所有者是 owner、已交付、交付记录里的专家 id、版本、摘要都对得上。测试：这次测试正在跑（`testing`），`run_id` 一致。数据要在这一版清单的绑定里、属于草稿所有者、没删、sha256 一致。不符一律 404，不区分「没有」与「不是你的」。
- **读出来是文字**：CSV、TXT、MD 原样；Excel 每张表转成 CSV；PDF 逐页抽文字（扫描件抽不出字，就说没有可读文字）。按页给，每页最多 20000 字，带出处 `{dataset_id, version, sha256, page, pages}`。抽出的文字最多 500 万字，超出截断并说明。抽取结果按 sha256 在 knowlab 进程里缓存。解析在 knowlab 后端进程里做，有字数与单元格上限（同 knowfeed 解析公开 PDF 的做法）。
- **专家能用的工具**只有这两个；`requires_tools`（用平台的数据）对专家仍然不许（`C-L2`）。每步说明里，委托的专家有数据绑定时，加一段「用户的数据」，写明这两个工具和 `task`。
- **不做**：图片识别；写数据；把原文件放进沙箱。

## 四、状态与不变量

| 不变量 | 强制点 |
| --- | --- |
| 专家只归一个所有者，只能被所有者请 | knowmart 每个接口按 owner 过滤；knowbench 只用会话里的 `sub` 作 owner；没有「按 id 不带 owner」的接口 |
| 版本不可改写 | knowmart 版本表只插不改；同 `id@version` 摘要不同的交付拒绝；knowbench 缓存按摘要校验 |
| 在跑的委托不受新版本、停用影响 | 委托钉死 `id@version@摘要`，读本地缓存；停用只拦「新请」 |
| 运行时只读这一版绑定的、本人的数据 | 令牌里列数据集；knowlab 验签 + 核数据归属 + 核委托未到终态 |
| 只有测试通过的版本能被用户「请」 | 草稿在 knowlab：待测试 → 测试中 → 测试通过（交付 knowmart）/ 测试未通过；「测试中」超时管理端可退回待测试。只有测试通过的才交付，knowmart 里只有能用的版本（另有用户自己的「已停用」） |
| 测试前核过规则出处 | knowlab 管理端发起测试前必须逐条核过规则出处（用户原文或用户确认的改写），未核过的草稿不能发起测试（`C-L1`） |
| 测试读用户数据有授权 | 用户提交时明确同意用于测试；测试令牌只开放这一版绑定的数据集 |
| 测试报告只说运行正确与否 | 报告结构里没有收益、胜率、评级类字段（`C-L5`） |

## 五、失败与恢复

| 失败 | 结果 | 恢复 |
| --- | --- | --- |
| knowlab 交付时 knowmart 不可用或超时 | 交付单停在「已验收」，记失败原因 | 重试同一幂等键；knowmart 已收则返回原结果 |
| knowmart 收到但 knowlab 没收到回执 | 下次重试拿到同一结果 | 幂等键保证不重复登记 |
| 工作台列专家时 knowmart 不可用 | 「我的分身」显示暂时取不到，内置的照常 | 无需补偿 |
| 请的时候清单校验失败 | 拒绝建委托，提示联系我们 | knowlab 重新交付修正版本（新版本号） |
| 运行中 knowlab 数据服务不可用 | 该步按现有「工具失败」规则处理（重试 / 问用户） | 无需补偿 |
| 用户删除了被已交付版本绑定的数据 | 不允许：先停用引用它的版本 | — |

## 六、威胁与越权

| 威胁 | 后果 | 强制点 |
| --- | --- | --- |
| 浏览器伪造 owner 或回跳参数，拿别人的专家 | 泄露、冒用别人的方法 | owner 只来自服务端会话；knowmart 网页端只列本人的；回跳的 `knowbot` 由 knowbench 后端按会话 owner 向 knowmart 核验；knowmart 只接受服务身份调用 internal |
| 单点登录会话留在公用电脑 | 下一位以上一位身份进入 | 退出登录同时结束 Casdoor 会话；会话时长按 Casdoor 设置 |
| 一个应用的服务身份被盗 | 能以任意 owner 查 | 服务身份按关系分（deliver / summon 各一个 client 与 scope）；内部网络策略只放行 knowlab、knowbench 到 knowmart |
| 专家清单里夹带越权工具 | 运行时越权 | 工具策略沿用现有「只能比平台更严」的校验；清单解析失败拒绝运行 |
| 专家读别人的或没绑定的数据 | 越权读数据 | 两道核：工作台按委托（属于令牌里的用户、没到终态、是会话当前在做的那件）和这一版清单的绑定核；knowlab 按草稿与交付记录核（所有者、版本、摘要、绑定、调用方是登记的运行方）。委托一到终态工作台就不再转发，不靠令牌过期（§3.5） |
| 我们的工程化偷偷加了投资判断 | 违反 `C-L1` | 清单带 `rule_sources`；受理时缺的判断回头问用户；管理端抽查 |
