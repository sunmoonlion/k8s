## 5. 裁决：选 luna 为基座

`[静态判断]`

**选定 luna（分支 `luna`，blob `13347913`，909 行）为整合基座。** 理由按权重：

1. **正确性最高且被实物证实**：本轮的核心教训是"产出物怎样才不被覆盖"。luna §0.4 给的
   判定条件（独立 worktree 改同一相对路径=安全；共用物理工作树=必须 owner namespace）
   是四份里唯一**精确**的表述，且 `[运行过]` 被现场（三份同名共存）证实。cursor 说对了同一
   件事但没给出"何时安全/何时必须降级"的精确边界；kimi 与本人在这一点上或偏移或说错。
2. **完整性最高，最贴合用户"写全/场景很多分别处理"的要求**：用户在触发本轮的请求里明确
   "注意这非常重要，场景很多，分别处理"。luna §7 用状态机 + 九载体 + 25 场景 + 发布协议 +
   8 步事故 + 保留/GC 把"产出物全生命周期"覆盖到四份里最全，且**唯一堵住了发布期竞争**（§7.7 CAS）。
3. **外部一致性最干净**：`[运行过]` luna 引用的权威文件全部存在，不像 cursor/本人挂了
   `collaboration.md`+`doc-conventions.md` 两条坏链，也不像 kimi 删了 `constraints.md`。
4. **忠实于人↔agent 对照**：§0.3 supervisor 等位（"协调职责等同，不表示系统授权相同"）+
   §11 带"共同不变量"列的对照表，既满足用户"人和 agent 中 supervisor 地位等同"的口径，
   又没有把"等同"误用成"授权相同"。

**cursor 紧随其后（17.5），是可执行性冠军**：若团队更看重"当下就能照做的 dev 侧 runbook"、
且能接受较轻的篇幅，cursor 是并列第一梯队的基座。本裁决选 luna 而非 cursor，是因为用户本轮
的显式要求偏向"全盘、写全、场景分别处理"，luna 的覆盖面与隔离理论精度更契合；cursor 的
可执行性优势通过 §6.2 的 Mode E 整合并入 luna，不必二选一。
