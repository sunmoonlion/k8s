# 用户给自己的专家补充方法（0035）

> 状态：**已发版**（qwen-014，2026-10-19；knowlab 迁移头 `20261019_0008`）。第一条补充 sig-am 已写（`e6df96db…`），第 3 稿引它。Opus 2026-10-19 起草；所有者「好，先写补充方法和引文核的设计」；审过三处（写下不能删、按「这一稿」挡、引文一字不差）：「三处都同意，开始写代码」。排在 K19 第 2 稿 c2、c3 跑完之后、建第 3 稿之前，和 [0036 引文核](0036-quote-check.md) 一起做。
> 起因：K19 第 2 稿测试中，所有者看了第 6 步「对照官方披露」，要换成拿分析结论对管理层讨论（[`总纲/数据拓扑.md`](../../../总纲/数据拓扑.md) §十之一）。这是方法上的改动，按 `C-L1` 要由用户本人说出来才能进规则出处；web端没有地方说。所有者问「用户改方法指的啥」，Opus 答「看了测试结果，想换掉某一步的做法」，所有者「好」。

## 一、要解决什么

用户的方法现在只有两个来处（0027）：

| 来处 | 在哪说 | 进规则出处时 |
| --- | --- | --- |
| 提交的想法（六问或 skill） | web端「提交一个想法」 | `user_text` |
| 测试中答专家的提问 | web端「需要我回答的问题」 | `user_confirmed`（运营答的不算） |

缺的是第三种：**用户看了测试结果，要改已有专家的某一步**。专家不会来问（它不知道用户想换思路），也不是新想法。现在只能用户在对话里告诉我们、我们照着改，规则出处只能写「Opus 转述」，系统里拿不出用户的原话（第 2 稿的出处里「2026-10-18 所有者答 G7」这类就是这样来的）。

决定记录 10-16 已定方向：「改方法回 knowlab 出新版本」（`decisions.md`）。本页补的是**用户在哪说、说的话怎么成为出处、我们怎么保证不漏掉**。

## 二、做法

### 1. 谁做什么

| 谁 | 做什么 | 不做什么 |
| --- | --- | --- |
| 用户（web端） | 对自己的某个想法写一段「补充方法」：哪一步、改成什么、为什么 | 不改已提交的原文；不直接改清单 |
| 运营 admin（管理端） | 照补充改出下一稿，规则出处指向这条补充；照不了的写理由「不照做」 | 不替用户补没说的判断；说得不清就「不照做」并写明要用户说清什么 |
| knowlab 后端 | 存补充；建草稿时核出处里引的补充是这个想法的；核对出处时挡住还没处理的补充 | 不判断补充的内容对不对 |

补充随时可以提，测试中也可以；不影响正在跑的那一次，进下一稿。

### 2. 数据

knowlab 新表 `knowbot_amendment`（一条补充一行，迁移 `20261019_0008`）：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID |
| `request_id` | 属于哪个想法 |
| `owner_subject` | 谁写的，必须是这个想法的所有者 |
| `text` | 用户的原话，1–4000 字；**写下后不改、不删**（证据，保留期同想法本身） |
| `created_at` | 提交时间 |
| `declined_reason`、`declined_by`、`declined_at` | 运营「不照做」时填，理由 1–500 字，用户看得到 |

一个想法最多 200 条补充。要撤回，用户再写一条（「第 3 条不要了」），运营把旧的那条「不照做」，理由写「被第 4 条取代」。

### 3. 补充怎么进规则出处

- 出处的来源仍写 **`user_text`**：补充就是用户的原话，和想法原文是同一种出处。`ref` 以 `amendment:<补充 id>` 开头，后面可以跟原话片段，如 `amendment:3f…：「拿分析结论对管理层讨论」`。
- **建草稿时核**（`add_draft`，程序挡）：凡是 `ref` 以 `amendment:` 开头的，那个 id 必须是这个想法的补充、没被「不照做」。对不上就是 `manifest_invalid`。
- knowmart 的清单契约 `knowbot/v1` 不动（来源仍只有 `user_text`、`user_confirmed` 两种）。

### 4. 状态（从记录推，不另存，P2）

| 用户看到的 | 怎么推 |
| --- | --- |
| 待处理 | 没被「不照做」，也没有哪一稿的出处引它 |
| 已用进第 N 稿 | 第 N 稿清单的 `rule_sources` 里有 `amendment:<它的 id>`（取最新一稿） |
| 没照做：理由 | 有 `declined_at` |

**最新一稿还引着的**不能「不照做」；更早的稿引过、用户又写了新补充撤回它的，最新一稿不引它了就可以不照做（理由写被哪条取代；审读 10-19，所有者「按建议」）。被「不照做」的不能再被引。

### 5. 不漏掉的强制点

**核对出处（`review_rules`）时程序挡**：这个想法里，在这一稿建之前提交的补充，每一条要么被**这一稿**的出处引了，要么已「不照做」；还有没处理的，核对出处返回冲突 `amendments_open`，列出是哪几条，测试发不起来（发起测试本来就要先核过出处）。

- 按「这一稿」算，不按「哪一稿引过」算：上一稿用了、这一稿丢了，同样挡住，免得改版时把用户的补充悄悄丢掉。
- 这一稿建好之后才提交的补充不挡这一稿，进下一稿；管理端在草稿卡上标「有 N 条新补充，下一稿处理」。

### 6. 界面

**web端**「我提交的想法」，每个想法下：

- 按钮「补充方法」，打开输入框，提示：「写你要怎么改：哪一步、改成什么、为什么。只写方法，不用写技术细节。我们照着改出下一稿，再测试。写下后不能改，要撤回就再写一条。」
- 补充列表：时间、原话、状态（待处理 / 已用进第 N 稿 / 没照做：理由）。

**管理端**想法详情与草稿卡：

- 列出这个想法的补充和状态；待处理的有「不照做」按钮（只有 admin，填理由）。
- 核对出处那一步，有待处理的补充时按钮不可点，旁边写「先处理这几条补充：用进这一稿的出处，或写理由不照做」。

### 7. 接口（knowlab 自己的 web、admin 接口，不是跨应用契约）

| 接口 | 谁调 | 说明 |
| --- | --- | --- |
| `POST /api/web/v1/knowbot-requests/{request_id}/amendments` | 用户 | 只能给自己的想法加；别人的、不存在的一律 404 |
| `GET /api/web/v1/knowbot-requests` | 用户 | 现有接口，每个想法带上它的补充与状态 |
| `GET /api/admin/v1/knowbot-requests/{request_id}` | 运营 | 现有接口，带上补充与状态 |
| `POST /api/admin/v1/knowbot-amendments/{amendment_id}/decline` | admin | 填理由；已被引的、已不照做的返回冲突 |
| `POST /api/admin/v1/knowbot-drafts/{draft_id}/rules-review` | admin | 现有接口，加第 5 条的挡 |

### 8. 越权与失败

- 用户只能给自己的想法写补充（按 `owner_subject` 核，不符一律 404，不区分「没有」与「不是你的」）。
- 运营不能替用户写补充：接口只在 web 面、只认用户本人的会话。
- 补充内容涉及买卖建议、目标价这类（`C-L1`、0026 第三节口径）：运营「不照做」并写明理由；平台不提供这类模板这条不变。
- 提交失败（库写不进）：返回错误、什么都没记，用户重提；同一段话提两次就是两条，运营把重复的「不照做」，理由「重复」。

## 三、取舍

| 路 | 为什么不选 |
| --- | --- |
| 出处新增来源 `user_amendment` | 要改 knowmart 已冻结的 `knowbot/v1`（改冻结契约要单独的修订单元），而补充本来就是用户原话，`user_text` 已经说得对；区别靠 `ref` 的 `amendment:` 前缀就够 |
| 让用户直接改想法原文 | 第 1 稿据以建成的原文就没了，「这一稿出自哪段话」查不回去 |
| 走测试中的问题 | 问题只在测试跑着时、由专家提出；用户想改的时候往往没有测试在跑，专家也不会问 |
| 运营把用户在对话里说的话录进系统 | 那仍是运营写的，不是用户本人的会话写的，正是现在缺的那一环 |
| 补充自动生成新草稿 | 改清单是工程化（我们的活），要人做、要核；自动生成就成了模型替用户补方法（0026 第五节第 8 条风险） |

## 四、这一版不做

- 补充的来回讨论（运营问、用户答）：先用「不照做 + 写明要说清什么」→ 用户再写一条，够用；量大了再做对话。
- 已交付专家的改版收费、通知：随 knowmart 改版流程再定。
- 「原话核对」（0029 §6.3，程序核 `user_text` 引的原话逐字出现在来处）：随孵化 S4 做；做的时候把补充原文算进来处。
- 旧出处不回填：第 2 稿之前写的「所有者答 G7」这类照旧保留、标旧格式，不改写成 `amendment:`（没有用户本人写下的记录可指）。

## 五、测试

knowlab 后端：

1. 用户给自己的想法加补充，列表里出现、状态待处理；给别人的想法加、给不存在的想法加，都是 404。
2. 文字为空、超 4000 字、超 200 条，拒。
3. 建草稿：出处引了本想法的补充，过；引了别的想法的、不存在的、已不照做的，`manifest_invalid`。
4. 核对出处：建稿前提交的补充没被这一稿引、也没不照做，`amendments_open` 并列出 id；引了或不照做后，过。
5. 上一稿引过、这一稿没引，照样挡。
6. 建稿之后才提交的补充不挡这一稿。
7. 不照做：已被引的、已不照做的，冲突；运营角色（非 admin）调，拒。
8. 状态推得对：待处理 → 已用进第 N 稿（N 取最新引它的那一稿）；不照做显示理由。

web端、管理端：组件测试覆盖补充的提交、列表、状态三种显示；管理端「不照做」要填理由、核对出处按钮在有待处理补充时不可点；中英文案齐。
