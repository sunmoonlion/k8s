## A 自述：我的候选提出了什么、放弃了什么

### A.1 流程结构（`pipeline.md`）

我的 ①a 把一条需求从提出到上线拆成 **7 个顺序阶段 + 1 条横切的协作协议（X1）**：

- S1 意图冻结、S2 技术设计、S3 任务规划、S4 实现、S5 验证、S6 发布、S7 运行与学习；
- X1 协作协议横切所有阶段，规定多 Agent 如何并行、评审与裁决。

每个阶段必须同时回答 **产出什么 / 存在哪 / 凭什么算过关**；否则只是一段时间。在此之上给出 DoR/DoD 两张门清单，并按“机器执行”与“靠纪律执行”分栏。

文档类型从阶段推导：REQ、TLD、ADR、CONTRACT、IMPL、HANDBOOK、PROTOCOL、RUN、STATUS、INDEX，共 10 类。每类给出了谁能改、能否被取代、旧版怎么办。

### A.2 260 节安置（`dev-plan-architecture.md`）

我的 ①b 用 9 条判据（A–I）把 260 节落进 10 类文档：

- `working/request-lifecycle.md` 整体作为 REQ，但标注其中 6 节含有 TLD 成分，本轮不物理拆分；
- `agent-dev-guide.md` 的 §2（运行时结构）迁出为 TLD，§8/§10 作为 ADR 归档，其余留在 HANDBOOK；
- `protocol/` 归为 PROTOCOL（横切协作协议），不是实施计划的一部分；
- `constraints.md` 归为 RUN；`handoff.md` 归为 STATUS；`README.md` 归为 INDEX。

对 Q1/Q2/Q3/Q6/Q8/Q9 给出了回答；B2 锚点保全方案是“不移动、不拆分内核文件，先用落点表标类型”。

### A.3 未验证的断言（标 ⚠）

- B2 中“71 个带行号锚点 / 40 份引用”我没有独立复测，直接采信了任务书数字；
- 其他候选的 `doc-gate.py` 结果我没有在自己的工作区复跑；
- 对 `agent-dev-guide.md` 各节的“内容”判断主要基于标题，没有逐字重读 3082 行。

### A.4 故意放弃的内容及理由

- **没有拆 `request-lifecycle.md`**：理由在 B2 保守性；我把它整体留在 REQ，宁可承认混装也不冒险断锚。
- **没有新增 `DEC` 类**：我把所有者拍板映射进了 ADR / STATUS，没有为“轮外决定”单开一类。
- **没有新建目录**：只建议在现有文件内重新归属，物理迁移留给后续工作单元。
- **没有把测试先行独立成阶段**：我认为测试是 S1 验收契约的可执行形式，放在 S4 实现前即可。

## C 评优：按 J1–J7 逐条比较、排序与基座选择

### C.1 比较方法论

我按任务书 §6.2 的 J1–J7 比较，事实题优先引用候选自身给出的 `file:line` 或可复跑命令，不靠“大家都说”。每家强项与缺陷并列，避免只列优点或只列缺点。

### C.2 opus

**强项**

- **J1 完整性最饱满**：9 个 A 线阶段 + B 线决策流水线，阶段、门、文档类型、生命周期、判据归属、AI 前提六项齐全；还把 B 线明确定位为 A 线阶段 3 的“被调用子例程”。
- **J2 推导关系最清晰**：在“文档类型从阶段推导”上给出可机械执行的三问判据（`opus-pipeline.md` 第 4 节），然后在 `dev-plan-architecture.md` 用“默认规则 + 8 条例外 + 260 行落点表”落实。
- **J3 判据先于结果**：三问在落点表之前完整给出；例外表逐条说明理由；§4 还主动指出三处自己跑出犹豫的边界。
- **J4/J5 内部结构与拆并代价**：§6 逐份文档论证内部结构，§5 给出迁移顺序和锚点保全，§9 登记发现并按 B3 处理。
- **J6 B2 最深入**：没有采信任务书“71 锚点 / 40 引用”的概括，而是自己实测并区分归档锚、钉 commit 锚、裸行号锚，指出真正会断的只有 **2 处**，据此给出可执行的拆分方案（`opus-dev-plan-architecture.md` §5.2–5.3）。
- **J7 Q 题回答最有增量**：新增 `DEC` 类回答 Q8（轮外决定落点），给出全局 ADR 编号方案回答 Q9。

**缺陷**

- **方案较重**：新建 `product/`、`decisions/`、`rules/` 三个目录，迁移步数多；若裁决方希望本轮只定方向、不落地大搬迁，opus 的基座会显得激进。
- **`development-plan.md` 全归 `DEC` 依赖语气判断**：opus 自己也承认这是 260 行中唯一需要所有者确认才能定案的归属（`opus-dev-plan-architecture.md` §4.2）。
- **9 阶段 vs 7 阶段**：把“测试先行”独立为阶段 5，与实现分离角色，逻辑上成立，但也让阶段表变厚；与现有 `protocol/` 的 T2 七环节不是同构，需要读者再学一套编号。

### C.3 cursor

**强项**

- **J1 完整性同样饱满**：常驻面 + 9 个阶段 + G1/G2 两道总门；12 类文档每类都给出“缺了它哪个阶段没过关物”的推导。
- **J2/J3 推导与判据**：§1.1 的 C-* 类型判据和 §1.2 的阶段判据先于落点表；§4 用“为什么不并进邻居”逐类辩护，避免类型膨胀无据。
- **J4/J5**：§2 逐份文档论证内部结构，§3 给出拆并代价；对 `request-lifecycle.md` 选择“类型上承认条款种类、物理上保持一份”的保守方案，代价写得诚实。
- **J6 B2 保守可执行**：不移动内核文件，只加投影页和 ID 锚，风险最低。
- **J7 Q8 有具体增量**：提出 `working/traces/<change-id>/` 作为不走轮次工作的证据袋，填补了其他几家只命名未给路径的空白。

**缺陷**

- **12 类略显臃肿**：索引（Index）类的存在理由只是“承认 `README.md` 的实际职责”，与操作手册（Operator）合并也未尝不可；Evidence、Status 两类虽然给出理由，但会让新读者一开始面对较多概念。
- **没有独立复测 B2 锚点数字**：cursor 直接采信任务书“71 锚点 / 40 引用”，不像 opus 那样用实测降低风险。
- **`protocol/` 定位为“常驻面”与 cursor 自己的任务计划之间**：虽然论证充分，但没有像 opus 那样把 B 线单独拎成“决策流水线”，与 A 线的调用关系表达得更弱。

### C.4 luna

**强项**

- **J1 阶段最贴近产品交付**：S0 受理 → S6 运行验收，每阶段都有明确的退出条件与返工入口；DEV/G0–G6 的门把“发布”与“运行后接收”分开，避免“部署成功 = 需求完成”的幻觉。
- **J2 推导与阶段-产物对应**：用“阶段交接问题”推导需要什么文档，逻辑上最贴近“一条需求怎么走完”。
- **J4 有机融合最激进也最有料**：把 `agent-dev-guide.md` 的运行时结构拆成 `design/runtime-tld.md`、`design/executor-sdd.md`、`design/authority-sdd.md`、`design/evidence-sdd.md`，每份目标文档都有栏目、顺序和来源 ID；这是真正把内容“长进架构”。
- **J5 拆并代价完整**：§四 用表格逐条写收益与维护代价，并主动声明“没有重新声称 294 行全部正文验过”。
- **J7 Q9 工具化**：在 `dev-plan-architecture.md` 里内嵌可执行的 Python 工具，能按冻结 commit 枚举 `rulings.md`、渲染目标文档，这是本轮唯一的“判据即命令”雏形。

**缺陷**

- **可能超出本轮范围**：luna 的架构几乎是一份完整的新目录树（新增 design/*、delivery/*、records/*），本轮任务是“提出结构并融合”，不是“写出可渲染的新正文”。工具代码 733 行里占了大量篇幅，可能把“架构候选”做成了“实现候选”。
- **机械可判性弱于 opus**：落点表用 I02-xxx 等 ID，但没有像 opus 那样给出“任意一行复算”的机械判据；内部结构靠“回测”论证，回测本身依赖对正文语气的判断。
- **B2 处理最安全但也最保守**：luna 选择完全不移动 `request-lifecycle.md`，这确实零风险，但也放弃了对“三份文档焊在一起”问题的任何物理解决。
- **部分归属可争议**：把 `README.md` 两节放进 `records/development-history.md` 作为“旧版入口与组织上下文”，更像归档而不是入口；把 `agent-dev-guide.md` 大量操作内容留在 guide，却把结构设计迁出，读者路径变化大。

### C.5 kimi

**强项**

- **J1 完整性**：6 阶段 + 3 条横切线，11 类文档，判据归属表与 AI 前提齐全。
- **J2/J3 判据优雅**：用 A–K 11 个槽 + P-投影 / P-自描 / P-轮属 三条通用判据，落点前先给规则；这是除 opus 三问外最可复算的方案。

- **J7 Q9 给出决定索引**：`rounds/decisions-index.md` 并给出机器可检规则（ID 唯一、指针存在），比 opus 更具体。

**缺陷**

## D 值得吸收进基座的具体主张

### D.1 从 cursor 吸收

1. **Q8 非轮次证据袋路径**：`working/traces/<change-id>/`（`cursor-pipeline.md` 第 9 节）。opus 只命名了 `DEC` 类但没有给出轮外取证的物理槽；cursor 的路径具体、可复跑、只追加，应补进基座的 S4/S5 阶段说明。
2. **“常驻面”概念与 G1/G2 总门**：cursor 把 `constraints.md` / `protocol/` / `agent-dev-guide.md` 作为“每次 Change 都踩着走的操作系统”，并用 G1/G2 两道总门统摄 T0/T1/T2。这比 opus 的 9 阶段表更便于读者把档位当成参数而不是另一套流程。
3. **保守的 `request-lifecycle.md` 处理**：cursor 主张“类型上承认条款种类、物理上保持一份”。如果裁决方认为 opus 的拆分仍然太激进，可以退到 cursor 方案：原文件保留为产品合同，内部用 C-CONTRACT-* 标注条款种类。

### D.2 从 luna 吸收

1. **S0–S6 阶段与发布/运行验收分离**：luna 把 S5（发布准入与执行）和 S6（运行验收与维护接续）分开，并给出 DEV/G5/G6 的退出条件。opus 的 9 阶段表把“发布”与“运行学习”放在阶段 9，可以借鉴 luna 的拆分让发布与运行验收不混为一步。
2. **把 `agent-dev-guide.md` 的运行时结构拆成 SDD 子文档**：luna 的 `design/executor-sdd.md`、`design/authority-sdd.md`、`design/evidence-sdd.md` 把“当前在做的”从操作手册里彻底拔出。opus 虽然把 guide §2–§7 归到 `product/design/`，但没有像 luna 那样按接口/授权/证据进一步细分；吸收这一点可以提高 TLD 的可维护性。
3. **阶段交接问题的表述方式**：luna 用“S1→S2：哪个系统设计能履行合同”这样的问题来推导产物，比单纯列阶段更贴近“门回答什么问题”。可以补进 opus 的阶段表作为每列的导语。

### D.3 从 kimi 吸收

1. **P-投影 / P-自描 / P-轮属 三条通用判据**：kim 的这三条比 opus 的三问更擅长处理“同一节跨两个槽”的边界情况（如 `handoff.md` 的“不能倒退的输入”是决定的投影）。可以补进 opus 的“默认规则 + 例外”之前作为通用过滤器。
2. **`handoff.md` 的“文档面待办”迁到 `implementation-plan.md`**：kimi 的判断准确——待办是未派工任务，不是状态。opus 把 `handoff.md` 全归 `ENTRY`，没有单独处理这节；应吸收。
3. **决定索引文件 `rounds/decisions-index.md`**：kim 给出的机器可检规则（ID 唯一、指针存在）比 opus 的“全局 ADR 编号”更具体；Q9 最终方案可以合并 opus 的全局编号与 kim 的索引文件设计。

### D.4 从 qwen（自己）吸收

自己的候选亮点较弱，但有一条可以补进基座：

- **X1 协作协议作为横切阶段**：opus 把 B 线定位为 A 线的“被调用子例程”，但没有显式用“横切”这个词。qwen 的 X1 表达可以强化“协作协议不是任何单一阶段的产物”这一点，减少读者把 protocol 归到实施计划或操作手册的误解。

## 结论
