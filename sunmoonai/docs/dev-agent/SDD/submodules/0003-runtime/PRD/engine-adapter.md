# 引擎适配边界

> 依据：产品合同附录 A 的 `D28`。驱动方式见 [`codex.md`](codex.md)，通道见
> [`channels.md`](../../../architecture/channels.md)。

**runtime 用 TypeScript**，作为独立后台进程运行，**不依附桌面窗口生命周期**。

## 核心保持引擎中立

引擎专属的协议与类型**只出现在适配器里**，不得泄漏到 runtime 核心、桌面公共契约或后端。
核心要隔离这五处差异：

| 隔离什么 | 为什么 |
| --- | --- |
| 会话与 Attempt 的 ID 映射 | 我们的 Task 与 Attempt id 不等于引擎的 thread/session id |
| 审批 | 授权规则由 runtime 定；适配器只负责接收引擎请求、回送决定 |
| 取消 | 见下「取消是三态」 |
| 事件与结果的格式 | 转成我们自己的进度、产物与证据格式 |
| 能力差异 | 见下「能力探针探行为」 |

## 取消是三态，不是一个布尔

必须分开表达，**不得合并成一个成功标志**：

| 态 | 含义 | 怎么证明（首个适配器 = `codex app-server`） |
| --- | --- | --- |
| 收到取消请求 | 引擎确认收到 | `turn/interrupt` 的应答 |
| 引擎停止 | 引擎自己的执行循环已停 | `turn/completed`，turn 结束为 interrupted |
| **副作用执行已停止** | 已启动的命令、子进程都已终止，不再写文件 | **两条同时成立**：①本 turn 全部 `CommandExecution` / `FileChange` item 已到终态；②**Codex 所在进程组已空**（OS 层核实，不依赖协议）。细则见 [`codex.md`](codex.md) |

只有第三态成立，才能对外说「取消完成」。

⚠ **第三态还有第四种可能：无法确认。**协议看不见的副作用——最典型的是
**已经发出去的模型 API 请求**——两条判据都覆盖不到。
这种情况**报「无法确认」，不报「已停止」**；把「没查到」写成「没有」是本仓反复点名的那类错。
适配器的取消接口因此返回的是**四取一**：收到／引擎已停／副作用已停止／无法确认，
**不得合并成一个成功标志**。

⚠ **「进程组已空」这条要求引擎能被放进我们控制的进程组里。**
换引擎时这是必检的一条能力（见下「能力探针」）：起不进独立进程组的引擎，
第三态只能靠协议事件，覆盖面随之缩小——这要在接入前写清楚，不能等出事才发现。

## 能力探针探行为，不探接口形状

不要求引擎有同名方法，要求这些行为成立：

| 要求的行为 | 不要求的形状 |
| --- | --- |
| 取消后的状态与**副作用边界可确认** | 有没有 `turn_interrupt()` |
| **每个命令与文件改动都有可观测的终态** | 叫 `item/completed` 还是别的 |
| **引擎能被起在我们控制的进程组里**，取消后可核实该组已空 | 用 job object 还是 cgroup |
| 一次执行的**输入、输出、证据可归属** | 是不是同一种 thread/turn id |
| **未经授权的操作确实不能执行** | 审批消息格式长什么样 |

⚠ **探针要探的是覆盖范围，不是「有没有这个事件」。**实测教训：
`codex app-server` 有 `process/exited`，看形状像「子进程退出的统一观测点」，
按名字列探针会直接判通过；读源码才知道它只覆盖客户端自己 `process/spawn` 起的进程，
turn 内命令一条都不产生这个通知。**「有这个事件」与「它覆盖我要管的那些动作」是两件事**，
探针必须问后者。

照接口形状列探针，得到的只是「把 Codex 的接口换了一套名字」。

**必要能力未通过验证时，不得启用依赖该能力的执行路径，不得静默降级**（`C-A7`）。

**准入以能力探针为准，不以项目名为准。**某引擎当前不满足则不启用；**换钉版须重跑探针**，
不得沿用历史结论，也不得给某个项目贴永久标签。

## 首个适配器：`codex app-server`

- 经 **stdio** 接入钉版 `codex app-server`，用官方生成的 TypeScript 类型与 JSON Schema，
  **不自行逆向报文**；
- **不为它新增本地 TCP 端口**——官方的 WebSocket 传输标为实验性，本机子进程集成没有用它的理由；
- **只实现产品需要的接口**，不复制一整套通用 SDK。直连协议意味着接手了 SDK 的一部分工作：
  请求与响应关联、服务端发起的审批请求、超时与断连、并发消息与事件分发、协议版本变化。

## 验证分两层

| 层 | 验什么 | 怎么验 |
| --- | --- | --- |
| 消息结构 | 报文形状、字段、枚举 | 对着官方生成的 TS 类型与 JSON Schema 做回归 |
| **行为** | 审批拒绝、断连、取消竞争、残留进程 | **另有集成测试**；类型回归代替不了 |

⚠ **Windows 宿主、安装、恢复与升级须经实际安装包验证。**Node 宿主怎么起——复用 Electron
可执行文件，还是单独分发一份 Node——**未定**，见 [`device.md`](device.md)。
