# 通用 Agent 程序化协作与评优协议（草案）

日期：2026-09-12  
拟议协议标识：`agent-general/0.1-draft`  
状态：设计草案，未生效；不代表适配器、状态推进器或浏览器审批已经实现。

本稿按用户要求改造 原 Luna 多方竞争草案 `competition-protocol-draft-luna.md`（2026-09-15 已删除，原文见提交 `0fba800d`），原文保持不动。改造对象是**产品中通用 Agent 路线的程序化协作**，不是在本次对话中启动一次多方竞争，也不自动取代现行研发协作规范 [competition-protocol.md](../../../dev-agent-task/composition/protocol/competition-protocol.md)。

专业自建路线使用同目录的 `competition-protocol-draft-luna-agent-pro.md`，不继承本稿的参与方数量与逐阶段人工审核默认值。两份协议共享产品基础契约，不是两套产品运行时。

## 1. 范围与架构位置

```text
浏览器 / Electron
    → 受信应用入口 → 现有顶层 Supervisor
        ├── 通用路线 → 本协议的协作编排 → 外部 Agent 适配器
        └── 专业路线 → 自建专业 Agent → 专业协议
```

顶层 Supervisor 负责分类、澄清、分派与任务协调，不亲自实现所有专业方法。通用路线可以调用 Codex 等现成智能体；本文不宣称任何具体产品的 SDK 已满足所需接口。

必须区分以下职责，允许在一个 Backend 代码库内按模块或运行角色实现，不因名称不同就拆成独立微服务：

| 职责 | 负责 | 不拥有的权力 |
| --- | --- | --- |
| 顶层 Supervisor | 形成并执行合法路由、连接用户任务与能力 | 不因路由扩大权限，不默认担任评优者 |
| 协作编排器 | 派工、检查阶段条件、收件、恢复、预算与停止 | 不凭模型文本认定用户已批准 |
| 外部 Agent | 在角色和权限范围内产出方案或意见 | 不改变判据，不直接宣布父 Task 成功 |
| 校验 / 验收组件 | 检查完整性、固定判据、证据及交付条件 | 不因验收通过授予新的执行权限 |
| 有权主体 | 按身份和策略批准、拒绝、撤销、追加预算 | 不通过聊天中的模糊措辞隐式扩大授权 |
| 执行 / 发布组件 | 执行已获授权且符合前置条件的动作 | 不把内容认可当成推送、删除或发布许可 |

**云端与客户本机从设计之初就是两种目标宿主，先完成云端只是交付顺序。** 界面、Runtime 位置、工具位置分别绑定；Electron 不意味着所有外部 Agent 必然本机可用。

## 2. 权威边界与产品对象

产品对象、Task / Attempt 合法状态、Interaction 原子恢复及结果交付，以 [请求生命周期合同](../../../dev-agent-task/composition/request-lifecycle.md) 为准；实现与约束按 [开发指导](../../../dev-agent-task/composition/agent-dev-guide.md) 和 [constraints](../../../dev-agent-task/composition/constraints.md) 处理。

| 本协议概念 | 对应产品对象或记录 |
| --- | --- |
| 用户要求得到最终方案 | 一个业务 Task，完成条件包含综合与所需验收 |
| 一次多方竞争 | 该 Task 下版本化的竞争契约和阶段记录，不是新增 Task 状态机 |
| 一个候选、评优、建言或综合角色的工作 | 可独立验收的子 Task；其重试使用新 Attempt |
| 方案、意见、差异、验证输出 | 不可变版本的 Artifact |
| 等人审核、补充信息或授权 | Interaction；影响相应 Task / Attempt 的等待状态 |
| 派工、收件、换人、阶段完成 | 受信事件及其可重建投影 |
| 应用补丁、推送、发送、删除 | Side Effect，单独登记意图、授权与回执 |

候选子 Task 成功只表示候选按其交付契约产出，不等于方案已经成为最终结果。比较多个候选时，不把它们建成同一候选 Task 的竞争重试 Attempt，否则“第一个成功就停止其余尝试”会提前终止比较。

如采用产品 `COORDINATION` Task，它只建立并验收依赖图，图完成后关闭；业务父 Task 等待候选和综合结果。不得用一个永远不结束的协调 Task 同时充当依赖真源、角色执行者和最终结果所有者。

本文中的字段和枚举是拟议逻辑契约，不是已经发布的 API schema。实施时由实际能力提供方维护唯一 schema 真源，消费方锁定版本；不得把本稿复制成另一份 DTO 真源。

## 3. 从人工投喂到程序化执行的改变

| 原草案做法 | 本稿的产品化替代 |
| --- | --- |
| 人复制任务、切换窗口、催交 | 编排器发送结构化任务包，适配器返回收件与执行事实 |
| tmux pane 作为投递位置 | 经认证并登记能力的执行器、会话与 Attempt 绑定 |
| Git 作者字段和人的审批分支 | 认证主体、授权服务、Interaction 与不可变审批记录 |
| 以分支文件和提交反推全部运行状态 | 产品持久账本与受信事件；Git 仅用于适用的代码产物 |
| 每个角色都必须有 Git 分支 | 每个角色独占输出命名空间；需要代码隔离时才建工作区 / worktree |
| 人负责传递上下游版本 | 自动组装固定 Artifact 引用，接收端校验摘要、权限和版本 |
| 人工观察窗口推断进度 | 结构化收件、执行、心跳、等待与结果记录 |

程序化不等于取消人工权力。保留判据先冻结、产出与审批分离、发布单独授权、未响应不等于同意等原则。

## 4. 执行形态与开始竞争的契约

### 4.1 形态

| 形态 | 用途 | 必须明确的限制 |
| --- | --- | --- |
| `single` | 一个外部 Agent 完成任务，再按契约验收 | 不宣称经过方案评优 |
| `review` | 已有一个固定方案，由另一角色审阅 | 不冒充多候选比较 |
| `compare` | 至少两个有效独立候选，依次评优、建言、综合 | 候选不足不能静默降成单稿通过 |

形态在受理阶段按已获批准的 Task Profile 和用户选择固定，不由执行 Agent 为减少工作私自降低。若尚无适用策略，先发 Interaction 明确，不能用未审批默认值消除既有人工门。

### 4.2 开始竞争前必须固定

竞争契约是 Artifact，至少包含：

```text
task_id, competition_id, protocol_id, protocol_version
task_profile_id/version, original_request_ref
normalized_goal, included_scope, excluded_scope
public_inputs[]: artifact_id, version, digest, access_scope
criteria[]: criterion_id, hard_or_preference, evidence_required
output_contract, partial_result_policy
execution_mode, role_assignments[], independence_policy
approval_policy_ref/version, approver_bindings
budget_policy, deadline_policy, retry_and_repair_limits
runtime_host, execution_environments[], workspace_bindings[]
allowed_tools, data_egress_policy, side_effect_scope
publication_targets[], expected_target_versions
```

身份、租户与可用授权来自受信入口，不采信模型或前端自报。协议、Profile、判据、公共输入与权限在首个候选启动前固定；引用的材料必须可取得、可验证且有权读取。

正文格式错误、版本未知、输入缺失、身份不符或必要能力未经验证，均不能派工。策略的批准来源必须独立于候选作者，不能由候选文件宣称自己获准。

## 5. 执行器能力与身份

适配器应提供或组合出：启动、查询状态、读取事件、获取产物，以及当前任务必需的暂停、审批转交、恢复、取消能力。接口具体名称不在此冻结。

登记区分三种状态：已验证支持、已验证不支持、未验证。只有当前任务必需能力全部满足，才可进入自动派工集合；“能聊天”不能证明“能受控执行”。

必要的能力声明包括：

- 可运行的宿主与操作系统、版本、认证方式和授权条件。
- 事件续传、执行状态查询、持久恢复与产物导出范围。
- 外部 Agent 原生工具与平台工具的实际执行位置、权限和审计覆盖。
- 原生审批能否映射为产品 Interaction，以及何种动作无法映射。
- 取消是停止进程、停止后续步骤，还是仅拒绝结果；不能混称。

若必需审批只能在外部 Agent 自己的界面处理，该动作不得伪装成已接通浏览器审批：可以限制为只读路径，或提供明确的人工接管并标记自动化缺口。不能默认批准，也不能用模拟回车、复制会话文本来冒充正式适配。

凭据通过受保护引用注入，不进入任务正文。执行器身份、Agent Profile、模型配置、角色实例和 Attempt 分别记录；不同窗口不自动成为不同助手，不同助手也不证明底层模型不同。

## 6. 角色分派与独立性

`compare` 的角色包括候选作者、评优者、至少一个建言者和一个综合者；编排器管理这些角色，不生成自己的偏好结论后再批准它。

默认保留原草案的分离原则：

1. 候选来自至少两个不同登记助手身份；未满足时不能声明符合此默认比较策略。
2. 顶层 Supervisor / 编排中的判断性出题执行者不兼任本次评优者。
3. 评优者与综合者不由同一登记助手身份承担。
4. 综合者兼任基座作者时，必须在角色策略或当前 Interaction 中明确获准。
5. 允许的其他兼任必须登记；评优自选、建言自处置须显式披露。

以上是本协议的默认策略，不是产品内核固定人数。需要不同角色结构时，在开始竞争前选用另外明确批准的策略，留下差异；不能通过更名绕过限制。

即使登记助手不同，仍要记录已知模型与上下文关联。无法验证模型来源时标记未验证，不宣传多模型独立性。若仅使用同一模型的多个会话，必须明示这一事实，并由所选策略决定是否允许该级别的评审，不假装满足更强独立性。

候选阶段使用相同公共输入，各候选看不到其他候选及评审意见。技术隔离需要资源访问控制、凭据、文件挂载及会话边界；只有目录约定时必须标记为约定隔离，不能承接要求强隔离的任务。

## 7. 阶段推进与产物

`phase` 只描述竞争内部进度；Task 仍使用产品合同状态，不新增“竞选中”等顶层状态。

| 阶段 | 必需产物 | 推进条件 |
| --- | --- | --- |
| 准备 | 固定契约、有效分派、授权、能力与输入校验 | 所有开始竞争的门都满足 |
| 竞选 | 各角色方案、判据对应、证据、假设、未完成项 | 必交角色交付有效；完成适用审核；有效候选至少两份 |
| 评优 | 对全部有效候选的逐项比较、基座引用或全部不合格结论 | 判据与输入未变，角色合法，适用审核通过 |
| 建言 | 唯一编号的建议、来源版本、理由；无建议也有审阅范围 | 所有必交建言可追溯，适用审核通过 |
| 综合 | 最终候选、差异、逐条处置、验证结果 | 所有编号有处置，新内容有依据，最终版本验收与适用审核通过 |

没有有效候选时，按冻结策略修订、补充输入或停止；禁止必须挑出一个“最好”的不合格答案。

评优不靠篇幅、模型名或票数替代理由。硬要求失败不能用偏好高分抵消；未知与失败分开记录，但未知也不自动算通过。

建议须绑定不可变来源片段，综合稿逐条列出采纳、部分采纳或拒绝的理由和落点。可合并重复意见，但原编号不消失。综合者自行新增的实质内容也要接受验收。

综合阶段内必须对最终版本重新执行必要检查，不继承旧候选的测试结果；这不是默认增加一次 Agent 辩论。需要新的判断性复核时，须由冻结策略明确角色、预算与停止条件。

## 8. 人工审核、执行授权与自动推进

### 8.1 三种记录不能混用

| 记录 | 回答的问题 | 产生者 |
| --- | --- | --- |
| 质量评审 | 哪些判据满足、哪些不足 | 校验器、评审 Agent 或专业审核者 |
| 内容批准 | 当前固定产物是否被有权主体接受 | 所选审批策略指定的主体 |
| 执行授权 | 是否允许对特定目标执行特定动作 | 有权主体或其已批准的窄权限策略 |

默认 `stage-review` 保留原草案的逐阶段人工审核；区别是通过产品 Interaction 接收决定，而非要求人复制材料、提交审批 Git 分支。

产品可另行配置已批准的 `policy-gated` 策略，使低风险内部步骤在校验后自动推进；它必须明确可自动放行的阶段和范围，以及仍要求人的节点。本文提出这一机制，不表示已经获得启用授权。系统放行记录写明策略来源，不能伪造为“人刚刚同意”。

任务明确要求逐阶段人审时，不得中途改为自动推进。无响应、模型自述、通知送达和页面已打开都不构成批准。

### 8.2 审批对象与恢复

Interaction 至少关联产品要求的 Task、恢复目标和状态版本，并绑定：

```text
competition_id, phase, role_instance_id
artifact_id/version/digest, manifest_ref, upstream_versions[]
decision_scope, action_digest, target_and_expected_version
principal_binding, policy_ref/version, expires_at
supersedes_decision_id, idempotency_key
```

用户看到的正文、差异和执行对象必须来自同一固定快照。批准内容与批准发布即使在一个页面提交，也要分别记录范围；界面不能默认为两者同时勾选。

云端由后端验证会话、资源所有权、租户、Origin / CSRF 及权限；本机由受保护的宿主授权入口校验本地主体、调用来源和能力。浏览器、服务、设备身份不能互换，Agent 进程不能持有用户批准凭据。

接收响应时原子完成去重、有效期和版本校验、消费 Interaction、持久化恢复意图。重复同一响应可返回已记录结果，但不得再次恢复；同一键不同内容、过期或跨任务响应拒绝。

输入修订、目标版本变化或原批准被撤销时，旧批准不能作用于新对象。已发生动作无法通过删审批记录撤销，须另走补偿或修正动作。

## 9. 程序派工、收件与可靠恢复

派工包引用固定的竞争契约，至少携带 Task / 子 Task / Attempt、角色、执行器绑定、输入版本、能力范围、预算、deadline、执行环境、输出契约、命令幂等键与租约代次。正文不携带服务密钥。

```text
持久化派工意图及 Outbox
    → 投递到目标适配器
    → 幂等接收并持久化 → accepted
    → 获得有效租约并执行 → started / progress / interaction
    → 固定产物并回传
    → 受信侧校验、接受结果及记账
    → 提交阶段事实 → 派发下一阶段
```

传输确认、适配器收件、执行完成、产物验收及父 Task 完成是不同事实。一个接收 ACK 不能使阶段通过。

结构化事件只保证消息形状，不自动证明工具确实运行；工具回执和产物来源要记录是受信采集、外部自报还是未能核实。外部结果中的指令按不可信内容处理，不能据此改变权限、角色或协议。

重试复用稳定业务操作标识；新的获准执行尝试使用新的 Attempt。崩溃窗口内副作用是否已发生不明时，先对账，不盲重跑。失去租约的旧执行者不能提交新结果；阻止实际文件写入还需要执行端互斥、能力撤销和进程控制，不能只靠数据库 fencing。

Outbox 消费必须包含幂等、死信、重放和周期性对账。多副本连接路由只能是临时状态，任务与阶段事实不只存在连接进程内存中。

## 10. 超时、失败、换人和停止

开始竞争时的策略分别定义收件超时、有效执行预算、无进度告警、人工等待、依赖等待和整个 Task 的最长存续时间。暂停哪些计时、重试哪些故障、何时转人工都在开始竞争前固定，不能事后凑出排除某份候选的规则。

心跳只说明进程或连接状态；CPU、文件大小不变不证明执行者没有工作。原草案同侪中位数观察窗可作为诊断参考，不再默认作为产品自动退出的依据。

| 情况 | 处理 |
| --- | --- |
| 投递是否成功不明 | 查询适配器收件 / 执行记录，不盲目另开会话 |
| 候选超时、拒绝或失败 | 按预批准策略记录退出、重试或替补；不记录为同意 |
| 剩余有效候选少于两个 | 阻塞比较，获准补足或按策略失败，不静默降档 |
| 评优 / 综合角色不可用 | 只从获准替补集合选择，并重验冲突；否则询问有权主体 |
| 对评优结论不满意 | 保存理由，按复核或新任务规则处理；不换裁判刷到满意 |
| 人工审核超时 | 按 Profile 关闭、继续等待或失败；绝不超时自动批准 |
| 用户取消 | 先记取消意图，停止新派工，收敛在途执行与副作用，再提交终态 |

并行角色仍可推进时，父 Task 不因某个角色等审批就全部进入 WAITING；等待事实记录到相应子 Task / Attempt。预算覆盖全部候选、评优、建言、综合、重试、工具及子任务，不能用多角色放大额度。

## 11. 版本、修订与无效化

工作草稿不覆盖已提交快照。修订生成新 Artifact 版本，记录替代对象、修改原因、上游依赖及新验收。

已被采用的上游产物被撤销或替换后，阻止受影响下游继续推进；下游即使正文不变，也须重新确认依赖并取得适用的审核。无关的新草稿不会自动使旧批准失效。

候选互相公开后产生的新候选不得被记为原来的独立竞选结果。保留原竞争的记录并另开一次竞争的记录；若改变用户目标、判据、公共输入范围、授权或其他已冻结 Task 合同，按产品合同新建有关联的新 Task，不原地改题。

仅在冻结任务允许的修订范围内修复产物时，可以保留父 Task 并创建新的角色 Attempt / 子 Task；记录修订次数上限。上限耗尽后转人工或按契约失败，不无限循环。

## 12. 工作区、执行环境与交付

工作区是权限、资源和产物边界，不等于必须使用 Git。纯文本方案可使用 Artifact 空间；修改仓库时才采用合适的独占工作区 / worktree。不同目录不是充分的安全隔离。

资源绑定必须包含 `runtime_host + device/environment + workspace + relative_path`。多目录逐项授权，不自动提升成整个用户目录；候选默认不直接修改用户原文件、共享发布路径或主分支。

本地 Runner 默认主动出站连接；WSS 或获准的 HTTPS 兼容通道只是传输，不决定角色和权限。本机 Runtime 调本机工具不必经云端转发。CLI 与沙箱分别表示调用方式和隔离方式。

共享目标只有一个获准执行者；执行前复核当前授权、源 Artifact 摘要和目标预期版本。写入完成但回执丢失时先查实际效果；不可逆、无法查证的动作保留待核实记录，不能承诺任意外部副作用严格执行一次。

完成条件以 Task 合同为准：若只要求交付方案，固定方案和验收可完成 Task；若要求应用修改或发布，相应 Side Effect 必须满足回执条件后才能成功。已批准、已应用、已发布不能混称。

先持久化结果再通知。浏览器 / Electron 刷新后可重取状态、快照与结果；通知失败独立重试。文件访问和产物下载每次复核权限。

清理只处理明确授权、无活跃引用的临时资源，保留可恢复证据；不默认删除原文件、主线历史、用户仓库或尚有在途执行的工作区。

## 13. 云端 / 本机兼容与约束自检

云端使用现有 PostgreSQL 权威账本；Runner 本地日志只承担接收、执行与回执恢复。本机 Runtime 拥有本机运行所需持久事实，云端同步是另外的交付能力，不双写同一个可变主档。

一个运行固定权威宿主；跨宿主迁移不在首版承诺中。本机仍调用云端模型或知识服务时如实声明联网依赖，不宣称完全离线。

| 约束 | 本稿处理 |
| --- | --- |
| D1–D4、D9 | 单一权威、领域归属、不跨库读写、不共享目录充当交换协议、前端不持后端凭据 |

## 14. 验收矩阵与生效门

以下是待实现验收要求，本次写文档没有执行这些运行测试。每项须登记实现所有者、代码位置、测试入口、证据与覆盖缺口。

| ID | 场景 | 必须证明 |
| --- | --- | --- |
| GG-01 | single / review / compare 路由 | 固定模式，轻模式不冒充完整评优 |
| GG-02 | 外部 Agent 必要能力不支持或未知 | 自动派工被拒绝，不能静默自动批准 |
| GG-03 | 重复命令及同键异载荷 | 无重复执行；冲突明确拒收 |
| GG-04 | 发出任务或收件后崩溃 | 可查询、恢复、对账，ACK 不当完成 |
| GG-05 | 候选越权读取其他方案 | 强隔离模式下实际拒绝；弱模式如实标注且不承接强隔离任务 |
| GG-06 | 角色兼任与身份别名 | 冲突可判；不能换窗口伪造独立身份 |
| GG-07 | 空名单、候选不足、全部不合格 | 不因空集合聚合或强制排名而通过 |
| GG-08 | 同模型、未知模型来源 | 独立性声明准确，策略不满足则阻塞 |
| GG-09 | 评优忽略候选、建议漏项、综合新增错误 | 覆盖与最终版本验收能够拒收 |
| GG-10 | 浏览器刷新、重复 / 过期审批、串租户响应 | 可重取且只恢复一次，越权和过期拒绝 |
| GG-11 | 质量通过但没有执行授权 | 副作用仍被执行端阻止 |
| GG-12 | 上游替换、撤销批准、旧事件晚到 | 依赖和旧结果失效规则生效，不推进错误版本 |
| GG-13 | 等人、角色失败、超时替补、预算耗尽 | 计时和预算可审计，不自动改变策略 |
| GG-14 | 取消与完成竞争、旧进程未停止 | 唯一终态；不在另一环境重复启动未知副作用 |
| GG-15 | 写后断线、目标基线变化、发布重试 | 对账或明确冲突，不覆盖用户新修改 |
| GG-16 | 云端与无 K8s / Celery 的本机测试宿主 | 共享核心契约；持久恢复实际可验证 |
| GG-17 | 清理与通知失败 | 活跃资源和证据不丢；通知失败不污染终态 |
| GG-18 | 候选注入、伪造审批、敏感输出 | 不扩大权限，不泄露越权内容或凭据 |

生效前必须：批准本协议及所选策略；明确现行规范的适用范围修订；发布唯一 schema 与适配器能力清单；通过合同、故障、身份和双宿主测试；提供可停用新策略的回退配置并保证在途任务版本固定。

原草案里的 tmux 实验不算上述能力的验收。不存在对应证据时只能报告草案、已定义或未验证，不能报告已经产品化。
