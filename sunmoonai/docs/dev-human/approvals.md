# 人的批准点

人兼了组织者：出题、派工、定稿、裁决、清理都是人做的，执行者是 AI 助手。
本文写**人自己在这个位置上要守什么**。

**本文只讲对「动作」的批准**——合并、推送、发布、追加预算、改判这些要放行的事。
对「答」的采纳叫**定稿**，见 [定稿](finalize.md)；对交回物按完成条件的判定叫**验收**，见 [UAT 怎么验](uat/verify-rules.md)。
三者不能互相代替：定稿采纳了一份设计，不等于批准了照它动代码。

同一件事交给程序执行时要落成什么机制——权力表与强制点、批准怎样才算成立、三道正交门、四档审批、
待批准事项的记录——在 agent 侧，见 [后端的人介入与权力](../dev-agent/SDD/modules/0001-backend/rules/agent-dev-guide.md)。
**不在这里复述**：人版没有服务端、没有工具网关、没有 Interaction 对象，那些条款在这边落不了地。

## 人的位置

人可以同时是 requester 与某些权力的 principal，但不因此获得执行角色。人的稳定职责是：

- 给出或确认目标、边界与验收；
- 回答绑定到自己身份的待决事项；
- 批准省事方向的裁定、预算与资源变化、不可逆副作用；
- 对最终交付负责，并可推翻先前裁定。

**「由人把固定指令粘进界面」是尚未自动化的传输动作**，记为派工事件并计成本，不新增权力行。
传递面还没建起来，现在这一步就是人在做——见 [怎么走这套流程](workflow.md)。

## 谁负责什么

| | 谁负责 |
| --- | --- |
| 决定做什么、不做什么 | **人** |
| 决定怎么做（在约束内） | 执行者 |
| 产出是否合格 | 未参与实施的一方；无人时由**人** |
| 上线后出问题 | **人**——agent 不承担后果 |

- **是否简化流程的裁量权在人，不在执行者。**执行者不得自行降档，也不得靠询问自己派出的子 agent
  或多数同意来制造批准——**自我批准禁令任何时候都成立**。
- agent 不得自我批准，不是因为不信任它的判断，而是因为它不承担后果。
- **批准的是执行某个动作**，不是把结论直接写成成功。
- 超出已说定的范围，**开新的 turn**，不在原任务里扩权。
- 「我看着行」不是依据；依据要能被半年后的自己复核。

## 批准绑定什么

- 批准要说清**批准哪一版、哪项动作、什么时候过期**。「我昨天说行」不等于今天这一版还算数。
- **授权不跨场景延续**：换分支、换任务、下一次，都要重新批准。
- **方向不对称**：朝**放行**走的（冻结用户消息、开工、降档、追加预算、不可逆副作用、判成功、改判）都要人明确点头；
  朝**停下**走的（取消、收敛）是失败安全方向，可以放宽。
- 但**取消必须附已产生副作用的清单**，缺清单的取消不生效——不知道产生了什么，就不知道要回滚什么。
- 推翻裁定或改判已冻结的标准：**追加新记录，不覆盖原判断**；标准变了要重新验收。

## 裁量权的底线

人可以判断「这件事不值得走全流程」，执行者不可以。但裁量有底线，**五条不因规模而豁免**：

1. 不篡改原始意图；
2. 不越过权限与范围；
3. 结论有与风险相称的证据；
4. 「完成」可判定；
5. 发生改判时，交代触发与变化（见下面「改判」）。

省略任何一步都必须显式写出「不适用」及理由——空着与「忘了」无法区分。
涉及安全边界、数据迁移、跨系统契约、不可逆外部动作、生产发布的，无论多小都走完整流程。

## 人这一侧的义务

不只是执行者有纪律。人这边同样有，而且被违反时后果更大——因为 agent 会照做。任务越重，前两条越要做到。

| 人的义务 | 违反会怎样 |
| --- | --- |
| 用户消息写清**边界**：含什么、不含什么、不含的归谁 | 执行者会自行扩大范围，或漏掉本该做的 |
| **不给倾向性结论**；判据先冻结，PRD 与 SDD 不发给答题方 | 候选向你的结论收敛，等于白问；写成条目的判据会把答案空间提前封死 |
| 并行派工时**不泄露其他方案** | 独立信号退化成改写 |
| 派活前先建好各自的 worktree 和命名分支 | 多个执行者写同一工作区，后写覆盖先写 |
| 收到「我不确定」时**不追问到它给出确定答案** | 逼出的确定性是编的 |
| 执行者说「没查过某处」时**当作真话对待** | 声明盲区的动力被消灭，下次它不说了 |

最后一条最容易被忽略：盲区声明是自愿的，只要说了就受罚，很快就没人说了。这与 [UAT 怎么验](uat/verify-rules.md)
「如实写『不能排除』不扣分，隐瞒才扣」是同一条规则的两侧。

**委派转移的是执行，不是最终责任。**用户消息写多严按轻重，但范围、权限、预算、停止条件和要交回什么，
凡是会影响结果或权限的，都必须写进去；对超范围、追加成本、不可逆动作和规范修改及时批准或拒绝；
亲自验收，或指定未参与实施的验收方。

## 改判

改判本身不是问题，装作没改过才是。每次改判写清三件事：

| | |
| --- | --- |
| **触发** | 什么新证据或什么情况变化 |
| **原判断错处** | 当初**哪一句**不再成立——不是「当时信息不全」，是具体哪一步推错了 |
| **新判断** | 现在以什么为准；**能独立成立**，不写「理由见上文」 |

不得装作从未判过，**也不得为了让检查变绿而静默删除旧标准**。修改验收标准时保留原标准、原始失败输出和改判理由。
把结论写进上游文档前回读代码或实物重新取证——文字改对了、代码里还是旧的，比不改更糟。
