## ② 架构评审

- 结论：**采纳并直接实施**。

- 需求的可操作形式：产出一套 `baseline/`，使一个从未接触本项目的人或智能体，
  **在决定动手改某处之前**，能在数分钟内知道三件事：改动落在哪个仓的哪个位置、
  该处有哪些不可违反的硬规则、以及怎么验证自己没改坏。

  「迅速」是硬指标，因此结构必须支持**部分阅读**：不存在「必须读完才能动手」的情况。

- 七个自主设计决定及理由：

  **1｜以表格为主形式，prose 为辅。**主形式是「规则或事实 → 代码位置」两列以上的表。
  理由：两类读者的需求在此重合——人需要扫读，智能体需要可 grep 的锚点。
  长段落对两者都不友好。只有在表格无法表达的因果链上使用 prose。

  **2｜`README.md` 按「读者要做什么」索引，不按文档列举。**入口回答的是
  「我要改契约 / 要加个 App / 要部署 / 要动某个仓」分别读哪两节，而不是「本目录有哪些文件」。
  理由：后者要求读者先建立全局图才能定位，与「迅速」相悖。

  **3｜九平台压缩为 `map.md` 一张表加真源指针，不建八份平台文档。**
  理由：本投影的用途是开发五仓。要改 Harbor 保留策略的人真正需要的是「配置在哪个文件」，
  不是一份复述其配置的文档。投影不复制真源，指向真源比转述更准且零维护。

  **4｜每份仓文件必设「已知未实现」一节。**列出容易被误认为已完成、实际是占位或未接线的东西。
  理由：这是让投影**主动暴露缺口**而非被动写漏的结构性手段。
  缺此节时，「设计意图」会以「现状」的身份进入文档，且无人负责发现。

  **5｜易腐值一律不落，只指真源。**镜像 digest、schema sha256、commit、迁移 head、
  文件数一类每次发布即变的值不写入正文，改为指向其真源文件或目录。
  理由：这些值的变化速率高于手写文档的维护速率，写进来必然先于文档失效。

  **6｜撰写方法：五个子智能体按仓并行读代码，且禁止读现有 `baseline/`。**
  理由：若允许参考现有文档，产出会退化为对旧文本的改写，无法保证与代码一致。
  禁读之后，本次产出是一份**独立于既有文档、直接从代码派生**的投影。

  **7｜`verify.md` 作为一等文件。**记录每份文件的验证时点与可重跑的取证命令。
  理由：投影的唯一质量指标是对代码的保真度，而保真度只有配上「何时验证过」才有意义。
  没有这一项，读者无法判断该不该相信它。

- 与既有文档的关系：本次产出**覆盖式替换** `baseline/` 全部文件。
  旧文件由 git 保留（本工作在 `opus` 分支，`master` 不受影响），不在文档内保留旧条文。

## ④ 验收标准

1. 每条事实性断言可落到 `file:line` 或可执行命令；正文无「应该 / 将来 / 计划」类表述。
2. 无易腐值（digest / sha256 / commit / 迁移 head / 文件数）；改为真源指针。
3. 五份仓文件均含「已知未实现」一节。
4. `README.md` 为任务索引形式；任一常见任务可在两跳内定位到具体章节。
5. `verify.md` 含每份文件的验证时点与可重跑命令。
6. 相对链接 0 坏链。
7. 接手演练：未接触过项目者只读 `baseline/`，能说出五仓分工、部署顺序、契约真源位置，
   以及当前镜像 digest 应到何处查。
