## 一、三个应用各管什么

| 应用 | 一句话 | 用户来这里做什么 | 管理员来这里做什么 |
| --- | --- | --- | --- |
| investment | 用数据做研究 | 聊天、让代理干活、请专家 | —（第一期没有管理页） |
| knowledge | 有什么数据、怎么定义、怎么给 | 看有哪些公司的数据、数据到哪一天、口径怎么算 | 看数据集的版本、工具的调用情况 |
| info | 把数据弄进来 | 申请「我要这家公司的数据」，看进度 | 批准申请、发起采集、看批次 |

分工的原则：一件事只在一个应用里办。别的应用要用，就用链接把用户带过去，不各做一份。

## 二、数据怎么流

```text
公开网站（巨潮、东方财富）
      │ 采集
      ▼
    info ──原件、数据集文件──→ 对象存储
      │ 登记「有一个新版本」
      ▼
  knowledge ──按登记的位置取文件
      │ 工具（MCP）
      ▼
  沙箱里的 Codex ←── 方向盘在用户或专家手里
      │ 事件
      ▼
  investment 的页面
```

| 规则 | 说明 |
| --- | --- |
| 专家和代理不直接连 info | 只经 knowledge 的工具拿数据 |
| 没过质量检查的数据不给 | info 不发布，knowledge 就没有 |
| 每个结果带出处 | 数据集、版本、数据时点 |

## 三、用户的一条完整的路

以「用户想看一家还没有数据的公司」为例，它会穿过三个应用。

| 步 | 在哪 | 发生什么 |
| --- | --- | --- |
| 1 | investment，聊天或专家 | 用户问茅台的毛利率。工具答复「没有这个数据集」 |
| 2 | investment | 对话里出现一张卡片：「这家公司还没有数据」，带按钮「申请入库」 |
| 3 | info 网页端（新标签页） | 申请页，代码已填好。用户提交 |
| 4 | info 管理端 | 所有者批准（关注清单里的公司自动批准） |
| 5 | info 后台 | 采集、建库、向 knowledge 登记。约 5 到 10 分钟 |
| 6 | info 网页端 | 申请的进度变成「可用」 |
| 7 | investment | 用户回来再问一次，这次查得到 |

另一条路：用户想先看看有什么数据。

| 步 | 在哪 | 发生什么 |
| --- | --- | --- |
| 1 | investment | 导航里点「数据目录」 |
| 2 | knowledge 网页端（新标签页） | 看到有数据的公司、每家的数据时点、有哪些表、口径怎么算 |
| 3 | knowledge 网页端 | 没有想要的公司：点「申请入库」，去 info |

## 四、跨应用的约定

### 4.1 一个应用把用户带到另一个应用

| 项 | 约定 | 状态 |
| --- | --- | --- |
| 形式 | 普通链接，在新标签页打开 | 所有者定（`P3` 甲） |
| 链接里带什么 | 业务参数（例如证券代码）、`from`（从哪个应用来）、`ref`（来处的引用） | 远程的建议 |
| 链接里不带什么 | 身份、令牌、回去的地址 | 远程的建议 |
| 用户是谁 | 由用户在目标应用的登录决定。三个应用用同一个身份服务，登录过的不用再输密码 | 已有 |
| 回去的地址 | 目标应用按 `from` 在自己的配置里查，把 `ref` 填进去。不从链接里取 | 远程的建议 |
| `ref` 的规则 | 不透明的字符串，限长 128，只许字母数字与 `._:-`；目标应用只存、只原样显示 | 远程的建议 |
| 拼链接的代码 | 每个应用写在一处；对方的地址来自配置 | 远程的建议 |

这套约定要写进模板，三个应用共用。具体的链接见各应用的文档。

| 从 | 到 | 链接 | 什么时候用 |
| --- | --- | --- | --- |
| investment | info 申请页 | `/<语言>/requests/new?code=&from=investment&ref=` | 工具答复没有数据时；导航 |
| investment | knowledge 数据目录 | `/<语言>/catalog?from=investment` | 导航 |
| knowledge | info 申请页 | `/<语言>/requests/new?code=&from=knowledge&ref=` | 数据目录里找不到公司时 |
| info | knowledge 数据集页 | `/<语言>/catalog/<数据集>` | 申请变成「可用」之后 |
| info、knowledge | investment | 配置里登记的回跳地址 | 「回到原处」 |

### 4.2 后端之间的调用

| 从 | 到 | 做什么 | 状态 |
| --- | --- | --- | --- |
| info | knowledge | 登记数据集的新版本 | 已做 |
| knowledge | 对象存储 | 按登记的位置取数据集文件 | 已做 |
| 沙箱里的 Codex | knowledge | 工具（MCP），用工作台签发的令牌 | 已做 |
| 沙箱里的 Codex | investment 工作台 | 读项目里别的对话的记录（MCP） | **新增**，见 [`investment.md`](investment.md) |
| investment 工作台 | info | 问「这家有没有数据」、在自己的页面里显示申请进度 | 第二期 |
| investment | knowledge | 文档检索 | 已撤销（旧运行时的，2026-09-29） |

第一期三个应用的后端之间不新增调用，只新增「沙箱到工作台」这一条。

## 五、前端共用的底座

所有者 2026-09-29：「和后端一样，开发代码要采用我们既有的底座」。

| 项 | 内容 |
| --- | --- |
| 模板 | `tpl-app` 的 `tpl-web-frontend`、`tpl-admin-frontend`。公共的东西先进模板，再同步到各应用 |
| 框架 | Next 16.2、React 19.2、Tailwind 4 |
| 组件 | shadcn，风格 `base-nova`，底下是 **Base UI**（不是 Radix） |
| 状态与校验 | zustand、react-query、zod |
| 文案 | 中文为主，英文同步；两套文案的键必须一致（已有自动检查） |
| 测试 | vitest（单元）、Playwright（浏览器里的端到端） |
| 接口的客户端 | 从后端的接口定义生成，不手写第二份（`F-WEB-06`） |
| 预览 | 用样例数据顶替后端，每个页面、每种状态都能打开（所有者 2026-09-29 定的调试方式） |
| AI 对话库 | shadcn 自己的聊天组件。所有者：「由你定」；试验与理由见下 |

### AI 对话库

**定了：用 shadcn 自己的聊天组件**（2026-06 出的 `message-scroller`、`message`、`bubble`、`attachment`、`marker`）。不用 assistant-ui，不用 AI Elements。
所有者 2026-09-29：「由你定」。远程当天在 investment 网页端的副本上做了试验，两个库各写了一个同样内容的试验页。

| 比什么 | shadcn 的聊天组件 | assistant-ui 0.15.22 |
| --- | --- | --- |
| 装得上 | 是 | 是 |
| 类型检查、代码检查、构建 | 都过 | 都过 |
| 测试 | 直接过 | 要先垫一个浏览器接口才过 |
| 底下用的组件库 | Base UI，和我们的底座一样 | Radix。装进来 60 个 Radix 的包 |
| 带进来的别的东西 | shadcn 自己的两个小包 | 另外两个版本的 zod；它自家云服务的客户端，里面写着默认地址 |
| 这一页独有的脚本，压缩后 | 32 KB | 123 KB |
| 代码归谁 | 拷进我们的仓库，归我们 | 它的包 |
| 版本 | 随 shadcn | 还没到 1.0；我们要用的那个接法放在它名为「旧运行时」的目录下，另有一批接口名字带着「不稳定」 |
| 我们的东西放不放得进去 | 每种东西各写一个组件，直接 | 它只认「消息」。审批、没有数据、系统行在它的模型里没有位置，只能装成「工具调用」塞进去 |

最后一行是主要的理由：我们的工作页是一条过程时间线，不是一串消息。用一个只认消息的库，等于一直在和它较劲。

| 要说明的 | 内容 |
| --- | --- |
| 远程之前的建议是 assistant-ui | 那是按它网页上写的判断的。实际试过之后改了 |
| 所有者听说的是 AI Elements | 没有试。它的前提里写着要装 Vercel 的 AI SDK，没写支持 Base UI。以后它要是支持了，它的组件也是拷进仓库的，可以按件取用 |
| assistant-ui 的云服务客户端 | 远程没有发现它在我们这种用法下会往外发请求，但也没有逐行审过。不用它，这件事就不存在 |
| 试验没有覆盖的 | 真的边出边显示（试验用的是静态样例）；很长的对话滚动起来顺不顺；手机 |

装的时候：`pnpm dlx shadcn@latest add message-scroller message bubble attachment marker`。它会问要不要覆盖已有的 `button.tsx`，答不要。它带进来的 `cn` 这个包是 shadcn 自己的，也可以改成用我们已有的 `@/lib/utils`。

只有 investment 需要这些组件。info 和 knowledge 的页面是表单、列表、进度，用 shadcn 的普通组件。

## 七、和以前的设计不一样的地方

| 项 | 以前（[网页设计初稿](../../SDD/modules/0002-web-design.md)，2026-09-24） | 现在 |
| --- | --- | --- |
| 入口 | 只有「会话」一种 | 聊天、工作、专家三种 |
| 专家 | 会话页侧栏里的「求助」面板 | 独立的功能，也能从对话里转入 |
| 第一层的样子 | 「过程时间线加输入框」，有意弱化聊天感 | 聊天就是聊天的样子；工作才是过程时间线 |
| 项目 | 新建会话时填一个目录 | 周边的一等概念，有自己的页面 |
| 不选项目 | 不允许 | 聊天允许 |
| 别的应用 | 没有提 | 数据目录在 knowledge，采集申请在 info，用链接连起来 |

没有变的：两层决策权、同一条线、结论永远是用户的、不做投资咨询、六条设计原则里的 P2 至 P6。P1（方向盘永远可见）保留，但给用户看的字眼不用「方向盘」（2026-09-26 已定）。

初稿里仍然有效的部分（审查面五要素、底稿页的区块、设置、我的机器、公开首页与注册入口、页面上的说明文字、文案原则）不在这里重写，各文档里指过去。
