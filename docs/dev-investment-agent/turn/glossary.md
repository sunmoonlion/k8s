# 词汇表

本仓文档的用词以本表为准：**同一个意思只用一个词**，「不要用」一栏的词不得在规范里指代同一个意思。
本表只增不改；要改名，按文末「用词纪律」办。各任务把这些词对应到具体产品或执行环境的名字，写在任务自己的目录里，不写在这里。

> 2026-09-23 经所有者裁定退役一组词：文档 thread、文档 turn、`response.md`、`turn.md`、`others/`、本地号。
> 一问一答不再落成编号目录，见 [turn 的投影](turn-project.md)。旧原件里仍能见到它们，不回改。

## 任务与目录

| 词 | 含义 | 不要用 |
| --- | --- | --- |
| 任务 | 交给 agent 做的一件事。一个任务目录就是一个任务；在需求树里也叫节点 | 工单、需求（指任务时） |
| 任务目录 | 一个任务的全部文件：`PRD/`、`SDD/`，可选 `human-ai-turn/` 与约束目录 | — |
| 入口 | 人把话说给 AI 助手的地方：命令行、IDE、脚本投喂的交互会话。**默认在入口里直接交互，不留痕** | 窗口、通道（指这个时） |
| 直接交互 | 在入口里一问一答，AI 直接答或直接改文件，人看 diff、提交。**绝大多数 turn 的形态** | 轻量 turn、口头 turn |
| `human-ai-turn/` | **值得持久化的那一问**所在的目录：只有 `user-message.md`，或按种类分子目录各一份。普通目录，可建可删可提交。名字是约定不是规则 | thread、turns、rounds、问答目录 |
| `turn/` 目录 | 本目录——**一次一问一答怎么走完**的规矩，跨项目通用。它是目录名，不是某个具体的 turn | — |
| turn | 一问一答，不论落没落目录。行文里说「这个 turn」指的是一次派工和它的交回 | 轮、轮次、回合 |
| 运行时 thread | 执行环境自己的会话，只有 id。换了会话就是换了运行时 thread；交接靠落盘，不靠它 | 会话 |
| `user-message.md` | `human-ai-turn/` 里的用户消息：这一问的全文，**追问追加在末尾**。没有 YAML 头 | 任务书、工单、PRD（指这一问时） |
| 追问 | 同一问的下一轮：理由追加在 `user-message.md` 末尾，AI 再答。**打回就是追问** | 新 turn、返工 turn |
| 用户消息 | 发给 agent 的那一问：直接交互时是入口里说的话，值得留时存为 `user-message.md`；正文须写明这一问要交回什么 | 任务书、工单、需求文档 |
| 附件 | 与 `user-message.md` 放在一起、随它发出的材料 | — |
| 派工 | 发出一问 | — |
| 交回物 | 一问交回来的东西：PRD、SDD 两类是**对目标文件的修改或新建的文件**；IMP、UAT 两类是分支上的提交 | 交付物（指这一份时）、response |
| 定稿 | **人对答的采纳**：看 diff、取舍、改、提交。PRD 类定稿成 `PRD/`，SDD 类成 `SDD/`；提交说明写明以什么为底、改了什么。见 [定稿](finalize.md)。**不等于批准，也不等于验收** | composition、设计稿、交接文件、审核（指这件事时） |
| `architecture/` | **只在 `SDD/` 下**：模块之间的关系——接口、共同约束、取舍；入口文件 `README.md`，可以再拆多份。需求侧不分模块，`PRD/` 下不得有 | 总体设计（指这一份时） |
| `modules/` | **只在 `SDD/` 下**：`SDD/modules/<模块>.md` 写**这一层对这块的说明**——承担什么、不承担什么、边界在哪 | components |
| `submodules/` | **只在 `SDD/` 下**：`SDD/submodules/<模块>/` 是**子任务**，内部是同样结构的任务目录。与 `modules/` 同号同名一一对应，也与实现时 worktree 里的模块目录一一对应 | 子任务目录 |
| 上层任务 | 其 `SDD/submodules/` 拆出了子任务的那个任务 | 父任务 |
| worktree | 开发侧的 git worktree：IMP 在里面实现，UAT 的测试在它的 `test/`；审核者在被审的 worktree 之上再开一个 | 工作区（指产品运行时的工作区时） |

## 种类与交付物

一问的**种类**有四个：PRD、SDD、IMP、UAT，规则见 [PRD](prd/finalize.md)、[SDD](sdd/finalize.md)、[IMP](imp/message-rules.md)、[UAT](uat/message-rules.md)。每一类该问什么，见各类规则的「这一类该问什么」；写多严见 [turn 的投影](turn-project.md)「用户消息写多严」。
**不要和产品侧的「任务类别」（通用 / 专业）混用**：那是产品侧按 [Profile](../tree-build/SDD/architecture/profile.md) 与专家包对客户委托的分类，与一问的种类无关。

| 词 | 含义 | 不要用 |
| --- | --- | --- |
| PRD | 产品需求：要什么、做到什么算满足，不写怎么实现。`PRD/` 是 PRD 类的定稿目录，SDD 拿它当输入 | 需求文档（指用户消息时） |
| SDD | 软件设计说明：设计成什么样——模块之间的结构与关系、接口、共同约束，以及各模块内部的结构、协议与数据、失败与恢复 | TLD |
| IMP | 实现：按定稿的设计做出来——工作单元、先后顺序、实施记录、代码与证据 | SDP（那是开工前的项目计划，不是这一类） |
| 工作单元 | IMP 里可以独立交付、验证、回滚的一块 | 任务（指工作单元时） |
| UAT | 用户验收测试：按用户消息逐条验证是否满足、能否接收 | — |

## agent 与人

| 词 | 含义 | 不要用 |
| --- | --- | --- |
| 讨论 agent | 答 PRD 类的问 | — |
| 规划 agent | 答 SDD 类的问；定稿之后按 `SDD/submodules/` 的拆分建子任务 | — |
| 执行 agent | 做 IMP：在自己的 worktree 里实现 | — |
| 验收 agent | 做 UAT：在 worktree 的 `test/` 里验收；不是实现这份 IMP 的那一个 | — |
| 驱动方 | 驱动这套流程的角色：发起一问、验收、打回、清理 worktree。**现在由人充当**；交给程序是待开发的能力。不要和产品的后端 supervisor 混——那是程序，而且不调用生成式模型 | supervisor（指这个角色时） |
| 人 | 写用户消息、定稿、批准、裁决。文档里不写具体是谁 | 具体人名或角色名 |
| principal、requester | 持有某项决定权的主体、提出请求的主体；见 [人的批准点](approvals.md) | — |

## 过程

| 词 | 含义 | 不要用 |
| --- | --- | --- |
| 批准 | **人对动作的放行**：合并、推送、发布、追加预算、改判。绑定哪一版、哪项动作、何时过期；见 [人的批准点](approvals.md) | 审核（指这件事时） |
| 验收 | **对交回物按已冻结的完成条件判定**：验收 agent 做 UAT，用户消息写明验的是哪个提交；逐条判定与证据在 worktree 的 `test/` 里，**结论写进那条提交的说明** | 审核（指这件事时） |
| 打回 | 判定交回物不满足用户消息。打回就是追问，理由追加在 `user-message.md` 末尾 | — |
| 返工 | 同一项交付物因打回而重做；什么时候不再重做由驱动方定 | — |
| 改判 | 修改标准或判断时写清触发、原判断错在哪、新判断；落在追问里和改定稿的那次提交说明里；见 [人的批准点「改判」](approvals.md) | — |
| 多方竞争 | 一种交付物由多个 agent 各交一份、比较选定；各家一条分支。见 [多方竞争](competition.md) | 轮次、评优轮 |
| 档位 | T0、T1、T2：这件事该走多重的流程；见多方竞争协议「档位」 | — |
| 先提交再改 | AI 答完先提交一次，人再改再提交：把「它答的」与「人改的」分开。替代上一版的「交回即冻结」；T0 可合成一次 | 冻结（指这件事时） |
| 进度 | 从 `human-ai-turn/`、`PRD/`、`SDD/` 的 diff 与提交推出的投影；**任务目录里**不另写记录或进度文件 | 交接文件、状态文件 |
| `CHECKPOINT.md` | IMP 在自己 worktree 的**代码分支上**的工作笔记：跨运行时 thread 续接靠它，就地更新、随代码提交、随 worktree 清理而消失。不是进度投影，不进任务目录 | 交接文件、进度文件 |

## 用词纪律

1. 同一个意思只用一个词；新词先进本表再用。
2. **改名须人确认**，按 [改判](approvals.md) 的三要素写清为什么改，并且一次改遍全仓、跑完检查，不留新旧两名并存。
3. 与具体产品、执行环境的名字怎样对应，写在任务自己的目录里；本表不出现具体产品名。
4. **编号也是词。**起一套新编号之前先查下表；一个字母只归一套编号。

## 规范用语

写规范时这四个词是硬性的，不是语气：

| 词 | 含义 |
| --- | --- |
| **必须** | 缺失即不符合本规范 |
| **应该** | 默认要求；偏离时必须记录理由、风险和等价控制 |
| **可以** | 合法选项，不构成统一实现要求 |
| **⚠** | 依赖尚未实测的前提，必须写明验证办法（`P6`）；记在 [待定决策与未验证事项](../tree-build/decisions.md) |

## 一个应用的三块（所有者 2026-10-17 定的叫法）

| 叫法 | 指什么 | 代码里 |
| --- | --- | --- |
| **web端** | 给用户用的网页 | `<名>-web-frontend` |

## 分身的生长阶段（2026-10-17 所有者提思路、Opus 拟、所有者核「行」）

所有者原话：「我觉得既然是bot，就从seed incubator infant到成品类似来定义，这样更好」「整个流程和命名你提建议，我核」。中文叫法为主，英文只用在代码里。

| 阶段 | 是什么 | 能不能改 | 代码里 |
| --- | --- | --- | --- |
| **种子** | 用户交来的想法（六问或 skill）、验收用例、他上传的数据 | 用户可补充 | `seed`（现有表 `knowbot_request`） |
| **孵化** | 后端把种子写成分身：出处表、缺口与答复、工程记录、清单候选（每改一次留一版） | 随时改 | `incubation`（新建） |
| **雏形** | 孵出、拿去测试的一版清单，带测试状态、测试中要人答的问题、测试报告 | 定了不改；要改回孵化出下一个 | `infant`（现有表 `knowbot_draft`） |
| **成品** | 测试通过、交付到 knowmart 的分身版本；工作台「请」的就是它 | 只读 | `knowbot` |

- 流转：种子 → 孵化 → 雏形 →（测试通过）→ 成品；未通过回孵化，孵出下一个雏形。
- 状态：种子「已提交」；孵化「起草中 → 等用户答 → 等运营核 → 已孵出」；雏形「待测 → 测试中（含等人答）→ 通过 / 未通过」；成品「可用 → 停用 → 已删（历史版本保留 100 天）」。
- 编号：成品按版本号 1、2、3；雏形写「版本号.第几个」（1.3 = 第 1 版第 3 个雏形）。
- 孵化的三种方式（都在 knowlab 管理端选）：**手工孵化**（运营手写清单，后端校验、存版本）、**辅助孵化**（后端调模型起草，运营看过改过，缺口发不发由运营定）、**自动孵化**（用户在 web端提交即起草，缺口直接发给用户，运营最后核出处、放去测试）。
- **方法包**（pack）：分身的方法——几步、每步怎么做、怎么验收；原来叫「专家包」（「专家」已不用）。**清单** = 方法包 + 外层（名字、版本、运行方、能读的数据、规则出处）。
- 代码里现有的表名与状态名（`knowbot_request`、`knowbot_draft`、`pending_test` 等）先不改，文档写明对应；统一改名等第一条实测之后。

## 我们和直接用 Codex 的区别：施工比方（2026-10-17 Opus 提、所有者「你的比喻准确」）

- **直接用 Codex**：业主找来一个能干的施工队，口头交代一句「给我盖个房子」，施工队自己看着办，盖好了业主自己去看哪里不对。
- **用我们**：业主找到我们，我们先把**业主自己想要的样子**画成施工图（孵化；图照业主的意思画，不是我们的设计），再按图管施工：分工序（分步）；每道工序开工前交底——做什么、用哪些上道工序的成果、能用什么工具（每步的方法原文、输入、工具）；尺寸用仪器量（数由平台算，0030）；每道工序完了质检、不合格返工（验收）；关键节点请业主签字（开步前问、审批、有人值守）；全程施工日志（留痕）。
- 施工队还是同一个（Codex），每道工序里怎么砌砖由它自己干（`C-C7`）。一句话：**Codex 是施工队，我们是把业主的想法画成图纸、再按图监理的那一方；图纸画得好不好，就是孵化的手艺。**
- 不要说成「上报集团、拿到指示再干」：指示（方法）来自用户本人，不是我们给的；控制在每一步都有，不只在开头。

**附：经 Codex app-server 真正能控制的地方**（2026-10-17 Opus 按 knowbench 代码核过；只经公开协议，不碰内部，`C-C7`）

| 时机 | 能控制什么 | 协议上怎么做 | 代码位置 |
| --- | --- | --- | --- |
| 开线（一段对话一次） | 用哪个模型；在哪台电脑、哪个目录干（执行端）；沙箱只读还是能写、能不能联网；命令要不要人批；关掉多代理、开「一轮中间能问人」 | `thread/start`：`model`、`environments[].cwd`、`sandbox`、`approvalPolicy`、`config`（`features.*`） | `domain/workbench/projects.py` 的 `thread_settings`、`THREAD_CONFIG`；`application/workbench/runner.py` |
| 拉起沙箱（每个用户一次） | 模型 key 与接入地址；能连哪些工具服务（MCP：工作台的记录与数据工具、知识库） | 沙箱的 Codex 配置，由供给器写入 | `application/workbench/provisioning.py` |
| 每一步开始 | **这一步的全部输入**：方法原文、上游交回物、工具说明、交回格式（施工比方里的「交底」）；这一轮的沙箱与审批设置 | `turn/start`：`input` 与这一轮的设置 | `application/workbench/advisor.py` 的 `compose`；`runner.py` 的 `run_turn` |
| 一步进行中 | 模型要跑命令、改文件、扩权限时**由我们答**（批准、拒绝、交给用户）；模型反过来问用户时转成提问卡；中途插话；用户点停下或超时就打断 | 服务端请求 `item/commandExecution`、`item/fileChange`、`item/permissions` 的批准，`item/tool/requestUserInput`，`turn/steer`，`turn/interrupt` | `runner.py` |
| 一步进行中（工具） | 模型能调的我们自己的工具：读项目记录、读用户数据、按格子读、**计算**——每次调用由我们按委托核权限、记账 | MCP 工具服务 | `interfaces/mcp/workbench_mcp.py` |
| 一步结束 | 收它交回的最后一句与改过的文件、用了多少 token；**验收**、重做、退回、交人；下一步给什么 | `turn/completed`、`item/completed`、`thread/tokenUsage/updated` | `advisor.py`、`acceptance.py`、`acceptance_numbers.py` |
| 随时 | 电脑断线、重连，接回原来的线 | `thread/environment/*`、`thread/resume` | `runner.py` |

**控制不了的**：一轮之内模型想几次、调几次工具、按什么顺序（Codex 自己的代理循环）；Codex 内置的系统提示与内置工具（命令行、改文件）本身；模型照不照方法原文做——这部分只能靠验收抓出来、靠工具权限框住。所以验收写得多严，决定了「控制」有多实。
