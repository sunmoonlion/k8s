# REQ-009：休眠能力可识别

> 状态：PROPOSED ｜ 提出日期：2026-08-15 ｜ 评审日期：2026-08-15

> 类型：实施 REQ。粒度刻意小，只定约定与检查，不含整改。
> 目标是成为第一个真正走完闭环的请求。

> 要不要单独提个req

## ② 架构评审

- 结论：**采纳**。约定与检查即刻立项；具体形式待 ④ 拍板。

- 理由：

  **先分清两种毛病，否则会治错。**REQ-008 最初把这批现象统称「未接线」，
  该归并不成立。回代码看，它们是两回事：

  | | 成因 | 例 | 是不是缺陷 |
  | --- | --- | --- | --- |
  | 甲 | 模板资产被实例继承但未使用 | Outbox（tpl-app 有 Port、仓库类、带大小约束的 DTO，且 `test_kernel_invariants` 专门检查其存在）；web-interaction 的 `Unavailable` 默认适配器 | **不是**。模板有意提供的可选能力，不用它是正常的；`Unavailable` 本身就是一个显式的未接线信号 |
  | 乙 | 本仓自建却无调用方 | `RunBudget`（investment-app 领域代码，四维限额与超限抛错齐全，两条生产链均不调用）、`AgentMemoryService`、`CancelRunCommand` | **是** |

  naive 的范围——「把未接线的接上或删掉」——会去动甲类（不该动），
  且横跨四仓，大到无法收口。故本 REQ 不采用该范围。

  **真正的缺陷是可识别性，不是休眠本身。**从代码看不出一个休眠能力是**有意待用**
  还是**被遗忘**。甲乙两类在代码里长得一模一样：都是定义齐全、无调用方。

  **该信息缺失已产生实测代价。**REQ-006 把 `RunBudget` 列为「已有且强于参考实现」，
  并据此推导子 Run 预算的继承设计。若定义处标明其未接线，该误判不会发生——
  一套无法验收的父子预算设计也不会被写出来。修正记录见 `REQ-006-投资研究编排/request.md` ⑤。

  **机制已存在，无须新建。**四仓各有 `app/tests/test_kernel_invariants.py`，
  其中四项检查在四仓中逐字相同（`test_legacy_split_backend_shortcuts_are_absent`、
  `test_interface_partition_and_dependency_direction_are_explicit`、
  `test_one_linear_canonical_migration_chain`、
  `test_runtime_image_context_excludes_credentials_and_tests`）。
  info-app 另有 `test_business_and_shared_outboxes_remain_distinct`（`:62`），
  **说明「把结构事实钉成测试」在本项目已是既成惯例**，本 REQ 只是再加一项同类检查。

  **检测方向的取舍。**「某符号有无调用方」在 Python 中无法静态判准（依赖注入、动态派发）。
  因此不做通用分析器，改为**声明加校验**的双向闭环：

  | 方向 | 可自动化程度 | 作用 |
  | --- | --- | --- |
  | 已声明休眠的项，验证其确实无调用方 | 高（grep 调用点即可） | 有人接线后必须撤销声明，否则检查失败 |
  | 未声明却无调用方的项，报为候选 | 中（启发式，有误报） | 捕捉 `RunBudget` 那一类遗漏 |

  误报正是需要声明清单的原因：被报出的项要么接线，要么显式声明休眠。两条都走不通的才是真缺陷。

- 冲突与代价对比：

  | | 立本 REQ | 维持现状 |
  | --- | --- | --- |
  | 一次性成本 | 一份约定 + 一个检查函数（四仓各一份，与现有四项同构）+ 首轮声明清单 | 0 |
  | 持续成本 | 新增能力时须声明或接线 | 每次读码者与设计者都可能把休眠能力当既有能力，代价已实测一次 |
  | 风险 | 声明清单沦为橡皮图章 | 投影侧 §8 是唯一防线，但它在代码之外，会漂移 |

  `baseline/repos/*.md` §8 目前已列出这批休眠项，可作首轮声明清单的输入，
  但它不能替代本 REQ：文档在代码之外，无法阻止新的遗漏产生。

- 边界：

  - **不含整改**。现有休眠项的接线、标记或删除均不在本 REQ 内。
  - **不含 `RunBudget` 的接线**，它是多智能体预算的前置条件，归 `REQ-006` ④ D7。
  - 甲类（模板资产）不视为缺陷，本 REQ 只要求其可识别。

## ④ 决策点

| 编号 | 决策 | 备选 | 建议 |
| --- | --- | --- | --- |
| D1 | 声明形式 | 定义处的代码标记（常量 / 装饰器 / docstring 约定）/ 仓内单独清单文件 | **单独清单文件**：可被检查脚本单点读取，且新增一项需显式改清单，比散落在定义处更难糊弄 |
| D2 | 清单放哪 | `app/tests/` 下与检查同处 / 仓根 / `app/` 下 | 与检查同处——它是检查的输入，不是运行时配置 |
| D3 | 甲类的声明归属 | 每个实例各声明一遍 / 模板声明一次、实例继承 | **模板声明一次**：甲类本就来自模板，四份重复声明会让清单失去信噪比 |
| D4 | 候选检测的范围 | 全仓公开符号 / 仅 `domain/` 与 `application/services/` / 仅新增代码 | 仅 `domain/` 与 `application/services/`——乙类都出在这两层，范围小则误报少 |
| D5 | 检查失败的语义 | 硬失败（同现有四项）/ 仅告警 | 硬失败。现有四项都是硬失败，混用两种语义会让人不再信任这个文件 |
| D6 | 声明是否须带理由 | 须写一句为何休眠 / 只列符号名 | 须写理由。无理由的声明就是橡皮图章，这是 ② 代价表中唯一列出的风险 |

## ⑤ 验收标准

1. 四仓各有一项新检查，与现有四项同构且为硬失败。
2. 声明清单存在，每项含符号位置与休眠理由（D6）。
3. **可证伪性**：把清单中任一项接上调用后，检查失败；撤销其声明后，检查通过。
4. **能捕捉真实历史缺陷**：以 `RunBudget` 为回归样例——在其未声明且无调用方的状态下，
   检查必须报出它。
5. 甲类（模板继承项）在模板处声明一次即可，实例不重复声明（D3）。
6. 不引入任何单一工具专有的配置。
