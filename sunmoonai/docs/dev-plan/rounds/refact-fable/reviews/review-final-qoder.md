## 2. 残余 concern（不阻塞冻结，但需在实施中验证或继续细化）

### C1：回执仓方案仍是显著基础设施负担

**说明**：回执仓方案比 ruleset 更健壮，但日常开发中每次 H1/H2/H3/H4/H5/H6 都要切到 Windows、输入口令、push tag（`refact-fable.md:620-633`）。文档把摩擦登记为观察值，但没有评估「收益是否大于成本」。对于 3–5 人的 CLI 开发协作，这可能把每个小任务的开销拉高一个数量级。

**建议**：在 §7 风险表新增一条「回执仓摩擦导致任务绕过流程」，处置为「S1 后跑两周观察：若 T0 任务因 H5 签名 burden 主动降档或拖延， reconsider T0 可逆出口（§7 风险 13）」。

### C2：T0 任务类包可能口径过窄，把大量小任务推到 T1

**说明**：T0 要求验收条必须是一个已签策略包（paths + gates + covers），不得自拼门禁子集（`refact-fable.md:401-426`）。这个设计在策略完整时很干净，但开发初期策略包覆盖不全，真实小任务往往跨包边界（例如「改一个脚本并更新其文档」会同时触及 `*.py` 和 `*.md`）。文档自己也承认风险 9：「T0 口径收窄后，大量小题目会落到 T1」(`refact-fable.md:776`)。

**建议**：这不是文档缺陷，而是实施假设。在 `policies/tier-defaults.toml` 首版中多放几个宽松包（如 `mixed-doc-script`），并规定「包不存在时升 T1」而不是「勉强塞入」。观察 T0/T1 比例，若两周内 T0 比例 < 20%，说明包设计失败，需改策略。

### C3：bootstrap 与 §8 冻结存在循环依赖

**说明**：S1 的验收判据包括「回执仓建成、越权被拒、测试 tag 存在、schema 合法」（`refact-fable.md:744`），但 S1 又要求「本文经 §8 冻结（3.13 随之冻结）」才能开工。而 §8 的某些判据（如第 6 条「VM 身份 push `confirm/_probe` 被拒」）又只能在 S1 后验证。文档用 `bootstrap` 概念解套（`refact-fable.md:756-759`），说 S1/R0 的效力来自本文被所有者冻结，不来自 `policy/1`。

**这仍然是一个鸡生蛋问题**：所有者凭什么在 S1 前就冻结 §8？合理做法是：先按 §8 草案跑 S1，S1 输出证明 §8 第 6 条可行后，所有者再正式冻结 §8。文档的叙事顺序应该改成「S1 先跑，§8 后冻结」，而不是「§8 冻结是 S1 前置」。

**建议**：把 §6 中 S1 的「前置：本文经 §8 冻结」改为「前置：本文 §3.13 已起草；S1 输出作为 §8 冻结的实证材料之一」。这样 bootstrap 更诚实。

### C4：H7（取消）不锚回执仓的理由可再商榷

**说明**：3.3 把 H7 作为唯一例外，允许 `rulings.md` 一条即生效，理由是「伪造取消只停工、不放行任何东西，属失败安全方向」（`refact-fable.md:290`）。但伪造取消会让合法在跑任务停止，产生副作用盘点和重开成本。虽然不放行坏东西，但也不是无成本。

**建议**：保留 H7 例外，但在 §7 风险表中增加「伪造/误触取消的恢复成本」，并规定取消必须附带「已产生副作用清单」，该清单格式由 L0 门禁校验。

### C5：`check-no-owner-creds.sh` 不是边界，只是卫生检查

**说明**：3.13.4 把凭据检查清单入仓（`refact-fable.md:641-645`），并作为 R1 验收判据。但由于 VM 全 root，agent 可以修改该脚本。文档清楚本地验证不是边界（`refact-fable.md:572-574`），但 R1 判据列表仍把脚本零命中放在第 ③ 条，可能让读者误以为是安全边界。

**建议**：R1 验收第 ③ 条文字改为「`check-no-owner-creds.sh` 作为配置卫生检查零命中（非边界，仅防人为疏漏）」，与真正的边界（回执仓只读权限）区分开。

### C6：lifecycle.md 400 行估算偏乐观

**说明**：5.1 预计 `lifecycle.md` ≈400 行。最终稿需要并入的内容包括：原 agent/human 共同内核、3.1.1 映射表、3.7 工作区函数、3.11 git 载体语义、human 差异表等。这些新增内容约 150–200 行，加上原共同内核约 500–600 行，总量很可能接近 700–800 行。文档已说明行数是观察值，但 400 行这个数可能给读者错误预期。

**建议**：把「≈400 行」改为「预计 600–800 行，以实际合并后为准」，避免冻结后被行数打脸。
