# 请求生命周期规范

> 最后更新：2026-08-27
>
> 一个「请求」从提出到关闭要经过哪些状态、每个状态凭什么进出、什么事永远不许做。
> 本规范**领域无关、工具无关**：正文不含任何具体项目的概念，也不依赖某一家 AI 工具的机制。
> 具体项目怎么套用见 §7。

## 1. 这份规范解决什么

一个请求从提出到关闭，会反复经手不同的执行者（人、不同的 AI 助手、不同会话）。
交接处最常丢的不是内容，而是三样东西：

- **当初为什么这么判**——改判时覆写掉原判断，理由随之消失；
- **做完没有**——没有可判定的验收标准，"完成"不可证伪；
- **这事归谁**——边界没写清，两个请求互相渗透，或者都以为对方在管。

本规范的全部条款都是为堵住这三个洞。每一条都能反向追到一次**已经发生过的**后果（见 §4 证据列）。

**适用**：任何需要跨执行者、跨时间交接的请求——开发任务、调研、决策、文档工作。

**不适用**：一次会话内即可完成且不产生长期后果的操作。为这类事情立请求是纯开销。

## 2. 状态机

```
                      ┌──────────────────────────────┐
                      │                              │
                      ▼                              │ 澄清完成
  RECEIVED ──→ REVIEWED ──→ ADOPTED ──→ EXECUTING ──┴──→ ACCEPTED ●
                  │  ▲                      │
                  │  └──── CLARIFYING ──────┤
                  │                         │
                  └──→ REJECTED ●           └──→ FAILED ●

  ● = 终态，不可转出
```

**三个终态不可转出**：`ACCEPTED` / `REJECTED` / `FAILED`。
要重开必须新立一个请求，并与原请求双向登记（R6）——不允许把终态请求"改回"活动状态，
否则状态本身失去意义，历史也无法追溯。

**`CLARIFYING` 带返回位**：它可从 `REVIEWED` 或 `EXECUTING` 进入，澄清完成后**回到来处**，
因此必须记录 `return_to`。这不是可选优化——不记来处，一次澄清就会把执行中的请求打回重审。

**为什么没有 `PLANNED` 状态**：规划的有无应由**产物**体现（存在或不存在一份任务拆分），
不由状态体现。设成状态会产生大量"名义通过"的空状态——小请求跳过规划是正常的，
而一个"可以跳过的状态"不是状态。

## 3. 各状态的准入准出

| 状态 | 准入条件（不满足不得进入） | 必有产物 |
| --- | --- | --- |
| `RECEIVED` | 请求方原话已原样落盘；已分配全局唯一且不复用的 ID | 请求记录（§5 ①） |
| `REVIEWED` | 结论四选一已写定；**边界三问已答**（R3）；与现状冲突时已摆出「按请求做 vs 维持现状」的代价对比 | §5 ② |
| `CLARIFYING` | 待澄清项已具体化为**可直接回答的问题**（不是"需要讨论"）；`return_to` 已记录 | 问题清单 |
| `ADOPTED` | 结论为采纳或修改后采纳；决策点或已定、或显式标注"待定且不阻塞开工" | §5 ③④ |
| `EXECUTING` | — | 进度可见（单一游标，见 R9） |
| `ACCEPTED` | 验收标准**逐条**判定通过，且每条判定附证据 | §5 ⑤ 的判定结果 |
| `REJECTED` | 不采纳的理由已写；记录保留不删 | §5 ② |
| `FAILED` | 失败原因已分类：**未开工 / 执行中失败 / 验收不通过** | 失败记录 |

**失败必须分类**，因为三类的后续动作完全不同：未开工的可直接重试；执行中失败的重试前
必须先查是否已产生外部副作用；验收不通过的重试没有意义——要改的是实现或标准本身。

## 4. 八条横切规则

不属于任何单一状态，全程有效。每条都追到一次已发生的后果。

| # | 规则 | 已发生的后果 |
| --- | --- | --- |
| **R1** | **原始请求一字不改**，含自相矛盾处。后续与之冲突时，在评审里记录该张力，不回头修原文 | 原话是意图的唯一证据。多轮改判后回读原话，往往才发现方向已偏——改写过就没有这个锚点了 |
| **R2** | **禁止「吸收」**：请求完成后，其长期有效事实进入现状文档的方式是**回读代码/实物重新取证重写**，不得搬运请求文件里的文字 | 一次核对核出 14 条偏差，其中 **7–8 条不是"改了没跟上"，而是"意图被当成事实写下"**——目标态文字经"吸收"通道原样进了现状文档 |
| **R3** | **边界三问必答**：含什么 / 不含什么 / **不含的那部分归谁**。第三问缺失会产生无人认领的议题 | 两个平行请求长期互相渗透，两次修正都在重划边界；另有一个请求整体被另一个吸收 |
| **R4** | **决策点用稳定 ID**（`D1` `D2`…），一经分配不复用、不重排、不带章节号 | 某文档累计 20+ 处形如「§④ D7」的跨文件引用，章节一移动全部失效 |
| **R5** | **验收标准必填**，每条须由第三方可判定，不含「合理」「清晰」「完善」这类不可判定词。**无验收标准者不得进入 `ACCEPTED`** | 一个请求状态为"已采纳"、声明六份产出物**一件未出**，因无标准而无法证伪，长期挂着 |
| **R6** | **关联双向登记**：取代、被取代、前置、引用，两侧都要记 | 上述那个请求的目标其实已由另外两个请求从别的路径达成，但它自己一侧无任何记录，成为僵尸 |
| **R7** | **改判追加不覆写**：追加「日期 + 修正」小节，写清触发、原判错在哪、新判是什么；被作废的决策点标注作废而非删除 | 两次重大改判若采用覆写，「当时为什么那样判」将永久丢失。作废的判断本身是证据，它记录了当时的信息状态 |
| **R8** | **事实断言须附可重跑取证**（文件位置、命令、或其他可复核的指针）。给不出取证的断言应删除，不靠推测补全 | 一次独立复核发现既有文档含三处错误断言；断言无取证时，"证据幻觉"没有任何机械防线 |
| **R9** | **进度只有一个面**：单一游标记录"现在卡在哪、下一步是什么"。其他文档一律不写进度 | 进度散落多处必然互相矛盾，且无法判断哪份是最新 |

R2 是其中最便宜也最要紧的一条。它不要求任何额外工作量——只要求"重写"而不是"复制粘贴"。

## 5. 请求记录的固定结构

一个请求 = 一份记录 + 按需派生的产物。记录固定七段，**任何一段不适用时须显式写"不适用"及理由**——
空段无法与"忘了填"区分。

```
① 原始请求      请求方原话，一字不改（R1）
② 评审          结论四选一：采纳 / 修改后采纳 / 不采纳 / 待澄清
                + 边界三问（R3）+ 冲突时的代价对比
③ 决策点        每个取舍一行，ID 稳定（R4）。理由须能独立成立，
                不写"理由见上文"——那样无法被别处引用
④ 落地去向      产出到了哪。"本请求不产生代码"也要显式写出
⑤ 验收标准      逐条可判定（R5）。决策型请求同样要填，
                其验收对象是决策的完备性（如"③ 中无阻塞性待定项"）
⑥ 依赖与关联    前置 / 取代 / 被取代 / 引用，双向登记（R6）
⑦ 状态流转      每次实质变化追一行。「说明」列写**改判依据**，
                而非改了什么——改了什么在 diff 里，为什么只有这里有
```

命名：ID 全局递增、一经占用不复用（被拒的也占号）；短名一看即知做什么，不含日期与状态。

## 6. 反模式

观察到的实际失效方式，逐条对应上面的规则：

| 反模式 | 表现 | 违反 |
| --- | --- | --- |
| **僵尸请求** | 状态是"进行中"，但目标已由别处达成或已无人推进，两侧都无记录 | R6 |
| **意图漂白** | 目标态文字被原样搬进现状文档，从此以"事实"身份流传 | R2 |
| **不可证伪的完成** | 宣称完成，但没有任何人能判定它是否真的完成 | R5 |
| **边界渗透** | 两个请求反复重划边界，每次都在讨论"这归谁" | R3 |
| **覆写式改判** | 直接改掉原结论，只留最新版本 | R7 |
| **引用悬空** | 引用了"第四节的 D7"，章节一动即失效 | R4 |
| **证据幻觉** | 断言了一个位置或事实，实际不存在或不含所述内容 | R8 |
| **橡皮图章** | 每段都填了，但填的是"合理""已完善"这类不可判定词 | R5 |

## 7. 映射到自动执行

本规范的状态机可直接作为**自动执行体（agent）处理请求**的领域模型。
「一个请求从受理到关闭」与「一个 run 从创建到终态」是同一个状态机，
区别只在执行者是人还是程序。

| 本规范的概念 | 自动执行体中的对应物 | 说明 |
| --- | --- | --- |
| 请求 ID 全局唯一不复用 | 幂等键 | 重复提交必须命中已有请求，而非新建 |
| 状态机 + 终态不可转出 | run 状态机 + 终态无出边 | 转换必须集中校验，不散落在各写入点 |
| `CLARIFYING` + `return_to` | 中断 / 等待输入 + 恢复令牌 | 恢复令牌须**原子消费且永不复用**；消费后投递失败必须落终态，不可悬空 |
| 验收标准逐条可判定 | 结构化产出契约（禁止未声明字段） | 产出格式不合规应拒收，而非降级接受 |
| R8 取证 | 证据 / 引用投影 | 结论必须能回指来源 |
| R7 改判不覆写 | 事件流只追加 | 状态是事件流的投影，不是可原地改写的字段 |
| 失败三分类（§3） | 失败原因码 | 重试路径按原因码分流：未开工可直接重试；执行中失败须先查副作用账 |
| — | **资源上限** | 本规范无对应物，因为人工执行天然有限；自动执行**必须显式设上限**，否则并行会把无限额乘以并行度 |

**四本必须由存储承担、不能靠执行者自律的账**：

| 账 | 为什么执行者自己做不到 |
| --- | --- |
| **幂等账**（此请求是否已受理过） | 重复触发时，两个执行体互不可见 |
| **副作用账**（此外部动作是否已发生） | 失败可能发生在"已执行"与"已记录"两条指令**之间** |
| **预算账**（累计消耗与上限） | 逐个自律无法约束整体：二十路各守"20 步"= 400 步 |
| **证据账**（结论依据什么、谁执行的、何时） | 执行者自报身份不具审计效力；且外部行为可能在本地无任何变更的情况下改变 |

四本账的共同要求是**进程被杀时依然正确**。这正是指令式约束做不到、而记账系统本职就做的事。
规模上是四张表加一个监督循环，不是一个框架。
