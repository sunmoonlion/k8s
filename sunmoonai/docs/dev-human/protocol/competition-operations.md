# 多方竞争的操作闭环与取件

> 依据的通用规范：[多方竞争协议「组织者的纪律」](../competition.md)

## T2 七环节的操作闭环

本节承接历史稿的流程导读，并按本次基线的 competition-protocol 校准路径与时序。
只在工单判为 T2 时使用；T0/T1 按 [`competition.md`](../competition.md)「档位」那张表执行。协议仍是流程真源，
某次竞争正式裁定的特例必须随工单明确给出，不能把以往竞争的特例当通用规则。

| 环节 | 谁做与交付什么 | 进入下一步的条件 |
| --- | --- | --- |
| ① 提案 | 各 proposer 在独占工作区产出候选；冻结自己的 commit、文件摘要和覆盖声明 | 候选冻结前不读他家方案或发起方倾向；全部取件对象可枚举 |
| ② 互评 | reviewer 写自述、候选集冻结、全部候选比较、其他稿值得吸收的具体主张 | 包括自己的候选；利益冲突明示；缺候选不能报全体评分；事实按证据裁 |
| ③ 裁决 | arbiter 从选定 commit 取基座；一条独立主张一个提交，形成处置记录 | 每条接受/部分接受/拒绝均有独立理由；部分接受写清边界 |
| ④ 异议 | 被处置到的来源方核自己主张；提交条目、为什么错、应当是什么、可复跑证据 | 无异议明确记录；异议不是否决权，裁决方须逐条回应；实质改结构回到 ③ |
| ⑤ 验收 | 独立 acceptor 对冻结最终版本逐条验收 | 标准疑似过期则附理由交裁决/请求者处理；不自行改标准；不通过回 ③ |
| ⑥ 确认 | principal 读取可检视的最终对象，批准具体不可逆动作或打回 | 显式批准并绑定版本，不能由“继续”或逾期默认代替；打回回 ③ |
| ⑦ 清理发布 | 指定单写者按 [`competition.md`](../competition.md)「清理与发布」收存证据、清理本次私有产物，再发布 | 目标版本比较通过、批准仍有效；只清理获准对象，不清空他家工作区 |

## 四层验证职责

**V0/V1/V2/V3 是验证职责，不是环节编号**，也不是 [IMP 的测试层次](../imp/message-rules.md) L1–L7。

| # | 谁做 | 判什么 |
| --- | --- | --- |
| V0 | 门禁脚本（[`doc-gate.py`](../../tools/doc-gate.py)、CI、pre-commit） | 链接、字段、冻结区、hash、diff、测试、角色冲突这些机械条 |
| V1 | 独立验收方——⚠ **既得利益最小的那一家，由处置记录算出**，不由谁指定 | 冻结判据里机器判不了的内容。⚠ **作者自检不能代替独立验收**；没有第二个执行者时由人验收。验收方**只能按冻结判据判，不能为让它通过而静默改判据**；判据已过期的交回裁决 |
| V2 | 被处置主张的原作者 | 自己的主张有没有被误读；异议必须带处置条目与可复跑证据 |
| V3 | principal | 意图对不对、不可逆项、抽样复算证据真实性。⚠ **不逐行读——抽样规则写进通知**，否则「抽检」会退化成「翻一翻」 |

**顺序不可倒**：V0 未过不进 V1，V1/V2 未过不请求最终批准。
T2 的来源核对 V2 在④发生，必须先于⑤的 V1；涉及正文改动后重跑 V0，随后独立验收。
新增机器判据首跑必须与人工结论对照。

处置记录包含固定三列：`出处家 / 条目 / 裁定`，裁定只能为接受、部分接受、拒绝。
验收方按以下顺序计算并记录结果：排除 arbiter 和基座作者；在其余参与方中取
“接受 + 部分接受”条数最少的一家；并列取候选行数最少者；仍并列由 principal 决定；
全部不可用由 principal 验收。若该次竞争经批准另设 integrator，按工单明确排除实际整合者。
不得因为不满意验收结果换人；因不可用换人按预先宣布的顺位与同一规则留痕。

设 `R` = 本次竞争的目录（在所属任务目录内）：

| 产物 | 进行中位置 | 收尾 |
| --- | --- | --- |
| 候选 | 各自工作区内与共享最终路径相同的相对路径 | 需要保留时收存为 `R/reviews/candidate-<名>.md`，附原 commit/digest |
| 评审/异议/验收 | `R/reviews/review-<名>.md`、`objection-<名>.md`、`acceptance-<名>.md` | 按本次保留决定收存，保持稳定取件索引 |
| 裁决稿 | 整合工作区的最终相对路径 | 最终批准后发布 |
| 处置记录 | `R/disposition.md` | 留来源、取舍、异议处置及验证引用 |
| 工单/通知/裁定 | `R/round.md`、`R/call-<环节>.md`、`R/rulings.md` | 工单状态由产物校验，历史裁定不覆盖 |

不沿用旧稿把评审平铺到竞争目录根下的命名；已冻结历史产物不为整齐而改名。
协议某处简写“清理”不授权丢掉本次仍需交付、追溯或正在被引用的对象。

## 通知、取件与人的检视面

一个流程只有规定“怎么写”还不完整，必须规定“怎么取得同一版并读到”。
每个阶段的通知至少含：带 commit 的取件方式、对象路径与行数/摘要、范围与门槛、
交付路径，以及截止判据。④起把各方受到的处置公开列在同一份通知中，便于交叉核对。

```bash
git show <冻结commit>:<仓内路径>
git diff <基座commit> <整合commit> -- <仓内路径>
git log --oneline <基座commit>..<整合commit>
```

分支可作定位线索，实际取件用冻结 commit；跨分支对象写为 `commit:路径`，
不要构造只在其他 checkout 才存在的 Markdown 链接。
通知发布后不在同一阶段偷偷改输入；必须重定对象时记录原版本、理由、受影响方，
按协议重发通知或回退，不把旧评审套到新对象上。

**请求最终确认前，把检视面准备好。**可以直接给当前可读的冻结文件；
需要读另一分支时，由供给方在获准位置创建钉 commit 的临时检视 worktree，
给出绝对路径、最终差异、验收结论与盲区。只有“稿子在某分支”不构成可确认的交付。
检视 worktree 的只读性要靠权限或明确约定，`--detach` 本身并不禁止写入；用完按 manifest 清理。

组织者不得在参与方正写候选时同步或写入其工作区。环节之间经允许同步后，
还须检查命令退出码、`MERGE_HEAD`、未合并索引和各方产物摘要；不能丢弃输出后默认同步成功。

## 投喂

每个环节，所有者在各参赛方的窗口里说同一句话，各家一字不差：

```text
看一下 <主线>/sunmoonai/docs/dev-human/protocol/GO.md，照做。
```

- **`<主线>` 换成本机的主线检出绝对路径**（见 [`competition-protocol.md`](competition-protocol.md)「产物、路径与命名」的 `M`；本机是 `~/master/k8s`）。**必须是绝对路径**：参赛方的分支从 ① 起不再跟进主线，写成相对路径，对方会读到自己 worktree 里的旧 `GO.md`。
- **说完不用再交代别的。**对方读 `GO.md` 后，按 `competition-protocol.md`「收到『继续』时怎么办」自己定位当前环节，再去读该环节的通知，通知里写了交什么、交到哪。
- **看谁交了**：按协议「环节判定」一节的判据查各家已提交的产物。以产物出现为准，不以对方说「做完了」为准。
- **对方报「缺东西 / 字段是空的 / 没有这个文件」**：是供给出了错，交给组织者去修，不要让对方自己想办法。
- **不用命令行一次性投喂**（`codex exec` / `agent -p` / `qoder -p`）：权限开关会把审批提前答掉——范围内静默同意、范围外静默退出，所有者当场批不了。
- **但可以用脚本投**，只要投给**交互会话**：消息由脚本发出，审批照样浮到所有者面前。
  自动化的是**传输**，不是**决定**——这与 [人的批准点](../approvals.md)「批准不能降级为自动批准」不冲突。

## 所有者的确认

所有者是人，不参赛，也不被投喂。所有者的确认，以**所有者本人署名的提交**为准。

**怎么认**：agent 的一切提交——参赛产物、代写的组织者文件——一律用 `--author` 署自己的名，
地址一律 `<名>@agents.local`（例如 `--author="opus <opus@agents.local>"`）。
所以判据是机械的：**作者地址以 `@agents.local` 结尾的，都不是所有者的确认。**
`GO.md` 第六节的提交命令已带上 `--author`。

所有者的 git 作者名是 `sunmoonlion`；确切地址不写在文档里，要核对就从主线上已有的提交读：

```bash
git -C ${M} log -1 --format='%an <%ae>' master   # M 见 competition-protocol.md「产物、路径与命名」
```
