## 一、项目背景【事实】

### 1.1 这是什么项目

SunMoonAI，一个面向投资研究的 AI 产品。仓库分五个平台仓（`tpl-app` 模板、`info-app` 资讯采集、`knowledge-app` 知识库与检索、`investment-app` 投资研究智能体、`k8s` 部署），必须并列放置。文档集在 `k8s/sunmoonai/docs/` 下：`project-guide/` 投影现有源码，`dev-investment-agent/` 是要建的目标态与开发流程。

内容流水线：外部信息源 → info-app 采集、治理、去重 → knowledge-app 建索引、提供检索 → investment-app 消费检索证据做研究。

### 1.2 现有源码状态

- 三个领域 App 都是 Next.js 前端（Admin/Web 各一）加单领域 FastAPI 后端，四运行角色（API / Worker / Scheduler / Migration）同一镜像。
- investment-app 后端约 8 到 9k 行，有 Run 状态机、LangGraph 检查点、事件流、副作用记账、共享 Outbox/Inbox 可靠投递（源码已接线）。一条 Pilot 链在跑：建 run → 调 knowledge 检索 → 零证据即失败 → LLM 草稿 → graph interrupt 等审批 → resume → 完成。
- `RunBudget` 四维限额已定义但生产链不调用；预算是内存态。
- **桌面客户端与本地 runtime 一行代码都没有。**目标态的三块里两块尚未开始。

### 1.3 现行目标态（`dev-investment-agent/tree-build/`）

这是讨论前的设计基线。评审者请先了解它，因为讨论的核心是"这套东西在新定位下留多少"。

**产品定位（PRD/requirement.md）**：提供 AI 研究能力与数据，类似金融数据终端，**不做投资咨询**。用户用自己的资料、在自己的电脑上、借助我们的数据与方法做研究；结论由用户下。服务对象是投资经理，能自己配置模型 key 的个人投资者同样适用。用户界面只有桌面应用。

六条硬约束：用户资料与研究成果不经过我们（存用户电脑，发给哪家模型由用户自选自付）；执行在用户电脑上；模型由用户自选、开通、付费；我们提供数据不提供观点；方法库只写方法不写判断规则；系统不替用户下判断。

**定位约束 F-POS-01 至 05**：自有数据只含事实不含观点；方法库只写研究步骤与计算方法不写买卖标准；研究产出是底稿，结论由用户填；对具体证券给评级、目标价、走势预测、买卖建议的输出必须被系统拦截并留痕；留存定性依据。

**三块**（按运行位置、信任域、发布方式切）：

| 模块 | 跑在哪 | 信任域 |
| --- | --- | --- |
| 0001-backend 后端 supervisor | 服务器 | 持久化账的唯一权威写入面；看不到资料与正文；**不调用生成式模型** |
| 0002-desktop 桌面应用（Electron） | 用户电脑 | 碰不到模型 key；独持结果私钥 |
| 0003-runtime 本地 runtime（TypeScript） | 用户电脑 | 唯一同时碰得到 key 和结果正文的一方；驱动 Codex（经 `codex app-server` stdio） |

**九站**（pipeline.md，一次委托的完整往返）：写 message → 提交 → 受理 → 派发 → 执行 → 中断 → 封装 → 验收 → 交付。每一站"谁做"是变量（人或脚本），项目在做的事就是把格子一个个从人改成脚本；现在只有"执行"这一格自动化了（AI 助手在做）。开发这个产品的过程本身也走这九站（人版），产品是把它们脚本化（agent 版）。

**后端八块**（按九站切，横穿的单列）：0002-router 受理、0004-bridge 派发、0005-interrupt 中断、0006-acceptance 验收、0007-delivery 交付、0008-competition 多方竞争（横穿派发与验收）、0001-ledger 账房（横穿五站，唯一能改状态写账的）、0003-orchestrator 编排（横穿所有步骤）。开工顺序 ledger → router → orchestrator+bridge → interrupt/acceptance/delivery → competition。

**现行路由设计（routing.md）**：任务类别分通用与专业。三层判定：用户所选（桌面应用）→ 本机预填（runtime 按本机文件的确定性规则）→ 后端兜底（只按任务文本的版本化规则）；判不出来交用户选，不得默认通用。**通用不是兜底是入口**：通用任务照常建单派发，执行后后端做一步"领域识别"（确定性规则，不调模型，只用自有数据的目录不用内容），结论随结果下发，桌面应用给出专业路径入口与预估费用，**用户点了才用专业 Profile 重跑**，不得自动升级。

**价值来源（value.md）**：核心价值是自有数据与编排。三类：领域数据与工具（知识服务与本地知识库）；领域流程与验收（后端 supervisor：拆步骤、按标准验收打回、规定何时停下问人、跨 Task 记住背景）；可靠性与可追溯。**价值检验**：去掉知识服务与编排，用户用原版 Codex 能否得到同样的结果？能，就不作为卖点投入。通用问题的回答按此不是卖点，是入口。要求做对比评测：同一批领域任务，原版 Codex 与本产品各做一遍，比准确率、验收通过率、返工次数、引用完整度、耗时。

**方法库（methods.md）**：方法收在后端，不落地用户电脑，不是 skill 包。两种形态：直发（整包随 Attempt 注入，一次执行用完，序列保不住，对应通用任务）；编排（后端按 workflow 逐步派 Attempt，每步只注入这一步要的，序列保得住，对应专业任务）。按敏感度分档：普通走直发，核心只走编排且"知道怎么做就能自己做"的步骤必须做成服务端 MCP 工具。原文承认：编排形态提高的是复制成本，不构成保密；真正抄不走的是数据、服务端计算与口径、评测闭环。方法工具只走 ①（经 runtime 代理回后端），不走 ⑤ 直连知识服务。

**七条通道**：① runtime ⇄ 后端（WSS，runtime 主动外连；派发、租约、事件、副作用、方法工具调用）；② runtime ⇄ Codex（app-server stdio）；③ 桌面应用 ⇄ runtime（本机管道）；④ 桌面应用 ⇄ 后端（HTTPS + 事件流）；⑤ Codex ⇄ 知识服务（HTTPS MCP，按设备 token 限流）；⑥ Codex ⇄ 模型厂商（用户自己的 key）；⑦ 管理后台 ⇄ 后端。

**信任边界（trust.md）**：口径是"不经过我们"不是"不出本机"——Codex 读过的内容会发给用户自选的模型厂商，界面提交前必须告知是哪一家。三把东西：模型 key 只在 runtime 侧钥匙串；结果密钥对在用户设备生成，私钥只在桌面应用主进程，runtime 只拿公钥（加密得了解密不了）；结果明文不持久保存，后端只存密文与元数据。

**分期估算（staging.md）**：桌面客户端 13–20 人周、本地 runtime 20–35、后端 15–25、知识服务 MCP 3–5、领域方法库 2–4、Windows 实测与发布 3–5，合计约 56–94 人周。第一期"验证能跑通"估 2–3 人约 6–8 周，内容含桌面客户端登录提交进度结果审批、runtime 连后端驱动 Codex、后端派发与设备配对、知识服务 MCP、一到两份领域方法。第一期结束交几位投资经理试用。

**与本次讨论相关的待定决策（decisions.md）**：D5 是否先做只接远程 MCP 的轻方案验证领域价值；D6 知识服务是否脱离编排单独提供；D7 桌面客户端怎么起步；D10b 并行 Attempt 是冗余择快还是竞争择优；D11 受理判定的实现与升级时机；D12 workflow 清单与"专业"的边界；D13 key 开通引导与费用展示；D17 定位的法律边界（**关键路径**）；D19 方法库范围与评审办法；D23 定价（建议订阅制）；D25 执行体维持 Codex 单腿；D28 runtime 用 TypeScript、首个适配器经 stdio 接钉版 codex app-server。

## 二、上午第一个议题：开发流程的 turn 机制改造（已落地）

这个议题关于**开发过程**，不是产品。放在这里是因为它和产品讨论有一处关联（见 2.5），且所有者可能也想听评审意见。

### 2.1 原机制【事实】

每一次人与 AI 的一问一答落成目录：`<任务目录>/thread/<四位号>-<种类>-<运行时id>/<四位号>-<运行时id>/`，内有 `user-message.md`（问，YAML 头含 `executor`、`verifies`）、`response.md`（答，PRD/SDD 类有）、`turn.md`（回执：`status`、`branch`、`commit` 三字段）。交回即冻结不可改，编号只增不减不复用，一个文档 thread 对一个 AI 运行时会话。定稿是人读 response 后**重写**进 `PRD/` 或 `SDD/`（"整理是重写不是搬运"）。门禁脚本 `doc-gate.py` 随提交检查目录形状、编号连续、字段、冻结区、链接。

### 2.2 所有者的提案【所有者决定】（原话）

> 现在我们要修改这个turn的机制，目前把turn的问和答写在文档里，人对ai助手的response的审核定稿也写在文档中，并且turn按顺序递增。这样长期下去，量很大，也不方便。我想改为：1，首先，无论是人还是将来代替人的脚本，要和ai助手交互，还是通过各种入口直接进行；2，只有觉得需要时，才在工作区建立专门的目录来处理人和ai助手的交互，目录名随便起，但为讨论方便，我们定为human-ai-turn，对于该human-ai-turn，可以设置多个可选目录对一个问题的相关turn进行分类，比如对于coding可设为prd、sdd、imp和uat，对于每一个目录，首先新建一个user-message.md,文件的内容即使turn的问，但是，针对问中指出的目标的不同，ai助手在回答时，可以不同的选择：如果问的目标是工作区已存在的文件，那么，回答可以针对已存在的文件进行修改，如果不存在则在问答目录下新建；人在审核定稿时，也类似：对于已存在的文档的ai回答的修改，人可以再修改，对于不存在的文档而ai新建的文档，人可以直接对ai新建的文档进行修改。3，和之前不同的另一方面是：我们不再有thread机制，对于某一个问题的turn可以多次和ai交互，但工作区里的human-ai-turn总保持最新状态。4，对于humanai-turn，它的地位和其它普通目录一样，人可以随时建也可以随时删，如果是在仓库内建立的human-ai-turn也和仓库内其它的目录相同：可建可删可提交推送

后续强调（原话）：

> 我还是要再强调指出：不是所有的turn都值得这么对待。这意味着大多数turn还将和原来一样，比如对于cli，ai还是在命令行答，它觉得有必要才在目录里新建文档。。。等等。我们这里只是觉得对于某些turn有持久化必要才这样。所以，你在接下来的重构过程中要特别注意这点，在文档里也强调这点，否则啥都走这流程，也太重了。

### 2.3 Claude 的看法【Claude 观点】

方向认同，理由：原机制是在用目录**模拟一个还没建的控制面**（手工维护一份 Task/Attempt 账本），而那份账本真正的家是产品的 0001-ledger；git 本来就记改了什么、谁改的、以哪版为底；新方案把状态映射到 git 的三个自然位置（有目录且目标文件有未提交改动 = AI 答了人没审；已提交 = 定稿；目录删了 = 结束），满足"状态从产物反推"；审 diff 比重写全文更能把注意力落到该看的地方。

必须补的四条规则（否则是纪律悄悄消失而非换载体）：

1. **AI 的答和人的改要能分开**：T1 以上，AI 答完先提交一次，人改完再提交一次。替代"交回即冻结"。
2. **追问不覆盖前一问**：追加在同一份 `user-message.md` 末尾，AI 再读时看到完整来龙去脉。
3. **改判理由进提交说明**：凡改已定稿的 `PRD/`、`SDD/` 文件，提交说明写以什么为底、改了什么、为什么。⚠ 现在靠纪律，尚无 commit-msg 钩子。
4. **目录能删，但产生过对正式文档修改的，提交后才删**。

与所有者提案不同的三处（所有者未反对）：目标路径已知时可直接在目标路径新建而非问答目录；多方竞争用分支隔离而非目录；imp/uat 子目录只放问题，答在分支上。

### 2.4 落地结果【事实】

`turn/` 目录已按新机制重写（暂存未提交）：README、turn-project、finalize、naming、glossary、user-message 模板整篇重写；`turn.md` 删除；其余九份精确替换；`protocol/` 三份一字未动（本就按分支与提交组织）。README 与 turn-project 第一节以 ⚠ 开头写明"绝大多数问答不留痕"，并给出"什么时候值得留"判据表：答会成为别的文档或代码的依据；不可逆、已知对立、判据未定；要交给另一个执行者或会话接手；同一问要发几家；人自己想留。旧 `thread/` 原件保留作历史，门禁对它们照旧查、对 `human-ai-turn/` 不查形状只查链接。两道门禁通过。

### 2.5 与产品讨论的关联【Claude 观点】

所有者纠正 Claude 一处表述：Claude 说"这个方案是把开发过程从模拟未来的控制面退回到用 git，而未来的控制面自己会有账本"，所有者指出开发过程与控制面按 pipeline 的说法始终是同一条九站，准确说法是"把开发过程退回用 git，控制面因没建完谈不上退回"，并点出推论：**将来建控制面时要尽量利用 git**。Claude 进一步区分：产物与历史归 git（内容寻址即幂等、候选绑不可变提交、merge 即采纳），状态与账归数据库（租约、fencing、预算、Interaction 一次性消费需要跨并发写入者原子成立，git 没有事务）。

## 三、上午第二个议题：产品定位

### 3.1 所有者的初始提案【所有者决定的方向】（原话）

> 还有一个要大改，因为它涉及产品定位：1，我们目前在用户提出问题时根据问题时通用问题还是专业问题来路由并通过一定的机制引导用户到专业问题，这涉及到local runtime和后端fastapi的交互。但我仔细想想，其实我们的目标定位可能时这样：用户一般仍然和ai执行体比如codex交互，但是，如果它能解决用户的问题，则问题结束，无需走云端，但是，如果用户对问题回答不满意需要寻求外部专家的帮助，这时它才需要走云端，换句话说，云端以前的专业功能可上升为通用：外部专家的知识帮助以及和ai助手更高效的帮助，本质或许是人和ai助手对解决问题的决策全的分配。2，随着产品定位的改变，许多问题都将改变：1，一个专家还是多个专家2，用户的资料是上传还是不上传；3，专家的知识如何提供以及专家如何和codex交互。。。。说说你的看法，不改代码

随后（原话）：

> 首先说明一点：我们不仅是代码开发，现在的阶段可能更主要的是产品设计。所以，你不必囿于现有的框架来思考问题，我们的根本目标是做一个有市场销路的产品，为此一切都可重构。所以，现在我们先不纠结与实现细节，我们先来定产品定位和大致框架。

### 3.2 讨论怎么演进的（四轮）

评审者请注意：Claude 前两轮的理解**被所有者纠正过**，纠正的内容是关键，这里如实记录。

**第一轮，Claude【Claude 观点】**：认同方向，指出转向的核心是"入口翻转"（云端从每一问的必经入口变成求助时的路径），提出比所有者三个问题更前置的一问——"专家是什么"，给出三种含义：A 固化的专业能力（方法库、数据、工具，云端持有、本机取用，资料不上传，合规守得住）；B 云端的专家 agent；C 真人专家（几乎必然上传资料，且是投资咨询持牌活动）。建议只做 A，C 单独立项卡在 D17 后。按 A 回答三问：多个专家、一个专家一份 Profile、用户从目录上选；上传分三级默认"问题 + 本机这一轮摘要"；知识经 MCP 代理链给、主动权翻转为本机问云端。并指出可能大幅简化的地方：结果加密跨设备取回可能不需要、桌面应用第一期可能不用做、路由领域识别整条线消失、Task 数量少一个数量级。

**第二轮，Claude【Claude 观点，后被部分纠正】**：所有者要求跳出框架从"什么东西有人掏钱"想。Claude 提出"给 AI 助手用的投研专家"：用户用自己的 agent，我们做本地知识库（本机）与专家服务（云端，以 MCP 工具形态），三层客户（所有人买数据、需要专业结论的人买专家包、机构买合规模式），先卖小私募与个人。**并断言"现有 tree-build 里的大部分是为'我们编排用户的机器'那个产品设计的，新定位下多数退役"**，认为九站、账房、派发、租约、Task 级中断、结果加密、桌面应用都不需要了。

**所有者纠正【所有者决定】**（原话）：

### 3.4 Claude 对方案的评价【Claude 观点】

所有者要求"不要接着写，给评价，更希望看到建议"。以下是原样整理。

**站得住的部分**：不自建 agent、用用户的 key，费用与隐私一起解决；两层决策权比通用/专业清楚且不需要分类器；MCP 与编排对应两层，漏斗是用户自己走过去的。

**担心的，按轻重排**：

1. **方法是三个价值源里最没验证、也最难守的，却被定为长期主体。**数据有授权壁垒，合规有机构粘性，方法没有。模型每年变强，今天手工编排能赢裸 Codex 的方法明年可能输给裸模型；资深分析师本来就会这些方法，付钱是为数据和省时间，不一定为我们版本的方法；方法要有人写，团队里有没有真正的领域专家文档里看不出。**它现在是一个假设不是事实**，整个架构的重量压在它上面。
2. **"同一个实例、经我们的 runtime"和"用户照常用 Codex"是矛盾的。**已经在用 Codex CLI、Claude Code、Cursor 的人日常不会切到我们的壳；如果只在求助时打开，第一层上下文根本不在我们这里，同一实例的好处落空。引擎钉死 codex app-server，市场另一半人用别的。
3. **token 由用户付、方向盘由我们握，激励错位。**我们的 workflow 每多一步返工、每派一个独立验收 Attempt、每开一路竞争都是用户账单；我们没有让流程变省的天然压力，用户会把贵账算在我们头上。
4. **第一期控制面太重，可能在任何人付钱之前先把一年花掉。**租约、fencing、outbox、多方竞争、跨设备密文取回都不是验证"方法有没有价值"所必需的。staging 估 56–94 人周又说 2–3 人 6–8 周，对不上。
5. **数据有什么没有答案。**如果 info-app 采的主要是公开公告与研报，MCP 层卖的是结构化、口径和引用，不是独占；定价和 value.md 都得按这个来。
6. **卖给谁没有收窄。**"投资经理"太宽；没有一个切得很窄的场景，第一个专家包和第一套评测集都定不下来。

**建议**：

1. **先用人肉跑一遍第二层，再决定建不建。**turn/ 的流程本来就是"人驾驶 AI 走九站"，现在就能用：挑一类任务，两三个分析师给五到十个真实问题，一个人扮顾问按方法一步步驱动 Codex，另一边裸 Codex 跑一遍，比准确率、返工次数、引用、耗时、token 费用，再问分析师愿不愿意为这个差距付钱。两周。**人驾驶的方法赢不了裸 Codex，自动化之后也赢不了。**这一步做完 PRD 树根才有依据。
2. **把切口收窄到一个高频、可度量、离不开数据的场景。**候选：财报季或业绩预告的快速覆盖；公告解读加财务勾稽异常筛查。第一个专家包、评测集、金标准从这里长。
3. **交接面做成引擎中立、不依赖我们的壳。**同一实例作最优路径保留，但要有显式交接的退路：用户在自己的 Codex 或 Claude Code 里干活，求助时把问题和已试过的东西打包交出。第一期不赌用户换日常工具，引擎换了不用重来。⚠ 注意这条与所有者已定的"同一个实例"有张力，Claude 的意思是**在同一实例之外保留退路**，不是推翻。
4. **把 token 费用写进评测指标和专家包标价。**一个包的真实价格是顾问费加预期 token，求助前都显示；评测加一列费用，更贵但只好一点点的方法不算赢。
5. **第一期控制面按最小可用切：单设备、单 Attempt、不并行、不跨设备。**对象模型和状态词照旧，可靠性机制先不做；账房第一期真正要的是状态机、事件、幂等三样，预算和副作用账可以晚。
6. **两件不花开发的事现在做**：盘点数据（有什么、从哪来、和 Wind 差在哪，一页）；法务先看输出形式（算了 DCF、结论栏留给用户填的底稿算不算咨询，D17 已是关键路径）。

一句话：方案形状是对的，风险在**它把最大的赌注押在最没验证的那一源上，又准备先把最重的机器造出来**。把顺序倒过来：先人肉验证方法、再收窄场景、再造机器。

终点四条同时成立：结果、验收、证据、副作用状态可靠持久化；Task 以唯一合法终态提交；有权的人断线重启换设备后仍能取得结果；通知失败可独立重试不改结果。

### A2. Task 与 Attempt 状态机（state-machine.md）

Task：RECEIVED → VALIDATING → QUEUED → RUNNING → SUCCEEDED；RUNNING 可回 QUEUED、进 WAITING、FAILED、CANCELLED；VALIDATING 可进 WAITING、REJECTED；WAITING 可回 VALIDATING、QUEUED，或 FAILED、CANCELLED。四终态 SUCCEEDED、REJECTED、FAILED、CANCELLED 不可转出。WAITING 原因码：INPUT、APPROVAL、DEVICE、DEPENDENCY、RESOURCE、EXTERNAL。QUEUED 与 WAITING 的分界：要不要一个外部事件来解除。

Attempt：CREATED → RUNNING ⇄ WAITING；PAUSED（失去租约）→ RUNNING 或 ABANDONED；终态 COMPLETED、FAILED、ESCALATED、CANCELLED、BUDGET_EXCEEDED。Attempt 终态不自动使 Task 转换。步骤推进不是状态迁移：走到第几步只动游标不动状态词；任何场景不得新增状态词（P0）。

### A3. 二十条不变量（invariants.md）

I1 原始输入可追溯不被覆盖；I2 幂等作用域内同键同摘要只对应一个 Task；I3 每次读写重新校验授权；I4 状态转换集中校验、事件只追加；I5 终态不可转出；I6 成功前结果密文与证据已持久化；I7 通知失败不改终态；I8 Attempt 失败不自动等于 Task 失败；I9 每个副作用有幂等键、状态、回执、补偿；I10 预算覆盖全部 Attempt、子 Task、工具调用；I11 结论与数值关联来源、时点、转换、执行者；I12 敏感信息不进事件日志界面；I13 一个可变事实只有一个权威写入面；I14 失去租约或 fencing 后不能提交；I15 每项义务有 ID、所有者、代码位置、测试；I16 用户 key 与设备私钥不发往本平台；I17 后端只保存密文与元数据、无解密能力；I18 工具级审批结论只来自本地；I19 离线时不产生新副作用、不离线记账再同步；I20 用户资料、文件名、本地知识库内容不上传。

### A4. 两层审批（approval.md）

工具级：单条命令、文件修改、联网；Codex → 审批回调 → runtime；桌面应用本地窗口；runtime 按策略自动放行、拒绝或交用户；结论摘要经 ① 上报存档。Task 级：澄清、计划批准、不可逆或对外动作、合并到用户工作区、预算追加、待审文档；后端落 Interaction，桌面应用审查窗口，原子消费。工具级请求可升级为 Task 级（不可逆命令、需云端决定的网络访问）：runtime 挂起、登记意图、后端建 Interaction、用户批准、后端原子消费经 ① 下发结论、runtime 核对摘要一致后回答 Codex。被攻破的后端：按 Profile 限定能力与自动放行是主防线，派发签名与本地确认是第二道。

### A5. 执行端纪律（discipline.md）

独立工作区（版本库用 worktree，其他用副本）；副作用记账分三档（只读不记；独立工作区内写入按运行时 turn 批量记；工作区外写入、网络、不可逆逐条记）；Attempt 内三条硬禁令（不得改派工、不得换执行通道、不得扩权，含不把人的批准降级为自动批准）；租约由后端签发按固定间隔续约，续约失败即暂停、重连先对账；不得离线记账再同步。

### A6. Task 契约（task-contract.md）

提交信封：idempotency_key、profile_id、profile_version、original_input（明文，不含本地资料正文）、local_refs（句柄，不含文件名）、target_device_id、client_context、requested_deadline、budget_limit。后端从认证上下文定 requester 与 tenant，不信任客户端自报。进 QUEUED 前固定：归一化目标、包含与不包含、输出 schema（研究底稿结构含用户填的结论栏）、可判定的验收条目、新鲜度与证据要求、预算与策略、允许的能力与副作用、须批准的动作、不确定性与部分结果是否允许。步骤交回物是固定版本 Artifact；格式合规由验收判定不由执行端声明；不合格按 on_reject 处置，max_reworks 用尽交人。

### A7. Profile（profile.md）

Task Profile：profile_id + version、input/output schema、normalization_rules、acceptance/evidence/freshness rules、content_check_rules（含 F-POS-04）、allowed_capabilities、default budget/retry/approval/privacy policy、device_policy、workflow_ref、step_contract。Agent Profile：工具绑定、权限边界、自动放行范围、方法、记忆策略、支持的 Task Profile；签名发布。通用 Profile 能力收紧不开领域工具；专业 Profile 对应一个 workflow。示例 DATA_QUERY、RESEARCH、ACTION。新增领域应新增 Profile 与 workflow，不改通用状态语义。

### A8. 验收矩阵节选（acceptance.md）

### A9. 代码规则里的智能体条款（constraints.md）

C-A1 一个执行体，任务差别只在 Profile 与 workflow，新增业务智能体是新增 Profile 不是 fork 代码；C-A3 四本账（预算/幂等/副作用/证据）必须落 PostgreSQL，执行端本地暂存不是权威副本；C-A4 执行引擎租用不自建，只经官方 SDK 或公开协议接入；C-A5 领域概念不进 Port 签名；C-A7 能力不足不得启用、不得静默降级；C-A8 SQLBot、WrenAI 是参考资料不是选型。

### A10. 设计原则 P0–P6（turn/sdd/finalize.md）

P0 只有一套状态机，场景差异只在配置；P1 同一事实只有一个权威写入面；P2 状态从产物反推不从声明读；P3 方向不对称，朝严谨可自裁、朝省事须人确认，默认值属于省事方向；P4 判据必须声明覆盖范围，覆盖不全比没有更危险；P5 凡能落成代码、测试或门禁的纪律必须落成；P6 设计机制前先核实动作实际发生在哪里，未核前提只能标假设。

### A11. 风险与应对节选（constraints.md）

被认定为提供投资分析 → F-POS 与法务；被攻破的后端借 Attempt 执行命令 → Profile 限能力、派发签名、本地确认；与用户自装 Codex 干扰 → 独立二进制路径与 CODEX_HOME；类别判错绕过 workflow → 三层判定、判不出交用户选；自有数据被整库拿走 → 只给片段、按设备 token 限流水印；编排逻辑被看光 → 按步下发、核心计算在 MCP 内部；强依赖 Codex → 编排与知识服务不绑定 Codex、只改适配层。

### A12. 已知未验证事项节选（decisions.md ⚠）
