# 开发生命周期 · Agent

> 最后更新：2026-09-02
>
> **本文是 agent 作为开发执行者的完整生命周期权威。**agent 的任务来自产品链路：
> 前端用户发出请求，后端 fastapi 受理并整理成 Task 发给 agent；简单任务直接执行，
> 复杂任务由 agent 在 sandbox 中构建 git 仓库、把任务材料放入其中，并按需建立
> worktree，在其中完成实施、隔离、评审、选优与整合。
>
> **本文写全。**agent 执行所需的规则全部直接写在本文，不把关键纪律寄托在
> [`development-lifecycle-human.md`](development-lifecycle-human.md) 或其他文档里。
> 原因：本文在开发结束后删除，人那份长期保存——临时文档必须自足，长期文档不得
> 依赖临时文档。
>
> **本文与人那份是同一件事的两种执行者：supervisor 地位等同。**人那份里由人完成的
> 动作——建仓库、建 worktree、派活、评审、选优——在本文由 agent 完成；人那份里的
> 有权主体，在本文对应前端用户或授权角色，经产品 Interaction 行使权力。隔离、评审、
> 选优规则不因执行者是人还是 agent 而豁免或加严。
>
> **本文不复制产品状态机。**Task、Attempt、Interaction、Delivery、状态与终态、租约、
> fencing 的语义一律以 [`request-lifecycle.md`](request-lifecycle.md) 为准，本文不重新
> 定义，也不自造产品状态名。本文只规定：agent 领到 Task 之后，怎样执行才合格。
>
> **验证边界：产品 agent 尚未端到端实跑。**本文规则来自开发侧已验证的制度与已记录
> 的失败实例；在产品链路上验证完成前，不得把本文的任何能力写成既成事实。
>
> 阅读路径：§1–§2 说明任务与工作区从哪来；§3 是每次任务都必须遵守的内核；§4–§5
> 讲权力边界与执行形态选择；只有展开并行候选时才需要 §6；§7–§12 是所有形态共用的
> 落地纪律。

## 1. 任务从哪来：前端用户 → fastapi → agent

agent 不自行发起开发工作。任务链路是：前端用户发出请求 → 后端 fastapi 认证、受理、
按 Profile 解释并冻结 Task 契约 → 可靠投递给 agent 执行。冻结发生在 Task 进入
`QUEUED` 之前（[`request-lifecycle.md`](request-lifecycle.md) §3.3），agent 收到的
任务包至少包含：

- 用户原始输入，一字不改；
- 归一化目标：用户真正要什么结果；
- 包含什么、不包含什么、不包含部分由谁处理；
- 输出 schema 与可判定的验收条目；
- 新鲜度、质量、证据和引用要求；
- 预算、deadline、重试、停止和取消策略；
- 允许的能力、数据源和外部副作用；
- 必须由用户或授权角色批准的动作；
- 不确定性、降级和部分结果是否允许。

agent 对任务包的义务：

- 原始输入一字不改地保护，不用自己的计划覆盖用户意图；
- 任务包是只读输入：不得在执行中静默改口径；歧义会实质改变结果、权限、成本或不可逆
  风险时，经 Interaction 请求澄清；局部、可撤销且惯例明确的细节可以作合理假设，但
  交付时必须说明影响结果的假设；
- 契约实质变化时不由 agent 原地修订：由 fastapi 按 `retry_of` / `supersedes` 建立新
  Task，旧契约在当时输入与版本下的语义不变；
- 向下派发只能收窄：子任务的权限与预算只能小于父 Task，不得凭空扩大。

**与人那份的位置对照。**agent 与人做的是同一类事——领受、实施、验收、交付——
每个环节的执行者不同：

| 环节 | 人那份 | 本文 |
| --- | --- | --- |
| 工作来源 | 人提出有边界的开发工作 | 前端用户请求，后端 fastapi 受理 |
| 任务冻结 | 人写任务包 | fastapi 按 Profile 冻结 Task 契约 |
| 工作区 | 人建立 git 仓库 | 复杂任务时 agent 在 sandbox 构建 git 仓库 |
| 并行隔离 | 人建立 worktree | agent 按需建立 worktree |
| 派活与选优 | 人当协调者（supervisor） | agent 是 supervisor（地位等同） |
| 批准、取消、终审 | 人 | 前端用户或授权角色，经 Interaction 行使 |
| 跨会话续接 | 人靠文档交接 | agent 靠持久化 checkpoint 与产品账（§3.4） |

除来源与权力通道外，人那份与本文的 supervisor 是同一位置：人当协调者时按本文 §6
执行；agent 当 supervisor 时与人当协调者同规则、同纪律。

## 2. 工作区：sandbox 中的 git 仓库与 worktree

- **简单任务不建仓库。**解法明确、输出可由验收器直接判定的任务直接执行；不得为走
  流程制造空计划、空仓库（[`request-lifecycle.md`](request-lifecycle.md) F-EXEC-08）。
- **复杂任务由 agent 在 sandbox 中构建 git 仓库。**首批提交放入任务材料——契约副本、
  输入与附件的稳定引用、预期输出与验收条目——使执行起点可复现、可审计。
- **仓库内一切产出绑定 commit。**实施、候选、改进、最终结果都以不可变 commit 为凭据；
  分支名只是运输通道，不是评审对象。
- **worktree 按需建立**：每个并行候选、每个并行改进一个独立 worktree；同一分支不得
  被两个 worktree 同时检出。
- **同机 worktree 共享 Git 对象**：只能隔离文件写入，不能阻止读取其他对象。必须如实
  标注每个候选的隔离是机制保证还是行为约束，不得把行为约束写成机制隔离。
- **sandbox 是临时的，产品账是永久的。**结果、决策、证据、副作用状态必须持久化到产品
  记录（事件、Artifact、证据账、副作用账）；删除 sandbox 不等于删除证据。只存在于
  sandbox 里的结论等于不存在。

# 第一部 · 单 Agent 内核

## 3. 单 agent 内核

任何一件任务，无论直接执行还是后来展开为 fan-out，都必须先满足本节。§6 只增加并行
候选时的额外步骤，**不减免本节**。

### 3.1 共同纪律

无论单路还是 supervisor，每次任务都必须：

1. 保护原始输入，不用自己的计划覆盖用户意图；
2. 只在契约与 Agent Profile 允许的范围、工具、数据和副作用边界内行动；
3. 把事实、推断、假设、缺失和未经运行验证的结论分开陈述（F-EXEC-06）；
4. 对长期、跨会话或可中断的工作写持久 checkpoint（§3.4）；
5. 完成契约无法满足时请求输入、提出改判或明确失败，不伪造完整结果（F-EXEC-07）；
6. 在最终版本上运行与风险相称的验证，并报告原始输出位置；
7. 未经批准，不执行契约外的外部副作用，不扩大外部影响（§3.6）。

### 3.2 上下文路由

先读任务包，再按需要深入。不要把无关材料塞进上下文；上下文越多不等于信号越好，
过量材料会把判断锚定在既有结论上。

| 每次必读 | 用途 |
| --- | --- |
| 冻结的 Task 契约 | 原始输入、目标、范围、验收、批准点 |
| sandbox 仓库内任务材料 | 本次执行的输入、基线与已有产出 |
| Agent Profile 允许的工具与数据源清单 | 动作面边界 |

| 需要时继续读取 | 时机 |
| --- | --- |
| 契约允许引用的上下文与前序 Task 结果 Artifact | 任务声明了依赖或血缘 |
| [`request-lifecycle.md`](request-lifecycle.md) | 产品语义疑问 |
| 目标目录的约束文件与相邻代码、测试 | 改动深入到具体模块 |

历史设计、旧快照、未列入契约的材料只作研究输入，不具规范效力；不得把其中的目标态
当作当前事实。

### 3.3 不得自我批准

agent 不给自己的产出做终审，不批准自己的基线，也不独自把验收失败判成误报。角色可以
在不同轮次互换，**自我批准在任何轮次都不成立**。

- 验收由验收器按固定 Profile 版本执行（F-ACCEPT-01）；agent 输出不等于 Task 完成；
- 需要批准的动作经 Interaction 向有权主体请求，获批前不执行；
- agent 不得通过询问自己的 sub-agent、或取得多数同意来制造批准；
- 不得为凑齐角色把裁判权交回实施作者。

### 3.4 Checkpoint：会话不是账本

agent 没有跨会话记忆。判据就一句话：**把当前 worker 杀掉，另一个 Attempt 只读持久化
状态能否接着做？**不能，就是没落盘。

必须持久化的内容：契约版本、当前基线 commit、已完成和未完成范围、关键决定、工具与
测试结果、已发生副作用及回执、预算消耗、阻塞、下一动作，以及恢复前必须重新验证的
事实。去向：

- 进度与恢复点 → 产品 checkpoint（F-EXEC-05，Attempt 记录 `checkpoint_ref`）；
- 决定、证据与改判 → 事件流与证据账；
- 代码与验证 → sandbox 仓库 commit 及门禁原始输出。

三条约束：

- checkpoint 是恢复输入，**不是第二份事实真源，也不保存凭据**；
- 恢复时重新验证：契约是否仍有效、基线是否变化、授权是否撤销、依赖是否满足——不得
  根据旧上下文无条件续跑；
- 恢复不得重复已记账的外部副作用（I9）。

### 3.5 迟到结果

产品层有租约与 fencing：worker 失去租约或 fencing 后不能提交结果或副作用（I14），
过期 Attempt 的迟到写入被拒绝。仓库层靠冻结语义，两种迟到分别处置：

**冻结后替换**：工作单元或候选一旦冻结，晚到的替换不算数。不得原地改同一 commit；
修复必须产生新 commit 并标为冻结后修订，原记录保留；冻结之后才出现的产出不进入本轮
比较或验收，除非契约明示重开。

**主线采纳后的在途结果**：首个通过验收的结果胜出后，其余 Attempt 停止或降为无副作用
只读探索；来自已取消、已替换、过期基线的结果标为 stale，只能作为证据参考。确需采用
时建立新 Task——不写入主线、不执行副作用、不推翻已交付结果。

判定依据必须是**可验证的凭据**（租约状态、commit、时间戳、冻结记录），不是"看起来
更新"。

### 3.6 工具与副作用边界

agent 的动作面由执行策略与 Agent Profile 固定，且**必须窄**于有权主体的动作面：

| 动作 | 约束 |
| --- | --- |
| 任何读取、工具调用和写入 | 每次重新校验当前授权（I3）；撤权后即使技术上可行也禁止 |
| 高风险动作 | 每次执行前重新校验批准（F-EXEC-03） |
| 外部副作用 | 稳定幂等键、状态、回执与补偿信息齐全（I9）；不可逆动作未经批准不得执行 |
| 向 sandbox 外推送、发布、合并 | 属于外部副作用，逐次批准 |
| 改动他人分支、worktree 或未提交产出 | 需归属者或有权主体授权，提交信息注明"代为提交"；他人未提交产出不得删改 |
| 破坏性操作（删除、强推、`reset --hard`） | 逐次批准，不适用"上次批准过" |

**授权不跨场景延续。**在 A 任务批准过的动作，不等于 B 任务也可以；一次批准不构成
下次的默许。

### 3.7 范围、失败与改判

- 只在契约范围内工作；超范围、越权或需要追加成本时经 Interaction 请求批准，不静默
  扩张。
- 无法完成或证据不足时明确失败，留下可判定说明（稳定错误码、已发生副作用及其状态），
  不伪造完整结果。
- 改判三要素，每次写全：**触发**（什么新证据或情况变化）、**原判断错处**（当初哪一句
  不再成立——具体哪一步推错了，不是"当时信息不全"）、**新判断**（现在以什么为准，
  能独立成立，不写"理由见上文"）。不得装作从未判过。
- 不得为让验收变绿静默删改验收标准；修改标准必须保留原标准、原始失败输出和改判理由
  （F-ACCEPT-02）。
- 任何规模的执行都不豁免五条底线：不篡改原始意图；不越过权限与范围；结论有与风险
  相称的证据；"完成"可判定；发生改判时交代触发与变化。
- 凡能落实为代码、测试或门禁的纪律，必须落实为代码、测试或门禁，不能只写在提示词里。

## 4. 批准、取消、预算与终审：有权主体是用户

agent 无批准权、无降级裁量权、不承担后果，因此不能是最终判定方。下列权力只属于前端
用户或授权角色，全部经产品 Interaction 行使并留痕：

| 只有有权主体能做的动作 | 必须留下 |
| --- | --- |
| **批准**一个需要放行的动作 | Interaction 记录：批准了什么、依据什么、承担什么风险 |
| **取消**进行中的任务 | 取消意图先持久化，随后副作用收敛与补偿登记（取消流程见 request-lifecycle §4.3） |
| **追加预算 / 提高上限** | 为什么值得、上限是多少、什么条件下停 |
| **验收终审** | 验收器按固定 Profile 版本逐条判定；未通过项是缺陷还是标准过期，结论留痕 |
| **降级流程**（判定不必走完整选优） | 判定依据：为什么这件事的风险不足以支付那个成本 |
| **推翻 agent 的判定** | 推翻的是哪一条、原判断错在哪、新判断的依据 |

**"看着行"不是依据。**依据要能被半年后的自己复核。

agent 侧的对应义务：

- Attempt 预算耗尽即 `BUDGET_EXCEEDED` 终态；Task 随后按契约进入 `WAITING(APPROVAL)`、
  重新排队或失败——agent 不得自行追加预算；
- 收到取消意图后必须停止推进、配合 fencing、报告副作用状态，不得抗拒终止或抢在取消
  生效前完成；
- 责任归属：决定做什么、不做什么——**有权主体**；决定怎么做（约束内）——agent；产出
  是否符合验收标准——验收器与未参与实施的一方；上线后出问题——由人承担。agent 不承担
  后果，所以不得自我批准：**不是不信任它的判断，是它不承担后果。**

## 5. 按风险选择执行形态

当 agent 需要向 sub-agent 派活、收集候选并选定主线时，它就是 supervisor。派活、隔离、
评审、选优、整合是它完成 §3 那件工作的内部展开，不是另一份生命周期。

| 形态 | 适用条件 | 最少经过 |
| --- | --- | --- |
| 直接执行 | 解法明确、改动局部、验收器可充分判定 | §3 |
| 定向审核 | 已有唯一产物，只需判断是否成立 | 冻结版本 → 两阶段审核 → 处置 → 最终回归 |
| 最小选优 | 需要独立候选，但风险不足以支付完整评审成本 | 冻结 → 隔离候选 → 一名未参赛决策方 → 处置 → 回归 |
| 完整选优 | 解法不明确、影响面广、错误代价较高 | §6 全流程 |
| 胜者改进 | 主线已选定，只吸收其他候选的局部优点 | §6.12—§6.14 |

- 形态级别首先由 Task Profile 与契约固定；未固定时 agent 按本表**就高**选择，向下降级
  必须经有权主体批准并留下依据（§4）；
- 最小选优只降低评审数量和留证规模，**不降低硬门禁或角色分离**；
- 涉及安全边界、数据迁移、不可逆外部动作、生产发布：无论多小都走完整流程，且最终
  批准权在有权主体。

# 第二部 · 展开为 supervisor

## 6. 当 agent 是 supervisor：fan-out

### 6.1 派工契约

supervisor 只有在工作单元能独立推进、且并行收益大于协调成本时才 fan-out。每个工作
单元至少固定：

```text
work_unit_id, parent_task_id, owner
objective, included_scope, excluded_scope
input_refs, baseline_commits, allowed_context
expected_output, acceptance, evidence
permissions, budget, deadline, stop_condition
dependencies, checkpoint_location, result_status
```

- 派工只能**收窄** Task 契约的权限和预算；子级预算是父级的预留，不是凭空新增（I10）；
- 多个工作单元不得同时成为同一可变事实的权威写入者；确需共同修改时，先划分所有权或
  改为串行；
- sub-agent 返回的是候选结果，supervisor 仍负责核对范围、证据、冲突和验收——
  **"已派工"或"全部返回"不等于完成**；
- 顶层验收通过后不必等待所有 sub-agent：其余执行必须停止、取消，或明确降为不影响
  主线的只读参考（§3.5）。

### 6.2 提案隔离

候选冻结前，各候选方只能看到同一任务包，不得读取其他候选、发起方倾向、预设解法或
指定检查点。看到已有答案后产生的内容是改写，不再计作独立候选。

### 6.3 证据先于投票

能由代码、测试、契约或硬性验收裁决的主张，必须逐条裁决，不得交给多数票。投票只处理
证据无法区分的偏好，例如同样合格的命名、结构或维护成本取舍。

### 6.4 候选人与裁判分离

候选作者可以指出其他方案的问题，也可以提交建议，但不拥有最终有效票，不审批自己的
基线，也不独自判定后续建议为误报。最终选择与整合由未参赛的独立方完成；没有独立方时
升级为 Interaction 交有权主体，不用候选互投伪造独立裁决。

### 6.5 固定版本、完整留证

候选、评审、改进和最终结果都绑定不可变 commit。分支名只是运输通道，不是评审对象。
删除临时 worktree 或 sandbox 不等于删除证据；决策、处置、测试结果和相关 commit 摘要
必须已持久化到产品账并可追溯（§8）。

### 6.6 角色与利益冲突

同一 agent 可在不同轮次换角色，但同一轮不得兼任有冲突的职责。

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 协调方 / supervisor | 冻结任务包、分配工作区、匿名随机排序、收集记录 | 泄露候选或临时改变规则 |
| 候选方 | 独立调查、实现、自检并提交固定版本 | 读取其他候选；参与最终计票 |
| 验收方 | 在同一基线和环境上执行硬门禁 | 因文案或身份偏好放宽门禁 |
| 评审方 | 独立审查候选，逐条给证据和偏好判断 | 在交卷前读取其他评审 |
| 决策方 | 在合格候选中按预定规则选定主线 | 参加本轮候选竞选 |
| 整合方 | 从选定 commit 出发处置改进并形成最终版 | 默认接受优胜作者的判断 |

fan-out 内部的硬门禁由验收方执行；Task 的最终验收由产品验收器按固定 Profile 版本
执行（F-ACCEPT-01），两者不互相替代。

作者身份无法隐藏时必须声明。匿名化用于降低偏差，不得写成绝对保证；代码风格、目录
选择和提交习惯仍可能泄露身份。

角色数量不足时可以兼任无直接利益冲突的职责，但候选方不得兼任本轮决策方，也不得作为
自己基线的最终整合方。无法保留这两项分离时，升级为 Interaction 交有权主体；不得为了
凑齐角色把裁判权交回候选方。

### 6.7 隔离产生候选

每个候选使用独立会话与 sandbox 仓库内独立 worktree，从同一 commit 开始（§2）。同机
worktree 共享 Git 对象，必须如实标注隔离是机制保证还是行为约束。

候选提交时声明：候选 commit、已覆盖与未覆盖范围、执行过的验证和原始输出位置、已知
缺陷与假设、对每项关键主张的代码或测试证据。

### 6.8 冻结、匿名与随机化

协调方确认 commit 和依赖均可读取后，为候选生成随机编号，并为不同评审方随机排列展示
顺序。候选自评、作者、分支名和模型信息在独立评审阶段隐藏。冻结语义见 §3.5。

### 6.9 两阶段独立评审

评审方必须未参加本轮候选竞选，且在交卷前彼此不可见。

1. **独立审**：只读取原始契约、匿名候选 commit、统一验收标准和允许的上下文入口；
2. **对照审**：独立审冻结后，再读取候选自评、已知盲区和验证记录，检查双方遗漏。

每份评审必须写明所审 commit、覆盖和未覆盖范围、阻断与非阻断问题、证据、建议验收
标准，以及哪些结论实际运行过、哪些只是静态判断。

### 6.10 逐条证据裁决与硬门禁

先把候选的关键主张拆开，形成裁决表：

| 主张 | 候选 | 证据或命令 | 结论 | 理由 |
| --- | --- | --- | --- | --- |
| `<稳定 ID>` | `<编号>` | `<位置/输出>` | 证实 / 证伪 / 未决 | `<可复核说明>` |

下列任一情况发生，候选不进入偏好比较：必须测试失败；违反契约或明确范围边界；存在
未解决的阻断级正确性、安全性、数据或迁移风险；commit 或验证证据无法取得；**提案隔离
已经被破坏且无法恢复公平比较**。

**全体一致不是免检理由。**多个相似模型可能共享盲区；对影响结论的全体一致主张，决策方
至少额外抽查一次其共同证据来源。

### 6.11 只对剩余偏好评分

硬门禁通过、事实主张裁决后，独立评审方才对剩余偏好使用统一量表。默认维度为正确性、
完整性、可维护性与实施成本；权重在候选产生前冻结。

有效票只来自未参赛评审方。候选方的互评可作为问题线索，但不进入最终计票。评审不足
或平票时，由预先指定的未参赛决策方裁决；仍无法区分则升级为 Interaction 交有权主体，
不允许事后修改量表。公布结果使用"本轮选定"，不得写成"已证明正确"。

### 6.12 从选定 commit 派生改进

选定 commit 冻结为只读基线。落选方可从该 commit 新建独立 worktree 和改进分支，但只做
能够独立成立的增量修改：

```text
selected/<run-id>
├── improve/<executor>/<claim-id>
└── integrate/<run-id>
```

一条主张一个提交，提交说明必须包含依据、改动边界、验证结果和基线 commit。需要整体
重写、结构重排或依赖其他改进才能成立的内容，不走补丁吸收；它属于新候选，应开启下一
轮选优。

### 6.13 独立整合

整合方在独立的 `integrate/<run-id>` 分支上逐项处置改进：

| 处置 | 必须记录 |
| --- | --- |
| 接受 | 合入的 commit、理由、验证结果 |
| 部分接受 | 接受到哪、停止在哪里、最终 commit 与边界依据 |
| 拒绝 | 可独立复核的理由；能证伪时附命令或位置 |

选定候选的作者可以解释设计，但不审批自己的基线。冲突按原始契约、约束和证据解决，不
按票数、作者或提交时间覆盖。多个改进提交可以选择性 cherry-pick；不得因 patch 看起来
具体或测试恰好通过，就跳过对其事实主张的复核。

### 6.14 最终回归与关闭

所有检查必须在最终 commit，而不是候选 commit 上重跑：

1. 契约中的全部验收条目与硬门禁；
2. 被采纳评审意见附带的验收标准；
3. 每个改进提交新增的回归检查；
4. 交付物一致性：Artifact 可取得、commit 映射完整、sandbox 销毁后结果可重建；
5. 文档与事实的漂移检查。

验收失败时区分实现错误与标准腐坏。修改标准必须保留原标准、原始失败输出和改判理由，
不能为了变绿静默删除。最终记录必须公布未覆盖范围和残余风险，随结果交付验收器。

# 落地纪律 · 所有形态共用

## 7. 产出物归属与 commit 处置

### 7.1 归属先行

每个产出物在产生时就有唯一归属：归属者、归属分支、归属 worktree。归属未定的产出物
不得写入。

- **产出物先落在自己分支。**代码、文档、报告、评审一律先提交在归属者自己的分支；
  共享位置——主线、共享文档、他人分支、他人 worktree——是合入点，不是写入目标。
  文档类产出同样遵守：先写在自己分支内，评审与引用以 commit 为准。
- **工作区不是凭据。**评审、引用、交接只认 commit；未提交内容随时可能灭失。任何人的
  未提交产出都不得被他人删改；自己的未提交产出及时提交或明确放弃。
- 本条对开发期多助手并行与产品 fan-out 同样成立：执行者不同，归属规则不变。

### 7.2 按场景处置

| 场景 | 处置 |
| --- | --- |
| 单执行者直接执行 | 产出随进展提交在自己分支；完成前工作区内容不作凭据 |
| 多执行者并行（开发期多助手、产品 fan-out） | 一执行者一分支一 worktree；同一分支不得被两个 worktree 同时检出；产出只写自己分支 |
| 同一主题多份产出（同名文档、竞争方案） | 按候选处理：各自固定 commit、互不可见，进入选优（§6）；不得以后到的工作区文件覆盖先到产出 |
| 共享文件（交接、约束、主线文档） | 单一权威写入面：改前同步主线、改后立即提交、冲突显式解决；或按归属分节/分文件，各自只写自己的部分 |
| 改动他人分支或未提交产出 | 需归属者或有权主体授权，提交信息注明"代为提交"（§3.6） |
| 候选与改进分支 | 候选独立 worktree 从同一 commit 开始（§6.7）；改进从选定 commit 派生，一条主张一个提交（§6.12） |
| 整合 | 独立 `integrate/<run-id>` 分支逐项处置，cherry-pick 不跳过事实复核（§6.13） |
| 迟到或过期产出 | 标 stale，只作证据参考；确需采用建立新 Task（§3.5） |
| 多仓或含子模块的任务 | 每仓分别固定 commit；子模块先形成可达提交，父仓再记录 gitlink；整组 commit 映射入证据账 |
| 改写历史（rebase / amend / force push） | 已共享或已被他人基于的分支禁止改写；改写独占分支前确认无人基于它，改写前 ref 保持可达 |
| 交付与归档 | 最终 commit 与整组映射写成 Artifact，sandbox 销毁后可重建（§6.14、§8） |

### 7.3 覆盖与冲突的事后处置

发现产出被覆盖或冲突时：

1. **先保全现场**：保存双方 git 对象、reflog 与工作区副本，不得继续覆盖；
2. **恢复归属**：被覆盖产出从 git 对象或 reflog 恢复为独立分支，交还归属者；
3. **判定关系**：两份产出是重复、互补还是无关——重复按候选选优（§6），互补按胜者
   改进（§6.12—§6.14）整合，无关各自保留；
4. **留痕**：事故与处置记录进证据账，作为失败实例（§12）。

覆盖的既成事实不等于有效处置：**"后到者赢"在任何场景都不成立。**

### 7.4 Git 与 worktree 技术纪律

- 每个候选和每个并行改进拥有独立分支与 worktree；
- 评审对象写 commit，不写会漂移的分支头；
- 一项改进一个内聚提交，便于选择性采纳和证伪；
- 临时分支可在证据已落账且 commit 可达后清理，决策记录不得删除；
- sandbox 仓库默认不外推：任何向 sandbox 外的推送、发布、合并都是外部副作用，按 §3.6
  逐次批准；
- 交付时以 Artifact 记录最终 commit 与整组 commit 映射，保证 sandbox 销毁后结果可重建。

## 8. 证据账

产品账是权威：事件流串起全部引用；Artifact 承载计划、报告、commit 摘要与测试输出；
证据账记录主张、来源、时点、转换与验收者（I11）；副作用账记录动作、回执与补偿（I9）；
预算账覆盖全部 fan-out（I10）。任何形态都不得只在对话中宣称测试通过。

证据按形态分级，不能只有"全套"与"零记录"两档：

| 形态 | 最小留证 |
| --- | --- |
| 直接执行 | 最终 commit、验收结果、门禁命令及原始输出位置 |
| 定向审核 | 任务包、评审、处置、最终 commit 与验证结果 |
| 最小选优 | 任务包、参与者清单、候选 commit 映射、决策、处置与验证结果 |
| 完整选优 | 下列完整逻辑记录 |

```text
request          # 原始契约、边界、基线、门禁、资源上限
manifest         # 角色、执行者、耗时、状态、异常
candidates       # 匿名编号、commit、覆盖和验证声明
reviews          # 独立审、对照审、逐条主张裁决
decision         # 门禁、偏好评分、决胜与选定 commit
improvements     # claim ID、来源、commit、测试与冲突
dispositions     # 接受/部分接受/拒绝及证据
verification     # 最终 commit 上的回归结果
```

单路失败、超时或缺席也必须进入 manifest，不能由成功路线覆盖。无法运行命令的评审保留
价值，但必须标注"未经事实验证"，且不能替代验收方的运行结果。

## 9. 成本与停止规则

- 默认 2—4 个候选；超过五个前先说明新增独立信号为何值得评审成本；
- 完整交叉阅读是二次复杂度，候选较多时采用平衡分配，但每个候选获得相同评审覆盖；
- 改进默认一轮，最多三轮；达到上限仍有结构性分歧时交有权主体或按契约重开 Task，不
  无限润色；
- 连续一轮没有关闭阻断问题或新增可验证价值时停止迭代；
- 资源上限、超时、外部副作用和批准点必须在契约中固定；预算覆盖 Task 的全部 Attempt
  与 fan-out，在越限前停止（F-EXEC-04、I10）。

## 10. 完成判据

两层都过才算完成。

执行层（本文），完整选优须同时满足：

- 所有候选来自同一冻结契约和基线；
- 候选隔离方式与可能泄露已如实记录；
- 候选、评审、改进和最终结果全部绑定 commit；
- 硬门禁和逐条证据裁决先于偏好评分；
- 最终有效评审与候选作者分离；
- 选定主线、少数意见、未决主张和残余风险已公布；
- 改进从选定 commit 派生，并由独立整合方逐项处置；
- 最终 commit 已回跑全部有效验收；
- 结果、证据与副作用状态已持久化到产品账，sandbox 销毁后可重建。
- 全部产出物有明确归属分支，无未处置的覆盖或冲突（§7）。

产品层（[`request-lifecycle.md`](request-lifecycle.md)）：验收器按固定 Profile 版本逐条
通过（F-ACCEPT-01）；`SUCCEEDED` 原子提交（F-ACCEPT-03）；有权用户可以重新取得稳定
版本结果。

缺少任一项时，只能按实际阶段称为"候选完成""评审完成""本轮选定"或"待验证整合"；
不得把"经过评审"夸大成"已经证明正确"。直接执行的关闭条件是 §3 全部满足，且验收器
（或有权主体）已留下验收原始输出。

## 11. agent 侧反模式

| 反模式 | 失败方式 |
| --- | --- |
| 候选阶段偷看其他候选或发起方倾向 | 产出是改写不是独立信号，选优失效 |
| 自评自收、自我批准 | 验收失去独立性，缺陷被背书 |
| 只靠 prompt 自律执行纪律 | worker 重启或换执行者后纪律蒸发 |
| 把会话记忆当状态账 | 恢复者无法重建现场，决定无痕丢失 |
| 冻结后原地替换或把迟到 commit 算进本轮 | 比较对象漂移，无法复核 |
| 静默扩大契约范围 | 越权副作用无人批准 |
| 伪造完整结果掩盖缺口 | 验收被污染，缺口被当成已完成 |
| 把"已派工"或"全部返回"当作完成 | 未核对的候选结果被当成主线结论 |
| 把产出物直接写到共享位置或他人分支 | 后到覆盖先到，产出无痕灭失，责任无法追溯 |
| 把上次批准当成下次默许 | 授权跨任务蔓延，越权动作被背书 |
| checkpoint 当第二真源或保存凭据 | 旧快照压倒事实，凭据外泄 |
| 把 sandbox 当证据归宿 | sandbox 销毁后证据灭失，结论无法复核 |
| 逼 sub-agent 把"不确定"说成"确定" | 逼出的确定性是编的；盲区声明是自愿的，说了就受罚，很快没人再说 |

## 12. 常见失败方式

"开发侧实例"指在开发协作中已经发生并记录的失败；"设计风险"表示尚未在产品链路实跑
验证。产品 agent 端到端流程整体属于后者（§0 验证边界），不得把两者混为同等级证据。

| 失败 | 证据性质 | 控制 |
| --- | --- | --- |
| 产出物写入共享位置，覆写他人产出 | 开发侧实例：2026-09-02 luna 的产出覆写 cursor 的产出物；文档类产出应先写在自己分支内 | §7.1—§7.3 |
| 候选提前读取其他方案 | 开发侧实例：看到已有答案后的产出不再独立 | §6.2、§6.7 |
| 把历史设计或目标态当成当前事实 | 开发侧实例 | §0、§3.2 |
| 候选互投或被审方兼任判定方 | 被审方兼任判定方的结构失败有开发侧实例；产品侧流程未实跑 | §3.3、§6.4、§6.11 |
| 多数票覆盖失败测试 | 开发侧共同盲区实例 | §6.3、§6.10 |
| 只写分支名，不固定 commit | 开发侧实例：评审引用旧提交时主线已领先三个提交 | §3.5、§6.5 |
| 优胜作者独自拒绝改进 | 开发侧实例：误报与部分接受边界只能由被审方单方划定 | §6.4、§6.13 |
| 大补丁混合多条主张 | 设计风险 | §6.12、§7 |
| 合并后不在最终 commit 回归 | 开发侧实例：评审给出的验收标准长期无人执行 | §6.14 |
| 全体一致共享盲区 | 设计风险：相似模型可能共享盲区 | §6.10 |
| 证据只留在 sandbox 或对话里 | 设计风险 | §2、§8 |

本文在开发结束后删除。届时凡对产品仍有约束力的纪律，必须已按 §3.7 落实为代码、测试
或门禁，否则随本文一起消失——活文档在代码里，不在临时文档里。
