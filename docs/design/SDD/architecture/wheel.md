# 方向盘

> 两层决策权在**同一个 Codex thread** 上怎么交接。这是产品本质落到机制上的那一处。

## 一个属性，两个取值

`Session.wheel ∈ {user, advisor}`。它是 Session 的属性，**不是状态词**（`P0`）。

| 取值 | 谁能对 thread 发 turn | 谁能回答工具审批 | 云端建单否 |
| --- | --- | --- | --- |
| `user` | 用户（经网页 → 工作台 → app-server） | 用户（网页） | 否 |
| `advisor` | 顾问（工作台内的编排） | 顾问按策略；越出策略的转 Interaction 给用户 | 是，正在跑一个 Task |

**同一时刻只有一个写入者。**用户在 `advisor` 期间发 turn 被拒（`AT-06`），可以做的是：看进度、回答 Interaction、取消。

## 交接

| 事件 | 触发 | 工作台做什么 |
| --- | --- | --- |
| `wheel.handover` 用户 → 顾问 | 用户求助：写清问题、选专家包、设预算 | 同一提交边界内：建 Task（`RECEIVED`）、写 `wheel=advisor`、写事件；若当前有未完成的用户 turn，先 `turn/interrupt` |
| `wheel.return` 顾问 → 用户 | Task 进任一终态 | 同一提交边界内：终态、结果、预算结算、`wheel=user`、交回物事件 |
| `wheel.return` 提前 | 用户取消；预算硬停后用户拒绝追加；顾问判定完成契约不可能满足 | 同上，终态为 `CANCELLED` 或 `FAILED` |

交回物契约（`AT-25`）：做了什么、什么已核实、什么未知、工作区怎么恢复（改了哪些文件、有没有备份版本）。

## 顾问接手时看得到什么

同一个 thread，所以顾问的第一个 turn 能读到用户之前的对话与产物；工作台另外把 Task 契约、这一步的方法文本与工具清单作为 turn 的输入注入。用户在第一层做过的事不重做。

## 为什么不用两个 thread

第二个 thread 拿不到用户的上下文，要么重头开始，要么把历史整段复制。复制后两个 thread 各自演进，用户回来时看到的和顾问操作的不是一份。同一实例是所有者的硬要求，这一节是它的机制。

## 粒度

第一期整段独占：交出后直到 Task 终态才交回（`D4`）。按步交替（每一步做完让用户看一眼再继续）留到验证需要时再加，只需在步骤边界上插 Interaction，不改方向盘模型。
