> 属于 [`0008-info`](0008-info.md)。2026-09-29 所有者提出：「不能仅仅是脚本调用，要有前端，让用户在界面提出」；「在其它应用要有点击的按钮之类的调用前端之后用户在前端提出采集需求」。
> 状态：**八个待定事项所有者已答**（2026-09-29：「按你的建议，全部做」），见文末。产品层面的要求与验收在 [`PRD/apps/info.md`](../../PRD/apps/info.md)，关注清单也在那里。

## 现状

| 项 | 现在 |
| --- | --- |
| 发起证券采集 | 只有管理接口 `POST /api/admin/securities/{代码}/ingestions`，要 info 管理员身份。没有页面 |
| 普通用户 | 没有任何办法提出采集 |
| 专家遇到未入库的公司 | 交回「这家公司未入库」，转人处理。人拿到这句话之后没有下一步可点 |
| info 管理端 | 有一个旧页面「Info crawl」（2026-07），管旧资讯线的文档与采集任务。没有证券采集的页面 |
| info 网页端 | 只有首页、登录、仪表盘、工具箱，没有业务页面 |

已定的约束（[决策](../../decisions.md) 2026-09-28）：

| 约束 | 内容 |
| --- | --- |
| `F-INFO-11` | 关注清单决定定时采集的范围；清单外的公司入库要所有者批准 |
| `F-INFO-12` | 采集在后台异步进行，不让用户在对话里等；专家不拿没过质量检查的数据作答 |

## 一句话

用户在 info 的网页上提出「我要这家公司的数据」；所有者在 info 的管理端批准；批准之后走现有的排队流程；别的应用用一个链接把用户带到申请页，代码已经替他填好。

## 三种人，三个入口

| 谁 | 在哪 | 做什么 |
| --- | --- | --- |
| 用户 | info 网页端 | 提出申请，看自己申请的进度 |
| 所有者（info 管理员） | info 管理端 | 批准或拒绝申请；也可以不经申请直接发起采集 |
| 别的应用里的用户 | 那个应用的页面 | 点按钮，被带到 info 网页端的申请页 |

## 流程

```text
别的应用（例如工作台）             info 网页端                 info 管理端
  专家交回「未入库」
  待办卡上出现按钮
  「申请入库」 ──── 新标签页 ────→ 申请页（代码已填好）
                                    │ 查一下：是不是已经有了
                                    ├─ 已入库 ──→ 告诉用户数据时点，不用申请
                                    ├─ 已有人申请 ─→ 加入那一个申请
                                    └─ 都不是 ──→ 提交申请
                                                        │
                                                        └──────────→ 待批准列表
                                                                      批准 / 拒绝
                                                        ┌──────────────┘
                                    进度：已批准 → 采集中 → 建库中 → 可用
  用户回到工作台，
  让专家重新做 ←─── 数据集已登记到知识服务
```

批准之后的三步（采集、建库、登记）是现有的，不用新做。

## 页面

### 用户：info 网页端

| # | 页面 | 内容 |
| --- | --- | --- |
| U1 | 申请入库 | 证券代码（从链接带来时已填好）；填完立刻显示公司是否已入库；申请理由（可不填）；从哪来的（只读）；提交 |
| U2 | 我的申请 | 列表。每个申请一条进度线：已提交 → 已批准 → 采集中 → 建库中 → 可用。失败时用一句白话说原因 |

U1 要处理的几种情形：

| 情形 | 页面怎么做 |
| --- | --- |
| 代码格式不对 | 当场提示，不能提交 |
| 已入库 | 显示数据版本与数据时点，给「回到原处」的链接。不生成申请 |
| 已有进行中的申请 | 显示它的进度，给「我也要」按钮（加入） |
| 在关注清单里但还没采 | 见待定 `P2` |
| 未完成的申请太多 | 提示上限，不能再提 |

进度里要告诉用户大概多久：批准之后通常 5 到 10 分钟（本机联调实测一家 5 到 6 分钟）；批准要等所有者。

### 所有者：info 管理端

| # | 页面 | 内容 |
| --- | --- | --- |
| A1 | 申请审批 | 待批准的列表：哪家公司、谁申请的、几个人要、理由、从哪个应用来。批准或拒绝（拒绝要写一句原因，用户看得到） |
| A2 | 证券采集 | 输入代码直接发起采集；批次列表与明细（采了几项、失败几项、为什么）；数据集列表；重新登记 |

A2 就是把现在只能用脚本调的五个管理接口做成页面。

### 别的应用：按钮放在哪

以工作台为例。

| # | 位置 | 什么时候出现 | 状态 |
| --- | --- | --- | --- |
| B1 | 待办卡 | 专家交回「这家公司未入库」时，卡片上多一个「申请入库」按钮 | 第一期做 |
| B2 | 导航 | 一个固定的入口「数据申请」，不带代码 | 第一期做 |
| B3 | 求助面 | 用户写问题时就识别出代码并提示「这家公司还没有数据」 | 以后再说。要工作台后端能问 info「有没有」 |

## 别的应用怎么调用申请页

一个普通的链接，不传任何凭据。

```text
https://<info 网页端>/<语言>/requests/new?code=600519&from=investment&ref=<不透明的引用>
```

| 参数 | 含义 | info 怎么对待 |
| --- | --- | --- |
| `code` | 证券代码 | 按证券代码的规则校验；不合规则就当没带 |
| `from` | 从哪个应用来 | 必须在 info 配置的应用名单里；不在就当没带 |
| `ref` | 来处的引用，例如工作台的委托编号 | 不解释它的含义；只存下来、原样显示。限长 128，只许字母数字与 `._:-` |

规则：

| 规则 | 说明 |
| --- | --- |
| 链接里不带身份、不带令牌 | 用户是谁，由用户自己在 info 网页端的登录决定。两个应用用的是同一个身份服务，已经登录过的用户不用再输密码 |
| 回去的地址不从链接里取 | 「回到原处」的地址由 info 按 `from` 在自己的配置里查（每个应用登记一个回跳地址的模板），再把 `ref` 填进去。这样别人伪造链接也不能把用户带到别处 |
| 打开方式 | 新标签页。用户在工作台里的会话不受影响 |
| 每个应用把拼链接的代码写在一处 | info 网页端的地址来自配置，不写死 |

这一套「一个应用把用户带到另一个应用的某个页面」的做法以后别处也会用到，建议写进模板，成为各应用共用的约定。

## 后端

### 新增的数据

| 表 | 一行是什么 | 主要的列 |
| --- | --- | --- |
| 采集申请 | 对一家公司的一次采集请求 | 证券代码；状态；对应的采集批次（批准之后才有）；批准人、时间、拒绝原因 |
| 申请人 | 谁要这个申请 | 申请编号；用户；理由；从哪个应用来、引用；时间 |

分成两张表，是因为一个申请可以有多个申请人（`F-INFO-22`）。

### 状态

| 状态 | 含义 | 谁推动 |
| --- | --- | --- |
| 待批准 | 已提交 | 用户 |
| 已拒绝 | 所有者拒绝，带原因 | 所有者 |
| 已撤回 | 所有申请人都撤回了 | 用户 |
| 已批准 | 已排队 | 所有者 |
| 采集中、建库中 | 跟着采集批次走 | 现有的排队流程 |
| 可用 | 数据集已发布并登记到知识服务 | 现有的排队流程 |
| 质量未过 | 采到了，但没通过质量检查，不发布 | 现有的排队流程 |
| 失败 | 采集或建库出错 | 现有的排队流程 |

批准之后的状态不另外存，从采集批次与数据集的状态算出来，避免两处对不上。

### 接口

用户面（登录的用户）：

| 接口 | 作用 |
| --- | --- |
| `GET /api/web/v1/securities/{代码}/availability` | 这家公司有没有数据、有没有进行中的申请 |
| `POST /api/web/v1/security-requests` | 提出申请，或加入已有的申请 |
| `GET /api/web/v1/security-requests` | 我的申请 |
| `POST /api/web/v1/security-requests/{编号}/withdrawal` | 撤回我的这一份 |

管理面（info 管理员）：

| 接口 | 作用 |
| --- | --- |
| `GET /api/admin/security-requests` | 申请列表，可按状态筛 |
| `POST /api/admin/security-requests/{编号}/approval` | 批准：发起采集 |
| `POST /api/admin/security-requests/{编号}/rejection` | 拒绝，带原因 |

现有的五个管理接口不变，A2 页面直接用。

### 限制

| 限制 | 值 | 状态 |
| --- | --- | --- |
| 一个用户同时未完成的申请数 | 见待定 `P5` | 未定 |
| 申请理由的长度 | 500 字 | 远程的建议 |
| 用户看不到别人的申请理由与身份 | 只看得到「还有几个人也要」 | 远程的建议 |

### 分层

按 [工程结构](../architecture/engineering.md) 的四条规则写：状态与规则在领域层；申请的服务在应用层，经端口用存储；接口按面分开放（用户面、管理面）。自动检查会拦住违反。

## 待所有者定的八件事（2026-09-29 已答：都按远程的建议）

`P7` 的建议是「与 `S10` 一起定」，所以它仍然没有定；在定之前不自动加入关注清单。

| # | 事项 | 选项 | 远程的建议（即所有者定的） |
| --- | --- | --- | --- |
| `P1` | 申请页放在哪 | 甲 放在 info 网页端，别的应用用链接带过去；乙 每个应用各做一个申请框，后端之间互相调用 | 甲。所有者说的就是这个做法；乙要每个应用重复做一遍 |
| `P2` | 哪些申请要批准 | 甲 全部要；乙 关注清单里的公司自动批准，清单外的要批准 | 乙。清单里的本来就在定时采集的范围内 |
| `P3` | 按钮怎么打开申请页 | 甲 新标签页；乙 在当前页跳过去，办完再跳回来 | 甲 |
| `P4` | 数据可用之后怎么让用户知道 | 甲 用户自己回申请页看；乙 原来的应用里也显示进度；丙 浏览器通知或邮件 | 先甲。乙要两个后端互通，放第二期。与网页设计的 `W2` 一起定 |
| `P5` | 一个用户同时能有几个未完成的申请 | 一个数 | 5 |
| `P6` | 管理端的「证券采集」页（A2）做不做 | 做；不做 | 做。这就是「不能仅仅是脚本调用」 |
| `P7` | 申请被批准并入库之后，这家公司要不要自动进关注清单 | 是；否 | 与 `S10` 是同一件事，一起定 |
| `P8` | 旧资讯线（网页、RSS）要不要也能申请 | 要；先不要 | 先不要。旧资讯采到的文档专家现在查不到（知识服务的 MCP 上没有文档检索的工具），申请了也用不上 |
