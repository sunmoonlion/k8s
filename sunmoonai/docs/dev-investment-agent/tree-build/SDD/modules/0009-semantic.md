# `0009-semantic` 语义层

> 内网；落在 `knowledge-app` 的知识后端里，位置在 MCP 工具的后面。把 WrenAI 的引擎当成库嵌进来。
> 依据：2026-09-27 的探针（原件留存在 [`0009-semantic-probe/`](0009-semantic-probe/README.md)，结论并入本文「探针结论」）；所有者同日决定正式做。
> 甲、乙、丙三段已做完并在远程机验过，见文末「实现状态」；丁段（部署）等集群。
> 这改动了规则 `C-A8`，见 [决策](../../decisions.md)「已定：语义层采用 WrenAI 引擎」。

## 解决什么

| 现状 | 用了语义层之后 |
| --- | --- |
| 只读防护是手写的正则：只许 `SELECT`/`WITH`，禁几个关键字 | 先按语法树检查，再由引擎按语义模型规划；库本身关掉一切对外访问 |
| 口径表只是文字，专家照着它手写公式 | 口径是可执行的定义，专家**报口径名**，由引擎算；「不适用」由定义里的条件判定，不靠模型自觉 |
| 跨表口径要专家自己写关联 | 表与表的关系写在数据集的自述里，引擎负责关联 |
| 字段能不能看，没有控制 | 语义模型里没有的字段与表查不到（第一步先全部暴露，机制留好） |

不变的：我们自己的 MCP 服务端、令牌、限流、按专家包过滤工具、每个结果带来源与数据版本（`F-KNOW-01`、`F-KNOW-02`、`F-KNOW-03`、`F-KNOW-07`）。

## 功能义务

| ID | 义务 |
| --- | --- |
| `F-SEM-01` | 引擎钉版本，只用三样：把 SQL 规划成目标方言、把按口径名的查询翻成 SQL、语义模型的文件格式。它的问答、图表、云端、记忆、自带的 MCP 服务端一律不用（`C-A9`） |
| `F-SEM-02` | 语义模型从数据集**自带的说明**生成，不手写：表结构、字段字典、口径表、表间关系。同一份数据集文件生成的结果相同 |

| `F-SEM-07` | 口径的内部名字不得与它引用的字段同名（探针问题二）；对外仍用口径表里的名字 |
| `F-SEM-08` | 有开关，默认关。关着时知识服务的行为与现在完全一样 |
| `F-SEM-09` | 开着时，同一条查询在新旧两条路上的结果一致：问数二十题的 31 条真值查询与财报十三题的 15 条真值查询逐项相同 |

## 数据集怎么变成语义模型

数据集文件不变，仍是 info 产出的 SQLite。知识服务取到文件后：

1. 读自述：每张表的字段与类型；`field_dictionary`（中文名、单位）；`metric_dictionary`（口径）；`table_links`（表间关系，可以没有）。
2. 转换：每张表原样写进 DuckDB 文件，表名加前缀 `phys_`。类型照搬：整数、小数、文字。日期保持文字，这样比较与截取的写法和 SQLite 上一致。
3. 生成语义模型：每张表一个模型，模型名是原表名；表间关系；口径生成口径集。
4. 缓存：DuckDB 文件与语义模型按「数据集文件的 sha256 加生成器版本」存放。生成器版本变了就重建。

### 数据集自述的约定（第二版）

`metric_dictionary` 在现有七列之后增加六列。现有七列不动，所以旧的读法不受影响。

| 列 | 含义 |
| --- | --- |
| `kind` | 口径的种类。现在只有 `row`：基础表的一行算出一个值，不做汇总 |
| `base_table` | 这个口径以哪张表为基础 |
| `value_expression` | 可执行的表达式，只引用基础表的字段；引用有关系的表写成 `表名.字段` |
| `applicable_when` | 可执行的条件；为空表示总是适用 |
| `reason_if_not` | 不适用时给出的原因 |
| `queryable` | 1 表示可以按口径名查询；0 表示只有定义，要由专家按定义从取数表算 |

新增两张表：

| 表 | 列 |
| --- | --- |
| `table_links` | `link_name`、`from_table`、`to_table`、`cardinality`（`one_to_one`、`many_to_one`）、`on_columns`（逗号分隔的同名字段） |
| `table_keys` | `table_name`、`key_columns`（一行由什么确定）、`label_columns`（看懂这一行还要带什么，例如报告类型、会计年度、口径） |

没有第二版自述的数据集（现在的零售库、第一版财务数据集）：三个原有工具照常可用；按口径名查询答复不支持，改用口径定义加 SQL。

需要上一期数值的口径（平均净资产收益率）`queryable` 为 0：一行表达不了，先不做。

**为什么是逐行而不是汇总**：财务报表一行就是一家公司的一个报告期，而且季报、中报、年报是累计数。
按维度求和的口径集用在这里，只要分组少带一个字段，就会把四份累计数加在一起。所以财务口径定义成逐行的，
查询的结果固定是「基础表的每一行一个值」。探针里验证过的口径集（按维度汇总）适合零售库那样的明细事实表，
等有数据集带这类定义时再做。

**口径的定义是数据不是代码**：表达式进知识服务后先按语法树校验，只许字段、常数、四则运算、比较、逻辑、
`CASE`、`COALESCE`、`NULLIF`、`ABS`、`ROUND`。不合规的口径不提供并记日志，不影响别的口径。

## 查询怎么走

```text
工具收到 SQL
  → 前置检查（语法树）：只许一条查询语句；不许带库名或模式名的表引用；
    不许引用以物理前缀开头的表；不许读文件、读环境、读密钥的函数；长度封顶
  → 引擎规划（严格模式）：只认语义模型里的表；输出目标方言的 SQL
  → 我们执行：只读挂载的库；关闭对外访问并锁定配置；超时中断；取回行数封顶
  → 类型规整 → 带上来源、时点、数据版本、查询摘要
```

按口径名查询多一步：把「口径名、筛选、排序」生成 SQL，然后走同一条路。筛选的值用语法树拼进去，不做字符串拼接。

## 工具

| 工具 | 变化 |
| --- | --- |
| `describe_schema` | 列的是语义模型里的表与字段，带中文名与单位；不出现物理表名 |

## 不做

| 不做 | 原因 |
| --- | --- |
| 引擎的记忆功能、问答、图表、云端、自带的 MCP 服务端 | 前者要向量库，后几样会调模型或连外网（`C-A9`） |
| 字段级的隐藏清单 | 机制已有（语义模型里不列就查不到）；现在的数据集是为暴露而建的，全部列出。要隐藏时在自述里加一张表 |
| 按时间粒度上卷（按月、按季汇总） | 日期保持文字。财务报表一行就是一期，不需要；零售库要用时再加日期类型的计算字段 |
| 需要上一期数值的口径按名查询 | 见上 |
| 行级权限 | 现在按数据集授权，不到行 |

## 风险

- **上游变得快**：四个月发了八个小版本。钉版本；引擎只在一个文件里被引入；升级前重跑 `SEM-03`、`SEM-04`。
- **镜像变大**：约 600 MB。开关默认关，但依赖是装着的。
- **方言变化**：专家写的 SQL 从 SQLite 方言变成 DuckDB 方言。常见写法两边相同；日期函数不同。工具说明里写明方言。
- **同名泄露是上游的问题**：我们靠前缀与前置检查两层堵住，不依赖上游修复。
- **本地的 WrenAI 分叉**：`/home/zym/repo/WrenAI` 在探针时从 0.7.0 合并到了上游 0.15.0（本地合并提交 `10062760`，未推送；合并前的位置是 `5f8bc24e9dad64a60d12bf37be137f99940365cd`）。产品装的是发布包，不依赖这个分叉；它只用来查源码。
