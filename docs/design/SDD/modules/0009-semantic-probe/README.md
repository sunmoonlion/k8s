### 发现的问题

### 问题一：同名时可读出未暴露字段（安全）

条件：模型名与物理表名相同，且查询里用带库名的全名引用物理表。
现象：`SELECT SUM(cogs_cents) FROM lesson23.main.order_performance` 返回了模型里没有暴露的成本字段；`SELECT *` 返回全部 20 个字段。严格模式、关闭回退都不能阻止。
原因（推断）：严格模式只拿表的裸名去对照模型名单；改写后的 SQL 用同名的公共表表达式承载模型，但带库名的引用不会被它遮住，直接落到物理表。
规避：
1. 命名规则：物理表名不得与模型名相同（例如物理表统一加前缀）。不同名时第 9 项全部通过。
2. 我们自己的前置检查：在交给引擎前，用语法树拒绝一切带库名或 schema 的表引用。
3. 是否向上游报告由所有者定（对方有 `SECURITY.md` 的私下报告渠道）。**本探针没有向外发送任何内容。**

### 问题二：口径名不能与它聚合的字段同名

我们口径表里 `net_revenue_cents` 的表达式是 `SUM(net_revenue_cents)`。照搬会被引擎判为循环依赖。探针里把求和类口径改名为 `total_<原名>`，原名保留在属性里。正式采用时口径表要定一条命名规则。

### 问题三：没有 SQLite 连接器

数据集要先转成 DuckDB 文件。转换本身可行，行数全部对上。探针里逐行插入很慢（约 5 分钟），正式做要用批量方式。日期字段在 SQLite 里是文本，转换时改成了日期类型，时间粒度聚合才可用。

### 问题四：返回值的类型要我们自己规整

大整数求和以字符串或 Decimal 返回；日期以毫秒时间戳返回；比率保留十位小数。MCP 工具对外的格式要统一。

它有 MCP 服务端（0.13 起），提供查询、口径查询、上下文、知识检索等约二十个工具。但其中**没有鉴权、限流、数据版本引用**。所以我们的做法应当是：保留自己的 MCP 服务端和令牌、限流、引用、按专家包过滤工具这些义务，把它的引擎放在工具后面。
