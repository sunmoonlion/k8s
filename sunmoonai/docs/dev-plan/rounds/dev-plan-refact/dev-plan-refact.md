## 1. 背景

### 1.1 现状：文档体系是「一轮一轮长出来的」，不是设计出来的

`dev-plan/` 现有 **12 份文档、6975 行、399 节（其中 3 份在 `archive/` 乙格）**，外加 `rounds/` 下 64 份轮次归档、
`working/request-baseline/` 下 15 份原始需求档案。

它们的形态是**历次轮次的沉积**，不是按任何一种成熟工程实践组织的：

| 现有文档 | 它其实是什么 | 问题 |
| --- | --- | --- |
| `working/request-lifecycle.md`（647 行 42 节） | **三份文档焊在一起**：34 个 `F-*` 功能需求 + 22 个 `AT-*` 验收用例（**PRD 血统**）、七个对象的**领域模型**、`I1`–`I15` **不变量与规格** | 三种读者被塞进同一份文件 |
| `rounds/`（64 份） | 决定 + 完整审议过程 | **决定不可检索**：26 条裁定散在 3 个 `rulings.md`，**编号还撞车**——`R1` 在三轮里分别指三件不同的事 |
| `protocol/`（975 行 61 节） | **工作方式规范**（近似 RFC 流程定义 / 工程手册） | 它**不是**实施计划的一部分，但从未被正式定位 |
| `constraints.md`（214 行 15 节） | 架构约束 / 护栏 | 定位大体正确 |
| `agent-dev-guide.md`（827 行）与 `agent-dev-refact.md`（1461 行） | **两份同职能文档**，都自称「面向今后开发的指导」 | ⚠ 违反 P1「同一事实只有一个权威写入面」；且后者地位**从未被裁定过** |
| `development-plan.md`（142 行） | 产品路线图 + 架构取向**混合** | 两样在标准实践里分属不同文档 |
| `implementation-plan.md`（93 行） | 交付计划 | 结构正确，但**阶段一任务清单是空的**，写着「U1 未定，现在列的任何任务都会作废」 |

### 1.2 触发事件：所有者提出按正规流程组织

所有者 2026-09-07 提出初步映射：`request-lifecycle` ≈ PRD、`rounds` ≈ ADR、
当前在做的 ≈ TLD、`protocol` ≈ 实施计划的一部分、`constraints` ≈ 开发纪律。
起草者对其中三处提出异议（见 §5 Q1–Q3），**本文不预设哪一方对**。

### 1.3 为什么必须走完整流程

所有者原话：**「鉴于工程巨大，意义重大」**。三条客观理由：

1. **规模**：399 节，是 `runtime-refact` 轮（64 节）的 **6.2 倍**；
2. **权威层**：重构对象包含**内核** `request-lifecycle.md`——它被 40 份文档引用、
   有 **71 个带行号的锚点**指进去。动它等于动全部取证的地基；
3. **不可逆性**：文档一旦重排，**丢掉的东西不会有人发现**——
   这正是 `runtime-refact` 轮已经栽过的形态（一次通读做融合，整节内容消失，事后才补回）。

### 1.4 一条必须先说的边界

**这一轮不改任何结论，只改组织方式。**
凡涉及「某个设计对不对」的问题，一律不在本轮处理——那是另起工作单元的事。
候选若在重构中**顺手修正了某个结论**，该处按 §4.1 B3 处理。

只给映射不给架构的候选，按 §6.3 一票否决。

| 必答 | 说明 |

⚠ 起草者对所有者的初步映射有三处异议，**一并列为不预设的问题**，

| # | 问题 | 声明 |

| **Q1** | `request-lifecycle.md` ≈ PRD？ | **不预设。**起草者认为它是 PRD + 领域模型 + 规格三者焊在一起（34 个 `F-*`、22 个 `AT-*` 是 PRD 血统，但七对象与 `I1`–`I15` 不是）。**拆或不拆都要论证，且拆必须过 B2** |
