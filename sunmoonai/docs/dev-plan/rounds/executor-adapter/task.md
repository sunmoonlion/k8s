## 1. 背景：一次实测把一个字段问题变成了架构问题

2026-09-06 夜，`runtime-refact` 轮 ② 首次尝试**由组织者自动分发**四家执行者。
四家里三家零产物，且**三种失败的退出码全是 0**：

| 家 | 现象 | 它自己说的话 |
| --- | --- | --- |
| `qwen` | 评审做完只在内存里，零文件 | 「请批准以下命令」，然后退出 |
| `luna` | 评审做完写不进 | 「沙箱无权写 `index.lock`，请在有权限的会话执行」 |
| `cursor` | 写出产物但不提交（三次） | ——（`-p` 非交互模式下就是不提交；所有者交互式跑一次即提交） |

起初按三个独立问题处理，逐个调权限档位（`workspace-write`、`dont_ask`、`accept_edits`），
**两次调错**。随后所有者指出真正的层次：

> 「投喂和用 SDK 机制不一样吧，你作为智能体调用 ai 助手，应该走 SDK 吧？
> 否则很多回复权限等如何解决？」

按这个视角复看，三种失败是**同一件事**：
`codex exec` / `qoder -p` / `agent -p` 都是**一次性、单向的非交互模式，没有回话通道**。
agent 一旦需要一次往返（批准、澄清、追加权限），就只能放弃并退出。
于是调用方只能**事前猜它待会儿要什么**，猜错即一轮空跑。

### 1.0 实测：自动化那条路今晚**没有走完**，它在每个决策点回落到人

⚠ **这是事实记录，不是结论。**结论归 §2.2 与 §7，本节只交代问题的形状，
好让接手的人不必重走一遍 2026-09-06 那一夜。

两条路当晚各跑了一次：

| 路径 | 结果 |
| --- | --- |
| **人在环**（所有者交互式跑 `agent`，无 `-p`） | **端到端跑完**：`cursor` 自己读、自己写、**自己提交**，全程无人替它做任何一步 |
| **取代人自动化**（组织者执行 `codex exec` / `qoder -p` / `agent -p`） | **没有走完**：产物能出来，流程走不完 |

自动化那条路当晚**回落到人四次**，且回落点**不是随机的**——
每一次都精确落在**需要当场做一个决定**的地方：

| # | 回落点 | 实际由谁决定 | 按设计本该由谁 |
| --- | --- | --- | --- |
| 1 | `luna` 写完产物、提交被沙箱拒 | 组织者代提交 | 运行时 |
| 2 | `qwen` 权限档不足，写操作全被拒 | 所有者裁定换档，组织者改登记表 | router / 策略 |
| 3 | `qwen` 写完产物、无 Bash 提交不了 | 组织者代提交 | 运行时 |
| 4 | `kimi` 阻塞在读 stdin，17 分 29 秒零 CPU | 组织者改调用方式 | executor adapter |

**四次回落，四次都是人。**所以自动化那条路当晚的成绩准确说是
**「产物能出来」，不是「流程能自己走完」**。

#### 由此看到的机制差异（**是观察，不是判定**）

> **人在环**：决策通道**在带内**——执行者随时能问，人随时能答，问答就在**同一次执行**里。
> **投喂**：**没有决策通道**，只有**事前授权**。
>
> ⚠ **精确说法**：投喂取消的**不是「需要决定」，而是「在飞行中回应它的能力」**。
> 需求一直在，只是每个决策点都变成一次失败。
> 本节初稿写成「把需要决定这件事本身取消掉」，**是错的**，
> 它把「能力缺失」说成了「需求消失」——所有者当场纠正。

**而 SDK 那条路上，做决定这件事照样能做，做决定的仍然可以是人。**

运行时不是替人做决定，它是**把人接进来的那条通道**（`agent-dev-refact.md` §2.1 的
`principal channel`）：执行者发出审批请求 → 运行时收到 → 按策略自决，**或转给人** →
答复回去 → **原地继续同一次执行**。人一直在环里，**只是够到他的方式变了**。

由此，「**取代人自动化**」这个说法本身就误导，本轮不要沿用：

> 自动化取代的是人的**传输角色**（`dispatch_event{mode = manual}` 那笔欠账），
> **不是人的 principal 角色**（权力表那八行）。

这正是整套架构立足的那条区分——**人是 principal 不是执行者；传输是欠账不是权力**。
候选若在任何一处把这两者混写，按 §4.1 的 **B4** 处理。

现行模型把这两者都记成 Agent Profile 的**字段**（`dispatch`、`observability`）。
本轮要判的正是：这个差异到底落在**字段值**上，还是落在**哪些状态边存在**上。

#### ⚠ 一条不得外推的边界

上表证明的是「**投喂** ≠ **人在环**」。
它**没有**证明「**自动化** ≠ **人在环**」——因为**一次 SDK 接入都还没跑过**。

若 SDK 能做到「收到审批请求 → 答复 → **原地继续同一次执行**」，
那么自动化就不再是「取消决定」，而是**把决定从人手里搬到 router / 策略手里**；
那时两者就是同一台机器、只差谁持有决策权，**「字段」的说法重新成立**。

**不得把「投喂 ≠ 人在环」悄悄扩写成「自动化 ≠ 人在环」。**这正是 §7 Q1 要判的事，
而 Q1 已写明：**判「字段」而论证扎实，应当高于判「结构」而论证草率**。

### 1.1 这与本项目已有的三条规定冲突

| 出处 | 规定 | 现状 |
| --- | --- | --- |
| `constraints.md` **A4** | 执行层租用不自建，**依赖边界严格限定在 SDK** | 实际在 shell 里调 CLI 的非交互模式 |
| `agent-dev-refact.md` §2.1 | **executor adapter**：决定「怎么调、**怎么看、怎么拦**」 | 三件一件也做不到 |

### 1.2 已查证存在、但**行为未验证**的接口

## 2. 题目：两问，第二问是重点

### 2.1 第一问（工程）：建 executor adapter

让运行时经协议/SDK 驱动执行者，做到 §2.1 要求的三件事：**怎么调、怎么看、怎么拦**。
最低限度要能回答：运行时能否**收到**执行者的审批/澄清请求、能否**答复**、答复后能否**继续同一次执行**。

### 2.2 第二问（架构）：投喂与 SDK 的差异，是字段还是结构

现行模型把「怎么调执行者」放成 Agent Profile 的**字段**
（`dispatch = argv | manual`、`observability` 四档），并据此主张
**开发与产品只差 Profile，唯一状态机不变**（`agent-dev-refact.md` §2.1、§2.2）。

**本轮要判定这个主张在这一处是否成立。**已知的一处疑点（**是疑点，不是结论**）：

> §2.7 的中断恢复依赖运行时能 `interrupt()` 执行者、再 `Command(resume=)` 令其**原地继续**，
> 前提是**运行时持有那个循环**。投喂模式下循环在助手自己手里，运行时只见「之前」与「之后」，
> **既不能中断也不能恢复**。于是 Attempt 执行期的 `WAITING(INPUT)` 对
> `dispatch = manual` 的执行者**似乎不可实现**：一问即等于本次 Attempt 结束，只能新开一次。

若该疑点成立，则差异**不止是「看得多细」，而是「哪些状态边对它不可用」**——
而现行登记表只记了前者。

⚠ **本文对结论不预设立场**，见 §7。

## 4. 边界

### 4.1 不可违反

| # | 硬约束 |
| --- | --- |
| B1 | **不自建被调 agent**（`constraints.md` A4）。本轮建的是**适配层**，不是 agent |
| B2 | **不新增内核状态词**，不走合法转换表之外的边。若结论是「某些边对某类执行者不可用」，那是**能力声明**，不是新状态 |
| B3 | **参数存在 ≠ 参数管用。**§1.2 表里每一条都要**最小 spike 实测**后才可引用 |
| B4 | **不得把「没查到」写成「没有」**（§8.1） |
| B5 | 不改动 `runtime-refact` 轮的任何产物 |

### 4.2 不含

- 不含权限档位的具体取值调优——那是**结果**，不是题目；
- 不含签名/身份问题。本轮解决「能不能自动化」，**不解决「谁签的」**，
  `agent-dev-refact.md` §2.6「这道关卡的证据强度是零」不因本轮而改动一个字。
