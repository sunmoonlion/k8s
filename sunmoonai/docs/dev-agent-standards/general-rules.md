# 通用规则

交给 agent 的每一件事都是一个**任务**。本文写所有 agent 开发任务及其交付共同遵守的基本理念与纪律，以及任务怎样随交付长出来、交付怎样验收、怎样记录、怎样返工。
每个任务的 `task.md` 按 [PRD 规则](task/prd/prd-rules.md) 写（模板见 [附录](task/prd/prd-template.md)），交付物按 [`deliverables/`](deliverables/) 的规范验收。其余规范见 [README](README.md)。

## 基本理念

**任务就是从入口进来、可能经过后端派发给模型的那段文本。**它可能只是一段自然语言，也可能是按规范严格写成的文本。
这里的规范必须对**没有任何格式**的一段话成立；严格写成的任务自然也满足。所以规范只规定「要表达出什么」，不规定「要用什么格式」，
也不假设有什么机制会替模型补上任务里没写的东西。

由此有一条贯穿全部规范的做法：**任务没说清、而会实质改变结果、权限、成本或风险的，停下来问，不自行假设；
无关紧要的，按最小、可逆的理解去做，并在交付里写明做了哪些假设。**下文凡说「按任务」「派工时的要求」，
指的都是派工时那段任务文本里说清了的内容。

## 总则

1. **每种交付都有三样东西**：交付物、验收条件（门）、没过门时退回哪一种任务。写完文字不等于过门。
2. **派哪几种任务、各交多深，由开发需要定。**小而可逆的改动可以由一次任务交齐所需内容，引用已有依据即算过门；
   但不能为了省文档，在没有依据时把某项填成「不适用」。
3. **开工条件与完成条件是两回事。**「候选验证通过」「指定版本发布成功」「需求满足」是三个不同的结论，
   状态记录必须说清是哪一个，不能都写「已完成」。
4. **门的执行归属分三档，不混进同一张「已保证」清单**：机器已能判；当前靠纪律、将来可机器化；
   本质上只能靠纪律（一直标 ⚠）。凡声称由机器判的，必须能写出一条跑出非平凡结果的命令。
5. **规则要有载体。**能跟着测试或提交自动跑的，做成自动检查；做不成的，老实标 ⚠ 并靠自检。
   要人记得去跑的检查，和写在文档里的规矩没有本质区别；检查的结论不能取决于某台机器的工作区状态。

## 执行者的共同纪律

不论单路还是并行，不论人还是 AI，八条都成立：

1. **不用计划覆盖原始需求**；
2. 只在范围、工具、数据、预算和副作用边界内行动；任务没说清边界、而越界会有影响时，先问；
3. **区分事实、推断、假设、缺失和未运行验证的结论**，不可混写；
4. 对可中断的工作持久化检查点；
5. 无法满足完成条件时请求输入或**明确失败**，不交半成品；
6. 在**最终固定版本**上运行与风险相称的验证；
7. 报告盲区、副作用和残余风险；
8. 未经授权不推送、合并、发布、删除远端资产或扩大外部影响。

第 3 条是 [UAT](deliverables/uat/uat-rules.md) 证据采信的前提：分不清事实与推断，采信分级就无从谈起。

## 改判

改判本身不是问题，装作没改过才是。每次改判写清三件事：

| | |
| --- | --- |
| **触发** | 什么新证据或什么情况变化 |
| **原判断错处** | 当初**哪一句**不再成立——不是「当时信息不全」，是具体哪一步推错了 |
| **新判断** | 现在以什么为准；**能独立成立**，不写「理由见上文」 |

不得装作从未判过，**也不得为了让检查变绿而静默删除旧标准**。修改验收标准时保留原标准、
原始失败输出和改判理由。把结论写进上游文档前回读代码或实物重新取证——文字改对了、
代码里还是旧的，比不改更糟。

## 任务的生命周期

任务不是事先排好的：它们随着交付一个个长出来——
上层任务的设计交回并通过后，才生出下层任务；交付被打回，就在原任务里返工。

### 一个例子

1. 一开始只有一个任务：「开发某个 agent」。它有一份 PRD。
2. 规划 agent 交回设计（SDD），设计里说「分前端和后端」。设计通过验收后，**这时才**建出「前端」「后端」两个子任务。
3. 后端的设计又拆出几个部分，通过验收后，**这时才**再建出这几个子任务。
4. 某个子任务交给执行 agent 去改代码；验收 agent 检查后判定不通过，打回重做。记下这是第几次返工、为什么返工。
5. 同一个任务返工超过两次，就停下来交给人判断。

下面四节就是把这个过程写成规则。

### 任务目录里放什么

```text
<任务目录>/
├── task.md          任务书：从入口收到的任务文本，原样保存（必有；可以就是一段自然语言）
├── log.md           派工、交回、验收、返工的记录（必有）
├── composition/     本任务交回的 SDD（任务要交回设计才有）
├── components/      子任务，每个子任务是同样结构的目录（SDD 通过后才有）
├── sdp.md           本任务的 SDP：计划、实施记录、改动所在的提交、测试与回滚（任务要交回 SDP 才有）
└── uat.md           本任务的验收结论（任务要交回验收结论才有）
```

改动过的代码和文件留在它们本来的位置，任务目录里只用提交号引用，不拷进来。

#### task.md 就是任务书

按 [PRD 规则](task/prd/prd-rules.md) 写（模板见 [附录](task/prd/prd-template.md)）。

#### log.md 逐行追加，不改旧行

| 时间 | 事件 | 交付物 | 版本（提交号） | 由谁 | 说明 |
| --- | --- | --- | --- | --- | --- |
| … | 建立 / 派工 / 交回 / 验收通过 / 打回 / 返工 / 停下交人 / 人裁决 / 取消 / 完成 | SDD、SDP 或 UAT | … | 哪个 agent 或人 | 打回、返工、裁决时按下文要求写 |

### 子任务什么时候建

- **只有本任务的 SDD 交回并通过验收之后**，才按 SDD 里拆出的部分建子任务目录。SDD 没通过，不建；**不预先建还没派出的子任务**。
- 子任务目录一建出来就写好 `task.md`（内容来自那份 SDD 的相应一节，**随 SDD 一起经人批准后生效**），派工的一方在 `log.md` 记一行「建立」，写明派生自哪份 SDD 的哪一版、哪一节。
- SDD 改版后拆分变了：新多出来的部分建新目录；不再需要的子任务**不删目录**，在它的 `log.md` 记「被 SDD 第 n 版取消」及原因，状态为已取消。
- 只交 SDP 或只交 UAT 的任务没有 SDD，也就不生子任务。

### 怎么看出做到哪了

状态**从文件和提交推出来，不在任何地方手写**；给人看的进度视图由此生成。
`log.md` 只是索引：通过、打回必须对应一份已提交的验收记录，两者对不上时以验收记录为准。

| 状态 | 判定依据 |
| --- | --- |
| 已建立 | `task.md` 已提交 |
| 已派工 | `log.md` 有这项交付物的「派工」 |
| 已交回 | 交付物文件（或改动所在的提交）已提交，`log.md` 有「交回」及提交号 |
| 已通过 | 有针对**这一版**（提交号）的验收记录，结论为通过 |
| 被打回 | 最新一份验收记录针对这一版，结论为不通过 |
| 停下待人 | 返工次数达到上限，`log.md` 有「停下交人」，还没有「人裁决」 |
| 已取消 | `log.md` 有「取消」及原因 |
| 已完成 | 任务要求交回的每一项都「已通过」，且全部子任务「已完成」或「已取消」 |

一个任务可以同时有几项交付物处在不同状态；任务本身的「已完成」只看上表最后一行。

### 返工怎么记、最多几次

- **打回**必须写明：任务里的哪一条要求（或本规范的哪一条）没满足、证据在哪、要求改什么；任务本身没说清、无法判定的，写「不可判」并交给人，不自己发明标准。返工派回给出问题的那一步——设计有问题回 SDD，实现有问题回 SDP。
- **每次返工**在 `log.md` 记一行「返工 第 n 次」。如果标准或判断也变了，同时写清改判三要素：触发、原判断错在哪、新判断（见本文「改判」一节）。
- **旧版本不覆盖**：返工交回的是新的提交，`log.md` 记「第 n 版取代第 n-1 版」及原因；验收结论永远绑定到具体的一版。
- **同一项交付物被打回第三次时停下**：不再自动派工，`log.md` 记「停下交人」。由人判断是 PRD 本身有问题、判据写错了，还是要换做法或换执行者；人的裁决记入 `log.md` 后才能继续。
- 返工上限可以在 `task.md` 里按任务调整；**调高上限须人确认**——多给几次自动重来的机会，就是少一次人的检查。
- 某项交付物需要多个 agent 各交一份再比较时，按 [多方竞争的轮次协议](protocol/round-rules.md) 进行；轮次内部的回退不计入本任务的返工次数，轮次最终被打回才计入。

## 任务持久记录模板

`task.md` 与 `log.md` 合起来承担下面这份模板的各栏：①②（任务书）在 `task.md`，④⑧ 在 `log.md`，⑤⑥⑨ 在各交付物里。
不按上面的目录结构组织的任务，也可以直接用这份模板作为持久记录。**这份模板对应最严格的任务**；一段话的任务只需 `task.md` 原文加 `log.md`。


载体可以是数据库、Issue、PR、事件流或仓库文件，但**不能丢失原始请求、边界、验收、基线、
证据和改判历史**。用这份模板时，**空栏必须写「不适用」及理由——空着与「忘了」无法区分。**

```markdown
# <任务编号>：<短名>

## ① 原始请求
<用户原话，不改写>

## ② 受理、边界和授权
- 规范化目标：            - 包含：                - 不包含：
- 不包含部分归属：        - 权限与批准点：
- 预算、期限和停止条件：  - 负责者 / 工作单元：
- 可写根与输出命名空间：
- 发布目标 / 整合者：

## ③ 基线与工作区
- 任务 / 尝试：           - 工作区：              - 来源引用：
- 基线提交：                                      - 适用指令：

## ④ 决策点
| ID | 问题 | 结论与理由 | 证据 |

## ⑤ 工作单元与落地去向
| 工作单元 | 负责者 | 分支/工作区/命名空间 | 产出提交/摘要 | 发布目标 | 状态 |

## ⑥ 验收标准与证据
| ID | 标准 | 判定 | 证据 |

## ⑦ 依赖、交互与副作用
- 依赖：                  - 澄清/批准：           - 副作用账：

## ⑧ 状态流转与改判
| 时间 | 状态/改判 | 触发 | 原判断错处 | 新判断 |

## ⑨ 交付与清理
- 最终提交 / 产物：                               - 来源 / 取代关系：
- 发布位置 / 发布者：                             - 未覆盖与残余风险：
- 交付通知：                                      - 工作区清理：
```

⑧ 的改判字段对应本文「改判」一节的三要素——「原判断错处」写「当时信息不全」不算填，要写出具体哪一步推错了。
