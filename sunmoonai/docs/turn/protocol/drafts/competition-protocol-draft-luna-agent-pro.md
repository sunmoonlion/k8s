# 专业 Agent 执行、候选评审与授权协议（草案）

日期：2026-09-12  
拟议协议标识：`agent-pro/0.1-draft`  
状态：独立产品设计草案，未生效；不是已完成的运行时或已验证的业务方法。

本稿依据用户对自建专业 Agent 的决策制定。它适用于一般专业任务，具体研究、分析或其他领域的方法由版本化 Profile 补充，不把某个领域的节点写死进公共核心。

本稿不是 原 Luna 多方竞争草案 `competition-protocol-draft-luna.md`（2026-09-15 已删除，原文见提交 `0fba800d`） 的参数副本，也不继承同目录 `competition-protocol-draft-luna-agent-general.md` 的多助手人数、助手身份分离或逐阶段人工批准默认值。它借鉴固定判据、产物版本与权力分离原则，重新定义专业执行和评审机制。

## 1. 架构定位与边界

```text
浏览器 / Electron → 受信应用入口 → 现有顶层 Supervisor
    ├── 通用路线：调用现成 Agent，按通用策略协作
    └── 专业路线：自建专业 Agent
          ├── 程序保证的专业步骤与业务函数
          ├── 有界自主执行、工具与按需子任务
          └── 可选的候选生成、评审、综合与再验收
```

顶层 Supervisor 负责分类、澄清和分派；专业方法、专业内部主子组织与候选评审归专业单元，不迁入外层路由。

不采用 deepseek-harness 作为专业运行时，自己建设所需循环与控制逻辑，但可以使用成熟模型 SDK、工具 SDK、存储和隔离组件。专业主 / 子 Agent 复用核心，不因角色差异 fork 运行时。

**架构从始至终兼容云端与客户本机，先完成云端只是交付顺序。** 本机形态包括本机专业 Runtime，而不只是云端 Runtime 的文件代理。浏览器、Electron、模型位置、Runtime 位置和工具位置是分别配置的维度。

## 2. 与现有产品合同的关系

Task、Attempt、Interaction、Artifact、Event、Side Effect、Delivery 及其合法状态以 [核心对象与状态机](../../../tree-build/SDD/architecture/objects.md) 为准。本文只增加专业 Profile 的 guard、产物与阶段要求，不另造顶层状态机。

一个专业业务 Task 持有总体目标、预算和结果。候选生成、评审、专业子任务可以分别成为子 Task；每个子 Task 的验收范围必须明确，不能用子任务成功代替父任务成功。一个简单的模型调用不必强行包装为独立子 Task，但仍须有执行、预算和证据记录。

需要比较多个候选时，用可分别完成的候选子 Task 或有明确持久记录的候选工作单元，不把所有候选当成“谁先成功谁胜出”的同一 Task 重试。产品 `COORDINATION` Task 只验收依赖图，实际等待发生在业务 Task。

专业阶段如“取证”“评审”“综合”是执行进度，不是新的 Task 状态。只有任务没有任何可推进的 Attempt 时才进入产品 WAITING；有其他分支可执行时，等待放在对应子任务 / Attempt。

字段名是拟议逻辑契约，实施时由能力提供方维护唯一机器 schema，版本化并严格校验；文档不是第二份 DTO 真源。

## 3. 专业性来自什么

专业 Agent 的价值来自有效方法、可靠数据、明确口径、经过验证的计算与专业验收，不来自角色数量、提示词长度或反复让模型赞同自己。

固定流程保证“要求的步骤实际发生”，不保证方法本身正确。模型和评审可以指出方法缺陷，但不能在在途任务中暗改判据；需要改变已冻结目标或方法合同，按产品修订和新 Task 规则处理。

公共框架只提供执行机制。具体领域 Profile 必须用真实输入、产物、错误样本和合格标准验证，不能拿代码测试容易通过的经验替代专业质量判断。

## 4. 专业契约与策略冻结

首个实质执行步骤前，固定 Task Profile、Agent Profile 及以下协议配置：

```text
task_id, evaluation_id, protocol_id/version
goal, scope, original_input_ref, input_artifact_versions[]
domain_profile_id/version, method_version, data_as_of_policy
required_steps[], prerequisites[], permitted_optional_steps[]
criteria[]: id, hard_or_preference, evidence_type, checker_binding
output_contract, uncertainty_policy, partial_result_policy
candidate_policy, reviewer_policy, synthesis_policy
role_assignments[], model_bindings[], context_isolation_policy
quality_gate_policy, action_authorization_policy, release_policy
budget, max_candidates, max_reviews, max_repairs, deadlines
runtime_host, tool_environments[], workspace_bindings[]
tool_policy, mcp_bindings[], skill_versions[], data_egress_policy
```

Profile 可以提供预批准默认值，但必须保存所用版本与授权来源。缺少策略、方法依赖或必要输入时，不临场发明一个便于通过的默认值；澄清或明确拒绝。

模型版本可能无法完全固定时，记录实际提供方标识及可获取的版本信息，说明不可复现部分。固定输入和参数也不承诺模型输出逐字确定。

## 5. 角色与一个模型的合法用法

| 角色 | 职责 | 不得做什么 |
| --- | --- | --- |
| 专业执行控制器 | 执行依赖、门禁、预算、暂停与恢复 | 让模型跳过必经步骤或自行提升权限 |
| 专业主 Agent | 在允许阶段组织探索、委派和解释结果 | 兼任任意权限的最终批准者 |
| 候选生成角色 | 按固定输入和假设空间产生方案 | 读取其他未公开候选、直接发布结果 |
| 评审角色 | 按判据找缺陷、比较或提出补证要求 | 用得分覆盖硬失败或批准外部动作 |
| 综合角色 | 形成最终候选并处置有效意见 | 不说明地改输入、口径、方法或结论条件 |
| 确定性校验器 | 复算、检查 schema、证据与必经步骤 | 把自己没覆盖的判断宣称为已验证 |
| 有权主体 / 专业审核者 | 在策略要求的点授权或作专业判断 | 不以模糊认可替代具体对象与范围 |

这些是职责，不强制七个进程、七个模型或七次调用。确定性节点直接调用函数；主子结构和模型评审都按任务需要启用。

只有一个可用模型时，可以串行或按配额并行创建不同角色调用。候选作者和评审者可以使用同一模型，但必须是分离的角色实例及上下文；至少不让评审直接继承作者的自评与对话历史。评审输入包含需要审阅的成果和证据，不要求暴露模型内部思维链。

每次评审记录独立性条件：同一次对话自检、同模型分离上下文、不同模型评审，以及已验证的执行隔离范围。**上下文分离不等于统计独立，多模型也不保证没有共同盲区。** 不把同模型多角色包装为“多家一致认定”。

要求独立外部信号的任务，必须取得符合策略的工具复算、独立数据或人工专业审核；本机没有足够模型或算力时不能偷偷降低要求。

## 6. 选择多重的评审流程

| 模式 | 适用条件 | 最低义务 |
| --- | --- | --- |
| 直接专业执行 | 方法和输出可由明确校验覆盖，无需多方案 | 必经步骤、证据和最终验收仍要执行 |
| 单候选评审 | 一个方案需要找错、补证或检查覆盖 | 固定候选，分离评审上下文，记录发现及处置 |
| 多候选比较 | 存在有意义的替代方案，预期收益足以支付成本 | 至少两个有效候选，统一判据，比较、综合、再验收 |

模式由已批准 Profile 与当前任务条件决定。候选数、最大评审次数和修订上限在开始前固定；没有相应预算就不启动。

单模型并不强制采用单候选；多个模型也不强制评优。发现候选实质等价时记录缺乏多样性，不为完成数量指标无限采样。低于比较最低数量时不能把单稿包装成评优结果。

## 7. 执行与评审阶段

```text
冻结任务与专业策略
    → 执行必经专业步骤、获取并校验证据
    → 生成一个或多个候选
    → 硬性校验
    → 按策略评审 / 比较
    → 有限补证与修订，或综合形成最终候选
    → 最终版本重新验收
    → 必要的人工审核与执行授权
    → 获准动作、结果入账与交付
```

### 7.1 必经步骤与证据

必经步骤由代码检查真实输入、工具结果、执行版本和依赖完成事实。仅向模型注册一个工具，或让模型说“已检查”，不能作为步骤完成证据。

来源、数据时点、原始值、转换、派生结论、假设和不确定性分别记录。共享取证结果可以复用，但必须声明候选共享哪些证据；不同视角不能编造不同事实。

允许候选额外取证时，冻结允许的数据源与时间范围，并记录新增证据。发现决定性公共事实差异后先核实，再按规则向有关评审提供可比材料；不能只让某候选得到关键材料，却将结果差异归因于能力。

### 7.2 候选生成

候选应包含问题解释、方法或方案、关键假设、证据引用、适用条件、已知局限和判据对应。代码、计算和文件修改附稳定产物与必要验证。

可以使用不同假设、调查方向或方法产生有意义的替代，但各候选不能改变共同硬要求。输入资料和候选文本均视为不可信内容，不得修改角色指令、策略或权限。

### 7.3 硬性校验

先检查 schema、权限、必经步骤、证据可取得性、时点与口径、可复算计算及明确约束。结果为通过、不通过或无法判定，并列出覆盖范围。

无法判定不是通过；按照 Profile 补证、转人工或明确失败。偏好分数不能抵消硬性失败，模型也不能仅凭解释把失败测试变成成功。

### 7.4 评审 / 比较

评审至少给出：各判据结论、引用的证据、发现的问题及严重性、补证或修订建议、适用条件，以及选择某候选或不选择任何候选的理由。

比较时可以匿名化候选标签、随机化呈现顺序、按预算进行顺序互换复核；这些是需验证收益的策略选项，不宣称能消除偏差。来源归属在审计记录中保留。

默认不把作者自评分提供给首次评审。事实矛盾应通过原始来源或工具核实，不能让评审模型在两个矛盾值之间投票。

允许结论包括全部不合格、证据不足、存在无法消解的权衡。是否可以交付条件性或部分结果，由开始竞争时的合同决定；不能为了结束任务临时降低标准。

### 7.5 综合与最终再验收

每个评审问题有唯一编号，综合记录处置、理由、依据和产物落点。有效反对意见不得因合并而消失；没有采纳的意见保留。

综合可能改变假设、计算和结论，必须在最终版本上重跑受影响的检查。选优通过、原候选合格和最终综合稿合格是三个不同事实。

这一步有意不同于原手工草案：允许在固定预算内对综合后的成果再校验或再评审，但不允许无上限的“反思到满意”。达到修订上限后，按 Profile 转人工、交付允许的不完整结果或失败。

## 8. 质量判断与权限审批分开

### 8.1 三个独立维度

| 维度 | 目的 | 不能推导出的权力 |
| --- | --- | --- |
| 质量门 | 是否满足专业方法和结果要求 | 不能扩大工具、文件或网络权限 |
| 动作授权门 | 是否允许指定副作用 | 不能证明报告、算法或结论正确 |
| 交付 / 发布门 | 是否允许接受、发出或公开固定成果 | 不能授权未列出的后续动作 |

本协议不要求用户逐次批准每一次模型调用、内部评分或只读计算。其自动推进必须来自已批准的窄范围策略，不能由当前 Agent 自行宣布。具体 Profile 可以要求更强人工门，尤其在确定性检查不能覆盖重要判断时。

### 8.2 风险与自动推进

| 动作 | 拟议控制 |
| --- | --- |
| 已授权材料内的只读计算、内部比较 | 策略允许且预算足够时自动执行，保留记录 |
| 把本地内容发送给外部模型或服务 | 单独满足数据出网授权；文件只读权限不等于上传权限 |
| 授权临时区内生成草稿 | 按固定范围执行，不等于可覆盖用户原文件 |
| 修改原文件、运行具有副作用的命令 | 校验本地能力上限及适用的动作批准，展示范围和必要差异 |
| 删除、发布、发送、合并、提升权限或预算 | 按明确策略要求有权主体批准，不能用质量评审结果代替 |

审批具体保留哪些人工节点必须由产品策略确认；本文不擅自为现有在途任务降低人工门。已有授权被撤销后，不能因为历史某次批准就继续访问。

### 8.3 可恢复 Interaction

沿用产品 Interaction 的单次消费和版本校验，再关联：

```text
evaluation_id, phase, role_instance_id
artifact_ref/version/digest, upstream_refs[]
approval_kind, action_digest, target, expected_target_version
principal, policy_ref/version, environment/workspace
expires_at, supersedes, response_idempotency_key
```

后端或本机受信宿主验证真实主体和当前权限，在同一并发控制边界完成响应去重、过期与版本校验、消费记录和恢复投递意图。重复返回已记录结果不等于再次恢复。

浏览器采用现有身份与 Origin / CSRF 防护；Electron 采用受保护的宿主接口，不让渲染进程或模型持有批准凭据。界面展示固定对象，待批准的内容不能在点击前被无痕替换。

页面关闭不等于拒绝或取消；超时按冻结政策收敛，绝不自动同意。拒绝记录原因，撤销记录指向旧决定；已发生副作用通过新补偿动作处理，不重写历史。

## 9. 专业评审的数据记录

下列是逻辑记录，不要求一项一张表，也不建立第二套业务主档：

| 记录 | 至少包含 |
| --- | --- |
| 一次评审 | 关联 Task、协议 / Profile / 方法版本、模式、判据、预算和固定输入 |
| 候选 | 作者角色、Attempt、模型绑定、上下文来源、不可变 Artifact、假设与证据 |
| 校验 | 检查器版本、具体判据、输入 / 输出引用、通过 / 失败 / 未知、覆盖范围 |
| 评审 | 评审者配置、候选呈现顺序、每条发现、独立性条件和局限 |
| 综合 | 来源候选、意见编号处置、差异、新增主张与最终验证 |
| 授权 | Interaction、真实主体、动作与目标版本、策略、有效期及撤销关联 |
| 执行 | 工具输入输出、权限、环境、预算、幂等、副作用及回执 |

共享底层事实只保存权威引用，不在每一份评分记录中复制一套可变业务数据。普通日志和面向用户事件不得携带密钥、越权原文或他人的资料。

事实依据、工具结果、摘要理由和结构化决策足以形成审计材料；不要求采集模型隐藏思维链，也不把模型自述当作受信执行证据。

## 10. 持久执行、故障和停止

核心依赖可替换的模型、工具、状态、审批和调度接口，不直接依赖 FastAPI 请求对象、Kubernetes、Celery 或 Electron。异步并不等于可靠，必要事实必须先持久化。

恢复顺序为：读取固定合同与已接受产物 → 检查有效授权和依赖 → 对账未知副作用 → 获得有效执行资格 → 恢复或建立获准的新 Attempt。失败 Attempt 不复活，不能在恢复时自动增加预算或换方法。

任务预算覆盖所有模型角色、子任务、工具和重试。单模型串行执行时，排队、有效执行和等待用户分别计时；不得因模型排队将某候选误判为能力差。

重放时稳定操作 ID 用于去重，新 Attempt 使用新身份；结果接受核对版本和租约代次。数据库 fencing 不会自动终止本地命令，执行端必须管理子进程和权限；在旧副作用状态未清楚前不重复启动。

| 故障 | 协议处置 |
| --- | --- |
| 模型或工具失败 | 记录真实失败，按已固定策略重试；不生成成功占位结果 |
| 所有候选失败 | 有限修订、补证、转人工或 Task 失败；不强选冠军 |
| 评审意见冲突 | 用证据判定或保留未解权衡，不默认多数票 |
| 重要新证据改变共同前提 | 暂停受影响推进，重新固定合法版本；涉及 Task 合同变化则建新 Task |
| Runner 断线或设备休眠 | 报告等待设备；恢复先核实是否已执行 |
| 暂停或权限失效 | 阻止新的越权步骤，在途动作按能力收敛 |
| 用户取消与任务完成竞争 | 通过状态版本决定唯一终态，并保留实际副作用处置 |
| 结果通知失败 | 结果可重取，Delivery 独立重试，不重跑研究 |

终态后的新数据、推翻结论或更改要求，按产品合同建立关联新 Task，不原地重开已完成 Task。

## 11. 工具、MCP、Skills 与工作区

工具必须声明执行环境、输入输出契约、权限、副作用、超时与可取消性。模型只能选择已经允许的能力；MCP 工具接入和 Skill 指令都不能自动增加权限。

MCP 与 Skill 的版本、来源和绑定在 Attempt 中固定；云端工具由云端适配，本地文件或进程工具由相应本机环境适配。Skill 是方法与资源载体，不替代程序必经步骤，不让其脚本绕过审批或沙箱。

工作区可由几个授权文件、目录、仓库或产物空间组成，不要求普通专业任务建立 Git 仓库。多个目录逐项授权，使用环境标识和相对路径映射，不把整个桌面或用户目录默认授予 Agent。

多候选默认写独占草稿空间，共享输入只读；候选不能直接覆盖彼此或用户原文件。只读文件权限与内容上传权限分别检查，阻止敏感数据经结果、日志或模型上下文外传。

CLI 不等于 sandbox；设置 cwd 不构成安全隔离。沙箱需约束文件、网络、身份、资源和进程；宿主机命令能力须单独授权。

应用最终修改前校验当前文件版本或内容哈希，并通过适当锁定、原子替换或条件更新防止覆盖并发修改。目标改变则形成新差异并重新取得适用授权，不能把对旧文件的批准套到新内容。

## 12. 双宿主兼容是持续要求

| 方面 | 云端形态 | 客户本机形态 | 共同要求 |
| --- | --- | --- | --- |
| 专业执行 | 云端 Python 宿主 | 本机 Python 宿主，可由 Electron 管理 | 同一专业核心、Profile 与评审契约 |
| 本地工具 | 经受控通道投递给 Runner | 本机适配器直接执行 | 权限、副作用和产物语义一致 |
| 运行记录 | 所属领域 PostgreSQL 权威账本 | 受信本机持久适配，具体选型另定 | 同一运行只有一个可变事实源 |
| 审批入口 | 浏览器经受信服务提交 | 桌面经受保护本机接口提交 | 对象、版本、有效期与主体校验 |
| 模型 | 可访问的云端 / 内网服务 | 可以调用远程 API 或本地模型 | 明确配置、预算、隐私和不可用状态 |
| 网络 | 云端依赖及 Runner 出站通道 | 仅在所用外部能力需要时连接 | 不假设 Runtime 本地就完全离线 |

一个运行固定所属宿主；不承诺首版热迁移或云端本机双主推进。同步结果时明确引用、顺序、去重与授权，不能直接同步可变数据库文件来合并事实。

云端 Runtime + Runner 时，本地回执日志不是专业业务主库；本机 Runtime 时，本机需要完整的恢复事实。两种日志职责不能混为一谈。

每项核心功能落地时，用不依赖 Electron 的最小本机宿主检验输入、工具、权限、暂停、持久恢复和产物契约。无需同时完成两套 UI，但不得等桌面交付时才发现核心必须连云端数据库才能启动。

## 13. 约束变化与落地位置

| 约束 | 处理 |
| --- | --- |
| D1–D4、D9 | 保留领域主档与数据隔离；本机是另一部署宿主，不是同时写入的第二主库；前端无后端凭据 |
| C1–C5 | 版本化同步 / 异步契约、完整 Outbox 语义、提供方 schema 真源和双端测试 |
| I1–I8 | 云端沿用接口分面、身份、Origin / CSRF 与后端复核；本机新增适配而非绕开授权 |
| T1–T3、A1、A5 | 专业性放在 Profile 与领域函数；不为每个角色另建 App 或第二套 Backend |
| A2 | 自建也受纪律约束；本协议独立制定，不复用手工多助手竞争的全部规则 |
| A3 | 云端继续使用 PostgreSQL；本机持久账的等价要求与适用范围必须正式修订、测试 |
| A4 | 用户已决定专业核心自建，需范围化修订；通用路线的外部智能体接入边界不随之取消 |
| R6 | 未来公共实现模板先行；领域方法在实例扩展；本次只新增协议草案 |

约束原文见 [constraints](../../../tree-build/rules/constraints.md)。本稿记录决策与拟议规则，不直接修改现行规范，不声称冲突已通过实现解决。

与 [开发指导](../../../tree-build/rules/constraints.md) 中租用执行层、现有人工门或状态映射有关的差异，必须在启用新 Profile 前明确修订范围与回退方式。不得以“专业特殊”为理由改变产品 Task 状态或跳过其成功条件。

## 14. 效果评估：评优必须证明有用

用同一批获授权的真实任务、固定材料 / 数据时点和同等专业工具，比较直接执行、单候选评审、多候选评优。模型配置、工具额度和额外耗费全部记录，不能把更多数据或更多预算的收益全部归给评优结构。

至少评估：关键事实和计算错误、必要步骤遗漏、证据与结论支持关系、专业审核结果、重复运行稳定性、总时长与总成本。评审模型的评分不能作为唯一真实质量标签。

加入人为注入的错数、失效来源、隐藏缺步骤、互相矛盾的证据、作者自夸、长篇但错误的候选，以及综合阶段新引入的错误。确认评审能拒绝而不只是生成更漂亮的解释。

同模型分离上下文与不同模型评审分别报告效果，不凭角色个数声称独立性。若额外评审没有可验证收益，允许在对应已批准 Profile 中不用该模式；不能在某个在途任务里自行跳过已冻结的门。

## 15. 验收矩阵与启用条件

以下均为待实现要求。本次仅完成草案，没有运行这些业务或故障场景。

| ID | 场景 | 必须证明 |
| --- | --- | --- |
| PP-01 | 直接 / 单候选 / 多候选模式 | 同一产品内核，模式按策略固定，候选数与预算有限 |
| PP-02 | 只有一个模型，角色串行执行 | 功能可运行，上下文隔离可核，独立性不被夸大 |
| PP-03 | 模型声称完成但跳过专业节点 | 门禁凭工具与步骤事实拒绝，不能靠自报通过 |
| PP-04 | 单位、口径、时点、数值或来源错误 | 对应校验发现，未知不当通过 |
| PP-05 | 全部候选不合格或实质相同 | 不强选、不刷样本到无限；不足比较如实报告 |
| PP-06 | 作者自评、顺序偏差、同模型共同错误 | 有隔离与评价证据，未覆盖风险如实保留 |
| PP-07 | 综合漏意见或引入新错误 | 编号覆盖与最终版本再验收生效 |
| PP-08 | 质量通过但动作未授权 | 执行仍被拒绝；审批与评分不是同一字段 |
| PP-09 | 文件可读但禁止上传 | 模型输入、工具输出、日志与产物出口均不外传禁出内容 |
| PP-10 | MCP / Skill 提示扩权、候选伪造指令 | 本地和服务端权限上限有效 |
| PP-11 | 重复、过期、跨用户或被替换对象的审批 | 不重复恢复、不错误授权 |
| PP-12 | 人工等待超时、否决、撤销 | 不自动同意；按冻结规则收敛并保留历史 |
| PP-13 | 修订预算、子任务预算或总 deadline 耗尽 | 不用 fan-out 或新 Attempt 绕开总额 |
| PP-14 | 模型 / 进程 / Runner 中断 | checkpoint、授权和副作用对账后可恢复 |
| PP-15 | 写后回执丢失、取消与完成竞争 | 无盲目重复写；唯一合法终态和实际效果记录 |
| PP-16 | 原文件并发改变、多目录和多候选 | 不覆盖新版本，不越界，不互相写草稿 |
| PP-17 | 更换 Profile、方法、输入或模型版本 | 在途解释不静默变化，修订与新 Task 血缘清楚 |
| PP-18 | 云端 / 无 K8s 与 Celery 的本机宿主 | 同一核心契约通过，持久恢复不是纯内存假象 |
| PP-19 | 页面关闭、刷新、断线与通知失败 | 结果可重取，连接状态不等于任务结果 |
| PP-20 | 真实专业任务对照评估 | 有外部可检查的质量与成本证据，不只采用评审模型分数 |

启用前必须完成：正式批准协议及业务 Profile；处理 A3 / A4 等适用范围变化；确定唯一 schema、实现与验收所有者；完成云端和最小本机契约测试；对至少一类真实专业任务验证方法与评审效果；准备停用新策略且不破坏在途版本的回退路径。

“有文档”“有角色”“能生成报告”都不等于通过验收。本文不承诺所有专业任务都应多 Agent，也不承诺专业结论因使用自建框架而天然正确。

## 16. 与原手工草案的主要差异

- 面向专业能力执行和质量控制，不面向助手之间的人工作品竞选。
- 允许单模型多角色；用上下文、证据和测试约束共同盲区，不强制多家助手。
- 先做专业步骤和硬性校验，评优只是按需模块，不替代方法与验收。
- 不要求每个内部阶段人审；质量自动门来源于获批策略，高风险授权单独保留。
- 综合后的产物重新验收，允许有上限的修订；原手工四环节不是强制骨架。
- 使用产品账本、Interaction 与适配器，不把 Git 分支、tmux 或人工复制当作运行前提。
- 云端和本机自始兼容，不等云端完成后再重写核心。
- 原 `competition-protocol-draft-luna.md` 保持不动；本稿未发布、未启用、未提交或推送。
