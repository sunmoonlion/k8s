# SDD：软件设计说明（Software Design Description）

由**规划 agent** 或**执行 agent** 交付：设计成什么样。

- **规划 agent** 只交 SDD。它的设计是下文的**结构层**，通过验收、由人整理进定稿设计之后，按其中的拆分建子任务。
- **执行 agent** 在实现之前也可以交一份 SDD，写它自己要做的这部分，是下文的**组成层**，不拆子任务。
  这份设计要不要先验收再实现，由任务写明；任务没写、而设计会实质改变接口、数据或风险的，停下来问。

回答「怎样满足任务的要求」。按 IEEE 1016，SDD 同时覆盖架构设计与详细设计；这里不再分 TLD 与 SDD：
总体还是详细，由这份设计在需求树里的层次决定，不由名称决定。

- **结构层**（有子任务的节点）：
  模块怎么划分、模块之间的关系与接口、共同约束和取舍。
- **组成层**（单个模块）：模块内部结构、协议与数据、失败与恢复。

层次是相对的：一个模块再往下拆时，它自己的设计对子模块就是结构层。

## 设计必须满足

**agent 的两部分。**

| | 通用部分 | 专用部分 |
| --- | --- | --- |
| 内容 | 执行编排：多方竞争、隔离、中断恢复、审批、工具协议 | 领域：提示、工具绑定、权限、记忆策略、领域约束 |
| 载体 | 执行运行时与多方竞争协议 | 每个 agent 的配置（Profile） |

两部分都必须有纪律，不存在「通用部分不需要约束」。新增一个业务 agent，**优先是新增一份配置，而不是复制一套代码**。

**设计约束：**

- 跨运行、或跨进程死亡仍须正确的不变量（预算、幂等、副作用、证据等账）**必须由持久存储承担**，不能放在执行进程本地。
- 执行层**租用、不自建**：依赖边界限定在稳定的 SDK，经端口隔离，不直接依赖裸协议。
- 领域概念**不进入执行端口的签名**：端口接受通用输入、能力与结果，领域名词留在领域配置里。

**设计原则：**

| # | 原则 |
| --- | --- |
| P0 | **只有一套状态机**，场景差异只体现在配置的约束、必需产物与中断策略；任何场景不得新增状态词 |
| P1 | **同一事实只有一个权威写入面**；两份同构文档即两个真源 |
| P2 | **方向不对称**：朝严谨可自裁，朝省事须人确认；默认值属于省事方向 |
| P3 | **判据必须声明覆盖范围**；覆盖不全比没有更危险 |
| P4 | 凡能落成代码、测试或门禁的纪律**必须落成**；文字只描述意图，不构成机制 |
| P5 | 设计机制前，**先核实它要处理的动作实际发生在哪里、由谁执行、经过什么路径**；未核前提只能标假设 |

两条推论：**一个只能靠人转述的环节等于没有环节**（P4）；对象各自的小生命周期是**对象属性**，不是第二套状态机——
把属性误认成状态机会让每个场景各造一套，把状态机误认成属性会让状态词失控增长。

**修改已冻结的契约，要提交明确的修订工作单元。**先证明是契约缺口，不在配置、适配层或文档里偷加语义。至少写清：

| 项 | 要交代什么 |
| --- | --- |
| 原始请求与证据 | 谁提的、原话、可复核的缺口或拒收用例 |
| 改与不改 | 具体定义块、字段、编号；状态、合法边、终态、幂等与租约哪些保持不变 |
| 影响 | 各组成部分分别要改什么，不改会怎样 |
| 迁移与回滚 | 版本、读写兼容、活动对象处理和退出条件 |
| 验收 | 原有用例集、必要新增用例、一条可复现实验 |
| 旧语义的处置 | 原先是什么意思、为何不够、谁依赖它 |

新增字段以带版本的可选字段引入；旧数据标「旧格式」，**不回填为无法证明的新语义**；新写入方不得回写旧版本语义。

**多个规划 agent 比方案时**，按 [`../../protocol/`](../../protocol/competition-rules.md) 的多方竞争协议产出这份 SDD。
