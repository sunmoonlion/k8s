## 一、PDF 方案

### 现在是怎么做的

info 后端用 pdfplumber，范围很窄：每份年报只看前 25 页，只抽「主要会计数据」那一张表。认不出就明确报错，不猜。
抽出的数与报表数据逐项比对，对上才标「已核实」。600009 的 9 份年报全部成功，共 177 个数。

局限：只验证过一家公司；只能处理有文字层的 PDF；表格没有边框线时抽不出来；字体缺映射时会乱码。
乱码时的表现是「找不到表」，数据标成未核实，不会写进错的数。

### PDF 在项目里有三种用途，不能走同一条路

| 用途 | 要什么 | 错了的后果 | 走哪条路 |
| --- | --- | --- | --- |
| 取数：报表数字进数据集 | 一分不差，能追到页码 | 专家算错指标 | info 平台，确定性抽取 |
| 取文：附注、公告、研报、用户资料进检索 | 版面和表格保留，能引用到页 | 引文不准，人可以翻原文核对 | 知识服务，交给 RAGFlow |
| 留存与预览 | 原件不丢，网页能看 | — | 对象存储；浏览器直接显示 PDF |

### 取数这条路

```text
原件留存（已有）
  → 体检：有没有文字层、是不是扫描件、文字是不是乱码
  → 第一档：确定性抽取（pdfplumber）
  → 乱码或抽不出 → 换一个引擎再试（pdftotext）
  → 还不行 → 标为「读不了」，不进数据集
  → 抽出的数过勾稽规则、与另一来源比对 → 通过才算已核实
```

数字不走大模型，也不走检索。扫描件要用识别模型时，识别出的数必须先过勾稽才能用。

### 取文这条路

RAGFlow 已经接在知识服务的接口后面，定位是可重建的派生系统（规则 `C-D5`）。
「原件直接喂 RAGFlow」与现有架构吻合。缺口：**知识服务现在只收文本和 Markdown，不收 PDF**，要把制品的允许类型加上 PDF。

RAGFlow 对 PDF 做的事（看的是本机 `~/repo/ragflow` 的源码，2026-05-14 的提交）：

| 步骤 | 做的事 |
| --- | --- |
| 文字识别 | 扫描件、图片里的字也能读 |
| 版面识别 | 分清标题、正文、表格、配图、页眉页脚、公式 |
| 表格结构识别 | 认出行、列、表头、合并的单元格 |
| 切块、记位置 | 每段记着在第几页、页面上的位置 |

但它的产出是文字：表格被认出来之后，会重新组织成句子或网页表格的文字。所以它能回答「公司怎么解释追溯调整」，
不能保证「2025 年营业收入是多少」一分不差，更不能算指标。数字要进数据集，这条路 RAG 替代不了。

### 原则

1. 原件永远先留存，解析在后。解析结果记下工具和版本，工具改进了可以重新解析。
2. 每个数、每段文字都带页码。
3. 认不出就说认不出，不降级成猜。
4. 用评测集选工具：攒一批有标准答案的 PDF（不同行业、不同年份、含扫描件），量准确率和速度。

### 先后

| 阶段 | 内容 | 价值 |
| --- | --- | --- |
| 已有 | 年报里一张表 | 判口径 |
| 下一步 | 从年报 PDF 抽三大报表全表 | 摆脱第三方网站：年报是法定披露，使用权清楚 |
| 再下一步 | 附注与公告进检索 | 专家能引用原文 |
| 最后 | 扫描件、用户上传的杂项资料 | 覆盖面 |

### 与《统筹考虑xpdf和ragflow.md》的关系

那份文档的三条核心教训都成立。它是按个人知识库的场景写的，放到本项目里要调整一处：
我们的数字要进数据集，不进检索；所以「一律直连 RAGFlow」只适用于取文这条路。

## 二、交易所 XBRL 的现状

| 来源 | 现状 | 能取到什么 |
| --- | --- | --- |
| 上交所旧的 XBRL 网站 `listxbrl.sse.com.cn` | 网址还在，跳转到「上市公司经营业绩概览」页 | 每期 8 个左右的关键指标；只有年报和半年报；每次查询近三年 |
| 深交所旧的 XBRL 平台 `xbrl.cninfo.com.cn` | 域名解析不到 | 无 |
| 证监会信息披露平台 `eid.csrc.gov.cn` | 能访问 | XBRL 专区只有公募基金，没有上市公司 |
| 巨潮资讯网站的财务数据页 | 能公开访问 | 三张表的摘要：资产负债表 14 项、利润表 6 项、现金流量表 3 项；近 5 年；年报、中报、一季报、三季报 |
| 深证信数据服务平台 `webapi.cninfo.com.cn` | 能访问，要注册 | 据介绍有完整报表接口；收费与条款没查到 |

### 用 600009 取了一次

| 项目 | 上交所返回（2025 年报） | 我们的数据集 |
| --- | --- | --- |
| 资产总计 | 71,678,547,661.74 | 71,678,547,661.74 |
| 负债合计 | 27,139,427,653.70 | 27,139,427,653.70 |
| 营业收入 | 1,334,619.22 万元 | 13,346,192,164.12 元 |

前两项相同，第三项在万元精度上一致。

### 不能替代解析 PDF 的原因

1. 科目太少：数据集三张表有几十个科目，摘要只有几个到十几个。
2. 精度不够：巨潮的摘要以万元为单位、保留两位小数；勾稽规则的容差是一元。
3. 覆盖不全：上交所只有年报和半年报；深交所没有对应的公开接口。

### 一个发现：各家对同一年给的数不一样

2021 年营业总收入：巨潮摘要给 37.28 亿（当年原始披露），东方财富给 81.55 亿（追溯调整后）。两边都不说明口径。
这说明给每个数标口径是必要的。

### 可以怎么用

上交所和巨潮的摘要可以作为额外的官方核对来源，成本低。是否采用待定。

## 三、Qlib 的实际情况

看的是微软 Qlib 仓库 `main` 分支的最新内容（仓库最近一次推送 2026-09-22，MIT 许可）。

### 财务数据

| 项 | 实际情况 |
| --- | --- |
| 数据从哪来 | baostock（第三方的免费证券数据网站） |
| 取哪些 | 两个指标：净资产收益率、净利润同比增长率 |
| 三大报表 | 没有 |
| 它自己的说明 | 数据来自 baostock，可能并不完美，建议有高质量数据的用户自备 |

这部分是演示「按时点存储」功能的示例采集器，不是财务报表的数据源。

### 价格数据

| 项 | 实际情况 |
| --- | --- |
| 官方数据集 | 停用。说明原文：因更严格的数据安全政策，官方数据集暂时关闭 |
| 官方给的替代 | 社区维护的一份数据（个人项目定期打包发布） |
| 自带的采集器 | 从雅虎财经取；说明里写着雅虎已屏蔽来自中国的访问 |
| 质量 | 做了复权处理；说明里承认有些价格序列仍然很不正常 |
| 采集器目录 | 雅虎、baostock 五分钟线、国内指数成分、基金、众包数据、按时点的财务指标等 |

### 值得借的

| 借什么 | 说明 |
| --- | --- |
| 按时点存储 | 每个数记「属于哪一期」与「哪天公布」；与 info 平台的三个时点是同一个想法 |
| 行情的存储格式、复权算法 | 专门为行情设计 |
| 交易日历、指数历史成分的采集办法 | 接口知识 |

做法与对 akshare、WrenAI 一致：借框架和方法，注明出处；不把它的数据当权威来源，产品运行时不依赖它。

### 要做价格数据时先想清楚的

| 问题 | 说明 |
| --- | --- |
| 使用权 | 雅虎与社区数据都是第三方来源。据我所知交易所行情对外展示需要授权，内部研究用没有问题；**未核实** |
| 稳定性 | 社区数据是个人维护；雅虎要境外网络，接口没有稳定性承诺 |
| 质量检查 | 与财务报表不同：复权前后是否一致、停牌日怎么处理、涨跌幅是否超出限制 |

时机：价格数据不在最小闭环里（财报体检专家包不做估值）；决策文档里第一批数据项的建议是行情先不碰。

## 三之二、2026-09-28 之后补充的

### 年报抽取的探针

| 报告 | 内容 |
| --- | --- |
| `~/annual-report-probe/REPORT.md` | 只有 600009：27 张表全部抽到，勾稽 162 次全平，与第三方数据的差异都有解释 |
| `~/annual-report-probe/batch/REPORT.md` | 14 家公司：348 张表抽到 339 张；勾稽 1860 次不平 15 次；能比的 9995 个数里 9214 个相同；换公司后改了 8 处；2 家没解决 |

结论：这条路走得通，但要按版式逐类处理。同时发现现有的采集与建库程序在别的公司上有五个问题，
其中最要紧的是质量检查「有一条不平就整个不发布」，导致采集成功的 11 家数据集全部发布不了。

### 采集方式（所有者 2026-09-28 已定，已进决策文档）

定时为主，临时异步补充；靠关注清单决定范围，先从少量公司开始。

### 数与文之间建立关系（所有者 2026-09-28 提出）

采数和采文都要，而且要能连起来。关系有三层：

| 层 | 靠什么连 | 可靠程度 | 成本 |
| --- | --- | --- | --- |
| 同一份年报、同一页 | 每个数、每段文字都记「哪份年报、第几页」 | 确定 | 几乎为零 |
| 附注编号 | 报表每一行后面标着附注编号，附注里按同样的编号展开 | 确定 | 低 |
| 内容相关 | 管理层讨论里谈到收入的段落，与收入这个数 | 不确定 | 靠检索，不事先连死 |

第二层是抽取时的发现：附注编号是公司自己给出的、从数字指向说明文字的链接。抽取时它被当作干扰去掉了，其实应该留下。

| 哪一边 | 要做的 |
| --- | --- |
| 取数 | 每个数多记：来自哪份年报、第几页、附注编号 |
| 取文 | 每段文字记：来自哪份年报、第几页、属于哪一条附注 |
| 两边共用 | 年报用同一个标识（原件的校验值，已有） |

注意：

1. 附注编号的写法不统一，十几家公司里见到三种（「（六十一）」「五（一）」「七、1」），同一家公司不同年份也会变。两边要用同一套规则认。
2. RAGFlow 切段之后还认不认得「这一段属于附注七、47」，没有验证。如果做不到，这一层要由我们自己在解析时建立，这会影响下面第 1 项。
3. 第三层不要硬连，交给检索，由人判断。

建议的顺序：先验证取文那边能不能按附注切分并保住编号；再让取数把页码与附注编号留下；最后给专家一个按「年报加附注编号」取原文的工具。
