# App Platform 数据所有权

## 1. 目标

本文定义 App Platform 中业务数据的权威所有者、存储边界、派生数据规则和跨应用引用方式。

核心原则：

```text
一种业务数据只有一个权威所有者。
其他系统只保存引用、缓存、索引或可重建副本。
```

数据所有权不等同于物理资源独占。不同 App 可以共用 PostgreSQL、S3 对象存储、Redis 或 Elasticsearch 集群，但必须使用独立数据库、Schema、Bucket、索引、凭据和访问策略。

## 2. 数据分类

### 2.1 权威业务数据

表达领域事实、必须长期保存且不可由其他数据完整推导的数据。

要求：

- 由唯一 App 管理写入。
- 具有稳定业务标识。
- 记录版本、来源和审计信息。
- 纳入备份、恢复和保留策略。

### 2.2 原始证据

用于证明业务数据来源的不可变内容，例如原始文件、HTTP 响应、附件、截图和导入批次。

要求：

- 先保存，再处理。
- 使用内容哈希校验。
- 修订产生新版本，不覆盖历史证据。
- 记录来源、获取时间和使用权限。

### 2.3 派生数据

可由权威数据重新生成的数据，例如搜索索引、向量、文档分块、摘要、缓存和统计快照。

要求：

- 记录生成来源和版本。
- 不作为唯一事实来源。
- 提供失效、删除和重建机制。

### 2.4 运行数据

任务状态、锁、会话、队列消息、临时文件和监控指标等运行期数据。

运行数据不能替代业务主档。需要长期审计的运行结果应沉淀到所属 App 的业务数据库。

## 3. 权威所有者

| 数据领域 | 权威所有者 | 允许的下游副本 |
|---|---|---|
| 用户、组织、服务身份、角色和权限 | `auth-app` | Token 声明、授权缓存 |
| 资讯源、原始文件、资讯、版本、血缘和质量 | `info-app` | 搜索索引、RAG 文档、业务引用 |
| 知识空间、文档投递、知识处理任务、引擎映射、模型辅助处理配置和推理运行引用 | `knowledge-app` | 领域引用、RAGFlow 处理副本、调用方业务快照 |
| 证券主数据、研究、组合、持仓、估值、风险和决策 | `investment-app` | 报表、缓存、分析索引 |

旧 `research-app` 已由 `investment-app` 取代，旧 Research 的投资研究数据归
`investment-app`，不是“等待未来 Research 认领”的无主数据。未来可能创建的通用
`research-app` 与 `tools-app` 尚未成立；只有独立 ADR、数据模型、迁移方案和权限边界获批后，
才能成为新数据的权威所有者，不能追溯改变现有数据归属。

## 4. Investment App 内部所有权

`investment-app` 初期可以采用模块化单体，但内部仍需明确数据所有者。

| 数据 | 所有模块 |
|---|---|
| 证券、公司、市场、交易所、币种、日历、标识映射 | `security-master` |
| 研究项目、笔记、观点、评级和证据引用 | `research` |
| 账户、组合、持仓和组合流水 | `portfolio` |
| 价格引用、汇率引用、估值、收益和损益 | `valuation` |
| 风险指标、风险暴露、限额和压力测试 | `risk` |
| 投资建议、决策、审批和执行状态 | `decision` |
| 关键操作和领域变更审计 | `audit` |

模块只能通过公开应用服务修改其他模块拥有的数据，不能直接写入其表。

## 5. 跨 App 引用

跨 App 关系保存稳定标识，不复制对方主档。

示例：

```text
investment-app.research_evidence
  info_id
  info_version_id
  citation_location
  quoted_hash

investment-app.ai_run_reference
  ai_run_id
  knowledge_run_id
  model_version
  prompt_version
```

当历史可重现性要求较高时，调用方可以保存必要的只读业务快照，但必须同时保留原始数据标识和版本。

## 6. 时间与版本

关键数据至少区分：

- `occurred_at`：现实世界中事实发生的时间。
- `effective_at`：业务规则开始生效的时间。
- `recorded_at`：系统记录该事实的时间。
- `version`：同一稳定业务对象的版本。

资讯、证券主数据、价格、组合状态、投资结论和模型结果不得只保存“当前值”。系统必须支持按历史时点重现关键业务状态。

## 7. 删除与更正

- 权威系统负责发起删除、更正和失效。
- 下游系统根据事件或对账任务同步处理副本。
- 法规、版权或用户请求触发的删除必须保留合规审计记录。
- 已被投资决策引用的内容发生更正时，不改写历史决策证据，而是增加更正关系和新版本。

## 8. 备份等级

| 等级 | 数据类型 | 要求 |
|---|---|---|
| A | 权威业务数据、原始证据、审计记录 | 严格 RPO/RTO、异地备份、恢复演练 |
| B | 重要业务快照、任务结果 | 定期备份，可以有限重算 |
| C | 索引、向量、缓存和处理副本 | 以重建能力为主 |
| D | 临时文件、锁和短期运行状态 | 通常无需备份 |

具体 RPO、RTO 由各 App 文档和生产环境配置确定。

## 9. 变更规则

新增数据实体前必须回答：

1. 它属于哪个领域？
2. 谁是唯一权威所有者？
3. 它是主档、证据、派生数据还是运行数据？
4. 是否需要版本、时间和审计？
5. 下游如何引用、失效和重建？

无法回答这些问题的数据模型不得直接进入生产实现。
