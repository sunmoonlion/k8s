**流程的主线是一项需求增量，不是一份文档，也不是一轮评优。**它必须依次回答：
收到的原话是什么 → 什么结果才满足需求 → 如何实现并证明可行 → 能否交给执行者开工 →
这个具体版本是否符合要求 → 是否允许把它投向指定环境 → 实际运行后能否接收和交接。
阶段以这些不同的问题划分，每阶段有可取件产物和退出门。写完文字不等于过门。

**常驻面不是阶段。**硬约束、协作协议、操作手册没有「做完」——它们是每条需求增量
都踩着走的操作系统。缺第三件（过关条件）的不是阶段，只是一段时间；把 constraints
写成 S0 产物、把改一次纪律当成做完一个阶段，正是现在 `agent-dev-guide.md` 的病。
S0–S6 只描述需求增量的时间顺序；常驻面贯穿全程，不占其中一个格子。

人负责提出需求、业务取舍、权限范围和验收拍板。AI 负责澄清稿、调查、设计、拆任务、
实现、测试、独立评审、发布操作和证据整理；机器检查可判条件。**不要求人代写技术规格、
人工拼提交、盯进程或凭代码行数判断进度。**受环境或授权限制必须由人执行的传输动作
仍如实记账，不把它说成已经自动化，也不因为追求自动化另造授权机制。

**本仓同时跑着两条流水线，关系是调用不是并列。** A 线是产品需求从提出到上线（本文
S0–S6）；B 线是多家隔离出稿、裁决、异议、验收（`protocol/` 的 T2 七环节）。B 线成熟、
A 线空，内容因此全堆进 B 线容器——这就是 `protocol/` 975 行而 `implementation-plan.md`
93 行且清单为空、以及 `agent-dev-guide.md` 近四分之一是上一轮产物的机制。T2 是同一条
需求增量在「需要多家比方案」时的加厚形态，不是另一套生命周期。

## 一、需求从提出到上线的七个阶段

阶段编号 `S0–S6` 与门编号 `DEV/G0–G6` 是开发里程碑，不新增产品 Task/Attempt 状态。
它们也不是 guide 中运行时演进 G0–G5、执行器 Gate 0 或 T2 七环节的别名。

| 阶段 | AI 在这里完成什么 | 产物与建议落点（相对 dev-plan） | 退出条件 | 未通过时往哪回 |
| --- | --- | --- | --- | --- |
| S0 受理与定范围 | 保存原话和附件，查已有需求/决定，识别对象、边界、风险与实质歧义；区分调查和交付 | `working/request-baseline/REQ-<id>/request.md` 原始需求；`changes/DEV-<id>/work.md` 受理/授权记录 | DEV/G0：来源可追溯、范围和责任归属可读、允许开展的下一步明确；影响结果/权限的歧义已解决或明确留给有边界的调查任务 | 仅补关键澄清；不为填满模板反复问人。未授权调查或越出范围则停止 |
| S1 需求与验收合同 | 把用户结果写成正向/反向场景，明确非目标、约束、允许的不确定性及验收口径；复核基线 | `changes/DEV-<id>/prd.md`；共用产品要求引用 `working/request-lifecycle.md` 的 F/I/AT，不复制定义 | DEV/G1：业务目标、输入输出、失败/降级、可验收条件及不可判部分已约定；出题与答题角色分开；冻结验收版本 | 缺事实回 S0 做调查，需求变化产生新版本；不能让实现者完工后偷偷改验收题 |
| S2 设计与决策 | 设计责任边界、接口/数据/状态、威胁与恢复；必要时做有预算和退出条件的 spike；比较可行方案 | `changes/DEV-<id>/design.md` 为变更 TLD；受影响组件 SDD（契约旧版本保留到 consumer 锁升级完成）；`rounds/<round-id>/` 或轮外工作记录保存决定和取证 | DEV/G2：设计能逐项解释怎样满足 PRD；关键未知有证据或明确阻断；重要选择有合法处置；接口与现行合同一致 | 设计失败留证后回 S2；改变用户目标/验收回 S1；没有可行路径可终止，不能把试验原型当已批准实现 |
| S3 拆解与施工就绪 | 把设计拆成可独立交付/验证/回滚的工作单元，定依赖、仓、写入面、执行者与验收者；供给可用环境 | `changes/DEV-<id>/plan.md` 为实施计划；每个子单元 `work.md` 与冻结判据；引用 `protocol/` 执行约定 | DEV/G3（DoR）：本节后文的开工条件全满足；新执行者仅凭持久载体知道任务、依据、命令、停止点；必要环境实际冒烟成功 | 单元过大或依赖未定回 S2/S3；环境缺失建供给任务，不让业务任务带着未知环境直接开工 |
| S4 实现与独立验证 | 在专属工作区改代码/契约/规格；跑相关检查；独立 AI 对确切提交做验收；记录失败和未覆盖 | 产品仓代码、测试、SDD/契约；原有 `docs/evidence/<task-id>/` 证据包；开发侧工作单元引用各仓 commit | DEV/G4：冻结的必要检查在明确环境通过、独立评审无未处置阻断项、规格与实现增量一致、证据绑定最终候选提交 | 修实现回 S4；暴露设计错回 S2；需放宽验收回 S1 经合法改判。修改后旧验收不能覆盖新提交 |
| S5 发布准入与执行 | 准备发布/回滚包，提交具体批准对象，按获准范围执行并记录真实环境及结果 | `changes/DEV-<id>/release.md`；发布清单、源码/镜像/数据版本、授权回执、操作与回滚证据 | DEV/G5：发布前权限和批准成立，版本与证据一致；发布后目标环境达到预定基础检查，失败已回滚或进入有责任人的处置 | 缺批准停在发布前；字节/对象变化重取批准；执行失败走冻结回滚，不宣称需求已完成 |
| S6 运行验收与维护接续 | 对真实用户路径、恢复/降级和观察窗验收；人确认业务结果；留可接续的运行说明和未决工作 | `changes/DEV-<id>/acceptance.md`；运行证据/交接；`handoff.md` 当前游标；`project-guide/` 更新实现投影 | DEV/G6（DoD）：达到已冻结完成合同，发布及实际观察证据可取，人的必要确认有效，残余项/责任/回退清楚且资产可恢复 | 运行不符合回 S4/S5 纠正；新需求另建关联需求。拒绝/取消留原因、已发生副作用及清理结果，不伪装成功 |

为什么是七阶段：S0 与 S1 分开，避免 AI 把自己的解释当成原始需求；S1 与 S2 分开，
避免方案反向规定用户该要什么；S2 与 S3 分开，因为方案成立不等于环境和依赖足以开工；
S4 与 S5 分开，因为候选通过不授予外部写权限；S5 与 S6 分开，因为部署命令成功不等于
真实用户拿到可靠结果。每一处拆分都对应一种不同的失败、批准对象或返工入口。

七阶段可在同一短任务记录中表达，**不强制七次会议或七份新文件**。可逆的小修复沿用
已批准 PRD/设计/政策，引用即满足相应阶段，不再重复写同一事实；仍保留适用的验收、
独立性与批准条件。无法提供既有依据时，不能为了省文档把该阶段填成“不适用”。

## 二、每道门的执行归属

下表将机器、AI 纪律、人判断分开。`机器可查` 只指指定命令可以执行的部分；
完整的 DEV/G0–G6 自动聚合器**尚未实现**，当前综合过门仍由受约束的 AI 留记录。
AI 声明 PASS 不是服务端强制点，缺载体不隐写成已自动化。

| 门 | 已有机器能够检查的局部 | AI 执行、独立 AI 复核的纪律 | 人负责的判断/批准 |
| --- | --- | --- | --- |
| DEV/G0 | Git 可取件、摘要和输入文件存在；不能证明是谁授权 | 原话/解释分开、重复请求识别、边界与下一步目的 | 实质歧义及授权范围；已有有效授权沿用，无须重新确认 |
| DEV/G1 | doc-gate 查文档链接、节引用和表格；不判需求正确 | 场景可证伪、适用 F/I/AT 有对应、未知/排除明确；冻结原版本 | 业务目标、损失容忍及需要人决定的验收取舍 |
| DEV/G2 | 对应 spike/test 的可复跑结果、契约 schema 检查（前提是该单元已有命令） | 对抗例和失败路线、边界适配、证据不能外推、候选隔离与处置完整 | 权威变更、已知分歧与重大取舍，按现行协议裁定 |
| DEV/G3 | Git 基线/diff；实际依赖安装和最小测试命令；T2 可用 round-status 检产物 | 验收者不等于产出者；任务可冷启动；依赖、写路径、预算、停止与回滚明确 | 必须由 principal 提供的权限、预算例外；技术供给可由 AI 完成 |
| DEV/G4 | 本工作单元声明的适用测试、doc-gate、必要时 anchor-gate；采集失败不能算通过 | 测试是否覆盖原问题、最终 diff 是否符合合同、负例及未测理由是否可信 | 不替 AI 跑测试；如需改变业务承诺或风险容忍，在这里发起改判 |
| DEV/G5 | 产物摘要、构建/配置/部署检查能判其各自对象；不把本地 author 当身份签名 | 精确批准对象、源码/镜像/数据一致、批准后不偷换、异常按预案处理 | 不可逆发布及其它 H 表管辖动作的具体授权；不能以“已有凭据”替代 |
| DEV/G6 | 冻结观察窗口中的可自动测指标和真实链路测试（须有环境及实际执行记录） | 检查观察对象/覆盖/交接完整、记录副作用及未决、更新实现投影 | 产品结果验收、剩余已声明风险的接收或拒绝；不是只签“测试绿了” |

当前可复跑的通用工具是 `python3 sunmoonai/docs/dev-plan/doc-gate.py --all`、
`python3 sunmoonai/docs/dev-plan/anchor-gate.py` 和
`python3 sunmoonai/docs/dev-plan/protocol/round-status.py`（在 k8s 仓根）。
**`round-status.py` 判的是轮次工单。**parse_round 读 `round.md`，缺 `final_path` /
`round_dir` / `prefix` 即拒绝判定；stage_table 按工单配置的产物路径查是否作为 git
提交出现（不看工作区、不看声明）；档位从工单解析留痕。这就是 S3「解析 round.md」和
S6「落点齐全 / 状态推导」已接线的部分。它**不能**判普通工作单元「目标/实施/测试/
验收/回滚」字段齐全，也**不能**判本轮 260 行落点表。
产品命令必须由工作单元写明仓、cwd、锁定依赖、命令和环境；本稿不编造一个已经存在的
`make check`，不声称 Jenkins 已接线，也不把“执行命令成功”当作有非空有效测试。

**机器结果字段**建议随工作单元携带：`gate_id, subject_commit/digest, environment,
command, expected_scope, observed_scope, exit_code, result, evidence_ref, checked, not_checked`。
这是既有证据纪律在流程中的记录形状，不是新的产品 API schema。缺输入、不可达、权限
不足和枚举失败记 `UNKNOWN` 或失败原因；只有完整的适用必需集合通过才能报该门通过。
不适用要有冻结依据；不能用一个空数组实现全部通过。

**凡声称「机器执行」的判据，必须能写出一条跑出非平凡结果的命令**（不能是空列表恒真、
不能是「脚本文件存在」）。写不出就改标纪律。

归属分三档，不得混进同一张「已保证」清单：

| 档 | 含义 | 本流程的例子 |
| --- | --- | --- |
| 机器已能判 | 指定命令对指定对象给出非平凡通过/失败 | `doc-gate.py --all`；`round-status.py` 判轮次产物是否作为 git 提交出现 |
| 当前纪律、目标机器 | 今天靠执行者留记录，声明了将来可接线的对象 | 完整 DEV/G0–G6 聚合器尚未实现 |
| 只能靠纪律，且必须永远保持 ⚠ | 无产物可查，机器化会假装查到了 | 提案隔离是否在执行者脑子里成立；「语义覆盖了原问题」 |

第三档存在的理由：两档会诱导把「暂时靠纪律」和「本质靠纪律」混同，进而假装后者将来会自动化。

## 三、可以开工与做完分别是什么意思

### DoR：准许实现的是一个有边界的工作单元

DEV/G3 至少逐项核：

1. 原始请求、有效 PRD/验收版本、TLD/必要决定都可从持久载体取得，未决不阻断本单元。
2. 任务列全所有仓、目标、包含/排除项、允许写路径和副作用；与现行 constraints 对照。
3. 输入/输出、成功与失败、适用测试、证据、停止/重试/预算、回滚已写明；没有“完善 X”。
4. 基线与依赖已冻结，执行者只能在归属写入面工作；分支、工作区及 Git 元数据能实际交付。
5. 执行者和独立验收者已指派，角色符合协议；T2 先冻结判据、保持提案隔离。
6. 所需 SDK、模型、数据库、业务数据/金标准和凭据等前置有对应可取证据；缺失就明确阻断。
7. 新工作区的最小检查实际能跑，并能报真正失败；仅有依赖声明或脚本文件不够。
8. 把当前会话关掉，另一个获准执行者只凭工单、来源版本和检查入口就能接着做；
   不能凭一个固定“最多改几文件”的数字替代这个判断。

调查/spike 也是工作单元，但其成功合同是“回答指定未知并交证据/失败解释”，不是完成
产品能力；它可以在实现 DoR 未满足时按自己的窄 DoR 开始。原型进入产品必须重新通过
产品实现的门，不能用“spike 已做完”绕过数据、授权或正式测试。

### DoD：完成合同覆盖实际交付，终态不被交付重试污染

DEV/G6 区分三个可取结论：**候选验证通过**在 G4，**指定版本发布成功**在 G5，
**需求完成合同满足**在 G6。状态记录必须带对象，不能都写一个“已完成”。
产品用户结果、源码/镜像/数据版本、独立验收、运行观察、人的必要确认、回滚/交接和
残余事项齐全，才按该需求合同收口。预算耗尽、拒绝或取消是其它合法结果，不是成功 DoD。
**执行前授权与执行后如实记账不能互相替代。**「已记录或已获授权」这类析取会让未授权
动作只因留了记录而算完成，与现行权力表和「技术可写不等于动作获批」冲突。

若交付物只是文档，S5 是发布批准版本，S6 是指定读者能取到正确正文与必要引用；
不为文档任务强加生产 Pod 观察窗。若交付物是分析器，S6 需真实数据/可判金标准和
明确的不可判范围；CLI 协作跑通不能外推 SDK 产品执行链已验证。

对已经完成的产品 Task，通知失败只重试 Delivery，不把 Task 改回非终态；部署/维护
新发现形成新的关联开发工作单元。这里直接沿用产品合同，不用开发阶段名改产品状态边。

## 四、AI 工作如何组织、评审与续接

| 位置 | 谁承担 | 责任与不能混的部分 |
| --- | --- | --- |
| 需求提出和 principal | 人 | 提原始意图、定业务取舍、批准必要动作、验收结果；不用成为代码审查机器 |
| 分析/设计/计划/实现 | 被派工的 AI | 产出技术内容和证据，不能自行扩大授权、替人改变目标，不能验收自己的最终输出 |
| 独立验证 | 另一获准 AI | 按冻结判据对确切对象复核，能反驳也能承认不可判；不以同模型同样回答当独立实证 |
| 路由与调度 | 确定性控制面及当前操作者 | 只按可判字段定档/派工/取件/记状态；当前手工传输如实记录，不混成业务裁决权 |

`round-protocol` 是 S3/S4 **调用**的协作执行子流程：某个阶段需要多家比方案时调用它，
然后把决定及证据交还外层需求流程。它的①到⑦处理一次 Artifact 决策，不替代从需求到
上线的 S0–S6。一条需求可能在 S2 开设计轮，在 S4 用单线实现与独立验收，不强制再跑
一整轮选稿；也可能因新权威变更再开轮。**T0/T1/T2 使用现行判据，不另按文件数发明分档。**

**类型上它是横切常驻面，不是实施计划的一章。**所有者映射「≈ 实施计划的一部分」成立的
是**调用关系**：SDP 引用其版本，任务、依赖和进度留在计划，规程不随某张任务表完成一起
过期。它不成立的是**类型合并**：`round-protocol.md` 与 `implementation-plan.md` 的
生命周期、读者时刻、内容种类都不同——证明「不是同一种内容」不足以推翻附件/调用关系
（luna 的反驳成立），也不足以把它写进 IMPL 目录树当一章（异议四家的举证成立）。
物理文件保持独立；派工时引用，类型上标横切常驻。

T0 保留冻结标准、独立验收、必要人确认；T1 走规定的独立评审；T2 保留提案/互评/
裁决/异议/验收/确认/清理。批准粒度仍依权力表和动作，不把阶段完成当成无限制批准。
框架变更必须先适用现行协议批准，不能凭本候选自行改变谁有权裁定。

AI 冷启动包是一次引用集合：原话/PRD版本、设计/决定版本、当前子单元、所有仓基线、
证据位置、未决与停止点、上一轮失败、允许写入面。每次完成、停下或交接写 checkpoint；
它是对持久主档的可重建摘要，不覆盖原请求、Task 状态或人的批准。
取件后先核版本和归属，发现重置、覆盖或来源不明，按 guide 的事故规程保全与停止。

**进度从证据读出**：将“计划做”“执行过”“验证通过”“获准发布”分开；无产物、超时、
退出、失败同样留记录。组织者不得在环节进行中重置参与方工作区。换执行者要保留原
Attempt 和证据，不能改作者字段来伪造独立性。

## 五、由阶段产物推导文档及维护规则

至此流程已经成立，才决定文件组织。每种文件的存在理由如下；同一次短工作可合并容器，
但不能合并批准对象、事实与计划的效力。

| 首次需要它的阶段 | 文档类型与解决的问题 | 维护、生效与旧版 |
| --- | --- | --- |
| S0 | 原始需求记录：恢复用户真正说过什么 | 原话一旦作为基线冻结不可覆写，澄清追加；AI 记录、人纠正意图；旧版本保留。既定 request-baseline 路径不动 |
| S1 | PRD/需求合同：约束成果及验收，而非实现现状 | AI 起草、独立核覆盖、人定业务取舍；冻结后变更经批准产生新版本。保留 F/I/AT 稳定引用；实现落后不得倒改需求。本轮 inventory 的 `Ixx-xxx` 是源节地址，不是产品合同章节编码；不另立 `REQ-05.3` 这类章节级第二套产品 ID |
| S2 | TLD 与组件 SDD：解释系统如何满足要求及每个接口/组件怎样实现 | TLD 定边界/权威选择，SDD 定具体结构/协议/失败语义；AI 随实现增量同步修订并评审，批准版本可被新版本取代。**契约旧版本保留到所有 consumer 锁升级完成**；新版本取代不等于立即删除仍被锁定的旧版本。实现变了而适用规格未同步，属于交付缺陷；不能为使代码合规悄改已冻合同 |
| S2 有选择时 | ADR 与完整决策包：恢复为什么做这个选择 | 冻结的决定只被追加更正或取代；保留依据、反对意见、范围与确认。rounds 中保留全审议过程，不能只剩结论表 |
| S0–S6 都会遇到、但不走轮次 | **DEC：所有者拍了但不走 ①–⑦ 的落点** | 写入 `records/decisions/<id>.md`（或进行中轮次的 `rulings.md`）。本轮第一次尝试作废（R1）就是这类决定没有检索面、被降级成待议题。工作取证袋不是它 |
| S3 | 实施计划 SDP、工作单元与**横切的**协作规程：把设计变成可派工依赖与可执行步骤 | AI 拆任务并冻结单元，状态随证据更新；protocol 是计划**引用**的共用执行附件（横切常驻，不并进 IMPL 目录），改规程按现有协议。计划完成可收口，不能因此删除仍适用的规程 |
| S4 | 验证计划与结果证据：证明哪个版本的哪些条款过关 | 判据先冻结；实现者出结果，独立 AI 验证；输出带环境/版本/覆盖，失败不得覆写成通过。原产品仓 evidence 路径不迁移 |
| S5 | 发布/回滚包与批准：给具体动作的可审阅对象 | AI 准备与执行，人按既有权限批准；批准绑定对象，变化重取；发布后的回执和版本清单追加记录，不能手改成成功 |
| S6 | 运行验收、交接和实现投影：让成果被接收、后续仍可维护 | 人定业务接收，AI 整理可复跑证据并更新现状；投影只引用实际实现，旧验收/事故记录保留，下一需求另起关联单元 |
| 从 S0 到 S6 都会遇到 | 开发纪律及**操作手册**：防止每次任务重复发明共用约束；冷启动必须有一份「照做」入口 | constraints 保持规则 ID 与执行载体；guide 按阶段提供共用**执行**正文，不是 TLD。技术架构归 TLD/SDD。权威规则变更走既有门，索引不另立规则 |

这些不是脱离流程的类别：没有 S1 的冻结目标就不需要 PRD，没有 S2 的可替代选择就
不需要 ADR，没有 S3 的派工就不需要 SDP。PRD 不装实现日志，ADR 不改写成今日规格，
SDD 不装某轮谁迟到，SDP 不把“规则已写”当作“任务已做”，证据不装将来承诺。
额外建一类的代价是多一种维护入口，只有新增了不同的问题/修改时机才值得。

压缩目标文件时对每一类再问两句：**缺了它，哪个阶段没有过关物？为什么不能并进邻居？**
答不出的不单独立类。luna 的十四份目标用这两问检验必要性，不另造一套分类。

**双向检验**（读完上表当场可做）：删掉某一个阶段，应有一类文档失去来源；删掉某一类
文档，应有一个阶段的产物失去落点。过不了这一关的「类型」是并列另立的，不是从阶段
推出来的。

**类型按内容走，不按目录走。**没有单独的「轮次档案」类型：`rounds/` 里同时装决定、
审议、机械结果、通知，四种生命周期不能共用一条规则。决定记录按 ADR 规则（只被取代）；
审议与机械结果按证据规则（冻结追加）；通知是组织者产物。按目录立 `ROUND` 类会把这四种
绑死——不采纳。

### 接受所有者的映射并落实到流程

- `request-lifecycle ≈ PRD`：作为 S1 的产品目标合同，其中对象/状态/不变量是需求的
  可验收精化、AT 是验收口径。保留完整原文和路径；S2/S4 复用它，不能另造状态规范。
- `rounds ≈ ADR`：其中 rulings 是决定记录，候选/评审/异议/验收是该决定的证据包。
  二者原地共存，以轮 ID 限定编号，既能查结论也能追反对理由。检索两个方向都能失败：
  有 ID 无正文行、有正文行无 ID 都不合格；当前轮裁定的条数和 ID 集合必须钉在可核对配置里，
  不能只锁旧三轮的 26 条。不另建一份与检索器并行的 `decisions-index.md`。
- 当前架构工作 `≈ TLD`：本候选选择文档责任边界，①b 细化结构及迁移；不是代码实现完成。
- `protocol ≈ 实施计划的一部分`：落实为 S3/S4 的**调用附件**，不是 IMPL 目录树里的一章。
  SDP 引用其版本；具体任务、依赖和进度留在计划。规程不会随某张任务表完成一起过期。
  类型上标横切常驻面（见第四节）。
- `constraints ≈ 开发纪律`：贯穿各门，所有具体动作按相关规则自检，标明谁在执行。

## 六、三条具体需求怎样走完整流程

### 例一：web 生产适配器（当前待决 U1，演示推进，不替 U1 选型）

S0 保存“让用户从 web 提交并拿到可靠结果”的原始需求及授权调查范围。S1 按产品合同
取 Submission、授权、幂等、Interaction、Delivery 和对应 AT，冻结正反例，不写“接口接通即可”。
S2 由 AI 比较薄转发与自持投影，核 session/BFF/后端授权边界及存储归属，必要时做窄 spike；
相关取舍由合法裁定留下 ADR。**U1 未定时，产品实现 G2/G3 不通过，调查单元仍可按授权运行。**

U1 有结论后，S3 才拆 provider/consumer 契约、适配器、前端、失败恢复和部署单元，
列全仓、顺序、测试和回滚。S4 实现并双端验证契约与用户链路，独立 AI 对最终版本评审。
S5 提交源码/镜像/配置/数据版本一致的发布包，由 principal 批准目标环境的具体动作。
S6 验刷新、断线重取、拒绝越权、通知失败不污染终态等冻结场景，人验收业务结果，
更新实现投影和交接。未复跑当前产品仓，以上不是“这些能力今天已经可用”的断言。

### 例二：窄范围、可逆的文档修复

S0 明确坏链及修复范围；S1 引用现有文档契约与“目标能取到且语义未变”的判据；
S2 以已有路径映射说明修法；S3 指派独立验收、冻结文件范围、能跑 doc/anchor 门；
S4 修复并复核正文；S5 在必要批准后发布同一提交；S6 读者取件成功并保留变更记录。
PRD/TLD/SDP 可以全在一个工单中用引用表达。涉及权威语义时按现行 T2，不能因文件小就降档。

### 例三：财务分析能力

S1 先分可判与不可判：来源、数字、口径、期间和引用可核；洞见与投资判断不能伪装成
唯一正确答案。S2 取得获准数据及独立定义的评价依据，验证 Profile/SDK 路线的可行性；
数据或关键金标准缺失时实现 G3 阻断。AI 可准备数据候选和题目，人确定业务取舍及接收
范围，出题/裁定者不等于答题者。S4 做可复跑评测及反例，S5 精确批准发布，S6 用冻结
质量/成本/失败口径接收，仍保留不可判的限制。不能用读起来流畅代替质量证据。

## 七、参考材料怎样使用、哪些事本轮没做

读了 `inputs/README.md` 与 `inputs/readiness.md`，后者用于核查冷启动、覆盖、数据、
判据与角色分离的遗漏；未将其数量、外部 SDK 读数或“AI 必然怎样”的概括当成现状依据。
上述七阶段由不同退出问题、批准对象与失败回路推导，不是把参考中的九阶段改名。
未把 standard/ai-pipeline/automation-roadmap 当既定框架，未使用两份已作废候选。
现有共同上下文包括本人之前参与 guide 再吸收；正文断言仍回到本次冻结输入，熟悉不算证明。

| 参考 | 装得下什么 | 装不下什么（故不照抄） |
| --- | --- | --- |
| `inputs/standard-pipeline.md` | 阶段要有产物/门/过关条件；决定与规格生命周期不同 | 默认「人写代码」；九段骨架与本仓已在跑的 Change+轮次加厚不是同一条轴 |
| `inputs/ai-pipeline.md` | AI 承担技术工作、人只在两端；冷启动要持久载体 | 把参考里的九阶段改名当 ①a；「实现几乎免费」未经本轮验证 |
| `inputs/readiness.md` | 待决问题当题面（冷启动、覆盖、数据、角色分离） | 文内 2026-09-04 取证数字；不得当现状 |
| `inputs/automation-roadmap.md` | 哪些门将来可机器化的备忘 | 自述不承担约束效力，不能当已接线 |

对于 readiness 的待决：检查入口/CI 先由供给单元实跑，不在文档里假定已接；条款→测试
映射随 S1 判据进入 S3/S4 工作包，必需条款逐项解释覆盖而非先定一个覆盖率百分数；
哪些纪律能自动化需逐条实测，不凭表里写了脚本名就通过。数据采购、金标准答案和新约束
是否生效需具体工作单元裁定，本轮不代拍板。编号以“来源文件或轮 ID + 原 ID”消歧，
不改产品内核编号；分档沿用 protocol，不新增另一套可逆性算法。

没有实现完整流水线服务、CI 集成、SDK/权限机制，没有运行产品部署或改四个产品仓。
本候选交付的是可直接审查、带门和退路的流程定义及文档迁移方案。批准后的第一次应用
应按已有 G0–G5 演进/退出纪律验证真实 T0/T1 及必要的 T2，不能把这次文档门禁的绿色
当成产品自动化已建成。
