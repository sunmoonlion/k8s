## 二、叫法：三样东西，两道工序

| 叫法 | 是什么 | 能不能改 | 代码里（不改名） |
| --- | --- | --- | --- |
| **创意** | 用户交来的：方法（六问或 skill）、验收用例、同意测试；之后写的补充方法也挂在它下面 | 用户可补充，不能改原文 | `knowbot_request` |
| **新手** | 照创意孵出、拿去测的一版清单，带测试状态、测试中的问题、测试结果、成稿与交回物 | 建了不改；要改就孵出下一个新手 | `knowbot_draft` |
| **专家** | 测试通过、交付到 knowmart 的版本；工作台「请」的就是它 | 只读 | `knowbot` |

- **工序**：创意 →〔孵化〕→ 新手 →〔测试、交付〕→ 专家；没通过回到孵化，孵出下一个新手。「孵化」只当动词用（手工 / 辅助 / 自动孵化三种方式照旧），不占一栏，孵化记录挂在创意下面（所有者「孵化不需要这个名吧」）。
- **编号**：专家按版本号 1、2、3；新手写「新手 版本号.第几个」，如「新手 1.3」= 第 1 版第 3 个新手（取代「第 1 版 · 第 3 稿」）。
- **代码、表名、接口路径不改名**（`knowbot_request`、`knowbot_draft`、`/knowbot-drafts`）：改名要迁移数据、动两个应用的契约，眼下不值得；词汇表写明对应。新加的页面路径用新叫法：`/ideas`、`/novices`、`/experts`。
- 取代 `turn/glossary.md`「分身的生长阶段」那张表（种子、孵化、雏形、成品）；`decisions.md` 记一条，写明取代 2026-10-17 那条的叫法部分（流程不变）。
- 界面文字跟着换（两端）：「想法 / 提交一个想法」→「创意 / 提交一个创意」；「专家草稿」→ 三栏；「第 N 稿」→「新手 1.N」；补充的状态「已用进第 N 稿」→「已用进新手 1.N」；补充的提示「我们照着改出下一稿」→「我们照着孵出下一个新手」。「专家」不变。

## 四、web端：同一套外壳，按用户的事来排

和管理端用同一套外壳（左边一级导航、可收起、手机抽屉、右边折叠栏的组件），**但不照搬**：用户要做的事、看的东西、说的话都不同。

### 1. 用户在这里做什么

1. **交创意**：写方法（六问或 skill）、填验收用例、选用哪些数据、同意测试。
2. **答问题**：孵化时我们回问的缺口、测试中专家停下来问的（判断、开步前的提问）——**最急，要一眼看到**。
3. **看测试结果、读成稿**：验收依据（`C-L3`「结果给用户作验收依据」），不满意就写补充方法。
4. **管自己的数据**：上传、看版本、删；一份数据可被几个创意用。
5. **用专家**：交付了去 knowbench 工作台请。

### 2. 一级导航

```text
首页          待我回答、进行中的、最近的测试结果、我的专家，各几条
待我回答  (n)  全部要我答的问题，按创意分组；数字为 0 时灰
创意           我的创意列表 + 「提交一个创意」
新手           我的新手：测试中的、测完的
专家           我的专家
我的数据       上传与管理（现在挤在「我在做的专家」页里）
设置
```

和管理端的不同：

| | 管理端 | web端 | 为什么 |
| --- | --- | --- | --- |
| 已打开页面（多页签） | 有 | **没有** | 运营同时盯好几个；用户一次看一件事，多页签是负担 |
| 「待我回答」 | 问题跟着新手走 | **单独一项、带数字，首页也列** | 用户不答，测试和孵化就停着；最该先看到 |
| 「我的数据」 | 只读看（在创意的页签里） | **单独一项**，上传、删 | 数据是用户的，跨创意共用 |
| 首页 | 治理控制台 | **我的进展一览** | 用户进来先要知道「到哪了、要我做什么」 |
| 右边折叠栏 | 对照材料（运营核对用） | 我的方法、我的用例、用到的数据、我的补充、**我的话用在了哪**（规则出处换成用户的说法） | 用户看的是「你们照我的哪句话做的」 |
| 成稿与交回物 | 成稿与各步交回物同等，没过的那步看交回原文与验收 | **成稿放主栏最前**，各步交回物收在下面「每一步的结果」里，默认折叠；不显示验收规则名，只显示一句白话原因 | 用户验收看成稿；交回物给想深究的人 |
| 动作 | 孵出新手、核出处、发起测试、不照做、重试交付 | 提交创意、回答、写补充、上传数据、去工作台请 | 各做各的 |
| 用词 | 新手 1.3、规则出处、run、case id | 新手 1.3、「你的第 2 条用例」、白话原因 | 用户不认内部字段 |

## 五、成稿与交回物带回测试结果

### 1. 谁、什么时候取

| 谁 | 做什么 |
| --- | --- |
| knowbench（测试推进器） | **每条用例跑完、记结果的那一刻**（`KnowbotTestConductor._record`，下一条用例开跑前、整次测试收尾删目录前）取这条用例的产出，存进 `workbench_test_cases.outputs` |
| knowbench 接口 | `GET /internal/v1/knowbot-runtime/test-runs/{run_id}/cases/{case_id}/outputs`（服务身份 `knowbench:testrun`，同现有测试接口） |
| knowlab | 刷新测试结果时，看到某条用例已有结论、本地还没存它的产出，就取一次，存进新表；以后不再取 |

成稿只能在 `_record` 时取：用例共用工作区（隔离没开），晚了就被下一条盖掉；整次测完目录就删。

### 2. 取什么

每条用例一份：

```text
{case_id,
 deliverable: {path, text, truncated} | null,   成稿（第 8 步写的 Markdown）
 deliverable_note: 为什么没有成稿 | null,
 steps: [{step_id, title, outcome: accepted | rejected | not_reached,
          artifact: 交回物 JSON | null,          通过的那一版
          returned_raw: 没过那次的交回原文 | null, 只有 rejected 才有
          checks: [{label, pass, detail}] }]}    验收逐条（管理端看；web 只用 pass 与白话原因）
```

- **成稿**：只有这条用例的写稿那步**这次真写了文件**（工作台记了 `workspace_path`，0015 的 `written`）才去读，经会合点请测试电脑上的代理 `fs/readFile` 读那个文件；没写、没走到那步、读失败（代理离线、超过上限）都不读，`deliverable_note` 写原因。不读「碰巧还在那儿」的文件：免得把上一条用例的成稿当成这一条的。
- **交回物**：从工作台的步骤视图（`ExpertDesk.steps(full=True)`，已有）取每步最后一次尝试：通过的取那一版交回物；没过的取最后一次交回的内容与原文（工作台已为排查存着）；没走到的记 `not_reached`。
- **上限**：成稿 20 万字（超了截断、`truncated: true`）；每步交回物序列化后 20 万字节、没过的原文 2 万字（现有 `RAW_CHARS`），超了只留前面并注明；一条用例的产出合计不超过 2 MB。测试电脑上读文件的单次上限是 512 KiB（`MAX_READ_BYTES`），成稿超过就记「成稿太大没取」。
- 取产出出错**不影响**这条用例的结论：结果照记，`outputs` 记 `{error: …}`，管理端显示「成稿没取到：…」。

### 3. 契约：`knowbot-test-run/v1` 只加不改

- 加一个接口与结果模式 `test-run-case-outputs.schema.json`，真源在 knowlab 的 pydantic（`domain/knowbots/test_run.py`，同 `RunResultV1`），由模型生成，knowbench 的锁 `contracts/knowlab-test-run-lock.json` 跟着更新；两边锁测试都要过。
- 现有 `RunResultV1`、`/test-runs/{id}` 一个字段不动：每次刷新拉的结果仍然小；产出每条用例只取一次。
- knowlab 调到旧版 knowbench（接口不存在，404）：当作「这次测试没有产出」，不报错，不重试到天荒地老（记一次原因）。

### 4. 存在哪、留多久

| 哪里 | 存什么 | 留多久 |
| --- | --- | --- |
| knowbench `workbench_test_cases.outputs`（新列，JSONB，迁移） | 第 2 节那一份 | 整次测试收尾后 **30 天**清空这一列（测试结果本身照旧留着）；knowlab 一般几分钟内就取走，30 天是给「没人刷新」留的余量 |
| knowlab 新表 `knowbot_test_output`（迁移） | `draft_id`、`case_id`（唯一）、`fetched_at`、成稿、各步 JSON | **跟着新手走**：新手删了才删（现在新手不删） |

knowlab 的新表单独存、不塞进 `knowbot_draft.report`：报告每次刷新整份重写，产出大、只取一次；分开存才好分开鉴权（web 只认主人）。

- 0027「结果」那一行原文「不回任何分析内容」改为：「回每条用例的成稿与各步交回物：运营看来验证这一稿（所有者 2026-10-19：『草稿毕竟要测试人员写啊，看不到成稿如何验证草稿』），用户看来作验收依据（`C-L3`）」。
- 守住的边界：成稿与交回物只用于验证与验收这一个新手，不拿去训练、宣传或给别的用户；测试结果里仍然没有收益、胜率、评级类字段（`C-L5`）；成稿照旧不许写目标价、评级（第 8 步的验收守着）。
- 代码里写着「不放交回物的内容（C-L5）」的两处说明（knowbench `domain/workbench/test_runs.py` 模块说明与 `case_result`、knowlab `domain/knowbots/test_run.py`）照新口径改写：结果本身仍不放内容，内容走单独的产出接口。
- `constraints.md` 的 `C-L3` 不用改：它本来就允许验收测试的结果给用户；运营看测试产出是工程化与测试的一部分。

## 七、取舍

| 路 | 为什么不选 |
| --- | --- |
| 成稿与交回物直接塞进现有测试结果（`cases[]`） | 每次刷新都整份拉、整份重写；web 现有接口原样回结果，就成了没有单独鉴权的大字段 |
| 测完一起从测试电脑上取 | 用例共用工作区，前两条的成稿已被盖掉；收尾时目录就删了 |
| 只给管理端看 | 用户的验收依据就是成稿（`C-L3`）；分析内容回到它的主人手里，不比只给运营看更敏感 |
| web端照搬管理端 | 所有者：「完全一样好像不太对」；用户的事是答问题、读成稿、管数据，运营的事是孵化、核对、发起，排法该不同 |
| 现在就改代码与表名（`knowbot_request` → `idea` …） | 要迁移数据、改两个跨应用契约，收益只是名字；词汇表写明对应就够 |
| knowbench 工作台里给测试账号开页面看 | 测试账号是我们的，不是用户的；用户和运营都在 knowlab 看，路径一条 |

## 八、这一版不做

- 专家「停用」「删除」（成品的状态机在 0027 有，接口与 knowmart 的配合另做）。
- 孵化记录（出处表、缺口与答复、清单候选各版）：0029 的事；创意页留位置（「孵化」一块），先只放「孵出下一个新手」。
- 成稿导出 Word / PDF：0031 已设计（浏览器里转），新手页的成稿块之后接上同一组按钮。
- 测试隔离（每次测试自己的目录）：待办账 129、agent 0.5.1；本页在不隔离时也取得到每条用例自己的成稿。
- 管理端「CRUD 参考」「富能力参考」「设置」：不动（所有者原话）。
