# UAT：怎么把关

验收结论由验收 agent 交回，**采不采信由人定**。定稿的通则见 [定稿](../finalize.md)，怎么验见 [UAT 怎么验](verify-rules.md)。

人是三层里的最后一层（见 [怎么验](verify-rules.md)「谁来判」）：判意图对不对、判不可逆项、抽样复算证据的真实性。
**抽样规则事先写进用户消息**，否则抽检会退化成「翻一翻」。

## 看结论时对照什么

下面这几项是**人读验收结论时**对照用的，不写进用户消息。除了三种结论本身：

- **残余风险**：验完还剩什么没盖住、影响多大、谁来决定接不接；
- **未决与交接**：后续要做的事、下一个接手的人需要知道什么；
- **覆盖**：查了什么、没查什么、不能排除什么（照上面的三档写）。

**通过只意味着按所述范围完成了一次检视**，不构成「已验证」的背书，也不能估计未发现缺陷为零；
发布说明与记录一律照此措辞。

## 验收发现不了什么

验收能发现局部矛盾、非法状态边、归属错误和证据不足；但**共同的前提错误、被完成条件封死的答案空间**，
验几遍也不会冒出来——「必须包含某机制」一旦冻成判据，「其实不需要它」就无法作为合格结果提交。

所以越重的任务，用户消息越要给硬约束与方向、可复核的问题、客观的完成条件和够用的材料，
**允许用证据质疑机制的必要性**，不给出题人的倾向。
