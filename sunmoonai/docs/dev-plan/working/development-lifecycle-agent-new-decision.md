## 2. 裁决：以 luna 为基座

```text
selected_base = luna
selected_commit = 530a5a8de335f9fd73ec15a3c0900334c5da35f5
selected_blob = 13347913d359
status = SELECTED_FOR_INTEGRATION
```

四份评审中三份（cursor、luna、qwen）指向 luna，一份（kimi）指向 cursor。我不按票数裁决，
理由如下——**其中 cursor 作为 C 的作者裁掉自己选 L，是本轮可信度最高的一票**。

### 2.1 为什么是 luna：它是唯一一份「按用户要的那条链重写」的稿

用户要的是**开发类请求的 Agent 路径，与 Human 路径同构对照**。只有 luna 的骨架就是那条链：

`§1 两条同构路径 → §2 受理与 Task 化 → §3 简单/复杂 → §4 sandbox 与 Git 物化 → §5 执行内核
→ §6 supervisor → §7 产出物全生命周期 → §8 冻结/迟到/取消 → §10 验收交付清理 → §11 对照表`

cursor 与 qwen 的骨架仍是原稿的「开发助手怎样闭环一件工作」，对照是在 §0.2 / §0.3 加的一节；
后面章节没有把 FastAPI 受理与物化门禁写成主流程。**cursor 在自己的评审 §6 里承认了这一点。**
kimi 重构得最彻底，但方向偏到「产品运行时 agent 执行权威」，且建仓主体写反（见 §2.3）。

### 2.2 为什么是 luna：产出物那一章是唯一闭合的链

用户对本轮的显式要求是「场景很多，分别处理」。四份里只有 luna §7 把产出物做成闭链：

`身份/所有权/发布权（owner_id vs integrator_id）→ 命名空间 → 九类载体分类 → 候选状态机
→ Git 对象语义 → 25+ 并发场景 → 发布协议（CAS）→ 覆盖事故 8 步 → 保留与 GC`

其中两条是别人都没有的、且不可替代：

1. **§7.7 发布期 compare-and-swap**。cursor/kimi/qwen 都把覆盖挡在**写入前**（worktree 隔离）。
   但隔离只解决候选期；**整合方写最终路径那一刻的竞争没人堵**。luna 要求发布校验目标 ref
   仍指向 integrator 开始时记录的 commit，目标已变则发布失败、重开整合 Attempt。没有这条，
   「最后写的人赢」只是从候选期挪到了发布期。
2. **§0.4 的安全判定条件**：「多个候选各自在独立 worktree 中修改同一个相对路径，这是安全的；
   若共用一个物理工作树，就必须使用 owner namespace」。这是四份里唯一**精确**的表述——
   它同时说明了何时安全、何时必须降级。`[已核对]` 本轮现场（三份同名文件三个 worktree 共存）
   正是这条的实证。cursor 说对了同一件事但没给边界，qwen 说反了，kimi 只给了概括。

第三点是覆盖面：luna 是唯一系统处理**非 Git 产出**的——CI 并行输出、内容寻址大文件、
敏感物（凭据禁止 commit、最短保留期）、共享缓存、对象存储键、外部副作用账。开发侧现在只写
md，但这份文档要管的是产品 Agent 路径，这些迟早都会撞上。

### 2.3 为什么不是 kimi：建仓主体写反，是模型错误不是措辞问题

`[已核对]` kimi 稿头及 §1 对照表、§2 均写「复杂任务由 agent 在 sandbox 中构建 git 仓库」。
用户原话的主语链是 fastapi 受理并整理成 Task、在 sandbox 中构建 git 仓库并塞入材料；
另三份独立收敛到同一读法。

我不把这当作抠字眼——它有实质后果：**把工作仓供给方和 supervisor 合成同一个 agent，
物化门禁就没有承载主体了**。luna §4.4「物化门禁通过前，Task 不得进入可执行 Agent Attempt」
和 cursor §5.1「Agent 不得另 `git init`」在 kimi 的模型里无处安放。而且结构上 sandbox 与仓
必须先于 agent 进程存在——agent 是在那个仓里被启动的，它不可能是自己工作区的供给方。

kimi 另有两处实质缺陷：`[已核对]` 冲突优先序表里没有 `constraints.md`（该文件真实存在且是硬权威），
「违反 constraints.md 不进入方案比较」这条门禁失去锚点；以及删掉了开发仓专属内容，使人那份
的引用悬空。

### 2.4 为什么不是 qwen：中心论点被现场证伪

qwen §5.2 把「带助手标识的文件名」抬为归属三律之一，并把本次事故根因归为「用了不带助手标识
的公共文件名」。`[已核对]` 这与现场不符：三份不带后缀的同名文件在三个 worktree 里毫无冲突地
共存；qwen 自己能幸存是因为写在 `worktrees/qwen3.8`，不是因为后缀。后缀既非必要条件也非充分
条件——两人在同一工作树写同一个带后缀的名，照样后写覆盖。

**qwen 在自己的评审里已经把这条列为「本轮最该被纠正的一条，且是本人自己的」并排自己末位。**
这份自我纠正的质量很高，但它纠正的是自己稿子的中心论点，稿子本身不能当基座。qwen 另缺恢复
规程、状态机和发布协议——而触发本轮的恰恰是一次**已发生**的覆盖。

### 2.5 为什么不是 cursor：它是最强的落地 runbook，但不是基座

cursor 是四份里可执行性最高的一份，我把它的三块内容列为**强制并入**（§3）。不选它作基座
有三个理由，前两个 cursor 自己承认：

1. 文档身份不对（§2.1）；
2. 产出物模型浅于 luna，无非 Git 载体、无状态机、无发布期 CAS；
3. `[已核对]` **两处坏链**：`working/collaboration.md` 与 `working/doc-conventions.md` **均不存在**
   （`constraints.md`、`parallel-proposals.py`、`handoff.md`、`request-lifecycle.md`、
   `project-guide/repos/investment-app.md` 存在）。这不是修个链接的事——cursor §0 把
   `collaboration.md` 列为 P5 权威，§10 把 `doc-conventions.md §5` 当作**四条「项目实例」的证据出处**。
   证据源不存在，这四条当前不可独立复核，严格说应从「项目实例」降级为「设计风险」。
   qwen 稿有同样两处坏链；luna 零坏链（`[已核对]` 它对协作规范用「现行专门规范」泛指）。

另外 cursor §5.4 S1 要求把稿子移走后**删掉共享路径上的那份**。这条不得进入整合稿：
在共享路径已被覆盖的场景下，当前内容未必属于本执行者，删除会造成第二次数据损失。
luna 的评审对这一条的判断是对的。

## 4. 我与各家评审的分歧（供复核）

1. **kimi A7「luna 自建第二套状态机」——我判不成立。** §7.4 是**候选**状态机
   （DRAFT/FROZEN/SELECTED/SUPERSEDED/INTEGRATED…），描述的是开发侧产出物，与产品 Task 的
   `QUEUED`/终态语义不相交，也没有复制产品状态名。要谈选优就必须有这套词汇。保留。
2. **cursor G6「luna 把产品状态机搬进开发侧」——部分成立，按 F2 收窄即可，不构成基座否决。**
   luna §0.1 已把租约/fencing 的权威归给 `request-lifecycle.md`，是引用不是重定义；问题只在
   §8 把它当成了开发侧迟到判定的机制。
3. **kimi 给 luna 可维护性打 2 分、理由含「本文定位是开发结束后删除的临时文档」——我判理由不成立。**
   `[已核对]` `development-lifecycle-human.md` 有 7 处引用 agent 那份（§6、§90、§118、§133、
   §152、§157、§162）。**正因为 agent 那份要删，共同内核必须写全**，写全带来的行数不是维护负担

4. **qwen G1「四份全未提交，选优不该现在发生」——已消解。** `[已核对]` 四份现均有可达 commit，
   §1 的表即冻结凭据。整合方必须从 luna 的 **commit `530a5a8d`** 取内容，不得从工作区文件取。
