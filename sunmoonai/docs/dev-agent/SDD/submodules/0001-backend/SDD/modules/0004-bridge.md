# 0004-bridge：执行端对接

**承担**：后端与执行端之间那条链路的看门人——认设备、发活、发租约、收回执、拒绝过期的写入。
通道 ① 这一侧的全部，它是后端与执行端之间的**桥**：认谁能上（设备身份）、发通行凭证（租约）、把活运过去（投递器）、
把回执运回来、拦住过期的（fencing）。五件事都以**设备**为单位——一台设备一条连接、一份租约、
一个投递目标、一份容量。

- WSS 连接：runtime 主动外连，后端维护设备在线状态，经已有连接派发；
- **设备身份**：配对、公钥绑定、吊销；
- **租约与 fencing**：随派发下发，按固定间隔续约；续约失败即暂停，重连后对账；
- **投递器**：读 `0001-state` 的 outbox、挑一台在线且已授权相应工作区的设备送过去、送成之后请求
  `0001-state` 标记已投递；设备离线则等待，不丢。**表在那边、worker 在这边**——
  表必须跟着事务走，worker 必须知道谁在线；
- 回传：事件与进度、副作用意图与回执、工具级审批结论摘要、用量、**方法工具的调用**；
- 派发内容**带签名**。

**不承担**：

- 不决定派什么——那是 `0003-orchestrator`；
- 不执行方法工具——转给 orchestrator 执行；
- 不写账、不改状态，经 `0001-state`；outbox 那张表也不归这里，这里只读它。

**为什么不叫 gateway 或 device**：gateway 的常义是**入口**，而这一块主要往外送，真正入站的只有连接
本身（runtime 主动外连）；device 只说了名词，漏了「对接」那一半。合同里这块的正式说法是
**执行端口**（`engineering.md`：「后端的执行端口保持中性，新增经 ① 派往 runtime 的适配器」），
`bridge` 是它的短名——桥天然双向，且两端都要管。

**为什么与 orchestrator 分开**：一个管「下一步是什么」，一个管「怎么送出去、设备在不在」。
新增一种 workflow 步骤类型只动 orchestrator；换连接方式、改租约策略只动这里。
合在一起，「步骤类型是开放集合」就守不住。
