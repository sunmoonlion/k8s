# Harbor 主服务版本重新评估

日期：2026-09-27。目标仍是一套部署代码、KIND/kubeadm两种建群方式；仓库独立于集群。

## 决策依据与当前实际版本

最初所有者要求Harbor等平台原版本搬迁，只有集群兼容性阻断才升级，因此有意先用2.13.2恢复并核数据，减少同时改变版本、位置和入口带来的排障困难。此前把版本选择描述成“疏忽”不准确，在此纠正；原决定继续作为迁移基线。后来所有者将固定版本的重点调整为数据库引擎，主服务升级因此进入后续评估。

所有者本轮确认：**先完成2.13.2同版本迁移验收，再备份、在独立数据库副本上演练2.15.2，演练通过后单独升级正式实例。PostgreSQL17.6、Redis8.2.1保持不变。**两个阶段分别保留证据和回退点，不把扫描器镜像更新当成Harbor主服务升级，也不把宿主恢复副本的部分验收当成正式搬迁完成。

2026-09-27官方GitHub API返回Harbor最新稳定版为 **2.15.2**，发布时间2026-07-02；并非2.15.3-rc。当前旧集群及已恢复的宿主副本仍是 **2.13.2**，没有执行主服务升级、数据库schema迁移或入口切换。

扫描器与主服务版本分开记录：官方`ghcr.io/goharbor/trivy-adapter-photon:v2.15.2`已准备、导入并通过断网rootfs扫描；其对应adapter0.38.0、Trivy0.72.0。这个镜像tag不表示Core/Portal/Jobservice等也已升级。

## 2.15.2 作为主服务升级候选的依据

| 检查 | 已核事实 | 实施前还需完成 |
| --- | --- | --- |
| 升级路径 | [2.15官方升级指南](https://goharbor.io/docs/2.15.0/administration/upgrade/)覆盖2.12及以后版本，包含当前2.13.2 | 在独立PG副本上演练schema迁移，不能仅根据文档宣称数据已兼容 |
| PostgreSQL17.6 | 升级指南说明外部PG至少12；[2.15.2配置模板](https://github.com/goharbor/harbor/blob/v2.15.2/make/harbor.yml.tmpl)保留external_database | 继续使用固定PG17.6镜像，核迁移SQL、运行查询、恢复与回退；最低版本条件不是完整兼容测试 |
| Redis8.2.1 | 同一模板保留external_redis、AUTH及独立DB index参数 | 继续使用原Redis8.2.1，实际验Core、Registry、Jobservice、Trivy队列与缓存 |
| 默认引擎变化 | [2.15.2发布说明](https://github.com/goharbor/harbor/releases/tag/v2.15.2)包含内置PG18及Valkey相关变化 | 只选择Harbor应用组件；禁止直接运行全套默认安装去替换既定PG/Redis |
| 显式迁移 | [Core源码](https://github.com/goharbor/harbor/blob/v2.15.2/src/core/main.go)支持`-mode migrate`和`-mode skip-migrate` | 独立迁移任务完成并对账后，API用skip-migrate启动，符合C-D8 |

**数据库引擎版本不变，不意味着Harbor表结构也不变。**应用版本升级可能修改schema，必须保留2.13.2逻辑备份和未升级数据库，不能让旧Core连接升级后的库假装回退。

## 修订后的实施顺序

1. **当前先完成同版本迁移。**补齐2.13.2的扫描器/Jobservice、账号/机器人令牌、认证推拉、CI/CD及重建KIND独立性验收。保留原密钥、五年证书、全registry目录摘要与逻辑备份；现有恢复基线仅通过只读和备份恢复部分验收，不能提前判为迁移完成。
2. 将2.15.2应用组件与官方prepare的离线物料单独钉摘要；PG17.6、Redis8.2.1单独固定，正式生成器不得默认带入PG18/Valkey。现在只备好了新版扫描器，不能宣称整套2.15.2物料齐备。
3. 先用独立PG/Redis副本演练；同盘registry17GB不盲目复制。数据盘仍需保留20GiB余量，候选阶段可设计只读引用已核对的registry，明确禁止双写；正式写入的数据归属和生命周期必须先接好。不得为了升级提前清理旧节点、卷或备份。
4. 对schema变更逐项解释，对账以业务数据和权限为准：项目、仓库、全部manifest/digest/tag、镜像层全文件SHA、用户/机器人权限、扫描器登记及系统设置。新增表或审计行不应伪装成“所有表字节不变”。
5. 第一步迁移验收后再执行主服务升级；升级前冻结写入，生成与当时数据一致的新备份，恢复演练不能只沿用早期副本的结果。升级后重复启停、认证推拉、Jobservice、扫描、CI/CD和备份恢复验收。正式30443切换和停止旧controlplane的具体窗口仍未批准。
6. 成功后完善唯一物料手册，最后按授权清单回收；旧容器/卷与回退数据继续按观察期保护。云上只改共享代码并做dry-run，未经实机验证。

## 安全与验收边界

最新稳定版本仍需检查已知问题。新版扫描器本次检测487包，报告17条CRITICAL（9个CVE）及82条HIGH，主要严重发现位于Photon系统库；原镜像与新镜像包集合、扫描器版本不同，不能用发现数相减当作风险下降比例。完整记录见[扫描器物料](scanner-offline.md)。

这些发现没有自动等同于可利用漏洞，也没有被忽略。功能通过、安全适用性评估、正式运行准入分别记录；现阶段`formal_admission=false`。下一步需核系统包公告、当前调用场景及修复方式，再确定最终候选，主服务升级同样遵循此标准。

本文是对主服务版本选择及下一阶段路径的重新评估，**不表示Harbor2.15.2已经部署或数据迁移通过**。后续执行不能仅把旧脚本中的版本字符串替换掉：生成配置、schema迁移、镜像角色、备份恢复与回退都要同步处理。
