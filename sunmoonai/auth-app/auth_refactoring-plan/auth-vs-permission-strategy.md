# 认证 vs 权限：实施策略分析

## 一、当前状态分析

### 1.1 认证（Authentication）现状

**当前实现**：
- 使用 JWT Token 机制
- 用户信息包含：`is_superuser`, `is_active`, `UserRole` 等基础字段
- 需要改造为：Session + Cookie 机制

**涉及范围**：
- auth-app-bff：认证服务核心
- auth-app-ssr：前端认证流程
- incubator-app-bff / llmops-app-bff：调用认证服务

### 1.2 权限（Authorization）现状

**当前实现**：
- 只有简单的 `is_superuser` 检查
- `llmops-app-bff` 有 `get_current_active_superuser` 依赖
- `proto/user.proto` 中定义了 `UserRole` 结构，但未完整实现
- 没有完整的 RBAC（基于角色的访问控制）系统

**涉及范围**：
- 权限判断逻辑分散在各个 BFF 中
- 没有统一的权限管理服务
- 权限数据存储在用户信息中（`is_superuser`, `UserRole`）

---

## 二、认证与权限的关系

### 2.1 依赖关系

```
认证（Authentication）
  ↓
确定用户身份（用户 ID、用户名等）
  ↓
获取用户信息（包含权限信息：is_superuser, roles 等）
  ↓
权限（Authorization）
  ↓
判断用户是否有权限执行操作
```

**关键点**：
- 权限系统**依赖**认证系统（需要知道用户是谁）
- 但权限系统的**设计**可以独立于认证机制
- Session + Cookie 改造主要影响**认证流程**，不影响**权限判断逻辑**

### 2.2 数据流

**当前流程**：
```
用户请求 → JWT Token → 验证 Token → 获取用户信息（含权限）→ 权限判断
```

**改造后流程**：
```
用户请求 → Cookie (session_id) → 从 Redis 获取 Session → 获取用户信息（含权限）→ 权限判断
```

**变化**：
- 认证方式改变（JWT → Session）
- 权限判断逻辑**不变**（仍然基于用户信息中的权限字段）

---

## 三、两种实施策略对比

### 策略 A：分开解决（推荐）

**步骤**：
1. **Phase 1**：先解决认证问题（Session + Cookie）
   - 改造认证流程
   - 确保用户信息正确获取（包含权限字段）
   - 权限判断逻辑保持不变（继续使用 `is_superuser` 等）

2. **Phase 2**：再解决权限问题（RBAC 系统）
   - 设计完整的权限系统
   - 实现角色和权限管理
   - 统一权限判断逻辑

**优点**：
- ✅ **关注点分离**：认证和权限问题分开解决，复杂度降低
- ✅ **风险可控**：先解决认证，稳定后再解决权限
- ✅ **迭代开发**：可以分阶段交付，先让认证系统稳定运行
- ✅ **测试简单**：每个阶段都有明确的测试范围

**缺点**：
- ⚠️ 可能需要两次改造（如果权限系统设计需要调整 Session 结构）

---

### 策略 B：一起解决

**步骤**：
1. **统一设计**：同时设计认证和权限系统
2. **一起实施**：在 Session 中存储完整的权限信息
3. **统一测试**：同时测试认证和权限功能

**优点**：
- ✅ **统一设计**：可以一次性设计好 Session 结构和权限模型
- ✅ **避免返工**：不需要因为权限系统调整而修改 Session 结构

**缺点**：
- ❌ **复杂度高**：两个问题一起解决，工作量大
- ❌ **风险高**：如果权限系统设计有问题，可能影响认证系统
- ❌ **测试困难**：需要同时测试认证和权限，测试用例复杂
- ❌ **交付周期长**：需要等两个系统都完成才能交付

---

## 四、建议方案

### 4.1 推荐：分开解决（策略 A）

**理由**：

1. **认证是基础，权限是上层**：
   - 必须先有稳定的认证系统，才能在此基础上构建权限系统
   - 权限系统可以复用认证系统的用户信息

2. **复杂度管理**：
   - Session + Cookie 改造已经是一个大工程
   - 权限系统设计（RBAC）也是一个独立的复杂系统
   - 分开解决可以降低风险

3. **迭代开发**：
   - Phase 1：完成认证改造，系统可以正常运行（使用简单的 `is_superuser` 权限）
   - Phase 2：在稳定的认证基础上，设计和实现完整的权限系统

4. **灵活性**：
   - 如果权限系统设计需要调整，不会影响已经稳定的认证系统
   - 可以独立优化权限系统，不影响认证流程

### 4.2 实施建议

#### Phase 1：认证改造（Session + Cookie）

**目标**：
- 完成 Session + Cookie 认证机制
- 确保用户信息正确获取（包含 `is_superuser`, `UserRole` 等权限字段）
- 保持现有的简单权限判断逻辑（`is_superuser` 检查）

**Session 结构**（包含权限字段）：
```json
{
  "session_id": "uuid",
  "user_id": 1,
  "username": "user@example.com",
  "is_superuser": true,
  "is_active": true,
  "roles": [{"roleId": 1}, {"roleId": 2}],  // 保留权限字段，供后续使用
  // ... 其他用户信息
}
```

**说明**：
- Session 中存储权限字段，但不实现完整的权限系统
- 权限判断逻辑保持不变（继续使用 `is_superuser`）
- 为后续权限系统预留接口

#### Phase 2：权限系统设计（RBAC）

**目标**：
- 设计完整的 RBAC 权限系统
- 实现角色和权限管理
- 统一权限判断逻辑

**可以复用 Phase 1 的成果**：
- Session 中已经包含权限字段
- 用户信息获取流程已经稳定
- 只需要在权限判断逻辑上扩展

## 五、如果选择一起解决（策略 B）

### 5.1 需要同时考虑的问题

1. **Session 结构设计**：
   - 需要同时考虑认证和权限的数据需求
   - 权限信息如何存储（角色、权限列表等）

2. **权限判断接口**：
   - 需要设计统一的权限判断接口
   - 各个 BFF 如何调用权限服务

3. **权限数据同步**：
   - 权限变更时如何更新 Session
   - 权限缓存策略

### 5.2 实施复杂度

- **工作量**：认证改造 + 权限系统设计 = 2倍工作量
- **测试复杂度**：需要同时测试认证和权限，测试用例数量增加
- **风险**：如果权限系统设计有问题，可能影响认证系统

---

## 六、最终建议

### 推荐：分开解决（策略 A）

**实施顺序**：

1. **第一步**：先解决认证问题（Session + Cookie）
   - 完成认证机制改造
   - 确保用户信息（含权限字段）正确获取
   - 保持现有简单权限判断逻辑

2. **第二步**：再解决权限问题（RBAC 系统）
   - 在稳定的认证基础上设计权限系统
   - 实现完整的 RBAC 功能
   - 统一权限判断逻辑

**关键点**：
- Session 结构设计时，**预留权限字段**（`is_superuser`, `roles` 等）
- 权限判断逻辑保持简单（继续使用 `is_superuser`），后续再扩展
- 为权限系统预留扩展接口

## 七、决策确认

### 7.1 已确认的决策

- [x] **策略选择**：分开解决（先认证，后权限）
- [x] **Session 结构**：预留权限字段（`is_superuser`, `roles` 等）
- [x] **权限系统范围**：完整的 RBAC 系统
- [x] **权限管理服务**：不需要独立的权限管理服务（权限管理集成在 auth-app-bff 中）

**Phase 1：认证改造（Session + Cookie）**
- Session 结构预留权限字段
- 保持现有简单权限判断逻辑（`is_superuser`）
- 为后续 RBAC 系统预留扩展接口

**Phase 2：权限系统设计（RBAC）**
- 在 auth-app-bff 中实现完整的 RBAC 功能
- 设计角色和权限管理
- 统一权限判断逻辑
- 更新 Session 结构以支持完整的权限信息
