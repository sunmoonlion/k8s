## 0. 一句话总括

> 成熟流程 = **阶段有产物、产物有落点、落点有判据、判据尽量由机器执行**。

再加三条横切：**契约先行**解耦全栈、**可逆性**降低流程重量、
**文档按决策/规格/状态三分**避免混写。

剥掉各家花名（Scrum / SAFe / Shape Up 各有术语），主干都是这一条：
**一条需求的生命周期**。差别只在阶段合并到什么程度、多少环节被自动化。

## 1. 主干：一条需求的九个阶段

每一阶段必须明确三件事：**产出什么、存在哪、凭什么算过关。**
缺第三件的阶段，实际上不存在——它只是一段时间。

| # | 阶段 | 核心产物 | 准出判据 |
| --- | --- | --- | --- |
| 1 | 需求定义 | PRD / User Story | 验收标准可验证；非功能需求已列 |
| 2 | 交互设计 | 用户流程 → 线框 → 视觉 → 组件规格 | 关键路径与四种状态都有稿；沿用设计系统 |
| 3 | 技术设计 | 技术方案 + ADR + 数据模型 + **API 契约** | 方案过评审；取舍记成 ADR；契约冻结 |
| 4 | 拆解排期 | Epic → Story → Task | 满足 **DoR** |
| 5 | 实现 | 代码 + 测试（特性分支） | 本地质量门全绿 |
| 6 | 评审 | Pull Request | CI 绿 + 有效评审通过 |
| 7 | 集成测试 | 契约测试 / E2E / 回归 | 金字塔各层通过；迁移已演练 |
| 8 | 发布 | 制品 + 迁移 + 特性开关 | 走完环境阶梯；**回滚路径已验证** |
| 9 | 运行反馈 | 监控 / 告警 / 复盘 / 技术债登记 | SLO 未破；问题回流成新需求 |

下面逐阶段展开，重点在**常见失败**——那才是判据要防的东西。

### 1.1 需求定义

**产物**：谁、在什么场景下、要达成什么、达成了怎么看得出来。

验收标准的通行写法是 Given / When / Then：

```
Given  用户已登录且持有 A 股组合
When   请求"对该组合做行业暴露分析"
Then   30 秒内返回按申万一级行业的暴露表，每一项可下钻到成分股
```

**非功能需求（NFR）必须同时写**：延迟、并发、数据规模、可用性、安全与合规、成本。
NFR 缺失是后期返工的头号来源——它们通常决定架构，而不是决定实现细节。

**常见失败**：
- 需求写成"完善 X"、"优化 Y"——**没有终点，永远做不完**；
- 只写功能不写 NFR，等压测时才发现架构选错；
- 验收标准由实现者自己定，等于没有验收。

### 1.2 交互设计

**产物**：用户流程图 → 线框 → 视觉稿 → 组件规格。

**四种状态必须都有稿**，这是最容易漏的一条：

| 状态 | 说明 |
| --- | --- |
| 正常态 | 有数据、一切正常 |
| 空态 | 没有数据，首次进入 |
| 加载态 | 尤其是长耗时任务的中间反馈 |
| 错误态 | 失败、超时、无权限，分别长什么样 |

**设计系统**（组件库 + 设计规范 token）是这一阶段的复用基础：
新界面应当由既有组件拼出来，需要新组件时要显式立项，
否则每个页面都长得不一样，且没人维护得动。

**常见失败**：只画了正常态，空/错/慢三态到开发时临时发挥——
这三态恰好是长耗时 AI 产品最常出现的态。

### 1.3 技术设计

**产物**三件，性质不同，别混：

| 产物 | 写什么 | 生命周期 |
| --- | --- | --- |
| 技术方案 | 怎么实现、涉及哪些模块、风险与备选 | 实现完成后价值衰减 |
| **ADR** | 当时面临什么问题、有哪些选项、**为什么选它** | **写完不改**，只被后来的 ADR 取代 |
| 数据模型 + API 契约 | 表结构、索引、迁移；接口的请求/响应/错误 | 随代码同步演进 |

ADR 的标准结构极简，值得照抄：

```
标题（编号 + 一句话结论）
状态：提议 / 已接受 / 已弃用 / 被 ADR-0042 取代
背景：当时面临什么约束和问题
决策：我们决定做什么
后果：这带来什么好处、什么代价、放弃了什么
```

**ADR 的价值全在"后果"和"当时"两个词上。** 它记的不是现状——现状看代码就行——
而是**代价与放弃**，那是代码里读不出来的。

**常见失败**：把 ADR 写成技术方案（于是它需要不断更新，然后就腐烂了）；
或者根本不写，半年后没人知道当初为什么不用某个更简单的方案，于是重新讨论一遍。

### 1.4 拆解排期

**产物**：Epic → Story → Task 三级，粒度递减。

关键不是层级，而是 **DoR**（就绪定义），见第 3 节。

**常见失败**：按技术分层拆（"先做完所有后端接口，再做前端"），
导致很久看不到可用的东西，且集成风险全部堆在最后。
成熟做法是**按用户可感知的价值垂直切**：一个 Story 穿透前后端，做完就能用。

### 1.5 实现

**产物**：代码 + 测试，在特性分支上。

**本地质量门**（提交前自动跑）：格式化 → lint → 类型检查 → 单元测试。
这四样应当是**一条命令**，且与 CI 跑的完全一致——
本地和 CI 检查不一致，是"在我机器上是好的"的根源。

分支策略两个主流：

| 策略 | 适用 |
| --- | --- |
| **主干开发**（trunk-based）+ 短命分支 + 特性开关 | 团队小、CI 强、发布频繁 —— 现在的主流 |
| GitFlow（develop / release / hotfix） | 有明确版本发布节奏、需要长期维护多版本 |

提交信息用 Conventional Commits（`feat:` / `fix:` / `refactor:`）之类的约定，
好处不是好看，而是**可以据此自动生成变更日志、自动判断版本号**——
凡是约定，都要有机器消费它，否则就是仪式。

### 1.6 评审

**产物**：Pull Request。

PR 描述要说清**为什么**，而不只是改了什么——"改了什么"读 diff 就有。
好的 PR 模板会强制三栏：**动机 / 做法 / 怎么验证的**。

评审的准出是两条：**CI 必绿**（不许"先合了再修"）+ **至少一次有效评审**。

**常见失败**：PR 太大。超过几百行的 diff，评审质量会断崖式下降，
评审人只能看格式和命名。**控制 PR 大小是提升评审质量最有效的单一手段。**

### 1.7 集成测试

测试金字塔：

```
        /\        E2E          少而慢，只覆盖关键业务路径
       /  \       集成 / 契约   中等，覆盖模块与服务边界
      /____\      单元          多而快，覆盖逻辑分支
```

层数不重要，两条纪律重要：

1. **CI 红了不许合。** 一旦允许例外，红色就变成噪音，几周后没人看 CI。
2. **每个 bug 修复先补一个能复现它的测试。** 这是让测试集随时间变值钱的唯一机制——
   否则测试集只会覆盖当初想到的场景，而 bug 恰好出在没想到的地方。

数据迁移要在**类生产规模的数据**上演练，并且演练回滚。
迁移是少数真正不可逆的操作之一。

### 1.8 发布

环境阶梯：`本地 → dev → staging → prod`。

三个机制让发布从"大事"变成"日常"：

| 机制 | 作用 |
| --- | --- |
| **特性开关** | 代码已合并但功能未开启，**部署与发布解耦** |
| **灰度 / 金丝雀** | 先放 1% 流量，看指标再放量 |
| **回滚路径** | 出问题几分钟内退回去，**且这条路径被验证过** |

**回滚路径未经验证 = 没有回滚路径。** 很多团队直到出事那天才发现回滚脚本是坏的。

这一节的深层道理：**可逆性买来的是速度。**
当发布随时可关、可退时，就不需要靠冗长评审去追求零缺陷；
反过来，真正不可逆的动作——数据库迁移、对外契约破坏性变更、删除数据——
才值得上重流程。**按可逆性分配流程重量**，比对所有变更一视同仁高效得多。

### 1.9 运行反馈

**产物**：可观测性三件套（日志 / 指标 / 链路追踪）、SLO 与告警、事故复盘、技术债登记。

事故复盘要**对事不对人**（blameless）：目标是找出系统为什么允许这个错误发生，
而不是谁犯的错。复盘的产出必须是**具体的改进项并进入待办**，否则复盘变成走过场。

技术债要**显式登记**并标注利息（不还的话，未来什么会变慢或变危险）。
不登记的技术债，最终以"这块没人敢动"的形式表现出来。

## 2. 三条横切线

### 2.1 契约先行（API-first）—— 全栈的核心解耦点

这是"全栈开发"区别于"前端 + 后端"的关键机制。

**做法**：契约（OpenAPI / JSON Schema / protobuf）是前后端**唯一的真相来源**，
且**先于两边的实现存在**。

三个直接收益：

| 收益 | 机制 |
| --- | --- |
| 前后端并行 | 前端拿契约生成 mock，不等后端实现 |
| 集成前发现不兼容 | 契约测试（consumer-driven contract）双向验证 |
| 变更成为显式事件 | 破坏性变更必须版本化，而不是某天前端突然报错 |

**没有这条，全栈开发就退化成"前端等后端，后端猜前端要什么"。**

契约还应当**能被机器校验**：实现是否符合契约、mock 是否与契约同步、
文档是否由契约生成。手工维护的接口文档必然与实现漂移。

### 2.2 测试金字塔 + CI —— 唯一不依赖人的守门人

见 1.7。这里补一条组织层面的：

**CI 是流程里唯一不会累、不会忘、不讲情面的角色。**
所以凡是能交给 CI 的判据都要交给它；交不了的，要显式承认它靠纪律。
把靠纪律的和靠机器的混在一张清单里，是最常见的自欺。

### 2.3 环境阶梯与可逆性

见 1.8。核心是那句：**按可逆性分配流程重量。**

## 3. 两个门：DoR 与 DoD

我认为这是整套流程里最值钱的东西。多数团队的混乱不是没有流程图，
而是**"可以开工了"和"做完了"每个人理解不一样**。这两个门就是把这两句话写成清单。

### 3.1 DoR — Definition of Ready（准入）

一个任务满足以下全部条件才可以开工：

- [ ] 需求清楚，验收标准可验证（不是"完善 X"）
- [ ] 依赖已就绪，或已明确阻塞在哪
- [ ] 技术方案有共识，重大取舍已记 ADR
- [ ] 涉及接口的，契约已定
- [ ] 涉及界面的，设计稿已出（含空/错/慢三态）
- [ ] 粒度合适：能在一个迭代内完成
- [ ] 测试策略已定：这条要用哪几层测试

### 3.2 DoD — Definition of Done（准出）

- [ ] 代码合并进主干
- [ ] 测试通过，且**新增了对应的测试**
- [ ] CI 全绿
- [ ] 文档已更新（契约、README、ADR 按需）
- [ ] 已部署到 staging 并验证
- [ ] 验收人确认（**不是实现者自己**）
- [ ] 监控与告警已覆盖（如涉及新链路）

**这两张清单要放在任务模板里，而不是放在流程文档里。**
放在流程文档里就没人看；放在任务模板里，每开一个任务它就出现一次。

## 4. 文档：分三类，从不混写

| 类 | 例子 | 更新频率 | 放哪 |
| --- | --- | --- | --- |
| **决策** | ADR：当时的问题、选项、为什么选它、放弃了什么 | **写完就不改**，只被后来的取代 | 仓内，编号递增，永不删 |
| **规格** | API 契约、数据模型、组件规格、验收标准 | 随代码同步，**改代码不改它就是 bug** | 紧挨代码，能被 CI 校验 |
| **状态** | 看板、迭代进度、待办、阻塞项 | 每天变 | 工具里，通常**不进仓** |

**混写的后果很具体**：

- 决策写进状态文档 → 随进度被改掉，几个月后没人知道当初为什么这么选；
- 状态写进规格文档 → 规格永远处于"待更新"，读的人不敢信；
- 决策写进规格文档 → 每次实现变化都要改决策，ADR 失去"当时"这个属性。

另有一条现代共识：**docs-as-code**——文档与代码同仓、同 PR、同评审，
且文档改动能被 CI 检查（链接有效性、契约与实现一致性）。
**不能被检查的文档一定会腐烂**，只是时间问题。

## 5. 哪些是仪式，可以不做

照抄流程时最容易连仪式一起抄进来。以下几项，除非有特定理由，收益都很低：

| 项 | 为什么低收益 |
| --- | --- |
| 详细工时估点、燃尽图、甘特图 | 除非要对外承诺日期，否则维护成本高于信息价值 |
| 需求追踪矩阵（RTM） | 除非受监管行业，手工维护的追踪表必然过期 |
| 多级评审签字 | 用 CI + 一次有效评审替代 |
| 穷尽式测试用例文档 | 用例应当是**可执行的测试**，不是表格 |
| 面面俱到的架构大文档 | 会腐烂；应拆成若干 ADR + 随代码的规格 |

**判断标准只有一条**：

> 这个产物，有没有人会真的回头读它？或者，有没有机器会检查它？
> 两者皆无，它就是仪式。

## 6. 这份参照系接下来怎么用

下一步是**逐格对照**，产出一张表，回答三个问题：

| 维度 | 要回答的 |
| --- | --- |
| 覆盖 | 九个阶段 + 三条横切，我们**哪几格有、哪几格空** |
| 重复 | 同一格里**塞了几份文件**，谁是权威 |
| 判据 | 每格的准出判据**是机器执行还是纪律**（对应 `constraints.md` 的三层） |

对照表出来之后，"乱在哪"就从感觉变成可指认的清单，
再决定是重组 `dev-plan/`、还是补空格、还是删重复。

**在那之前，本文件不产生任何约束力。**
