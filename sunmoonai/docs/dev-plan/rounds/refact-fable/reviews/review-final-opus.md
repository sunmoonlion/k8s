## 2. 必改：§3.13.1 的取证错误

**§3.13.1 表格第一行三处证据全错**，2026-09-05 在同一台机器复核：

| 原文断言 | 复跑命令 | 实际 |
| --- | --- | --- |
| 「`id` → `uid=0`」 | `id` | `uid=1003(zym) gid=1003(zym) groups=…,27(sudo),988(docker)` |
| 「`ps -eo user,cmd` 中 codex / claude 均为 root」 | `ps -eo user,comm \| grep -E 'codex\|claude\|cursor'` | 全部 `zym` |
| 「`/home/zym` 属 `root:root`」 | `stat -c '%U:%G' /home/zym` | `zym:zym` |

本机 106 个 root 进程全部是内核线程、systemd 服务与云厂商 agent
（`barad_agent` / `sgagent` / `tat_agent` / `YDLive` / `YDService`，腾讯云监控），**不含任何一家助手 CLI**。
`~/.ssh`、`~/.gnupg`、`~/.codex-*` 均为 `zym:zym` 700。

### 2.1 结论仍然成立，但理由要换

该行的结论——「本机不存在任何 agent 读不到的文件」——**依然为真**，只是原因不是「都是 root」，而是
**四家 CLI 与人的 shell 是同一个 UID（`zym`）**。同 UID 即同权限，`~/.gnupg`、`gpg-agent` 套接字、
`id_rsa`、仓内验证脚本，agent 一样可读可写。所以 §3.13.2「A 档回执仓」的裁定不受影响。

**但这不是措辞问题。**本仓自己立的规矩是「锚点存在但不支持断言，比没有锚点扣得更重——那是伪取证」
（`refact-rulings.md` / round-protocol「判据自身的质量」）。一份把威胁模型建在取证上的文档，
取证栏必须准。

### 2.2 连带后果：B 档的成本评估基于错误前提

§3.13.2 B 档（账户隔离）成本栏写「运维改造大：四家 CLI 目前都装在 `/home/zym/.nvm` 下**以 root 跑**」。
既然它们本来就以普通用户 `zym` 运行，**B 档的成本比文档估的低得多**——只需给四家各建一个 Unix 用户、
把 worktree 归属改掉，不涉及降权改造。

我不主张本轮就上 B 档（A 档确实单独成立），但**成本评估要改对**，否则将来复核「为什么没选 B」时依据是假的。

补一条 B 档真实成立的前提（原文没写）：`zym` 同时在 `sudo` 与 **`docker`** 组。
docker 组等价于 root（可挂载宿主文件系统）。**B 档要有效，agent 专用用户必须不在 `sudo` 与 `docker` 组**，
否则隔离是纸面的。

## 3. 一个缺口：方案 A 防住了伪造 tag，没防住伪造判定

§3.13.1 的引用块自己写了威胁面包含「**改掉验证脚本**」：

> agent 能生成一把新钥、把公钥加进任何本地信任列表、**改掉验证脚本**、再签一条 tag。

但 §3.13.2 的 A 档只把**信任锚**移到了 agent 够不着的地方（回执仓），**执行判定的代码仍在工作仓里**：
`round-status.py`、`round-dispatch.py`、`.githooks/pre-commit` 全部 `zym:zym` 可写。

于是攻击路径变成：不伪造 tag，**伪造判定**——改 `round-status.py` 让它对 H5 直接返回成立，
或改 pre-commit hook 跳过 tag 校验。§3.3 的 `enforcement_point` 列写「主线 push hook 校验回执仓 tag 存在」，
**而 hook 本身也在仓里**。

### 3.1 这不推翻 A 档，但要补一条

真正不可绕的强制点只有两类：

| 强制点 | 为什么不可绕 | 代价 |
| --- | --- | --- |
| **服务端**：主线分支保护 / 服务端 hook | 不在 agent 可写范围 | GitHub 私有仓分支保护需 Pro（本稿已核 ruleset 同此限制），故与 A′ 同命 |
| **发布动作由人在 Windows 上执行** | agent 根本不发起该动作 | 人多一步 `git push origin master`；但 H5 本来就要人签，顺手 push 不增触点 |

我建议采第二条并写进 §3.3 的 H5 行：**H5 的 enforcement_point 不是「VM 上的 hook 校验 tag」，
而是「主线 push 由持有回执私钥的那台机器执行」**。这样 H5 的强制点与签名点合一，都在 agent 边界之外，
且不依赖付费功能——与 A 档的选择理由一致。

⚠ 未验证：Windows 侧是否已有对工作仓的 push 权限、以及那台机上的 Cursor 本地 agent 是否也能发起 push
（§3.13.4 第 2 条已指出 Windows agent 同样是威胁，但只处置了签名，没处置 push）。

## 4. 三条未解决的旧问题

### 4.1 `independence` 的取值边界，在现有四家上就有歧义

3.2 给了折算规则（不同组个数、带证 ×2），但**没定义怎么分组**。现有配置里：

| 家 | 二进制 | 认证 | 模型 |
| --- | --- | --- | --- |
| luna | `codex` | `~/.codex-official` | gpt-5.6-sol |
| kimi | `codex` | `~/.codex-kimi` | kimi-k3 |

**同一个 codex 二进制、同一套提示词与工具，不同模型。**按模型算是 `cross-vendor`，按 harness 算是 `same-runtime`。
折算规则的第一步（「所属不同 `independence` 组」）在我们**最典型的一对**上就判不了。

建议：取值从单值改为**两个维度**（`harness` / `model`），先只登记不折算；
折算规则等有「同 harness 不同模型的候选相似度」观测值之后再定（这与 §7 风险 6 的方向一致，
但那条只说「靠人登记」，没说取值本身没定义）。

### 4.2 `bootstrap` 档是绕过判据，不是解决判据

cursor C3 加 `bootstrap` 档解决了 R0/S1「验收条不能引用尚不存在的策略」这个真问题，**这一步是对的**。
但它没有回答我上一轮提的：**六轮里三轮 T2，是不是档位判据本身偏紧**。

`round-protocol`「判据：命中任一条即 T2」的「权威层」一条几乎覆盖 `dev-plan/` 下所有文件——
于是「改协议」「改权力表」「改策略」全是 T2，而 T2 是四家并行 + 互评 + 裁决 + 异议 + 验收。

这不是本稿的错（判据是我写的），但本稿把它照单全收，并用新增档位来回避冲突。
**新增一个档来绕过判据，通常说明该改判据。**建议列入 §7 未决，与 §7-12（协议变更是否必须开轮）合并考虑。

### 4.3 T0 任务类包的 `paths` 过宽，机械门形同虚设

3.6 的示例：

```toml
[bundle.doc-typo]
paths  = ["sunmoonai/docs/**/*.md"]
gates  = ["doc-gate.py", "link-check"]
covers = "仅改文档笔误与链接，不改约束、协议、脚本行为"
```

`covers` 明确说「不改约束、协议」，但同节又明确写「**不做 `covers` 与 `intent_restatement` 的字面匹配**」——
即 `covers` 不判。于是唯一的机械边界是 `paths`，而 `sunmoonai/docs/**/*.md` **包含**
`constraints.md`、`round-protocol.md`、`authority.md` 本身。

复跑：

```bash
ls sunmoonai/docs/dev-plan/{constraints.md,round-protocol.md}   # 都在 paths 覆盖内
```

后果：一个把「改写 constraints.md 某条规则」包装成 doc-typo 的 T0 工单，**开工前零触点**，
`doc-gate` 与 link-check 都会通过（它们不判语义）。H5 仍需签名，所以危害有界；
但「T0 的诚实定义是『改动限于路径 X、通过门禁 Y』」这句话，在示例包上不成立——
路径 X 大到把权威文件全包了。

建议二选一：

- `paths` 加排除项（`paths_excluded = ["**/constraints.md", "**/round-protocol.md", "**/authority.md", "**/policies/**"]`）；
- 或规定**任务类包的 `paths` 不得覆盖任何 `doc-gate.py` 的 `SELF_CONTAINED` 文件与 `policies/`**，由脚本校验包定义本身。

后者更好：它把约束加在**包的定义**上，而不是每次用包时再判——符合本稿自己「门加在会报错的地方」的取向。

## 5. 三处小的不一致

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | §7 风险 4 vs §3.13.5 风险 5 | 一处写「每轮 ⑦ 用 VM 身份 `git push receipts confirm/_probe`，必须被拒」，另一处写「做一次 `push --dry-run`」。**前者若配置漂移成可写就真写进去了**，而回执仓规则是「只增不改」，那个假 tag 会永久留下。应统一为 `--dry-run` |
| 2 | §3.13.3 `expires` 字段 | 只说「过期 tag 不算回执；重新签」，未定义**时长由谁定**，也未说明**已按该回执发布之后 tag 过期**意味着什么（回执失效？发布回滚？）。建议写明：`expires` 只约束「该回执可用于放行的窗口」，放行发生后不追溯 |
| 3 | §8 第 4 条 (a) | 要求「三份新文档中出现的 Task / Attempt 状态词与内核对称差为空」。但 Artifact 状态词 `DRAFT`/`FROZEN`、历史说明、词汇对照里必然出现旧词。§8 第 1 条给禁止词表留了「除词汇对照小节外」的豁免，第 4 条没留同类豁免，实现时会误报。建议同样加豁免范围，并写进判据本身（P4：判据必须声明覆盖范围） |
