# 0001-state：状态与账

**承担**：状态与账的**唯一权威写入面**。合同的原话是「**状态与账只有一份，在后端自己的库里**」——这一块就是那一份。

- Task 与 Attempt 两层状态机，**所有入口共用同一个转换函数**，以状态版本比较交换；
- 事件表，只追加（`I4`）；
- **四本账**：幂等、预算、副作用、证据；
- **outbox 与投递器**：派发与状态改在同一个事务里落 outbox，投递器另跑；
- 任务队列；
- 重启恢复：后端不驻留内存状态，扫非终态对象即可恢复。

**不承担**：

- **不决定做什么**——路由归 `0002-router`，下一步是什么归 `0003-orchestrator`；
- 不与外界通信。它不朝任何一侧，其余五块都经它改状态与写账。

**注意不要和「产品内核」混**：那个词在本项目里指 Task、Attempt、Interaction、Artifact、Event、
Side Effect、Delivery 这套**对象模型与状态机语义**，是跨三个模块的抽象契约（见 [`objects.md`](../../../../architecture/objects.md)）。
这一块是后端里**实现**那套语义的地方，不是那套语义本身。

**为什么单列**：四本账与状态机是其余五块的公共依赖。不单列，「同一事实只有一个权威写入面」
（P1）就只能靠纪律守——最典型的是**预算**：派发时扣、验收时结算，分在两块就是两处写同一本账。
提出来之后，终态、结果、预算结算的原子提交（`F-ACCEPT-05`）由这一块一处保证。

**边界要点**：任何状态改动都是「某块请求这一块做一次转换」，**不是自己写表**。
引入图执行框架会多出一份 checkpoint 状态，与这里的状态机成为两个真源（`I13`）——所以不引入。
