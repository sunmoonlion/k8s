# 开发的生命周期

**一问从人发出到人拿到可用的答的完整往返。**和产品那条往返是同一件事的两种实现：
[agent 版](../dev-agent/SDD/architecture/lifecycle.md) 由程序推，本文这一版由人推。

人现在兼着两个位置：**出题的人**和**驱动方**。这两件事要分开看——入口和分发不是一回事，
分发那一半将来会交给程序，入口不会。

⚠ 这里说的**驱动方**是「驱动这条流程的角色」，现在由人充当。**别和产品的后端 supervisor 混**——
那是程序，而且不调用生成式模型（见 [词汇表](glossary.md)）。

## 这条往返上有谁

| 角色 / 载体 | 是什么 | 在哪 |
| --- | --- | --- |
| **人** | 同时是出题的人、驱动方、批准人、定稿人——四个位置一个人兼 | 本机 |
| **执行者** | AI 助手；一问可以只派一家，也可以并行派几家 | 各自的会话窗口 |
| **传递** | **没有**：人当面说、当面给、当面批。这是人版与 agent 版唯一的结构性差别 | — |
| **问与答的载体** | 任务目录：`thread/<thread>/<turn>/` 下的 `user-message.md`、`response.md`、`turn.md` | git 仓 |
| **代码的载体** | 每个执行者一个独占 worktree、一条命名分支 | git 仓 |
| **定稿的落点** | `PRD/`、`SDD/`；要动代码则合并到 master | git 仓 |

**载体就是投影**——做到哪、谁在做、第几次返工，都从这些目录与提交读出来，不另写记录
（见 [turn 的投影](turn-project.md)）。

## 七站

```text
人
【写用户消息】这一问要什么、边界、要交回哪一种；存成 turn 的 user-message.md，发出即冻结
   ▼
【入口】人 → 驱动方：把这一问交出去
   │   现在驱动方就是人自己，所以这一步看不见；它对应 agent 版的【提交】
   ▼
【分发】驱动方 → 执行者：投喂
   │   单路：一家答 ┊ 多方竞争：几家各答（见 competition.md）
   │   通知里写清交什么、交到哪，执行者不用猜
   ▼
执行者【做】在自己的 worktree 里；文档段就写 response
   ├──【中断】要动不可逆的东西就停下来问，人当场批
   ▼
执行者【交回】response.md，或分支与提交；写 turn.md，交回即冻结
   ▼
【验收】未参与实施的一方按冻结的完成条件判（见 uat/verify-rules.md）
   ▼
人【定稿】读完取舍整理成 PRD/ 或 SDD/；要动代码则合并（见 finalize.md）
```

## 每一站算走完了没有

| 站 | 谁做 | 走完的判据 |
| --- | --- | --- |
| **写用户消息** | 人 | 边界写清了：含什么、不含什么、不含的归谁。**模型只知道这里写了的东西** |
| **入口** | 人 → 驱动方 | 这一问存进了 turn 目录，发出即冻结 |
| **分发** | 驱动方 | 执行者知道交什么、交到哪；并行时各家隔离，不泄露别家方案 |
| **做** | 执行者 | 在自己的 worktree、自己的分支上；不碰别人未提交的改动 |
| **中断** | 执行者 → 人 | 需要批准的动作**没批准就不做**；批准绑定这一版、这一项、有有效期 |
| **交回** | 执行者 | 交的是**分支与提交**或 `response.md`；报路径不报提交不算交回 |
| **验收** | 另一方 | 每条判定有 `pass` / `fail` / `undecidable`；判不了停在 `undecidable` |
| **定稿** | 人 | 写明以哪个 turn 为底、改了什么。**定稿不等于批准动代码** |

## 和 agent 版差在哪

人版七站，[agent 版](../dev-agent/SDD/architecture/lifecycle.md) 九站，逐站对：

| 人版 | agent 版 | 差在哪 |
| --- | --- | --- |
| 写用户消息 | 【写 message】 | 一样：都在本机把这一问写清楚 |
| 入口 | 【提交】 | 人版是人心里那一下，没有载体；agent 版是提交信封 + 幂等键，经通道 ④ |
| 分发 | 【受理】【派发】 | 人版是**投喂**——把话送到执行者窗口里；agent 版要受理、路由、排队、带签名投递、租约与 fencing |
| 做 | 【执行】 | 一样：在独立工作区里跑。agent 版多一层沙箱与 key 隔离 |
| 中断 | 【中断】 | 人当场说行；agent 版是 Interaction——绑版本、有有效期、**只能消费一次** |
| 交回 | 【封装】 | 人版交分支与提交，人自己去看；agent 版要本地内容检查 → 加密 → 上报密文 |
| 验收 · 定稿 | 【验收】【交付】 | 人版是人读完取舍整理；agent 版是确定性验收 + 终态原子提交 + 本机解密呈现 |

差别集中在**分发**和**中断**两站，原因只有一个：**人版没有传递面**。人当面说、当面给、当面批，
所以不需要信封、签名、租约和一次性令牌。一旦这条链要交给程序，这些就全都得有——
这不是把人版翻译一遍，是同一条意图在有传递面时必须落成的机制。

## 投喂可以脚本化

**分发**这一站的传输可以自动化，**中断**这一站不可以。

- 可以：脚本把消息投给**交互会话**——消息由脚本发出，审批照样浮到人面前。
- 不可以：非交互一次性模式（`codex exec` / `agent -p` / `qoder -p`）——权限开关把审批预先答掉。

自动化的是**传输**，不是**决定**。细则见 [操作闭环](protocol/competition-operations.md)「投喂」。

## 竞争挂在哪一站

多方竞争不是另一条周期，它是**分发**那一站的一种形态：同一问发给几家，多出互评、裁决、异议三个环节，
到【定稿】重新合流。规则见 [competition.md](competition.md)，本平台的做法见 [protocol/](protocol/README.md)。

## message 怎么到执行者

现在靠人当面说、当面给。要把话送出去时，形态有这几种：

| 层 | 状态 |
| --- | --- |
| 手工投喂：人把话粘进助手窗口 | **现在唯一跑通的** |
| 脚本投喂：脚本把话投给**交互会话** | 可行且不破坏批准点——消息由脚本发出，审批照样浮到人面前 |
| 非交互一次性（`codex exec` / `agent -p` / `qoder -p`） | **不可用**：权限开关把审批预先答掉 |
| 走产品通道派发 | 待开发 |

**自动化的是传输，不是决定。**这条线把「投喂可以自动」和「批准不能自动」分开——
两者不冲突，见 [人的批准点](approvals.md)。

## 人要盯住的几件事

- **用户消息里没写的，模型不会知道**：要它交回什么、能改哪些文件、哪些动作要先问，都写进用户消息。
- **判据先于产出冻结，但 PRD 与 SDD 不写进用户消息**：这两类按各类规则判；IMP 必须写完成条件。出题与答题分开，事后改题等于白问。
- **一个 turn 只问一件事**：PRD 问「要什么」，SDD 问「怎么做」，别混在一个 turn 里。
- **定稿是人的动作**，不是 AI 的：AI 交的是 response，进 `PRD/`、`SDD/` 的那一版由人负责（见 [定稿](finalize.md)）。
- 其余义务见 [人的批准点](approvals.md)。

## 交给程序驱动之前，两条已知风险

**一、人不在场之后，「确认」会退化成盖章。**现在人能确认，是因为全程在旁边、知道每一步发生了什么。
自动化之后，人会在流程末尾看到一份一千多行的稿子和一句「请确认」——这时点通过几乎是必然。

已经挡住一半：不设逾期默认、人不确认就不发布、确认前必须有检视面。**挡不住的是「看了但没真看」**。
补法是让人的注意力有落点——验收结论必须点名最该看的三处，见
[UAT 把关](uat/finalize.md)。

**二、难度地图和直觉是反的。**

| | 性质 | 状态 |
| --- | --- | --- |
| 怎么组织一群不确定的执行体 | **设计难**——没有现成答案，买不到抄不来，失败模式隐蔽 | 人版已跑通 |
| 怎么判断执行体做得对不对 | **工程难**——方法已知，费钱费时但路清楚 | 未做 |

所以不要按「先建判据与回路，再谈组织多个执行体」排期。**也不要把协作层跑通误读成执行内核已验证**：
那是另一条线，另有它自己的可证伪条件。
