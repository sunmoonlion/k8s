# turn 的投影

任务不是事先排好的：一问一问问出来、答出来、定稿，再由定稿长出下一问和下一层。

**本文写的是投影**——人要看见的那些东西。一问一答的状态本身摸不着：谁在答、答到哪、这一版算不算数、
在等谁，这些不会自己显形。目录怎么套、文件叫什么名、号怎么排、回执里那三个字段，**都是为了把它显给人看**。
做到哪、第几次返工、卡在哪，全从这些投影读出来，**不另写记录或进度文件**。

所以本文列的是人需要的几种投影：

| 投影 | 显出什么 |
| --- | --- |
| 任务目录（`thread/`、`PRD/`、`SDD/`） | 这个任务长什么样、拆到第几层、哪些是定稿 |
| thread 与 turn 两级目录 | 问过几轮、每一轮的问与答分别是什么 |
| `user-message.md` / `response.md` | 发出去的原话、交回来的原物；两者都冻结，所以**事后可以复核当时到底问了什么** |
| `turn.md` 的三个字段 | 交回没有、产物在哪条分支哪个提交 |
| 编号与命名 | 先后顺序、谁对应运行时的哪一个、跨节点怎么引用 |

**人版的投影载体就是 git 里的目录与文件**；换成数据库、Issue、PR 或事件流承载也可以，
但不能丢失原始请求、边界、验收、基线、证据和改判历史。agent 版的真源会移进记录里，
目录到那时才成为真正的投影。

**目录现在既是真源又是投影。**交给程序驱动之后，真源移到控制面，目录**只剩投影**。

- **不得直接编辑投影**：改目录不改记录，等于同一事实有两个权威写入面（P1）。
- 换成数据库、Issue、PR 或事件流承载都可以，但不能丢失原始请求、边界、验收、基线、证据和改判历史。

现在怎么执行见 [九站](../pipeline.md)。

## 四个种类

| 种类 | 问什么 | 答（response）在哪 | 定稿成什么 |
| --- | --- | --- | --- |
| **PRD** 产品需求 | 要什么、做到什么算满足 | turn 里 | `PRD/` 目录 |
| **SDD** 设计 | 怎样满足 | turn 里 | `SDD/` 目录 |
| **IMP** 实现 | 做出来 | 各自的 worktree | 审核通过后合并到 master |
| **UAT** 验收 | 验证是否满足 | worktree 的 `test/` | **结论写进那条提交的说明**，不进回执 |

**每一类的定稿就是它自己那份东西**：response 是 agent 的答，定稿是人读完取舍整理后的那一版，不换成下一种文档。
后面的问拿前面的定稿当输入：SDD 拿 `PRD/`，IMP 拿 `SDD/`。**但这不是排队**——一个任务可以开好几个 PRD thread，
IMP 里发现设计不对要回 SDD，子任务各走各的。四类不是四个先后相接的阶段，是四种问法；不是每件事都要把四类都走一遍。

### 一问属于哪一类

归类只问一句：**这一问的答案定下来，跟着改的是上表「定稿成什么」里的哪一份？**
改 `PRD/` 就是 PRD，改 `SDD/` 就是 SDD，改代码就是 IMP，改「这一版满不满足」的结论与证据就是 UAT。
**四份都不改的问题，多半不属于这个任务**：过程与工具怎么定（候选由谁选、用哪套门禁）是规范的事，去改规范，不在任务树里开 turn。

常混的几种：

| 这一问 | 属于哪一类 | 为什么 |
| --- | --- | --- |
| 后端能不能读客户任务的正文 | **PRD** | 信任边界是约束，属于「要什么」——明文读什么、加密什么，是需求对系统的限制 |
| 控制面用不用图执行框架 | **SDD** | 选型是怎样满足；否掉了哪几条、为什么，写进 `SDD/architecture/` 的「取舍」 |
| 并行候选取最先通过的一份，还是全交回再比较选定 | **SDD** | 两种都成立、要定死，定完 `SDD/` 才写得下去 |
| 状态机与 workflow 怎么分工 | **SDD** `architecture/` | 责任边界 |
| 步骤交回物要带哪些字段 | **SDD** | 接口与数据的形状 |
| 失败重试三次 | **SDD** | 除非这个次数客户要看得见、要进验收口径，那才是 PRD |
| 响应两秒内 | **PRD** | 非功能要求：要什么，不是怎么做 |
| 这一版为什么没通过 | **UAT** | 结论与证据。要改设计，写进结论并回 SDD 开新 turn，不在验收里改 |

这一类到什么程度算够，各类规则里紧接「这一类该问什么」的那一节各写各的——那也是它与下游那一类的界线。

### 归错了怎么办

- **一问里混了两类**：拆成两问，各归各类——不在同一个 turn 里混着答。
- **答越界了**（PRD 的 response 里给了技术方案）：**不打回**。定稿只收本类的那部分，越界那部分挪进下游那一类 turn 的用户消息里当输入。
- **整问派错了类**：agent 停下来问（见下面八条的第二条），由人改派到正确的那一类重开一个 turn，**不在原 turn 里补**。

## 一个例子

1. 一开始只有一句话：「做一个 AI 投资研究工具」。第 `0001` 个 thread 是 PRD：人问、AI 答、人改，几个 turn 之后人把 response 定稿成 `PRD/`。
2. 第 `0002` 个 thread 是 **SDD**：拿定稿的需求去问怎么做，response 定稿成 `SDD/`。`SDD/architecture/` 写模块之间的结构与关系，`SDD/modules/<号>-<短名>.md` **一个模块一份文件**说它是什么；往下的子任务目录在 `SDD/submodules/<号>-<短名>/`。
3. 某个子任务开自己的 thread，同样走 PRD、SDD 两类（需要哪类走哪类），再往下拆。
4. 要动代码时开 IMP thread：用户消息发出去，执行者在自己的 worktree 里做；回执记分支与提交。
5. UAT thread 派给验收者，测试写在 worktree 的 `test/`，**结论写进那条提交的说明**（回执只有三个字段）。判定不通过，就在新的 turn 里写明理由重做。
6. 重做到什么时候不再重做，由驱动方定：人自己判断，或由驱动程序的循环控制管。

## 任务目录里放什么

```text
<任务目录>/
├── thread/
│   └── <四位号>-<种类>-<运行时 thread id>/     种类是 prd、sdd、imp、uat
│       └── <四位号>-<运行时 turn id>/
│           ├── user-message.md   问：这一次发出去的用户消息
│           ├── response.md       答：PRD、SDD 两类有；IMP、UAT 没有
│           ├── turn.md           交回时写的回执
│           └── others/           可选：人或驱动方追加的材料与附件
├── PRD/requirement.md                 PRD 类的定稿：要什么。**不分模块**，长了按主题再拆几份
├── SDD/                          SDD 类的定稿
│   ├── architecture/                模块之间的关系
│   ├── modules/<四位号>-<短名>.md   每个模块本身是什么
│   └── submodules/<四位号>-<短名>/  子任务：内部是同样结构的任务目录
└── <约束目录>/                   可选：这一层的约束、纪律与开发提醒；名字自定
```

- **约束目录可选，名字自定**（本项目用 `rules/`）：装这一层必须守的和必须记得的——代码规则、开发指导。
  它不归哪一类，四类都要守，所以**与 `thread/`、`PRD/`、`SDD/` 平级**，不塞进某一段的定稿里。
- **模块只在 `SDD/` 下划**：分成哪几块是怎样满足，不是要什么。`architecture/` 是目录，入口文件 `README.md`，可以再拆多份。
- `SDD/modules/` 与 `SDD/submodules/` **同号同名一一对应**：前者是这一层对这块的说明，后者是它往下的子任务。
- 两者与实现时 worktree 里的模块目录**一一对应**；**以定稿为准**：代码结构要变，先改定稿。
- 子任务自己的 `PRD/` 写它要满足什么。
- 改动过的代码留在 worktree 与它的提交里，不拷进任务目录。
- **不另写记录或进度文件。**做到哪、谁在做、第几次返工、在等谁，都从这些目录与提交推出来；给人看的进度视图是投影。
  ⚠ 禁的是**任务目录里的第二份进度**。IMP 在自己 worktree 的代码分支上写 `CHECKPOINT.md`
  不在此列——那装的是推不出来的工作材料（决定、证据引用、要重新核实的事实），
  见 [IMP 规则](imp/message-rules.md)「跨运行时 thread 续接」。
- **目录只是一种载体。**换成数据库、Issue、PR 或事件流承载也可以，但**不能丢失原始请求、边界、验收、基线、证据和改判历史**。

## thread 与 turn

目录名、编号与运行时的对应关系见 [命名与编号](naming.md)；这里只写生命周期本身的规矩。

- **一个文档 thread 对一个运行时 thread**：运行时换了 thread（resume、fork、上下文压缩后重开），就新开一个文档 thread，接着做什么写在它第一个 turn 的用户消息里。
- **一个 turn 就是一问一答**：`user-message.md` 是问，`response.md` 是答。
- **发出时就把用户消息存进 `user-message.md`**：发出去的是什么，存的就是什么，包括附带的打回理由。模型只知道这些，判断交回对不对也以此为准。
- **response 只有一份**，是这一问的答，写成一个文件。它是草稿：定稿时才拆进 `PRD/` 或 `SDD/` 的 `architecture/`、`modules/` 与 `submodules/`。
- IMP、UAT 两类的 turn **没有 `response.md`**：产物在各自的 worktree 里，UAT 的测试放 worktree 的 `test/`。回执里记分支与提交。
- **turn 交回即冻结**，不改、不删；要改，只能开新的 turn。冻结防的是**篡改**——改写当时的问答，
  或抽掉一个不利的 turn。所以有两个例外，判据都很窄：
  - **整体搬迁**：上层目录改名时 turn 跟着走，字节零改动（`R100` 且 thread 名、turn 名、文件名都不变）；
  - **整棵任务目录退役**：这棵树不再生长时可以整体删除——该目录下的每个文件**同时**删除、
    **只删不改**，并在提交说明里写明退役原因与取证位置（tag 或提交号）。
  单独删一个 turn、只删一部分、或边删边改，一律不行。
- **turn 只负责问，不承载对答的判断**。意见不写进已有的 turn；要重做就开新 turn，理由写进它的 `user-message.md`。
- **并行**：同一问同时发给几个执行者时（多方竞争，或多次尝试取最好的一次），各家在各自的运行时 thread 里，所以是几个文档 thread 各开一个 turn，用户消息各存各的；定稿写明以哪一个为底。

## 用户消息写多严

用户消息就是发出去的那一问，存成 `user-message.md`。**模型只知道用户消息里写了的东西**：要它交回什么、能改哪些文件、
哪些动作必须先问人、有哪些背景和出处——凡是要它知道、要它遵守的，都必须写进去。没有哪个机制会替它补上。

写多严按任务轻重。下面说的是用户消息里要**表达出什么**，不是要用什么格式：一段自然语言说清了就算满足。

| 程度 | 适用 | 至少要说清 |
| --- | --- | --- |
| 一段话 | 可逆、局部、方向明确（T0） | 要什么、交回哪一种，以及要它遵守的任何限制 |
| 加边界 | 影响跨多个文件或多个仓（T1） | 要什么、交回哪一种、范围；IMP 类另加完成条件 |
| 按模板填全 | 命中任一条 T2 判据：不可逆、权威层、已知对立、判据未定 | 本类规则「这一类该问什么」里的每一栏；不适用的写「不适用」及理由 |

档位判据见 [多方竞争协议](competition.md)「档位」；各类要写清什么，见各自的规则。

- **用户消息由人写**；由上层定稿拆出的任务，用户消息来自定稿的相应一节，随定稿一起生效，人在定稿前可以修改。
- **写清边界**：含什么、不含什么、不含的归谁——否则执行者会自行扩大范围，或漏掉本该做的。
- **不把内容判据写进 PRD 与 SDD 两类的用户消息**：一旦写成条目，答案空间就被提前封死，
  「其实不需要这个机制」这类答案再也交不上来。这两类合不合格按各类规则判——规范本身就是判据，而且早就冻结了。
  ⚠ 禁的是**内容判据**（什么答案算对），不是**形式判据**（交什么、要回答哪几个问题、边界、格式）——
  后者必须发，否则各家交的东西形状各异，没法逐项比。两类的完整矩阵见
  [多方竞争协议](protocol/competition-protocol.md)「工单发什么、不发什么」。
- **IMP 类必须写完成条件**：执行者不知道做到哪算完，就只能猜。UAT 类照抄被验 turn 的完成条件，不另立。
- **不给倾向性结论**——否则产出向写用户消息的人的结论收敛，等于白问。
- **内容判据先冻结、密封，⑤ 验收才公开**；没发出去的判据只能用于排序或加分，**不得用于扣分或判不通过**（见 [多方竞争协议](competition.md)「立判据的人怎么约束自己」）。密封时记下 SHA-256，公开时可验它没被改过。
- **出题的人与答题的 agent 分开**。agent 不改用户消息，发现用户消息有问题时停下来问。
- 哪些动作需要人批准，见 [人的批准点](approvals.md)；写用户消息的人要把它们写进用户消息。人这一侧的其余义务见同一份的「人这一侧的义务」。

## 交给 agent 的活，八条都成立

不论哪一类、不论单路还是并行、不论人还是 AI：

1. **不用计划覆盖原始需求**；
2. 只在范围、工具、数据、预算和副作用边界内行动；用户消息没说清边界、而越界会有影响时，先问；
3. **区分事实、推断、假设、缺失和未运行验证的结论**，不可混写；
4. 对可中断的工作持久化检查点；
5. 无法满足完成条件时请求输入或**明确失败**，不交半成品；
6. 在**最终固定版本**上运行与风险相称的验证；
7. 报告盲区、副作用和残余风险；
8. 未经授权不推送、合并、发布、删除远端资产或扩大外部影响。

第 3 条是 [UAT 怎么验](uat/verify-rules.md) 证据采信的前提：分不清事实与推断，采信分级就无从谈起。

## turn 的固定字段

`user-message.md` 开头用下面几项（YAML 头），发出时写好，随用户消息冻结：

| 字段 | 写什么 |
| --- | --- |
| `executor` | 派给谁；**还没派出去写 `unassigned`** |
| `verifies` | 验收的是哪个 turn，写「thread 号/turn 号」，如 `0004/0001`；只有 UAT 类有，其余三类写 `无` |

种类不进 YAML 头：它的唯一真源是 thread 目录名（见 [命名与编号](naming.md)），正文里那句「交回什么」把它当面告诉模型。

`turn.md` 交回时写，写完冻结；**没有 `turn.md` 就是还没交回**：

| 字段 | 写什么 |
| --- | --- |
| `status` | `completed`、`interrupted` 或 `failed` |
| `branch` | 交回物所在的**分支名**；就在当前分支上做的写 `无`。⚠ 旧名是 `worktree`，只在已冻结的原件里还能见到——它装的一直是分支名，路径/worktree/branch/commit 是四种不同对象 |
| `commit` | 交回物所在的提交；同上 |

**字段集固定，不因种类增减行**：用不上的写 `无`，不删行、不留空。这样任何一份回执都长一个样，人扫一眼、机器取一个键都不用先判断种类。
建 turn 时直接复制两个模板文件：[`user-message.md`](user-message.md) 与 [`turn.md`](turn.md)，把尖括号里的说明换成内容。

**`branch` 与 `commit` 什么时候有值**：IMP、UAT 两类必有——产物本来就在另一条分支上。
PRD、SDD 两类看这一问是在哪里做的：

- **就在当前分支上做**：两个都写 `无`。答就是同一个 turn 里的 `response.md`，它在哪个提交、什么时候交的，git 都记着。
- **另开了分支**：两个都填。一问一答也可能值得单开一条分支——讨论会连带改好几份文档、要和主线隔开、或者同一问并行发给几家各走各的。
  这时 `response.md` 只存在于那条分支上，**从主线 `git log` 找不到它**，不写下来这一问的答就丢了。

**回执只有这三个键，没有正文**：交回物在哪，`branch` 与 `commit` 已经说了；PRD、SDD 两类的答就在同一个 turn 的 `response.md` 里。
只有 `interrupted` 或 `failed` 才写一句为什么停的。不知道的值写 `unknown`，不得空着。

**验收的结论不进字段**：它的真源是 `test/` 里的结果与那条提交的正文。回执只说这次验收做完没有（`status`）、产物在哪（`branch`、`commit`）。

## 定稿

PRD 类的 response 定稿成 `PRD/`，SDD 类的定稿成 `SDD/`；IMP 类的「定稿」是实现本身，走下面的 worktree。

**定稿是人对答的采纳，怎么做见 [定稿](finalize.md)**——它与对动作的**批准**、对交回物的**验收**是三件事，不能互相代替。

## IMP 与 UAT 的 worktree

- 执行者在自己的 git worktree 里实现；验收者在 worktree 的 `test/` 里写测试。
- 交回时 `turn.md` 记分支与提交；产物不拷进任务目录。
- 审核者在被审的 worktree 之上再开一个审核 worktree，逐层向上，最后合并到 master。层数、谁审谁、谁清理见上面那张图与它下面两条。
- **worktree 完成后才清理**；清理前分支或标签必须留下——工作区可以删，提交不能跟着消失。
- 审核发现问题：**不在审核 worktree 里替对方写**，开新 turn 让它重做；审核 worktree 只用来核对、跑测试、做最小修补。
- **人负责清理**：工作完成、合并进 master 之后再清 worktree；清理前确认分支或标签还在。

## 返工怎么做

- **打回就是开新的 turn**：理由写进新 turn 的 `user-message.md`——用户消息里的哪一条要求（或本规范的哪一条）没满足、证据在哪、要求改什么；用户消息本身没说清、无法判定的，写「不可判」并交给人，不自己发明标准。返工派回出问题的那一类——设计有问题回设计，实现有问题回实现。
- 标准或判断变了，写进新 turn 的 `user-message.md`，并写清改判三要素：触发、原判断错在哪、新判断（见 [人的批准点「改判」](approvals.md)）。
- **什么时候不再重做，由驱动方定**：现在驱动方是人，人自己判断——改用户消息、改判据、换做法还是换执行者。本规范不定次数。
- 某项交付物需要多个 agent 各交一份再比较时，按 [多方竞争协议](competition.md) 进行；各家的交回各占一个 turn，竞争内部的回退不计入本任务的返工次数，竞争的最终结果被打回才计入。
