# 任务类别的判定与路由

> 控制面怎么实现见 [控制面与执行体](../submodules/0001-backend/SDD/architecture/blocks.md)。

**任务类别的判定**：分三层，每一层都在它信息最全的地方判断；后端不为此调用模型。

| 层 | 在哪 | 依据 | 结论怎么算数 |
| --- | --- | --- | --- |
| 用户所选 | 桌面应用 | 用户指定的类别，或产品入口、模板自带的类别 | 直接作为 `profile_id` 提交 |
| 本机预填 | 本地 runtime | 本机文件与任务文本的确定性规则：扩展名、表头、首页关键词、历史选择 | 必须经用户确认或改正才提交；未经确认的预填不算数 |
| 后端兜底 | 后端 | 只有任务文本，按版本化规则与清单匹配 | 命中则入账；判不出来创建 Interaction 交用户选 |

- **算在 runtime、确认在桌面应用**：读本机文件的是 runtime——三方里只有它碰得到用户资料。
  桌面应用经通道 ③ 取到类别，摆在提交按钮旁让用户确认或改正，它自己不开用户的文件；
- 本机预填只在用户电脑上读文件；**文件内容、文件名以及由它们派生的任何特征都不上传**，上报的只有类别；
- 判不出来时进入 `WAITING(INPUT)`，**不得默认判为通用，也不得回退到能力更大的 Profile**；界面上以一行候选呈现，不做成表单；
- 类别决定怎么做，**不授予任何数据权限**（F-GUARD-04）；
- 判定器的实现可替换（规则、检索或模型），替换不改交回的结构与入账字段；换成模型时先要有标注集与评测（D11）。
- **runtime 没在跑或设备离线时这一层不可用**，直接落到后端兜底，后端此时只按任务文本的规则判断；
- runtime 用单次调用客户端直连用户所选厂商，不借用 Codex。

## 判成通用之后

**通用不是兜底，是入口。**用户提什么问题我们选不了；能做的是：通用问题照样给一个像样的回答，
同时**设法把他引到我们的专业领域**。所以判成通用**不等于这一问就此走完**。

| 在哪一步 | 谁做 | 做什么 |
| --- | --- | --- |
| 受理 | `0002-router` | 判成通用即照常建单派发，**不因为是通用就降低标准** |
| 执行之后 | `0003-orchestrator` | **领域识别**：拿任务文本与执行产出，判这一问最接近哪个专业领域（`F-DISPATCH-06`） |
| 交付 | `0007-delivery` | 把识别结论随结果一起下发（`F-DELIVERY-12`） |
| 呈现 | 桌面应用 | 结果旁给出专业路径与**预估费用**，用户点了才重跑（`F-REVIEW-07`） |

⚠ **三条边界**：

1. **识别在后端跑，不注入给执行体**——它用的是我们的判据，注入出去就等于把判据送人；
2. **只用自有数据的「目录」，不用内容**：可以说「这一问涉及 X 的产业链数据和近 8 个季度财报，
   我们有」，**不得把数据片段下发到通用路径**——直发是整包暴露的形态，把自有数据放上去，
   等于用最贵的料做引流；
3. **不得自动升级**。费用是用户出的，升到专业模式必须用户明确同意——
   与 `D10b`「升到竞争形态要用户明确同意」是同一条线。

⚠ **不能反着用**：上面「判不出来**不得默认判为通用**」那条不因引导而松动。
引导是「判成通用之后再给一条路」，不是「把通用硬判成专业以便引流」。

**识别结论一律入账。**它是 `D11`（受理判定何时改用模型）与 `D12`（workflow 清单与「专业」的边界）
一直缺的那批标注——「交用户选」的样本量太小，通用路径的量大得多。
