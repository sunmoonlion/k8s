# BRD：业务需求（Business Requirements Document）

BRD 阶段用来**把要做什么讨论清楚**。还不知道要什么、或只有一句模糊的想法时，先走这一段：人问、AI 答、人改，几个 turn 之后定稿成 `PRD/`。
已经清楚要做什么的任务可以跳过这一段，直接从 PRD 起。

两个 YAML 头照抄 [模板](../templates.md)；正文没有模板，这一段的问要说清什么见下。

## 这一段的用户消息

**这一段的问没有模板，也没有必填栏**。讨论就是一问一答往前推：人说一句，agent 答，不对就在下一个 turn 里说清楚——修正本身就是下一问。
问怎么写按 [任务的生命周期](../lifecycle.md)「用户消息写多严」，一段话说清就够；发出去的原样存进 `user-message.md`，发出即冻结。
**不写验收标准，也不复述下面两节**：答要覆盖什么、怎么写，判据就是本规则，早已冻结；把提纲抄进这一问，等于替模型把骨架列好了。
交回一份 `response.md`，不改代码。多家同时答同一问时按 [多方竞争协议](../detailed-rules/protocol/competition-rules.md)，那种场合问要一次写全。

## 这一段在问什么

| 问什么 | 说明 |
| --- | --- |
| 要解决谁的什么问题 | 用户是谁、现在怎么做、卡在哪 |
| 做成什么样算解决 | 可判断的结果，不是「更好用」 |
| 边界 | 这次做什么、不做什么、以后再说什么 |
| 约束 | 资质、合规、平台、成本、时间上不能碰的 |
| 取舍 | 有哪几条路、各自代价、为什么选这条 |
| 未知 | 现在答不了、需要去查或去试的 |

## response 写什么

一个 turn 的 `response.md` 就是这一问的回答：可以是分析、可以是方案对比、可以是把问题重新问清楚。要求：

- **区分事实、推断、假设与未知**，不把推断写成事实；
- 给出取舍的**理由与代价**，不只给结论；
- 涉及外部规则（资质、合规、平台限制）时标明依据与出处，查不到就写「未核实」；
- 不替人做决定：把选项和后果摆清楚，决定由人下。

## 定稿成 `PRD/`

人读完 response，整理进 `PRD/`：

| 位置 | 写什么 |
| --- | --- |
| `PRD/architecture/` | 模块怎么分、模块之间的关系与边界；为什么这样分 |
| `PRD/modules/<四位号>-<短名>/` | 每个模块要满足什么：它的职责、输入输出、验收 |

定稿时写明以哪个 turn 为底、改了什么。定稿即批准，见 [人的批准点](../detailed-rules/approvals.md)。

讨论过程留在各 turn 里，不必搬进 `PRD/`；`PRD/` 只写结论。
