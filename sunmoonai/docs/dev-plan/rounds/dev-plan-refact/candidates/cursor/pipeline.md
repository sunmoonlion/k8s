# 规范开发流程：一条开发变更从提出到上线

> **①a** ｜ 身份：worktree 目录名 `cursor`（`~/worktrees/cursor/k8s`）
> 产品名、模型名、界面上的称呼一律不是证据。
>
> 本文件回答：一条需求从人嘴里出来，到代码上线，经过哪些阶段、哪些门、
> 每阶段产出什么、凭什么算过关。文档类型全部从这些阶段推导，不另立一套分类。
>
> `sha256` 见提交信息与文末。

---

## 0. 前提：人只提需求、拍板、验收

本项目的开发工作全部由 AI 助手承担。人做且只做三件事：

| 人做的 | 不是人做的 |
| --- | --- |
| **提出**：用原话说要什么 | 调研、拆任务、写设计、写代码、跑测试、写文档 |
| **拍板**：不可逆的方向、取舍、授权 | 在方案之间「先写着看」 |
| **验收**：看产物、说通过或不通过 | 声称「已经满足 AT-07」却没有机器能反驳 |

这个前提改变的不是速度，是**失败的形状**：AI 会流畅地编造合规，语气与真正合规无异；
每次会话冷启动，写在文档里但没有自动载体的规矩约等于不存在。
因此本流程的硬规则是：

1. **交卷 = 可达 commit**。工作区文件没有作者、没有 digest，不算产物。
2. **状态从产物反推，不从声明读取。**「我做完了」不是过关条件。
3. **凡能落成测试、钩子或命令的纪律，必须落成。**落不成的老实标 ⚠，不得混进同一张「已保证」清单。
4. **人的三件事也要留下产物。**提出要有可定位的原话；拍板要有可检索的决定；验收要有落盘的通过/不通过——不能只存在于窗口滚动历史里。

下文的阶段、门、文档类型都在这个前提下成立。默认「人写代码、人记纪律」的实践，有一条用一条的理由，不默认沿用。

## 1. 先看这一条：一条变更怎么走完

开发的基本单位不是「一轮文档」、也不是「一个 sprint」，是一次 **Change**：
人提出一个目标，AI 把它做成可验收的产物，人说过还是不过。

```text
人提出原话
    │
    ▼
G1 开工门  ──── 原话可定位、完成契约可勾、方向不冲突、
    │            该拍的板已拍、本增量条目齐全、硬约束已对照
    ▼
AI 实施（改代码/文档，落到可达 commit）
    │
    ▼
机器先验证（测试、doc-gate、本变更声明的机械条）
    │
    ▼
G2 完工门  ──── 机械条绿、独立验收通过、状态游标已更新、
                该发布的已发布（无悬空 gitlink）
    │
    ▼
人验收 / 主线生效
```

并行评优轮（`protocol/round-protocol.md` 的 T2 七环节）是这个 Change 在
「多家隔离出稿、有人裁决」时的**加厚形态**，不是另一套生命周期。
不走轮次的工作走同一条 Change，只是跳过隔离提案和互评——跳过必须显式，默认值属于省事方向，省事须人确认。

**产品用户的 Task**（前端提交、后端受理、Agent 执行、结果返回）是我们正在建设的**产品**，
由产品合同约束。它不是本流程的阶段。本流程管的是：**我们怎样改代码去实现那份合同。**

## 2. 阶段

每个阶段写三件事：产出什么、存在哪、凭什么算过关。缺第三件的不是阶段，只是一段时间。

「常驻面」不是阶段，是每条 Change 都踩着走的操作系统。先写它，再写 Change 的时间顺序。

### 2.0 常驻面：共事的操作系统

| | 内容 |
| --- | --- |
| **产出** | 三份始终生效的规定：硬约束、协作协议、操作手册（类型从本面推导，见 §4） |
| **存在哪** | `constraints.md`、`protocol/`、`agent-dev-guide.md`（操作手册的现行载体；内部混了别的类型，拆法见 ①b） |
| **过关** | 提交文档时 `doc-gate.py` 绿；标了测试载体的约束随 pytest 跑；没有载体的条目保持 ⚠，不得改口成「已保证」 |

常驻面没有「做完」。它被改，本身就是一次 Change，走下面的门——而且改协议、改内核合同，默认升到最重档。

### 2.1 提出

| | 内容 |
| --- | --- |
| **产出** | 人的原话。可以是 `working/request-baseline/` 里的一条、窗口里随后被钉进工单的一段、或任务书里「所有者原话」引用 |
| **存在哪** | 原始请求档案，或工单里单独标明「原话」的字段。⚠ **不得只写在 AI 转述的计划里** |
| **过关** | 原话可定位（路径 + commit，或工单里的引用）。计划可以解释原话，不能覆盖原话 |

人在这一阶段的动作就是提出。AI 可以帮着整理，整理稿不是原话。

### 2.2 立约

| | 内容 |
| --- | --- |
| **产出** | 本 Change 的完成契约：做完之后什么变了、怎么验收、失败怎么办。若本 Change 改的是产品对用户的保证，还要产出对产品合同的修订草案 |
| **存在哪** | 单次 Change：工单 / 任务条目的「目标、验收」栏。产品级保证：`working/request-lifecycle.md` |
| **过关** | 完成条件可以一条条勾，不能是「完善 X」。涉及产品编号（`F-*` / `AT-*` / `I1`–`I15`）时，契约必须点到那些编号——今天测试还不认领这些编号（⚠，见 ①b 对 readiness 缺口的安置），所以这一条目前靠纪律，目标是落成测试 |

立约把「想要」变成「可证伪」。不可证伪的规则，AI 会 100% 声称满足。

### 2.3 定向

| | 内容 |
| --- | --- |
| **产出** | 这件事落在路线图的哪一段、是否冲击已冻结的方向。多数 Change **产出是「不改定向」**，也要能指到被遵守的那几句 |
| **存在哪** | `development-plan.md` |
| **过关** | 与已冻结方向不冲突。冲突则本阶段不结束，转入决策 |

定向回答「要建什么、为什么这么建」，不回答「现在做到哪」（那是状态）、「这次改哪几个文件」（那是增量设计）。

### 2.4 决策

| | 内容 |
| --- | --- |
| **产出** | 一条可检索的决定：选了什么、没选什么、凭什么、谁拍的板。完整审议过程可以很长，决定本身必须能单独被找到 |
| **存在哪** | 决定记录（类型 ADR）。今天的载体是 `rounds/<id>/rulings.md`；检索问题见 §10 |
| **过关** | 决定有全局 ID、有作者、有「有效/被取代」状态。未记录的裁定无效 |

不是每个 Change 都经过本阶段。无分歧、可逆、不碰权威层的，可以不决策。
「可以不」属于省事方向，须在工单里显式跳过，不能因为没写就当成已经决策。

### 2.5 本增量设计

| | 内容 |
| --- | --- |
| **产出** | 这一次具体怎么改：动哪些仓、接口怎么变、测什么、怎么回滚。这就是所有者说的「当前在做的 ≈ TLD」 |
| **存在哪** | 任务计划里的一条，或轮次的 `task.md` / 工单正文。运行时「这次怎么搭」若尚未写入任务条目，会暂时寄居在操作手册里——那是现状，不是归属（见 ①b） |
| **过关** | `implementation-plan.md` 规定的任务栏齐全：类型、仓库、前置、目标、实施、测试、验收、回滚、状态。缺栏视为未定义，不开工 |

### 2.6 实施

| | 内容 |
| --- | --- |
| **产出** | 代码和文档的可达 commit。并行时每家一条分支 |
| **存在哪** | git。工作区不是存在哪 |
| **过关** | `git rev-parse HEAD` 能指到含该产物的 commit；作者归属清楚 |

### 2.7 验证

| | 内容 |
| --- | --- |
| **产出** | 可复跑证据：测试输出、门禁输出、本 Change 自己声明的机械条结果 |
| **存在哪** | 证据类文档。走轮次的放 `rounds/<id>/`；不走轮次的见 §9；产品仓任务按实施计划写在各仓 `docs/evidence/<task-id>/` |
| **过关** | 机械条全绿。判不了的显式标 ⚠ / 🔶人判，**不许默默不查、也不许把空集合当成全部完成** |

验证在验收前面。人验收的是已经过机器的东西，不是 AI 的自述。

### 2.8 验收

| | 内容 |
| --- | --- |
| **产出** | 通过或不通过，落盘。通过意味着：在声明的范围内，独立于产出方的一方认为可以进入主线 |
| **存在哪** | 轮次的验收记录 / 人确认列；不走轮次则在证据目录里由人写下通过 |
| **过关** | 验收方不是产出方（能分则分）。人的确认是全流程唯一不可由命令判定的环节——所以它必须留下产物，且内容对不对仍是人的事 |

### 2.9 发布与交接

| | 内容 |
| --- | --- |
| **产出** | 主线（或约定的发布面）上的 commit；状态游标更新 |
| **存在哪** | 主线 git；`handoff.md` 只写状态 |
| **过关** | 父仓无悬空 gitlink（约束 T4）；跨仓交付带「仓 + 提交号」（T5）；`handoff.md` 的游标与真实进度一致 |

## 3. 门：什么叫「可以开工了」、什么叫「做完了」

阶段内部还有进出条件。整条 Change 对外只暴露两道总门。把它们分开，是因为本仓多数混乱来自把「正在写」当成「已经可以合」。

### 3.1 G1 开工门（可以开工了）

**必须同时成立：**

| # | 条件 | 谁判 |
| --- | --- | --- |
| G1.1 | 原话可定位 | 纪律（人确认「这就是我要的」）；路径存在可由机器查 |
| G1.2 | 完成契约可勾（立约过关） | 纪律；栏是否空可以由机器查（任务条目缺栏 = 未定义） |
| G1.3 | 定向不冲突，或冲突已转入决策并已有决定 | 纪律；「有无 rulings 记录」可机器查 |
| G1.4 | 本增量设计栏齐全 | 纪律为主；将来可对必填栏做机械检查 |
| G1.5 | 硬约束对照表：相关组已列出结论 | 纪律（`constraints.md` 怎么用）；标了测试载体的那些随 pytest |
| G1.6 | 工作区已供给、基线已钉 | 机器：分支、worktree、`HEAD` |

**T2 并行轮**在 G1 上额外要求：参与方隔离、题目冻结、各家尚未读其他候选。那是协作协议的门，不是产品门。

### 3.2 G2 完工门（做完了）

**必须同时成立：**

| # | 条件 | 谁判 |
| --- | --- | --- |
| G2.1 | 产物在可达 commit 上 | 机器：`git cat-file` / `ls-tree` |
| G2.2 | 本 Change 声明的机械验证全绿 | 机器：pytest、`doc-gate.py --all`、轮次 `round-status.py --verify` 能判的部分 |
| G2.3 | 判不了的项已显式标出，且人已处理 | 混：机器拒绝把它们算进「通过」；人处理内容 |
| G2.4 | 独立验收通过 | 人（或指定验收方 + 人确认） |
| G2.5 | 状态游标已更新 | 纪律；将来可对「handoff 与 round 状态」做弱检查 |
| G2.6 | 若宣称发布：T4/T5 满足 | T4 有同步脚本当场报错；T5 靠纪律 |

**「做完了」不是「AI 说做完了」。**也不是「分支上有文件」。

### 3.3 两道门与档位

T0 / T1 / T2 不是三套流程，是同一条 Change 的参数：隔离几家、要不要互评、裁决多重。
`protocol/round-protocol.md` 已经用「一套流程、参数覆盖三种形态」写过这件事。
本文件承认它，并把它嵌进 G1/G2：档位改变的是决策与验收的厚度，不改变提出→立约→实施→验证→验收的顺序。

升档随意，降档要理由——这条不对称保留，因为默认值属于省事方向。

## 4. 文档类型：从阶段推导，不另立分类

每一类只回答一个问题：**缺了它，上面哪个阶段会没有过关物？**
多一类必须说明为什么不能并进相邻类。

| 类型 | 从哪推导 | 缺了它哪个阶段没过关物 | 为什么不并进邻居 |
| --- | --- | --- | --- |
| **原始请求** Request | 提出 | 提出：没有可定位的原话 | 并进产品合同会让人的原话被规格覆盖，违反「计划不得覆盖原话」 |
| **产品合同** Contract（≈ PRD） | 立约（产品级） | 立约：产品保证不可证伪 | 并进方向会把「用户必须得到什么」和「我们下阶段建什么」焊在一起，两拨读者互相打扰 |
| **方向** Direction | 定向 | 定向：无法判断冲突 | 并进任务计划会让路线图被进度改写 |
| **决定记录** Decision（≈ ADR） | 决策 | 决策：未记录的裁定无效 | 并进轮次档案会让决定不可检索——今天已经发生（三份 `rulings.md`，`R1` 撞车） |
| **增量设计** TLD | 本增量设计 | 本增量设计：不知道这次改什么 | 并进操作手册会把「这一次」写进「每一次」，手册膨胀且过期——今天已经发生 |
| **任务计划** Work Plan | 本增量设计的队列面 | 本增量设计：没有顺序、依赖、验收栏 | 与 TLD 分开：队列会变，单条设计在开工后应冻结 |
| **硬约束** Discipline | 常驻面 | 常驻面：动代码前无「不进入讨论」的规则 | 并进产品合同会把平台级禁令（数据、身份、发布）和用户 Task 合同焊在一起；编号还会撞车（两边都有 `I1`–`I8`） |
| **协作协议** Protocol | 常驻面 + 决策的加厚形态 | 决策/验收：不知道多家怎么一起干活 | ⚠ **不并进任务计划**。任务计划说「建什么、什么顺序」；协议说「怎么做决定、产物算不算数」。所有者起点把 protocol 标成「实施计划的一部分」，本候选在此提出替代落点，举证见 §7.2 |
| **操作手册** Operator | 常驻面 × AI 前提 | 实施：冷启动的 AI 不知道一次 Change 怎么执行 | 通行名里没有这一类。人写代码的团队靠口耳相传和记忆；AI 每次冷启动，必须有一份「照做」的入口。它不是 PRD，不是 ADR，不是 TLD |
| **证据** Evidence | 验证 | 验证：没有可复跑记录 | 并进决定记录会把「审议过程」和「机械输出」混成不可检索的一团；并进状态会把过期证据当成当前进度 |
| **状态** Status | 发布与交接 | 发布与交接：下一任不知道卡在哪 | 并进方向或任务计划，读计划的被状态打断，查进度的要翻论证——`README.md` 已经把这个后果写死了 |
| **索引** Index | 所有阶段的入口 | 无。它不承载规范 | 只有指路义务。⚠ 不得以索引充当架构（任务书 B10）；本类存在是为了承认 `README.md` 的实际职责，并限制它不准长成规范 |

**没有单独的「领域模型」类型。**产品合同内部可以有对象、状态机、不变量、功能项、验收矩阵——那是同一份合同的条款种类，不是另一份要走完的流程文件。拆不拆物理文件是 ①b 的事，受锚点保全约束；类型上它们同属产品合同。

**没有单独的「轮次档案」类型。**`rounds/` 是决定记录和证据的**载体**，里面同时装决定、审议、机械结果、通知。类型按内容走，不按目录走。目录可以继续按轮次切，因为一轮是一次（或一组）Change 的加厚形态。

## 5. 每类文档的生命周期

| 类型 | 谁能改 | 怎么改 | 能否被取代 | 旧版怎么办 |
| --- | --- | --- | --- | --- |
| 原始请求 | 人（principal）。AI 不得改原话 | 只追加澄清，不改已钉的句子 | 不被取代；后续合同引用它 | 留在 `working/request-baseline/`（位置已由所有者裁定，不动） |
| 产品合同 | 经 Change 修订；修订本身走 G1/G2，默认最重档 | 改条款必须带影响、迁移、验收 | 条款可修订，合同身份不换文件乱跳 | 修订纪律在合同自己的 §12；历史版本用 git。物理路径保持稳定（锚点，见 ①b B2） |
| 方向 | 经决策后改 | 改「为什么」必须留下决定 | 可以被新方向取代 | 被取代的句子留在 git；`handoff` 的「不能倒退」列出仍有效的冻结项 |
| 决定记录 | **不得修改已发布的决定正文** | 只能追加「被取代 / 被澄清」 | **只被取代，不被修改** | 旧决定留在原轮次目录；索引改指向。编号撞车用全局 ID 消解，不靠改历史文件 |
| 增量设计 | 开工前可改；**G1 之后冻结** | 冻结后要改范围 = 新 Change 或显式解冻（人拍板） | 可被新增量设计取代 | 旧设计随该 Change 的 commit 留存 |
| 任务计划 | 队列可以改（增删条、改状态） | 改「怎么算做完」视同改增量设计，须重新过 G1 | 条目状态走到 ACCEPTED 后，内容冻结 | 状态变更写在条目上，不另起一份历史文件 |
| 硬约束 | 经 Change；新增规则易、放松规则难（方向不对称） | 能落测试的必须同期改测试 | 可被更严的规则取代；放松须人确认 | 旧规则 git 可溯；测试载体是真正的强制点 |
| 协作协议 | 经 Change，默认 T2 | 规范与实现（脚本）必须一起改 | 版本取代 | 旧协议随轮次归档；进行中的轮次仍按其开工时冻结的协议走 |
| 操作手册 | AI 可在吸收轮更新；**不得在手册里改产品合同或硬约束的结论** | 操作步骤可改；改了要能指到仍有效的合同/约束 | 活文档，整本可被新版取代 | 历史稿进 `archive/`；落点表证明没丢，不证明放对（任务书已有实测） |
| 证据 | 产出方追加，不得改已采信的记录 | 只追加 | 不被改写；被推翻时另写一条并指向旧条 | 随 Change 目录留存 |
| 状态 | 接手的人或完成发布的 AI | **只写状态，不写论证、不写步骤** | 整页是游标，本来就该被新状态覆盖 | 旧状态在 git。需要追责时查 commit，不查「现在这页还记不记得」 |
| 索引 | 随类型增减改指针 | 不写规范语句 | 随时更新 | 无旧版问题 |

## 6. 判据归属：机器执行还是靠纪律

混在一张清单里是最常见的自欺。这里按门拆开。

### 6.1 机器已经能判的

| 判据 | 载体 |
| --- | --- |
| 文档链接、章节号、表格列数 | `doc-gate.py`（pre-commit，对照 git 索引） |
| 部分硬约束（迁移链、契约锁、配置硬校验、CSRF 等） | 各仓测试 / 启动期校验 |
| 轮次进行到哪、产物在不在 | `round-status.py`（只看 git 提交） |
| 父仓悬空 gitlink | 同步脚本在拉取侧报错 |
| 镜像 tag 是否 digest | 部署门禁正则 |
| 交卷是不是可达 commit | `git cat-file` / `ls-tree` |

### 6.2 今天靠纪律、目标是机器的

| 判据 | 现状 | 目标 |
| --- | --- | --- |
| 产品合同 47 个编号被实现认领 | 测试零命中编号（`inputs/readiness.md` 缺口二；⚠ 该文 2026-09-04 取证，本候选未重跑） | 每个 `AT-*` / `I*` 至少有一个能失败的测试 |
| 任务条目缺栏不开工 | 纯读表 | 缺栏即拒绝进入实施 |
| `handoff` 游标与 round 状态一致 | 纯人工 | 弱检查：进行中的轮次必须在游标里出现 |

### 6.3 只能靠纪律、且必须保持 ⚠ 的

| 判据 | 为什么机器判不了 |
| --- | --- |
| 「这就是人要的原话」 | 语义，不是路径 |
| 验收内容对不对 | 协议已写：机器只判确认有没有落盘 |
| 硬约束里标 ⚠ 自检的那些（约一半） | 静态看不出来；做成要人记得跑的脚本 = 仍是纪律，还假装不是 |
| 提案隔离是否在脑子里成立 | 读过别人的候选没有产物；无产物 ≠ 没开工 |
| 章节引用指向存在但语义错的节 | `doc-gate.py` 已自陈抓不到 |

**把 6.3 写进「已保证」等于没有门。**

通行名不加分也不扣分。本候选用通行名当别名，规则以类型表为准。

### 7.1 所有者 2026-09-07 映射：起点，不是逐字套用

| 所有者起点 | 本流程里的落点 | 异议？ |
| --- | --- | --- |
| `request-lifecycle` ≈ PRD | **采纳为产品合同（PRD 类）。**它自己的标题就叫「产品请求生命周期合同」，§0.1 的入门问题是产品要求过滤器。起草者说它焊了 PRD + 领域模型 + 规格——焊是真的，但焊的是**同一份合同的条款种类**，不是三个流程阶段。物理上先不拆（B2） | 不异议「它是 PRD 类」。异议「必须拆成三份文件才叫 PRD」 |

| `constraints` ≈ 开发纪律 | **采纳为硬约束。**`constraints.md` 标题即「开发必须遵守的规则」，按数据/契约/身份/拓扑/发布/智能体分组，并区分机器载体与 ⚠ 自检 | 无 |

### 7.2 为什么 protocol 不是实施计划的一部分

任务书允许对所有者映射提出异议，但必须在自己的结构里给替代落点。

**替代落点：**协作协议 = 常驻面的文档类型，物理上保持 `protocol/`（规范与实现必须一起改，这一点 `protocol/README.md` 已经说对了）。

**举证：**

1. `implementation-plan.md` 自己声明：「这里是任务本体：每件事怎么做、怎么算做完。」栏是类型/优先级、仓库、前置、目标、实施、测试、验收、回滚、状态。阶段一任务清单因 U1 未定而为空。
2. `protocol/round-protocol.md` 的 57 节是：档位、裁量权、七环节、产物路径、取件、环节判定、隔离、互评、裁决、异议、验收、停止超时、角色、清理。没有一条是「investment-app 下一个要建的适配器」。
3. 同一份 `README.md` 已经把「怎么共事」放在 `working/` / `protocol/`，把「接下来建什么」放在 `development-plan` / `implementation-plan`，并写明混写的后果。
4. 若把协议并进实施计划：改「① 提案必须隔离」要动任务清单文件；改「阶段一任务」要担心碰了七环节。这是产品合同已经犯过的「三种读者一份文件」，不该再犯一次。

起草者认为二者不同种类——本候选同意，并把它从「起草者主张」提升为流程结构里的正式落点。

### 7.3 自造名：操作手册

现有通行名装不下「给每次冷启动的 AI 的执行说明书」。PRD 是产品保证，ADR 是决定，TLD 是这一次怎么改，SDD 通常是系统设计说明书（更接近运行时结构，即 TLD 的一种）。
操作手册回答：你是执行者，接到一个 Change 之后先读哪、写哪、什么算交卷、人在什么点介入。
本仓已经有这份东西的活文档：`agent-dev-guide.md`。本轮要做的不是再起一个名字就算完成，而是承认它是从 AI 前提推导出来的**必要类型**，并停止往里面塞产品合同、决定收据和本次运行时设计。

## 9. Q8：不走轮次的工作，取证放哪

`rounds/` 装轮次产物，`working/` 装共事约定与原始请求，都不是「一次非轮次 Change 的证据袋」。这个位置今天空缺。

**本流程给出的槽：证据类型，路径按载体分，而不是新发明一种文档类型。**

| 工作形态 | 证据放哪 |
| --- | --- |
| 走轮次 | `rounds/<id>/`（已有） |
| 不走轮次、发生在本仓文档/脚本 | `working/traces/<change-id>/`（**新槽，本轮只命名不创建**；创建本身是一次 Change） |
| 产品仓任务 | 各仓 `docs/evidence/<task-id>/`（`implementation-plan.md` 交付规则已写） |

三者都是证据类型：只追加、可复跑、带日期。不走轮次**不是**可以不留证据。
R0 修脚本那次「由 opus 直接修，不走轮次」若再发一次，证据应进 `working/traces/`，而不是散落在聊天记录。
