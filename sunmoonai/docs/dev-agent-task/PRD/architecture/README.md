# 需求层：模块划分与关系

> 依据：[产品合同](../product-contract.md)。本文只写**要什么**，怎么做见 [SDD](../../SDD/architecture/README.md)。

## 目标与范围

把产品合同要求的东西做出来：用户在桌面应用里提交 Task，后端受理、路由、编排并验收，Agent 在用户电脑上执行，结果端到端加密后可靠取回。

- **包含**：合同 §5 到 §9 的功能与纪律，以及 §15 的验收；
- **不包含**：合同里标为后置的能力（私有部署、企业网关、团队协作、统一分发、Linux 与信创），以及附录 A 未定的决策事项；
- **不包含部分的归属**：后置能力在相应决策拍板后另建模块。

## 模块划分

| 模块 | 要满足什么 |
| --- | --- |
| [`0001-backend`](../modules/0001-backend/README.md) | 受理、路由、编排、派发、验收、持久化账与审计：合同 §6 到 §9 里归后端的那部分 |
| [`0002-frontend`](../modules/0002-frontend/README.md) | 用户界面：提交、进度与结果、审批与审查、本地配置；合同 §8.1、§7.3 与 §8.7 的客户端侧 |

⚠ 第一层是分两部分（前端、后端）还是三部分（客户端、本地 runtime、后端），合同附录 A 的 D1 未定。定了再改这里与 [`SDD/modules/`](../../SDD/modules/)：本地 runtime 的运行位置、信任域与发布方式都与后端不同，很可能要单列。

## 模块之间

- 客户端与后端之间只走合同 §2.2 的通道 ④：提交、查询、取消、Task 级审查、结果密文；
- 执行端与后端之间走通道 ①：派发、续约、事件、副作用意图与回执、推理请求；
- 客户端与执行端在同一台电脑上，走本机通道 ③；
- 谁对哪条要求负责，以合同 §12 的责任投影为准，本文不复制第二份。

## 共同约束

- [代码必须遵守的规则](../../SDD/constraints.md)；
- 合同 §1 的定位约束 `F-POS-01` 至 `F-POS-05`：自有数据只装事实、方法库只写方法、输出是研究底稿、系统不替用户下判断、留存定性证据；
- 合同 §9 的不变量 I1 至 I20。

## 未决

以合同附录 A 为准，本文不另立一份清单。影响模块划分的是 D1（第一层怎么分）与 D17（定位、备案与数据授权）。
