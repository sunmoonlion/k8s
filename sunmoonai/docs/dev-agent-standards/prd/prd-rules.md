# PRD：产品需求（Product Requirements Document）

`PRD/` 是 BRD 阶段的定稿目录，也是 PRD 阶段的输入：**要什么、做到什么算满足**，不写怎么实现。

```text
PRD/
├── architecture/             模块之间的结构与关系（入口 README.md）
└── modules/<四位号>-<短名>/  每个模块要满足什么
```

**模板**：[用户消息](user-message-template.md) · [回执](turn-template.md)。

## 这一段的用户消息

这一段由 discussion agent 答。这一问要写清：以哪一份 `PRD/` 定稿为底、要产出什么、范围三行、
可判定的验收标准、约束。交回的 `response.md` 要能定稿成 `SDD/`，所以它必须满足上面几节。
模板见 [用户消息](user-message-template.md)；写多严见 [任务的生命周期](../lifecycle.md)「用户消息写多严」。

## `architecture/` 写什么

| 部分 | 写什么 |
| --- | --- |
| 目标与范围 | 这个任务要达成什么；包含什么、不包含什么、不包含的归谁 |
| 模块划分 | 分成哪几个模块、各自承担什么、为什么这样分 |
| 模块之间 | 依赖、边界、谁向谁提供什么；跨模块的共同约束 |
| 约束 | 必须遵守的规则、不能动的东西、外部限制 |
| 未决 | 还没定的事，以及定不下来会影响什么 |

## `modules/<模块>/` 写什么

| 部分 | 写什么 |
| --- | --- |
| 职责 | 这个模块要满足什么，一句话说清 |
| 输入与输出 | 从谁拿什么、给谁什么 |
| 验收 | 可判定的条件，做完能一条条对着勾 |
| 约束 | 只对这个模块成立的限制 |

- 模块的号与短名在同一父目录内从 `0001` 起连续编号，并与 `SDD/modules/` 下的同名目录、实现时 worktree 里的模块目录**一一对应**。
- **以定稿为准**：模块要拆、要合、要改名，先改这里，再改设计与代码。

## 纪律

- **只写要什么，不写怎么做**：技术方案属于 SDD。
- **验收标准可判定**：写「响应时间小于 2 秒」，不写「响应要快」。
- **不给倾向性结论**：把要求写清楚，把方案留给设计。
- 改 `PRD/` 要写明改了什么、为什么；已据它派出去的任务按 [改判](../detailed-rules/approvals.md) 处理。
