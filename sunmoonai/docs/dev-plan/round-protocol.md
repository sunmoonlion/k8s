# 并行评优轮：流程

> 最后更新：2026-09-03
>
> **本文定义一轮「多家并行出稿 → 互评 → 裁决 → 验收 → 发布」怎么走。**
> 它是 [`agent-discipline.md`](agent-discipline.md) 模式 A 与模式 C 的合成落地：
> 那份讲**为什么**（隔离原则、评审要声明什么、吸收要留处置记录），本文讲**怎么做**
> （几个环节、谁产出什么、写在哪、什么时候冻结、什么时候清理）。
>
> 每一轮的**题目与角色分配**写在该轮自己的任务书里，不写进本文。本文只放不随轮次
> 变化的部分。
>
> 规则来自两轮实跑：2026-09-02 的生命周期文档重写（四候选选优 → 整合 → 异议 →
> 验收 → 发布）与 2026-09-03 的一次失败整合，失败原因见 §7。

## 1. 六个环节

```text
① 提案   N 家各自写候选，互不可见                     产物：候选
           ↓ 候选提交并冻结（SHA-256），此后不得再改
② 互评   N 家各自读全部候选，评优并写评审              产物：评审
           ↓
③ 裁决   裁决方依据 N 份候选 + N 份评审定基座，
         以基座吸收各家候选与评审的优点                 产物：裁决稿 + 处置记录
           ↓
④ 验收   验收方按任务书的验收标准逐条判定               产物：验收稿
           ↓
⑤ 确认   人读最终稿，确认或打回                        产物：确认
           ↓
⑥ 清理   删除各分支的本轮产物，然后写入共享最终路径      产物：最终稿
```

**只有 ⑥ 写共享最终路径。**①② 的产物留在各家 worktree，③ 的产物在裁决方的整合分支。
候选分支不合并回主线，所以全程不存在同名文件冲突。

## 2. 产物与落点

| 环节 | 谁 | 产物 | 落点 |
| --- | --- | --- | --- |
| ① | 各提案方 | 候选 | 自己 worktree 的**共享最终路径同名文件** |
| ② | 各提案方 | 评审 | 自己 worktree，文件名带作者后缀 |
| ③ | 裁决方 | 裁决稿 + 处置记录 | 裁决方 worktree 的整合分支 |
| ④ | 验收方 | 验收稿 | 验收方 worktree，文件名带作者后缀 |
| ⑥ | 裁决方 | 最终稿 | 主线的共享最终路径 |

**候选用与主线一致的路径和文件名**，好处有三：`git diff master` 一条命令看清每家改了
什么；路径本身标明作者，不靠文件名区分；枚举形状固定，不会漏。

**评审与验收稿必须带作者后缀**，因为它们可能被收进主线当过程记录，同名会撞。

## 3. ① 提案：隔离与冻结

**候选完成前不得读任何其他 worktree。**看到别人答案之后写的内容属于评审或改进，
不再是独立候选。隔离原则见 [`agent-discipline.md`](agent-discipline.md) §2。

候选写完即提交，**提交后不得再改**。冻结方式：把候选文件的 SHA-256 与所在 commit 写进
自己的评审文件。**裁决方按 hash 从提交取候选，不从工作区文件取**——工作区文件会变，
提交不会。

**枚举用固定路径形状，不要按文件名凭印象列。**2026-09-02 那轮在这里出过事故：四家里
三家用一个文件名、一家用了带后缀的另一个名字，评审方按精确文件名枚举，**漏掉一份候选，
整轮评分作废重做**。

## 4. ② 互评：评审文件写什么

冻结自己的候选之后，读其余各家的候选，写评审。四块，缺一块该评审不计入裁决：

**A. 自述**（关于你自己的候选）

- 改了基座哪些节、新增哪些节；
- 哪些断言未验证、标了 ⚠ 的有哪些；
- 与基座有分歧的地方；
- **放弃了哪些本可以写但故意没写的内容，以及理由**——这项能看出取舍是不是想过。

**B. 候选集冻结**

全部候选的 worktree 路径、行数、字节数、SHA-256、所在 commit。
**少一份，你的评分作废**（§3 的事故就是这么发生的）。

**C. 评优**

按任务书的验收标准逐条给比较依据，指出每份候选的强项与缺陷，给出
**你认为该选谁当基座及理由**。

- **利益冲突必须声明**：评优方同时是候选作者，这不是独立终审。给可复核的比较依据和
  固定 hash；裁决方可以推翻该结论，但必须指出具体标准与证据。
- **事实题用证据裁，不用票数裁。**多家说法一致但都没取证，输给一家带 `file:line` 的。

**D. 值得吸收的点**

不管你选谁当基座，逐条列出**其他候选里值得并进最终稿的具体主张**，每条写明出自谁、
在哪一节、为什么值得。

这一块是裁决阶段最有用的输入。**裁决方靠它避免只看整体印象、漏掉落选稿里的好东西**——
2026-09-03 那次失败整合正是这么丢掉了基座候选独有的锚点（§7）。

## 5. ③ 裁决：定基座与吸收

- **一条主张一个提交**，便于事后复核与回退；
- **从选定候选的 commit 取基座，不从任何人的工作区文件取**；
- 逐条处置，每条写明**接受 / 部分接受 / 拒绝**及理由，理由须能独立成立，
  不能只写「已处理」；部分接受要写清接受到哪、为什么止于此
  （[`agent-discipline.md`](agent-discipline.md) §5.3）；
- 处置记录与裁决稿一并交出。

## 6. ④ 验收 与 ⑤ 确认

**验收方由裁决方在裁决稿完成后指定**，规则：

1. **不得是裁决方**——整合方不能自验，这是分角色的全部意义；
2. **不得是基座作者**——验自己的稿子等于自检，基座作者在裁决稿里的存量最大；
3. 在剩下的家里，**优先指定主张被采纳最少的那家**——它对结果的既得利益最小，
   最可能按标准判而不是按立场判；
4. 都不可用时，由项目所有者验收。

**裁决稿完成后才指定**，避免提案期有人为当验收方而写。指定结果与理由写进处置记录，
**不得事后更换验收方**。

验收方**只能按冻结的标准判定，不得为通过而静默修改标准**。标准不通过时，先判断是产出
没达标还是标准本身过期——标准也会腐坏。

裁决方依验收稿修订后，**最终稿交人确认**。人确认前不得写入共享最终路径。

## 7. ⑥ 清理与发布

**顺序是：人确认 → 清理各分支产物 → 写入共享最终路径。**

清理清单：

| 对象 | 处置 |
| --- | --- |
| 各提案方 worktree 的候选 | 删除。内容在各自分支的提交里，git 历史可取 |
| 裁决方整合分支的裁决稿 | 删除或并入最终稿 |
| 各家评审、验收稿 | 删除；结论已进处置记录。需要长期保留的另行决定 |
| 处置记录 | 由人决定保留或压缩为指针 |

**先清理再写入**，理由是：候选与最终稿同名同路径，不先清理，各分支后续与主线同步时
会把候选态当成本地修改，产生本可避免的冲突。

清理后各分支重置到发布点。

## 8. 角色不分会怎样

2026-09-03 有一次整合失败，五条毛病全部源于角色不分，逐条记在这里当反例：

| 毛病 | 后果 |
| --- | --- |
| 整合方同时是参赛方 | 自己裁自己那份，无人复核 |
| 无互评轮 | 各家的独有发现没人指认，只能靠整合方一人扫描 |
| 无独立验收 | 下面三条本该被逮住，全部漏网 |
| 与既有权威文档大量重复 | 自编一套不变量与已定稿的编号并存，且遗漏若干条 |
| 弄丢基座的长处 | 基座候选独有的稳定 ID 锚点被抹成散文，全稿此类 ID 出现 0 次 |

**分角色的意义是**：裁决方不提案，所以整合可信；裁决方不验收，所以判定可信。
这两条缺一条，这一轮的产物就没有可信来源。

## 9. 通用纪律

- **产物只写自己的 worktree**，主线只读，任何人不得在提案期写主线；
- 候选绑定不可变 commit，并声明覆盖/未覆盖范围、验证原始输出、假设、盲区、缺陷
  与关键主张证据；
- 做不成的老实标 ⚠，不假装已完成；
- 未验证的结论标注清楚，不把推断写成事实；
- 评审同样是一种产出，同样要自陈盲区
  （[`agent-discipline.md`](agent-discipline.md) §5.2）。
