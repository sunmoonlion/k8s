# 公有云 Celery 架构完整分析

## 一、架构概述

### 1.1 架构目标

在公有云 Kubernetes 集群中部署 Celery 分布式任务处理系统，实现以下目标：

- **llmops-service**：提供 FastAPI Web API 服务，接收客户端请求并发送异步任务
- **celeryworker**：独立的 Worker 服务，执行异步任务
- **RabbitMQ**：消息代理（Broker），存储和分发任务消息
- **Redis**：结果后端（Result Backend），存储任务执行结果
- **代码共享**：通过 Init Container 机制实现代码同步，确保任务定义一致性

### 1.2 架构图

```
┌─────────────┐
│   客户端     │
└──────┬──────┘
       │ HTTP 请求
       ▼
┌─────────────────────────────────────┐
│      llmops-service (Pod)           │
│  ┌──────────────────────────────┐  │
│  │  FastAPI 应用                 │  │
│  │  - 接收 HTTP 请求              │  │
│  │  - 调用业务逻辑                │  │
│  │  - 发送 Celery 任务            │  │
│  └──────────────────────────────┘  │
│            │                         │
│            │ task.delay()            │
│            │ 或 send_task()          │
└────────────┼─────────────────────────┘
             │
             ▼
      ┌──────────────┐
      │   RabbitMQ    │  ← 消息代理（Broker）
      │  (llmops-queue)│
      └──────┬───────┘
             │
             │ 任务消息
             ▼
┌─────────────────────────────────────┐
│    celeryworker (Pod)                │
│  ┌──────────────────────────────┐  │
│  │  Init Container               │  │
│  │  - 从 llmops-service 镜像      │  │
│  │    提取代码到 emptyDir         │  │
│  └──────────────────────────────┘  │
│            │                         │
│  ┌─────────▼─────────────────────┐  │
│  │  Celery Worker Container       │  │
│  │  - 挂载提取的代码              │  │
│  │  - 从队列接收任务              │  │
│  │  - 执行任务代码                │  │
│  └──────────────────────────────┘  │
└────────────┼─────────────────────────┘
             │
             │ 任务结果
             ▼
      ┌──────────────┐
      │     Redis     │  ← 结果后端（Result Backend）
      └──────────────┘
```

### 1.3 组件说明

| 组件 | 作用 | 部署方式 |
|------|------|---------|
| **llmops-service** | Web API 服务，发送任务 | Kubernetes Deployment |
| **celeryworker** | 任务执行 Worker | Kubernetes Deployment（带 Init Container） |
| **RabbitMQ** | 消息代理，存储任务队列 | 独立服务（messaging-platform） |
| **Redis** | 结果存储 | 独立服务（data-platform） |
| **PostgreSQL** | 业务数据库 | 独立服务（data-platform） |

## 二、代码共享设计详解

### 2.1 为什么需要共享代码

#### 2.1.1 任务名称必须一致

任务名称是连接发送方（llmops-service）和接收方（celeryworker）的关键桥梁：

```
llmops-service（发送方）          celeryworker（接收方）
      │                                │
      │ 发送任务                        │ 接收任务
      │ task_name = "llmops.build_documents" │
      │                                │
      ▼                                ▼
  任务名称必须完全一致！
```

**示例代码**：

```python
# llmops-service 发送任务（app/services/document_service.py）
from app.worker.llmops_tasks import build_documents

# 方式一：直接调用任务函数
build_documents.delay(document_ids)

# 方式二：使用 send_task（不需要导入任务函数）
celery_app.send_task("llmops.build_documents", args=[document_ids])

# celeryworker 接收任务（app/worker/llmops_tasks.py）
@celery_app.task(acks_late=True, name="llmops.build_documents")
def build_documents(document_ids: list[str]) -> None:
    """任务定义和执行代码"""
    # 执行逻辑
    pass
```

**如果任务名称不一致**：
- 发送方：`celery_app.send_task("llmops.build_documents", ...)`
- 接收方：`@celery_app.task(name="other.name")` 
- **结果**：Worker 找不到任务，任务失败 ❌

#### 2.1.2 任务定义代码需要共享

**llmops-service 需要**：
- 任务名称（用于发送任务）
- 任务参数格式（确保参数正确）
- 任务函数引用（如果使用 `task.delay()` 方式）

**celeryworker 需要**：
- 任务名称（用于匹配任务）
- 任务执行代码（实际执行任务）
- 任务参数验证（确保参数格式正确）

**共享的内容**：
```python
# app/app/worker/llmops_tasks.py（必须共享）
@celery_app.task(acks_late=True, name="llmops.build_documents")
def build_documents(document_ids: list[str]) -> None:
    """任务定义和执行代码"""
    # 执行逻辑
    pass
```

#### 2.1.3 依赖代码也需要共享

任务执行需要依赖其他代码模块：

```
任务定义（worker/）
  ├─ celery_app 配置（core/celery_app.py）
  ├─ 服务层（services/）
  ├─ 数据库模型（models/）
  ├─ 数据库连接（db/）
  ├─ 数据模式（schemas/）
  └─ CRUD 操作（crud/）
```

**Init Container 提取的目录**（celeryworker.yaml 第 34 行）：
```bash
for dir in worker core services db models schemas crud; do
    cp -r "$SOURCE_DIR/$dir" "$TARGET_DIR/"
done
```

### 2.2 为什么使用 Init Container 而不是全部共享代码

#### 2.2.1 镜像大小对比

**方案 A：全部共享代码（不推荐）**

```dockerfile
# celeryworker Dockerfile
COPY ./app/ /app/  # 复制所有代码
```

**包含的内容**：
- ✅ 任务定义代码（需要）
- ✅ 服务层（需要）
- ✅ 数据库模型（需要）
- ❌ API 路由（不需要）
- ❌ FastAPI 中间件（不需要）
- ❌ HTTP 处理代码（不需要）
- ❌ Web 相关依赖（不需要）

**问题**：
- 镜像体积大（包含不需要的代码）
- 依赖多（FastAPI、gunicorn 等）
- 构建时间长

**方案 B：Init Container 提取（推荐）⭐**

```dockerfile
# celeryworker Dockerfile（轻量级）
FROM python:3.11
RUN pip install celery redis sqlalchemy psycopg2-binary ...
# 不包含应用代码
```

**Init Container 提取**（celeryworker.yaml 第 23-48 行）：
```bash
# 只提取需要的代码
SOURCE_DIR="/app/app"
TARGET_DIR="/shared/app"

for dir in worker core services db models schemas crud; do
    if [ -d "$SOURCE_DIR/$dir" ]; then
        cp -r "$SOURCE_DIR/$dir" "$TARGET_DIR/"
    fi
done
```

**优势**：
- ✅ 镜像体积小（只包含 Celery 和基础依赖）
- ✅ 依赖少（不需要 FastAPI、gunicorn 等）
- ✅ 构建快（基础设施镜像可以复用）

#### 2.2.2 代码分离对比

| 内容 | llmops-service 需要 | celeryworker 需要 | 是否共享 |
|------|-------------------|------------------|---------|
| **任务定义** | ✅ 需要（发送任务） | ✅ 需要（执行任务） | ✅ 共享 |
| **服务层** | ✅ 需要（业务逻辑） | ✅ 需要（任务执行） | ✅ 共享 |
| **数据库模型** | ✅ 需要（数据操作） | ✅ 需要（数据操作） | ✅ 共享 |
| **数据库连接** | ✅ 需要 | ✅ 需要 | ✅ 共享 |
| **API 路由** | ✅ 需要 | ❌ 不需要 | ❌ 不共享 |
| **FastAPI 中间件** | ✅ 需要 | ❌ 不需要 | ❌ 不共享 |
| **HTTP 处理** | ✅ 需要 | ❌ 不需要 | ❌ 不共享 |
| **Web 依赖** | ✅ 需要 | ❌ 不需要 | ❌ 不共享 |

#### 2.2.3 Init Container 的优势

**1. 镜像解耦**

```
llmops-service 镜像：
  ├─ 完整应用代码（app/app/）
  ├─ FastAPI 依赖
  └─ Web 服务依赖

celeryworker 镜像（基础设施）：
  ├─ Celery 依赖
  ├─ 数据库依赖（SQLAlchemy、psycopg2）
  ├─ Redis 依赖
  └─ 基础依赖（tenacity、pydantic）
  └─ 不包含应用代码（运行时提取）
```

**2. 代码同步**

```
Pod 启动
  ↓
Init Container（llmops-service 镜像）
  ↓ 提取最新代码
emptyDir 卷（/shared/app）
  ↓ 挂载代码
Celery Worker Container（/app/app）
  ↓ 使用最新代码
```

**优势**：
- Pod 重启时自动提取最新代码
- 确保代码版本一致
- 不需要重新构建 celeryworker 镜像

**3. 多应用支持**

同一个 celeryworker 基础设施镜像可以服务多个应用：

```
应用 A（llmops-service）
  ↓ Init Container 提取代码
  ↓
celeryworker（基础设施镜像）
  ↓ 处理应用 A 的任务

应用 B（其他服务）
  ↓ Init Container 提取代码
  ↓
celeryworker（同一个基础设施镜像）
  ↓ 处理应用 B 的任务
```

## 三、队列配置详解

### 3.1 配置层次

Celery 的队列配置涉及三个层次：

```
1. 任务路由配置（celery_app.py）
   ↓ 决定任务发送到哪个队列
   
2. Worker 监听配置（worker-start.sh）
   ↓ 决定 Worker 从哪个队列接收任务
   
3. 环境变量配置（Kubernetes YAML）
   ↓ 提供队列名称等配置
```

### 3.2 任务路由配置（发送方）

**文件位置**：`llmops-service/app/app/core/celery_app.py`

**完整代码**：
```python
import os
from celery import Celery

# 从环境变量读取 Broker URL
broker_url = os.getenv("CELERY_BROKER_URL", "amqp://guest@queue//")

# 从环境变量读取 Result Backend（可选）
result_backend = os.getenv("CELERY_RESULT_BACKEND")

# 创建 Celery 应用
if result_backend:
    celery_app = Celery("worker", broker=broker_url, backend=result_backend)
else:
    celery_app = Celery("worker", broker=broker_url)

# 从环境变量读取队列名称，如果没有则使用默认值
default_queue = os.getenv("CELERY_QUEUE", "llmops-queue")
celery_app.conf.task_routes = {"app.worker.*": default_queue}
```

**作用**：
- 当调用 `task.delay()` 或 `send_task()` 时，Celery 会根据 `task_routes` 决定任务发送到哪个队列
- `app.worker.*` 是任务名称模式，匹配所有 `app.worker` 模块下的任务
- 例如：`llmops.build_documents` 任务会被路由到 `llmops-queue`

**任务名称匹配规则**：
- `app.worker.*` 匹配所有以 `app.worker.` 开头的任务模块
- 实际任务名称如：`llmops.build_documents`、`llmops.delete_document` 等
- 这些任务定义在 `app/app/worker/llmops_tasks.py` 中，使用 `name="llmops.xxx"` 指定

**任务定义示例**：
```python
# app/app/worker/llmops_tasks.py
@celery_app.task(acks_late=True, name="llmops.build_documents")
def build_documents(document_ids: list[str]) -> None:
    """构建文档任务"""
    # 执行逻辑
    pass

@celery_app.task(acks_late=True, name="llmops.delete_document")
def delete_document(dataset_id: str, document_id: str) -> None:
    """删除文档任务"""
    # 执行逻辑
    pass
```

**任务名称**：`llmops.build_documents`（通过 `name` 参数指定）  
**模块路径**：`app.worker.llmops_tasks`（文件路径）  
**路由匹配**：`app.worker.*` 匹配 `app.worker.llmops_tasks` 模块

### 3.3 Worker 监听配置（接收方）

**文件位置**：`celeryworker/build/worker-start.sh`

**完整代码**：
```bash
#!/usr/bin/env bash
set -e

# Celery Worker 启动脚本
# 任务定义代码通过 Init Container 从应用镜像提取并挂载到 /app/app/

echo "=========================================="
echo "Celery Worker 启动中..."
echo "=========================================="

# 检查任务定义代码是否存在
if [ ! -d "/app/app/worker" ]; then
    echo "错误: 任务定义代码未找到 (/app/app/worker)"
    echo "请确保 Init Container 已成功提取代码"
    exit 1
fi

echo "✓ 任务定义代码已就绪"
echo "  位置: /app/app/worker"
echo ""

# 显示队列信息
QUEUE="${CELERY_QUEUE:-llmops-queue}"
echo "队列: $QUEUE"
echo ""

# 启动 Celery Worker
exec celery -A app.worker worker \
    -l info \
    -Q "$QUEUE" \
    -c "${CELERY_CONCURRENCY:-1}" \
    --hostname=worker@%h
```

**关键配置**：
- `QUEUE="${CELERY_QUEUE:-llmops-queue}"`：从环境变量读取队列名称，默认值为 `llmops-queue`
- `-Q "$QUEUE"`：指定 Worker 监听的队列名称
- Worker 只会处理发送到这个队列的任务
- 如果队列名称不匹配，任务不会被处理

### 3.4 环境变量配置

#### llmops-service 配置

**文件位置**：`llmops-service/deploy-llmops-service/secrets/llmops-service-config/llmops-service-config.yaml`

**配置内容**：
```yaml
data:
  # Celery 配置
  CELERY_BROKER_URL: "amqp://admin:admin123@rabbitmq-sunmoonai.messaging-platform-dev:5672//"
  CELERY_QUEUE: "llmops-queue"  # 队列名称
  CELERY_RESULT_BACKEND: "redis://redis-service.data-platform:6379"
```

**作用**：
- 提供 `CELERY_BROKER_URL`：RabbitMQ 连接地址
- 提供 `CELERY_QUEUE`：队列名称，`celery_app.py` 读取此变量配置任务路由
- 提供 `CELERY_RESULT_BACKEND`：Redis 连接地址，用于存储任务结果

#### celeryworker 配置

**文件位置**：`celeryworker/resources/celeryworker.yaml`

**配置内容**：
```yaml
env:
- name: CELERY_BROKER_URL
  value: "${CELERY_BROKER_URL:-amqp://admin:admin123@rabbitmq-sunmoonai.messaging-platform-dev:5672//}"
- name: CELERY_QUEUE
  value: "${CELERY_QUEUE:-llmops-queue}"  # 队列名称
- name: CELERY_CONCURRENCY
  value: "${CELERY_CONCURRENCY:-1}"
- name: CELERY_RESULT_BACKEND
  value: "${CELERY_RESULT_BACKEND:-redis://redis-service.data-platform:6379}"
```

**作用**：
- 提供 `CELERY_QUEUE` 环境变量给 celeryworker
- `worker-start.sh` 读取这个环境变量，配置 Worker 监听的队列
- 提供 `CELERY_CONCURRENCY`：Worker 并发数（默认 1）

### 3.5 队列配置的完整流程

#### 3.5.1 任务发送流程

```
1. llmops-service 代码中调用任务
   delete_document_task.delay(dataset_id, document_id)
   或
   celery_app.send_task("llmops.delete_document", args=[dataset_id, document_id])
   
2. Celery 查找任务路由配置
   celery_app.conf.task_routes = {"app.worker.*": "llmops-queue"}
   
3. 根据任务名称匹配路由规则
   任务名称：llmops.delete_document
   任务模块：app.worker.llmops_tasks
   匹配规则：app.worker.* ✓
   
4. 发送任务到指定队列
   RabbitMQ 队列：llmops-queue
   消息格式：Celery 协议（二进制）
```

#### 3.5.2 任务接收流程

```
1. celeryworker 启动
   celery -A app.worker worker -Q llmops-queue
   
2. Worker 连接到 RabbitMQ
   从 llmops-queue 队列接收消息
   
3. 解析任务消息
   任务名称：llmops.delete_document
   从挂载的代码中查找任务函数（app/app/worker/llmops_tasks.py）
   
4. 处理任务
   执行任务代码（使用共享的服务层、数据库等）
   
5. 返回结果
   结果存储到 Redis（CELERY_RESULT_BACKEND）
```

### 3.6 队列配置的关键点

#### 3.6.1 队列名称必须一致

**发送方（llmops-service）**：
- `celery_app.py` 中的 `task_routes` 配置的队列名称
- 从环境变量 `CELERY_QUEUE` 读取，默认值：`llmops-queue`

**接收方（celeryworker）**：
- `worker-start.sh` 中的 `-Q` 参数指定的队列名称
- 从环境变量 `CELERY_QUEUE` 读取，默认值：`llmops-queue`

**必须匹配**：两个地方的队列名称必须完全一致，否则任务不会被处理。

#### 3.6.2 任务路由规则详解

**当前配置**：
```python
celery_app.conf.task_routes = {"app.worker.*": default_queue}
```

**说明**：
- `app.worker.*` 是任务模块路径模式，不是任务名称模式
- 匹配所有 `app.worker` 模块下定义的任务
- 虽然任务名称是 `llmops.*`，但任务定义在 `app.worker` 模块中

**任务定义位置**：
- 文件：`app/app/worker/llmops_tasks.py`
- 模块路径：`app.worker.llmops_tasks`
- 任务名称：`llmops.build_documents`（通过 `name` 参数指定）

**路由匹配过程**：
1. 任务定义在 `app.worker.llmops_tasks` 模块
2. 路由规则 `app.worker.*` 匹配该模块
3. 任务被路由到 `llmops-queue` 队列

#### 3.6.3 多队列配置（扩展）

如果需要支持多个队列，可以这样配置：

**任务路由配置**：
```python
celery_app.conf.task_routes = {
    "app.worker.llmops_tasks.*": "llmops-queue",
    "app.worker.other_tasks.*": "other-queue",
}
```

**Worker 监听多个队列**：
```bash
# worker-start.sh
QUEUE="${CELERY_QUEUE:-llmops-queue,other-queue}"
exec celery -A app.worker worker \
    -Q "$QUEUE" \  # 监听多个队列，用逗号分隔
    -c "${CELERY_CONCURRENCY:-1}"
```


## 四、Init Container 机制详解

### 4.1 Init Container 工作原理

Init Container 是 Kubernetes 的一个特性，用于在主容器启动前执行初始化任务。

**celeryworker Pod 结构**：
```yaml
spec:
  initContainers:
  - name: extract-worker-code
    image: llmops-service:1.0.0  # 使用 llmops-service 镜像
    command: ['sh', '-c', '...']  # 提取代码脚本
    volumeMounts:
    - name: worker-code
      mountPath: /shared
  
  containers:
  - name: celeryworker
    image: celeryworker:latest  # 轻量级基础设施镜像
    volumeMounts:
    - name: worker-code
      mountPath: /app/app  # 挂载提取的代码
  
  volumes:
  - name: worker-code
    emptyDir: {}  # 临时存储卷
```

### 4.2 Init Container 提取代码流程

**详细步骤**（celeryworker.yaml 第 23-48 行）：

```bash
# 1. 设置源目录和目标目录
SOURCE_DIR="/app/app"      # llmops-service 镜像中的代码位置
TARGET_DIR="/shared/app"   # emptyDir 卷的挂载点

# 2. 创建目标目录
mkdir -p "$TARGET_DIR"

# 3. 复制任务定义相关的代码目录
for dir in worker core services db models schemas crud; do
    if [ -d "$SOURCE_DIR/$dir" ]; then
        echo "复制 $dir/..."
        cp -r "$SOURCE_DIR/$dir" "$TARGET_DIR/"
    fi
done

# 4. 复制必要的配置文件
[ -f "$SOURCE_DIR/__init__.py" ] && cp "$SOURCE_DIR/__init__.py" "$TARGET_DIR/"
[ -f "$SOURCE_DIR/celeryworker_pre_start.py" ] && cp "$SOURCE_DIR/celeryworker_pre_start.py" "$TARGET_DIR/"
```

**提取的目录结构**：
```
/shared/app/              # emptyDir 卷
  ├── __init__.py
  ├── celeryworker_pre_start.py
  ├── worker/             # 任务定义
  │   └── llmops_tasks.py
  ├── core/               # Celery 配置
  │   └── celery_app.py
  ├── services/           # 服务层
  ├── db/                 # 数据库连接
  ├── models/             # 数据库模型
  ├── schemas/            # 数据模式
  └── crud/               # CRUD 操作
```

### 4.3 主容器挂载代码

**挂载配置**（celeryworker.yaml 第 58-60 行）：
```yaml
volumeMounts:
- name: worker-code
  mountPath: /app/app  # 将 emptyDir 卷挂载到 /app/app
```

**挂载后的结构**：
```
/app/                    # Celery Worker 容器的工作目录
  └── app/               # 挂载的代码（来自 emptyDir）
      ├── worker/
      ├── core/
      ├── services/
      └── ...
```

```yaml

  value: "/app"  # 确保可以导入 app.worker 模块
```

### 4.4 Init Container 的优势

#### 4.4.1 代码自动同步

**Pod 启动流程**：
```
1. Pod 创建
   ↓
2. Init Container 运行
   - 使用 llmops-service 镜像
   - 提取最新代码到 emptyDir
   ↓
3. Init Container 完成
   ↓
4. 主容器启动
   - 挂载 emptyDir 卷
   - 使用最新代码
```

**优势**：
- Pod 重启时自动提取最新代码
- 确保代码版本与 llmops-service 一致
- 不需要重新构建 celeryworker 镜像

#### 4.4.2 镜像解耦

**llmops-service 镜像**：
- 包含完整应用代码
- 包含 FastAPI 和 Web 依赖
- 镜像较大，但包含所有业务逻辑

**celeryworker 镜像**：
- 只包含 Celery 运行时
- 不包含应用代码
- 镜像小，构建快，可复用

**解耦效果**：
- 业务代码变更：只需重新构建 llmops-service 镜像
- celeryworker 镜像：基础设施镜像，很少变更
- 代码同步：通过 Init Container 自动完成

#### 4.4.3 多应用支持

同一个 celeryworker 基础设施镜像可以服务多个应用：

```
应用 A（llmops-service）
  ↓ Init Container 提取代码 A
  ↓
celeryworker Pod A
  ↓ 处理应用 A 的任务

应用 B（other-service）
  ↓ Init Container 提取代码 B
  ↓
celeryworker Pod B
  ↓ 处理应用 B 的任务
```

**配置示例**：
```yaml
# celeryworker Pod A
initContainers:
- name: extract-worker-code
  image: llmops-service:1.0.0  # 应用 A 的镜像

# celeryworker Pod B
initContainers:
- name: extract-worker-code
  image: other-service:1.0.0  # 应用 B 的镜像
```

### 5.3 运行时流程

#### 5.3.1 任务发送流程

```
1. 客户端发送 HTTP 请求
   POST /api/v1/datasets/{dataset_id}/documents/{document_id}
   
2. llmops-service 接收请求
   FastAPI 路由处理
   
3. 调用业务逻辑
   document_service.delete_document()
   
4. 发送 Celery 任务
   delete_document_task.delay(dataset_id, document_id)
   或
   celery_app.send_task("llmops.delete_document", args=[dataset_id, document_id])
   
5. Celery 查找任务路由
   task_routes = {"app.worker.*": "llmops-queue"}
   任务模块：app.worker.llmops_tasks
   匹配规则：app.worker.* ✓
   
6. 发送任务到 RabbitMQ
   队列：llmops-queue
   消息格式：Celery 协议（二进制）
   消息内容：
     - task: "llmops.delete_document"
     - id: "task-uuid"
     - args: [dataset_id, document_id]
     - kwargs: {}
```

#### 5.3.2 任务接收和执行流程

```
1. celeryworker 从 RabbitMQ 接收消息
   队列：llmops-queue
   消息：Celery 协议格式
   
2. 解析任务消息
   任务名称：llmops.delete_document
   任务参数：dataset_id, document_id
   
3. 查找任务函数
   从挂载的代码中查找（/app/app/worker/llmops_tasks.py）
   任务函数：delete_document(dataset_id, document_id)
   
4. 执行任务
   - 导入任务函数
   - 调用服务层（services/document_service.py）
   - 操作数据库（models/、db/）
   - 执行业务逻辑
   
5. 返回结果
   - 任务成功：结果存储到 Redis
   - 任务失败：错误信息存储到 Redis
   
6. 发送 ACK
   确认任务已处理（acks_late=True）
```

#### 5.3.3 消息格式说明

**Celery 发送到 RabbitMQ 的消息格式**（二进制，不是 JSON）：

```
消息结构：
{
  "body": base64_encoded_task_data,
  "headers": {
    "task": "llmops.delete_document",
    "id": "task-uuid",
    "lang": "py",
    "argsrepr": "(dataset_id, document_id)",
    "kwargsrepr": "{}"
  },
  "properties": {
    "correlation_id": "task-uuid",
    "reply_to": "result-queue-uuid"
  }
}
```

**为什么 taskworker 无法工作**：
- taskworker 使用 `json.loads(body)` 解析消息
- 但 Celery 消息是二进制格式，不是 JSON
- 即使格式兼容，taskworker 也没有实现任务执行逻辑
