# UAT：用户消息怎么写

UAT 这一类验证做出来的东西**是否满足用户消息**。验收方按 [怎么验](verify-rules.md) 做；人看结论时怎么把关见 [UAT 把关](finalize.md)。

**规范不规定答。**要让答符合某种形式、走某条路、带某些东西，**就在这一问里提出来**——
规范里不替你规定，模型也不会自己知道。写进问里的才算数。

答由验收 agent 交回，它不是实现这份 IMP 的那一个。

逐条判定与证据写在 `test/` 里，结论写进那条提交。多个验收者各自验收再比对时，按
[多方竞争协议](../competition.md) 进行。

## 这一类该问什么

**没有模板**，但和 IMP 一样：验收者是另一个进程，只知道消息里写了的东西。
下面这些不说清就判不了：

| 问什么 | 说明 |
| --- | --- |
| **验收对象** | 哪条分支上的哪个提交——**写完整提交号**，分支是会被快进、重置、强推的指针 |
| **按哪几条判** | 照抄被验那一问里已冻结的完成条件，不在这里改、不在这里加 |
| **真实路径** | 要走哪几条用户路径；哪些恢复与降级场景也要验 |
| **观察窗** | 看多久、看哪些可观测的量；不是裸的时钟时间 |
| 哪些能机器判、哪些只能靠纪律 | 不分档，答会把纪律条目写成「已验证」（见下面「门的三档」） |
| **可用的证据** | 能跑的命令、测试入口、日志与产物位置；够不着的路径要点明 |
| 在哪开 worktree | 在被验的 worktree 之上再开一个，不得修改被验的产物 |
| 残余风险谁接收 | 验完还剩什么没盖住、谁来决定接不接 |

执行者不能是实现这一份 IMP 的那一个。
写多严见 [turn 的投影](../turn-project.md)「用户消息写多严」。

## 验到什么程度算够

**每条判定都有 `pass`、`fail` 或 `undecidable`，覆盖按三档写全，残余风险写明谁接收**，这一份验收就完整了。
判不了的停在 `undecidable`，不自己发明标准补齐。

发现设计不对、或者完成条件本身有问题，写进结论并回相应那一类追问，**不在验收里改设计，也不改窄判据换取通过**。
