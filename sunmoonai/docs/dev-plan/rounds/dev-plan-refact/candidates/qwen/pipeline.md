## 0. 前提：开发全部由 AI 承担

本项目约定：**开发工作全部由 AI 助手承担，人只提需求、拍板、验收。**
这个前提把经典流程的三个成本结构同时翻转：

| 成本 | 人类团队 | AI 执行 |
| --- | --- | --- |
| 产出（写代码/文档/测试） | 高，是瓶颈 | 趋近 0 |
| 验证（读、判断对不对） | 中，靠评审 + 常识兜底 | **不变**——人的时间是唯一没变便宜的东西 |
| 上下文延续 | 靠记忆、口头传承 | **归零**，每次冷启动 |

因此本流程的设计目标不是“让 AI 写得更快”，而是：

1. **把瓶颈从产出搬到验证**：每份产物必须有可复跑的验收证据；
2. **把稀缺资源从工时变成人的注意力**：只在必须人拍的环节请人；
3. **把纪律尽量编译成错误**：凡“忘了做”与“故意做”长得一样的地方，必须显式化、门禁化。

这一前提直接决定阶段合并、门禁归属和文档类型。

## 1. 流程主干：七个阶段 + 一条横切

一条需求从提出到上线，经过七个顺序阶段；协作协议横切所有阶段，规定多执行体如何并行、评审与裁决。

每个阶段必须同时回答三件事，否则它只是一段时间：

1. **产出什么**（artifact）；
2. **存在哪**（location / 真源）；
3. **凭什么算过关**（gate criteria，机器执行或纪律执行必须显式声明）。

| 阶段 | 核心产出 | 存在位置 | 过关判据 |
| --- | --- | --- | --- |
| **S1 意图冻结** | REQ 需求基线（原始请求 + 规范化目标 + 验收标准 + 边界） | `working/request-baseline/` + `request-lifecycle.md` | 人确认 AI 复述无偏差；验收标准可执行化 |
| **S2 技术设计** | TLD 技术设计 + ADR 决策记录 + 契约 | `dev-plan/` 下 `tld/` + `rounds/` ADR | 方案评审通过；不可逆部分被识别；契约可被机器校验 |
| **S3 任务规划** | IMPL 实施计划 + 任务条目 | `dev-plan/implementation-plan.md` | DoR 满足；每个任务有独立机器可判验收 |
| **S4 实现** | 代码 + 测试 + 证据 | 各 App 仓库 | 测试先行且转绿；质量门全绿 |
| **S5 验证** | 评审记录 + 验收记录 | 评审报告 / CI 记录 / `rounds/` 验收归档 | 机器门禁全绿 + 人抽检三样通过 |
| **S6 发布** | RELEASE bundle + manifest | `k8s/app-platform/*/deployment/bundle/` | 回滚路径已验证；digest 一致 |
| **S7 运行与学习** | 运行反馈、约束更新、交接 | `handoff.md` + `constraints.md` 更新 + 事故记录 | SLO 未破；改进项进待办 |
| **X1 协作协议** | 多 Agent 并行、评审、裁决、异议规则 | `dev-plan/protocol/` | 按规则执行；产物从 commit 反推 |

### 1.1 为什么分成这七个阶段

- **S1 与 S2 必须分开**：需求目标（REQ）与技术方案（TLD）是两类不同读者。混写导致产品人员读架构、架构人员读验收——这是 `request-lifecycle.md` 当前 647 行的主要病因。
- **S3 独立存在**：实施计划回答“按什么顺序建什么”，与技术设计回答“建成长什么样”不同。`development-plan.md` 当前把路线图和架构取向混在一起，需要拆分。
- **S4 不写进 `dev-plan/`**：代码和测试的真源在 App 仓库，`dev-plan/` 只保留对它们的引用、契约和证据要求。
- **S5 独立存在**：验证不是实现的尾巴，而是独立角色按冻结标准执行的动作。AI 流程里“自己写实现 + 自己写测试 + 自己报告通过”等于没有验证。
- **S6 与 S4/S5 分开**：发布是可逆性最关键的分界线；回滚路径未验证 = 没有发布。
- **S7 让流程闭环**：运行反馈回流成新需求，否则文档会变成一次性快照。
- **X1 横切**：协作协议不是某个阶段的产物，而是任何阶段触发多执行体协作时的规则。

## 2. 两个门：DoR 与 DoD

### 2.1 Definition of Ready（可以开工了）

一个任务满足以下全部条件才可以进入 S4 实现：

| # | 条件 | 执行者 |
| --- | --- | --- |
| R1 | REQ 已冻结：原始请求、规范化目标、验收标准、边界、不包含部分归属明确 | 机器：工单字段非空；纪律：人确认复述无偏差 |
| R2 | 技术方案已记录：重大取舍已写 ADR，契约已定义并可被机器校验 | 机器：ADR 文件存在 + 契约 schema 通过校验 |
| R3 | 依赖已就绪或已明确阻塞点 | 纪律 |
| R4 | 测试策略已定：每条验收标准指向一个未来的测试标识 | 机器：IMPL 任务条目含 `test_ref` |
| R5 | 任务粒度满足“可独立验收”——杀掉当前会话，另一执行者只读持久载体能接着做 | 纪律 |
| R6 | 约束自检已做：相关 `constraints.md` 规则列出结论 | 纪律，但检查清单由机器生成 |

### 2.2 Definition of Done（做完了）

一个任务满足以下全部条件才算完成：

| # | 条件 | 执行者 |
| --- | --- | --- |
| D1 | 代码合并进开发分支（或候选 commit 已冻结） | 机器：commit 可达 |
| D2 | 测试新增并通过；CI 全绿 | 机器 |
| D3 | 文档已更新：契约、ADR、IMPL 按需同步 | 机器：相关文件变更与代码同 commit |
| D4 | 证据已附：命令、环境、commit、摘要可复跑 | 纪律，但证据格式由机器校验 |
| D5 | 验收由独立方执行并通过 | 机器：验收记录存在；纪律：验收方不是实现方 |
| D6 | 不可逆副作用已记录或已获授权 | 机器：副作用账有记录 |
| D7 | 未覆盖范围、盲区和残余风险已披露 | 纪律 |

**关键原则**：机器执行的判据与靠纪律的判据不能混在一张清单里。上表已按执行者分栏。

## 3. 文档类型：从阶段推导

文档类型不是先立一套分类再倒推流程，而是每个阶段的产物自然长成一类文档：

| 阶段 | 产物 | 文档类型 | 命名 | 生命周期 |
| --- | --- | --- | --- | --- |
| S1 | 需求基线 | REQ | `request-lifecycle.md` / `working/request-baseline/` | 随需求修订产生新版本；旧版保留血缘 |
| S2 | 技术设计方案 | TLD | `dev-plan/tld/*.md` | 随实现演进，但架构基线版本化 |
| S2 | 不可逆决策记录 | ADR | `rounds/<轮次>/rulings.md` + 归档 | **只被取代不被修改**；编号递增 |
| S2 | 接口/数据契约 | CONTRACT | provider schema + consumer lock | 随代码同步；改代码不改契约 = bug |
| S3 | 实施计划 | IMPL | `development-plan.md` + `implementation-plan.md` | 按里程碑更新；路线图与任务清单分离 |
| S4-S5 | 执行者操作指南 | HANDBOOK | `agent-dev-guide.md` | 随工具、SDK、流程更新 |
| X1 | 协作协议 | PROTOCOL | `protocol/round-protocol.md` | 修订需走协议自身规定的流程 |
| S7 | 运行纪律/约束 | RUN | `constraints.md` | 新增约束需论证；旧约束撤销需记录 |
| S7 | 当前状态交接 | STATUS | `handoff.md` | 只投影当前游标和阻塞；不复制覆盖状态 |
| 入口 | 目录说明 | INDEX | `README.md` | 随文档集合变化 |

### 3.1 为什么用这些命名

- **REQ / TLD / ADR / IMPL** 是通行名，不加不减分。本结构保留它们是因为：
  - 它们准确对应“需求 / 设计 / 决策 / 计划”四类不同生命周期；
  - 项目成员已有共识（所有者 2026-09-07 映射）。
- **HANDBOOK** 不是传统文档三分法中的类型，但本项目需要它：AI 执行者每次冷启动都需要一份“上下文包”，它既不是决策（不会变）、也不是规格（不随代码同步）、也不是状态（不每天变），而是写给 AI 的操作入口。`agent-dev-guide.md` 就是这类文档。
- **PROTOCOL / RUN / STATUS** 是从 S7 和 X1 推导出的支撑类型，分别承载协作规则、长期纪律和当前状态。

## 4. 每类文档的生命周期

| 类型 | 谁能改 | 能否被取代 | 旧版怎么办 |
| --- | --- | --- | --- |
| REQ | 需求所有者或授权修订工作单元 | 可以，产生新版本并保留血缘 | 旧版作为历史基线保留；外部锚点通过稳定 ID 迁移 |
| TLD | 技术设计工作单元 | 可以，但架构基线版本化 | 旧版标 `superseded`，保留来源映射 |
| ADR | 不可修改 | 只被新 ADR 取代 | 旧 ADR 永久保留，状态改为“被 ADR-NNN 取代” |
| CONTRACT | provider 仓权威，consumer 持锁 | 版本化演进 | 旧版本保留到 consumer 全部升级 |
| IMPL | 规划工作单元 | 按里程碑更新 | 已完成条目保留，未完成任务迁移 |
| HANDBOOK | 流程维护者 | 持续更新 | 旧操作步骤被覆盖，但重大变更需记录 |
| PROTOCOL | 协议修订工作单元 | 修订需自身流程批准 | 旧版本归档在 `rounds/` |
| RUN | 约束委员会 / 所有者 | 新增或撤销需论证 | 撤销记录进 ADR 或 rulings |
| STATUS | 当前主驾驶 / supervisor | 每次交接覆盖 | 只保留最新状态；历史状态进 ADR/rounds |
| INDEX | 文档维护者 | 随文档集合更新 | 旧入口说明不保留 |

## 5. 判据归属：机器还是纪律

| 门 / 判据 | 执行者 | 说明 |
| --- | --- | --- |
| 链接存在性、`§N` 引用、表格列数 | 机器：`doc-gate.py` | 随提交自动跑 |
| 架构不变量（接口分层、迁移链单调等） | 机器：`test_kernel_invariants.py` | 跑 `uv run pytest` 即带上 |
| 契约 schema 双向锁定 | 机器：双端契约测试 | provider/consumer 各跑自己的半 |
| 代码格式 / lint / 类型 / 单元测试 | 机器：CI / `make check` | 待建；当前靠纪律 |
| REQ 复述是否无偏差 | 纪律：人确认 | 机器只能检查字段存在 |
| 验收标准是否可执行化 | 纪律 + 机器辅助 | 机器检查 `test_ref` 存在；语义可执行靠人 |
| 不可逆动作审批 | 纪律：有权主体 | 但审批记录必须由机器落账 |
| 未覆盖范围 / 盲区披露 | 纪律 | 机器无法判定是否已穷尽 |
| 候选隔离（提案冻结前不读其他候选） | 纪律 | 无法事后机械证明 |

**核心原则**：凡是能交给机器的判据都交给机器；交不了的显式标 ⚠，不靠“记得检查”。

## 7. 与 `project-guide/` 的边界

- `project-guide/` 描述**当前项目长什么样**（事实文档）；
- `dev-plan/` 描述**要建什么、怎么建、凭什么算完成**（目标与流程文档）；
- 两者交叉点：TLD 引用 `project-guide/` 的当前事实，但 TLD 给出“要改成什么样”；`project-guide/` 不承载流程门或验收标准。

## 8. 哪些东西本轮不改

按任务书 §1.4：

- 不改任何产品结论（如 Task 状态机、接口分面规则）；
- 不改 `rounds/` 已归档轮次的内部结构；
- 不改四个产品仓的代码；
- 不把 `working/request-baseline/` 移出 `working/`（所有者已裁定）。

本轮只改 `dev-plan/` 的组织方式。
