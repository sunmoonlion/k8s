# UAT：用户验收测试（User Acceptance Testing）

UAT 阶段验证做出来的东西是否满足用户消息。由验收 agent 交回，它不是实现这份 SDP 的那一个。

**产物在 worktree 的 `test/`，不在任务目录里。**这一段的 turn 没有 `response.md`；`turn.md` 记分支与提交，
结论写在回执正文与那条提交里，见 [任务的生命周期](../lifecycle.md)「SDP 与 UAT 的 worktree」。

多个验收者各自验收再比对时，按 [多方竞争协议](../detailed-rules/protocol/competition-rules.md) 进行。

建 turn 时复制 [`user-message.template.md`](../user-message.template.md) 与 [`turn.template.md`](../turn.template.md)；正文的写法不设模板，这一段的问要说清什么见下。

## 这一段的用户消息

**这一段的问没有模板**，但和 SDP 一样：验收者是另一个进程，只知道消息里写了的东西。YAML 头里填 `verifies`（验收哪个 turn）。
这几样不写就判不了：

- **验收对象**：哪个 turn、哪条分支上的哪个提交——写完整提交号，分支是会被快进、重置、强推的指针；
- **按哪几条判**：照抄被验 turn 里已冻结的完成条件，不在这里改、不在这里加；
- **哪些能机器判、哪些只能靠纪律**：不分档，答会把纪律条目写成「已验证」（见下面「门的三档」）；
- **可用的证据**：能跑的命令、测试入口、产物位置；够不着的路径要点明，验收才写得出「不能排除」而不是含混的「没查」；
- **在哪开 worktree**：在被验的 worktree 之上再开一个，不得修改被验的产物。

执行者不能是实现这份 SDP 的那一个。这一段不交 `response.md`。写多严见 [任务的生命周期](../lifecycle.md)「用户消息写多严」。

## 判据与结论

- **验收依据是被验 turn 派工时的完成条件**：SDP 段的用户消息里写明的那几条，照抄过来，派工后不改；
  用户消息没写的部分，以它说清的要求、各阶段规则和本规范为准。出题的人与答题的 agent 分开，实现者完工后不能改验收题。
- **每个判定只有三种结论**：`pass`、`fail`、`undecidable`。用户消息没有可判定依据的地方判 `undecidable` 交给人，**不自己发明标准来判通过**。
- **整份验收的结论**是逐条判定汇总后的那一个——有任何一条不通过就是不通过，没有不通过但有不可判就是不可判。
  逐条判定与证据写在 `test/` 里，那是真源；回执正文和提交说明只把结论指过去。
  它说的是被验的那个 turn 过没过，与 `status`（这次验收本身做完没有）是两件事。
- **开工条件与完成条件是两回事。**「候选验证通过」「指定版本发布成功」「要求满足」是三个不同的结论，记录必须说清是哪一个，不能都写「已完成」。
- **完成条件逐条满足才叫完成。**缺项时只能称相应的中间状态（已派工、候选完成、待验收……），不能笼统说完成。
- **验收不能外推。**在一类任务上跑通的便宜验收（可用测试、diff 机械复算），不能证明判断昂贵的另一类任务也过关。
- **先核前提。**比较方案之前，先顺着真实调用链核实：要控制的动作是否一定经过所说的强制点；查不到就标假设。

## 门的三档

门的执行归属分三档，**不混进同一张「已保证」清单**：

| 档 | 含义 | 要求 |
| --- | --- | --- |
| 机器已能判 | 有一条能跑出非平凡结果的命令 | 必须能写出这条命令 |
| 当前靠纪律、将来可机器化 | 有办法做成检查，只是还没做 | 登记为欠账 |
| 本质上只能靠纪律 | 做不成机器检查 | 一直标 ⚠ |

规则要有载体：能跟着测试或提交自动跑的做成自动检查；做不成的老实标 ⚠ 并靠自检。
要人记得去跑的检查，和写在文档里的规矩没有本质区别；检查的结论不能取决于某台机器的工作区状态。

## 证据采信

- 自述只是待验证的主张；结论由验收方从冻结的产物独立重算。
- 采信程度取各项中最低的一项（来源、可见范围、隔离强度、验收独立性、覆盖），任一项未知就降级，不取平均。
- 覆盖声明同时写查了什么、没查什么；零命中只有在输入集合被完整枚举时才算通过，否则是 `undecidable`。

证据分三级，**不可互相升格**，尤其不得把「机制上必然如此」当成「此处已核对」：

- **已核对事实**：证据当前仍可独立取得并复核（提交、文件、可重跑命令）；
- **事故报告**：确实发生过，但现场已灭失，只能按当事方陈述记录；
- **设计风险**：机制上成立，但尚未实际踩到，或原始出处已不可取得。

用不可复核的叙述去加强一条本来就成立的规则，只会削弱整份文档的证据标准。

## 覆盖声明：查了、没查、不能排除

覆盖声明要能装下「不确定」，不是只有「查了」「没查」两档。凡「不能排除某事发生过」，就如实写进来：

| 写法 | 含义 |
| --- | --- |
| 查了 | 有观测，有结论 |
| 没查 | 没有观测，**明知自己不知道** |
| **不能排除** | **有观测但不足以定论**，或存在自己控制不到的路径 |

「没查」还要按类别分列，不能混成一段：

| 类别 | 例 | 性质 |
| --- | --- | --- |
| **环境事实** | 主机名、身份、命名空间映射 | **可当场复跑**；没查是因为没跑，跑了就有结论 |
| **远端与授权** | 远端分支、分支保护、部署密钥 | 部分可读，**写授权不能只靠读取来验证** |
| **执行者内部** | 界面里选的模型、沙箱内的工具调用 | **结构上够不着**，换接入方式才可能有结论 |

第三类是唯一「不改变接入方式就永远查不了」的；把它和前两类并排写成「没查」，会让人以为再跑几条命令就能补上。

**如实写「不能排除」不扣分，隐瞒才扣。**这与 [人的批准点](../detailed-rules/approvals.md)「人这一侧的义务」里
「执行者说没查过某处时当作真话对待」是同一条规则的两侧。

## 验证分层

| 层 | 谁 | 判什么 |
| --- | --- | --- |
| L0 | 自动检查（CI、提交钩子、校验器） | 链接、schema、冻结区、摘要、diff、测试、角色冲突等机械条 |
| L1 | 独立验收方 | 用户消息里机器判不了的内容；**作者自检不能代替独立验收**，验收方只按派工时的要求判，不为通过而静默改标准 |
| L2 | 被处置主张的原作者 | 是否被误读；异议必须带处置条目与可复跑证据 |
| L3 | 人 | 意图是否正确、不可逆项、抽样复算证据的真实性；抽样规则事先写进用户消息，否则抽检会退化成「翻一翻」 |

顺序不可倒：L0 未过不进 L1，L1、L2 未过不请求最终批准。新增的机器判据，首跑必须与人工结论对照；
锚点存在但不支持断言，比没有锚点更危险。

## 检查本身也必须接受检查

每个检查都输出 `pass` / `fail` / `undecidable`，并写明查了什么、没查什么。
缺输入、权限不足、枚举失败不能被吸收为通过；聚合前先判输入集合是否完整、是否允许为空。
**不让空集合、空 diff、吞掉的退出码或「0 个文件通过」代替完成条件。**

新增或修改检查时至少核查适用的边界用例：正常通过、真正失败、输入缺失、命令失败、空集合、
引用对象不可达、否定句与历史引用。误报要区分是解析问题还是内容问题，不能为了消掉一个红字删掉失败标准；
假失败偏安全，也不是长期保留误报的理由。

常见的假答案与核法：

| 边界案例 | 错误结论怎样产生 | 怎样核 |
| --- | --- | --- |
| 验收方集合为空 | `all([])` 为真，被当成完成 | 先验证应有参与方或产物数量，再聚合；未指定不是通过 |
| 身份命令在仓外运行 | 失败被管道吞掉，从错误文本生成假名字 | 每个依赖命令检查退出码；取不到仓库根就停止 |
| 身份判别失败后按产品猜人 | 「运行在某产品」被推成「属于某参与方」 | 对照登记的 worktree 与任务身份 |
| 机械检查读到否定句 | 「没有这条边」被误判为声明了非法边 | 从规范定义块或 schema 取状态 |
| 两层调用各吞一个错误 | 内层失败被外层成功掩盖 | 原始退出码逐层传递 |
| 文档门禁只查链接 | 被纯文本「文件:行」引用的文件删了，门禁仍绿 | 并查纯文本锚点与可重取来源 |
| 标题保留而正文被切掉 | 空节不产生坏链接 | 对照源段的主张、条件、反例与未验证项 |

假通过会成为下游继续执行的依据，比一次明确的失败更危险；判不了时停在 `undecidable`。

文档复核分四层：链接可达；标题有对应；对应正文真正承载原主张及其边界；证据本身支持该主张。
**空标题、只有结论没有证据、映射到同名异义的段落，都不算吸收。**链接和表格一类的机械检查不能替代正文层与证据层。

## 载体各能证明什么

| 载体 | 覆盖会怎样 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 未提交的工作区文件 | 后写直接覆盖先写：无冲突、无历史、无作者归属 | 磁盘此刻的内容 | 谁写的、谁先写完、被覆盖前是什么 |
| 提交 | 新提交不摧毁旧对象，旧对象需有引用才找得到 | 一组文件内容及父历史不可变 | 谁批准、测试是否通过、外部副作用状态 |
| 分支 | 指针可被快进、重置、强推 | 当前指向哪个提交 | 稳定的评审对象 |
| worktree | 一条分支只能被一个 worktree 检出 | 某执行者当前可写目录 | 长期证据 |
| 标签与引用 | 可被移动或删除，所指对象仍在 | 使对象可达、表达冻结点 | 不自动构成验收或发布 |
| 补丁 | 应用到不同基线结果不同 | 可传输的差异 | 完整父基线与外部状态 |
| 共享发布面 | 未授权写入等于闯入他人发布面 | 只有整合后的最终提交算交付 | 任何未经整合的内容 |

**交回 = 自己分支上的可达提交。**候选和评审一律引用完整提交 ID 与基线；冻结后禁止改写历史，需要变基时形成新候选并保留新旧映射；
删除分支或 worktree 前确认要保留的提交已由持久引用保持可达——「对象暂时还在 reflog」不是保留策略。
Git 不能证明跨记录的事务提交或写入隔离，也不能证明执行者内部发生过哪些工具调用。

## 证据账按档位

| 档位 | 最小留证 |
| --- | --- |
| T0 直做 | 固定最终提交、验收方、门禁命令及原始输出位置 |
| T1 单稿加独立评审 | 用户消息链接、评审、处置、最终提交与验证结果 |
| T2 完整多方竞争 | 请求、清单、候选、评审、决策、改进、处置、最终提交上的回归结果 |

载体可以分散，但必须由一个稳定的主记录串起全部链接，并能由第三方读取。**任何档位都不得只在对话里宣称测试通过**；
别人不能恢复和复核的内容视为未持久化。候选提交必须来自该候选自己的分支。

## 能力状态只用四级

| 级 | 含义 |
| --- | --- |
| `defined` | 有类、DTO、迁移或测试夹具**存在** |
| `wired` | 生产链**已接线**，会被真实请求走到 |
| `deployable` | 部署面（打包、网络、凭据、配额）**已就位** |
| `runtime-verified` | 在目标环境**实跑验证过** |

类、DTO、迁移或测试夹具存在，都不等于生产链已经接线。候选与对话只作线索；当前实现的断言必须回到代码、测试或运行结果取证。

## 完成判据

同时满足才叫闭环：用户消息可追溯，派工幂等；worktree 与清单可复现；范围、验收、权限、预算、批准点在派工时就已定下，基线已固定；
执行者接单核对过 worktree、指令与输入；按风险执行，角色冲突已处理；每个产出有归属、命名空间、状态、来源和唯一的发布目标与整合者；
候选没有直接写共享路径；发布经预期版本的原子条件更新；并行结果绑定提交，迟到、失败、取消已处置；最终提交上门禁与验收逐条通过；
结果、证据、副作用、盲区和风险已持久化；终态唯一，可重取结果；提交与产物可达、血缘可追溯且无活跃引用后才清理 worktree。

**缺项时只能称「已派工」「候选完成」「本次选定」「待验收」或「清理待处理」，不能笼统宣称完成。**

## 验收能发现什么、发现不了什么

验收能发现局部矛盾、非法状态边、归属错误和证据不足；但**共同的前提错误、被用户消息封死的答案空间**，可能经多轮验收仍不被发现——
「必须包含某机制」一旦冻成标准，「其实不需要它」就无法作为合格答案提交，增加候选数也修不了这种出题错误。

所以任务越重，出题越要给硬约束与方向、可复核的问题、客观的完成判据与完整的源集，允许用证据质疑机制的必要性，不给出题方的倾向。
**通过只意味着按所述范围完成了一次检视**，不能估计未发现缺陷为零；发布说明与记录一律照此措辞。

## 用历史证据

使用证据前固定：仓库或 SDK 版本、配置或策略版本、主机、身份、沙箱或容器上下文、命令、退出码、原始输出引用及时间；敏感字段去敏。
沙箱内观测不能直接外推宿主，受限环境不能代替同身份的生产测试。文档里的「曾经通过」只说明那个版本的那个用例；
原记录不得改成新日期。原作者的数字与读数可作回归线索，没有独立重取证据时引用为「原作者记录」。
