### 0.3 二十二个词，一句话一个

**前七个是内核对象**，权威定义在 `working/request-lifecycle.md`「核心对象」，这里给的是便于阅读的一句话：

| 词 | 一句话 |
| --- | --- |
| **Task** | 用户提交并等待业务结果的那一件事。跨连接、跨进程、跨多次尝试而存在 |
| **Attempt** | 为完成一个 Task 发起的**一次执行**。一个 Task 可以有零到多次 Attempt |
| **Interaction** | 系统向人请求输入或批准，**以及人的回答** |
| **Artifact** | 任何有版本、有作者的产出物：工单、候选稿、评审、裁定、代码提交 |
| **Event** | 只追加的事实记录。状态是它的投影 |
| **Side Effect** | 对外部世界的不可逆动作：写共享路径、推主线、发布 |
| **Delivery** | 结果怎么送到人面前，以及怎么重新取回 |

**两个 Profile**，权威定义在同一文件「Task Profile 与 Agent Profile」：

| 词 | 一句话 |
| --- | --- |
| **Task Profile** | 「**这类活的契约**」：输入什么、输出什么、怎么算验收通过、要什么证据、什么策略 |
| **Agent Profile** | 「**这个执行者的能力**」：模型、工具、权限边界、**运行时能看见它多细** |

**七个本文引入的**，本文即权威：

| 词 | 定义 |
| --- | --- |
| **principal** | **有权在某条状态转换上做决定的主体，且这个权力不来自它能不能执行**。本项目当前只有一个：`owner`。**人不是执行者，是 principal**——理由见 §2.6 |
| **orchestrator** | 推进状态、派发、收集、观测逾期的那段**确定性代码**。**它是代码，不是角色**——过渡期由人按脚本跑，人是它的触发通道，不是它本身 |
| **harness** | 执行者的**运行外壳**：二进制 + 提示词 + 工具集。`codex-cli`、`cursor-agent`、`cursor-app`、`qoder` 各是一个 |
| **可观测粒度** | 运行时**能看见**被调 agent 多细。四档，见 §2.4。它决定证据算不算数 |
| **provenance（来源等级）** | 一条记录是**运行时实证的**（`attested`）、**执行者自报的**（`reported`）、还是**事后推断的**（`inferred`） |
| **档位（T0/T1/T2）** | 这件事该走多重的流程：直做 / 单稿加独立评审 / 完整并行轮。见 §3.1 |
| **方向不对称** | 朝严谨的方向可以自己裁定，**朝省事的方向必须人确认**。见 §3.3。这是全套纪律的统一原则 |
| **router** | 从一个请求算出「这是哪类活、走什么档、派给谁、在哪个工作区做」的那段代码。出三值：`decide` 定了 / `ask` 问人 / `refuse` 不接。**它是代码，不是角色**（同 orchestrator） |
| **等效判据** | 换一种实现之后，拿什么证明还是同一套东西。分**形状**与**跑动**两层，见 §6 |
| **投影 Π** | 比较两次跑动前先丢掉的东西：执行者私有的内部步骤，以及时间戳。不丢时间戳，两种实现永远不等效 |
| **未归因效应** | 在账本里找不到对应任务的那些变更。**只登记、不补造任务、不自动惩罚**。见 §4.4 |
| **登记集合 / 自动路由候选集** | 前者记「这个执行者存在」，后者记「router 可以选中它」。**两个集合**——不能自动分发的执行者留在前者，退出后者。见 §2.3 |

## 1. 我们在建什么

### 1.1 三层：什么租、什么建

```
┌─ 我们自建：运作纪律 ───────────────────────────────────┐
│  什么时候必须问人、判据是什么、什么算通过、怎么留痕、       │
│  隔离与三阶段可见性、提案包构造、评审协议、吸收处置记录     │
├─ 我们自建：编排（用 LangGraph 作为实现手段）───────────┤
│  Task/Attempt 状态、派发、收集、中断与恢复、检查点         │
│  ⚠ 用库的原语实现，**不重定义它的协议**（见 §2.7）        │
├─ 租用：被调用的 agent ─────────────────────────────────┤
│  通用：Codex 的 Python SDK                                │
│  专业：deepseek-harness 建的领域 agent（如财务分析）       │
│  不自建它们的轮次生命周期、隔离进程、沙箱、工具协议         │
└────────────────────────────────────────────────────────┘
```

依据：`constraints.md` **A4**「执行层**租用不自建**，依赖边界严格限定在 SDK」；
`development-plan.md`「执行层租用，不自建」与「智能体分两部分」。

**A4 管的是最下层**（被调 agent），不是说我们的编排不能自建。
中间层是自建的，但**它的机制原语来自库**——投资仓已经在用
`langgraph>=1.2.8` 与 `langgraph-checkpoint-postgres>=3.1.0`
（`investment-app/investment-backend/app/pyproject.toml`）。

### 1.2 六条设计原则

全部取自本仓已成文的判断或所有者裁定，本文只是把它们**一致地用到底**：

| # | 原则 | 出处 |
| --- | --- | --- |
| **P0** | **只有一套状态机（Task / Attempt）**；场景差异只体现在 Profile 的门禁、必需产物与中断策略；**任何场景不得新增状态词** | 所有者裁定；内核「Profile、Artifact 与扩展」「不修改通用状态语义」、反模式表「Profile 修改通用状态机 → 新领域产生第二套生命周期」 |
| **P1** | **同一事实只有一个权威写入面**；两份同构文档即两个真源 | 内核不变量 `I13` |
| **P2** | **状态从产物反推，不从声明读取**；**人的动作也不例外** | §3.7 |
| **P3** | **方向不对称**：朝严谨可自裁，朝省事须人确认；**默认值属于省事方向** | §3.3 |
| **P4** | **判据必须声明覆盖范围**；覆盖不全比没有更危险 | §3.7 |
| **P5** | **凡能落成代码、测试或门禁的纪律必须落成**；文字只描述意图 | `constraints.md` |
| **P6** | **设计任何机制之前，先用命令确认它要处理的动作现在实际怎么发生**（2026-09-06 立，成因见 §1.3） | §1.3 |

**三条推论**：

- **一个只能靠人转述的环节等于没有环节**（P2 + P5）。这决定了本文对「中断问人」的全部设计。
- **P0 的适用层级是 Task 与 Attempt。**Artifact、Interaction 等对象各有自己的小生命周期
  （候选的 `DRAFT → FROZEN → PUBLISHED`、问询的「已消费」），
  那**不是**第二套状态机，是对象属性——但同样跨场景共用、不得按场景另造。
- **P3 的理由不是谨慎，是自动化的默认漂移方向永远是省事**：若两个方向一样容易，
  档位会一路滑到最轻、检查会一条条消失、判据会为了让产出通过而被改。

### 1.3 先看六条已经被证伪的设计

**放在最前面，是因为它们曾经写得很详细、很自洽，而且都错了。**
每一条旁边是**证伪它的那条命令**——都在两分钟以内。

| # | 曾经的设计 | 为什么错 | 验伪方式 |
| --- | --- | --- | --- |
| 1 | Interaction 三值 + `amend` 载荷 + `amend_schema` + `amend.mode` + 过期校验 | 库的 `Command(resume=<任意值>)` 一个参数就够；且 12 次真实裁决**零次**使用 amend | 读 `pilot_graph.py:59` 与 `Command(resume=...)` 的实际用法 |
| 2 | 人的介入 → Task 级暂停 → 恢复时换新 Attempt | 检查点天然**原地恢复**，同一次执行接着跑。载荷之所以需要，正是因为我造了一个不该有的执行边界 | 读 `graph_runtime_service.py:40-46` |
| 3 | 回执仓（人的批准写成签名 commit，独立仓，VM 只读） | **动作本身即记录**；且它解决不了它想解决的问题（身份不可区分的根因是同机同用户有 sudo） | 见 §5.3 |
| 4 | 候选仓（agent 把产出推到隔离仓） | **agent 从不 push**，全部工作在本机 worktree 里 | `git ls-remote --heads origin` |
| 5 | VM 换三把 key、主仓只读 | **发布是本地 merge**，不经网络，key 管不着；换了还会打断所有者现在的发布流程 | `git ls-remote --tags origin`（冻结标签一个都不在远端） |
| 6 | 三道边界作为安全架构 | 要拦的动作**不经过它们** | 同上 |

**六条的共同成因**：在没核过「这个动作现在实际发生在哪、由谁做、经过什么」的情况下推演。
由此立一条纪律，放在 §3.3 的不可裁量下限里：

> **设计任何机制之前，先用命令确认它要处理的动作现在实际怎么发生。
> 没验过的前提不叫前提，叫假设；用假设推演出的设计，精致程度与正确性无关。**

## 2. 系统：一个运行时

### 2.1 只有一个运行时，开发是它的第一个 Task Profile

**所有的活——今天的文档开发、将来的财务分析——都是跑在同一个运行时上的 Task**，
按各自的 Task Profile 走**同一套状态机**。

「开发」不是运行时旁边的另一套流程，它是**第一个 Task Profile**。
它今天看起来特殊，只因为我们正用现有的 AI 助手**开发运行时本身**；
运行时建成之后，后续开发照样走它，只是由它调助手，而不是人手工调。

状态机取自内核，**本文不新增一个状态词、不走一条内核之外的边**：

```
Task:    RECEIVED → VALIDATING → QUEUED → RUNNING ⇄ WAITING
                  → SUCCEEDED | FAILED | CANCELLED | REJECTED
Attempt: CREATED → RUNNING ⇄ WAITING
                  → COMPLETED | FAILED | CANCELLED | BUDGET_EXCEEDED
```

**一个最容易混的地方**：Attempt 的终态叫 `COMPLETED` 不叫 `SUCCEEDED`。
一次执行跑完了、产出了东西，**不等于**用户要的结果达成了——中间隔着验收。
所以 `Attempt COMPLETED` 是 `Task SUCCEEDED` 的**必要不充分**条件。
反向也不对称：一次 Attempt 失败**不会**让 Task 失败，Task 退回排队再试（内核 `I8`）。

#### 运行时由什么组成

「运行时」不是一个笼统的词。它 = **内核对象的唯一写入面** + 四个确定性组件 + 两个适配层：

| 组件 | 职责 |
| --- | --- |
| **router** | 从请求算出 Task Profile 版本、档位、执行者候选、工作区计划；出三值 `decide / ask / refuse` |
| **orchestrator** | 推进 Task / Attempt 状态（只走合法转换表里的边）、派发、收集、观测逾期、回退 |
| **interaction service** | 产生 Interaction、**鉴别响应者**、原子消费 |
| **validator** | 按 Task Profile 版本跑验收的机械部分；判不了的显式交给验收方 |
| *适配层* **executor adapter** | 按 Agent Profile 的粒度字段决定怎么调、怎么看、怎么拦（§2.4） |
| *适配层* **principal channel** | 人怎么被叫到、怎么回，**响应者身份怎么鉴别**（§2.6） |

**orchestrator 是确定性代码，不是角色。**过渡期由人运行脚本时，人是它的**触发通道**，
不是这个组件。把欠账重命名为组件，下一轮就会有人对着这个名字设计接口。

#### 路由：模型只建议，规则表才决定

router 是唯一一个「可以用模型」的地方，但模型在这里**只产生证据，不产生决定**：

```text
输入：原始请求 + 附件 + 请求者上下文
  │
  ├─ 分类建议（可选；受限模型节点，无工具，固定 schema，低预算）
  │      → { 档位倾向, 领域倾向, 复杂度倾向, 证据[] }      ← 只是证据
  │
  └─ 确定性规则表（版本化）
         → decide  唯一命中 → 落账 { 档位, 参与方, 工作区计划, 策略版本, 命中的规则 }
         → ask     零命中或多命中 → 产生一次问询，收件箱里列出候选与各自理由
         → refuse  命中拒绝规则（越权、不可受理）→ Task `REJECTED`，带原因码
```

**为什么是三值而不是两值**：二值会把「不知道」压成「默认那个通用的」。
`ask` 存在的意义就是让不确定性可见——**不得默认落通用档**。

规则表的**命中理由必须落账**（`matched_rule` + `policy_version`），
只写「简单 / 复杂」不算。判不出来就 `refuse` 或 `ask`，**fail-closed**，
不猜一个能往下走的答案。

开发这个 Profile 里，档位判据就是 §3.1 那四条（不可逆 / 权威层 / 已知对立 / 判据未定），
分类节点的产出是**四条各自命中与否 + 证据**，规则表据此判档，人只在 `ask` 时介入。

⚠ **别把这个叫 gateway。**外部项目里同名的东西是按渠道/账号做确定性绑定的，
它两层都不读用户语义来决定领域。可借的是「确定性绑定 + 命中理由落账 + fail-closed」这个形状，
**不可借的是用它的名字去指语义路由**——名字借错，下一轮就有人照着那个名字设计接口。

### 2.2 开发 Task Profile：`dev.change`

```text
profile_id            dev.change
input_schema          工单：目标 · paths[]（允许触及的路径集）· baseline_commit
                      · read_only_inputs[]（路径 + 版本锚）· 档位 · 参与方名单 · 验收条（逐条编号）
output_schema         一个或多个 Artifact 落在共享最终路径，版本 = commit
normalization_rules   目标 → 可判定的验收条；**歧义实质改变结果 / 权限 / 成本 / 风险时才问人**
required_context      read_only_inputs 按版本锚取；候选**不得改动**它们
acceptance            机械条（脚本跑）+ 判断条（独立验收方跑，按冻结标准逐条给结论，不得改标准）
evidence              每条断言现状的句子附 file:line 或可复跑命令；采信等级按 §2.5 计算
freshness             baseline_commit 固定；**基线移动 → 新 Task**，不在原 Task 上改
allowed_capabilities  读整仓、写自己 worktree、不推主线
budget                观察窗 W = 已交付各家用时的中位数；max_rollbacks = 2
retry                 逾期 → 该家 Attempt FAILED(timeout)，Task 不失败
approval              权力表 H1–H8（§2.6）；档位决定开工前的审批触点数
privacy               文档任务无；数据类任务由它自己的 Task Profile 定
```

**别名只登记不并存**：`DEV`、`DEV_ROUND`、`DEVELOPMENT`、`dev.change.v1` 都是
`dev.change` 的别名，正式 id 取 `dev.change`。五家各起一个名字是自然的，
留着五个就是五个真源。

**档位不是三个 Task Profile**，是策略里的一个字段——改的是并行度与环节数，
**不改输入/输出/验收的形状**。这与 §3.1 的「一套流程三组参数」是同一条原则的两处应用。

#### 2.2.1 工单：一个冻结的 Artifact，一次确认

**工单是 Artifact，不是 Task 状态。**它只有 `DRAFT → FROZEN` 两个词，
Task 自己的状态由产物推导（§2.1）。**任何档位都有工单**，字段固定：

```toml
[order]
id, tier                    # 档位只用来选 guard 表，不是状态
artifact_state              # DRAFT | FROZEN
route_proposal              # router 的输出：模型证据 + 确定性规则结果，含 policy_version
route_effective             # T0：= proposal，由策略放行；T1/T2：人确认后的值
route_delta                 # 人相对 proposal 改了哪些字段；空 = 全盘沿用
intent_restatement          # 执行者用自己的话复述需求 + 决策点清单 + 标出的歧义
acceptance = [...]          # 逐条编号，冻结后不改；每条尽量指向一个未来的机械检查
frozen_sections = [...]
[executors]
intake_author               # 起草复述与验收条的执行者；同一家不得再任 proposer / arbiter / acceptor，
                            # 分发前机械拦。题目与验收条由所有者直接给时，intake_author = owner
proposers, arbiter, acceptor, approver
[workspace]
source, baseline_commit, write_actors, review_needed, submodule_plan
[budget]
observation_window_rule, max_rounds, max_rollbacks
```

`route_proposal` / `route_effective` / `route_delta` **三个字段分开存**是有意的：
建议与决定必须可分辨，`route_delta` 为空说明人全盘沿用了机器的建议——
那正是「盖章化」的度量（§2.6）。

**档位 = 三张表，不是三套状态。**每个档位对应一张 **guard 表**（哪些转换要过哪些门）、
一张**必需产物表**（哪个 Attempt 组要交什么）、一份 **interrupt 策略**（哪些审批能默认）。
三个档位读**同一个工单 schema**，脚本按档位取表。

**工单冻结（H1）与开工确认（H2）是两个转换**，开工前的触点数按档位是 **0 / 1 / 2**：

| 档 | 触点 | 为什么 |
| --- | --- | --- |
| T0 | 0 | H1 由已签策略承担，H2 按策略放行（见下节） |
| T1 | 1 | H1 + H2 合并为一份回执 |
| T2 | 2 | **验收标准要在参与方看到题目之前冻结**，而参与方名单本身可能还要人再定，两件事不能合并 |

#### 2.2.2 T0 怎么做到「开工前零触点」而不是把关卡默认掉

三条要求会同时冲突：H1 无默认 × T0 开工前零触点 × T0/T1 一签两用——
H2 默认放行了，工单却因 H1 无人签而停在 `DRAFT`。
**解法不是给 H1 加默认**（那是把最后一道关卡默认掉），
而是让 T0 **不产生需要单独冻结的东西**：

策略文件里定义若干**命名任务类包**，每个包三项：

```toml
[bundle.readiness-docs-typo]
paths  = ["sunmoonai/docs/ai-dev-readiness/**/*.md"]   # 机械判：完工 diff 的文件集 ⊆ paths
gates  = ["gates/doc-gate", "gates/link-check"]        # 必须通过的门禁，机械判
covers = "仅改 readiness 文档的笔误与链接"              # 人读；签策略时所有者签的就是这句话
```

T0 工单的验收条**只能是一个包名**，不得自拼门禁子集。理由：扁平的门禁列表加任意子集
会被「合法零件架空意图」——「修登录失败」配上 `[lint, doc-gate]`，脚本全绿而意图为空。

**包纪律，加在包定义上，由脚本在策略签名前校验：**

> 任何 T0 包的 `paths` 展开集**不得覆盖**权威层文件（内核、协议、约束册、门禁脚本本身）、
> 策略目录、以及各门禁的依赖文件。否则「改门禁」与「被门禁判」落在**同一个可写面**，
> `diff ⊆ paths` 照样成立。

早先一版写 `docs/**/*.md`，把约束册和协议全包了进去，`covers` 是人读的、不参与机械判，
**等于没挡**。**宽包不许，多个窄包可以。**

**两道门，不是一道**——这是最容易漏的一处：

| 何时 | 查什么 | 失败则 |
| --- | --- | --- |
| **开工门**（分发时） | 包名 ∈ 已签策略；路由决定已落账 | 拒发 |
| **完工门**（发布前） | 实际 diff 的文件集 ⊆ `paths`；`gates` 全过 | 不进发布，不判确认 |

把 `diff ⊆ paths` 绑在分发时是错的：**分发时还没有 diff，空集 ⊆ 任何 paths 恒真**。
这条检查会稳定地报「通过」，正是 §3.4「判据自身的质量」点名的形态。

两条配套：

- **不做** `covers` 与复述的字面匹配——自然语言的包含关系判不了，
  硬判会得到一个看起来在工作、实际在猜的检查；
- 跨包的题目**升档，不塞进宽包**。T0 的诚实定义由此是：
  「题目能被『改动限于路径 X、通过门禁 Y』完全表达」；表达不了的就不是 T0。

于是 T0 的 H1 在**策略签名时一次完成**，不是被默认掉：所有者签的是
「这类题目用这组门禁就够」，不是一张可任意挑选的零件清单。
包的增删改按 T2 走（改策略本就是 T2）。

代价是 **T0 的口径变窄**。这是正确方向：不能机械验收的东西本来就不该全自动。

⚠ T0 的承诺**只是「开工前零触点」**，它仍然是「做 → 独立验收 → 确认」，
发布仍要人签。「可逆、不写共享最终路径、免签发布」是另一条权力表行，属省事方向，
未加，登记在 §6.1。

⚠ **一条不能外推的边界**：开发的验收**机械且便宜**（测试、门禁、diff），
财务分析的验收**判断且昂贵**。`dev.change` 只证明对象形状与状态转换跑得通；
验收机制对「判断且昂贵」那一半不能从它外推。

#### 2.2.3 产物 → 状态机：每个内核状态都有落点

这张表是「**没有新词、没有内核之外的边**」这句话的证据。左边是流程里真实发生的事，
右边是它落在唯一状态机的哪条边上——对不上的地方就是设计还没想清楚的地方。

| 发生了什么 | Task | Attempt |
| --- | --- | --- |
| 工单文件出现 | `RECEIVED` → 即刻 `VALIDATING` | — |
| 工单 `DRAFT` / `FROZEN` | 停在 `VALIDATING` | — |
| router 要问人 | `VALIDATING → WAITING(INPUT)` → 回 `VALIDATING` | — |
| **H1** 冻结题目 | `WAITING(APPROVAL) → VALIDATING` | — |
| **H2** 开工确认 | `VALIDATING → QUEUED` | — |
| 派发 | `QUEUED → RUNNING` | `CREATED → RUNNING` |
| 某家交付 | 仍 `RUNNING` | `RUNNING → COMPLETED`（**不等于 Task 成功**） |
| 某家逾期 | 仍 `RUNNING` | `FAILED(timeout)` |
| 某家用尽预算 | `→ WAITING(APPROVAL)`（H4）或重新 `QUEUED` | `BUDGET_EXCEEDED` |
| 执行期澄清 | `RUNNING → WAITING(INPUT) → QUEUED → RUNNING` | 在跑的 → `WAITING` |
| 后面的环节退回前面 | 仍 `RUNNING` | **新 Attempt；旧的终态不重开** |
| **H5** 待人确认 | `RUNNING → WAITING(APPROVAL)` | — |
| 人确认成立 | `WAITING → QUEUED` | publisher `CREATED` |
| 发布 | `RUNNING → SUCCEEDED` | publisher `COMPLETED` |
| 没有获准的成功路径 | `RUNNING → FAILED` | — |
| 候选被取代 / 过期 | — | — |

**最后两行是重点**：候选的 `STALE` / `SUPERSEDED` 和工单的 `DRAFT` / `FROZEN` 一样，
都是 **Artifact 的状态，不是 Task 或 Attempt 的状态**。混进状态机就会多出一批
既不属于任务也不属于执行的僵尸状态词。

**合法转换全集**（任何设计的边都必须 ⊆ 这个集合）：

```text
RECEIVED    → VALIDATING | CANCELLED
VALIDATING  → QUEUED | WAITING | REJECTED | CANCELLED
QUEUED      → RUNNING | WAITING | FAILED | CANCELLED
RUNNING     → QUEUED | WAITING | SUCCEEDED | FAILED | CANCELLED
WAITING     → VALIDATING | QUEUED | FAILED | CANCELLED
```

### 2.3 执行者：Agent Profile

五家助手各是一个 Agent Profile。**人不在这张表里**（§2.6）。

| Agent Profile | harness | 怎么调 | 可观测粒度 |
| --- | --- | --- | --- |
| `ap.luna` | `codex-cli` | `codex exec` | `process` |
| `ap.kimi` | `codex-cli` | `codex exec` | `process` |
| `ap.cursor` | `cursor-agent` | `agent -p` | `process` |
| `ap.fable` | `cursor-app` | **无命令行入口，人手工投喂** | `fs-only` |
| `ap.qwen` | `qoder` | `qoder -p` | `process` |

**登记表要能装下「存在但不可自动分发」的执行者**：`dispatch = argv | manual`。
`manual` 的执行者，人代行的那次传输记为 `dispatch_event`——
**它不是权力，是欠账；但必须可数**，因为成本核算要数它（§4.3）。

**执行者的身份只能来自它工作区的目录名。**产品名、模型名、界面长什么样，
**一律不是身份证据**。这条来自一次真实事故：某家的身份判别命令在仓外一层执行，
`git rev-parse` 退 128 而管道吞掉了错误，`basename` 对着报错文本输出一串 `.`；
该执行者于是退回文本推理，读到工单里「X = 某某 CLI，Y = 某某应用」的产品对照，
推出「我跑在那个产品里 → 我是 Y」，并宣告正在把候选写进另一家的工作区。

两条结论：**判别命令必须响亮地失败**（`git rev-parse --show-toplevel 2>/dev/null`
取不到就报错退出，不许输出一个不匹配的名字）；**工单里不要写产品映射表**——
它本身会成为误判身份的凭据。

**「登记集合」与「自动路由候选集」是两个集合。**前者记「这个执行者存在」，
后者记「router 可以选中它」。无命令行入口的执行者，**要么**经显式桥接
（产生可审计的派发记录），**要么**退出自动路由候选集——
**不得靠不可见的手工粘贴冒充自动分发**。退出候选集的仍留在登记表里。

### 2.4 可观测粒度：三个字段，四档

**这是全文最重要的一节**，因为它决定下一节（证据算不算数）。

早期设计把三件事绑成一列，它们其实可以分开取值：

| 字段 | 取值 | 问的是 |
| --- | --- | --- |
| `observability` | `tool.enforced` ＞ `tool.reported` ＞ `process` ＞ `fs-only` | 运行时**能看见**多细 |
| `enforcement` | `tool-level` / `outer-only` | 运行时**能拦**在哪 |
| `sandbox` | `runtime` / `self` / `none` | 沙箱**谁提供**、策略谁定 |

**必须分开的理由是一个实例**：`codex exec --json` 会把每次命令执行、每次文件修改逐条吐 JSONL
（`~/repo/codex/codex-rs/exec/src/cli.rs:60`）——**看得见到工具调用级**；
但吐的是执行者**自报**，运行时既拦不住（拦截点在它进程内）也验不了。
所以它是 `tool.reported`：比 `process` 细，**但不是证据**。

四档的含义：

| 档 | 运行时能看见 |
| --- | --- |
| `tool.enforced` | 每次工具调用**经运行时的网关**发生并被记录 |
| `tool.reported` | 执行者**自报**的工具级事件流 |
| `process` | argv、stdin/stdout、退出码、事后的文件系统差异 |
| `fs-only` | 只有文件系统前后差异（没有进程句柄，就没有 stdio） |

**当前五家全是 `outer-only` + `self`，没有一家是 `tool.enforced`。**
那个取值要等运行时自己的 agent 建成才会出现。

### 2.5 证据等级：能看多细，决定能不能信

采信等级 = `min(来源等级, 可见上限, 隔离强度, 验收独立性, 覆盖范围)`，
**任一未知即降级，不取平均**。

| 等级 | 来源 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| `E0` | 执行者或人的自述 | 只是一条待验证的**主张** | 行为发生过、作者是谁 |
| `E1` | 运行时从冻结的工作区**重算**（diff、哈希、复跑测试） | 重算范围内的结果 | 进程内部没留痕的动作 |
| `E2` | 外层记录 argv / 输出 / 退出码，加 E1 | 调了哪个进程、外部结果如何 | 内部逐次工具调用 |
| `E3` | 运行时自己的工具网关逐次记录，加 E1 | 经网关发生的调用与策略检查 | 绕过网关的系统调用 |
| `E4` | **执行者凭据域之外**的受保护日志、签名、审计接口 | 指定主体或外部副作用的权威事实 | 人是否真的看懂了 |

四条推论：

1. **`process` 及更粗的执行者，自报一律不采信。**「我跑了测试」「我核过源码」是**主张**。
   证据必须由运行时从工作区**重新推导**：diff、复跑命令、独立取证。
   *反面实例*：有一家拿**休眠代码**（生产引用数为 0）当能力证据，九份评审无一发现。
2. **只有 `tool.enforced` 的事件是证据。**`tool.reported` 的事件流是**索引**——
   可据它决定去重新推导什么，不能据它下结论。
3. **`RUNNING` 判不了，原因不在账本。**缺交付可能是「未调用 / 在跑 / 崩了 / 失联 / 超时」五选一。
   换成数据库一样判不了**进程内部**——这是执行者属性，不是账本载体缺陷。
4. **覆盖声明必须同时列「查了什么」和「没查什么」。**
   零命中只有在输入集合可枚举且枚举成功时才是证据；否则结论是 `UNKNOWN`，**不是通过**。

### 2.6 人：principal 与八条权力

#### 人不是执行者

早期设计把人和 agent 一起登记在「执行者表」里，理由是分发脚本不必特殊处理人。
**那是挂错了对象**，两条证据：

- 在「产物 → 状态机」的映射里，**人一次都没有出现在 Attempt 那一侧**。
  人出现的位置全是等待批准的边上——那是**转换边上的门**，不是跑 Attempt 的东西。
- 早期文档自己列的「人的四点差异」，四条落点是批准权、裁量、最终责任、跨会话——
  **没有一条是关于「执行」的**。

**挂错了会怎样**：权限跟着挂错。你会写出「人这个执行者有批准权」——
将来 agent 要代表人做决定时（产品里必然发生），这个模型装不下。

**人产出的内容怎么进系统**：从 Interaction 的响应侧进，或人自己写一个 Artifact 版本
（作者是人），不从 Attempt 出来。人有两个位置，都在 Task 的边上：
**requester**（创建 Task）与 **principal**（在受门的边上响应）。

#### 权力表

**权力表必须驱动流程，而不是被人记得读。**旧文档把「只有有权主体能做」的动作
散在一千多行流程叙述里，另一份文档又抄了一遍——那样的权力表是第二份说明书，
不是机制。这里的每一行都绑一条**状态转换**：orchestrator 走到那条边上时查表、停下、
产生问询，**不查表就走不过去**。

每一条都对应唯一状态机的**一条边**，且都有一个 agent 够不着的**强制点**：

| 行 | 人做什么 | 状态转换 | 强制点 |
| --- | --- | --- | --- |
| **H1** | 冻结题目与验收标准 | 工单 `DRAFT → FROZEN`；Task `WAITING → VALIDATING` | 所有者的动作本身 |
| **H2** | 开工确认（路由、名单、工作区） | `VALIDATING → QUEUED` | orchestrator 不分发 |
| **H3** | 省事方向的裁定生效 | `WAITING → QUEUED` | 无记录的裁定视同不存在 |
| **H4** | 扩权（追加预算或范围） | 同上，或 `→ FAILED` | 同上 |
| **H5** | **不可逆动作**：写共享最终路径 | `RUNNING → SUCCEEDED` 的门 | 所有者亲自执行 |
| **H6** | 推翻已生效的裁定、改已冻结的标准 | `WAITING → QUEUED` | 冻结区逐字节校验 |
| **H7** | 取消 | 非终态 `→ CANCELLED` | 失败安全方向 |
| **H8** | 回答问询 | 验证期 `WAITING → VALIDATING`；执行期见 §2.7 | 见 §2.7 |

**H7 取消要附一份「已产生的副作用清单」。**取消本身是失败安全方向、不锚在仓外，
所以它是表里最容易被误触或伪造的一行；代价不在取消本身，在**恢复**——
不知道已经产生了哪些副作用，就不知道要回滚什么。清单的格式固定，缺清单的取消不生效。

**八行里只有一行允许默认**：H2，且只在最轻档位 + router 出 `decide` 时。
其余七行 `auto_policy = 无`——**没人回就等着**，不设超时通过。
把「无默认」写进表，是为了让「给某一行加默认」变成一次需要人确认的改动（朝省事方向）。

三条纪律：

- **H5 批准的是执行动作，不是终态。**内核里**没有** `WAITING → SUCCEEDED` 这条边。
- **H1 属验证阶段**，恢复边是回 `VALIDATING`，不是 `QUEUED`。
- **改授权范围不算「改方案」**，那要建新 Task（内核「终态、刷新与重新处理」）。

#### 推翻一件已经做完的事，落点是新 Task，不是问询

一个 Task 到了终态就**不可转出**。所以「上一轮的结论我不认了」在内核里的正确落点是：
**建一个新 Task，标 `supersedes = <旧 Task>`**，而不是往旧 Task 上挂一个 Interaction。

这不是形式主义。旧 Task 的验收已经通过、产物已经发布，往它身上再挂问询，
等于让一件已经结账的事重新变成未结账——账本会失去「什么时候算完成」的定义。
本项目的 `runtime` 轮就是这么开的：所有者推翻了上一轮的四条结论，
落成的是一个新 Task 而不是对旧 Task 的修订。

#### 无默认的字段不得预填

| 分级 | 字段 | 规则 |
| --- | --- | --- |
| **无默认，必须显式填** | 验收条、参与方名单、档位 | 问询里留空 |
| 可预填默认 | 工作区计划、预算窗、观察窗规则 | 预填值与人改后的值**都落账**，改动幅度是观察值 |

理由：**预填等于把盖章做成阻力最小的那条路**。引擎要是把验收条替你填好，
你点一下「同意」——你其实什么都没决定。

**人的回执只认落盘**：对话里说「同意」不算。**人不回执时不设超时默认**——
最后一道关卡不能因为没人回就自动通过。

收件箱的每条必备四个字段，**缺任一个就是无效条目，脚本机械判**：

| 字段 | 是什么 |
| --- | --- |
| `interaction_id` | 这次问询的编号 |
| `transition` | 要决定的是哪条状态转换 |
| 待决内容 | 具体要你定什么，以及各选项的后果 |
| 截止判据 | 什么条件下这条算过期（**不是时钟，是判据**） |

凡会产生正式回执的条目，另加 `target_commit` 与 `diff_stat`——
**人要签的是一个具体对象，不是一个说法**。

**通知丢了不要紧，收件箱文件才是真源。**终端提示、桌面通知、将来的 IM，
都只是让人知道有事，不是结果的载体。这与「流式输出不是结果的唯一载体」是同一条。

**每次回执登记三个观察值**：回执耗时、相对预填值的改动项数、每类触点的次数。
汇总给人看趋势，**但不由观测值自动触发任何权力行**——
「触点太多了，自动降档」是把权力做成告警，权力是人的，告警不是。

#### 当前最尖锐的矛盾：这道关卡的证据强度是零

**人的回执，现在证明不了是人做的。**所有者与 agent 同机、同一个 git 身份、没有签名——
账本上分不出哪一笔是人做的。而「人的确认」恰恰是全流程唯一不可逆的一步。

已复核的事实：本机无 GPG 私钥，git 未配 `user.signingkey` / `commit.gpgsign`；
所有者的确认 commit 与 agent 的提交同为一个作者身份、均无签名；
所有者用的两个界面都远程连进同一台机器，人的动作与 agent 的动作**同机器、同身份**。

后果要如实记，不许绕过去说：

- 所有涉及权力的轨迹条目，来源等级只能标 `reported`，直到那个通道换掉；
- 「回执只认落盘」这条规矩**降低了随口同意的概率，但没有提高证据强度**——
  两件事不要混为一谈；
- 因此 §6 的拆脚手架表里，Interaction 那一项有一条硬前置：
  **先有一个 agent 够不着的操作面，再谈换 key**。否则只是在同一个信任域里搬家。

这也是 §1.3 废掉「回执仓 + 三把 key」的原因：那套设计换的是**位置**，
换不动**信任域**。真正要先有的是操作面，不是仓和钥匙。

### 2.7 中断与恢复：用库的原语，不自造协议

**这一节曾经是一整套自定义协议（三值、载荷、schema、过期校验、原子消费），全部作废。**

机制用现成的，投资仓已经在跑：

```python
# 出向 —— app/infrastructure/graph/pilot_graph.py:59
value = interrupt({
    "kind": "confirmation",
    "action_id": action_id,
    "prompt": "确认使用这些检索证据生成最终回答？",
})

# 入向 —— scripts/*.py
Command(resume="approved")

# 恢复 —— app/application/agent/graph_runtime_service.py:40-46
#   同一个 thread_id + 检查点 → 节点原地继续，不换执行
```

三件事一次性解决：

| 曾经自造的 | 现成的 |
| --- | --- |
| 出向六字段表 | `interrupt()` 收**任意 dict**——展示哪个版本、几级证据、有哪些选项，加键即可 |
| 入向三值 + 载荷 + schema + mode + 过期校验 | `Command(resume=<任意值>)`，**一个参数** |
| Task 级暂停 → 换新 Attempt | 检查点**原地恢复**，同一次执行接着往下跑 |

**本文不重定义它的签名。**我们要定的只有下面四件，库一件也替不了：

| | 我们定 |
| --- | --- |
| **什么条件下必须中断问人** | 权力表八行（§2.6） |
| **给人看什么才算问清楚** | 展示哪个 Artifact 的哪个版本、它是几级证据（§2.5）、有哪些选项 |
| **什么算批准** | 落盘；不设超时默认；无记录视同不存在 |
| **人否决之后走哪条路** | 见下 |

**人否决后的两条路**，取决于**下一版谁写**：

| 场景 | 做法 |
| --- | --- |
| 人说哪里不对，**agent 重做** | 恢复值带上反馈 → **同一次执行原地继续** |
| 人**自己写**下一版 | 人写一个 Artifact 版本（作者 = 人）→ 批准指向它 → 下一个 Attempt 的输入钉它 |

⚠ 实测：至今 **12 次真实裁决全部是第一种**，第二种一次都没发生过。

**不是每次问询都要背一个产物。**按问询的类型分层，否则「问一个缺失的参数」
也要挂上 Artifact 版本、证据等级、可改范围——那会让最轻的问询变成最重的动作，
而内核的规矩本来是「只有歧义实质改变结果 / 权限 / 成本 / 风险时才问」：

| 问询类型 | 出向要带什么 | 人能回什么 |
| --- | --- | --- |
| **要人批准一个产物** | 产物版本、证据等级、可改范围、选项 | 同意 / 否决 / 给出改法 |
| **只是补一个缺失参数** | 一段人读的问题 | 答复 / 拒答 |
| 依赖、资源、外部事件 | 现行字段不变 | 现行语义不变 |

⚠ 这个形状**不是开发期特有的**：财务分析 agent 交出一份计划给人审，
人改两条数据源、计划出新版本（作者 = 人），下一次执行照新版本跑——
形状完全一样。所以这里定的东西将来不用重定。

### 2.8 工作区供给

```text
provision(task_id, source, baseline_commit, write_actors, review_needed) →

  前置判据（任一不成立即新建，不复用）：
    现有工作区归属 == 本 task 且 == 该执行者      # 独占
    git status --porcelain 为空                   # 干净
    HEAD == baseline_commit                       # 基线一致

  数量规则：
    写者 0 个 → 不建可写工作区
    写者 1 个 → 一个独占工作区、一条命名分支
    写者 N 个 → 同一基线上 N 个 worktree、N 条命名分支 + 一个整合 worktree
    需要人读 → 额外一个检视 worktree，用完删
```

三条判断：

- **worktree 的数量看写者数，要不要新建看独占与干净**，两者都不看复杂度——三者都可机械判定，复杂度不可。
- **「事先创建好的仓库」只能是来源，不能是工作区。**
- **来源一律钉 commit，不钉地址或分支。**只固定分支名 → 评审对象漂移。

两个补充参数：**多仓任务**逐仓钉 commit 并记父仓 gitlink；
**遇到人的未提交改动**时绕开、新建，**不要 `stash`**——那是动别人的东西。

#### 工作区形态决定执行者能不能自己落账（2026-09-07 实测）

**沙箱按目录划边界，而 git 把仓和工作树分开——两者一撞，执行者就写得出产物、提不了交。**

实测三步，结论全部来自实跑：

| 试的 | 结果 |
| --- | --- |
| `git worktree` + 沙箱只给工作区 | ❌ 提交要写主仓 `.git/worktrees/…` 与共用的 `objects/`、`refs/`，都在工作区外 |
| **独立 clone** + 沙箱只给工作区 | ❌ **仍然不行**——该沙箱**按设计把 `.git` 挂只读**，与仓的布局无关 |
| **独立 clone + 显式把它自己的 `.git` 加进可写根** | ✅ 通过 |

所以**不是二选一，是两半必须凑齐**：clone 让 `.git` 变成这家私有的，
放行可写根让它能写。**顺序不能反**——先放行再用 worktree，等于放行**共用**的 `.git`，
那里放着所有家的分支引用，一家可写就是每家能改别家的 refs，
与 §2.9「强制点必须在 agent 的凭据域之外」直接冲突。

⚠ 这只解决**能不能自动化**，**不解决谁签的**：clone 在本机，`author` 字段可随意填。
§2.6「这道关卡的证据强度是零」不因此改动一个字。

⚠ 第二行是**被实验推翻的一个判断**：先前据「仓与工作区拆开」推出「独立 clone 就能解」，
实验直接证伪。**留着这一行，是因为不留它，下一个人会照同样的推理再走一遍。**

⚠ **「独占」在命令行/GUI 执行者上是约定，不是隔离。**
运行时在宿主建个目录、把路径告诉进程，而那个进程**看得见整个文件系统**。
登记字段 `workspace_isolation = enforced | convention`，**当前六家全是 `convention`**。

两则现场证据：

- 有一份候选在自己的 worktree 起草，却读了 `~/repo/codex`、`/tmp` 与其他 worktree；
- 同一执行者同一会话内 `id` 先报 `uid=0(root)` 后报 `uid=1003`——
  **身份切换发生在它自带的沙箱里，运行时看不见，也没批准过任何策略。**

由此有一条必须提前写下的边界，因为它决定将来能不能接真实数据：

> `convention` 级的执行者，其授权范围声明只能依赖**事后审计能发现越权读取**，
> 不能依赖「事中读不到」。**在接入第二个租户或真实业务数据之前，
> 这类执行者的数据源必须经运行时的数据网关，不得给裸库凭据。**

这条现在没有代价（本项目只有文档任务、单租户），正因如此才要现在写——
等有代价的时候再想起来，通常已经给出去了。

### 2.9 边界：哪些强制点是真的

#### 一条实测结论

本机跑 agent 的用户拥有**免密 sudo**（`(ALL) NOPASSWD: ALL`）且在 **docker 组**。
两者各自独立地把 agent 提权到 root。由此：

| 强制点放在哪 | 对 agent 有效吗 |
| --- | --- |
| **托管方**的 key 作用域、分支保护、账户端点 | **✅ 有效**——在 agent 够不着的地方 |
| 本机的脚本、hook、门禁 | ❌ 无效——`sudo` 一句就改了 |
| 本机的文件权限、只读挂载 | ❌ 无效——同上 |

**这把「强制点必须在 agent 的凭据域之外」从设计判断变成了实证。**

#### 但当前不需要建任何边界

原因是**要拦的动作不经过它们**：

```
agent      只在自己 worktree 里写，从不 push（git ls-remote 可验）
发布       是本地 merge，不经网络
真源       就在本机；远端连冻结标签都没有
```

所以曾经设计的回执仓、候选仓、三把 key **全部作废**（§1.3 第 3–6 条）。
**授权本身就是批准**：给不给它凭据，这件事已经完成了批准；
在它之上再造一层「证明批准发生过」的协议，是给一个已完成的动作补收条。

#### 真正的风险不是伪造，是只有一份

三轮流程、全部归档、九个冻结标签，**只存在于一台机器上**。
最高价值的一条动作成本几乎为零：把产出推到远端。

#### 什么时候边界才需要建

三条触发，一条都还没发生：

1. orchestrator 变成服务、**发布不再经人手**——那时凭据在机器里，边界才有对象；
2. 出现**第二个 principal**——那时才需要区分「谁批的」；
3. 出现**外部审计要求**（如财务合规）——那时才需要给第三方看的不可否认记录。

到那时是**重新设计**，不是把旧那套拿出来用——旧那套的前提当时也没验过。

#### 但威胁模型要留着，因为它是对的

作废的是那套**机制**，不是对威胁的判断。等上面三条触发之一发生时，
不要从零想，从这里接着想：

**攻击者不是恶意的。**它是一个**与人共享同一凭据域、会流畅执行任何命令、不会犹豫**的
agent 进程。要防的不是「它想害你」，是「**它顺手替你做了**」。

要防的是三件不同的事，早先只写了第一件：

1. **伪造一条肯定的批准**——伪造否定的没有意义，流程只会停下来等，不危险；
2. **绕过批准直接产生不可逆动作**——有没有批准是一回事，**没批准能不能写出去是另一回事**，
   这两件必须分开设强制点；
3. **批准动作被人自己机器上的 agent 代做**——人的工作站上同样跑着以人的账户运行的 agent，
   凭据管理器要是缓存了推送凭据，它不需要口令就能推。

由此一条通用结论，与载体无关：

> **本机上的任何本地验证都不是边界**——验签、读公钥文件、跑判定脚本、pre-push hook。
> agent 能生成新钥、把公钥加进任何本地信任列表、改掉验证脚本或 hook，再签一条。
> 「本地判定通过」只能当**便利的参考显示**，不得作为任何「无默认」权力行的强制点。

现状里还有两条与此相关的事实：本机**没有任何签名私钥**，已有标签全部未签名
（从零设计，没有兼容包袱）；本机的 ssh key 对主仓**有写权限**——
也就是说「绕过批准直接写出去」这件事在今天是**做得到**的，
只是当前没人做，且真源就在本机、发布不经网络（上一段），所以它现在不构成风险。
**这句话的两半都要读**：不是「防住了」，是「还没有对象」。

#### 取证纪律：取证工具自己也有边界

上面那张表能立住，是因为它是**实测**的。但取证本身出过一次错，形状值得记：

早先一版写「本 VM 所有进程都是 root、`/home/zym` 属 `root:root`」——**是错的**。
两家在同一台机器复核得到 `uid=1003(zym)`。错因查明：起草者在一个带沙箱的界面里执行取证命令，
`cat /proc/self/uid_map` 输出 `0 1003 1`——沙箱用 user namespace 把宿主 uid 1003 映射成了 0，
**于是沙箱内一切看起来都是 root**。取证工具自身有边界而没有声明，正是「判据自身的质量」禁止的事。

由此三条：

1. 取证的每一条注明**主机、执行身份、是否在沙箱或容器内**（`hostname; id; cat /proc/self/uid_map`）；
2. 权限测试必须以**与生产 agent 完全相同的 OS 用户与进程环境**复跑，不在任何沙箱内；
3. 边界的表述写成「**agent 与人是否共享同一个凭据域**」，
   不要绑定「是不是 root」这个偶然事实——换台机器那个事实就变了，而结论不该跟着变。

⚠ 与之配套的 `scripts/check-no-owner-creds.sh`（查 VM 上有没有混进所有者的凭据）
**是配置卫生检查，不是边界**：agent 能改它。它防的是人为疏漏，不防对抗。
文件头写着这句话，改它的人先读到。

### 2.10 角色：五个各有定义的词

「supervisor」这个词在旧文档里同时指四件事，解开后是五个：

| 词 | 是什么 | 开发里的实体 | 产品里的实体 |
| --- | --- | --- | --- |
| **router** | **确定性代码**：算出档位、执行者、工作区计划 | 规则表 + 分发脚本的选人逻辑 | TaskRouter |
| **orchestrator** | **确定性代码**：推进状态、写环节通知、派发、观测逾期、收集迟到结果、触发回退、供给与回收工作区 | 状态脚本 + 分发脚本 + 过渡期运行它们的人 | 调度监督器 |
| **arbiter** | **agent 角色**：定基座、逐条吸收、写处置记录、处置异议 | 工单里 `arbiter` 字段指向的执行者 | 执行监督 Agent 的选优整合部分 |
| **acceptor** | **agent 角色**：按冻结判据独立验收 | 由处置表算出的一家（§3.4） | validator |
| **approver** | **principal**：持有权力表某行的批准权 | `owner` | 有权用户 / 授权角色 |

**两条硬约束**：

- **router 与 orchestrator 必须是代码，不得是 agent 角色。**
  把 orchestrator 写成 agent，就长出第五个同名物。
  过渡期由人运行脚本，那是「**可自动**」的欠账，**不是角色**。
- **arbiter 不兼 orchestrator。**环节通知与截止由脚本按工单生成，
  arbiter 只写裁决与处置——否则整合权与流程控制权合一，④ 异议那道制衡就形同虚设。

⚠ 登记表里 `roles_allowed` 由表约束，**不由每轮口头指定**——
分发前对照它与「角色分离」禁令，冲突即拒绝并给出原因。

#### 为什么一直在长同名物

这个词曾经有三套同名物，第三套还带一个从没定义过职责边界、只借了名字的别名。
**每加一层就加一个名字，说明抽象层级选错了。**

真正稳定的概念不是「谁监督谁」——那是组织图，会随着谁来做而变。稳定的是：

> **这个状态转换由谁执行、需要什么权力、在哪里强制。**

三问都有答案时，叫它什么都行；三问没答案时，起一个好听的名字只是把问题藏起来。
上表那五个词之所以能立住，是因为每一个都能回答这三问；
「supervisor」立不住，是因为它一个都答不上来。

## 3. 流程：一轮怎么走

### 3.1 档位：这件事该走多重的流程

**不是每件事都值得走完整轮。**完整轮是 N 倍成本；但用轻了，代价是不可逆的错误被推到底。

| 档 | 形态 | 角色 | 典型场景 |
| --- | --- | --- | --- |
| **T0 直做** | 一个执行者做完，无候选、无互评 | 执行者 + **独立验收者** | 可逆、单点、方向无争议 |
| **T1 单稿 + 独立评审** | 一家出稿，另一家按冻结判据评审并验收 | 出稿方 / 评审方 / 人（若不可逆） | 影响面跨多文件，但方向无争议 |
| **T2 完整并行轮** | 七个环节全走 | 提案 N / 评优 N / 裁决 / 异议 / 验收 / 确认 | 见下 |

**命中任一条即 T2**：

| 判据 | 说明 |
| --- | --- |
| **不可逆** | 产物一旦发布，改判代价高：对外契约、编号体系、数据迁移、**流程本身** |
| **权威层** | 会成为其他文档或代码的依据 |
| **已知对立** | 开工前就存在两个及以上互不相容的主张 |
| **判据未定** | 连「什么算做对」都还没共识 |

⚠ **一个已登记未解决的问题**：「权威层」几乎覆盖 `dev-plan/` 全部文件，
按字面，改一处锚点形式也要开完整轮——不成比例。
**实务上按「问题是否欠定」判**：答案确定、机械可判的，即使在权威层也不必开轮；
但**降档必须写明理由并经人确认**（§3.3）。

**裁定要留痕**：写进工单的档位字段，附一句理由与命中的判据。T0 不必建轮次目录，
但**裁定要记在任务条目里**——记在对话里不算。

### 3.2 任何档位都不能省的三条

档位调节的是**并行度与环节数**，不是**判据**。省掉任何一条，「轻流程」就变成「无流程」：

1. **验收判据先于产出冻结。做完再定标准等于自证。**
2. **产出方 ≠ 验收方。**出题方与答题方是同一个，验收就不是独立信号。
3. **不可逆动作由人确认。**这一条与档位无关，只与动作性质有关。

⚠ 2026-09-05 有过一次实例：执行者对已发布产物连改四次，第 1、2 条**各破 4 次**，
第 3 条守住 4 次。补救过程本身又漏掉两节内容——**由独立验收方抓出**。
这恰好证明第 2 条不是形式主义。

### 3.3 裁量权与方向不对称

#### 不可裁量的下限

以下几条任何时候都不能由 agent 单方决定：

1. **验收判据先于产出冻结**，冻结后不得为让产出通过而修改；
2. **产出方 ≠ 验收方**；
3. **不可逆动作由人确认**；
4. **降档必须人确认**；
5. **未记录的裁定无效**——记在对话里不算，必须落盘；
6. **设计任何机制之前，先用命令确认它要处理的动作现在实际怎么发生**（§1.3 立）。

#### 方向不对称

> **朝严谨可以自裁，朝省事必须人确认。**

**中途只能升档，不能降档。**开工后发现分歧或触及不可逆，随时升；
已经在跑的重流程**不得因为嫌慢而降档**。

#### 裁量是规则的孵化器

一次性的判断记为裁定；**同类问题再现，就该升级成规则**。
本项目当前有三条已达再现门槛、待升级为正式纪律的（见 §5.2、§5.3）。

### 3.4 七个环节（T2 专用）

| 环节 | 谁 | 产物 | 要点 |
| --- | --- | --- | --- |
| **① 提案** | 各提案方并行 | 候选，落在**共享最终路径的同名文件** | 期间**隔离**：不得读他家候选、不得写他家 worktree |
| **② 互评** | 各提案方 | 评审 | 隔离解除；**必须评自己那份**，可以排第一但依据强度要一致 |
| **③ 裁决** | 裁决方 | 裁决稿 + **处置记录** | **票数不是依据**；理由必须是可复核的差异 |
| **④ 异议** | 被处置到的各家 | 异议稿 | 对整合权的**唯一制衡**：只有原作者知道自己原本想说什么 |
| **⑤ 验收** | 验收方（**算出来的**） | 验收稿 | 只能按冻结判据判，不得为通过而改判据 |
| **⑥ 确认** | **人** | — | 全流程**唯一不可逆**的一步，不得由固定指令推进，不得由 agent 代行 |
| **⑦ 清理与发布** | 裁决方 + 人 | 最终稿 | 顺序：人确认 → 清理各分支产物 → 写入共享最终路径 |

**验收方由处置记录算出，不由裁决方指定**，规则依次适用：

1. 不得是裁决方；2. 不得是基座作者；
3. 在剩下的家里取处置表中「接受 + 部分接受」条数**最少**的一家——它对结果的既得利益最小；
4. 并列时取候选行数最少者；5. 都不可用时由人验收。

**名次与验收资格无关**，判据是既得利益不是质量。
⚠ 实例：某轮评优五家一致排末位的一家成为验收方，而它交出了全轮最严格的验收——
它自建独立沙箱、造 10 个用例复核了裁决方写的门禁脚本。

### 3.5 产物、路径与命名

| 环节 | 产物 | 落点 |
| --- | --- | --- |
| ① | 候选 | 自己 worktree 的**共享最终路径同名文件** |
| ② | 评审 | `rounds/<轮次>/review-<名>.md` |
| ③ | 裁决稿 + 处置记录 | 裁决稿在共享最终路径；处置记录在轮次目录 |
| ④ | 异议稿 | `rounds/<轮次>/objection-<名>.md` |
| ⑤ | 验收稿 | `rounds/<轮次>/acceptance-<名>.md` |
| 每个环节开始时 | **环节通知** | `rounds/<轮次>/call-<环节>.md` |
| 任何时候 | **裁定记录** | `rounds/<轮次>/rulings.md` |

**候选用与主线一致的路径和文件名**：一条 `git diff` 就能看清每家改了什么。

**其余产物一律 `<环节>-<名>.md`，不得自创文件名。**
*事故*：某轮四家里三家用一个文件名、一家用了别的，评审方按精确文件名枚举，
**漏掉一份候选，整轮评分作废重做**。

#### 环节通知：组织者的产物，不是发起人的话术

**每个环节由一份落盘的通知开启。**通知必须自足，含四样：

| 必含 | 说明 |
| --- | --- |
| 取件命令 | 本环节要读的对象怎么取，**含分支与 commit** |
| 对象事实 | 行数、SHA-256、HEAD，供读者证明自己读的是同一版 |
| 范围与门槛 | 这一环节允许做什么、什么不受理 |
| 交付路径 | 产物写到哪、叫什么 |

**从 ④ 起，通知把各家各自被怎么处置公开写在同一份里**——公开让处置可被交叉检验。

⚠ **产物一旦随环节通知发布，本环节内不得再改。**必须改则重发通知并更新对象事实表。
*两次实例*：① 期间改动了各家正在引用的裁定记录；④ 通知发出后又改了处置记录，
使通知里钉的哈希失配，而各家手里是旧版。

### 3.6 取件与检视面

**一个流程如果没规定产物怎么被读到，它只完成了一半。**

```bash
git show <分支>:<路径>                       # 取某家某个产物
git diff <基座commit> <裁决分支> -- <路径>    # 看裁决方改了什么
git log --oneline master..<裁决分支>          # 看逐条主张
```

**工作区文件会变，提交不会。**任何环节引用他人产物，都要同时给出分支与 commit。

**跨分支产物不得写成 markdown 链接**——门禁按当前分支的索引判定，链到别的分支必然失败。
写成 `<分支>:<路径>` 的纯文本即可。

#### 检视面：需要人读时开临时 worktree

```bash
git worktree add --detach ~/review/<名> <commit>   # 开，钉在 commit 上不随后续提交漂移
git worktree remove ~/review/<名>                  # 用完删
```

**⑥ 确认尤其如此**：裁决方在请求确认前**必须已经把检视面开好并给出路径**，
「稿子在我分支上」不构成可确认状态。

### 3.7 环节判定与判据自身的质量

**判据即命令，结论只依赖 git 提交；工作区文件不参与判定。**

#### 判据自身的质量：覆盖不全比没有更危险

> **一个覆盖不全的检查，比没有检查更危险——因为它会报「通过」。**

这不是理论。**本项目已经发生七次**（§5.2 有完整清单）。由此三条：

1. **每个判据必须能表达第三态「不可判」**，且 `不可判 ≠ 通过`。布尔判据是缺陷，不是简化。
2. **聚合判据必须显式定义空集合上的取值。**`all(空集)` 为真是数学正确、语义错误。
3. **门禁全绿 ≠ 判据满足。**门禁只代表它查的那些项没问题。
   *实例*：两道文档门禁都看不见「有标题没正文」——空标题不产生锚点，无从判起。

### 3.8 逐环节的规则

**① 提案**：期间隔离。隔离目前**靠纪律不靠机制**（§2.8），如实声明。

**② 互评**：四块——自述（改了什么、分歧、未验证、故意放弃的）、候选集冻结
（列出全部候选的 commit + 行数 + 哈希，缺一份即枚举有漏）、评优（逐份判 + 可复核指摘 + 排序依据）、
值得吸收的点。**必须评自己那份**。

**③ 裁决**：一条主张一个提交；从选定候选的 commit 取基座，不从工作区取；
逐条写明**接受 / 部分接受 / 拒绝**及理由。
处置记录必须含一段**机器可读的处置表**，三列固定：`出处家 | 条目 | 裁定`——**验收方由它算出**。

**④ 异议**：只发给被处置到的家；只能就自己那条主张的处置提异议；
门槛是「处置条目 + 为什么错 + 应当是什么 + **可复跑证据**」，「读起来更好」不受理；
**不是否决权**，裁决方可以驳回但必须逐条给理由，连同异议原文写进处置记录；
**没有异议的家要明确回一句「无异议」**——空回复无法与「还没看」区分。

**⑤ 验收**：只能按冻结判据判，**不得为通过而静默修改判据**。
判某条是「判据本身过期」要**写明理由交裁决方处置，不得自行改**。

**⑥ 确认**：人的显式动作。**人确认前不得写入共享最终路径。**

⚠ 这一环曾经是整条状态机上唯一判不了的洞——状态脚本对它写的是
「人的动作，不可由命令判定」。那与「状态从产物反推、不从声明读取」（P2）直接冲突，
而且**全自动化正好卡在这个洞上**。

解法不是给它加默认，是让**人的确认也成为产物**：

> **内容由人判，落盘由命令判。**人的确认落成裁定表里的一行（「人确认 = 是」），
> 脚本读那一列。确认的**对**不对是人的事，确认**有没有发生**是可判的。

代价要如实说：现在那一行由执行者写在一个执行者可写的文件里，
**证据强度是零**（§2.6）。它解决的是「判不了」，不是「可信」——
两件事分开，别拿前者的进展去充后者。

### 3.9 停止、超时与回退

**没有这一节的流程只会一路向前。**

| 情况 | 处置 |
| --- | --- |
| 某家迟迟不交 | 见下。**不要只说「快点」**——模糊压力下执行者会砍掉它认为最省事的部分（通常是取证与验证），而砍了什么你看不见 |
| ④ 异议被采纳且**触及基座结构** | 回到 ③ 重整合；已做的 ⑤ 作废重做 |
| ⑤ 验收不通过 | 回到 ③；若判定为「判据本身过期」，由人决定改判据还是改产出 |
| ⑥ 人打回 | 回到 ③ |
| **同一轮回退超过两次** | **停下**，判断是题目本身有问题还是判据写错了，不要第三次重整合 |

**回退不是失败，把不合格产物推到底才是。**

**逾期判据不锚时钟，锚可观测的停滞与同侪基准**：观察窗 = 已交付各家用时的中位数。

### 3.10 清理与发布

**顺序是：人确认 → 清理各分支产物 → 写入共享最终路径。**

| 对象 | 处置 |
| --- | --- |
| 各提案方 worktree 的候选 | 删除（**先打标签**，内容可复原） |
| 各家评审、异议、验收稿 | 归档进轮次目录 |
| 处置记录 | 保留 |
| 工单 | 状态改「已完成」 |

**先清理再写入**：候选与最终稿同名同路径，不先清理，各分支后续同步时会把候选态
当成本地修改，产生本可避免的冲突。

### 3.11 验证分层：谁判什么，顺序不可换

| 层 | 谁 | 判什么 | 判据要求 |
| --- | --- | --- | --- |
| **L0 机器门** | pre-commit / CI / 校验脚本 | 全部机械判据：链接、表格、冻结区逐字节、提交与处置记录对账、锚点可达、必须零命中的正则、测试、角色冲突 | **声明覆盖范围**；首跑先与人工对照再当门禁 |
| **L1 独立验收** | acceptor（既得利益最小的一家，由处置表算出） | 冻结的验收判据逐条；机器判不了的部分 | 只能按冻结判据；判「判据过期」要写理由交 arbiter |
| **L2 来源核对** | 被处置到的各家（④ 异议） | **「我的主张有没有被误读」** | 条目 + 为什么错 + 应当是什么 + 可复跑证据 |
| **L3 人抽三样** | approver（不可逆动作之前） | ① 意图是否被正确理解 ② 不可逆的部分 ③ **抽样复算证据真实性** | **不逐行读**；抽样规则写进工单 |

**顺序不可换：L0 不过不进 L1，L1/L2 不过不叫人。**

L3 是「机器全审 + 人抽检三样」——人的注意力是最贵的资源，
把它花在逐行读稿上，等于让 L0/L1/L2 白做。

### 3.12 状态判定与分发脚本的设计要点

**从产物反推、判据即命令、只生成不执行**——这三条是对的，要改的是「一般化」不是「推翻」：

| 现在 | 应改为 | 理由 |
| --- | --- | --- |
| 只认最重档位的七环节 | 按工单档位读取对应的门禁表与必需产物表 | 轻档位也需要判定 |
| 输出「当前环节」 | 同时输出 **Task 状态（唯一状态机的词）+ 当前环节 + 各 Attempt 状态** | P0：环节是投影，状态才是本体 |
| 工单的状态字段是**声明** | 删除，或降为人读缓存并由脚本校验：**推导值 ≠ 声明值即报错** | P2 |
| 只判状态词 | 每次推导同时输出「上一状态 → 本状态」，**边不在内核合法转换表里即失败** | 只查词表抓不到非法边（§5.2 第 3 条同源） |
| 角色由每轮口头指定 | 分发前对照登记表的 `roles_allowed`，冲突即拒绝并给原因 | §2.10 |
| 无法分发的执行者无处理 | 输出给人的投喂说明而非命令，**并记一次 `dispatch_event`** | §2.3 |
| 只看工作仓产物 | 加读 orchestrator 单写的执行事件，区分「已分发 / 在跑 / 超时」 | §2.5 推论 3 |

**每条判定都要声明覆盖范围**（P4）：输出里「查了什么、没查什么」与结论并列；
**「零命中」与「没查到」必须分开写**。

### 3.13 文档的删除条件

**删一份被引用的文档，下列判据全部机械可判之后才能删**：

1. 承接它内容的新文档全部通过文档门禁；
2. **引用清理零命中**——用命令数，不用印象数。
   *实例*：某次估计「5 处」，实际取证是 **13 个文件**；
3. **旧 → 新映射零缺口**（按旧文全部标题逐条对照，脚本判）；
4. 旧文里标 ⚠ 未验证的条目，在新落点逐条可寻且**仍标 ⚠**；
5. **不经 git 历史即可读到**——`git show <commit>:<路径>` 是可复核性，**不是可读性**，
   读的人不会去翻历史。

⚠ 第 5 条是 2026-09-06 补的：曾有一次只验了前四条就删，
把「回执模型、实施路线、工作区供给」等仍在被依赖的内容变成了只有历史里才有。

## 4. 什么时候不该走这套流程

**运行时省的不是「调用助手」的成本，是编排、记忆、留痕、审批的成本。**

### 4.1 机械可判的分类

只看工单字段，**不读题目自然语言**。命中任一条，走流程更便宜：

- 执行者两个及以上；
- 计划中有任何需要人批准的触点；
- 输入带版本锚，或依赖另一件事，或需要跨会话续接；
- **触及权威层路径**（约束册、内核、协议、策略、门禁脚本）——这条是**必须走**，无关便宜；
- 有副作用要记账，或产物要进证据账，或同形状反复跑。

都不命中的，走流程**更贵**。

⚠ **不得用档位反推成本**：档位由不可逆性与权威层判，用它推成本是循环。

### 4.2 三类走流程反而更贵的活

1. **改一个错字**。手工是「说一句 + 提交」两个动作；走流程即使全自动，也要建工单、
   **供给独占工作区**、发布。**贵在供给**：一个不需要隔离的任务被强制隔离。
2. **一次性提问 / 探索性阅读**。它没有产物要落盘，而输出契约必须有落点——
   于是要么造一个没人再读的产物，要么为一个不需要契约的任务形成契约。
   目标未定时更糟：契约固定不了，会在「澄清—改目标—再澄清」间空转。
3. **对不能自动分发的执行者的任何一次派发**。人要先把界面打开在正确的目录、
   跑身份判别、粘指令。**贵在派发与身份核对，与任务大小无关**。

**不接受「都值得走，留痕总是好的」**：留痕成本高于这笔改动的价值时，
留痕不会发生，绕过会发生。

### 4.3 最轻档位的开销上界

**如果最轻的档位走流程比直接干还贵，人就会绕过它；一绕过，账本就有洞；
账本有洞，这套东西存在的理由就没了。**

所以上界要可数，**锚可数物，不锚时钟**：

```
(人的必需动作数, 落盘产物数, 从请求到派发的步骤数, 需要人代传的次数)
      ≤  (      2,          4,              2,              0        )
且 人的必需动作数 ≤ 同一任务直接干的动作数
```

**通知送达或敲命令不算决策，但仍计动作**——防止把传声筒成本藏掉。

### 4.4 绕过看得见吗

**先说限度：绕过发生在流程之外，账本天然看不见。**声称「完全可观测」就是在造假指标。

三层，没有一层承诺全知：

1. **让绕过无利**：写入交付面只经人签的那道门；绕过的最大动机（快）被保留为合法路径（§4.3）；
2. **对账，分母取外部**：拿托管方审计、git 底座去比，找不到对应记录的变更登记为「未归因」，
   **不得反向补造一个正常记录**；
3. **如实声明看不见的**：没提交的改动、纯对话的问答，任何机制都看不见——不为它们造代理指标。
   **零命中只能写成「没查到」，不能写成「没有绕过」。**

第 2 层的分母**必须取外部 sink**，不能取运行时自己看见的事件——拿自己的账本当分母，
绕过率恒为零。每个 sink 要显式写出它**不**覆盖什么：

| sink | 信号 | 覆盖 | **不**覆盖 |
| --- | --- | --- | --- |
| 托管方 pre-receive（在 agent 域外） | 无有效任务标识的写被拒 | 一切要进交付面的变更 | 本地未推送的改动 |
| git 底座对账 | `git log --all --since=<上次对账>` 减去账本里全部 Attempt 的 commit 集 | 已提交的改动 | 改了又扔、未提交 |
| 工作区脏状态 | `git status` 非空且无对应任务 | 有人在 worktree 里干活没建单 | 纯只读提问 |
| 终端 / 会话历史 | 对 CLI 的直接调用，argv 不含任务标识 | CLI 的手工调用 | GUI 会话、别的机器、加密历史 |

找不到对应记录的变更写成**未归因效应**，**不得反向补造一个正常任务**；
命中只记观察事件，**不自动建 Task、不自动惩罚**。「绕过」不是内核对象，不得为它新增状态。

**同时要降低登记成本**：提供「从 commit 追认」的一步登记，把已经发生的改动补成一个
最轻档位的 Task（验收 = 机械门禁对该 diff 复跑），让绕过变成账本里一个**带标记的合法对象**。
追认的比例本身就是「上界破了」的信号。

⚠ 当前条件下 git author 无法区分人与 agent，**人这一侧的绕过指标是 `UNKNOWN`**，不是零。

## 5. 实测记录

**这一节全是本项目真实发生的，不是设想。**它比前面任何设计都值钱，因为设计会被推翻，测量不会。

### 5.1 手工模式看起来在跑，轨迹却基本不可复原

拿某一轮的真实产物导出轨迹，23 条记录里：

```
attested（运行时能证实）  2 条   ← 而且这 2 条的「谁做的」仍不可证实
reported（自报）        15 条
inferred（事后推断）     6 条

六个版本的稿子   零个独立 commit
两次评审         有事件、无产物
两条不同的权力   由同一个 commit 承担，账本分不开
```

**对照组**：另一轮的整合分支有 **28 条逐主张提交**，同一套流程、同一种驱动方式，
`attested` 条目数量级不同。**差别不在账本，在纪律有没有落成动作。**

同一批数据里还有一条更难看的：**六次所有者裁决，在账本上没有一条是 Interaction 对象**。
它们以 `rulings.md` 里的表格行存在——而那是**执行者写的文件**。
人做了决定，记录这个决定的却是被决定的一方，中间没有任何东西保证两者一致。
这不是「记录不规范」，是**人的决定在系统里没有自己的对象**。

### 5.2 判据给假答案：七次

| # | 边界条件 | 产出的假答案 | 方向 |
| --- | --- | --- | --- |
| 1 | 验收方未指派，集合为空 | `all(空集)` 为真 → 报「完成」，还会跳过验收环节 | **假通过**，危险 |
| 2 | 命令在仓外执行 | 管道吞掉错误，输出一串 `.` 而不是报错 | 假结论 |
| 3 | 身份判别失败后 | 「我跑在 X 产品里 → 所以我是 X 参与方」 | 假结论，差点写错他家目录 |
| 4 | 检查遇到否定句 | 把「内核**没有**这条边」判成非法边 | 假失败，**安全方向** |
| 5 | 脚本里两个 `\|\| true` | 各吞一个错误，叠起来「看起来跑完了」 | **假通过**，危险 |
| 6 | 文档门禁只查 markdown 链接 | 删掉被引文件后仍报「全部通过」——纯文本锚点它看不见 | **假通过**，危险 |
| 7 | 补内容时切掉了两节正文 | 两道门禁全绿——**空标题不产生锚点，无从判起** | **假通过**，危险 |

**共同形态**：不是「检查漏了一项」，是「检查产出了一个可被下游继续推理的结论」。
**假失败是安全方向，假通过是危险方向**——判据写不准时该往哪边错，第 4 条给了实例。

### 5.3 未经现状核查的设计：六条

见 §1.3 的表。**六条全部可以在两分钟内用一条命令证伪，而在整整一轮完整流程里一次都没验。**

那一轮的九份评审全都在检查「你的设计自洽吗、锚点对吗、判据可判吗」——
**没有一份检查「你的前提是真的吗」**。因为任务书没要求，而任务书是裁决方写的。

### 5.4 并行竞争评比的边界

**它抓什么**（实测）：

- 抓出裁决方的改判与其自己的表**自相矛盾**；
- 抓出隐含了一条**内核里不存在的边**——只查状态词表抓不到；
- 用三条命令推翻裁决方的一处错误归属；
- 抓出有人拿**休眠代码**当能力证据（九份评审里只有一份发现）。

**它抓不到什么**：

- **框架本身的错**。某轮的核心结构错误（一个假分叉）过了九份评审、一次裁决、
  一轮异议、验收、冻结，最后由**目标持有者**指出。
- **题目本身封死的答案空间**。若任务书把某个设计写成「必须包含 X」并冻结成通过条件，
  那么「X 根本不需要」这个答案**说了就挂**——五家只能在里面优化 X 的形状。

**由此三条应写进出题环节**：

1. **任务书必须点名至少一个外部对照实现**（已有的库、已发货的产品），要求「对照它说明你为什么不同」；
2. **判据里必须有一条「该不该」型**，例如「本方案有哪一部分**可以删掉而系统仍成立**？
   给出至少一处，**不接受『都需要』**」；
3. **任务书的只读输入清单必须包含 `constraints.md` 与 `development-plan.md`**——
   *代价实例*：某轮没包含，产出的设计与「执行层租用不自建」的既定分工打架。

### 5.5 一条元观察

某轮结束时统计：**裁决方自陈的错误十二条，其中六条由参与方抓出、三条由目标持有者抓出、
三条自查**。而参与方犯的实质错误远少于此。

这与「控制面可信、执行者不可信」的直觉相反。
**按那个直觉设计的系统——只防执行者、不防自己——会在这类问题上原样翻车。**
所以控制面自身的动作也必须留痕、可复算、**可被他方推翻**。

#### 脚手架什么时候可以拆

现在这套东西跑在 **git 上**，而 git 在这里干了两件不同的事，必须先拆开：

- **git 当 Artifact 载体**——代码与文档的版本就是 commit。**这是永久的，不拆。**
- **git 当账本**——用 commit 历史 + `rulings.md` 反推状态，用 `round.md` 当 Task 主档。
  **这是脚手架，要拆。**

在谈拆之前先把账算清：**git 在这里到底承担了什么，又有哪些内核性质它根本验不了。**

| 内核要求 | 在 git 上怎么落 |
| --- | --- |
| 权威事件 | 可从发布点标签到达的 commit。**工作区文件永不作判据** |
| branch 与 tag 的语义 | **branch 是运输通道，不是评审对象**；tag 只有在受保护模式下才是权威引用 |
| 比较交换（乐观并发） | 发布用 `--force-with-lease`，或校验目标 ref 仍指向开始时记录的 commit；不一致即失败、新建整合 Attempt |
| 终态不可重开 | 轮次 id 全局不复用；纠错用 `supersedes` 新建，不 force-push 改历史 |
| ref 被重置后怎么恢复 | 发布点与各家候选都打标签 |

**验不了的三样，如实登记，不得说成「已在这一层验过」：**

| 验不了的 | 为什么 | 现在靠什么顶 |
| --- | --- | --- |
| **事务性** | 内核要求结果、验收、预算结算与终态事件原子提交；git 的多 ref 更新**不原子** | 顺序 + 人核对 |
| **租约** | Attempt 的持有者与到期时间；没有能自动拒绝迟到写入的运行时 | 观察窗判据，事后发现 |
| **fencing** | 过期 worker 的写入被拒 | 整合方核对候选状态，靠人不靠机制 |

所以「先在这一层跑通，再往下实现」的准确含义是：
**跑通对象形状、状态转换与交互纪律；并发语义留给数据库载体。**
换载体不是为了更好看，是因为这三样在 git 上做不出来。

拆除条件**全部机械可判**，不靠「觉得成熟了」：

| 组件 | 现在（人跑脚本） | 目标（服务） | 什么时候可以拆 |
| --- | --- | --- | --- |
| Task 主档 | `rounds/<id>/round.md` 的 toml 块 | `task` 表 | 服务态对 ≥1 个各档真实 Task 的轨迹，与手工态同档历史轨迹按下文的等效判据**全等**，且每类条目的 `attested` 计数 **≥** 手工态 |
| Event 日志 | commit 历史 + `rulings.md` | `event` 表（只追加） | 同上；另加 `round-status.py` 与服务态对同一历史轮次输出**相同的状态序列**，且新判据首跑先与人工对照 |
| 并发语义 | **验不了** | 租约 / 取消竞争 / 重启重建 三项通过 | git 载体验不了事务、租约、fencing——**不假装换个说法就能验** |
| Interaction | 环节通知 + 收件箱 + 裁定行 + 所有者 commit | `interaction` 表 + 鉴别响应者的端点 | **前置**：所有者拥有 agent 够不着的操作面，响应者身份达到 `attested`。**在此之前不得拆**——服务态若在同一信任域里提供端点，只是把 `reported` 搬了个家 |
| 派发 / 收集 | `round-dispatch.py` 生成命令 + 人粘贴 | executor adapter | 该 Agent Profile 可自动分发，且 adapter 已对它跑通一次 Attempt。**不能自动分发的执行者永远由人承担，它不是拆除对象而是登记对象**（§2.3） |
| 验收 | `round-status.py --verify` | acceptance runner | 对三轮历史产物，两者判定**逐条一致** |
| 工作区供给 | `git worktree add` | provision 服务 | worktree 本身留（属载体侧）；供给**判据**（独占 × 干净 × 基线）进代码并有测试 |

由此，「先在这一层跑通，再往下实现」的准确说法是：

> 手工态跑通的是**对象形状、边、Interaction 形状与权力行**；
> 它跑不通的是**并发语义与证据的 `attested` 等级**——后者与载体无关，换个实现也不会自动变好。

#### 等效判据：拿什么证明「换了实现，还是同一套东西」

分两层比，**不要混**：

| 层 | 比什么 | 什么时候可机械判 |
| --- | --- | --- |
| **S 层（形状）** | 对象集合、状态词、**边**、权力表行、Interaction 绑定字段、Agent Profile 字段 | **现在**。给出字段即可判 |
| **R 层（跑动）** | 同一个 Task 的轨迹，经投影之后逐条对应 | 两种实现都按同一形状落账之后 |

**「谁在哪条边上有权」属 S 层，是静态约束，不塞进一次跑动的轨迹里比。**

R 层的一条轨迹条目长这样：

```text
trace_entry = {
  seq          Task 内单调
  layer        task | attempt | interaction | artifact
  subject_id
  from → to    状态边；artifact 是 版本→版本；interaction 是 请求→决定
  actor        Agent Profile id / principal id / orchestrator
  power_row    触发这条边的权力表行，或 "—"
  payload_ref  interaction 层：出向的 artifact 引用 + 入向决定所落成的版本
  at           时间——**载体差异，不参与比对**
  provenance   attested | reported | inferred
  evidence_ref commit / 表行 / 文件:行
}

投影 Π = 丢掉执行者私有的事件（工具调用、内部 token、GUI 会话内部步骤）与 at，
         保留 Task/Attempt 的边、命中权力表的 Interaction、Artifact 版本与作者
```

比的是 **Π(手工态轨迹) 与 Π(服务态轨迹)**。丢掉 `at` 是有意的：
两种实现的时间戳必然不同，拿它比只会得到「永远不等效」这个没有信息量的结论。

#### 要改内核时，工作单元长什么样

开发这一层解决不了的问题，落点是**一个改内核的工作单元**，不是在这一层想办法绕。
单元的字段固定，缺哪一项都不受理：

| 项 | 写什么 |
| --- | --- |
| **原始请求** | 谁提的、原话；以及**量化证据**——不是「感觉不够用」，是「六次裁决在账本上零个对应对象」 |
| **改哪** | 逐条点到具体的定义块、字段表、验收用例编号 |
| **不改** | 明写。状态词、合法转换表、终态语义、幂等与租约纪律通常都在这一栏 |
| **影响分析** | 前端 / 后端 / agent / 验收器四侧各写一句：谁要跟着改，不改会怎样 |
| **迁移** | 见下 |
| **验收** | 原有用例全集 + 新增用例 + 一条**可复现**的实验 |
| **保留旧语义** | 旧的是什么、为什么不够。删掉旧解释，下一个人会把同一个坑再踩一遍 |

**迁移这一栏有一条铁律，值得单独拎出来：**

> 新字段以**可选**进入，带 schema 版本；旧数据**只能标成「旧格式」，严禁回填成新语义**。

举个具体的：旧的批准记录只有一个「已消费」的布尔。迁移时很容易顺手把它们全填成
「已批准」——**不行**。那个布尔只证明**这条问询被消费过**，不证明**人批准了**。
回填一次，账本里就永久混进一批查不出来的假批准，而且看起来完全正常。

配套三条：新版本的写入方**不得回写旧版本**；双读期的指标按版本**分开统计**；
活动中的旧版本对象归零之后才移除旧写入方，读取方为历史展示多留一阵。

### 6.1 已登记的未决项

**空着不等于没有，等于没记。**下列各条都已有处置方向，但都还没关闭：

| # | 未决 | 当前处置 |
| --- | --- | --- |
| 1 | **档位判据偏紧**：「权威层」几乎覆盖 `dev-plan/` 全部文件，按字面改一处锚点也要开完整轮 | 实务上按「问题是否欠定」判；**降档必须人确认**。判据本身待改（§3.1） |

| 9 | **触点疲劳导致盖章化** | 登记三个观察值（回执耗时、相对预填值的改动项数、每类触点的次数），**只看趋势，不自动触发动作** |
| 10 | **唯一真源只有一份**：全部产物与冻结标签只在一台机器上，远端严重落后 | ⚠ **当前最高优先级的实际风险**，且成本几乎为零：把产出推到远端 |
