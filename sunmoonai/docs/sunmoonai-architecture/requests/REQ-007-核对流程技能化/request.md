## ② 架构评审

- 结论：**采纳**。粒度小、判据明确、可独立验收，建议作为 REQ-005 三层演进的第一步实施。

- 理由：

  **为何技能化从核对流程开始——判据需先修正。**REQ-005 ② 初拟的判据是「执行过至少两次且
  产物格式没变」。按该判据，核对流程只执行过**一次**（REQ-002），而 REQ 立项已执行五次，
  应先技能化 REQ 立项。但该判据不完整，遗漏了收益侧。修正为三条并取合集：

  | 判据 | 核对流程 | REQ 立项 |
  | --- | --- | --- |
  | 执行过 ≥1 次 | 是（REQ-002 五仓并行） | 是（五次） |
  | 产出可机械校验 | **是**（`file:line` 可脚本验证是否存在且含所述内容） | 否（产出是散文） |
  | 预期高频重复 | **是**（投影维护的常态操作，见 REQ-004 §3） | 低频（每次新请求一次） |

  核对流程三条全中，REQ 立项只中一条。**技能化的收益来自「重复执行 + 产出可校验」，
  而非单纯的执行次数**，故核对流程优先。

  **它是本项目唯一已产生可验证价值的智能体流程。**REQ-002 那次核对产出 14 条真实偏差，
  其中 7–8 条为「意图被当成事实」（见 REQ-004 ② 与 REQ-002 `plan-baseline.md` §1）。
  相比之下 REQ-005 与 REQ-006 目前都还是设计稿。优先固化已验证回报的流程，风险最低。

  **REQ-004 §3 已把该操作定为投影的核心维护动作**，非一次性评审。技能化是其落地形式。

- 冲突与代价对比：无架构冲突。代价是一份技能文件的编写与一次跨工具验证。

## ⑤ 验收标准

1. 技能文件存在，且包含：切分方式、每单元输入、四类结论定义、`file:line` 取证要求、产出格式。
2. **换一个助手照样能跑出同格式产物**——REQ-002 那次由 Cursor 执行，验收时用另一工具
   （Codex 或其它）对同一仓跑一遍，产出格式一致即通过。这是「工具中立」唯一的可测形式
   （REQ-005 ②）。
3. 每条结论附带可重跑的取证命令，且抽样重跑全部成立（D2）。
4. 不引入任何单一工具专有的配置（hook、agents.toml 一类）。
