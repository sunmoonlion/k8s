# 智能体运作纪律

> 最后更新：2026-08-29
>
> **这是通用部分的行为规范。**它最初写作"多个 AI 助手怎么协作"，
> 但那套纪律与"多个智能体怎么协作完成一个任务"是同一件事——
> 区别只在执行者是助手还是程序。本项目决定按它来建智能体的通用部分。
>
> 每一条都来自**真实发生过的失败**，不是设想。
> 纯粹的 git 操作机制（拉取、推送、子模块）不在本文，
> 见 [`../working/collaboration.md`](../working/collaboration.md)。

## 1. 三种模式，别混

| | A · 并行提案 | B · 定向审核 | C · 评审—吸收循环 |
| --- | --- | --- | --- |
| 输入 | 同一个 request | 已有产物 | 已有产物 |
| 参与方 | N 个助手**互不可见**，各自出方案 | 一个助手查另一个的产出 | **N 个助手各自评审**，主方吸收 |
| 产出 | N 份独立方案 | 一份审核结论 | 评审记录 + **处置记录** |
| 闭环 | 比较 → 综合 | 结论交回 | **跑评审方的验收标准，公布结果** |
| 用途 | 拿到多个独立信号 | 验证工作是否成立 | 让已有产物被外部视角修正 |

**三种模式共用同一套 git 机制（见 [`../working/collaboration.md`](../working/collaboration.md)），但对"给什么材料"的要求不同。**

C 是 B 的多方版本加上吸收协议。它值得单列，因为**吸收环节是最容易失守的地方**：
被审方既是接受方又是判定方，不加约束就等于被告当法官（见 §5.3）。

## 2. 隔离原则

这是本文件最要紧的一条：**提案阶段，助手之间必须互相不可见。**

理由不是保密，是**信号质量**。B 若看到 A 的方案，产出会向 A 收敛——
得到的是"对 A 的改写"而不是独立判断。那样问 N 个助手的成本花了，
拿到的信息量却接近问一个。

同一条逻辑已有先例：`../working/doc-conventions.md` 要求重写投影时
"只读代码，禁止读本文档集，否则产出会退化为对旧文本的改写"。

**三个阶段，可见性不同：**

```
① 提案   各助手只见 request + 项目总览        ← 互相不可见，这是硬要求
② 比较   把 N 份方案摆在一起找分歧点          ← 人或某个助手来做
③ 综合   允许读全部方案，产出最终版            ← 此时才解除隔离
```

③ 阶段允许读别人的方案，但**不得直接拼接**——现有方案只作"该核对什么"的
候选清单，结论仍须回代码取证重写（同 `../working/doc-conventions.md`）。

## 3. 提案模式：发什么，不发什么

发给每个助手的**提案包**：

| 必给 | 说明 |
| --- | --- |
| 原始需求 | 用户原话，一字不改（见 [`../working/request-lifecycle.md`](../working/request-lifecycle.md) R1） |
| 验收标准 | 客观、第三方可判定（R5）。这是助手自检的依据 |
| 上下文入口 | 指向 [`../project-guide/overall-architecture.md`](../project-guide/overall-architecture.md)，让它自己按需深入 |
| 边界 | 含什么 / 不含什么 / 不含的归谁（R3） |

| **不给** | 为什么 |
| --- | --- |
| 其他助手的方案 | 破坏隔离（§2） |
| 提出方自己的倾向或初步结论 | 助手会向它收敛，等于白问 |
| 指定的检查点、"重点看这几处" | 划定了思考范围，没被点到的地方不会被想到 |

**判断标准**：给出去的东西应当只描述"要什么"和"怎么算做到了"，
不描述"我觉得该怎么做"。

### 3.1 自动化实现

[`parallel-proposals.py`](parallel-proposals.py) 把本节的流程脚本化：
同一份提案包发给 N 个**互相隔离**的实例，各自出方案，收集产出与执行元数据。

```bash
pip install openai-codex        # 自带钉版 CLI 二进制
python3 parallel-proposals.py --request req.md --n 5 --out ./proposals
```

**隔离由机制保证，不再靠自律**：每路一个独立进程 + 独立 `CODEX_HOME`，
会话、历史、状态互不可见。这补上了 §9 指出的那个洞——
此前同机隔离"只能靠明确指令，机制上拦不住"。

产出的 `manifest.json` 记录每路的模型、耗时、token 与状态，
是证据账（[`../working/request-lifecycle.md`](../working/request-lifecycle.md) §7）的最小形态。

**已验证到哪一步**（2026-08-28，本机实测）：

| 项 | 结果 |
| --- | --- |
| SDK 安装、JSON-RPC 握手、subprocess 起停 | ✓ |
| N 路并发，各自独立 `CODEX_HOME` | ✓ 实测 3 路与 5 路，各写入 53 个文件互不干扰 |
| 用户 `~/.codex` 不被触碰 | ✓ 零文件改动 |
| 单路失败不拖垮其余、manifest 照常写出 | ✓ |
| **真实模型调用** | **✗ 未验证**——本机未登录、无可用端点 |

⚠ 系统已装的 CLI 若版本低于 SDK 所钉版本，`thread_start` 会因响应字段缺失而失败
（实测 0.125.0 报 `ThreadStartResponse.thread.sessionId Field required`）。
用 `pip install openai-codex` 自带的二进制即可。

## 4. 审核模式：分两阶段，避免锚定

定向审核有个隐蔽陷阱：**提交方写的"审核说明"会划定审核范围。**
提交方没想到要查的地方，审核方也不会去查——看起来独立，锚点其实全是提交方给的。
这比"自己验自己"更难察觉。

**因此拆成两阶段：**

| 阶段 | 给审核方 | 明确不给 |
| --- | --- | --- |
| **一 · 独立审** | 原始需求 · 产物位置 · 客观验收标准 | 提交方的结论、自评、自陈盲区、指定的检查点 |
| **二 · 对照** | 这时才给提交方的自陈盲区清单 | — |

第二阶段的价值是**双向查漏**：

- 审核方发现了提交方没自陈的 → 提交方确有盲区
- 提交方自陈了审核方没发现的 → 审核方的审核有盲区

两边都能被检验。若跳过第一阶段直接给全套说明，这个检验就做不成了。

## 5. 模式 C：评审—吸收循环

多家助手评审主方产出、主方吸收意见。**本项目已实跑过一轮**（2026-08-27，
qoder 评审 opus 的文档重构），下列规则全部来自那一轮暴露的实际问题，
上一轮的记录（qoder / cursor / kimi / luna 四方评审 + 吸收处置）
已随 2026-08-29 的 merge 完成并删除，见 git 历史。

### 5.1 为什么值得做

外部视角能发现**自查在结构上碰不到的东西**。实例：评审方指出一处空链接，
顺着查下去发现的是**主方的坏链检查器自身有 bug**——它把 `[x]()` 当作"跳过"
而非"坏链"，导致此前三次"0 坏链"的自查报告全是假的。

**工具自身未被验证**这类问题，自查无论跑多少次都发现不了。

### 5.2 评审方必须声明的三件事

| 必须声明 | 不声明会怎样（均已实际发生） |
| --- | --- |
| **所审的提交号** | 评审在写出时就已滞后。实例：评审引用某提交，而主方已领先 3 个提交 |
| **覆盖范围**：看了哪些仓/目录，**没看哪些** | 产生误报，且未覆盖区域会被误当作"已审"。实例：评审只看了 `k8s` 一个仓，对已在 App 子仓修复的问题报了"未处置" |
| **可判定的验收标准** | 吸收方无从证明自己真的吸收了 |

第二条尤其重要：投影须自陈盲区（[`../working/doc-conventions.md`](../working/doc-conventions.md) 的编辑自检），
**评审同样是一种产出，同样要自陈盲区**。

### 5.3 吸收方必须留处置记录

每条意见给出**接受 / 部分接受 / 拒绝**，各带理由。理由须能独立成立，
不能只写"已处理"。

**"误报"是最需要举证的一类判定**——被审方判定某条意见是误报，
等于自己给自己免责。该判定本身必须可验证：给出命令或位置，让第三方能复核。

**部分接受要写清接受到哪、为什么止于此。**实例：评审指出"行号锚点是易腐值"，
主方接受了"验证命令改为模式锚定"（行号会让命令静默产出错误输出），
但保留了正文里的 `file:line`（作为近似指针，代码微动仍能找到附近）——
这个分界是主方单方划的，写出来才能被质疑。

### 5.4 闭环：跑评审方的验收标准

**吸收之后必须回跑评审方给的验收标准，并公布结果。**不跑就不算闭环——
2026-08-27 那轮里，评审方认真写了八条验收标准，而它们直到主方主动回跑前
一直没人执行过。

回跑时注意：**验收标准自己也会腐坏**。同一轮的实例：评审方写的
`grep -rn ']()' architecture/` 是按"该目录只有 md"设计的，
主方随后新增了一个含字面量 `]()` 的 `.py`，该标准立即开始误报。
所以标准不通过时，先判断是产出没达标还是标准过期。

### 5.5 多家并行评审时，同样要隔离

多家评审若能互相看到，第二家会顺着第一家的思路看，重叠部分虚高、
盲区依旧是盲区。隔离要求同 §2。

**多家的价值在重叠与分歧本身**：

- 两家都指出的 → 大概率是真问题
- 只有一家指出的 → 要么那家更强，要么是误报，需要单独判定
- 两家发现的集合几乎不相交 → **说明整体覆盖率低**，不是"审得全"

### 5.6 这个模式没有解决的问题

**单靠它无法估计残余缺陷。**评审方找到了主方漏的，但评审方漏了什么，
没有任何机制能告诉你。增加评审方数量能改善估计（§5.5），但不能消除该盲区。

因此模式 C 的产出**不构成"已验证"的背书**，只构成"经过一次外部检视"。
合并记录里应当照此措辞。
