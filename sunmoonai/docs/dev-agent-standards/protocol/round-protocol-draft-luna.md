# 轮次协议（Luna 草案）

> **独立提案，未生效。**作者：Luna，2026-09-10。
> 基于所有者提供的主工作区 `round-protocol-draft.md` 起草。本文的新增、修改均为 Luna 建议，不代表所有者已经同意。
> 现行规范仍是 [`round-protocol.md`](../../dev-agent-task/composition/protocol/round-protocol.md)。本文获批且配套工具通过检查后，才可替换现行规范。

## 一、目的与底线

多家 AI 助手就同一件事独立提案，经评优、建言、综合，形成一份定稿。
每个角色的判断性产物都须人审核同意；人可以否决、要求修改、暂停或终止本轮。

三条底线：

1. **判据先于产出冻结**，不得为了让某份稿子通过而中途改判据。
2. **产出方不等于批准方**，任何 agent 都不能代人批准。
3. **发布须有人明确授权**，批准某份产物不自动授权未写明的发布动作。

本协议规定完整的四环节轮次。综合之后不增加 agent 复查环节，人是最后一道；机器核对版本、记录和规则，不替人判断内容质量。

## 二、角色与分派

| 角色 | 由谁担任 | 职责 |
| --- | --- | --- |
| 人 | 所有者 | 指定 supervisor；批准任务、角色分派和各角色产物；裁决异常；批准发布 |
| supervisor | 人指定 | 起草任务与判据、分派角色；查进度、送通知、整理送审入口；执行已获授权的发布 |
| 竞选者 | supervisor 提议，人批准 | 独立提出方案 |
| 评优者 | supervisor 提议，人批准 | 按冻结判据比较全部有效提案，确定基座 |
| 建言者 | supervisor 提议，人批准 | 建议基座吸收哪些长处，说明来源和理由 |
| 综合者 | supervisor 提议，人批准 | 逐条处置建言，完成综合稿 |

分派规则：

1. 同一家不得同时担任评优者和综合者。
2. supervisor 不得把自己分派为评优者。
3. 综合者若同时是基座作者，须有人的明确许可；未许可时不得开始综合。
4. 其余角色可以兼任。评优者可以选自己的提案，综合者可以处置自己提出的建言，但须分别标明「自选」「自处置」。
5. 评优者、综合者各一名；竞选者至少两家；建言者至少一名。每项分派都要指定具体执行者。

**执行者身份和角色实例分开登记。**例如 `luna` 是执行者，`candidate-luna` 与 `advisor-luna` 是两个角色实例。
同一家开的不同窗口仍是同一家；不能用改名或换窗口绕过分派规则。这里的「一家」指登记的助手身份，不按模型供应商合并不同助手。

## 三、开轮与冻结

每轮使用不复用的轮次名，在 supervisor 分支的 `rounds/<轮次>/task.md` 定义本轮。

| 必填内容 | 要写清什么 |
| --- | --- |
| 请求与范围 | 人的原始请求、目标、包含与不包含的内容 |
| 判据 | 硬要求、比较偏好及必要证据；待定事项须先定下或明确不参与判定 |
| 只读输入 | 仓库、路径、完整提交号；各竞选者获得同一套公共输入 |
| 协议版本 | 本轮使用的已生效协议及配套通知、脚本的固定版本 |
| 角色分派 | supervisor、执行者身份、角色实例、分支与工作区；兼任许可或其待决条件 |
| 发布范围 | 目标仓库、分支、允许变更的路径，以及起始基线提交 |
| 运行安排 | 检查频率、通知模板、通道、超时规则；频率仅决定多久查看一次 |

人的审批分支及所有者身份由人事先指定，不能靠一个尚未获批的 `task.md` 自行指定审批来源。
supervisor 起草任务前须取得人的任命；人的任命、任务批准均留在人的分支上。

**开轮门：任务获批、分派合法、工作区就绪之后，supervisor 才能发送竞选启动通知。**
第一次启动通知发出即冻结任务的目标、范围、判据、公共输入和协议版本；各家计时则从各自送达回执开始。

冻结后不原地修改 `task.md`。换人、退出、延期等运行变化另记变更记录，按本文规定生效。
目标、判据或公共输入需要实质修改时，由人终止本轮，另开新轮。
主线协议后续更新不静默改变在途轮次；若必须迁移，由人终止旧轮后按新版本重开。

## 四、四个环节

| 环节 | 产物 | 进入下一环节的条件 |
| --- | --- | --- |
| 竞选 | 各家的独立方案：方案正文、判据对应、证据、假设和未完成项 | 所有仍须交付的竞选者均获人批准，且有效提案至少两份 |
| 评优 | 全部有效提案的比较理由、选定基座的提交号与路径 | 评优产物获人批准 |
| 建言 | 对已批准基座的逐条建议，注明来源提案、吸收内容、理由 | 所有仍须交付的建言者均获人批准 |
| 综合 | 综合稿、基座到综合稿的差异、逐条处置记录、必要的验证结果 | 综合产物获人批准；发布另按「发布与保留」执行 |

环节只能顺序启动。上一环节未通过，不提前生产下一环节的正式产物。

**竞选期间隔离。**竞选者不得读取其他家的本轮提案、摘要或比较结论；兼任 supervisor 时，只查交付与运行元数据。
某家提前获批，也须等竞选环节关闭后才可读其他提案。公开其他方案后需要重开竞选，须作为新轮处理，并披露这些方案已成为已知材料。
共享仓库内的读取隔离依赖执行纪律，不能宣称技术上不可见。

批准提案表示允许它进入比较，不表示它已达最终发布标准；比较中发现的缺陷仍须写明。
评优须按同一判据对全部有效提案给理由，不以票数、自选身份或篇幅代替理由。

每条建言有本轮唯一编号，例如 `advisor-luna-01`，来源绑定提交号和具体位置。
无建议也须明确提交「无建议」及审阅范围，不能用空文件或未响应代替。

综合者对每条建言**原文引用**，标明采纳、部分采纳或驳回并给出理由。
采纳与部分采纳须指出综合稿的落点；部分采纳还须说明未采纳的部分及理由。
合并处理重复或冲突建言时，每个原编号仍须有对应处置，不能因合并漏项。
综合者自行新增、删除或修改的实质内容，也须列出与判据的关系及理由，不能藏在编辑性修改中。

## 五、送审与批准

**先提交送审快照，人批准后，该快照才成为正式产物。**送审与正式产物使用同一个提交，不为「转正」再造一个提交。

### 送审对象

每份送审产物附一份清单，与正文放在同一次提交里，至少写明：

- 轮次、环节、角色实例、执行者；
- 本次送审包含的全部文件路径；
- 所依据的已批准任务提交、上游产物提交及路径；
- 若是修订，替代哪次送审，以及修改说明；
- 验证结果与未验证项，适用时提供证据路径。

提交信息标明「送审」。清单不填写它自身所在的提交号，提交号由提交完成后取得，写进送审通知和人的审批记录。
一次提交可以包含正文及其处置记录等配套文件，但不得混入其他角色或其他任务的修改。

### 人实际看什么

送审通知给出仓库、**完整提交号**、文件清单，以及读取该提交正文和差异的入口。
正文从 `git show <完整提交号>:<仓内路径>` 或等价的固定提交视图取得，不以可变工作区为审批对象。
人可在工作区边读边讨论，但作出批准前须核对固定快照；修订稿须同时可查看相对上一版的差异。

### 人如何留批准

人在自己的分支追加审批记录并提交。每条记录至少包括：

| 字段 | 含义 |
| --- | --- |
| `round` / `stage` | 轮次与环节；开轮审批使用准备环节 |
| `role` / `actor` | 角色实例与执行者，兼任时也不得省略角色 |
| `submission` / `manifest` | 被审批的完整提交号及清单路径 |
| `decision` | 同意、否决或撤销同意 |
| `reason` | 否决、撤销时的理由与修改要求 |
| `supersedes` | 改判时所替代的审批记录编号；首次为空 |

同意可批量提交，但每个对象各有明确记录。聊天里的「可以」「继续」、通知送达、agent 自述均不能代替这条记录。
同一对象的改判须显式引用旧记录，旧记录保留；出现无法确定先后效力的冲突记录时，脚本报告阻塞，交人澄清。

人的分支只收人本人作出的提交，agent 署自己的身份，不代写人的批准。
**Git 作者字段只用于检查署名约定，不构成操作者身份认证。**此方案以各方不冒用所有者身份为信任前提；需要技术身份保证时，须另行接入仅人控制的审批凭据并验证，不能把作者匹配称为已经认证。

## 六、版本变化与回退

审批只对清单列出的那次快照有效。分支新增无关提交，不改变旧快照的批准；新版本也不会因位于同一分支而继承批准。

已批准产物不能由作者单方面替换。作者发现需要修改时，先报人；人要求修订或撤销批准后，冻结受影响的下游推进。
仅存在一个未被人选用的新草稿，不自动使已批准版本失效。

| 变化 | 处理 |
| --- | --- |
| 当前送审稿被否决，尚无已批准版本 | 原角色按意见重做，以新提交再次送审 |
| 人要求修订、撤销或替换已批准产物 | 暂停依赖它的下游；该产物及受影响下游不得继续作为过关依据 |
| 上游修订版获批 | 依赖旧版的下游逐级重做或确认仍适用；均须更新依赖清单、产生新送审提交并重新获批 |
| 下游正文仍适用于新上游 | 可以保留正文，但须说明为什么仍适用；不得沿用旧依赖和旧批准 |
| 已公开候选后，要求修改候选或增删比较对象 | 终止本轮并重开，避免把看过答案后的修改算作独立竞选 |
| 目标、判据、公共输入发生实质变化 | 人终止本轮，按新任务重开 |

只有沿依赖关系受影响的产物失效，未受影响的产物保留批准；不得只看提交时间推断依赖。
若人撤回修订要求、恢复原版本，也须明确记录；已经失效的下游审批须由人明确恢复或重新批准。

**同一角色实例在同一环节累计第二次被否决后，暂停该环节，不自动开始第三次送审。**
人判断是继续按原判据修改，还是终止本轮重开；计数与恢复决定留痕，换人不清零。

## 七、分支、工作区与记录

每个角色实例有自己的分支和工作区；人、supervisor 同样各有独占分支和工作区。
兼任不合并角色的写入面。执行者只写所任角色的工作区，按当前角色提交。

| 位置 | 放什么 |
| --- | --- |
| 主线 `protocol/` | 已生效规范、每环节一个通知模板、配套脚本 |
| supervisor 分支 `rounds/<轮次>/` | `task.md`、运行变更、观测、通知与发布记录 |
| 各角色分支 `rounds/<轮次>/` | 该角色的产物、送审清单及必要证据 |
| 人的分支 `rounds/<轮次>/` | 任命、审批、裁决、撤销与发布授权 |
| 主线约定最终路径 | 人批准发布的定稿 |

以上限制针对**本协议管理的内容**，不要求删除仓库已有代码或历史文档。
新的过程产物不合并进主线。每轮的配置只写在任务与正式变更记录中，不在通知里另造一套配置。

协议以本轮任务钉住的主线已生效提交为准；产物以送审或批准所指的提交为准。
别人工作区中的旧协议、未提交修改及当前分支 HEAD 均不替代这些版本。

## 八、机器如何判定

`round-status.py` 的结论从可取得的 Git 提交及其中的结构化记录推导，不从聊天、工作区或手填的「已完成」字段推导。
每次检查固定各记录分支的读取提交，输出读取版本；检查期间分支再变化，留到下次检查，不混用两次快照。

每个角色实例的状态至少区分：

| 状态 | 含义 |
| --- | --- |
| 待交 | 已启动，未有有效送审 |
| 待审 | 已有有效送审，尚无人同意或否决 |
| 待修改 | 人已否决或要求修订 |
| 已批准 | 快照获批、依赖仍有效、批准未被撤销 |
| 已失效 | 原有批准因改判或依赖变化不能继续使用 |
| 已退出 | 退出已按规则生效，不再属于必交名单 |

另行标记等待人工操作、通道故障等运行阻塞，它们不是批准或退出。

**环节完成 = 当前有效分派中的所有必交角色均已批准，且满足该环节的最低人数与依赖要求。**
必交名单由已批准的初始分派及已生效的退出、换人记录计算；不能因文件没出现而自动缩减名单。

脚本至少核对角色冲突、任命与任务批准、产物完整性、审批对象匹配、依赖有效性、退出依据、建言编号逐条覆盖和发布范围。
无法取得提交、字段缺失、未知格式、冲突审批、对象不匹配均报告阻塞及具体原因，不推断为同意。
检查结果区分「未交」「待人审」「规则不满足」「工具无法判定」，避免向已经交稿的人重复催交。

## 九、通知与送达

通知模板和触发规则随协议发布，并由人批准本轮启用。
**按已批准模板、向已批准角色发送满足触发条件的通知，属于执行已授权动作，无须逐条再审。**
supervisor 新增判断、变更要求或改变角色时，仍须按相应规则送审；不得借通知正文修改判据。
人的批准原件由人提交，supervisor 只通知其位置，不替人写一份同意。

通知给接收者明确的轮次、角色和固定协议入口。接收者先跑判定，再取本角色当前有效输入，重复收到同一通知不得重复启动工作。

各助手可以运行在同一 tmux 会话的不同窗口。任务登记精确到目标 pane 和角色，不能只凭窗口顺序猜对象。
兼任者先确认当前角色与工作区，再开始写入。

发送纪律：

1. 先检查目标身份与画面，确认停在空输入框；菜单、审批、确认提示、正在运行或已有未发送输入时，一律不送。
2. 发送前再次核对；发现状态变化或无法确认时停止。截图检查不能保证检查后界面不会变化。
3. 按该界面已验证的方式输入文字和提交，不盲发回车，不替人处理权限提示。
4. 发送后等待界面刷新，检查消息是否成为已提交消息；记录通知编号、发送对象、时间与结果。
5. 送达不确定时先查对话与运行状态，不自动重发或补回车。没有可靠送达证据，不开始交付计时。

未验证的界面或不在 tmux 中的执行者，由 supervisor 给人准备好目标与通知文字，交人发送；人的确认也可作为送达记录来源。
通知正文被提交到会话不等于任务已完成，也不等于人已批准产物。

## 十、停滞、逾期与退出

**停滞信号用于检查，逾期判据用于裁定，两者分开。**文件字节数、内容摘要、分支提交、CPU 时间、输出与界面状态可以作为观测证据，但单独或组合静止均不证明执行者没有工作。

supervisor 按任务批准的检查频率查进度。发现疑似停滞，先辨别是否送达、是否等待模型或工具、是否等待人工操作、通道是否故障。
已送审但等待人的批准，不计为执行者迟交。

### 有同环节样本时

1. 对该环节当前必交角色数取 `N`。至少 `ceil(N / 2)` 家已有效送审后，建立一次同侪观察窗。
2. 各样本用时为「确认送达到有效送审被观察到」的时长，扣除已留痕的等待人工操作及已确认通道故障时段；人的审稿用时不进入样本。
3. `W` 取这些已送审者用时的中位数；偶数样本取中间两数平均。记录样本、暂停区间、计算结果和触发时刻，随后固定本窗，不随新样本缩短。
4. 对未交者发送「再给 W 的有效执行时间，可交现状，未完成处标 ⚠ 并说明缺什么」的催交通知；从该催交通知确认送达起，各自计时。
5. 扣除上述暂停时段后仍超过 W 且未有效送审，才满足逾期判据。宣布前重新核对产物和阻塞，提交观测与计算记录。

W 非正、送达时间缺失或暂停区间无法核对时，报告无法计算，不补猜测值。
角色数量变化时重算适用人数；若需新建观察窗，不得让已通知者的有效截止提前。
supervisor 可延长窗口并留痕，缩短须经人同意。

### 没有样本或无法计算时

没有同环节有效样本，不自动生成逾期结论，也不拿其他角色的用时替代。
supervisor 报告阻塞、现有证据及可选处置，由人决定继续等、明确一个截止，或按已确认的不可用原因换人。
评优、综合通常只有一名执行者，适用此规则。这是同侪方法的边界，不宣称它能为所有环节自动算出截止。

### 逾期和退出的后果

| 情况 | 处置 |
| --- | --- |
| 竞选者在竞选关闭前满足已批准的逾期规则 | supervisor 提交退出记录，引用规则与观测证据；据开轮时批准的规则生效，不逐次再审 |
| 竞选者明确主动退出 | 取得该执行者的退出记录，supervisor 留痕并据已批准规则移出必交名单 |
| 有效竞选者少于两家 | 停轮报人；不得自动把一份提案当作评优结果 |
| 评优者、建言者、综合者不可用 | 报人决定换人或继续等；批准换人前，原角色仍阻塞环节 |
| supervisor 不可用 | 由人任命接替者，交接固定提交和未决事项 |
| 人的审批迟迟未到 | 等待；不设超时通过，不由 agent 代批 |

退出记录至少写明轮次、角色、执行者、原因、证据、所依据的授权及生效范围；脚本核对后才从必交名单排除。
退出后迟到的产物保留但不自动恢复资格。竞选关闭前需恢复资格，由人批准并重新核对人数；关闭后不得插入新候选。

**换人只因不可用，不因对结论不满意。**新分派须经人批准并重新检查角色冲突，保留原执行者的产物和处置记录。
未响应、主动退出、逾期分别如实记录；任何一种都不写成「认可」。

## 十一、发布与保留

综合送审时同时备好可供人审核的发布清单：源提交、源文件到目标路径的映射、拟新增/修改/删除的范围、预期主线提交，以及实际拟发布差异。
发布清单作为送审产物的一部分固定在提交中。

人可以一次批准综合产物并授权按清单发布，也可以只批准内容、稍后再授权发布。
授权必须明确引用该提交与发布清单，不能由 supervisor 把普通「同意综合稿」解释成发布授权。

获准后，supervisor：

1. 从获批的固定提交取文件，核对发布清单；不从工作区取「最新稿」。
2. 在自己的工作区准备发布提交，仅包含清单允许的变更，核对目标文件与批准源的内容一致，并执行所需机械检查。
3. 以清单中的预期主线提交为条件更新目标；主线已经变化时停止发布，准备新的基线与差异并重新取得发布授权，不强推或覆盖。
4. 记录实际发布提交、源提交、批准记录和核对结果。发布失败记为待发布；重试前先查目标是否已完成同一发布，避免重复执行。

**已批准不等于已发布。**实际主线结果符合有效授权后，才能判本轮已发布。
人的授权在执行前被撤销时停止；执行后需要撤回发布，由人批准新的修正发布，不改写既有记录。

过程分支默认保留。清理须另有明确范围，并先确保送审提交、审批及依赖记录有持久引用、可重取；不能仅因手里记着提交号就删掉最后一个可达分支。

## 十二、生效前的配套验收

本文是规范提议，不表示现有 `round-status.py` 已实现上述能力。
替换现行规范前，应同步通知模板、任务与审批记录格式、入口文档和脚本，并至少演练：

| 场景 | 应有结果 |
| --- | --- |
| 工作区有未提交修改，人批准旧快照 | 仅旧快照获批，工作区修改不参与判定 |
| 同一家兼任两个角色 | 审批只作用于指定角色实例，分派检查仍按执行者身份判断 |
| 上游获批后被撤销或替换 | 受影响下游阻塞；正文未改也须更新依赖并重新批准 |
| 竞选者逾期退出、随后迟交 | 有效名单按退出记录计算，迟交不自动恢复资格 |
| 没有任何交付样本，或卡在人工审批 | 报告具体阻塞，不自动逾期或通过 |
| 通知重复、送达不明、目标在审批界面 | 不重复启动，不盲补回车，不自动回答审批 |
| 发布前主线变化或发布重试 | 旧基线授权不能覆盖新主线；已经发布的不重复执行 |
| 人撤销批准、记录冲突、对象缺失 | 按改判处理或明确阻塞，不沿用旧结论默认通过 |
