### 我是怎么判错的：`||` 兜底从未触发

检查命令的形状是

```
git show <refA>:<文件> | grep … | head | cut | sed  ||  git show <refB>:<文件> | …
```

**管道的退出码取自最后一个 `sed`，它永远成功**，于是 `||` 的兜底分支**一次也没跑过**。
而 `luna` / `qwen` 的 ② 评审提交在**裸分支** `luna` / `qwen` 上（组织者代提交时用的是它们的当前分支），
第一个 ref `runtime-refact/<家>` 上没有该文件 → `git show` 失败 → 空输出 → **看起来就像「没声明」**。

**不需要为此立新规矩。**协议 §8.1 第 1 条早已写明：

> 零命中要能区分「**真的没有**」与「**没查到**」。

规则在，是执行者（我）没照做。**方向是危险的那一侧**：它不是漏报，是**冤枉了两个合规的参与方**——
与 ① 那次「判据只认一个 ref，把照指示做的那家判成没交」同一形态、同一天内第二次。

### 仍然成立的那一半

而不是写进 M 类由脚本判。这是**发起方的缺口**，与四家无关，作为下一轮的改进项登记。

## O-3 ｜ 组织者把四家置于未完成的合并状态，然后在该状态下发了 ④

### 发生了什么

发 ④ 之前同步主线，命令是

```bash
git -C /home/zym/worktrees/$w/k8s merge master --no-edit >/dev/null 2>&1
```

主线此时已有裁决稿 `agent-dev-guide.md`，而各家分支上有自己的 ① 候选，
**同路径两边新增 → `AA` 未解决冲突**。而该命令
**把输出重定向丢弃，又没有检查退出码**，于是：

> **四家全部停在合并中途，组织者毫不知情，并在这个状态下发出了 ④。**

后果不是理论上的：各家的索引里躺着一批组织者的暂存改动，
任何一家若照常 `git add -A && git commit`，会把**整个未完成的合并**一并提交。

### 谁发现的

**四家里两家**（`kimi`、`luna`）在自己的输出里主动报告了这件事：

- `kimi`：「索引里已有一批组织者暂存的改动，提交时需注意只提交我这一个文件」；
- `luna`：「当前 luna 工作树已有未决 merge 冲突，且 `.git` 不可写，因此无法提交」。

**组织者是被参与方告知才发现的**，不是自查发现的。

### 处置

按「保留各家自己的 ① 候选」解冲突——裁决稿由 `runtime-refact/arbiter` 这个 ref 取，
本来就不需要进各家工作区。解完逐家核对候选 sha256：

| --- | --- | --- | --- |
| `luna` | `cc47d068c39c9bcd` | `cc47d068c39c9bcd` | ✅ 未被动过 |
| `kimi` | `913ccb082320b8e6` | `913ccb082320b8e6` | ✅ |
| `cursor` | `926a974e02df238f` | `926a974e02df238f` | ✅ |

`qwen` 仍在跑，**不动它的工作区**，等它结束再修。

### 教训：这一条比前几次都重，因为它不是判错，是把别人置于坏状态

前几次（检查器覆盖不全、`||` 兜底、① 单 ref）都是**判据给了假答案**，
错在结论。这一次是**动作本身失败了而组织者不知道**——
错在**没验证自己做的事成没成**。

协议 §8c.1 只写了「环节进行中不得写入参与方工作区」。**它防不住这次**：
本次同步发生在**环节之间**，是允许的。缺的是下一句：

> **写入之后必须验证写入成功。**`>/dev/null 2>&1` 加不检查退出码，
> 等于把一次失败的写入当成了成功的写入。

已补进协议 §8c.1。
