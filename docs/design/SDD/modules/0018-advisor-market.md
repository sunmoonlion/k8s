## 一、决定

| 项 | 定了什么 |
| --- | --- |
| 第四个应用 | **`knowmart-app`**（知识市场：上架、购买知识；**专家是第一种上架的知识**，请专家 = 买知识），由 `tpl-app` 实例化：`knowmart-backend`、`knowmart-web-frontend`（市场 + 作者工作室）、`knowmart-admin-frontend`（上架审核、分类）。一条链：knowfeed 采集 → knowbase 加工入库 → knowmart 上架卖 |
| 与 knowbase 的区别 | knowmart 把作者的 profile 内化为工作流给 Codex 用，并存放每位专家的私有资料；knowbase 加工、存储采集来的公共数据。专家知识库由 knowmart 自己存、自己索引（2026-10-11 所有者定「甲」），两者不存在分工 |
| 市场怎么分 | 三大类：宏观、行业、上市公司；每类若干专家 |
| 一位专家是什么 | **知识库 + skill**。skill 是专家包整体（六问、步骤、每步验收、工具范围、放行表），不等同于一个普通 `SKILL.md` 文件；知识库是这位专家在云上的私有资料 |
| 谁上架 | 第一期我们；以后主要靠作者（独立的账号体系，§二之二），所以要有作者工作室。第一期只有我们自己的作者账号 |
| 知识库归谁、谁能读 | 归这位专家（作者）私有；用户选定这位专家后，那次委托里的 Codex 可读，别处读不到；用户看不到原件 |
| 用户还上传吗 | 不。用户的 Codex 能读的资料只有：项目目录、本地知识库（0019）、选定专家的云上知识库、公共数据 |
| 选专家 | 在投研的专家对话框里点「选专家」→ 跳 knowmart 市场页 → 选定 → 跳回原处；编排按选定专家的那一版做 |
| 第一批上架 | 「中国A股上市公司财务分析与预测」（2026-10-15 所有者定「专家收成一位」：问数、财报体检下架，财务分析与预测吸收财报体检）。它的第 3 版做出来以后迁入 knowmart；迁入前仍由 `packs.py` 内置 |

## 一之二、市场里有哪些对象（吸收对比分析第二节）

市场做大以后，最容易把所有东西都叫「专家」。先把对象分开：

| 对象 | 含义 | 例子 | 第一期 |
| --- | --- | --- | --- |
| 作者 | 为方法、资料和维护负责的供给方 | 我们自己；以后是研究团队或个人 | 做 |
| 专家 | 长期身份与能力定位 | 中国A股上市公司财务分析与预测 | 做 |
| 专家版本 | 一次发布的执行内容与资料清单（§三之二） | 某一版的方法、依赖、规则与知识库快照 | 做 |
| 服务规格 | 用户这次要完成的工作范围与适用边界 | 对一家已入库的 A 股公司做财务分析并预测下两个季度 | 做（写进六问与受理规则） |
| 使用权益 | 用户能用什么、多久、几次 | 免费试用、单次委托、订阅内使用 | 不做，商业模式定了再加 |
| 委托 Task | 某次实际执行 | 一次具体的分析与预测 | 已有（工作台） |
| 交付记录 | 这次承诺对应的结果与检查证据 | 文件位置、摘要、数据版本、验收记录 | 已有（底稿、`交回.md`、验收记录） |

前四项先讲清；收费权益、订单、结算等到商业模式确定后再加，第一期不为未来的市场提前做电商系统。

## 二、Codex 可读的四处资料（取代 0011 §一与 knowbase PRD 六之二）

| 层 | 谁的 | 放哪 | 谁能读 | 怎么进来 | 页面上 |
| --- | --- | --- | --- | --- | --- |
| 公共数据 | 我们 | 服务器（knowbase-app） | 所有用户、所有专家 | 我们在管理端采集、建库、登记 | 不以库的面目出现，「问就有」 |
| 专家的云上知识库 | 每位专家（作者） | 服务器（knowmart-app），按专家隔离 | 选定这位专家的那次委托，凭按「用户 × 专家 × 委托」签发、可撤销的授权（§四） | 作者在工作室里备：专家资料夹 + 作者私有知识库挂给它的部分（§二之二） | 市场页只显示概况（多少份、涉及什么），不显示原件 |
| 项目目录 | 每个用户 | 用户电脑 | 该用户的 Codex 经本地代理 | 用户自己放、工作与专家产出 | 项目、右边栏文件树 |
| 本地知识库 | 每个用户 | 用户电脑上的一个目录 | 该用户的 Codex 经本地代理，跨项目 | 用户自己放、信息采集放入 | 侧边栏「本地知识库」（0019） |

规矩：四处互不流动。专家知识库不进公共库；本地知识库不上传；委托到终态，授权失效。**作者不因用户选用了他的专家就能读用户的项目文件**——作者访问买方材料要另有独立、明确的授权。

## 二之二、两套账号体系（所有者 2026-10-11 定「好像最好是两套账号」）

| 体系 | 谁 | 在里面有什么 | Casdoor |
| --- | --- | --- | --- |
| 投研平台的用户 | 做投研的人 | 电脑、工作区、项目文件夹、本地知识库、对话 | 组织 `sunmoonai`（0014），应用 knowbench |
| 知识市场的作者 | 编专家的人 | 专家、每位专家的资料夹、作者自己的私有知识库 | **另一个组织**（暂名 `knowmart-authors`，原暂名 `advisors`），应用 knowmart-studio |

两套各自独立：同一个人要既做投研又编专家，就注册两个账号；两边不互认、不合并。形状上两边一样——作者的「专家资料夹 + 私有知识库」对应用户的「项目文件夹 + 本地知识库」，只是作者的在云上（本来就要给别人的 Codex 读）。所以**专家的云上知识库 = 这位专家的资料夹 + 作者私有知识库里挂给它的部分**，按专家隔离。普通用户的项目与本地知识库永远不上云。

| 面 | 谁登录 | 说明 |
| --- | --- | --- |
| 市场（浏览、专家页、选定回跳） | 投研用户 | 用户只在这里出现。**同一个身份提供方不等于 cookie 能直接复用**：knowmart-web 怎么认投研用户（会话受众、校验接口、回跳时带什么）实施前写成跨应用契约，按 0014 与[跨应用跳转规则](../architecture/cross-app-links.md)定 |
| 作者工作室（编辑、资料、试跑、送审） | 作者账号 | 第一期只有我们自己的作者账号 |
| 管理端 | 内置管理员（0014） | 分类、送审、上架、下架 |

作者往资料夹与私有知识库里放东西：网页上传为主；作者若另有投研账号，也可从那边的电脑经代理读入——这是两套体系之间**唯一**的一条通道，而且只在作者本人两个账号都登录时手动触发。两个 Casdoor 应用与组织怎么配，实施前按 0014 的做法补一节。

## 三、knowmart-app 的域

```text
分类 category        宏观 / 行业（可分层）/ 上市公司（按证券代码挂）
作者 author          作者组织里的 Casdoor 用户（§二之二）；第一期 = 我们自己的作者账号
专家 expert          id、名字、一句话、分类、作者、状态（草稿 / 送审 / 上架 / 下架）、当前版本
专家版本 version     不可改写；内容 = 发布清单（§三之二）
资料夹 folder        每位专家一份：条目（名字、类型、版本、sha256、大小、出处与授权说明）、对象存储前缀 `knowmart/<expert>/…`、索引
作者知识库 library   每位作者一份，同样的条目；挂接表记录哪些条目的哪个版本挂给了哪位专家
选用记录 selection   哪个用户、哪个项目、哪次委托、哪位专家哪一版、何时；供计费与作者看用量（不含对话内容）
```

| 接口面 | 给谁 | 做什么 |
| --- | --- | --- |
| Web | 用户、作者 | 市场：三类浏览、搜索、专家页（六问、步骤、验收、知识库概况、用量）；「选这位」回跳；作者工作室（第二期开放） |
| Admin | 我们 | 分类、送审清单、上架 / 下架 / 紧急撤回、作者管理 |
| Internal | knowbench-backend、沙箱 MCP | `GET /internal/experts/{id}@{version}`（发布清单原文，供编排）；知识库三个工具（§四）；选用记录写入；授权状态查询 |

skill 的真源从 `knowbench-backend/.../packs.py` 搬到 knowmart 的数据库；knowbench 按 `id@version` 取并缓存，编排期间版本钉死。

## 三之二、专家版本 = 可执行的发布清单（吸收对比分析第五节）

版本不可改写之外，一个版本要把「这一版到底承诺什么、依赖什么」全部固定下来：

| 内容 | 记录什么 | 避免的问题 |
| --- | --- | --- |
| 身份与服务说明 | 专家、作者、服务规格与适用边界（六问） | 同名专家或宣传变了，承诺说不清 |
| 方法与步骤 | 工作流、每步输入输出、验收、失败去向 | 作者更新后在途委托的含义变了 |
| 资料清单 | 专家资料夹与挂接的作者知识库条目，**各自钉住版本与 sha256** | 方法没变，知识内容却悄悄变了 |
| 依赖与兼容 | 用到的工具、要的数据集、授权、必要的运行时、已验证过的模型范围 | 上架后才发现跑不起来 |
| 验收规则 | 作者给的检查，加平台要求的独立检查 | 作者自定宽松规则掩盖错误 |
| 评测证据 | 数据版本、题目范围、时间、模型、检查结果 | 把一次成功当成普遍有效来宣传 |

| 规则 | 说明 |
| --- | --- |
| 资料被多位专家引用 | 作者知识库里的同一份资料可挂给多位专家，但每个专家版本钉住它引用时的版本 |
| 作者换掉或删除资料 | 区分「停止新的引用」与「历史委托所需证据的保留」；因权利或安全问题必须撤回时，标明旧委托无法完整复现，不再承诺可用 |
| 记录了模型版本也不保证结果一样 | 复核以当次输入、取数结果、计算记录、交付快照为准；重跑用于比较，不宣称逐字复现 |
| 发布流程（建议，不是新的状态枚举） | 草稿 → 结构与依赖检查 → 作者试跑 → 平台独立评测 → 审核 → 发布。发布前至少覆盖正常输入、信息不足、缺依赖、执行失败、不适用的问题；作者自测与平台结果分开保存；试跑用专门的测试数据与环境，不读真实用户的项目 |
| 下架与紧急撤回 | 普通下架：停止新的选用，在途委托按已有承诺处理。紧急撤回：停止相关授权与执行，并说明原因。两种都保留已有交付的必要记录，不用静默替换版本的办法「修复」历史 |

## 四、专家的云上知识库怎么被读

沙箱里加一个 MCP `sunmoon_knowmart`（与 `sunmoon_workbench`、`sunmoon_knowbase` 同一套令牌机制，`aud=knowmart`，`sub=用户`，加 `expert`、`version`、`task`、`exp`）：

| 工具 | 做什么 |
| --- | --- |
| `list_expert_library` | 列这位专家这一版知识库的条目 |
| `read_expert_item` | 读一条（大文件分页），返回内容 + 引用 `{expert, item, version, sha256}` |
| `search_expert_library` | 按问题找片段，带出处。第一期先做全文；语义索引第二期 |

| 规则（吸收对比分析第七节） | 说明 |
| --- | --- |
| 授权的生命周期 | 令牌由 knowbench 在一次委托开始编排时签发，只带选定的那一位专家、那一版；委托到终态授权作废。**旧授权不因同一段对话里开始了新委托而复活**，新委托另签 |
| 撤销要即时 | 只靠签名没过期不能即时撤销：knowmart 每次调用除了用平台公钥就地验签（`security.md` MCP token 一行），还要查一次授权状态（委托是否已到终态、专家是否已紧急撤回） |
| 只读这一版的清单 | 工具只返回该版本发布清单里钉住的条目与版本 |
| 访问隔离不等于内容保密 | 用户看不到原件，但读进模型上下文的内容不能承诺「绝不会被转述」。做法是按需检索、控制引用粒度与读取范围，对直接索要整库的使用定明确规则；真正必须保密的方法或计算，评估改成受控服务只返回必要结果（复杂度与收益另判） |
| 资料授权 | 作者能上传不等于有权让别的用户的模型读取：发布时说明资料来源与允许的使用方式，并有撤回流程。这是市场的内容授权机制，不代替具体的法律判断 |

knowbase PRD「已知的缺口：文档检索」里的 `search_documents` 先在这里做出来，以后公共库复用。

## 五、选专家：跳出去、跳回来

```text
投研 专家对话框 ──「选专家」──▶ knowmart 市场页（链接带业务参数与 from=knowbench、ref=<项目或对话的引用>）
                                   用户浏览三类、看专家页、点「选这位」
投研 专家对话框 ◀── knowmart 按服务端登记的回跳目标跳回，带 expert=<id>@<version> 与原 ref ──┘
   显示选定专家的名字与承诺；提交后编排按这一版做
```

| 规则 | 说明 |
| --- | --- |
| 跳转 | 用现成的 `CrossAppLink`，不手拼地址 |
| 回跳地址 | **不从链接里接受回跳地址**：只带 `from`、`ref`，knowmart 按服务端登记的各应用回跳目标拼回去（[跨应用跳转规则](../architecture/cross-app-links.md)；旧骨架里的 `return=` 示意作废） |
| 回跳校验 | knowbench 收到 `expert` 后向 knowmart internal 取一次，确认上架中；下架或撤回的拒绝并提示换一位 |
| 市场页直接开工 | 专家页上也有「用这位专家」：跳到投研专家对话框，专家已选 |
| 版本 | 委托里钉死选定时的版本；作者发新版不影响在跑的委托 |
| 登录 | 市场面认投研用户的方式按 §二之二 的跨应用契约做，跳过去不用再登录 |
