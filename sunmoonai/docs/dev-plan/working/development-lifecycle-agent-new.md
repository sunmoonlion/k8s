## 0.2 人与 Agent：同一套生命周期，不同的工作仓供给

人和 Agent 做的是同一类事：领受一件有边界的工作，实施、验收、留证、交付。
差别不在 supervisor 怎么当，而在**工作仓从哪来**。

### Agent 侧：请求进仓

```text
前端用户
  │ 发请求
  ▼
FastAPI
  │ 校验、授权、整理成 Task，发给 Agent
  │
  ├─ 简单任务：不必建仓；Agent 在获准工具面内直接执行
  └─ 复杂任务：在 sandbox 中构建 git 仓库，
               按该 Task 把需要的材料塞进这个仓库，
               再把 Agent 放进这个仓库工作；
               后续按需要建立 worktree
```

FastAPI 是工作仓的供给方，**不是 supervisor**。它不派活、不选优、不整合、不验收。
它做的是人侧「建立 git 仓库并把任务材料放进去」那一步的自动化。

塞进仓库的材料由该 Task 决定：原始请求、边界、验收、允许的上下文入口、基线代码
或所需数据，以 Task 契约为准。不同 Task 进不同的仓；不得把上一 Task 的仓或材料
复用到下一 Task，也不得由 Agent 在 sandbox 外另 `git init` 替代 FastAPI 已供给的仓。

### 人侧：人建立仓

人这边没有 FastAPI 代劳：**git 仓库由人建立，worktree 也由人建立。**
人同时可以是请求提出者、执行者和 supervisor。后一种与本文的 Agent supervisor
**地位等同**。

### 对照

| 动作 | Agent 侧 | 人侧 |
| --- | --- | --- |
| 受理并任务化 | FastAPI 把前端请求整理成 Task | 人提出并冻结任务包 |
| 建立工作仓 | FastAPI 在 sandbox 按 Task 构建 git 仓库并塞入材料 | 人建立 git 仓库 |
| 并行隔离工作区 | supervisor 按需建立 worktree | 人建立 worktree |
| 派活 / 选优 / 整合 | Agent supervisor | 人（地位等同） |
| 单路实施 | 被放进该仓的 Agent | 人亲自做，或派一名助手 |
| 产出物与 commit 落点 | 只写派给自己的 worktree + 命名分支 | 只写自己的 worktree + 命名分支；人的主 checkout 不是投稿箱 |
| 批准、取消、追加预算、终审、降级流程、责任归属 | 无；最终权力在人 | 人，见 human 文 |

读本文时把「supervisor」换成「人当协调者」，规则不减。人向多名助手派活时，
隔离、评审与选优仍按 §3 执行，不因执行者是人而豁免。

**2026-09-02 的直接教训：**多个助手把同一相对路径的未提交 md 写进人的主
checkout，后写覆盖先写，Git 不报冲突、不留历史。正确做法是每人写在自己的
worktree 与命名分支里。完整场景处置见 §5。

# 第一部 · 单 Agent 内核

## 1. 单 agent 内核

任何一件开发工作，无论单路还是后来展开为 supervisor fan-out，都必须先满足本节。
§3 只增加并行候选时的额外步骤，**不减免本节**。人当 supervisor 时同样先满足本节。

### 1.1 共同纪律

无论单 agent 还是 supervisor，每次任务都必须：

1. 保护原始请求，不用自己的计划覆盖用户意图；
2. 只在获准的范围、工具、数据和副作用边界内行动；
3. 把事实、推断、假设、缺失和未经运行验证的结论分开陈述；
4. 对长期、跨会话或可中断的工作写持久 checkpoint（§1.5）；
5. 完成契约无法满足时请求输入、提出改判或明确失败，不伪造完整结果；
6. 在最终版本上运行与风险相称的验证，并报告原始输出位置；
7. 未经授权，不推送、发布、合并、删除远端资产或扩大外部影响（§1.7）。

Agent 侧的「原始请求」是前端用户提交、经 FastAPI 固化进 Task 的那一份，一字不改。
人侧是任务包里冻结的原话。两边都不得用计划稿覆盖。

### 1.2 上下文路由

先读同一组入口，再按改动范围深入。不要把整个文档树塞进提示词；上下文越多不等于
信号越好，过量材料会把判断锚定在既有结论上。

Agent 侧优先使用 FastAPI 已塞进 sandbox 仓的材料；那就是本 Task 的允许上下文。
需要仓外材料时，必须仍落在 Task 授权的工具面和数据源内，不得自行扩大检索范围。

| 每次必读 | 用途 |
| --- | --- |
| [`../project-guide/overall-architecture.md`](../../project-guide/overall-architecture.md) | 仓库、依赖方向与跨 App 边界 |
| [`constraints.md`](../constraints.md) | 不可违反的规则；违反者不进入方案比较 |
| [`../project-guide/repos/investment-app.md`](../../project-guide/repos/investment-app.md) | 当前运行时事实和已知未实现 |
| 本文 §1.3 | 本工作单元的原始请求、边界、验收 |
| sandbox 仓内由 FastAPI 塞入的任务材料 | Agent 侧本 Task 的允许上下文与基线 |

| 改动范围 | 继续读取 |
| --- | --- |
| 跨 App 契约、检索或身份 | `project-guide/topics/` 对应主题，以及提供方代码和消费锁 |
| 产品 Task 目标语义 | [`request-lifecycle.md`](request-lifecycle.md) |
| 当前实现、覆盖与已知缺口 | [`../project-guide/repos/investment-app.md`](../../project-guide/repos/investment-app.md) |
| 当前阻塞与交接 | [`handoff.md`](../handoff.md) |
| Git、分支、子模块或推送 | [`../working/collaboration.md`](../../working/collaboration.md) |
| 前后端或组件内部约束 | 目标目录向下生效的 `AGENTS.md` 和相邻代码测试 |
| 需要人类批准或终审 | [`development-lifecycle-human.md`](development-lifecycle-human.md) |

历史设计、候选稿和 `codex-reference/` 只作研究输入，不具规范效力。不得把其中的
目标态或旧快照当作当前实现。

### 1.3 冻结工作单元

动手前把本单元写成不可覆写的任务包（PR、Issue、sandbox 仓内的持久记录，或等价
载体）。至少包含：

- 用户原始请求，一字不改；
- 涉及的仓、子模块和基线 commit；
- 包含什么、不包含什么、不包含部分归谁；
- 硬门禁与质量偏好，两者分开；
- §1.2 的共同上下文入口；
- 时间、token、工具、联网、沙箱与最大轮次；
- 需要人类批准的动作。

Agent 侧：产品 `Task` 是 FastAPI 的受理对象，不是开发侧任务包的替代。Task 解决
「这是谁的请求、预算和授权是什么」；任务包解决「本工作单元实现什么、验收什么」。
复杂任务的 sandbox 仓由 FastAPI 按 Task 建好并塞入材料，任务包仍须在仓内冻结，
不得只靠 Task 行或会话记忆充当任务包。

需求发生实质变化则结束本单元，以新任务包重开，不在旧包上静默改口径。Agent 侧
对应为新 Task 或经批准的新 Attempt，不在已冻结仓里改原始请求。

### 1.4 不得自我批准

执行者——无论是 Agent 还是人亲自实施——不给自己的产出做终审，不批准自己的基线，
也不独自把别人的意见判成误报。角色可以在不同轮次互换，**自我批准在任何轮次
都不成立**。人当 supervisor 时这条同样成立：不得因为「人可以拍板」就给自己的
实施做终审。

- 单路实施的验收方不得是实施作者；
- 没有第二名可运行验证的助手时，由人类验收，并保留门禁原始输出；
- supervisor 不能通过询问自己的 subagent、或取得多数同意来制造批准；
- 高风险动作、预算追加、规范修订、生产发布的最终批准权归人类，见
  [`development-lifecycle-human.md`](development-lifecycle-human.md)；
- 不得为了凑齐角色把裁判权交回实施作者。

### 1.5 Checkpoint：会话不是账本

Agent 没有跨会话记忆。人有记忆，但传不出去。判据就一句话：**把当前会话杀掉，
另一个执行者只读仓库能否接着做？**不能，就是没落盘。

必须持久的内容：请求与 Work Unit、当前基线、已完成和未完成范围、关键决定、
工具或测试结果、已发生副作用、预算消耗、阻塞、下一动作，以及恢复前必须重新验证
的事实。去向：

- 状态、决定、阻塞 → 由 **supervisor / 主驾驶** 写入 [`handoff.md`](../handoff.md)
  或任务包记录；执行者把自己的 checkpoint 写进**自己的 worktree**，不写共享
  `handoff.md`。Agent 侧另按产品契约回写 Attempt checkpoint；
- 覆盖与缺口 → 实现矩阵（由有权方更新，不是每个候选各写一份覆盖共享文件）；
- 代码与验证 → **自己分支上的 commit** 及门禁原始输出。

三条约束：

- checkpoint 是恢复输入，**不是第二份代码真源，也不保存凭据**；
- 恢复时重新验证：请求是否仍有效、基线是否变化、权限是否撤销、依赖是否满足——
  不得根据旧上下文无条件续跑；
- 恢复不得重复已记账的外部副作用。

接手时先读交接再动手。不得只靠 prompt 自律或聊天记录声称"上次已经验证"。

### 1.6 迟到结果

两种迟到，分别处置：

**冻结后替换**：工作单元或候选一旦冻结，晚到的替换不算数。不得原地改同一
commit / 同一提交物；修复必须产生新 commit 并标为冻结后修订，原记录保留；冻结
之后才出现的产出不进入本轮比较或验收，除非任务包明示重开。

**主线采纳后的在途结果**：一件活被判定完成后，**同一活的其他在途产出一律作废**，
不得覆盖已采纳结果；已取消或已超时分支的后续提交不得进入整合；来自已取消、
已替换、过期基线或已关闭请求的结果标为 stale，只能作为证据参考。迟到结果确需
采用时，建立新的改进或重新处理请求——不写入主线、不执行副作用、不推翻已交付
结果。

判定依据必须是**可验证的凭据**（commit、时间戳、冻结记录），不是"看起来更新"。
开发侧没有租约机制，这条靠整合方显式核对：整合前必须确认每个待吸收 commit 仍在
有效分支上、且提出方未撤回。这是 Git 冻结语义，不是产品 worker 的租约 / fencing；
产品迟到写入见 [`request-lifecycle.md`](request-lifecycle.md) §4.5。

### 1.7 工具权限边界

Agent 可用的动作面比人窄，且**必须窄**。sandbox 仓是 FastAPI 供给的工作区，
不是对外发布许可证。

| 动作 | 约束 |
| --- | --- |
| 在**派给自己的** worktree 内改文件、提交、建自己的命名分支 | 复杂任务的正常工作方式；不构成对外发布 |
| 写入人的主 checkout、其他助手的 worktree、或任何未派给自己的工作区 | **禁止**。相对路径相同即覆盖；`-new` 后缀不是隔离 |
| 在已供给的 sandbox 仓内由 supervisor 建 worktree | 多执行者时的正常隔离；单执行者可在供给仓的默认工作区写，仍用自己的分支 |
| 自行 `git init` 另起一仓，或改用 sandbox 外的仓 | 禁止。顶层工作仓由 FastAPI 供给（人侧由人建立） |
| 把上一 Task 的 sandbox 仓或材料拿到本 Task 用 | 禁止 |
| 推送、开 PR、合并、删远端分支 | 未经用户授权不得执行（§5）；获准也只推自己的命名分支 |
| 删除文件或目录 | 先读内容；未在 git 里的东西删前必须备份；不删别人工作区的文件 |
| 改动他人分支 | 需用户明确授权，且提交信息注明"代为提交" |
| 执行破坏性命令（`reset --hard`、`push --force`、`rm -rf`） | 逐次授权，不适用"上次批准过" |

**授权不跨场景延续。**在 A 分支批准过推送，不等于 B 分支也可以；一次批准的危险
动作不构成下次的默许。对 Agent：Task A 的授权不延续到 Task B。

### 1.8 范围、失败与改判

- 只在任务包范围内工作；超范围、越权或需要追加成本时请求人类批准，不静默扩张。
- 无法完成或证据不足时明确失败，留下可判定说明，不伪造完整结果。
- 改判必须说明触发、原判断错处和新判断，不装作从未判过。
- 事实进入 project-guide 前必须回读代码或实物重新取证，不能把目标态文字直接写成现状。
- 凡能落实为代码、测试或门禁的纪律，必须落实为代码、测试或门禁，不能只写在提示词里。

一次会话内可完成、无长期副作用的小请求可以简化，但仍必须：不篡改原意、结论有与
风险相称的证据、"完成"可判定、若改判则交代变化。**是否简化的裁量权在人，不在
Agent。** Agent 不得自行把完整选优降为单路。人如何行使裁量见
[`development-lifecycle-human.md`](development-lifecycle-human.md)。

### 1.9 单路实施与定向审核

解法明确、改动局部、可由测试充分判定时，走单路：冻结请求 → 实施 → 独立验收
（§1.4）。Agent 侧对应：FastAPI 已建仓（若需要）→ 单 Agent 在**派给自己的
worktree + 命名分支**实施 → 独立验收。即使只有一名 Agent，也不得写进人的主
checkout。

已有唯一产物、只需判断是否成立时，走定向审核：冻结版本 → 两阶段审核 → 处置 →
在最终 commit 回归。

不要让所有工作都支付完整竞选成本。涉及安全边界、数据迁移、跨 App 契约、不可逆
外部动作或生产发布时，最终批准权归人类。

## 2. 按风险选择是否展开为 supervisor

当本执行者需要向其他开发助手派活、收集候选并选定主线时，它就是 supervisor。
人当协调者与 Agent 当 supervisor **是同一个角色**。派活、隔离、评审、选优、整合
是它完成 §1 那件工作的内部展开，不是另一份生命周期。

| 流程 | 适用条件 | 最少经过 |
| --- | --- | --- |
| 单路实施 | 解法明确、改动局部、可由测试充分判定 | §1 |
| 定向审核 | 已有唯一产物，只需判断是否成立 | §1.9 |
| 最小选优 | 需要独立候选，但风险不足以支付完整评审团成本 | 冻结任务包 → 隔离候选 → 一名未参赛决策方 → 处置 → 回归 |
| 完整选优 | 解法不明确、影响跨层或跨仓、错误代价较高 | §3 全流程 |
| 胜者改进 | 主线已经选定，只吸收其他候选的局部优点 | §3.12—§3.14 |

最小选优只降低评审数量和留证规模，**不降低硬门禁或角色分离**。
Agent 不得自行把完整选优改成最小选优或单路；那是人的裁量。

# 第二部 · 展开为 supervisor

## 3. 当本执行者是 supervisor：fan-out

本节对 Agent supervisor 和人当协调者同样适用。

进入本节的前提：工作仓已经存在。Agent 侧由 FastAPI 在 sandbox 建好 git 仓库并
按 Task 塞入材料；人侧由人建好 git 仓库。supervisor **不负责建顶层仓**，负责
在已有仓里按需建 worktree、派活、选优、整合。

### 3.1 派工契约

supervisor 只有在 Work Unit 能独立推进、且并行收益大于协调成本时才 fan-out。
每个 Work Unit 至少固定：

```text
work_unit_id, parent_request_id, owner
objective, included_scope, excluded_scope
input_refs, baseline_commits, allowed_context
expected_output, acceptance, evidence
permissions, budget, deadline, stop_condition
dependencies, checkpoint_location, result_status
workspace_path, exclusive_branch, forbidden_write_paths
```

`workspace_path` 和 `exclusive_branch` 必须在派工时写死，且对每个执行者唯一。
`forbidden_write_paths` 至少包括人的主 checkout、其他候选 worktree，以及非
supervisor 不得写的 `handoff.md`。执行者动手前核对自己的 cwd 就是
`workspace_path`，当前分支就是 `exclusive_branch`；对不上则停，不写任何文件。

- 派工只能**收窄**顶层请求的权限和预算，不能凭空扩大；
- 多个 Work Unit 不得同时成为同一可变事实的权威写入者；确需共同修改时，先划分
  所有权或改为串行；
- subagent 返回的是候选结果，supervisor 仍负责核对范围、证据、冲突和验收——
  **"已派工"或"全部返回"不等于顶层完成**；
- 顶层请求满足验收后，不必等待所有 subagent：其余执行必须停止、取消，或明确降为
  不影响主线的只读参考（迟到处置见 §1.6）。

Agent 侧：产品子 Task / `COORDINATION` 仍只由
[`request-lifecycle.md`](request-lifecycle.md) §8 约束。本节的 Work Unit 是开发侧
派工，落在 sandbox 仓的分支与 worktree 上，不另造一套产品状态机。

### 3.2 提案隔离

候选冻结前，各候选方只能看到同一任务包，不得读取其他候选、发起方倾向、预设解法
或指定检查点。看到已有答案后产生的内容是改写，不再计作独立候选。

### 3.3 证据先于投票

能由代码、测试、契约或硬性验收裁决的主张，必须逐条裁决，不得交给多数票。
投票只处理证据无法区分的偏好，例如同样合格的命名、结构或维护成本取舍。

### 3.4 候选人与裁判分离

候选作者可以指出其他方案的问题，也可以提交建议，但不拥有最终有效票，不审批自己的
基线，也不独自判定后续建议为误报。最终选择与整合由未参赛的独立方完成；没有独立方
时交给人类维护者，不用候选互投伪造独立裁决。人当 supervisor 时也不得让候选助手
互投凑独立，决策留在未参赛的人。

### 3.5 固定版本、完整留证

候选、评审、改进和最终结果都绑定不可变 commit。分支名只是运输通道，不是评审对象。
删除临时 worktree 不等于删除证据；决策、处置、测试结果和相关 commit 必须仍可追溯。
sandbox 仓被回收前，证据必须已经落到产品账或可达的外部载体上。

### 3.6 角色与利益冲突

同一执行者可在不同轮次换角色，但同一轮不得兼任有冲突的职责。

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 协调方 / supervisor | 冻结任务包、在已有仓内分配 worktree、匿名随机排序、收集记录 | 泄露候选或临时改变规则；自行另建顶层仓 |
| 候选方 | 独立调查、实现、自检并提交固定版本 | 读取其他候选；参与最终计票 |
| 验收方 | 在同一基线和环境上执行硬门禁 | 因文案或身份偏好放宽门禁 |
| 评审方 | 独立审查候选，逐条给证据和偏好判断 | 在交卷前读取其他评审 |
| 决策方 | 在合格候选中按预定规则选定主线 | 参加本轮候选竞选 |
| 整合方 | 从选定 commit 出发处置改进并形成最终版 | 默认接受优胜作者的判断 |

作者身份无法隐藏时必须声明。匿名化用于降低偏差，不得写成绝对保证；代码风格、
目录选择和提交习惯仍可能泄露身份。

角色数量不足时可以兼任无直接利益冲突的职责，但候选方不得兼任本轮决策方，也不得
作为自己基线的最终整合方。无法保留这两项分离时，由人类维护者承担决策；不得为了
凑齐角色把裁判权交回候选方。

### 3.7 隔离产生候选

每个候选使用独立会话与独立可写工作区，从同一 commit 开始。代码任务使用独立
worktree **且独立命名分支**；同机 worktree 只能隔离**文件写入**，不能阻止读取
其他 Git 对象，因此必须如实标注隔离是机制保证还是行为约束。

Agent 侧：worktree 建在 FastAPI 已供给的 sandbox 仓内，不另起远端 fork 来隔离。
人侧：人在自己建立的仓里为每个助手建 worktree。两边的隔离语义相同。
**多执行者共用供给仓的默认工作区（或人的主 checkout）等于没有隔离**，见 §5.4。

需要脚本化产生候选时使用 [`parallel-proposals.py`](../parallel-proposals.py)。它已验证
独立进程、独立 `CODEX_HOME`、失败隔离与 manifest 写入；真实模型调用尚未在本项目
验证，不得把脚本存在写成端到端流程已经可用。

候选提交时声明：候选 commit 及各仓/子模块 commit、已覆盖与未覆盖范围、执行过的
验证和原始输出位置、已知缺陷与假设、对每项关键主张的代码或测试证据。

### 3.8 冻结、匿名与随机化

协调方确认 commit 和依赖均可读取后，为候选生成随机编号，并为不同评审方随机排列
展示顺序。候选自评、作者、分支名和模型信息在独立评审阶段隐藏。冻结语义见 §1.6。

### 3.9 两阶段独立评审

评审方必须未参加本轮候选竞选，且在交卷前彼此不可见。

1. **独立审**：只读取原始请求、匿名候选 commit、统一验收标准和允许的项目入口；
2. **对照审**：独立审冻结后，再读取候选自评、已知盲区和验证记录，检查双方遗漏。

每份评审必须写明所审 commit、覆盖和未覆盖范围、阻断与非阻断问题、证据、建议验收
标准，以及哪些结论实际运行过、哪些只是静态判断。

### 3.10 逐条证据裁决与硬门禁

先把候选的关键主张拆开，形成裁决表：

| 主张 | 候选 | 证据或命令 | 结论 | 理由 |
| --- | --- | --- | --- | --- |
| `<稳定 ID>` | `<编号>` | `<位置/输出>` | 证实 / 证伪 / 未决 | `<可复核说明>` |

下列任一情况发生，候选不进入偏好比较：必须测试失败；违反 `constraints.md` 或明确
范围边界；存在未解决的阻断级正确性、安全性、数据或迁移风险；commit、子模块对象或
验证证据无法取得；**提案隔离已经被破坏且无法恢复公平比较**。

**全体一致不是免检理由。**多个相似模型可能共享盲区；对影响结论的全体一致主张，
决策方至少额外抽查一次其共同证据来源。

### 3.11 只对剩余偏好评分

硬门禁通过、事实主张裁决后，独立评审方才对剩余偏好使用统一量表。默认维度为
正确性、完整性、可维护性与实施成本；权重在候选产生前冻结。

有效票只来自未参赛评审方。候选方的互评可作为问题线索，但不进入最终计票。
评审不足三名或平票时，由预先指定的未参赛决策方裁决；仍无法区分则交人类，不允许
事后修改量表。公布结果使用"本轮选定"，不得写成"已证明正确"。

### 3.12 从选定 commit 派生改进

选定 commit 冻结为只读基线。落选方可从该 commit 新建独立 worktree 和改进分支，
但只做能够独立成立的增量修改：

```text
selected/<run-id>
├── improve/<agent>/<claim-id>
└── integrate/<run-id>
```

一条主张一个提交，提交说明必须包含依据、改动边界、验证结果和基线 commit。需要
整体重写、结构重排或依赖其他改进才能成立的内容，不走补丁吸收；它属于新候选，
应开启下一轮选优。

这些是一次选优内部的临时分支，不取代
[`../working/collaboration.md`](../../working/collaboration.md) 的长期"一助手一命名分支"
约定。跨仓改进时，每个受影响仓都从该仓选定的 commit 建同一 `run-id` 的对应临时
分支；子模块先形成可达提交，父仓再记录 gitlink，证据账保存整组 commit 映射。

### 3.13 独立整合

整合方在独立的 `integrate/<run-id>` 分支上逐项处置改进：

| 处置 | 必须记录 |
| --- | --- |
| 接受 | 合入的 commit、理由、验证结果 |
| 部分接受 | 接受到哪、停止在哪里、最终 commit 与边界依据 |
| 拒绝 | 可独立复核的理由；能证伪时附命令或位置 |

选定候选的作者可以解释设计，但不审批自己的基线。冲突按原始请求、约束和证据解决，
不按票数、作者或提交时间覆盖。多个改进提交可以选择性 cherry-pick；不得因 patch
看起来具体或测试恰好通过，就跳过对其事实主张的复核。

### 3.14 最终回归与关闭

所有检查必须在最终 commit，而不是候选 commit 上重跑：

1. 原任务包中的全部硬门禁；
2. 被采纳评审意见附带的验收标准；
3. 每个改进提交新增的回归检查；
4. 涉及的契约双端、父仓 gitlink 和部署引用一致性检查；
5. 文档链接与漂移检查。

验收标准失败时区分实现错误与标准腐坏。修改标准必须保留原标准、原始失败输出和
改判理由，不能为了变绿静默删除。最终记录必须公布未覆盖范围和残余风险。

Agent 侧：sandbox 仓内的最终 commit 不等于产品 Task `SUCCEEDED`。Task 终态仍按
[`request-lifecycle.md`](request-lifecycle.md) 验收、持久化和交付。仓被回收后，
没有落到产品账或外部可达载体上的 commit 视作未留证。

# 落地纪律 · 所有流程共用

## 4. Investment App 的范围门禁

本文不复制项目实现，只规定执行者遇到不同改动时必须去哪里验证。人和 Agent 同样
遵守。

| 改动命中 | 必须追加的核对 |
| --- | --- |
| Agent run、状态、恢复、预算、事件或副作用 | `repos/investment-app.md` 对应章节、生产链代码与相关测试；不得由历史设计稿推断现状 |
| knowledge 检索契约 | 提供方 schema、investment 消费锁和双端契约测试 |
| Admin/Web/API | 对应面向下的 `AGENTS.md`、认证边界和端到端交互测试 |
| 数据模型或迁移 | 迁移链、数据库约束、回滚/前滚策略和数据不变量 |
| 模板共有结构 | 先判断是否属于模板职责；需要同步时按模板与实例门禁处理 |
| K8s 或发布 | bundle、release 与部署门禁；App 源码通过不代表发布可用 |
| 跨仓改动 | 每个仓分别固定 commit，并验证 provider/consumer 与子模块 gitlink |

对"已知未实现"的能力，必须先验证它当前仍未实现。不能因为类、DTO、迁移或测试
夹具存在，就宣称生产链已经接线。能力状态统一使用
[`../project-guide/overall-architecture.md`](../../project-guide/overall-architecture.md)
§8.2 的 `defined / wired / deployable / runtime-verified` 四级词典；休眠能力优先回跑
[`../project-guide/repos/investment-app.md`](../../project-guide/repos/investment-app.md)
§7 指向的 `tests/test_dormant_capabilities.py`，同时检查锚点仍存在和能力仍未接线，
不由执行者自行发明"已实现"的判断口径。

## 5. Git、分支、worktree 与产出物处置

Git 操作细节以 [`../working/collaboration.md`](../../working/collaboration.md) 为准。
本文规定：**谁建立什么、产出物落在哪、不同载体怎样覆盖、每个场景怎样处置。**

动手写任何文件之前先问四句；任一答「共享 / 别人的 / 不知道」则停：

1. 这是未提交文件、commit、分支指针，还是远端？
2. 当前工作区是不是派给我的 worktree？
3. 当前分支是不是我的命名分支？
4. 会不会有另一个执行者往同一路径写？

### 5.1 谁建立仓，谁建立 worktree

| | 顶层 git 仓库 | worktree |
| --- | --- | --- |
| Agent 侧 | FastAPI 仅在复杂任务时于 sandbox 中构建，并按该 Task 塞入材料 | supervisor 按需建立；**每执行者一棵** |
| 人侧 | 人建立 | 人建立；**每助手一棵**，不是共用 `~/master` |

- 简单任务不建仓。不得为问数或一次只读查询在 sandbox 里起 git。
- 复杂任务必须进 FastAPI 已供给的那一个 sandbox 仓。Agent 不得另 `git init`，
  不得把工作写到 sandbox 外的目录再声称完成。
- 人侧没有 FastAPI：人自己建仓，自己按需建 worktree。人当 supervisor 时，
  建 worktree 的纪律与 Agent supervisor 相同。
- FastAPI 建仓 ≠ 已派活、已验收、已交付。建仓只是工作开始的前提。
- **一仓一个默认工作区不够多执行者用。**同一 Task 有两名以上可写执行者时，
  supervisor 必须先建好各自的 worktree 和命名分支再派活。

### 5.2 四种载体，覆盖语义完全不同

隔离靠 **worktree + 命名分支**，不靠文件名。`-new`、时间戳、助手名写进文件名，
都不能阻止「同一工作区、同一相对路径」被后写覆盖。

| 载体 | 覆盖会怎样 | 隔离单位 | 评审 / 交付绑什么 |
| --- | --- | --- | --- |
| **未提交工作区文件** | 后写直接覆盖先写；无冲突、无历史、无警告 | 工作区（worktree），不是路径字符串 | 不能作为候选；只能当本地草稿 |
| **commit** | 新 commit 不摧毁旧对象；旧的要有 ref 才找得到 | 对象库 + 指向它的 ref | **评审对象就是 commit** |
| **分支指针** | 指针可被快进、重置、强推；像标签在移动 | 一分支一所有者 | 运输通道，会漂移，不单独当评审对象 |
| **远端 / 主线 / 人的主 checkout** | 共享面；未授权写入等于闯入别人的工作区或发布面 | 有权整合方 | 只有整合后的最终 commit 算交付 |

同机并列 worktree **共享 Git 对象**：文件写入被隔开，但别人的 commit 和分支名
仍可能被 `git log` / `git branch` 看到。提案阶段的「不读其他候选」是行为约束，
不是机制保证。机制保证的只有：不在同一工作区写同一路径。

### 5.3 硬规则

- 每个执行者一条命名分支、一棵 worktree；长期约定仍是「一助手一命名分支」。
- 同一分支不能被两个 worktree 同时检出。
- 执行者只写 `workspace_path`，只提交到 `exclusive_branch`。
- **人的主 checkout（如 `~/master/<仓>`）不是投稿箱**，也不是「文档原件所在所以
  该写这里」。读可以在主仓只读进行；写必须在自己的 worktree。
- sandbox 默认工作区只给**该 Task 的唯一可写执行者**。第二名执行者出现时先拆
  worktree，不往默认工作区加写者。
- 共享单面（`handoff.md`、实现矩阵的权威行）只有一个写者，默认是 supervisor /
  主驾驶。执行者的进度写在自己 worktree 的 checkpoint，由 supervisor 投影到单面。
- 未提交草稿不拿给别人比、不拷进主仓、不当作「已经交卷」。交卷 = 自己分支上的
  可达 commit。
- 未经用户授权，不推送、不开 PR、不合并、不删除远端分支；获准也只推自己的分支。
- 临时分支可在证据已落账且 commit 可达后清理；决策记录和 commit 哈希不得删除。

### 5.4 场景分处置

每行四件事：正确落点、禁止、已发生时怎么收。人和 Agent supervisor 同一张表。

| # | 场景 | 正确落点 | 禁止 | 已发生时 |
| --- | --- | --- | --- | --- |
| S1 | 单助手、未提交草稿 | 自己的 worktree；尽快 commit 到自己的分支 | 写进人的主 checkout 或共享目录 | 立刻 `mv` 到自己的 worktree，**删掉共享路径上的那份**；不要在主仓 commit 来「补救」 |
| S2 | 单助手、已 commit 未推送 | 自己的命名分支；交卷报 commit 哈希 | 在别人可能已读之后 `commit --amend`；`reset --hard` 丢掉唯一 ref | 需要改则 **新 commit**，旧哈希仍报给评审；amend 只允许尚未交付、且无人读过的本地最新一条 |
| S3 | 单助手、获准推送 | 推自己的远端命名分支 | 推 `master` / `main`；强推共享分支 | 误推共享分支：不要强推回滚；报告人，由人决定 revert 或冻结 |
| S4 | **多助手写同一相对路径**（2026-09-02） | 各写各的 worktree；相对路径可以相同 | 都写 `~/master/.../foo.md` 或同一 sandbox 工作区 | 以 **commit 哈希** 认主，不以磁盘上最后一版为准。共享路径上的未提交文件视为污染：移走、比对哈希、声明哪些候选已不独立 |
| S5 | 多助手并行选优（正确形态） | supervisor 先建 worktree+分支再派；候选只见任务包 | 先动手后补 worktree；读其他候选工作区 | 未建仓就已开写：停写，补隔离，已写出的标为可能污染 |
| S6 | 从共享目录拷走别人未提交稿 | 不拷。交卷只通过 supervisor 收集的 commit | 把别人的草稿当自己的起点 | 该路不再计独立候选；记录污染来源与时间 |
| S7 | 两助手提交到同一分支 | 不可能发生——派工时分支互斥 | 共用 `cursor` / `tmp` / `new` 这种分支名还不拆所有者 | 停写。按 commit 作者和时间拆成两条分支，原分支冻结不再提交 |
| S8 | 同一分支两处检出 | Git 默认拒绝，这是保护 | 强行绕过；删 `.git` 锁来「修好」 | 恢复为一 worktree 一分支 |
| S9 | 对已推送或已交卷分支 amend / force-push | 新 commit；必要时新分支 | `push --force` 到可能被别人 fetch 的分支 | 当作迟到替换（§1.6）：原 commit 仍在的话继续当评审对象；强推过的远端由人处置 |
| S10 | 冻结后还改「那一个」commit | 新 commit，标冻结后修订 | 原地 amend、覆盖同一哈希的工作树后再假装没变 | 新哈希进入「冻结后修订」；不进本轮比较，除非任务包重开 |
| S11 | 主线已采纳，在途 worktree 还在写 | 停写、停推；分支标 stale | 把在途文件拷进主线或继续往选定分支提交 | 在途 commit 只作参考；需要吸收则开新的改进请求 |
| S12 | 整合收主线 | 整合方自己的 `integrate/<run-id>` worktree+分支；**源是选定 commit 哈希** | 把候选工作区未提交文件拷进 `~/master`；在候选分支上直接合 | 已误拷：从 master 工作区撤出，改从 commit cherry-pick / merge |
| S13 | 胜者改进 | `improve/<agent>/<claim-id>` 新 worktree，基线是选定 commit | 改选定分支；在落选 worktree 里继续当主线改 | 选定分支已被改：从原选定哈希重新建改进分支，多出来的提交单独审查 |
| S14 | 评审意见 | 评审方自己的分支或 supervisor 指定的评审记录；读的是候选 **commit** | 写进候选 worktree；以工作区脏文件当评审对象 | 写进候选区的意见移出；评审对象改绑 commit |
| S15 | 跨仓 / 子模块 | 每个受影响仓都有该助手自己的分支；子模块先可达提交，父仓再记 gitlink | 只在父仓工作区改子模块文件当普通目录；跨仓共用一个「临时」分支名且不映射 | 补齐每仓 commit 映射；未可达的 gitlink 不进入整合 |
| S16 | sandbox 将回收 | 回收前：commit、证据落到产品账或外部可达 ref | 只把 md 留在即将删除的工作区 | 未 commit 的视为丢失；能抢救则先 commit 到仍存在的对象库并外送哈希 |
| S17 | 简单任务、无 git 仓 | 产品 Attempt / Artifact / 证据账 | 为了「有地方放 md」去写共享磁盘或人的主仓 | 已写下的文件迁到产品载体或（若已补建 sandbox）自己的分支 |
| S18 | 会话、聊天里的稿 | 要留下的立刻落到自己 worktree 并 commit | 用聊天当交卷；让别的助手去「同一路径」接盘未提交文件 | 从会话抢救到自己的分支；共享盘上的接盘文件不具作者归属 |
| S19 | 门禁输出、测试日志 | 绑 commit；放自己 worktree 或 CI artifact | 写到共享 `docs/`、`/tmp/latest.log` 这种单槽文件 | 单槽文件作废；重跑到绑 commit 的位置 |
| S20 | `handoff.md` / 实现矩阵权威行 | 仅 supervisor 或主驾驶写 | 每个助手往同一 handoff 追加自己的进度当交卷 | 冲突时以主驾驶版本为准，助手进度改从各自 checkpoint 重投影 |
| S21 | 人正在主 checkout 工作 | 助手不写主 checkout；人也不进助手 worktree 改同一路径 | 助手「顺手」改主仓里打开着的那份文档 | 助手改动撤出主仓；人的未提交改动优先保留，助手那份只存在自己 worktree 才算数 |
| S22 | 只读探索 | 不写；或只写一次性抛弃分支且不推送 | 探索写进实施分支或主仓 | 探索提交不进选优，除非任务包事先允许 |
| S23 | 删除 worktree | 先确认分支仍指向需要的 commit，证据账已记哈希 | 删 worktree 当删证据；连带 `branch -D` | 能从 reflog / 对象库找回的哈希记入证据账；找不回则记缺口 |
| S24 | 删除分支 | 证据账已有哈希且对象仍可达（或已推送）后再删运输分支 | 删分支当收工 | 同 S23 |
| S25 | 迟到 / stale 分支后续提交 | 不写主线、不推共享、不覆盖已交付 | 把迟到文件改名写进主仓「以免丢失」 | 标 stale；若要采用，新开请求，源仍是 commit |
| S26 | FastAPI 一仓、多名 Agent | 先拆 sandbox 内 worktree 再派 | 多个 runtime 挂同一工作目录 | 视为 S4：停写、拆工作区、未提交产物降级为污染草稿 |
| S27 | 跨机 / 新会话接手 | 只凭分支 + commit 恢复；cwd 必须是自己的 worktree | 凭「上次写在 master 里」接着写 | 先 `worktree list` 和 `status`；主仓出现的未跟踪文件先当污染处理（S1/S4） |

### 5.5 仓内其余协作约束

- 并列 worktree 共享 Git 对象，改进只需从选定 commit 建分支，不需要远端 fork
  来做隔离；
- 评审对象写 commit，不写会漂移的分支头，更不写工作区脏文件；
- 一项改进一个内聚提交，便于选择性采纳和证伪；
- 子模块中的提交先形成可达分支，再更新父仓 gitlink；
- 删除 worktree 不等于删除证据；sandbox 回收前证据必须已落到产品账或可达载体。

## 6. 证据账

证据按流程分级，不能只有"全套"与"零记录"两档。人和 Agent 同一套最小留证。

| 流程 | 最小留证 |
| --- | --- |
| 单路实施 | 请求记录或 PR 中固定最终 commit、验收方、门禁命令及原始输出位置 |
| 定向审核 | 任务包链接、评审、处置、最终 commit 与验证结果 |
| 最小选优 | 任务包链接、参与者清单、候选 commit 映射、决策、处置与验证结果 |
| 完整选优 | 下列完整逻辑记录 |

证据使用项目已有的请求记录、PR/Issue、CI artifact、Git commit，以及 Agent 侧的
产品 Task/Attempt/证据账。不在 `docs/` 下为每轮另建归档目录。载体可以分散，但必须
由一个稳定的主记录串起全部链接，并能由第三方读取。Agent 侧不得只把证据留在即将
回收的 sandbox 里。任何流程都不得只在聊天中宣称测试通过。完整选优至少保留：

```text
request          # 原始请求、边界、基线、门禁、资源上限
manifest         # 角色、模型、耗时、状态、异常
candidates       # 匿名编号、commit、覆盖和验证声明
reviews          # 独立审、对照审、逐条主张裁决
decision         # 门禁、偏好评分、决胜与选定 commit
improvements     # claim ID、来源、commit、测试与冲突
dispositions     # 接受/部分接受/拒绝及证据
verification     # 最终 commit 上的回归结果
```

自动化必须保证单路失败、超时或缺席也进入 manifest，不能由成功路线覆盖。无法运行
命令的评审保留价值，但必须标注"未经事实验证"，且不能替代验收方的运行结果。

候选 commit 必须来自该候选自己的分支。共享工作区里的未提交文件、从别人路径拷来
的稿，不得写入 candidates 清单。

## 7. 成本与停止规则

- 默认 2—4 个候选；超过五个前先说明新增独立信号为何值得评审成本；
- 完整交叉阅读是二次复杂度，候选较多时采用平衡分配，但每个候选获得相同评审覆盖；
- 改进默认一轮，最多三轮；达到上限仍有结构性分歧时交人类或重开任务，不无限润色；
- 连续一轮没有关闭阻断问题或新增可验证价值时停止迭代；
- 资源上限、超时、外部副作用和人工批准点必须在启动前写入任务包。

Agent 侧这些上限同时受产品 Task 预算约束；开发侧停止规则不能突破 Task 预算。
突破预算必须按 human 文走追加批准，不得由 supervisor 自行加额度。

## 8. 完成判据

只有同时满足以下条件，完整选优才可关闭：

- 所有候选来自同一冻结任务包和基线；
- 候选隔离方式与可能泄露已如实记录；
- 候选、评审、改进和最终结果全部绑定 commit；
- 硬门禁和逐条证据裁决先于偏好评分；
- 最终有效评审与候选作者分离；
- 选定主线、少数意见、未决主张和残余风险已公布；
- 改进从选定 commit 派生，并由独立整合方逐项处置；
- 最终 commit 已回跑全部有效验收；
- 涉及的多仓提交和 gitlink 均可取得；
- 证据账完整，且没有把"经过评审"夸大成"已经证明正确"；
- Agent 侧：sandbox 内最终结果已按产品契约持久化；仓回收后证据仍可达；
- 没有任何执行者把未提交产出留在人的主 checkout 或其他共享工作区；交卷清单里
  每一项都是执行者自己分支上的 commit。

缺少任一项时，只能按实际阶段称为"候选完成""评审完成""本轮选定"或"待验证整合"。
单路实施关闭条件是 §1 全部满足，且独立验收方（或人类）已留下门禁原始输出。

## 9. 助手侧反模式

| 反模式 | 失败方式 |
| --- | --- |
| 候选阶段偷看其他候选或发起方倾向 | 产出是改写不是独立信号，选优失效 |
| 自评自收、自我批准 | 验收失去独立性，缺陷被背书 |
| 只靠 prompt 自律执行纪律 | 会话切换或换助手后纪律蒸发 |
| 把会话记忆当状态账 | 接手者无法恢复现场，决定无痕丢失 |
| 冻结后原地替换或把迟到 commit 算进本轮 | 比较对象漂移，无法复核 |
| 静默扩大任务范围 | 越权副作用无人批准 |
| 伪造完整结果掩盖缺口 | 验收被污染，缺口被当成已完成 |
| 把"已派工"或"全部返回"当作顶层完成 | 未核对的候选结果被当成主线结论 |
| 把上次批准当成下次默许 | 授权跨场景蔓延，越权动作被背书 |
| checkpoint 当第二真源或保存凭据 | 旧快照压倒代码，凭据外泄 |
| Agent 自行 `git init` 另起一仓 | 丢掉 FastAPI 已塞入的材料，工作仓与 Task 脱节 |
| 把 FastAPI 建仓当成 supervisor 已完成 | 供给工作区被误认为派活、验收或交付 |
| 简单任务强行建仓，或复杂任务不进已供给的 sandbox | 要么浪费隔离成本，要么把改动写到仓外 |
| 证据只留在即将回收的 sandbox | 仓一删，决策与验证无痕消失 |
| 人当协调者就跳过隔离与角色分离 | 独立信号退化成改写；候选人互投伪造独立 |
| 多助手写入同一工作区同一相对路径 | 后写覆盖先写，无冲突无历史；独立稿变成一份 |
| 用 `-new` / 时间戳 / 助手名当隔离 | 文件名不是工作区；共享路径上照样覆盖 |
| 把人的主 checkout 当文档原件投放点 | 覆盖人的未提交改动，也覆盖其他助手的草稿 |
| 未提交就让别人来「同一路径」接盘 | 拷走的是污染源；接盘者不再独立 |
| 交卷报路径不报 commit | 路径会漂、会被覆盖；评审对象丢失 |
| 每个助手都写共享 `handoff.md` | 单面交接被互相覆盖，游标失真 |
| 在候选分支上直接合主线，或把脏工作区拷进 master | 绕过冻结 commit，整合不可复核 |

## 10. 常见失败方式

表中"项目实例"指已经发生并记录的失败；"设计风险"表示尚未经本项目完整实跑验证，
不得把两者混为同等级证据。既有项目实例的完整说明以表内引用为准。

| 失败 | 证据性质与出处 | 控制 |
| --- | --- | --- |
| 候选提前读取其他方案 | 污染机理与文档重写实例：`doc-conventions.md` §5；看到已有答案后的产出不再独立 | §3.2、§3.7 |
| 把历史设计或目标态当成代码现状 | 项目实例：`doc-conventions.md` §5 | §0、§1.2、§4 |
| 候选人互投决定胜负 | 被审方兼任判定方、错误相关的结构失败已有项目实例；候选互投这一具体流程尚未实跑 | §1.4、§3.4、§3.11 |
| 多数票覆盖失败测试 | 共同盲区实例：`doc-conventions.md` §5 | §3.3、§3.10 |
| 只写分支名，不固定 commit | 2026-08-27 项目评审曾引用旧提交，而主方已领先三个提交 | §1.6、§3.5 |
| 优胜作者独自拒绝改进 | 2026-08-27 吸收中出现误报和部分接受边界只能由被审方单方划定 | §3.4、§3.13 |
| 大补丁混合多条主张 | 设计风险，尚未在本项目实跑 | §3.12、§5 |
| 合并后不在最终 commit 回归 | 2026-08-27 评审给出的八条验收标准曾长期无人执行 | §3.14 |
| 只测 investment 一端就宣布跨仓契约完成 | 现行硬规则：`constraints.md` C4 | §4 |
| 删除分支时连同决策依据一起删除 | 改判与证据纪律 | §1.5、§3.5、§6 |
| 把产品 Task 当成开发任务包，或把 sandbox commit 当成 Task 已成功 | 两套生命周期边界相邻但不是同一对象 | §0、§0.2、§1.3、§3.14 |
| sandbox 回收后证据不可达 | 设计风险；工作仓是临时供给，不是档案 | §3.5、§5.5、§6 |
| 多助手把同一相对路径的未提交文件写进共享工作区 | **项目实例（2026-09-02）**：至少三路并行重写同一 `*-new.md`；写进人的主 checkout 的两路哈希相同，后写即可覆盖先写；写在自己 worktree 的一路得以幸存。文件名加 `-new` 未构成隔离 | §1.7、§3.7、§5 |
| 以工作区最后一版代替 commit 做交卷或比选 | 与上行同一实例：磁盘上的「当前文件」没有作者归属，也不能证明谁先写完 | §5.2、§5.4 S2/S4/S12 |
| 整合时拷贝未提交文件进主仓 | 设计风险；绕过选定哈希，主仓变成公共投稿箱 | §5.4 S12、§3.13 |
