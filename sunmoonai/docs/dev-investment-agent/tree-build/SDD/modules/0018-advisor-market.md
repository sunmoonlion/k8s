# 专家市场 advisor-app 与专家的云上知识库（0018，骨架）

> 状态：所有者 2026-10-11 定方向（「专家市场：我们专门创建一套前后端组件即 advisor-app，由 tpl-app 实例化」「每位专家的云上知识库是云上专家私有，选定后 codex 可读」「我们首先上架，以后主要靠用户，肯定要有用户的编辑页，这是一个大架构，你先搭骨架，后细化」），远程写骨架，未实施。取代 `0011-library.md`（用户私有云端库作废：「用户已经不会上传资料了」）与 `PRD/apps/knowledge.md` 六之二的三层表。与 0017（专家对话框「选专家」）、0019（侧边栏底部三项）配套。

## 一、决定

| 项 | 定了什么 |
| --- | --- |
| 第四个应用 | `advisor-app`，由 `tpl-app` 实例化：`advisor-backend`、`advisor-web-frontend`（市场 + 作者编辑页）、`advisor-admin-frontend`（上架审核、分类）。与 knowledge 是不同的概念：advisor 把 profile 内化为工作流给 Codex 用，knowledge 加工存储采集来的信息；专家知识库由 advisor 自己存、自己索引（甲） |
| 市场怎么分 | 三大类：宏观、行业、上市公司；每类若干专家 |
| 一位专家是什么 | **知识库 + skill**。skill 就是现在的专家 profile / 专家包（六问、步骤、每步验收、工具范围、放行表）；知识库是这位专家在云上的私有资料 |
| 谁上架 | 第一期我们；以后主要靠作者（独立的账号体系，§二之二），所以要有作者编辑页。第一期只有我们自己的作者账号 |
| 知识库归谁、谁能读 | 归这位专家（作者）私有；用户选定这位专家后，那段专家对话里的 Codex 可读，别处读不到；用户看不到原件 |
| 用户还上传吗 | 不。用户的 Codex 能读的资料只有：项目目录、本地知识库（0019）、选定专家的云上知识库、公共数据 |
| 选专家 | 在投研的专家对话框里点「选专家」→ 跳 advisor 前端 → 选定 → 跳回原处；编排按选定专家的 profile 做 |

## 二、Codex 可读的四处资料（取代 0011 §一与 knowledge PRD 六之二）

| 层 | 谁的 | 放哪 | 谁能读 | 怎么进来 | 页面上 |
| --- | --- | --- | --- | --- | --- |
| 公共数据 | 我们 | 服务器（knowledge-app） | 所有用户、所有专家 | 我们在管理端采集、建库、登记 | 不以库的面目出现，「问就有」 |
| 专家的云上知识库 | 每位专家（作者） | 服务器（advisor-app），按专家隔离 | 选定这位专家的那段对话，经按「用户 × 专家 × 对话」签的令牌 | 作者在市场里备：专家资料夹 + 作者私有知识库挂给它的部分（§二之二） | 市场页只显示概况（多少份、涉及什么），不显示原件 |
| 项目目录 | 每个用户 | 用户电脑 | 该用户的 Codex 经本地代理 | 用户自己放、工作与专家产出 | 项目、右边栏文件树 |
| 本地知识库 | 每个用户 | 用户电脑上的一个目录 | 该用户的 Codex 经本地代理，跨项目 | 用户自己放、信息采集放入 | 侧边栏「本地知识库」（0019） |

规矩：四处互不流动。专家知识库不进公共库；本地知识库不上传；专家对话结束，令牌失效。

## 二之二、两套账号体系（所有者 2026-10-11 定「好像最好是两套账号」）

| 体系 | 谁 | 在里面有什么 | Casdoor |
| --- | --- | --- | --- |
| 投研平台的用户 | 做投研的人 | 电脑、工作区、项目文件夹、本地知识库、对话 | 组织 `sunmoonai`（0014），应用 investment |
| 专家市场的用户（advisor，作者） | 编专家的人 | 专家、每位专家的资料夹、作者自己的私有知识库 | **另一个组织**（暂名 `advisors`），应用 advisor-studio |

两套各自独立：同一个人要既做投研又编专家，就注册两个账号；两边不互认、不合并。形状上两边一样——作者的「专家资料夹 + 私有知识库」对应用户的「项目文件夹 + 本地知识库」，只是作者的在云上（本来就要给别人的 Codex 读）。所以**专家的云上知识库 = 这位专家的资料夹 + 作者私有知识库里挂给它的部分**，按专家隔离。普通用户的项目与本地知识库永远不上云。

| 面 | 谁登录 | 说明 |
| --- | --- | --- |
| 市场（浏览、专家页、`/pick` 回跳） | 投研用户，用 investment 那个会话 | 用户只在这里出现；advisor-web 验 investment 的会话，不要求作者账号 |
| 作者工作室（编辑、资料、试跑、送审） | 作者账号 | 第一期只有我们自己的作者账号 |
| 管理端 | 内置管理员（0014） | 分类、送审、上架 |

作者往资料夹与私有知识库里放东西：网页上传为主；作者若另有投研账号，也可从那边的电脑经代理读入——这是两套体系之间**唯一**的一条通道，而且只在作者本人两个账号都登录时手动触发。两个 Casdoor 应用与组织怎么配，实施前按 0014 的做法补一节。

## 三、advisor-app 的域

```text
分类 category        宏观 / 行业（可分层）/ 上市公司（按证券代码挂）
作者 author          作者组织里的 Casdoor 用户（§二之二）；第一期 = 我们自己的作者账号
专家 expert          id、名字、一句话、分类、作者、状态（草稿 / 送审 / 上架 / 下架）、当前版本
专家版本 version     不可改写；内容 = skill（现在的 ExpertPack 整体：六问、workflow、auto_allow、output_file 等，0015 之后 dossier 段撤）
资料夹 folder        每位专家一份：条目（名字、类型、版本、sha256、大小、出处说明）、对象存储前缀 `advisor/<expert>/…`、索引
作者知识库 library   每位作者一份，同样的条目；挂接表记录哪些条目挂给了哪位专家
选用记录 selection   哪个用户、哪个项目、哪段对话、哪位专家哪一版、何时；供计费与作者看用量（不含对话内容）
```

| 接口面 | 给谁 | 做什么 |
| --- | --- | --- |
| Web | 用户 | 市场：三类浏览、搜索、专家页（六问、步骤、验收、知识库概况、用量）；「选这位」回跳；作者编辑页（第二期开放） |
| Admin | 我们 | 分类、送审清单、上架 / 下架、作者管理 |
| Internal | investment-backend、沙箱 MCP | `GET /internal/experts/{id}@{version}`（skill 原文，供编排）；知识库三个工具（第四节）；选用记录写入 |

skill 的真源从 `investment-backend/.../packs.py` 搬到 advisor 的数据库；investment 按 `id@version` 取并缓存，编排期间版本钉死。现有的内置专家包作为第一批上架数据迁入。

## 四、专家的云上知识库怎么被读

沙箱里加一个 MCP `sunmoon_advisor`（与 `sunmoon_workbench`、knowledge 同一套令牌机制，`aud=advisor`，`sub=用户`，加 `expert`、`session`、`exp`）：

| 工具 | 做什么 |
| --- | --- |
| `list_expert_library` | 列这位专家知识库的条目 |
| `read_expert_item` | 读一条（大文件分页），返回内容 + 引用 `{expert, item, version, sha256}` |
| `search_expert_library` | 按问题找片段，带出处。第一期先做全文；语义索引第二期 |

令牌由 investment 在专家对话开始编排时签发，只带选定的那一位专家；对话到终态令牌作废。advisor 后端用平台公钥就地验（`security.md` MCP token 一行）。knowledge PRD「已知的缺口：文档检索」里的 `search_documents` 先在这里做出来，以后公共库复用。

## 五、选专家：跳出去、跳回来

```text
投研 专家对话框 ──「选专家」──▶ advisor /pick?return=<投研回跳地址>&project=<id>
                                   用户浏览三类、看专家页、点「选这位」
投研 专家对话框 ◀── return?expert=<id>@<version> ──┘
   显示选定专家的名字与承诺；提交后编排按这一版做
```

| 规则 | 说明 |
| --- | --- |
| 跳转 | 用现成的 `CrossAppLink`，不手拼地址 |
| 回跳校验 | investment 收到 `expert` 后向 advisor internal 取一次，确认上架中；下架的拒绝并提示换一位 |
| 市场页直接开工 | 专家页上也有「用这位专家」：跳到投研专家对话框，专家已选 |
| 版本 | 对话里钉死选定时的版本；作者发新版不影响在跑的对话 |
| 没登录 | 市场面验的是 investment 的会话（§二之二），跳过去不用再登录 |

## 六、作者编辑页（第二期，第一期只给管理员）

| 页 | 内容 |
| --- | --- |
| 我的专家 | 清单、状态、用量 |
| 编辑 skill | 表单：六问、分类、步骤（标题、白话、方法原文、输入、输出文件、验收规则、被拒后怎么办）、工具范围、放行表。保存成草稿版本 |
| 资料夹与私有知识库 | 专家资料夹（只给这位专家）与作者私有知识库（可挂给作者的多位专家）；上传、从自己电脑经代理读入、改名、删、看索引状态；单文件与配额另定 |
| 试跑 | 用作者自己的沙箱和项目跑一遍，不上架也能试 |
| 送审 | 送管理端；上架后对用户可见 |

分成、计费、作者间复制，骨架不设计。

## 八、要定的、要验的

| 项 | 说明 |
| --- | --- |
| 专家知识库放哪（2026-10-11 所有者定「甲」） | advisor 自己存、自己建索引、自己出 MCP；knowledge 只碰公共数据，两者是不同的概念，不存在分工 |
| 编排在哪（2026-10-11 所有者定「甲」） | advisor-app 存 profile / 工作流的真源与版本（作者编辑、校验、试跑、出版本，「把 profile 内化为工作流」在这一侧）；工作台取版本逐步跑、喂 Codex，Task / 方向盘 / 审批 / 验收 / 记账都不动 |
| 作者上传资料的版权 | 作者承诺条款；举报下架。第二期 |
| 专家知识库配额与文件类型 | 作者编辑页开放前定 |
| 用户选专家时看到多少 | 六问、步骤、验收、知识库概况、用量；不看方法原文、不看资料原件 |
