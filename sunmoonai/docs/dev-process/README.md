# 开发流程规范

开发周期各阶段的通用规范：每个阶段写什么、按什么模板、过什么门。
它与任务的生命周期正交——任何开发任务（如 [`../dev-agent-task/`](../dev-agent-task/)）在任何层次、用到哪个阶段，就按该阶段的规范写；用哪几个阶段、各写多深，由任务的种类和需要决定。

## 四个阶段

| 目录 | 缩写与全称 | 中文名 | 回答什么 | 主要负责 |
| --- | --- | --- | --- | --- |
| [`01-prd/`](01-prd/) | **PRD** · Product Requirements Document | 产品需求文档 | 要什么、做到什么算满足 | 两部分：① 原始需求——原话、背景、范围、授权、待澄清项，冻结后只追加；② 需求与验收合同——场景、功能要求、不做什么、约束、验收标准，按版本修订，验收判据在此冻结 |
| [`02-sdd/`](02-sdd/) | **SDD** · Software Design Description | 软件设计说明 | 怎样满足 PRD | 结构层写各部分怎么划分、彼此的关系与接口；组成层写单个部分的内部结构、协议与数据、失败与恢复。按 IEEE 1016，总体设计与详细设计都在这一阶段 |
| [`03-sdp/`](03-sdp/) | **SDP** · Software Development Plan | 软件开发计划 | 怎样拆、怎样做 | 把设计拆成可独立交付、验证、回滚的任务（目标、依赖、实施、测试、验收、回滚），并规定开发活动怎样进行 |
| [`04-uat/`](04-uat/) | **UAT** · User Acceptance Testing | 用户验收测试 | 是否满足、能否接收 | 按冻结的判据逐条验证，证据按规则采信，写明查了什么、没查什么，最后由人做业务接收 |

阶段按顺序推进，但不是每个任务都要走满四个：用哪几个、各写多深，由任务的种类和需要决定。

这里只放与具体项目无关的原则和纪律，篇幅刻意很少；具体项目怎样落实，写在各任务自己的目录里
（agent 项目的具体流程见 [pipeline.md](../dev-agent-task/components/backend/composition/pipeline.md)）。

## 流程总则

1. **每个阶段都有三样东西**：产物、退出条件（门）、没过门时回到哪一阶段。写完文字不等于过门。
2. **用哪几个阶段、写多深，由任务定。**小而可逆的任务可以在一份记录里表达各阶段，引用已有依据即算过门；
   但不能为了省文档，在没有依据时把某阶段填成「不适用」。
3. **开工条件与完成条件分开写。**「候选验证通过」「指定版本发布成功」「需求满足」是三个不同的结论，
   状态记录必须说清是哪一个，不能都写「已完成」。
4. **门的执行归属分三档，不混进同一张「已保证」清单**：机器已能判；当前靠纪律、将来可机器化；
   本质上只能靠纪律（一直标 ⚠）。凡声称由机器判的，必须能写出一条跑出非平凡结果的命令。
5. **规则要有载体。**能跟着测试或提交自动跑的，做成自动检查；做不成的，老实标 ⚠ 并靠自检。
   要人记得去跑的检查，和写在文档里的规矩没有本质区别；检查的结论不能取决于某台机器的工作区状态。

## 执行者的共同纪律

不论单路还是并行，不论人还是 AI，八条都成立：

1. **不用计划覆盖原始需求**；
2. 只在范围、工具、数据、预算和副作用边界内行动；
3. **区分事实、推断、假设、缺失和未运行验证的结论**，不可混写；
4. 对可中断的工作持久化检查点；
5. 无法满足完成条件时请求输入或**明确失败**，不交半成品；
6. 在**最终固定版本**上运行与风险相称的验证；
7. 报告盲区、副作用和残余风险；
8. 未经授权不推送、合并、发布、删除远端资产或扩大外部影响。

第 3 条是 [UAT](04-uat/README.md) 证据采信的前提：分不清事实与推断，采信分级就无从谈起。
agent 项目的原文见 [顶层组成设计](../dev-agent-task/composition/agent-dev-guide.md)「1.5 执行者的共同纪律」。

## 改判

改判本身不是问题，装作没改过才是。每次改判写清三件事：

| | |
| --- | --- |
| **触发** | 什么新证据或什么情况变化 |
| **原判断错处** | 当初**哪一句**不再成立——不是「当时信息不全」，是具体哪一步推错了 |
| **新判断** | 现在以什么为准；**能独立成立**，不写「理由见上文」 |

不得装作从未判过，**也不得为了让检查变绿而静默删除旧标准**。修改验收标准时保留原标准、
原始失败输出和改判理由。把结论写进上游文档前回读代码或实物重新取证——文字改对了、
代码里还是旧的，比不改更糟。
