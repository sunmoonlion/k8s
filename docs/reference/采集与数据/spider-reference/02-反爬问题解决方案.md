# 爬虫项目：反爬问题解决方案

来源：`~/spider/爬虫项目 - 反爬问题解决方案.html`

说明：本文由 ChatGPT 保存页提取并清理，只作为 Info App 采集与资讯治理设计参考；不是当前实现状态。

在你的金融研究信息收集项目里，“反爬问题”要单独作为一个模块设计，不能只靠 Scrapy/Playwright 硬抓。尤其是 A 股公告、研报、新闻、公司官网 IR 页面，数据来源多、页面结构不稳定、访问频率敏感，反爬处理要分层。

## 一、先明确原则：不要把反爬当成“对抗”

更合理的思路是：

优先官方 API / 数据接口 > 合规网页采集 > 浏览器自动化补充 > 人工处理异常。

不建议把项目设计成“破解验证码、绕过登录、绕过付费墙、强刷代理池”的模式。这类做法风险高，而且对金融研究项目来说长期不可持续。

你真正要解决的是：

-
如何稳定获取公开信息；

-
如何降低被误判为恶意访问；

-
如何在页面变化、限流、封禁时自动降级；

-
如何保证数据完整性和可追溯性。

## 二、金融信息采集常见反爬场景

### 1. 交易所公告、巨潮资讯、公司 IR 页面

这类页面通常不是特别“强反爬”，但会有：

访问频率限制、接口参数变化、分页限制、文件下载失败、PDF 链接过期、Referer 校验、Cookie 校验、偶发 403/429。

应对重点不是“突破”，而是：

控制频率、断点续爬、失败重试、保存原始链接和原始文件、不要短时间批量扫全站。

### 2. 新闻网站、财经媒体

这类反爬更明显，常见问题包括：

JS 渲染、滚动加载、正文隐藏、登录墙、付费墙、验证码、User-Agent 检测、IP 限流、页面结构频繁变化。

建议：

能用 RSS、开放接口、授权数据源就不用硬抓网页。新闻正文抽取可以用 Trafilatura，但对于强 JS 页面再用 Playwright。遇到付费内容和登录墙，不建议绕过。

### 3. 券商研报、研究机构网站

这类最敏感。很多研报平台有明显的版权和授权限制。

建议：

公开可下载的研报可以保存元数据和 PDF；需要登录、付费或机构授权的研报，不要用爬虫绕过。更适合通过合规的数据供应商、公司已有授权渠道、人工上传 PDF 到 RAGFlow/WeKnora。

### 4. 公司官网、投资者关系页面

公司官网结构千差万别，反爬不一定强，但页面变化大。

适合用：

Scrapy 抓列表页，Trafilatura 抽正文，changedetection.io 监控变化，Playwright 兜底处理动态页面。

## 三、反爬问题的分层解决方案

### 第一层：数据源选择层

这是最关键的一层。

你要把数据源分成三类：

| 类别 | 示例 | 策略

| 高优先级稳定源 | 交易所、巨潮、上市公司公告、官方 IR | 重点建设稳定采集

| 中优先级新闻源 | 财经新闻、政策网站、行业网站 | 控频抓取 + 正文抽取

| 高风险源 | 付费研报、登录平台、强验证码平台 | 不建议爬，走授权或人工上传

金融研究项目里，不要追求“什么都爬”，而要追求“核心数据稳定、可追溯、可复用”。

### 第二层：访问频率控制层

反爬问题里最常见的触发原因就是访问太快。

建议在 Scrapy 中做这些配置：

Python
DOWNLOAD_DELAY=2
RANDOMIZE_DOWNLOAD_DELAY=True
CONCURRENT_REQUESTS=4
CONCURRENT_REQUESTS_PER_DOMAIN=2
AUTOTHROTTLE_ENABLED=True
AUTOTHROTTLE_START_DELAY=2
AUTOTHROTTLE_MAX_DELAY=30
AUTOTHROTTLE_TARGET_CONCURRENCY=1.0
RETRY_ENABLED=True
RETRY_TIMES=3

核心思路是：

不要高并发，不要短时间扫全站，不要对同一域名密集请求。

对公告、新闻、IR 页面来说，分钟级、小时级更新已经够用，没必要秒级抓取。

### 第三层：请求头与会话管理层

基础请求头要规范，不要使用明显异常的默认爬虫标识。

可以设置：

Python
DEFAULT_REQUEST_HEADERS= {
"Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
"Accept-Language": "zh-CN,zh;q=0.9,en;q=0.8",
"Connection": "keep-alive",
}

User-Agent 可以设置为正常浏览器格式，但不建议伪造复杂指纹去规避检测。

对于需要 Cookie 才能正常翻页的网站，可以维护正常会话，但不要绕过登录权限。

### 第四层：失败重试与降级层

要把失败分类型处理，而不是统一重试。

| 状态 | 含义 | 建议处理

| 403 | 拒绝访问 | 降低频率，检查来源是否合法

| 404 | 页面不存在 | 记录，不重复抓

| 429 | 请求过多 | 暂停该域名一段时间

| 500/502/503 | 服务器异常 | 延迟重试

| PDF 下载失败 | 链接失效或网络问题 | 重试并保留失败记录

| 正文为空 | 页面结构变化或 JS 渲染 | 切换 Trafilatura / Playwright

你需要建一个 crawl_error_log 表，记录：

来源、URL、状态码、错误类型、失败时间、重试次数、最后处理状态。

这样后期才能知道是“源站变化”还是“采集策略有问题”。

## 六、针对不同来源的具体策略

### 1. 公告类

建议：

公告类信息是金融研究系统的核心，优先保证稳定性。

做法：

保存公告标题、公司代码、公司名称、公告类型、发布时间、PDF 链接、PDF 原文、文件 hash、抓取时间。

反爬策略：

低频抓取、增量采集、不要重复下载已存在 PDF、失败后进入重试队列。

### 2. 新闻类

建议：

新闻类信息更新频繁，但质量参差不齐，不建议全网泛抓。

做法：

只选 20-50 个高质量来源，按栏目抓取，正文用 Trafilatura 抽取。

反爬策略：

对每个站点设置独立频率；JS 页面再用 Playwright；正文抽取失败时保存网页快照，后续人工修规则。

### 3. 研报类

建议：

研报不要以“爬虫突破”为核心，而要以“合规收集 + RAG 入库”为核心。

做法：

公开研报抓取元数据和 PDF；内部已有研报通过上传或 API 入库；每篇研报保留来源、机构、作者、发布日期、行业、覆盖公司。

反爬策略：

不绕过登录，不绕过付费墙，不破解下载限制。重点做去重、分类、OCR、PDF 解析和向量化。

### 4. 公司官网 IR 类

建议：

适合用 changedetection.io 做变化监控。

做法：

监控重点公司的投资者关系、新闻中心、公告栏、业绩说明会页面。

反爬策略：

低频监控即可，比如每日 1-2 次。发现页面变化后，再触发 Scrapy 或 Playwright 抓取详情页。

## 七、最推荐的 MVP 反爬设计

初期不用做复杂代理池。更推荐：

第一阶段：
Scrapy AutoThrottle + Redis 队列 + PostgreSQL 错误日志 + MinIO 原文保存

第二阶段：
加入 Playwright 处理动态页面
加入 changedetection.io 监控重点页面
加入域名级限流策略

第三阶段：
加入任务优先级、失败重试队列、页面结构变更报警、人工复核后台

不要一开始就搞复杂的分布式代理池。金融研究项目真正的价值不是“抓得猛”，而是：

抓得准、抓得稳、能追溯、能复用、能进入 RAG。

## 九、判断是否被反爬的信号

你可以在系统中设置这些规则：

| 信号 | 可能原因

| 大量 403 | 访问被拒绝

| 大量 429 | 频率过高

| 返回 HTML 很短 | 被返回风控页

| 标题为空 | 页面结构变了

| 正文为空 | JS 渲染或抽取失败

| PDF 文件过小 | 下载到错误页

| 同一域名连续失败 | 该站点需要暂停

| 页面 hash 大幅变化 | 站点结构更新

这些信号都应该进入监控系统。

## 十、最终建议

你的项目里，反爬模块不要设计成“突破模块”，而要设计成稳定采集与合规风控模块。

我建议你采用这个原则：

公告和官方信息：重点抓、稳定抓。

新闻和政策信息：精选源、低频抓。

研报信息：公开抓取 + 授权导入 + 人工上传。

强登录、强验证码、付费墙：不碰。

这样项目才能长期跑下去，也更符合金融研究场景的专业要求。
