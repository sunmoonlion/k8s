# 人的批准点

所有 agent 开发任务共用：人在哪些点上做决定、批准怎样才成立、人自己要守什么。
各任务按这里写出自己的权力表、强制点与取值（具体化），并链接回来。

## 人的位置

人可以同时是 requester 与某些权力的 principal，但不因此获得执行角色。人的稳定职责是：

- 给出或确认目标、边界与验收；
- 回答绑定到自己身份的 Interaction；
- 批准省事方向裁定、预算/资源变化和不可逆 Side Effect；
- 对最终交付负责并可推翻先前裁定。

“由人触发脚本”不等于“人是 orchestrator”；“由人把固定指令粘到 GUI”是尚未自动化的传输动作，
应记 `dispatch_event` 并计成本，不新增权力行。

## 谁批什么

- 受控动作分成若干**权力行**，每行写明：受控的动作或合法状态边、谁是 principal、默认值、强制要求。
  表外没有「未分类的批准」；普通的补充信息只有在歧义会实质改变结果、权限、成本或风险时才问。
- 朝**放行**方向的行（冻结工单、开工、降档或跳环节、追加预算、不可逆副作用与最终成功、改判）都要求人明确批准，
  强制点必须落在执行者够不着的地方——伪造这些批准会造成不可逆后果。
- 朝**停下**方向的行（安全收敛为取消）是失败安全方向，可以放宽；但取消必须附**已产生副作用的清单**，缺清单的取消不生效，
  否则不知道要回滚什么。
- 超出已冻结授权的范围，必须**新建任务**，不在原任务里扩权。
- 批准的是**执行某个动作**，不是把任务状态直接写成成功。
- 推翻裁定或改判冻结标准：**追加新记录，不覆盖原判断**；标准变更后重新验收。

## 批准怎样才成立

- 批准必须同时回答：**谁、批准哪个任务的哪个版本、批准哪项动作、何时过期、是否已被原子消费**。
- 通知文件或聊天回复只证明「有文本」，不证明身份；执行者能修改的脚本、hook、权限位，不是对它的安全边界。
  强制点必须落在执行者够不着的服务端身份、凭据作用域、工具网关或写入口。
- 取证结论的措辞限定到「**这台主机、这个身份、这个时刻**」；边界的表述绑定到「**凭据域是否共享**」，不绑定到偶然事实。
- 威胁模型同时覆盖三件事：伪造肯定的批准；没有批准仍能直接写交付面；人的设备上另一个 agent 借缓存的凭据代做批准。
  批准证据的鉴别与副作用入口的强制是**两道不同的检查**。
- 拥有凭据只说明有技术能力，不等于批准了具体动作；只有一位 principal 也不免除批准。
  鉴别服务不可达、批准过期或配置漂移时**失败关闭**，并区分查询失败、未批准与策略拒绝。
- 身份未经鉴别的手工确认只能记作 `reported`，不得写成 `attested`。边界能防伪造和绕过，不能证明人读懂了对象；
  误签靠对象展示、独立验收与抽检来降低。

## 权限取交集

- 有效权限是各项授权的**交集，不是并集**：请求方授权、任务与 agent 的配置、沙箱与工具策略、当前批准、有效租约。
  不在执行尝试内的开发操作没有租约，不能因此算作无权限——约束来源不同，强度不变。
- **授权不跨场景延续**：换分支、换任务、下一次，都要重新批准；批准绑定任务、动作、目标、版本和有效期。
- 下列动作**只有 principal 能做**，且各有留痕义务；协调职责不带来其中任何一项：

| 动作 | 必须留下 |
| --- | --- |
| 批准高风险或不可逆动作（推送、合并、发布、迁移、删除远端资产） | 批准人、动作、目标、版本、有效期 |
| 取消任务或中止在途执行 | 取消依据、已产生副作用、需补偿项、需保留对象 |
| 追加预算或提高并行度 | 原上限、新上限、依据 |
| 最终验收终审 | 所验的最终提交、逐条判定、门禁原始输出位置 |
| 降档（把完整选优改成最小选优或单路） | 降档依据、被省略的环节、承担的风险 |
| 推翻已有判定或改判冻结标准 | 原判断、错在哪、新判断、原标准与原始失败输出 |

- 「我看着行」不是依据；依据要能被半年后的自己复核。
- **是否简化流程的裁量权在 principal，不在执行者。**执行者不得自行降档，也不得靠询问自己派出的子 agent 或多数同意来制造批准——
  **自我批准禁令任何时候都成立**。

| | 谁负责 |
| --- | --- |
| 决定做什么、不做什么 | **人** |
| 决定怎么做（在约束内） | 执行者 |
| 产出是否符合验收标准 | 未参与实施的一方；无人时由**人** |
| 上线后出问题 | **人**——agent 不承担后果 |

agent 不得自我批准，不是因为不信任它的判断，而是因为它不承担后果。

## 三道正交门

一次动作的有效能力必须**同时**通过三道独立的门，三者不能互相代替：

| 门 | 决定 | 硬规则 |
| --- | --- | --- |
| 工具策略 | 哪些工具存在 | deny 优先；allow 非空时未列出的工具默认拒绝 |
| 执行范围 | 在哪里、对什么资源执行 | 工作区、数据、网络、租户、操作者逐次收窄，**不能由模型自报** |
| 审批策略 | 这次具体动作谁可批准 | 批准不能扩出前两门；缺失、过期或漂移一律失败关闭 |

- 工具策略是**硬停**，不是提示词里的建议：被拒绝的工具应当**不存在**——发给模型之前从工具清单里移除，网关收到伪造名称再拒一次。
  「工具还在，只是描述为禁止」不算满足。
- 只能在进程外层拦截时，要如实标注「**事后审计**」，不得声称事中拦截。

## 四档审批

| 档 | 适用 | 决策者 | 纪律 |
| --- | --- | --- | --- |
| `auto-deny` | 未声明、越权、不可满足门禁 | 确定性策略 | 直接拒绝并留原因码 |
| `auto-allow` | 冻结策略明确的低风险、可逆、范围内动作 | 确定性策略 | 仍逐次验权、记预算与副作用 |
| `llm-review` | 只需语义检查、且策略明确允许委托的中风险动作 | 独立受限的评审模型 | **必须落账**模型与版本、输入摘要、判定、理由；否则等于产出者自我批准 |
| `human-approval` | 高风险、不可逆、发布、扩权、追加预算 | principal | 一次性、短时、精确绑定，**不可转授** |

- 每份批准绑定任务、尝试、动作、目标、策略版本，以及待执行载荷与计划或 diff 的内容哈希；**执行前重算，任一字节、目标、权限或版本漂移即作废**。
  批准有短时效，超时失败关闭。
- 不得把工具自带的默认接受当作任何一档批准，也不得让**生成候选的同一 agent** 充当 `llm-review`。
- **超时是独立的审计结果**，不折成 `auto-deny`：两者后果相同，审计含义不同——一个是策略作了拒绝判断，一个是没有任何人作出判断。
- 四档与权力行是**两条正交的轴**：权力行回答「哪个 principal 可以走哪条合法边」，四档回答「一次具体动作经过什么审批形态」。

## 裁量权的底线

人可以判断「这件事不值得走全流程」，执行者不可以。但裁量有底线，**五条不因规模而豁免**：

1. 不篡改原始意图；
2. 不越过权限与范围；
3. 结论有与风险相称的证据；
4. 「完成」可判定；
5. 发生改判时，交代触发与变化（三要素见 [总则「改判」](general-rules.md)）。

省略任何一步都必须显式写出「不适用」及理由——空着与「忘了」无法区分。
涉及安全边界、数据迁移、跨系统契约、不可逆外部动作、生产发布的，无论多小都走完整流程。

## 人这一侧的义务

不只是执行者有纪律。人这边同样有，而且被违反时后果更大——因为 agent 会照做。任务越重，前两条越要做到。

| 人的义务 | 违反会怎样 |
| --- | --- |
| 请求写清**边界**：含什么、不含什么、不含的归谁 | 执行者会自行扩大范围，或漏掉本该做的 |
| 给**可判定的验收标准**，不给倾向性结论 | 候选向你的结论收敛，等于白问 |
| 并行提案时**不泄露其他方案** | 独立信号退化成改写 |
| 派活前先建好各自的工作区和命名分支 | 多个执行者写同一工作区，后写覆盖先写 |
| 收到「我不确定」时**不追问到它给出确定答案** | 逼出的确定性是编的 |
| 执行者说「没查过某处」时**当作真话对待** | 声明盲区的动力被消灭，下次它不说了 |

最后一条最容易被忽略：盲区声明是自愿的，只要说了就受罚，很快就没人说了。这与 [UAT](deliverables/uat/uat-rules.md)
「如实写『不能排除』不扣分，隐瞒才扣」是同一条规则的两侧。

**委派转移的是执行，不是最终责任。**任务写多严按轻重，但范围、权限、预算、停止条件和要交回什么，凡是会影响结果或权限的，都必须写进任务；对超范围、追加成本、
不可逆动作和规范修改及时批准或拒绝；亲自验收，或指定未参与实施的验收方。

## 待批准事项要具体、可读、可重取

- 待批准事项以持久记录为真源；通知丢失不应丢失待决事项。它至少表达：问询定位（哪个任务、哪条权力、问谁）、待决内容与选项后果、
  决定对象（目标提交或摘要、实际 diff 摘要、冻结的验收条及结论）、时效（**过期不等于拒绝或默认同意**）、决定记录（经鉴别的主体、
  响应、实际生效值、原建议与改动）。
- **无默认的决定不得预填为已同意**；允许预填的项，同时保留原值和实际采用值。
- 同一次人机触点涉及多条权力时**逐条绑定**，不能只写一个「同意」；需要批准的对象版本变了，旧批准不能自然延续。
- 记录响应耗时、相对建议的改动项数、各类触点次数，作为观察值；它们不自动触发降档、减检查或扩大自动批准范围。
