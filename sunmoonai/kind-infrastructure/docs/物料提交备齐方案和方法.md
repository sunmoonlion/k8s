## 1. 我们要达到什么效果

沿用已有做法：基础软件通过 tar/deb 等离线物料安装，容器镜像预先放入私有 Harbor；补齐 Git 源码、npm/pnpm、Python、系统包、构建工具和发布证据。

形成一条可重复执行的流程：

```text
确定源码提交、目标平台与用途
  → 联网准备全部依赖，固定版本和来源
  → 逐件校验，保存到集群之外的独立批次
  → 关闭公网，在干净环境中恢复、安装和构建
  → 测试通过，镜像进入内部 Harbor，生成固定摘要发布包
  → 按已批准的目标部署、检查、记录结果
```

家庭网络和国内云的公网访问都可能失败。目标是让准备工作能中断恢复，让已经备齐的批次可以继续构建和部署。新增提交、依赖或平台可能需要重新取得物料；不得承诺未来所有新代码都能永久离线构建。

### 三种完成状态必须区分

| 状态 | 能证明什么 |
| --- | --- |
| 文件已下载并校验 | 本批次列出的文件完整；尚不能证明没有漏项 |
| 构建物料已验收 | 指定源码、工具版本和平台在隔离环境构建成功，必要负例通过 |
| CI/CD 已验收 | 指定流水线实际完成测试、构建、发布与获准部署，结果可以追溯 |

基础设施 Ready、缓存命中、流水线页面绿色、镜像 push 返回成功，都不能代替上面的完整判定。

## 3. 每个批次先填这张执行卡

AI 在改配置或大批下载前生成执行卡，给出差异、体量估计和步骤；用户确认的是这张卡对应的具体范围。

| 项目 | 必填内容 |
| --- | --- |
| 批次标识 | 唯一 batch_id；含日期、用途、平台，不能复用已验收批次名 |
| 目标 | 基础安装／构建／部署；列出这次要完成的层次 |
| 源码 | 顶层仓和子仓路径、完整 commit、gitlink、工作树是否干净 |
| 环境 | OS/架构/libc、解释器与包管理器版本、Docker/BuildKit 版本 |
| 物料根 | 宿主机独立绝对路径；不得只存待清理的节点容器或业务 PVC |
| 准备网络 | 本地统一代理、可用公共来源、已授权远程中转；每个来源可达性单独记录 |
| 构建网络 | 首轮验收完全禁外网；内部服务版另列允许访问的精确目标 |
| 发布目标 | Harbor 地址/项目、允许推送的试验标签；未授权则仅导出本地镜像 |
| 部署目标 | 显式 kubeconfig/context/API/namespace；未授权则止于发布产物 |
| 资源 | 可用空间、预计增量、并发、每项超时、总尝试上限 |
| 凭据 | 只记录私有文件/Secret 的引用；不记录内容 |
| 退出条件 | 缺依赖、校验错误、预算耗尽、目标冲突时停止对应阶段并保留证据 |

本次试验建议：先以 tpl-backend、tpl-web-frontend 验证公共方法；覆盖测试用依赖。通过模板门禁后，再按 Info → Knowledge → Investment 串行扩展。runtime 列入盘点，Windows 制品另行验证。

默认串行下载；并发至多 2。下载每项最多 3 次尝试，连接超时 15 秒，文件/镜像总超时按大小在执行卡中明确（例如普通文件 300 秒、镜像 1200 秒）。新增占用达到执行卡上限时停扩量，不能无限下载。首次建议上限 30 GiB，准备前核查磁盘实际余量；这是停止阈值，不是假定依赖必然小于该值。

| 类别 | 收集内容 | 不能遗漏 |
| --- | --- | --- |
| Git | 指定提交的完整源码对象、子仓对象、源码对应关系 | 子模块、LFS 对象、Git 依赖、本地 workspace/file 引用、patches |
| 基础工具 | KIND/kubectl/Helm、Git、Node/pnpm、Python/uv、构建器 | 工具自身下载、构建器镜像、Dockerfile frontend 镜像 |
| 系统包 | 构建所需系统库、编译器、头文件及传递依赖 | apt 元数据/签名与依赖，不能只留几个 deb 猜测齐全 |
| 容器镜像 | 控制面/CNI/Harbor/基础设施/构建工具/运行时/测试依赖 | initContainer、hook、Job、PVC helper、浏览器测试镜像 |
| JS 包 | pnpm 锁文件所有目标构建需要的包、开发依赖、包管理器 | native/optional 包、安装脚本下载、字体、浏览器、编译器资产 |
| Python 包 | uv.lock 对应目标环境的 wheel/sdist 与构建依赖 | PEP 517 构建后端、测试工具、间接下载的 Node/浏览器、系统共享库 |
| 部署输入 | charts、CRD、values 模板、bundle、初始化/迁移脚本 | Helm 子 chart、webhook 证书流程、镜像外部引用 |
| CI 自身 | 控制器/agent、插件与传递依赖、测试工具、临时数据库镜像 | Jenkins 更新站点、插件安装、测试数据和故障诊断工具 |
| 质量与证据 | 来源、SHA256/digest、许可元数据、SBOM/扫描工具及必要数据库 | 离线扫描数据库更新时间；不能把过期扫描写成当前无风险 |
| 身份与配置 | 配置模板、必要信任链、Secret 名称与获得方法 | 私钥、令牌、口令独立保存，不进入公开物料或仓库 |

## 5. 批次目录与清单

建议根目录：`~/packages-to-be-installed/releases/<batch_id>/`。

```text
plan.json                    本次目标、资源与动作范围
source-lock.json             顶层仓/子仓 commit、gitlink 与恢复位置
materials.lock.json          全部物料、来源、摘要和目标平台
checksums.sha256             物料文件散列，不包含它自身
sources/                     受控源码 bundle/归档
tools/                       工具二进制与版本信息
images/                      固定平台镜像归档
packages/pnpm/               专用 pnpm store 的完整归档
packages/python/             已保存的 wheel/sdist 与受控 uv 缓存归档
packages/os/                 deb 等重建工具链需要的物料（若本次需要）
charts/                      chart/子 chart/CRD
configs/                     无凭据的配置与初始化模板
evidence/                    下载、来源验证、恢复、构建、负例、部署结果
outputs/                     构建产物、镜像摘要、SBOM、发布候选
status.json                  阶段状态、失败与最后成功步骤
```

源码与含敏感上下文的证据默认受控访问（目录 0700、文件 0600）；公开物料和私有源码明确区分。检查 Git 历史或跟踪文件中的凭据风险；发现凭据只报告位置，不输出内容、不把归档传到公共中转机，也不擅自重写历史。

清单每项至少包含：`id`、用途、精确版本、来源、相对路径、字节数、SHA256、目标 OS/arch/libc、直接依赖项、获取结果、校验依据。镜像另记 repository、index digest、platform digest、归档 SHA256。源码另记仓名、commit、gitlink、bundle 前置条件。不存在的摘要不得填假值。

清单不包含认证 URL、临时签名参数、token。SHA256 证明内容一致；它不自动证明发布者身份。优先核对官方发布校验/签名及可信 TLS 来源，签名验证方法和信任根另记。

状态依次为 `PLANNED → PREPARING → VERIFIED → BUILD_VALIDATED → CI_VALIDATED → DEPLOY_VALIDATED`。只完成前一层就停在对应状态，失败记录具体阶段；未获准部署的批次可以交付为 `CI_VALIDATED`。状态文件不是执行授权。

已验收批次不原地覆盖。版本、平台或物料变化产生新批次；相同摘要的完整文件可以复用。损坏文件保留诊断副本后重新获取，不能更新清单里的预期散列来“通过”。合法修改生成配置时保留旧版和差异，重新渲染、校验和验收。

## 6. 方法一：源码脱离公网仍可恢复

1. 从指定工作区读取 HEAD、工作树状态和父仓 gitlink，生成 source-lock。未提交内容不自动打包；用户确需试验未提交修改时另立明确快照与标识。
2. 优先用已有本地 Git 对象创建自包含 bundle；提交必须存在，不能用缺少历史对象的浅克隆冒充完整包。
3. 每个子仓独立打包；父仓中的 gitlink 只是一条引用。LFS 内容也单独备齐，Git bundle 不代替 LFS 对象。
4. 在全新目录离线恢复，逐仓核对完整 commit 和源码树；父仓指向的子仓提交必须一致。恢复时不得让 submodule update 悄悄访问公网。
5. 源仓同步与 CI 消费分开。当前已有提交可直接形成批次；后续新增提交通过已批准的同步流程进入内部副本，再产生新批次。

标准 Git 命令示意（变量先按执行卡赋值；输出必须为新路径）：

```sh
git -C "$source_repo" rev-parse HEAD
git -C "$source_repo" status --porcelain
git -C "$source_repo" bundle create "$bundle_file" HEAD
git -C "$source_repo" bundle verify "$bundle_file"
git clone "$bundle_file" "$fresh_checkout"
git -C "$fresh_checkout" checkout --detach "$expected_commit"
git -C "$fresh_checkout" rev-parse HEAD
```

第一次应使用无外部前置对象的自包含包，并在空目录恢复。后续增量包必须记录和验证前置提交。不得对现有用户工作区执行恢复覆盖。方法依据：[Git bundle 官方文档](https://git-scm.com/docs/git-bundle)。

## 7. 方法二：npm/pnpm 依赖备齐

本项目实际使用 pnpm。锁定 pnpm 版本、Node 版本、目标 OS/架构/libc，并保存已验证的工具本身；不能每次离线构建再调用 Corepack 从公网下载 pnpm。

准备方法：

1. 在与目标一致的临时工具链容器中，用专用 store 预取锁文件依赖。保留 package.json、pnpm-lock.yaml、workspace 配置、patches、项目自己的 pnpm 设置与 file/workspace 依赖。
2. 包含构建和测试所需 dev 依赖；不能只用 `--prod` 后宣称测试物料齐全。
3. 原生包按目标平台取得；WSL 宿主的 glibc 缓存不能直接证明 Alpine musl 的 Next/SWC/sharp 依赖齐全。
4. 检查 install/postinstall、next/font、Playwright/Cypress 等额外下载，逐项保存或改为已批准的本地资产路径；不得通过跳过实际需要的脚本来伪造成功。
5. 网络准备结束且无并发写入后归档整个专用 store，记录散列。不得假设 Docker cache mount 的内容已随构建镜像自动保存。

在已恢复的临时源码目录、已预装准确 pnpm 的目标环境内执行示意：

```sh
# 联网准备；registry/代理由已批准配置注入。
pnpm fetch --frozen-lockfile --store-dir "$batch_store"

# 全新消费环境；batch_store 来自本批次归档，网络另由容器边界关闭。
pnpm install --offline --frozen-lockfile --store-dir "$batch_store"
pnpm build
```

采用固定版本实测命令支持情况。`--offline` 约束包获取，安装脚本和构建命令仍需外层网络限制。不得设置 `strict-ssl=false`、关闭完整性验证、改用 `--no-frozen-lockfile` 来消除失败。

缺包时回到准备阶段补充清单，重新归档和验收。方法依据：[pnpm 10 fetch](https://pnpm.io/10.x/cli/fetch)、[pnpm 10 install](https://pnpm.io/10.x/cli/install)。

## 8. 方法三：Python、uv 与系统依赖备齐

1. 固定 Python 完整版本、uv 版本、目标 glibc/架构和工具链镜像摘要。项目声明的范围不等于已固定实际解释器。
2. 解析 pyproject.toml、uv.lock、测试分组与构建入口；先检查锁文件和项目声明一致，再按冻结的锁文件安装。
3. 在独立容器、独立 `UV_CACHE_DIR` 中准备依赖。保存目标平台所需 wheel/sdist；无 wheel 的包还需要构建后端、编译器和头文件。重建的 wheel 记录其来源和生成过程。
4. 第一轮可使用固定 uv 版本的完整缓存归档实现离线消费，但缓存仅是本版本实现细节；同时保留发布资产与散列，不能把一份 `.venv` 当可移植物料。
5. 在无 `.venv` 的独立源码目录中恢复缓存并离线安装，执行实际检查和构建。含路径/可编辑依赖的项目要核对恢复位置与源码，不能盲目跨机复制缓存。

在已有准确 Python/uv 的临时环境内示意：

```sh
# 准备阶段，具体 extras/group 参数必须与本批次构建和测试一致。
UV_CACHE_DIR="$batch_uv_cache" uv sync --locked

# 全新消费环境，无旧 .venv；下式禁止 uv 自动下载解释器或访问网络。
UV_CACHE_DIR="$restored_uv_cache" UV_PYTHON_DOWNLOADS=never \
  uv sync --offline --locked
```

项目适用时可选 `--frozen`，但它不检查锁文件是否与项目声明一致，因此需另做一致性检查。精确参数由已固定的 uv 版本验证。锁文件里的远程资产 URL 不因改一条 `PIP_INDEX_URL` 就自动成为内部物料。

APT 和工具自下载统一移到**工具链准备阶段**：预装应用构建真正需要的系统包、uv、Node 等，输出固定摘要工具链镜像。应用离线构建不再临时 apt-get。若要求从零重建工具链，也必须保存对应系统包、元数据与验证材料，并单独完成工具链恢复验收；已有工具链镜像可用不代表这一步已经通过。

方法依据：[uv 离线设置](https://docs.astral.sh/uv/reference/settings/#offline)、[缓存规则](https://docs.astral.sh/uv/concepts/cache/)、[命令参考](https://docs.astral.sh/uv/reference/cli/)。

## 10. 家庭网络波动和远程中转的执行方法

### 10.1 本地准备

先读取网络方案，运行已有的 `sunmoon-network check`，核实地址与配置；联网检查通过仍不代表大文件稳定。下载使用临时文件、有限重试，最终校验通过再放入批次正式路径。

清单中同摘要且已完整的文件直接复用；部分下载只有服务器支持安全续传且最终校验通过才接纳。来源变化、认证失败、证书错误和散列不匹配分别记录；不得无限重试或任意换站。

### 10.2 远程中转

本次已授权主机是 `txy-tokyo`，只准备公开工具/包/镜像。主机身份、磁盘空间、架构、工具版本与剩余有效期每次复核。私有源码和凭据不随下载器上传；npm scopes、私有包名等信息也须先判断是否适合传出。

采用已有 known_hosts 严格校验和独立缓存目录；不得跳过 SSH 主机验证。只上传该批次必要的公开清单/下载代码，写入独立目录。远程拉取前保留至少 8 GiB 空间，不能通过清理其他服务来腾空间。

回传命令形态（源、目标先按执行卡确定，目标为独立接收目录）：

```sh
rsync -a --partial --append-verify \
  -e 'ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10' \
  "$remote_public_batch/" "$incoming_batch/"
```

传输结束后，本地对照**先前锁定的预期清单**验证全部文件与镜像摘要。不能只接受远程同时传来的“文件+新校验值”。校验通过再将接收目录发布成正式批次。失败保留断点，按本轮尝试上限停止；旧完整批次继续可用。

远程主机是可替换的下载渠道，不是永久唯一物料库。服务器到期前本地必须已有经过校验的副本。后续替换下载主机时重新明确权限与目标。

## 11. 怎样证明真正备齐：本次试验

### 11.1 试验顺序

1. **T0 清单与目标检查**：确定源码、子仓、工具链、包、测试镜像、chart 和平台，报告尚缺项。
2. **T1 获取与完整性检查**：所有必需文件存在且散列一致，来源明确；锁文件和源码指纹关联正确。
3. **T2 空目录恢复**：从批次恢复源码与工具，逐仓 commit/gitlink 一致；不借用开发目录的 node_modules、.venv 或工具缓存。
4. **T3 离线安装与构建**：新的临时 builder，预装本批次工具链与物料，关闭外网，从头安装依赖并构建模板后端和前端；记录构建命令、网络边界与退出码。
5. **T4 负例与中断恢复**：在批次副本中故意移走一个必需包、破坏一个文件，各自明确失败；恢复后通过。受控中断一次下载，证明能复用已校验项且不会发布半成品。
6. **T5 CI 闭环**：按获准流水线执行真实质量检查、构建和内部发布；所需临时数据库在独立环境，不能使用业务库。
7. **T6 CD 闭环**：仅在明确授权的新集群/命名空间部署同一个 digest，核对 rollout、实际 imageID、配置和指定功能；失败保留此前可用版本及证据。

首轮 T0–T4 先验证模板方法，T5–T6 分阶段完成。批准模板构建试验不自动批准全部业务上线。

### 11.2 离线边界与证据

- `pnpm --offline`/`uv --offline` 不能约束任意安装脚本；容器/构建环境必须另有网络隔离。
- Docker build 的 `--network=none` 主要控制 RUN；FROM、Dockerfile frontend、远程 context、ADD URL、Git source、构建器启动镜像仍要明确处理。应预装并锁定来源，使用隔离 builder，记录隔离边界。
- 首轮使用新 builder，禁用构建结果缓存；专用物料缓存作为显式输入导入。否则复用旧构建层可能根本没有运行依赖安装。
- 允许内部 registry 的试验另记为“禁公网、内网可用”；不得将其写成完全无网络。
- 负例只修改临时副本，禁止破坏已验收批次或共享缓存。
- CI 需要数据库等内部服务时，使用独立内部网络与合成测试数据；业务 E2E 仍放在整体建设最后。
- 不通过关闭测试、忽略导入错误、禁用 TLS/完整性检查、替换真实镜像为 scratch 或“缺项自动在线”让结果变绿。

结果表至少记录：批次、输入清单 SHA256、源码提交、工具版本、目标平台、网络边界、命令、开始/结束时间、退出码、产物摘要、每项 pass/fail/未验证及证据路径。

## 12. 怎样接入 CI/CD

### 12.1 三条职责分开的流程

**物料准备流程**：获准同步源码 → 解析锁文件 → 获取新物料 → 校验与离线验收 → 发布不可变物料批次。

**CI 流程**：收到确定提交与 batch_id → 核验适配关系 → 从内部恢复源码 → 质量检查/测试 → 构建镜像 → 输出 SBOM、来源与 digest → 推送获准 Harbor 项目 → 核对远端 digest → 生成发布候选。

**CD 流程**：读取已验收候选 → 核验授权目标、配置、Secret 与数据初始化条件 → 渲染/审阅发布差异 → 部署相同 digest → 检查结果与回退条件。晋级不重新构建，标签仅作为别名。

任何物料缺项在准备或 CI 前置检查失败；不能等部署过程中临时访问公网补包。镜像必须能关联源码提交、锁文件、工具链、CI 检查与部署包；只记录 tag 或 BUILD_NUMBER 不够。

### 12.2 本项目的落点

- 构建器优先沿用当前 Dockerfile 能力对应的 BuildKit；不直接启用历史 Kaniko 示例。该示例既有不安全参数，也引用了已归档的上游项目。
- Jenkins 可作为待评估调度器；需先固定控制器、agent、插件与传递依赖，并确认与 Kubernetes/Java 的兼容性。文件存在不等于实际流水线已部署。
- 第一条真实业务 CI 建议是 Investment backend：ruff/pyright/pytest（独立临时 PostgreSQL）→ 构建 → Harbor digest → 发布证据。前置公共构建修复遵循模板优先。
- 准备、构建、发布、部署使用不同权限；构建任务不得取得集群管理员凭据。不可信代码与带发布凭据的任务隔离；凭据采用专门的 secret 挂载，不写进 ARG、镜像层或日志。
- 公网 webhook 可丢失，采用内部已同步提交队列/周期性对账；以明确提交和批次作为幂等依据。只给纯下载有限重试，部署重试先判断是否已产生副作用。

### 12.3 从本地批次发展为内部服务

本次先做可移植批次和恢复验证。以后将源码同步到内部 Git，将包导入或预热内部 npm/Python 仓库，将镜像放入 Harbor；仍保留冻结清单与可恢复副本。

内部包仓库若只是按需代理缓存，首次请求仍可能需要外网。只有该批次所需内容已备齐、关闭上游后实测通过，才能作为离线供应源。选型要说明持久化、权限、备份、容量、保留策略和恢复方法，不只给一个镜像启动命令。

BuildKit 缓存用于加速，不能替代完整物料与源码；缓存需显式导出/恢复，范围相互隔离。构建结果缓存和包管理器 cache mount 分别处理。参考：[Docker 缓存说明](https://docs.docker.com/build/cache/backends/)。
