# 请求生命周期

**一条 message 从用户发出到用户看到 response 的完整往返。**起点和终点都在用户电脑上，后端只占中间。

这一份是**轮廓**：每一站发生在哪、经哪条通道、什么算这一站走完了。各站的细节在对应模块的设计里，
合同里那些还没归位的细节按 [去向](../../../product/product-contract.md) 一点一点搬。
人自己做同一件事的周期见 [人版](../../../dev-human/lifecycle.md)——两版是同一条往返的两种实现。

别和这两个混：**状态机**管纵向（这个 Task 现在算什么），**七阶段产品功能**是按段分组的功能义务；
本文管的是横向的那一条线，从用户按下提交之前一直到他看见结果。

## 九站

```text
用户（桌面应用）
【写 message】任务文本；本地资料只给句柄；类别按本机规则预填、由用户确认或改正；
              生成幂等键；显示预估费用与本机模型配置状态
   ▼ 通道 ④
后端【受理】校验 / 授权 / 幂等 / 路由（用户所选 → 后端兜底 → 交用户选）
   ▼
后端【派发】持久化 Task / 排队 / 投递到选定设备（离线则等待）
   ▼ 通道 ①
执行端【执行】Attempt：Codex 在独立工作区执行
   │            ├─ 通道 ② 驱动 Codex ├─ 通道 ⑤ 知识服务 ├─ 通道 ⑥ 模型厂商
   ├──【中断】工具级审批走通道 ③（本地窗口）；Task 级审查走通道 ④（后端 Interaction）
   ▼
执行端【封装】本地内容检查 → 加密
   ▼ 通道 ①
后端【验收】结果密文与证据持久化 / Task 终态
   ▼ 通道 ④
桌面应用【交付】事件回放 / 取回密文 / 通知 → **本机解密呈现**
```

部件的定义见 [组成部分与本轮范围](components.md)，通道见 [通道](channels.md)。

## 九站落在哪个模块

| 站 | 谁做 | 本轮范围 |
| --- | --- | --- |
| 写 message · 提交 · 交付 | 桌面应用 | [`0002-desktop`](../modules/0002-desktop/PRD/requirement.md) |
| 受理 · 派发 · 验收 | 后端 | [`0001-backend`](../modules/0001-backend/PRD/requirement.md) |
| 执行 · 中断 · 封装 | 本地 runtime 驱动 Codex | [`0003-runtime`](../modules/0003-runtime/PRD/requirement.md) |
| 执行站里的取数 | 知识服务（通道 ⑤）、模型厂商（通道 ⑥） | **范围外**，见 [组成部分与本轮范围](components.md) |

**中断那一站跨两个模块**：工具级审批的界面在 `0002-desktop` 的本地窗口，拦截点在 `0003-runtime`；
Task 级审查的界面在 `0002-desktop` 的审查窗口，原子消费在 `0001-backend`。这是三方交界处，最容易出错。

## 每一站算走完了没有

| 站 | 在哪 | 走完的判据 | 条款 |
| --- | --- | --- | --- |
| **写 message** | 桌面应用 | **未经用户确认的类别预填不算数**；没有可用的模型 key 不得提交；资料正文、文件名及其派生特征不出本机 | `F-INTAKE-05/06/07` |
| **提交** | 桌面应用 → 后端 | 幂等键在「租户 + 请求方 + Profile」作用域内唯一；同键同摘要返回原 `task_id`，同键异摘要返回幂等冲突，**不静默复用也不另建** | `F-INTAKE-01`、提交信封 |
| **受理** | 后端 | 身份从认证上下文确定，**不信任客户端自报**；一旦分配 `task_id` 并写首个事件，后续拒绝也必须形成可审计的 `REJECTED` Task | `F-ADMIT-*` |
| **派发** | 后端 → 执行端 | 派发内容带签名；租约与 fencing 随派发下发；设备离线则等待，不丢 | `F-DISPATCH-*` |
| **执行** | 执行端 | 在独立工作区里跑；key 只在本机；本地资料不上传 | `F-EXEC-*`、`I16` |
| **中断** | 本地窗口 / 后端 | 工具级在本机闭环，Task 级经后端 Interaction **原子消费**；两条提交逻辑**不得共用** | `F-APPROVE-*`、`F-REVIEW-*` |
| **封装** | 执行端 | 先本地内容检查，再加密；后端只拿到密文与元数据 | `F-CRYPTO-*` |
| **验收** | 后端 | 确定性验收与回执核对通过；终态、结果、预算结算**原子提交** | `F-ACCEPT-*` |
| **交付** | 后端 → 桌面应用 | 事件按 cursor 续传、重复幂等；**密文在本机解开、渲染出来** | `F-DELIVERY-*` |

## 终点在哪

终点不是「模型返回了文字」，也不是「一条事件推送成功」，而是四条同时成立：

1. 最终结果（密文）、验收、证据和副作用状态已经可靠持久化；
2. Task 已以唯一合法终态提交；
3. 有权用户在断线、应用重启或换设备后，凭结果密钥可以重新取得结果；
4. 通知失败可以独立重试，不改变 Task 结果。

**起点同理在用户电脑上**：类别预填与资料选择都发生在提交之前。两头都在本机，这不是实现细节，
是信任边界的直接结果——后端读得到问题，读不到资料，也读不到结果。
