# 后端的八块

> 依据：[后端要满足什么](../../PRD/requirement.md)。每块**承担什么、不承担什么**在
> [`SDD/modules/`](../modules/) 下各自那一份，本文只管**怎么切**与**彼此怎么连**。

## 按环节切，横穿的单列

**主轴是环节**——[九站](../../../../../../pipeline.md) 里后端占的那五站，一站一块，
**编号即站序**。横穿所有站的东西不摊进任何一站，单独成块。

| 块 | 对应哪一站 | 拥有什么 | 朝哪一侧 |
| --- | --- | --- | --- |
| [`0002-router`](../modules/0002-router.md) | **受理** | 身份、幂等、建单、契约固定、类别三层判定、Profile 与设备选择 | 客户端 ④ |
| [`0004-bridge`](../modules/0004-bridge.md) | **派发** | 执行端对接：WSS 连接、设备身份与吊销、租约与 fencing、投递器、回传接收 | runtime ① |
| [`0005-interrupt`](../modules/0005-interrupt.md) | **中断** | Interaction 的创建与原子消费、两层审批后端侧、批准后执行副作用 | 人（经 ④） |
| [`0006-acceptance`](../modules/0006-acceptance.md) | **验收** | 确定性验收、语义验收派 Attempt、终态提交的发起 | **不朝外** |
| [`0007-delivery`](../modules/0007-delivery.md) | **交付** | 事件流投影与 cursor 续传、结果密文存取、通知 | 客户端 ④ |
| [`0008-competition`](../modules/0008-competition.md) | **横穿派发与验收** | 多方竞争：并行派 N 个 Attempt、候选冻结与取件、择优与处置记录、验收方算出、异议 | **不朝外** |
| [`0001-ledger`](../modules/0001-ledger.md) | **横穿五站** | 状态机与唯一转换函数、事件表、四本账、outbox 这张表、重启恢复 | **不朝外**，其余六块经它 |
| [`0003-orchestrator`](../modules/0003-orchestrator.md) | **横穿所有步骤** | workflow 游标、按步拆与派发、步骤契约、`escalate` 裁决、方法库与按步工具面、子 Task 编排 | **不朝外** |

**朝向是结果，不是依据。**受理本来就接客户端，派发本来就往执行端送，交付本来就给客户端——
朝哪一侧是站决定的。真正需要单独说的规则只有一条：

> ⚠ **凡横穿多于一站的，不摊进任何一站。**摊进去，那件事就会横穿几块却不归任何一块，
> `P1`（同一事实一个权威写入面）只能靠纪律守。三个实例：
> `0001-ledger`（横穿五站）、`0003-orchestrator`（横穿所有步骤）、
> `0008-competition`（横穿派发与验收）。

**横穿的那三块必须不朝外。**这不是巧合：横穿多站的东西一旦有外部面，
它就成了绕过站序的第二个入口——那正好是它被单列出来要防的事。

**每块内部按什么切由它自己定**（职责、资源、朝向都可以）——主轴只管块与块之间。
例如 `0004-bridge` 内部分连接、设备身份、租约、投递器、回传，那是它一块之内的事。

每块认领哪些 `F-*` 写在它自己那一份里；一条义务跨两块时，定义放**主要承担方**那一份，
另一方只在自己文档里注明边界。

## 后端不占的那四站

上表已经说了后端占哪五站。**九站里另外四站不在后端**：

| 站 | 在哪 |
| --- | --- |
| 写 message | 桌面应用 + runtime（类别预填） |
| 提交 | 桌面应用 → 后端；由 `0002-router` 接住，但写信封的是客户端 |
| 执行 | 执行端 |
| 封装 | 执行端（本地内容检查 → 加密） |

两处只占一半的要注意：**中断**的工具级在本机闭环那半不经后端；**验收**的终态提交经 `0001-ledger`。

## 彼此怎么连

**只有 `0001-ledger` 能改状态与写账。**其余六块都是「请求 `0001-ledger` 做一次转换」，
不自己写表；所有入口共用同一个转换函数，以状态版本比较交换；派发与状态改在同一事务里落 outbox。

| 连接 | 怎么回事 |
| --- | --- |
| **outbox 表在 `0001-ledger`、投递器在 `0004-bridge`** | 表必须跟着事务走，worker 必须知道谁在线。投递器读表、送出去，送成之后请求 `0001-ledger` 标记已投递——标记也是状态改，照样经它 |
| **`0003-orchestrator` 决定、`0004-bridge` 投递** | 前者产出「下一步是什么」，后者负责送达与租约。分开是为了让「workflow 的步骤类型是开放集合」这句守得住 |
| **方法工具经 `0004-bridge` 的 ① 通道代理回 `0003-orchestrator`** | 清单随派发下发、随换步失效；回来时由 `0003-orchestrator` 二次校验。执行体从头到尾只跟 runtime 说话，「不直接连后端」没破 |
| 与执行端之间**只有一条通道** | 派发、续约、回传、工具调用都走 ① |

两条全局纪律：

- 传递只经**数据库与事件流**，不经进程内状态；后端不驻留内存状态，重启扫非终态恢复。
- **没有独立的待办表。**「任务队列」是**执行模式**不是一张表：各块的后台活从持久状态**扫**
  出来——扫 `QUEUED` 的 Task 知道该派什么，扫过期租约的 Attempt 知道该回收什么。另存一份
  待办就和状态机成了两个真源。**唯一的例外是 outbox**：它记的是「待发出的消息」不是 Task
  状态，且与状态改同事务，不构成第二个真源。
