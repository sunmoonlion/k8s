## 1. 范围、权威来源与读法

本指南只说明如何把一项开发工作组织成可审计、可复核的交付；它不是产品请求生命周期合同、业务功能设计、进度表，也不重复流程规范正文。

## 2. 开发工作如何落入产品内核

开发工作应以一个版本化 Task Profile 进入产品内核，本文将其简称为 `dev.change`。该名称不是另一套状态机：它的输入、输出、验收、证据与执行策略均受 `request-lifecycle.md`「Task 契约」和「Profile、Artifact 与扩展」约束。

一张开发工单至少钉定原始请求、范围、只读输入及其版本锚、基线 commit、可写面、验收条、预算/观察窗与交付路径。工单冻结后，题目与验收条不能为了让产出通过而改写；需要改变目标、口径、授权范围或 Profile 版本时，按内核「终态、刷新与重新处理」建立关联的新 Task。

### 2.1 角色和组件

- **router** 是确定性组件：依据可复核规则给出 `decide`、`ask` 或 `refuse`，模型输出只能作为证据，不是路由决定。
- **orchestrator** 是确定性组件：依照内核合法边推进、分发、观察、回退与汇总。过渡期由人运行脚本是传输欠账，不把人命名为该组件。
- **arbiter**、**acceptor** 是开发任务里的角色：前者整合并写处置记录，后者按冻结标准独立验收。其选择与回避规则以 `round-protocol.md`「⑤ 验收 与 ⑥ 确认」为准。
- **principal** 或 **requester** 可以提出、澄清、授权或确认；人不属于执行者登记项。不可逆动作仍须由人显式确认。

角色、组件和权力不是同一个概念。把“谁运行脚本”“谁写整合稿”“谁有批准权”混为一个称呼，会制造无法检验的责任边界。

### 2.2 档位与工作区

按 `round-protocol.md`「流程档位」裁定 T0、T1 或 T2；命中不可逆、权威层、已知对立或判据未定任一条件即进入 T2。升档可直接记录，降档、跳环节、缩短观察窗等省事方向必须经人确认并落入裁定记录。

可写工作区由写者数量、独占、干净状态和钉定基线决定，不由“任务看起来复杂”决定：

1. 每位并行写者在同一基线 commit 上使用独占 worktree 与命名分支；
2. 人需要通读时开临时检视 worktree，用完移除；
3. 只读输入按 commit 取件，评审和裁决不把工作区未提交内容当证据；
4. 多仓输入同时记录父仓 gitlink 与子仓 commit；
5. worktree 隔离对同一宿主、同一身份的 CLI/GUI 只是约定，不是安全隔离。

## 3. 原生中断、恢复与产品边界

开发指南不得为已有库原语再造交互协议。当前代码的已核事实是：

- `investment-backend/app/app/infrastructure/graph/pilot_graph.py:53-66` 向 `interrupt()` 传入普通字典并取得返回值；
- `investment-backend/app/app/application/agent/graph_runtime_service.py:13-46` 以 `session_id` 构造稳定的 `thread_id`，并在流中发现中断后返回；
- `investment-backend/app/tests/test_runtime_selection_spike.py:33-46` 对同一 `thread_id` 调用 `Command(resume="approved")` 后完成执行且副作用只发生一次；该文件 `80-98` 还证明等待中的检查点继续使用钉定图版本。

因此，产品实现应在 SDK 适配层使用库提供的 `interrupt()`、`Command(resume=...)` 与 checkpoint 语义。当前 `GraphRuntimeService.resume()` 仍明确抛出 `NotImplementedError`（`graph_runtime_service.py:26-31`）；这说明抽象层尚未完成适配，不能据此宣称端到端恢复能力已经落地。

任何确有必要的产品级交互字段、响应鉴别或版本迁移，都必须按 `request-lifecycle.md`「修订纪律」开独立规范修订单元，包含原始请求、影响分析、迁移和验收。它不能由开发任务或文档自行扩展内核，也不能把库的单参数恢复包装成未经证实的新契约。

## 4. 证据与判定纪律

### 4.1 断言的最低形状

每个关于现状的断言都附 `仓 + commit + file:line` 或可复跑命令；结论必须小于等于证据覆盖范围。建议按以下层次写作：

| 层次 | 可说什么 | 不可说什么 |
| --- | --- | --- |
| 自述 | 执行者、模型或人报告了什么 | 行为、身份或完整性已经被外部证明 |
| 可重算 | 冻结输入上重跑的 diff、hash、测试或枚举 | 未被枚举的进程内活动 |
| 进程观察 | argv、标准流、退出码和可重算结果 | 进程内部每次工具调用或未留痕出网 |
| 外部权威 | 在执行者权限域之外取得的审计记录 | 人是否理解、未被观察的其他通道 |

对照 `round-protocol.md`「判据自身的质量」：检查必须同时声明查了什么和没查什么；无法枚举输入集合时，零命中是 `UNKNOWN`，不是“没有”。新门禁第一次运行先与人工结论对照，再作为门禁。

### 4.2 当前宿主事实与安全表述边界

`rounds/_spike-sign/forensics.md:20-31` 记录的宿主取证显示：`zym` 有免密 sudo、属于 docker 组，且当时主仓 dry-run 推送未被拒。此次复跑 `id && sudo -n -l` 得到 `uid=1003(zym)`、`sudo` 与 `docker` 组，以及 `(ALL) NOPASSWD: ALL`。

结论仅限这台宿主和这个身份：本机脚本、hook、文件权限、凭据扫描和 worktree 约定都可被该权限域内的 Agent 改写，属于卫生检查、审计提示或流程纪律，不是抵抗该 Agent 的强制点。`forensics.md:58-74` 同时说明，若要取得域外授权通道，须由所有者在 Agent 够不着的环境完成；本文不宣称这项前置已经满足。

这不是取消安全需求，而是拒绝把不可证明的本地控制误称为安全边界。任何外部托管控制、独立身份或部署设置，未独立核验前一律标 ⚠。

### 4.3 Git 的用途和限度

Git commit 可作为 Artifact 版本、评审对象与可重算输入；分支是运输路径，不是自动可信的状态账。开发侧能够验证提交、哈希、内容差异和一些冻结关系，但不能据此证明事务原子性、租约、fencing、执行者身份或进程内部活动。涉及这些内核性质时，回到 `request-lifecycle.md`「两层状态机」「跨进程纪律与持久化账」的持久化与并发要求。

## 5. 验收、成本与不可外推项

验收按三层组织：先运行机械门禁，再由独立 acceptor 按冻结标准判断，最后由来源作者在异议环节核对自己的主张是否被误读。人确认只处理不可逆决定和抽样复核，不能替代前两层。完整顺序、角色计算和回退规则以 `round-protocol.md` 为准。

**开发验收是机械且便宜的**：测试、文档门禁、冻结 diff 和可复跑命令通常可自动化。**金融分析验收是判断且昂贵的**：它依赖专业结论、数据口径与证据质量；本指南没有解决这一半，也不允许从开发任务的成功外推到财务 Task 的验收能力。

运行时不总比直接操作便宜。并行写者、不可逆副作用、版本化只读输入、续接、跨 Task 依赖或权威层改动通常值得结构化运行；单文件笔误、一次性探索或需人手工转交给无可观测入口的执行者可能反而更贵。成本判断须记录可观察字段和适用范围，不用模糊“复杂度”代替证据。

绕过也不能被假装完全可见。可将外部交付面、已提交变更和可用会话记录做有限对账，并把无法归因的现象登记为待核查；没有覆盖的本地未提交改动、对话或其他机器活动仍是未知。

## 6. 迁移、删除与未决项

两份源稿被删除前，应满足：新指南的逐节映射零缺口；权威文档引用可达；历史引用清理完成；适用的门禁和人工抽查通过；并至少留下按新指南运行的可复核任务记录。删除旧文不会使其曾经的结论消失，历史依据仍由 git 记录保存。

以下事项保持未决而非被本文默认解决：

- 产品运行时 SDK 适配何时完成并在哪些真实 Task 上通过验收；
- 外部身份域、托管控制和实际部署策略是否存在且有效；
- Agent 可观测性与强制能力的实测等级；
- 财务 Task 的具体契约和昂贵验收如何设计；
- 哪些小任务经过观测后可以稳定进入较轻档位。

每项需要改变内核、协议、授权范围或不可逆发布方式的决定，都应按相应权威文档重新建单，不通过复制本文中的历史方案绕过。
