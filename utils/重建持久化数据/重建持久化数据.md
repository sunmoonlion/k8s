## 开发环境重建 kind 集群时复用数据盘方案

本文以 `messaging-platform-dev` 中的 RabbitMQ 为例，说明在 **重建 kind 集群** 时，如何复用 NFS 上已有的数据盘，而不是每次都从空数据开始。

思路可以推广到 PostgreSQL、MongoDB、Elasticsearch、Redis 等所有有状态组件。

---

### 一、基本思路

1. **第一次部署**（初始化基线数据盘）仍然使用当前脚本（如 `deploy-sunmoonai-all.sh`）：
   - 各组件通过 `storageClass: nfs-2` 自动创建 PV/PVC；
   - NFS 上生成对应目录，例如：
     - RabbitMQ：`/data/kind-nfs/messaging-platform-dev-data-rabbitmq-sunmoonai-0-pvc-<UID>`
2. **记录/确认这些 NFS 目录**，为每个需要“可恢复”的组件准备一份“静态 PV + PVC” 的 YAML：
   - `spec.nfs.path` 指向刚才生成的目录；
   - `persistentVolumeReclaimPolicy: Retain`，避免误删数据。
3. **在各组件的 dev-values 中声明使用固定 PVC（existingClaim）**：
   - 让组件始终挂载同一个 PVC 名称；
   - 由静态 PV 决定这个 PVC 背后对应哪块 NFS 目录。
4. **以后每次重建 kind 集群时**：
   - 先 `kubectl apply` 所有“静态 PV/PVC”；
   - 再用 Helm 安装/升级组件（values 里已经写死 `existingClaim`）；
   - 新集群自然挂回老数据盘，实现数据复用。

---

### 二、RabbitMQ 示例（messaging-platform-dev）

#### 1. 当前 NFS 数据目录

通过 `kubectl get pv -o yaml` 已确认，RabbitMQ 当前的数据目录为：

- NFS 服务器：`172.28.46.235`
- 路径：  
  `/data/kind-nfs/messaging-platform-dev-data-rabbitmq-sunmoonai-0-pvc-dfc6039a-5cf1-4646-9ca9-f01e610b3d44`

这个目录中保存了 RabbitMQ 的 mnesia 数据，包括用户、密码、队列等内部状态。

#### 2. 静态 PV + PVC 定义

文件：`kind-infrastructure/deploy-kind/rabbitmq-dev-pv-pvc.yaml`

- PV 固定指向上述 NFS 目录；
- PVC 名：`rabbitmq-sunmoonai-dev-pvc`，namespace：`messaging-platform-dev`；
- 以后**所有集群**里，只要 apply 这份 YAML，就能把这块 NFS 盘接回去。

#### 3. 组件 values 中使用 existingClaim

文件：`messaging-platform/rabbitmq/resources/custom-values/dev-values.yaml`

- 在顶层增加：

  ```yaml
  persistence:
    enabled: true
    existingClaim: rabbitmq-sunmoonai-dev-pvc
    storageClass: ""   # 使用 existingClaim，不再通过 storageClass 动态创建
  ```

- 这样，RabbitMQ StatefulSet 创建 Pod 时，不再请求新的 PVC，而是**永远挂载 `rabbitmq-sunmoonai-dev-pvc`**；
- 这个 PVC 背后的实际目录由静态 PV 决定（即上面的老 NFS 目录）。

#### 4. 密码策略（与数据复用强相关）

`dev-values.yaml` 中的 `auth` 段：

- 使用：

  ```yaml
  auth:
    username: "admin"
    existingPasswordSecret: "rabbitmq-auth-secret"
    existingSecretPasswordKey: "rabbitmq-password"
    existingErlangSecret: "rabbitmq-auth-secret"
    existingSecretErlangKey: "rabbitmq-erlang-cookie"
    updatePassword: false
  ```

- 含义：
  - 密码和 Erlang cookie 固定从 `rabbitmq-auth-secret` 里读取；
  - `updatePassword: false`，启动时**不尝试自动修改 NFS 上已有的密码**；
  - 避免“新密码 + 旧 mnesia”不一致导致 Pod 一直起不来的问题。

### 三、完整流程梳理

#### 第一次（初始化基线数据盘）

1. 使用现有脚本（例如 `deploy-sunmoonai-all.sh`）在一个干净的 kind 集群上部署所有组件；
2. 通过 `kubectl get pv` 找到各组件对应的 NFS 目录；
3. 为需要持久化的组件编写静态 PV/PVC YAML，并将 NFS 目录写入其中；
4. 在各组件的 dev-values 中配置：
   - `persistence.existingClaim: <组件对应 PVC 名>`；
   - `storageClass: ""` 或去掉该字段，避免再走动态创建；
   - 按组件特性（例如 RabbitMQ）配置与密码/内部状态相关的策略。

> 注：RabbitMQ 的静态 PV/PVC 和 dev-values 已经按以上思路配置完成，可作为样板。

#### 以后每次重建 kind 集群

1. **重建 kind 集群**（现有 kind 脚本不变或略作调整）；  
2. **先应用所有静态 PV/PVC**：

   ```bash
   kubectl apply -f kind-infrastructure/deploy-kind/rabbitmq-dev-pv-pvc.yaml
   # 以及其他组件的 pv-pvc.yaml
   ```

3. **再部署各业务组件（Helm）**：
   - 例如 RabbitMQ 使用 `dev-values.yaml`（其中已经包含 `existingClaim` 设置）；
   - 建议在 `deploy-sunmoonai-all.sh` 里，把 “apply PV/PVC” 放在 Helm 安装之前，使流程全自动。

组件在新集群中启动时，会直接挂到这些静态 PVC 上，因此：

- 如果 NFS 目录中已经有历史数据（生产/长期 dev 集群）：  
  → 自动“接盘”，恢复历史队列、用户、密码等；
- 如果 NFS 目录中是“空基线盘”（刚初始化完）：  
  → 相当于每次重建都从一份干净的初始数据开始。

### 四、对其他组件的推广建议

1. **挑选需要数据复用的 A 级组件**：
   - 如：PostgreSQL、MongoDB、Elasticsearch、RabbitMQ、Redis 主节点、Neo4j 等；
   - B 级（缓存、副本、临时工具）可以继续使用动态 `storageClass`，不做静态 PV。
2. 为每个 A 级组件复制一份 RabbitMQ 的模式：
   - 写 `<component>-dev-pv-pvc.yaml`；
   - 在对应的 dev-values 中声明 `persistence.existingClaim`；
   - 根据组件特性处理初始账号、密码、schema 等。
3. 在 `deploy-sunmoonai-all.sh` 中：
   - 增加统一步骤：`kubectl apply -f <pv-pvc 目录>`；
   - 确保该步骤在 Helm 安装/升级组件之前执行。

这样，开发环境中即使频繁 **关机 / kind 崩溃 / 重建集群**，也能在新的 kind 集群中**自动挂回 NFS 上的老数据盘**，保证关键有状态组件的数据得到复用和保护。

> 说明：这里讨论的“存储独立于集群生命周期”这一点，对 **kind 集群和远程 k8s 集群同样成立**。  
> - kind 场景：删除/重建 kind 集群，不会自动删除 NFS 服务器上的 `/data/kind-nfs/...` 目录；  
> - 远程集群：删除 namespace 或整个集群，同样不会自动销毁独立存在的 NAS 目录或云盘卷（除非显式配置了自动清理策略）。  
> 因此，只要底层存储独立存在，就可以通过“静态 PV + existingClaim”的方式，在新集群中重新挂回同一块数据盘，实现持久化数据的重用。

### 五、通过开关区分“初始化集群”和“重建复用数据”

为了在同一套脚本下便捷地切换两种模式，可以约定一个环境变量（或脚本参数），例如：`SUNMOONAI_MODE=init|reuse`。

#### 1. 模式含义

- `SUNMOONAI_MODE=init`（默认）：
  - 用于**第一次部署**或不关心历史数据的场景；
  - 各组件使用“原始 dev-values”（例如动态 `storageClass: nfs-2`），按当前逻辑新建 PV/PVC。
- `SUNMOONAI_MODE=reuse`：
  - 用于 **kind 集群重建后复用 NFS 老盘** 的场景；
  - 先应用静态 PV/PVC（指向老目录），再用带 `existingClaim` 的 dev-values 部署组件。

#### 2. 部署脚本中的示例逻辑（以 RabbitMQ 为例）

伪代码示意：

```bash
MODE=${SUNMOONAI_MODE:-init}

if [ "$MODE" = "init" ]; then
  # 第一次部署 / 新盘模式：使用原始 dev-values（动态 nfs-2）
  helm upgrade --install rabbitmq ./rabbitmq \
    -n messaging-platform-dev \
    -f messaging-platform/rabbitmq/resources/custom-values/dev-values-init.yaml
else
  # 重建模式 / 复用老盘：
  # 1) 先把静态 PV/PVC 应用到新集群（接回 NFS 老目录）
  kubectl apply -f kind-infrastructure/deploy-kind/rabbitmq-dev-pv-pvc.yaml

  # 2) 再用带 existingClaim 的 dev-values 部署 RabbitMQ
  helm upgrade --install rabbitmq ./rabbitmq \
    -n messaging-platform-dev \
    -f messaging-platform/rabbitmq/resources/custom-values/dev-values-persist.yaml
fi
```

实际落地时可以有两种方式：

- 方式 A：把当前的 `dev-values.yaml` 当作 `dev-values-persist.yaml`，再额外准备一个偏“空盘初始化”的 `dev-values-init.yaml`；
- 方式 B：在一个 values 里用条件（例如环境变量）控制 `persistence.storageClass` / `existingClaim` 的分支（脚本注入 `--set` 或 `--set-file`）。

无论采用哪种方式，核心目标都是：

- 通过一个简单的开关（环境变量/参数），在“初始化新集群（新盘）”和“重建复用老数据盘”之间切换；
- 脚本逻辑尽量保持声明式和幂等，避免重建流程中出现手工步骤。

### 六、推荐操作流程（init → update → reuse）

按下面顺序做，可以稳定走通「先空盘初始化 → 把 NFS 路径写进静态 PV YAML → 以后用 reuse 挂回老数据」。

#### 第一次：空盘初始化并生成静态 PV 配置

1. **清空集群与 NFS 数据（全新起点）**
   - `kind delete cluster --name <你的集群名>`（或你平时的删集群方式）；
   - `sudo rm -rf /data/kind-nfs/*`  
   这样集群和 NFS 下的旧数据都清掉，相当于全新环境。

2. **init 模式部署（总控）**
   - 进入总控目录，不设置或显式设置全局为 init，然后执行总控脚本，例如：
     ```bash
     cd <k8s 项目根目录>/sunmoonai/deploy-sunmoonai-all
     export KUBECONFIG=$HOME/.kube/kind-config   # Kind 时按需
     # 不设置即 init；或显式： export SUNMOONAI_GLOBAL_PERSIST_MODE=init
     ./deploy-sunmoonai-all.sh deploy sunmoonai development false
     ```
   - 总控会先通过基础设施阶段（如 `deploy-kind.sh`）完成建集群及 NFS 等，再按 init 模式部署各平台/组件，在 NFS 下创建新的空目录和动态 PVC。无需单独执行 `kind create cluster`。

3. **update：把当前集群的 NFS 路径写回静态 PV YAML**
   - 在 k8s 项目根目录（即包含 `sunmoonai`、`utils` 的那一层）执行：
     ```bash
     cd <k8s 项目根目录>
     ./utils/重建持久化数据/update-all-static-pv-paths.sh
     ```
   - 脚本会从模板生成各组件 `*-dev-pv-pvc.yaml`，并把集群里实际绑定到的 NFS server/path 写进去。
   - **update 后集群照常使用，无需重建**；只有当你需要重建集群时，才做下面步骤 4、5，用 reuse 挂回老数据。

#### 需要重建集群时（reuse 模式）

4. **只删集群，保留 NFS 数据**
   - `kind delete cluster --name <你的集群名>`；
   - **不要**再执行 `rm -rf /data/kind-nfs/*`，保留已有数据目录。

5. **按 reuse 部署（总控）**
   - 执行总控即可；总控会通过基础设施阶段完成建集群（若启用 `infrastructure_enabled`），无需单独执行 `kind create cluster`。例如：
     ```bash
     cd <k8s 项目根目录>/sunmoonai/deploy-sunmoonai-all
     export KUBECONFIG=$HOME/.kube/kind-config   # Kind 时按需
     SUNMOONAI_GLOBAL_PERSIST_MODE=reuse ./deploy-sunmoonai-all.sh deploy sunmoonai development false
     ```
   - 总控会把所有已实现持久化模式的组件统一按 reuse 处理：先 apply 各 `*-dev-pv-pvc.yaml`，再用各组件 `dev-values-persist.yaml` 部署，挂回同一批 NFS 目录。

**小结**：`kind delete` + `sudo rm -rf /data/kind-nfs/*` 只用在「第一次 init 之前」的那次清空；之后要测 reuse 时只删集群，保留 `/data/kind-nfs/*`。
