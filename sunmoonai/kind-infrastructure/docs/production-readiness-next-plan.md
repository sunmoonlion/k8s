## 1. 所有者已确定的方向

- 当前以本机 WSL/KIND 开发验证，设计面向以后云端；国内云不能假定始终能访问公共镜像和包源。
- 新 Kubernetes 基础集群 A/B 已通过，目标为 `sunmoon-kind-136`。
- **旧业务数据无需保留，新平台全新初始化，不做旧业务数据迁移。**此项覆盖此前的“先讨论如何迁移旧数据”。
- **所有者随后明确：私有 Harbor 镜像必须保留。**默认保留全部现存制品，并保护 registry、数据库、配置、Secret/证书及相关存储；按物料手册第 9.1 节完成独立备份与恢复验证后，才讨论旧环境清理。
- 源码、离线安装物料、重建所需镜像和必要凭据仍属于重建输入；不能与可清理的业务数据混在一起。
- 先了解情况、讨论具体方案、确定后实施；助手负责主动调查和排定工作，不等所有者逐项提醒。
- 企业级目标按阶段落实，业务 E2E 最后；本机多节点不冒充云端故障域高可用。

## 3. 推荐实施顺序

### 阶段 1：构建物料闭环（建议现在批准的单元）

**目标：固定源码和物料，在没有公网的干净构建环境中完成模板前后端构建。**先用模板验证公共方法，再按项目规则串行用于 Info → Knowledge → Investment。

范围与交付：

1. 在 `k8s/sunmoonai/cicd-platform/` 增加独立物料入口和公开清单，物料放
   `~/packages-to-be-installed/releases/build-<批次>/`；源码归档、pnpm store、uv 缓存、工具链镜像各自记录摘要和来源。
2. 保存六个顶层仓与十二个子仓的选定提交及完整依赖关系。优先从已有本地对象生成独立 Git bundle；检查恢复所需对象，单独处理子仓/LFS（若实际存在）。不改现有 origin，不 fetch/pull/rebase/push，不把未提交文件或私有配置打包。
3. 固定 Node/pnpm/Python/uv 和 Linux amd64 的实际 libc 环境。前端 Alpine musl 与后端 Debian glibc 分开准备；包量按目标平台裁定，不把锁文件中全部跨平台 URL 当作必须下载清单。
4. 通过官方已支持的预取与离线安装路径准备 pnpm/uv；使用独立缓存，不清理用户原缓存。准备构建所需 dev 依赖、PEP 517 构建依赖与明确的额外下载资产。
5. 把 apt、pnpm、uv 等工具准备放进可审阅的工具链构建阶段；应用构建使用其固定摘要。准备阶段允许联网、有限重试、完整校验；离线阶段缺项即失败。
6. 先修模板的公共构建配置：恢复包管理器完整性检查，固定基镜像摘要，将构建与运行环境分开；确认实际发布入口和运行命令。需要修改实例时遵循模板门禁与串行同步，禁止无条件覆盖领域代码。
7. 从旧 Harbor 只读盘点全部现存制品。构建试验先取得所需镜像，但这不代表全部 Harbor 数据已保留；另按物料手册第 9.1 节准备全部制品与状态的备份/恢复方案。保存新 Harbor 启动镜像，不能只保存“由旧 Harbor 提供的引用”。不改旧 Harbor 项目、保留策略或镜像。

验收（此方案批准后执行）：

- 从独立临时目录恢复指定源码，核对顶层与子仓提交；目录中无默认凭据和开发工作树依赖。
- 在本地预装并锁定工具链的干净 builder 中，禁用网络完成模板前后端依赖安装与构建；关闭构建结果缓存，所需包仅来自本批次物料。验证基础镜像获取与 RUN 网络两个层面，不能只加 `RUN --network=none` 就宣称全过程隔离。
- 至少一个必需包缺失、一个校验错误的负例明确失败，不能静默回公网或改锁文件。
- 模板现有质量门禁按构建变更范围执行；本单元不跑完整业务 E2E。
- 输出物料清单、构建结果摘要、原始命令记录、磁盘用量和恢复说明；原集群不变。

资源：下载串行/低并发，独立缓存；准备前检查磁盘余量。新增物料累计到 30 GiB 时暂停扩量并报告实际占用，所有下载也有单次超时/有限重试。远程主机只用于已授权公开物料下载，不上传私有源码、包或凭据；该主机不可用时本地准备保留已完成进度。

失败处置：保留批次和已校验物料，报告具体缺项；修复模板不等于自动发布业务。原部署、默认 kubeconfig、入口、旧 PVC 保持原状。本单元的代码与结果仅本地提交。

### 阶段 2：新平台全新初始化

阶段 1 之后提出锁定到具体 chart/镜像/路径的实施清单：存储与入口 → Harbor/制品恢复 → PostgreSQL/Redis/RabbitMQ/对象存储等必要基础设施 → Casdoor 身份与应用数据结构 → Info/Knowledge/Investment 和沙箱/relay。

- 新数据库使用正式迁移链从空库建立；保留每 App 独立逻辑库、角色与权限。迁移 Job 和运行角色继续分离。
- Casdoor 用户、OIDC client、角色与初始化账号重新建立；外部 API Key、证书/信任链逐项确定是复用还是重签，凭据仅在私有文件/Secret 中。
- 对象存储、知识库、任务历史、队列内容等旧业务数据不导入；必要演示数据由受控初始化生成。
- Harbor 不属于上述全新初始化范围；先完成保留与恢复方案，再决定目标 Harbor 的兼容版本和恢复路径，不能默认抛弃旧数据库。
- 先确认现有控制平面 CRD/准入 webhook/chart 的 Kubernetes 1.36 适配，使用明确的 kubeconfig 与 profile；旧自动重建入口不直接用于新平台。
- 新集群目前是基础验证布局。如业务入口或宿主持久化需要重新创建该验证集群，先展示精确配置与损失范围并获得对应批准；不能默认已有新集群已适合作最终平台。
- local-path/宿主目录适合当前开发，但备份不能只在同一个节点容器内；云端的存储与故障域另定。

完成条件：组件健康、内部连接与精确网络策略成立、从空库初始化成功、认证基础链路可用、新镜像来源与清单一致。业务完整 E2E 留到最后。

### 阶段 3：CI/CD 首条真实流水线

先把阶段 1 的命令变成可复用构建任务，再设计调度与事件触发。候选先复用项目 Jenkins 方向，但安装版本、插件闭包和运行权限必须重新评估；构建器推荐与当前 Dockerfile 对齐的 BuildKit。

首条业务流水线选择 Investment backend：固定提交与依赖 → lint/typecheck/unit/integration（独立临时数据库）→ 构建 → 镜像按 digest 入 Harbor → 生成发布证据；部署独立受控。晋级使用同一 digest，不重新构建。

此时将源码副本与包供应服务化：比较内部 Git 托管、npm/Python 仓库与现有离线批次维护成本，明确选型与恢复流程后安装。第一步产物须可导入后续服务，避免把新 CI 的启动依赖绑在待初始化的业务集群中。公网事件丢失/断连需要补偿机制，不依赖家里持续收到 webhook。

### 阶段 4：可观测性、恢复与旧环境清理

按现有指标身份接入采集、告警、日志，明确留存与资源预算；接收端回执验证告警送达。备份与恢复覆盖新环境；单区域云端高可用方案依据届时主机与故障域制定。

旧业务数据清理方向已确定。执行前的清单要列明：旧 `kind` 节点、对应 PVC/PV、宿主路径、镜像缓存处理、端口与 kubeconfig；列明保留的源代码、独立物料和必要凭据。Harbor 全部现存制品与必要状态完成独立备份、恢复和摘要核对，且新集群能实际拉取所需镜像后，再结合新入口验收提出旧集群清理清单；不得全局 Docker prune 或整目录扫空。

### 阶段 5：完整业务 E2E 与生产准入结论

覆盖真实登录、业务功能、隔离和故障恢复；最终按证据列出已满足与未满足项。网络供应、构建成功或基础集群 Ready 都不能单独得出“整个项目达到生产标准”。

## 4. 技术依据与选择

- Git 的 [bundle](https://git-scm.com/docs/git-bundle) 支持独立传输源码对象；构建物料使用自包含包，增量包必须检查前置对象。父仓包不自动包含子仓内容。
- [pnpm 10 的 fetch](https://pnpm.io/10.x/cli/fetch) 提供按锁文件预取、随后离线安装的路径；生命周期脚本的额外访问须单独限制与验收。
- uv 的 [离线设置](https://docs.astral.sh/uv/reference/settings/#offline) 与[缓存说明](https://docs.astral.sh/uv/concepts/cache/)用于设计准备/消费分离；固定当前版本及目标平台后实测，不把跨版本缓存可用性当保证。
- [BuildKit](https://docs.docker.com/build/buildkit/)与当前 Docker 构建路径相符；CI 权限和隔离需要另定，不把宿主 Docker socket 无差别授予业务或不可信任务。
- 现有示例引用的 [GoogleContainerTools/kaniko](https://github.com/GoogleContainerTools/kaniko) 已于 2025-06-03 归档，并声明不再维护；新方案不直接继承该示例选型。

规则：C-R1/R2/R3 固定源码、依赖、镜像与发布证据；C-R6 模板优先；C-D1/D2/D3/D8 保留数据所有权和独立迁移，旧数据无需迁移不豁免新库权限；C-T7/T8 未来云端薄边缘与深处出站保持成立。
