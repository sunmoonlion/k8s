## 3. 对基座作者主张的改动（luna 可提异议）

下面三条**改的是 luna 自己的设计主张**，不是补缺口。按 §6.5「整合方不得默认接受优胜作者

### 3.1 F2 · 租约：部分接受 cursor 的主张

- **基座原文**：§8「迟到依据状态、租约/fencing、commit 和冻结时间判断」；「过期执行者的
  写入由 fencing 拒绝，不能只靠自律」。
- **改成**：两层并列——产品侧用租约/fencing（语义只引用 `request-lifecycle.md`），开发侧
  用冻结 commit + 候选状态 + 整合方显式核对，并明写「开发侧没有租约机制」。
- **理由**：分支、worktree 和文件路径上没有任何东西会自动拒绝过期执行者的写入。按原文
  执行会产生虚假安全感，进而省掉整合方的显式核对。
- **未全盘接受 cursor 的部分**：§9 权限公式保留 `∩ 有效租约`，只标注机制归属。cursor 主张
  本文不应出现租约，我判过头——删掉它会让有效权限的计算不完整，那确是产品侧的真实约束。
- **可证伪点**：若能指出开发侧存在一个会拒绝迟到写入的运行时机制，本条应回退。

### 3.2 M3 · 项目实例：接受，但这是路线改动

- **基座事实**：全文 0 处 `2026-08-27`、0 处 `investment`、0 处 `parallel-proposals`、
  0 处 `dormant`（已核对）。这是「写通用合同、不写项目实例」的路线选择，不是疏漏。
- **改成**：§5.2 补本项目范围门禁与四级能力词典，§6.4 补 `parallel-proposals.py` 验证边界，
  新增 §14 项目实例与设计风险两级表。
- **理由**：本文当前的读者是本仓执行者，而 human 那份将来要继承这些门禁。一旦两份文档
  同时不写，门禁就没有着落——而这正是本轮重写要解决的问题（§11.1）。反模式说明「这样
  会失败」，项目实例说明「这里已经失败过」，后者是纪律的效力来源。
- **luna 最可能的反驳**：通用合同不该绑单一项目。我的回应是分层——门禁写在 §5.2 通用路由
  之后并标明「本项目」，实例集中在 §14 且标注证据等级，两者都可随项目变化独立更新。

### 3.3 F5 · 事故写法：收窄

  三份同名文件在三棵 worktree 共存。**不写谁覆盖了谁。**
