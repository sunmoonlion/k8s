## 1. 两条流水线

### 1.1 定义

```text
A 线 · 产品流水线      对象：一条产品需求
                       起点：人说「我要 X」
                       终点：X 上线并被验证
                       现状：几乎是空的

B 线 · 决策流水线      对象：一个待定的判断（架构、规范、口径、命名）
                       起点：出现一个「不预设结论」的问题
                       终点：裁定落盘，成为 A 线的输入
                       现状：成熟（七环节、档位、判据即命令）
```

### 1.2 两者的关系不是并列，是**调用**

```text
A 线 ─── 阶段 3「设计、决定与契约」───┐
                                      │  遇到不可自裁的判断
                                      ▼
                              B 线（轮次）① … ⑦
                                      │  裁定
                                      ▼
A 线 ◀─── 裁定回填为 ADR / 契约 / 纪律 ───┘
```

**A 线是主干，B 线是被调用的子例程。**现在的问题是主干太细、子例程太粗，
于是所有内容都顺着子例程流下去，堆在 `rounds/` 与 `agent-dev-guide.md` 里。

### 1.3 为什么这个区分是**本轮的第一步**，不是一个附带观察

因为「阶段」这个词在两条线上指的不是一回事：

| | A 线的阶段 | B 线的环节 |
| --- | --- | --- |
| 推进方式 | 需求向前流动 | 同一个问题被反复审视 |
| 并行性 | 多条需求并行 | **全仓同时只允许一个 ACTIVE** |
| 门的性质 | 「这条需求可以进下一步了」 | 「这一环节的产物齐了」 |
| 产物寿命 | 随产品演进 | 冻结归档，不再改 |

不分开就无法回答「有哪些阶段」——因为答案是两套。
上一版任务书要「一套文档组织架构」，候选只能把两套揉进一个分类，**必然悬空**。

## 2. A 线：产品流水线

### 2.1 组织轴：人的注意力出现在哪里

前提是本项目的定义：**开发全部由 AI 承担，人只提需求、拍板、验收。**

在这个前提下，**人的注意力是唯一稀缺资源**。实现几乎免费，所以流程的重量必须
从「盯实现」移到「定义」和「验证」两端——否则产出量会淹没验证能力。

⚠ 这条分布论来自 [`inputs/ai-pipeline.md`](rounds/dev-plan-refact/inputs/ai-pipeline.md) §5，
本文采用并把它变成**组织轴**：阶段不按「工作内容」排，按**人在哪几个点必须出现**排。

**人只出现在三个点：**

```text
定义 ── 阶段 1、2      人说要什么，并确认 AI 的复述无偏差；人拍板验收标准
拍板 ── 阶段 3、9      人在决策点上选；不可逆动作在这里授权
验收 ── 阶段 8         人抽检三样：意图、不可逆、证据可复算
```

其余六个阶段由机器守门，人不出现。

### 2.2 九个阶段

每个阶段写清三件事：**产出什么、存在哪、凭什么算过关**。
⚠ 缺第三件的阶段不存在，它只是一段时间。

| # | 阶段 | 谁做 | 产出（文档类型见 §4） | 存在哪 | 准出判据 | 判据由谁执行 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 需求受理与**意图确认** | 人提，AI 复述并列出决策点 | `REQ` | `working/request-baseline/` | 人确认复述无偏差；决策点已列全 | **人** |
| 2 | **验收标准先行** | AI 起草，人拍板 | `AT` | 与 `REQ` 同档 | 每条验收指向一个未来可执行的测试标识；非功能需求已列 | **人**（拍板）+ 机器（标识存在性） |
| 3 | 设计、决定与契约 | AI 起草；人只授权不可逆部分 | `TLD` · `ADR` · `CONTRACT` | `design/` · `decisions/` · 紧挨代码 | 契约可被机器校验；每个取舍有 `ADR`；不可逆项已授权 | 机器（契约校验）+ **人**（不可逆授权） |
| 4 | 拆解为 Work Unit | AI | `WU` | 状态面，**不进仓** | 满足准入门（§3.1） | 机器 |
| 5 | **测试先行** | AI，**与实现分离的角色** | 测试代码 | 代码仓 | 测试为红，且**红的原因正确** | 机器 |
| 6 | 实现 | AI | 代码 | 代码仓 | 测试转绿 + 本地质量门全绿 | 机器 |
| 7 | 机器门禁 | CI / gate 脚本 | CI 记录 | CI | 全绿，**不许例外** | 机器 |
| 8 | **人类抽检** | 人 | `抽检记录` | 追加式记录 | 意图 / 不可逆 / 证据三项抽样通过 | **人** |
| 9 | 发布与反馈 | AI 执行，人授权 | 制品 + 复盘 | — | 回滚路径**已验证**；改进项进待办 | 机器（回滚演练）+ **人**（授权） |

⚠ 九阶段的骨架取自 [`inputs/ai-pipeline.md`](rounds/dev-plan-refact/inputs/ai-pipeline.md) §3，
**本文的增量是**：把它按 §2.1 的注意力轴重排、给每阶段补齐「存在哪」与「判据由谁执行」两列、
并在 §4 从它推导出文档类型。原表没有后两列，因此推导不出文档架构。

### 2.3 与经典九阶段的差别，以及**为什么**

| 变化 | 说明 |
| --- | --- |
| **消失**：拆解排期的估点与批量排期 | AI 无切换成本，估点没有消费者 |
| **消失**：多级人工评审 | 换成机器全审 + 人抽检三样（阶段 7、8） |
| **新增**：意图确认（1） | 没人会「凭常识补全」——写多含糊就执行多含糊 |
| **新增**：验收先行（2） | 产出方≠验收方的载体。验收标准由实现者事后定，等于没有验收 |
| **新增**：人类抽检（8） | AI 不会犹豫、语气也不会变，自述不可信 |
| **变重**：测试先行独立成阶段（5） | 且**与实现分离角色**——同一个会话既写测试又写实现，测试会长成实现的形状 |

**三个新增全部是人的动作，一个消失也不是人的动作。**这不是巧合：
AI 承担执行之后，人的工作整体从「做」迁移到「定义」和「验证」两端。

## 3. 两个门

### 3.1 准入门 — 一条 Work Unit 可以开工的条件

- [ ] 需求清楚，验收标准可验证（不是「完善 X」这类没有终点的写法）
- [ ] 依赖已就绪，或已明确阻塞在哪
- [ ] 重大取舍已记 `ADR`
- [ ] 涉及接口的，契约已定且可被机器校验
- [ ] 测试策略已定：这条用哪几层测试
- [ ] **不可逆动作已识别并已获授权**（本项目特有，见 §3.3）

### 3.2 准出门 — 一条 Work Unit 算做完的条件

- [ ] 测试通过，且**新增了对应的测试**
- [ ] 全部门禁脚本绿（`doc-gate.py` / `anchor-gate.py` / CI）
- [ ] 契约、`ADR` 按需已更新
- [ ] **验收人确认，且验收人不是实现者**
- [ ] 抽检三样已过（阶段 8）

⚠ 这两张清单**放在任务模板里，不放在流程文档里**。放流程文档里没人看；
放任务模板里，每开一个 Work Unit 它就出现一次。
（`DoR/DoD` 的形式取自 [`inputs/standard-pipeline.md`](rounds/dev-plan-refact/inputs/standard-pipeline.md) §3；
本文的增量是准入门末尾那条不可逆授权。）

### 3.3 判据归属：机器 / 人，**不许混在一张清单里**

```text
机器执行   契约校验、测试、门禁脚本、落点表覆盖、命名与路径枚举、回滚演练
人执行     意图确认、验收标准拍板、不可逆授权、抽检三样
```

⚠ **把靠纪律的和靠机器的混在一张清单里，是最常见的自欺。**
本项目已经有一个实测：`round.md` 的 `mechanical_absent` 写了两条机械缺席检查，
而解析器把多行数组静默吞成空列表，**那两条从未真正执行过**
（`rounds/dev-plan-refact/findings.md` F-7）。

由此得出一条本流程的硬规则：

> **凡声称由机器执行的判据，必须有一条能跑出非平凡结果的命令；
> 跑不出来的，一律改标「靠纪律」。**

## 4. 文档类型：从阶段推导

### 4.1 推导，不是另立

每个阶段的产物就是一类文档。类型不自己立，**逐格从 §2.2 的表读出来**：

| 来自阶段 | 类型 | 通行名 | 装什么 |
| --- | --- | --- | --- |
| 1 | `REQ` | 需求档案 / PRD 的原始输入 | 人说过的话、意图复述、决策点清单 |
| 2 | `AT` | 验收标准 | 可验证的验收条目，每条对应一个测试标识 |
| 3 | `TLD` | 技术方案 | 怎么实现、涉及哪些模块、风险与备选 |
| 3 | `ADR` | 架构决定记录 | 当时的问题、有哪些选项、**为什么选它、放弃了什么** |
| 3 | `CONTRACT` | 契约 / 规格 | 接口、数据模型、状态机、不变量 |
| 4 | `WU` | Work Unit | 任务条目、进度、阻塞 |
| 8 | `AUDIT` | 抽检记录 | 抽了什么、结论、证据 |
| 横切 | `RULE` | 开发纪律 | 不随某条需求变的护栏 |
| B 线 | `ROUND` | 轮次产物 | 工单、通知、候选、评审、裁决、处置、验收 |
| B 线 | `DEC` | **所有者决定** | 人拍板过、但不走轮次的判断 —— 见 §4.4 |
| 入口 | `ENTRY` | 目录入口 / 交接 | 冷启动的读者从哪进 |

### 4.2 归属判据：三问，机械可执行

⚠ **归属判据必须先于归属结果。**给一段内容定类型，问三个问题，顺序固定：

```text
问一：它记的是「人说过什么」，还是「我们算出什么」？
        人说过的        → REQ / DEC / AUDIT     （追加不改类）
        我们算出的      → 继续问二

问二：它会不会因为代码变而**必须**跟着变？
        会              → CONTRACT / 测试        （随码类，改代码不改它就是 bug）
        不会            → 继续问三

问三：它记的是「现在是什么」，还是「当时为什么」？
        当时为什么      → ADR                    （只被取代，不被修改）
        现在是什么      → TLD / RULE             （可修订类）

三问都不适用的，只可能是 WU（状态）或 ROUND（轮次产物）或 ENTRY（入口）。
```

**这三问是机械的**：任取一节，三问各有唯一答案，不靠品味。§9 给了可复核的抽查方法。

### 4.3 生命周期由**在流程中的位置**决定，不是由内容种类决定

| 类型 | 谁能改 | 怎么改 | 旧版怎么办 | 为什么是这条规则 |
| --- | --- | --- | --- | --- |
| `REQ` | 只有人 | **追加，不改**已写的 | 全部保留 | 它是人说过的话；改了就不知道当初要什么 |
| `AT` | 人拍板后冻结 | 改要走 B 线 | 记入 `ADR` | 产出方≠验收方的载体，实现者不得自行放宽 |
| `TLD` | AI 可改 | 直接改 | 实现完成后价值衰减，可整份被取代 | 它描述「怎么做」，做完就不重要了 |
| `ADR` | **写完不改** | 只能被后来的 `ADR` 取代 | 永久保留，标「被 ADR-NNNN 取代」 | 它的价值全在「当时」和「代价」两个词上；改了就没有「当时」 |
| `CONTRACT` | 随代码 | 与代码同一个提交 | 破坏性变更必须新 major + 双版本窗口 | 改代码不改它就是 bug |
| `WU` | AI | 每天变 | 不保留 | 状态；**不进仓** |
| `AUDIT` | 只有人 | 追加 | 全部保留 | 证据 |
| `RULE` | 走 B 线 | 只增不减；减也要走 B 线 | 保留并标失效理由 | 护栏被悄悄拿掉是本仓已发生过的事 |
| `ROUND` | 环节内可写，环节结束冻结 | 不改 | 归档，永久可取件 | 冻结物不可改，改了证据链断 |
| `DEC` | 只有人 | 追加 | 全部保留 | 同 `REQ` |
| `ENTRY` | AI 可改 | 直接改 | 随时重写 | 它只是路标 |

### 4.4 `DEC` 是本文新增的一类，理由来自本轮自身的失败

**问题**（对应任务书 Q8「不走轮次的工作，其取证记录放哪」）：

所有者在窗口里拍板的判断，今天**没有落点**。`rounds/` 装轮次产物，
`working/request-baseline/` 装产品需求，两者都不是它。

**这不是假想**。本轮第一次尝试作废的直接原因就是这个洞：

> 所有者 2026-09-07 给出映射（`request-lifecycle`≈PRD、当前在做的≈TLD……）。
> 那是拍板。但因为没有一个「所有者决定」的落点，起草者把它写进了任务书的
> §5「本文不预设立场的问题」，**于是拍板被降级成待议题**，
> 再在 §6.4 F1 里给正确答案设了扣分项。两份候选都绕开了 PRD/TLD。
> （`rounds/dev-plan-refact/rulings.md` R1）

**有了 `DEC` 之后**，那句映射会落在 `DEC` 里，属「追加不改」类；
任务书引用它时只能引，不能把它挪进「不预设」表——因为两类的生命周期规则不同。

⚠ 这是本文最不依赖外部参考的一条：它从本项目**已经发生的一次失败**推出，
而不是从任何一份流程实践里抄来。

### 5.1 什么时候必须调 B 线

沿用现有档位判据，不改：**不可逆 / 权威层 / 已知对立 / 判据未定**，四者任一命中即 T2。
本文补一条**方向不对称**（现有纪律，写进流程以便机械化）：

> **朝严谨可自裁，朝省事须人确认。**
> 加一条判据、收紧一个门——AI 可自行决定。
> 去掉一条判据、放宽一个门、跳过一个阶段——必须走 B 线或人授权。

## 6. 命名：用通行名，但注明差异

**用通行名。**理由：新人认得，且所有者已给出映射。
⚠ 但每个名字都必须注明**我们的规则与通行期待的差异**，否则名字会带来错误预期。

| 我们的类 | 通行名 | ⚠ 差异 |
| --- | --- | --- |
| `REQ` | PRD | 通行 PRD 是整理过的需求文档；我们的 `REQ` 是**人说过的原始档案，追加不改** |
| `AT` | 验收标准 | 通行做法允许实现者补充；我们**冻结**，改要走 B 线 |
| `TLD` | 技术方案 / SDD | 一致 |
| `ADR` | ADR | ⚠ **最大的差异**：通行 ADR「只被取代不被修改」，而现有 `rulings.md` 是**可追加可编辑**的。采用 `ADR` 这个名字就必须同时接受它的生命周期规则——见 §7 Q9 |
| `CONTRACT` | API 契约 / Schema | 一致 |
| `WU` | Story / Task | 我们不估点、不排期 |
| `RULE` | 编码规范 / 护栏 | 我们的只增不减 |
| `ROUND` | —— | **无通行对应物**。这是本项目特有的并行提案机制 |
| `DEC` | —— | **无通行对应物**。见 §4.4 |

**两类没有通行名，因此自造。**按任务书要求说明为什么现有名装不下：
`ROUND` 装的是「同一个问题被五方独立审视再裁决」的全过程，ADR 只对应它的最后一格；
`DEC` 装的是「人在流程之外拍的板」，通行实践默认这类判断会自然进入 PRD 或 ADR，
而本项目的实测是**它会掉进缝里**（§4.4）。

```text

                             → 问三：现在是什么 → RULE  ✓ 唯一
```
