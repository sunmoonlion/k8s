## 基线与一次冻结失误（如实记）

⚠ **`call-①` 在 `08d138f1` 写了「本通知与任务书在本环节冻结，不再改动」，
而此后 `round.md` 又被改过一次**（`44213399`，改角色：投喂改由所有者执行）。
**是我破的冻结。**

**为什么这次没有造成损害**：那时**一家都还没投喂**，无人在冻结物上开工。
按协议 §8c.1 的同一逻辑（同步只在环节之间做），**未开工前重定基线是干净的**。

**处置**：重定基线到当前 master，五家工作区重新供给到该点，`call-①` 随之重新冻结。
⚠ **教训**：**「冻结」不该在角色还没定完时宣布。**`call-①` 写于角色定案之前，
冻结声明因此必然要被打破——**错在宣布得太早，不在后来改**。

**基线的口径**：`baseline` 指**五家工作区的起点 commit**。
记录它的那次提交必然晚于它自身一拍（一份文件不能包含自己的哈希），
故 `round.md` 落盘时间晚于 `baseline` 一个提交，**这是记录顺序，不是不一致**。

## 检视面：所有者怎么读五份候选

⚠ **候选落在各家的 `dev-plan-refact/<家>` 分支上，而所有者的 checkout 在 master——读不到。**
这不是权限问题，是 git 的工作方式：一个 checkout 一次只能在一个分支上。

```bash
python3 sunmoonai/docs/dev-plan/protocol/round-review.py --round dev-plan-refact
```

开出 `~/review/dev-plan-refact-<家>/` 五个只读检视面，逐家报**行数与 sha256**；
没交的那家会明说「⚠ 该文件不存在——还没交，或交到了别的路径」。

| 规矩（协议 §7.2） | 为什么 |
| --- | --- |
| 一律 `--detach`，不占分支 | 一个分支只能被一棵 worktree 检出；占了会把该家踢出自己的工作区 |
| **不要往检视面里写** | 它是只读参照；要改稿在整合面上改 |
| 读完拆：`--close` | 长期挂着会被误当成第九个参与方 |

⚠ **已存在的检视面不会自己跟进**——它 detach 在开的时候那个 commit 上，该家之后再提交，
这里还是旧内容**而看起来一切正常**。脚本每次跑都刷到分支当前头并验证，
刷新会打印 `↻ <家> 已刷新 <旧> → <新>`。

## 本轮的角色特例：裁决方是 principal

所有者 2026-09-07 定：**五家全参赛（含 opus），所有者本人裁决，吸收方到时指定。**
这是本项目第一次由 principal 担任裁决方，有四处连带影响，逐条写明。

### 一、裁决与整合被拆成两个位置

协议原文把两者合在一个角色里：验收方规则第 1 条写「**不得是裁决方——整合方不能自验**」，
括号里的理由说的其实是**整合方**。本轮两者分离：

| 位置 | 谁 | 干什么 |
| --- | --- | --- |
| **arbiter** | `owner` | 定基座、逐条裁定吸收与否、处置异议 |
| **integrator** | ③ 之后由所有者指定 | 执行吸收：把裁定落成文字，写处置记录 |

⚠ **验收方计算随之改口径**：排除 **integrator**（不是 arbiter），再排除基座作者，
然后取处置表中 `接受 + 部分接受` 最少的一家。
⚠ 协议第 5 条「都不可用时由项目所有者验收」**本轮不可用**——所有者已是裁决方，
再兼验收就没有独立验收了。若算不出，改由所有者从五家中指定一家，并写明理由。

⚠ **这是对协议的一处实质偏离，本轮按特例执行，不改协议正文**；
是否把「裁决/整合分离」立为通则，另起工作单元（属 T2，协议修改）。

### 二、裁决方不重读 320 节也要能判 —— 这改变了候选的交付形态

以往裁决方（opus）读过全部输入，候选可以把论证建立在「你也知道那些内容」之上。
**本轮不成立**：裁决方是所有者，不会去逐节读 320 节。

⚠ **由此推出一条硬要求：候选必须是自证的。**具体是：

1. **落点表必须机械可核**——骨架由脚本按 commit 枚举生成，人只填第三列（`B8`）；
2. **每条归属判据要能抽查**——给出「随便挑一节，怎么验它放对了」的方法，
   而不是「因为它属于这一类」；
3. **争议点必须自己标出来**——候选自己知道哪几处是判断而非事实的，要列出来；
   ⚠ **藏起来的争议点，裁决方发现不了，但验收方会发现，那时代价更大**。

**做不到自证的候选，等于要求裁决方替它做功课。**

### 五、投喂由所有者执行，`dispatch_event` 全部记在 principal 名下

| 位置 | 谁 | 本轮 |
| --- | --- | --- |
| **router / orchestrator** | 代码 + 跑它的人 | **所有者**（此前是 opus） |
| **传输动作** | `dispatch_event{mode = manual}` × 5 | **全部由所有者执行**，含对 opus 的那一次 |
| **arbiter** | principal | 所有者 |
| **integrator** | ③ 之后指定 | 待定 |
| **proposer** | 五家 | 含 opus，opus **仅此一个角色** |

⚠ **这使 opus 从三个角色降为一个。**此前 opus 同时是 orchestrator（跑脚本）、
arbiter（裁决）与本轮 proposer——**三者叠加正是协议反复警告的角色混同**。
现在它只是五家之一，与其余四家在同一条件下。

⚠ **代价：`dispatch_event` 数量不变但全部落在 principal 身上**（§5.1 要求可数）。
本轮五次投喂 + 后续各环节，所有者的动作数会显著高于以往——
这是 `dispatch = manual` 执行者的固有欠账，不是本轮新增的。

### 四、有一位参赛方的候选，裁决方读起来最费力

**不得以「我之前查过」作为依据**——所有者没有那个上下文。

## 与 `executor-adapter` 轮的排队关系 —— **已定**

| | 内容 |
| --- | --- |
| 本轮按哪个走 | **按所有者的判定**：`executor-adapter` 不改结论，故本轮重构不必等它 |
| 前提若被推翻会怎样 | 若 `executor-adapter` 日后确实改了 `agent-dev-guide` 的架构主张，本轮产物需按新结论做一次**定向修订**，不是重做——因为本轮只动组织方式（B1） |

另有「现在做不了」的事实原因：`executor-adapter` 需要 SDK 侧的实测取证，
而今晚的测试已证明 CLI 投喂路径答不了审批请求，SDK 路径尚未搭起来。
**取不到证据的轮次不能开**——这与协议 §8「验收判据先于产出冻结」同源。

## 本轮的特殊之处

`runtime-refact` 轮是 64 节，本轮 **399 节**。规模差 6.2 倍，而
「靠一次通读做融合会丢东西，且丢了不会有人发现」这条已经被上一轮证实过一次。
**落点表因此是交付物而非附赠，且验收会抽查落点是否属实。**
