# 规范开发流程结构（①a 候选）

> 候选作者：`kimi`（身份自证：本稿写在 `~/worktrees/kimi/k8s`，分支 `dev-plan-refact/kimi`）。
> 轮次：`dev-plan-refact` ①。基线：本工作区 `HEAD`（`git rev-parse HEAD`）。
> 本稿为 ①a；260 节逐节安置见同目录 `dev-plan-architecture.md`（①b）。

## 0. 一句话与前提

**一条需求的生命周期 = 定义 → 设计 → 派工 → 执行 → 验收 → 吸收归档，
每个阶段有产物、产物有落点、落点有判据、判据尽量由机器执行；
流程重量按可逆性分配，人的动作只留在「定义」与「验收」两端。**

前提（任务书 §2 一）：**开发全部由 AI 助手承担，人只提需求、拍板、验收。**
这不是细节，是结构条件——它把瓶颈从「产出」搬到「可信度」（AI 产出廉价，
验证不廉价，且 AI 不懂时会流畅地编）。因此本结构的修正全部落在
「让人/机器能证伪 AI 的自述」上（§6）。

⚠ 与 `inputs/` 的关系声明（B14）：本稿写作前通读了 `inputs/` 四份参考。
它们由参赛方 opus 起草，**不作为基准**。本稿与它们的取舍见 §8；
凡划分一致处，均给出「为什么它装得下我们的内容」的独立论证。

## 1. 主干：六个阶段

每个阶段写清三件事：**产出什么、存在哪、凭什么算过关**。
缺第三件的阶段不存在，它只是一段时间。

| # | 阶段 | 谁做 | 产出 | 存在哪 | 凭什么算过关 |
| --- | --- | --- | --- | --- | --- |
| S1 | **定义** | 人提需求；AI 复述 + 列决策点；人确认 | 需求条目 + 验收契约（每条可判定，或显式标 ⚠ 为什么当前不可判定） | 产品合同档 / 工单 | 人确认复述无偏差；每条验收指向一个未来的测试标识或人工门禁 |
| S2 | **设计** | AI 起草；人只评审不可逆部分 | 方案 + 决定记录（当时的问题、选项、代价与放弃） + 约束自检表 | 方向档 / 决定记录 | 约束表逐条勾过；不可逆项显式列出 |
| S3 | **派工** | AI 拆，人按档位授权 | 工单 / 任务条目（目标、前置、测试层次、验收、回滚） | 任务档 / `round.md` | **DoR**（§2.1），含「杀掉会话可续接」判据 |
| S4 | **执行** | AI，隔离工作区 | 代码 + 测试 + 证据（可复跑命令锚点） | 分支 commit + 取证 | 机器门全绿（§5 机器列） |
| S5 | **验收** | 独立验收方（≠ 产出方）；人抽检三样 | 验收结论 + 证据 | 验收记录 / 状态档 | **DoD**（§2.2），按冻结判据，不为通过而改标准 |
| S6 | **吸收归档** | 吸收方；人确认不可逆步 | 主线 commit + 决定索引更新 + 状态档更新 | 主线 + 档案 | 落点收据齐全；状态档与事实一致；人的确认落盘 |

三条横切线（不属于任何单一阶段，贯穿全部）：

1. **决定记录只追加**：任何阶段的「为什么选它」落成决定记录，写完不改，只被取代。
2. **证据可复跑**：任何阶段断言「做完了」必须附可复跑证据；自述不算。
3. **按可逆性分配重量**：可逆工作走 T0/T1（单线 + 独立评审），
   不可逆 / 权威层 / 判据未定走 T2 完整并行轮。档位判据与环节机械
   已在 `protocol/round-protocol.md` 实跑验证，本结构直接采用其为
   **协作协议**这一类文档的内容（见 §3），不重造。

**为什么是六段而不是九段**：经典划分里的「拆解排期」并入 S3（估点与批量排期
是产出昂贵的优化，AI 执行时失去意义）；「评审」不是独立阶段——机器评审是 S4 的
准出判据，人的评审收敛为 S5 的抽检三样；「交互设计」不单列，作为 S2 在涉及
界面时的规定产物（含空/错/慢三态），因为本仓当前阶段没有独立的设计
交付物读者。⚠ 该合并是本稿的判断，依据是「阶段必须有独立产物与读者」这条
判据本身。

## 2. 两个门

「可以开工了」与「做完了」是多数混乱的真正来源，各写成一张清单。

### 2.1 DoR —— 可以开工（S3 的准出）

- [ ] 验收判据**先于产出冻结**（任何档位都不能省的第一条）；
- [ ] 验收判据每条可判定：指向测试标识 / 可复跑命令，或显式标 ⚠ 归人工门禁；
- [ ] 前置已就绪，或阻塞点已显式登记；
- [ ] 约束自检表已勾（S2 产物），不可逆项已显式列出；
- [ ] 档位已定且留痕（T0 记在任务条目，T1/T2 记 `round.md`）；
- [ ] **杀掉当前会话，另一个执行者只读持久载体能接着做**——
      通不过说明还没拆到可交给 AI 的粒度，不是助手的问题；
- [ ] 任务条目栏位齐全，缺栏视为未定义，不开工（沿用现行纪律）。

### 2.2 DoD —— 做完了（S5 的准出）

- [ ] 冻结判据逐条通过；机器能判的部分由机器判（§5），**不许例外**；
- [ ] 验收方 ≠ 产出方（任何档位都不能省的第二条）；
- [ ] 证据可复跑：命令、commit、输出三件套，不是「我之前查过」；
- [ ] 不可逆动作已经人确认（任何档位都不能省的第三条）；
- [ ] 规格类文档与代码同步更新（改代码不改规格即 bug）；
- [ ] 状态档更新到与事实一致；决定索引登记了本次产生的决定。

## 3. 文档类型：从阶段推导，不独立另立

推导规则：**每个阶段的产物是一类文档；横切线各是一类；
「流程自身要被冷启动的 AI 执行」再生产两类（协作协议、上下文包）。**
类别没有先验清单——它是上一行规则的输出。

| 类 | 从哪推出 | 例子（本项目） | 生命周期 |
| --- | --- | --- | --- |
| **需求合同** | S1 产物（项目尺度即 PRD） | `working/request-lifecycle.md` | 修订须过规范修订工作单元；旧语义保留修订记录，不得无痕消失 |
| **规格** | S1 验收契约随实现落地的部分 | API 契约、数据模型、验收测试 | **随代码同步**；改代码不改它是 bug；能被 CI 校验 |
| **决定记录** | 横切 1（≈ADR 的「决定」部分） | 各轮 `rulings.md` 的裁定行 | **只被取代，不被修改**；旧版永不删 |
| **约束护栏** | S2 的不可违反项沉淀 | `constraints.md` | 变更门槛高于普通文档（权威层，走 T2）；每条标「谁在执行」 |
| **方向档** | S2 在项目尺度的产物（要建什么、为什么这么建） | `development-plan.md` | 随方向决定更新；不记进度 |
| **任务档** | S3 产物 | `implementation-plan.md`、`round.md` | 条目级更新；完成即归档，不回写论证 |
| **状态档** | S6 的「现在到哪了」 | `handoff.md` | 每天可变；只写状态，不写论证（写论证会随进度漂移） |
| **协作协议** | 「流程自身要被执行」——怎么一起干活、怎么做决定 | `protocol/`（`round-protocol.md` + 脚本） | 协议改变走 T2；规范与实现对不上时以规范为准，立工作单元改 |
| **工程手册** | 同上，面向「怎么搭、怎么干」的执行知识 | `agent-dev-guide.md` | 活文档，随架构演进修订；自增内容须声明理由（其 §9 现有纪律） |
| **取证档案** | 横切 2 的沉淀 + 审议过程 | `rounds/` 64 份、`evidence/` | **归档即冻结**，只追加不内部重排 |
| **上下文包** | AI 冷启动前提（§6.4） | 五仓 `AGENTS.md`、组件 `CLAUDE.md` | 随项目结构校准；**越短越好**（每行都占上下文预算） |

「决定记录」与「取证档案」的关系：决定记录是档案中**被索引的那一格**——
档案装全过程（决定 + 审议），决定索引（Q9，见 ①b）让决定可检索。
两者不拆成两份正文，拆了就制造第二真源。

**为什么这是推导而非并列**（J2）：删掉任何一个阶段，对应的类就没有来源；
删掉任何一类，对应阶段的产物就没有落点。读者可以用这条双向检验上表。

## 4. 每类文档的生命周期规则

| 类 | 谁能改 | 怎么改 | 能被取代吗 | 旧版怎么办 |
| --- | --- | --- | --- | --- |
| 需求合同 | 任何人提议，人拍板 | 规范修订工作单元（原始请求、影响分析、迁移方案） | 能，整份修订 | 修订记录保留旧语义与迁移边界 |
| 规格 | 实现者 | 随代码同 PR | 随代码演进 | 版本历史 |
| 决定记录 | 任何人起草，裁决方定 | **写完不改** | 只能被新决定显式取代 | 永不删，保留「当时」 |
| 约束护栏 | 走 T2 | 升档修改 | 条目级取代 | 版本历史 + 修订理由 |
| 方向档 | 人拍板 | 直接改 | 整体可被新方向取代 | 旧方向降级为历史设计输入（如 v5 现状） |
| 任务档 | 执行者 | 条目级 | 完成即失效 | 完成条目留痕，不展开 |
| 状态档 | 执行者 | 随时重写 | 每天被下一次状态取代 | 不留旧版（git 历史即旧版） |
| 协作协议 / 工程手册 | 走轮次 / 工作单元 | 规范优先 | 章节级演进 | 历史稿归档 `archive/` |
| 取证档案 | 归档动作本身 | 只追加 | 否 | 原样冻结 |
| 上下文包 | 维护者 | 随结构校准 | 整体重写 | 不留旧版 |

## 5. 判据归属：机器还是纪律

把两者混在一张清单里是最常见的自欺（本仓 `constraints.md` 三层理论已写死这一点：
「只有第一层不依赖人」）。逐门归属：

| 门 / 判据 | 执行者 | 现状载体 |
| --- | --- | --- |
| S1 验收条目可判定性 | ⚠ 纪律（人 + AI 自检）；机器只能判「是否标了 ⚠」 | 任务条目格式（缺栏不开工） |
| S2 约束自检 | 混合：有测试载体的随测试跑（机器），22 条 ⚠ 自检（纪律；现状断言见 `inputs/readiness.md` §1.2，可复跑出处在该文附录） | `test_kernel_invariants.py` 等 |
| S3 工单字段齐全 / 档位留痕 | **机器** | `round-status.py` 解析 `round.md` |
| S4 代码与文档机械不变量 | **机器** | `pytest`、`doc-gate.py`（pre-commit）、`anchor-gate.py` |
| S5 机器可判部分 | **机器** | `round-status.py --verify`；判不了的显式标 🔶人判，不计入通过 |
| S5 人抽检三样（意图 / 不可逆 / 证据抽样） | **人**，不可委派 | 验收记录 |
| S6 落点齐全 / 状态推导 | **机器** | `round-status.py`（从产物反推，不看声明） |
| 不可逆动作确认 | **人** | 回执落盘；⚠ 现状回执强度不足（`handoff.md`「不能倒退的两条」已登记） |

⚠ 诚实边界：S1/S2 的多数判据**当前只能靠纪律**。本结构不假装它们已机器化，
而把「把判据从纪律层搬到测试层」登记为流程自身的待建工作。

## 6. AI 前提下的五条结构修正

经典流程为「产出昂贵」优化；AI 执行后三个成本结构翻转（产出→0、验证不变、
上下文延续→0）。本结构由此做五条修正——它们是阶段与门的**形状**，
不是附加清单：

1. **S1 内嵌意图确认**：AI 复述需求 + 列决策点 + 标歧义，人确认后才允许开工。
   人写的需求只被解释一次，偏差到交付才暴露时返工最贵；这一步几分钟，
   挡掉的是最贵的错误。
2. **验收先于实现且角色分离**：验收判据由 S1 产生、不由实现方产生；
   产出方 ≠ 验收方。AI 流程里「自己实现 + 自己写测试 + 自己报告通过」
   是三位一体的自证，等于没有验证。
3. **证据可复跑是准入不是加分**：AI 报告「测试全绿」不可信——不是撒谎，
   而是可能跑的不是那件事。证据必须是可复跑命令或 CI 产出。
4. **上下文包单列一类**：AI 隐性知识为零，每次冷启动。它的判据特殊：
   短、准、自动注入；写长了不是更周到，是更差。
5. **不可逆动作靠门禁不靠纪律**：AI 执行破坏性操作时语气与安全操作完全一样，
   「看着点」不成立。显式清单 + 硬门禁 + 人确认。

## 7. 命名说明

本稿给六个阶段与十一类文档用了自描述名（定义/派工、需求合同/决定记录……），
括注通行名（PRD/ADR/TLD）只为对齐读者直觉。**按任务书口径，通行名不加分
不扣分**；判的是每一格的规则是否说清（§3–§5 的表即规则）。
所有者起点「当前在做的 ≈ TLD」落在本结构的**工程手册 + 协作协议**两类上，
理由见 ①b 的 Q3。

## 8. 与 `inputs/` 四份参考的关系（B14 声明）
