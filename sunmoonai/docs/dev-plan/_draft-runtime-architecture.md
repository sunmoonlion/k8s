### 0.2 十二个词，一句话一个

前八个是**内核对象**，定义在 `working/request-lifecycle.md`「核心对象」一节，
本文给的是**便于阅读的一句话**，**以内核为准**：

| 词 | 一句话 | 权威定义 |
| --- | --- | --- |
| **Task** | 用户提交并等待业务结果的那一件事。跨连接、跨进程、跨多次尝试而存在 | 内核「核心对象」 |
| **Attempt** | 为完成一个 Task 发起的**一次执行**。一个 Task 可以有零到多次 Attempt | 同上 |
| **Interaction** | 系统向人请求输入或批准，**以及人的回答**。本文主张它必须能带内容（§4.3） | 同上 |
| **Artifact** | 任何有版本、有作者的产出物：工单、候选稿、评审、裁定、代码提交 | 同上 |
| **Event** | 只追加的事实记录。状态是它的投影，不是它的对手 | 同上 |
| **Side Effect** | 对外部世界的不可逆动作：写共享路径、推主线、发布 | 同上 |
| **Delivery** | 结果怎么送到人面前，以及怎么重新取回 | 同上 |
| **Task Profile / Agent Profile** | 前者是「**这类活的契约**」（输入、输出、验收、证据、策略）；后者是「**这个执行者的能力**」（模型、工具、权限、可观测粒度） | 内核「Task Profile 与 Agent Profile」 |

后四个是**本文引入的**，本文即权威：

| 词 | 定义 |
| --- | --- |
| **principal** | **有权在某条状态转换上做决定的主体**，且这个权力**不来自它能不能执行**。本项目当前只有一个 principal：`owner`（项目所有者）。人**不是**执行者，是 principal——这是本文最重要的一条主张，理由见 §4.1 |
| **orchestrator** | 推进状态、派发、收集、观测逾期的那段**确定性代码**。**它是代码，不是角色**——过渡期由人按脚本跑，人是它的**触发通道**，不是它本身 |
| **provenance** | 一条轨迹记录的**来源等级**，三值：`attested`（运行时从它控制的底座直接取得）/ `reported`（执行者或人的自报）/ `inferred`（事后读产物推出来的） |
| **harness** | 执行者的**运行外壳**：二进制 + 提示词 + 工具集。`codex-cli`、`cursor-agent`、`cursor-app`、`qoder` 各是一个 harness。⚠ 早期文档管这个字段叫 `runtime`，与「产品运行时」一词三义，已改名 |

## 1. 一句话说清这是什么

**只有一个产品运行时。**它是内核七个对象的**唯一权威写入面**，加四段确定性代码。
所有的活——今天的文档开发、将来的财务分析——都是跑在它上面的 **Task**，
按各自的 **Task Profile** 走同一套状态机。

**「开发」不是运行时旁边的另一套流程**，它是运行时的**第一个 Task Profile**（`dev.change`）。
它今天看起来特殊，只因为我们正用现有的 AI 助手**开发运行时本身**——
运行时建成之后，后续开发照样走它，只是由它调助手，而不是人手工调。

这一条推翻了上一版方案（`refact-fable.md @ 7e8464c2`）的「两个 Profile」分层：
那两者只差**取值**（账本用 git 还是 PostgreSQL、执行者是 CLI 还是 SDK），不差**结构**，
不构成两个抽象。推翻的经过见 `rounds/runtime/runtime-disposition.md`。

## 2. 运行时由什么组成

```
                    产品运行时
  ┌─────────────────────────────────────────────────┐
  │  内核对象的唯一权威写入面                          │
  │  Task · Attempt · Interaction · Artifact ·        │
  │  Event · Side Effect · Delivery                   │
  ├─────────────────────────────────────────────────┤
  │  四段确定性代码（不是角色，是代码）                 │
  │   router          从请求算出走哪个 Profile、什么档位、派给谁 │
  │   orchestrator    推进状态、派发、收集、观测逾期        │
  │   interaction     产生问询、鉴别响应者、把人的修改落成版本 │
  │   validator       跑验收里机械可判的那部分            │
  ├─────────────────────────────────────────────────┤
  │  两个适配层                                       │
  │   executor adapter  怎么调执行者、能看见多少、能拦在哪  │
  │   principal channel 人怎么被叫到、怎么回、身份怎么鉴别  │
  └─────────────────────────────────────────────────┘
```

四段代码为什么必须是**确定性代码**而不是 agent：如果编排本身由 agent 做，
那么「谁在推进状态」就不可复核了。这条在早期文档里已立，本文沿用。

**状态机只有一套**，取自内核，本文不新增一个状态词、不走一条内核之外的边：

```
Task:    RECEIVED → VALIDATING → QUEUED → RUNNING ⇄ WAITING
                  → SUCCEEDED | FAILED | CANCELLED | REJECTED
Attempt: CREATED → RUNNING ⇄ WAITING
                  → COMPLETED | FAILED | CANCELLED | BUDGET_EXCEEDED
```

**一个容易混的地方**：Attempt 的终态叫 `COMPLETED` 不叫 `SUCCEEDED`。
一次执行跑完了、产出了东西，**不等于**用户要的结果达成了——中间隔着验收。
所以 `Attempt COMPLETED` 是 `Task SUCCEEDED` 的**必要不充分**条件。
反过来也不对称：一次 Attempt 失败**不会**让 Task 失败，Task 会退回排队再试。

## 3. 谁在执行：Agent Profile

五家助手各是一个 Agent Profile。**人不在这张表里**（理由见 §4.1）。

| Agent Profile | harness | 怎么调 | 运行时能看见多少 |
| --- | --- | --- | --- |
| `ap.luna` | `codex-cli` | `codex exec` | 进程级 |
| `ap.kimi` | `codex-cli` | `codex exec` | 进程级 |
| `ap.cursor` | `cursor-agent` | `agent -p` | 进程级 |
| `ap.fable` | `cursor-app` | **无命令行入口，人手工投喂** | **只有文件系统前后差** |
| `ap.qwen` | `qoder` | `qoder -p` | 进程级 |

### 3.1 「能看见多少」是三个字段，不是一个

早期文档把三件事绑成一列，它们其实可以分开取值：

| 字段 | 取值 | 问的是 |
| --- | --- | --- |
| `observability` | `tool.enforced` ＞ `tool.reported` ＞ `process` ＞ `fs-only` | 运行时**能看见**多细 |
| `enforcement` | `tool-level` / `outer-only` | 运行时**能拦**在哪 |
| `sandbox` | `runtime` / `self` / `none` | 沙箱**谁提供**、策略谁定 |

**分开的理由是实例**：`codex exec --json` 能逐次工具调用吐 JSONL
（`~/repo/codex/codex-rs/exec/src/cli.rs:60`），**看得见**到工具级；
但吐的是执行者**自报**，运行时既拦不住（拦截点在进程内）也验不了。
所以它是 `tool.reported`——比 `process` 细，但不是证据。

**当前五家全部是 `outer-only` + `self`，没有一家是 `tool.enforced`。**
那个取值要等运行时自己的 agent（SDK 腿）建成才会出现。

### 3.2 由此推出的三条

1. **进程级及以下执行者的自报，一律不采信。**「我跑了测试」「我核过源码」是**主张**，不是证据。
   证据必须由运行时从工作区**重新推导**：diff、复跑命令、独立取证。
   反面实例：上一轮有一家拿休眠代码当能力证据，九份评审无一发现。
2. **`RUNNING` 判不了，原因不在账本。**缺交付可能是「未调用 / 在跑 / 崩了 / 失联 / 超时」五选一。
   早期文档把这归咎于 git 载体——**归因错了**，换成数据库一样判不了**进程内部**。
   这是执行者属性。
3. **「独占工作区」在 CLI 腿上是约定，不是隔离。**运行时在宿主建个目录、把路径告诉进程，
   而那个进程看得见整个文件系统。SDK 腿才是真隔离。两者强度不同，不能用同一个词。

## 4. 人在哪里

### 4.1 人不是执行者，是 principal

这是本文最重要的一条，值得展开为什么。

早期文档把人和 agent 一起登记在「执行者表」里，理由是分发脚本不必特殊处理人。
**那是倒过来的**，两条证据：

- 在「产物 → 状态机」的映射里，**人一次都没有出现在 Attempt 那一侧**。
  人出现的位置全是 `WAITING(APPROVAL)`——那是**转换边上的门**，不是跑 Attempt 的东西。
- 早期文档自己列的「人的四点差异」，四条落点是批准权、裁量、最终责任、跨会话——
  **没有一条是关于「执行」的**。

一个东西从不产出 Attempt、其全部特征都是权力，那它就不是执行者。

**那人产出的内容怎么进系统？**从 **Interaction 的响应侧**进，不从 Attempt 出来（见 §4.3）。
人有两个位置，都在 Task 的边上：**requester**（创建 Task）与 **principal**（在受门的边上响应）。

### 4.2 人的八条权力

每一条都对应唯一状态机的**一条边**，且都有一个 agent 够不着的**强制点**：

| 行 | 人做什么 | 状态转换 | 强制点 |
| --- | --- | --- | --- |
| **H1** | 冻结题目与验收标准 | 工单 `DRAFT → FROZEN`；Task `WAITING(APPROVAL) → VALIDATING` | 回执仓的签名回执 |
| **H2** | 开工确认（路由、名单、工作区） | `VALIDATING → QUEUED` | orchestrator 不分发 |
| **H3** | 省事方向的裁定生效 | `WAITING(APPROVAL) → QUEUED` | 回执仓；无回执的裁定视同不存在 |
| **H4** | 扩权（追加预算或范围） | 同上，或 `→ FAILED` | 同上 |
| **H5** | **不可逆动作**：写共享最终路径、推主线 | `RUNNING → SUCCEEDED` 的门 | **凭据层**：主仓对 agent 只读 |
| **H6** | 推翻已生效的裁定、改已冻结的标准 | `WAITING(APPROVAL) → QUEUED` | 回执仓 + 冻结区逐字节校验 |
| **H7** | 取消 | 非终态 `→ CANCELLED` | 裁定行（唯一不锚仓外的行，失败安全方向） |
| **H8** | 回答问询，**含带内容的修改** | 验证期 `WAITING → VALIDATING`；执行期 `WAITING → QUEUED` | interaction service 鉴别响应者 |

三条纪律：

- **H5 批准的是执行动作，不是终态。**内核里**没有** `WAITING → SUCCEEDED` 这条边。
- **H1 属验证阶段**，恢复边是回 `VALIDATING`，不是 `QUEUED`。
- **改授权范围不算「改方案」**，那要建新 Task。

**人代跑脚本（把固定指令粘给不能自动分发的执行者）不是权力**，
它是 orchestrator 的欠账，记成 `dispatch_event`——**但必须可数**，因为成本核算要数它。

### 4.3 Interaction 必须能带内容

所有者要的是三件事：**全部否定**、**部分否定**、**以自己的方案替代**。
内核当前的 Interaction 装不下后两件——它的入向只有「令牌被消费了没有」一个布尔。

缺的是两个方向：

| 方向 | 现在有 | 缺 |
| --- | --- | --- |
| 出向 | 一句话 | **展示哪个 Artifact 的哪个版本**、人**可以改哪些字段**、这份东西是**几级证据** |
| 入向 | 一个布尔 | `approve` / `reject` / `amend` 三值 + amend 的内容 |

关键三条：

1. **人的修改成为一个新 Artifact 版本**，作者是 principal，并成为**下一次 Attempt 的输入**。
2. **可改范围是入向的拒收约束，不是出向的展示提示。**只展示不强制，第一次「人改了范围外一条」
   就退化回「布尔 + 全文替换」。
3. **不能绕成「建新 Task」**：内核规定建新 Task 的条件是「改目标、口径、授权范围或 Profile 版本」，
   而部分否定一份方案时这四条一条都不命中。

**这不是开发期特有的。**财务分析 agent 交一份分析计划给人审、人改两条让它照改——形状完全相同。
所以这是**内核要改**，不是在开发这一侧打补丁。

## 5. 边界：为什么必须在别人家里

### 5.1 一条实测结论

本机跑 agent 的用户 `zym` 拥有**免密 sudo**（`(ALL) NOPASSWD: ALL`）且在 **docker 组**。
两者各自独立地把 agent 提权到 root。由此：

| 强制点放在哪 | 对 agent 有效吗 |
| --- | --- |
| **托管方**的 key 作用域、分支保护、账户公钥端点 | **✅ 有效**——它在 agent 够不着的地方 |
| VM 上的脚本、hook、门禁 | ❌ 无效——`sudo` 一句就改了 |
| VM 上的文件权限、只读挂载 | ❌ 无效——同上 |

**这条把「强制点必须在凭据层」从设计判断变成了实证。**复跑记录见 `rounds/_spike-sign/forensics.md`。

### 5.2 三道边界

| 要防的 | 边界 | 为什么 agent 够不着 |
| --- | --- | --- |
| **伪造回执** | **回执仓**：一个私有仓，VM 只持只读 key。每份回执是仓里的一个**签名 commit**。验签用的公钥**在线**取自托管方的账户端点，不落本地 | 写权限与公钥端点都不在 VM。本地脚本可以被改，**但它改不了「回执仓里有没有那条 commit」** |
| **绕过回执发布** | **主仓写权限移出 VM**：agent 的候选推到**候选仓**，主线的写由人在签回执的**同一个动作**里做 | agent 根本发不起对主仓的写 |
| **签名被代做** | 签名私钥只在人自己的设备上，带口令，不进 agent 域 | 见下 |

⚠ **第三条有个坑，是本项目实际踩到的**：所有者的编辑器是 **Remote 连到这台 VM** 的，
**在它里面开的终端就是 VM 的 shell**。所以「在自己电脑上签」必须是**本地 shell**，
不能是 Remote 终端——否则私钥落在 agent 能 `sudo` 读到的地方，整套边界白做。

**这三道边界不是过渡期的安全措施，是永久的架构组件。**
只要还在调用「运行时看不见内部」的执行者，它们就必须在。

### 5.3 证据等级

采信等级取 `min(来源, 可见上限, 隔离强度, 验收独立性, 覆盖)`——**任一未知即降级，不取平均**。

| 等级 | 来源 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| `E0` | 执行者或人的自述 | 只是一条待验证的主张 | 行为发生过、作者是谁 |
| `E1` | 运行时从冻结的工作区重算（diff、哈希、复跑测试） | 重算范围内的结果 | 进程内部没留痕的动作 |
| `E2` | 外层记录 argv / 输出 / 退出码，加 E1 | 调了哪个进程、外部结果如何 | 内部逐次工具调用 |
| `E3` | 运行时自己的工具网关逐次记录，加 E1 | 经网关发生的调用与策略检查 | 绕过网关的系统调用 |
| `E4` | **执行者凭据域之外**的受保护日志、签名、审计接口 | 指定主体或外部副作用的权威事实 | 人是否真的看懂了 |

**一条必须写死的纪律**：覆盖声明要同时列「查了什么」和「**没查什么**」。
零命中只有在输入集合可枚举且枚举成功时才算证据，否则结论是 `UNKNOWN`，**不是通过**。

### 5.4 当前最尖锐的矛盾

**人的回执，现在证据强度是零。**所有者与 agent 同机、同一个 git 身份、没有签名——
账本上分不出哪笔是人做的。而「人的确认」恰恰是全流程唯一不可逆的一步。

后果：所有涉及权力的轨迹条目，来源等级都只能标 `reported`，直到那个通道换掉。
**先有一个 agent 够不着的操作面，再谈换 key**——否则只是在同一个信任域里搬家。

## 6. 今天怎么跑，和目标态差在哪

同一个 Task Profile，两种 orchestrator 实现：

| | 今天 | 目标态 |
| --- | --- | --- |
| Task Profile | `dev.change` | 同一个 |
| 状态机 | 同一套 | 同一套 |
| orchestrator | 人按脚本跑 | 运行时服务 |
| 账本 | git 提交历史 | PostgreSQL |
| 分发 | 四家命令行 + 一家手工 | executor adapter |

**git 有两个角色，要分开看**：当 **Artifact 载体**（代码和文档的版本就是 commit）是**永久的**；
当**账本**（用提交历史反推状态）是**脚手架，要拆**。

### 6.1 怎么知道两种模式真的等价

分两层比，中间隔一个投影：

| 层 | 比什么 | 现在能判吗 |
| --- | --- | --- |
| **S 层** | 对象、状态词、**边**、权力表、Interaction 的字段 | **能**，看 schema 即可 |
| **R 层** | 一次具体执行的四条序列，投影之后逐条对应 | 要等两种模式都按同一 schema 落账 |

四条序列是：Task 状态序列、每个 Attempt 的状态序列、Interaction 序列、Artifact 版本序列。
投影 Π 丢掉执行者的私有事件（工具调用、界面内部步骤），保留边、权力命中、版本与作者。

**「谁在哪条边上有权」属 S 层**，是静态约束，不该塞进一次执行的轨迹里比。

四条比对规则，每条都有实际教训垫底：

1. **白名单制**：允许不同的只有账本、orchestrator 实现、可观测粒度的**取值**；其余一律判失败。
2. **取较粗的一腿比，并显式列出「没比的项」**——不声明就会把「粒度差」误读成「行为差」。
3. **两边都要声明权威源**：手工模式的轨迹是从提交历史**重建的投影**，不声明重建规则，
   比的就是两份各自编的故事。
4. **等价只能在两条轨迹里较低的来源等级上宣称。**一条全是自报的轨迹与一条全是实证的轨迹「全等」，
   证明的只是后者没多走边，证明不了前者真的走过。

### 6.2 一个实测：手工模式看起来在跑，轨迹却基本不可复原

拿上一轮的真实产物导出轨迹，23 条记录里：

```
attested（运行时能证实）  2 条   ← 而且这 2 条的「谁做的」仍然不可证实
reported（自报）        15 条
inferred（事后推断）     6 条

六个版本的稿子   零个独立 commit
两次评审         有事件、无产物
H1 与 H5         由同一个 commit 承担，账本分不开
```

**对照组**：更早一轮的整合分支有 **28 条逐主张提交**，同一个 Task Profile、同一种 orchestrator，
`attested` 条目数量级不同。**差别不在账本，在纪律有没有落成动作。**

### 6.3 拆脚手架的条件

不设「一键毕业」。逐项拆，每项一条机械可判的条件。其中最硬的一条：

> **Interaction 那一项，在「人拥有 agent 够不着的操作面」之前不得拆**——
> 服务态若在同一个信任域里提供响应端点，只是把「自报」搬了个家。

## 7. 什么时候该走运行时，什么时候不该

**运行时省的不是「调用助手」的成本，是编排、记忆、留痕、审批的成本。**

### 7.1 机械可判的分类

只看工单字段，不读题目自然语言。命中任一条，走运行时更便宜：

- 执行者两个及以上；
- 计划中有任何需要人批准的触点；
- 输入带版本锚，或依赖另一个 Task，或需要跨会话续接；
- **触及权威层路径**（约束册、内核、协议、策略、门禁脚本）——这条是**必须走**，无关便宜；
- 有副作用要记账，或产物要进证据账，或同形状反复跑。

都不命中的，走运行时**更贵**。

⚠ **不得用档位反推成本**：档位由不可逆性和权威层判，用它推成本是循环。

### 7.2 三类走运行时反而更贵的活

1. **改一个错字**。手工是「说一句 + 提交」两个动作；运行时即使全自动，也要建工单、
   **供给独占工作区**、发布。贵在供给：一个不需要隔离的任务被强制隔离。
2. **一次性提问 / 探索性阅读**。它没有产物要落盘，而运行时的输出契约必须有落点——
   于是要么造一个没人再读的产物，要么为一个不需要契约的任务形成契约。
3. **对不能自动分发的执行者的任何一次派发**。人要先把界面打开在正确的目录、
   跑身份判别、粘指令。**贵在派发与身份核对，与任务大小无关**——
   运行时看不见的执行者，每次调用都要人替它证明「是谁、在哪」。

**不接受「都值得走，留痕总是好的」**：留痕成本高于这笔改动的价值时，留痕不会发生，绕过会发生。

### 7.3 为什么这条这么要紧

**如果最轻的档位走运行时比开终端还贵，人就会绕过它；一绕过，账本就有洞；
账本有洞，运行时存在的理由就没了。**

所以「省手工成本」不是运行时的顺带好处，是它的**生存条件**。
最轻档位的开销上界因此要可数：人的必需动作、落盘产物数、从请求到派发的步数、
需要人代传的次数——任一维超标，这件事就不属于最轻档位。

### 7.4 绕过看得见吗

**先说限度：绕过发生在运行时之外，账本天然看不见。**声称「完全可观测」就是在造假指标。

能做的是三层，没有一层承诺全知：

1. **让绕过无利**：主线写入只经人签的那道门，绕过的产物永远进不了交付面；
2. **对账，而且分母取外部**：拿托管方的审计、git 底座去比，找不到对应记录的变更登记为
   「未归因」，**不得反向补造一个正常 Task**；
3. **如实声明看不见的**：没提交的改动、纯对话的问答，任何机制都看不见——不为它们造代理指标。
   **零命中只能写成「没查到」，不能写成「没有绕过」。**
