## 1. 背景

### 1.1 现状：文档体系是「一轮一轮长出来的」，不是设计出来的

`dev-plan/` 现有 **9 份文档、5320 行、260 节**（逐节清单见 [`inventory.md`](inventory.md)），
外加 `rounds/` 下 64 份轮次归档、`working/request-baseline/` 下 15 份原始需求档案。

它们的形态是**历次轮次的沉积**，不是按任何一种成熟工程实践组织的：

| 现有文档 | 它其实是什么 | 问题 |
| --- | --- | --- |
| `working/request-lifecycle.md`（647 行 42 节） | **三份文档焊在一起**：34 个 `F-*` 功能需求 + 22 个 `AT-*` 验收用例（**PRD 血统**）、七个对象的**领域模型**、`I1`–`I15` **不变量与规格** | 三种读者被塞进同一份文件 |
| `rounds/`（64 份） | 决定 + 完整审议过程 | **决定不可检索**：26 条裁定散在 3 个 `rulings.md`，**编号还撞车**——`R1` 在三轮里分别指三件不同的事 |
| `protocol/`（975 行 61 节） | **工作方式规范**（近似 RFC 流程定义 / 工程手册） | 它**不是**实施计划的一部分，但从未被正式定位 |
| `constraints.md`（214 行 15 节） | 架构约束 / 护栏 | 定位大体正确 |
| `agent-dev-guide.md`（3082 行 108 节） | 面向今后开发的指导 | 这条谱系唯一活文档；⚠ 它自己的内部组织从未被论证过，见 §2 三 |
| `development-plan.md`（142 行） | 产品路线图 + 架构取向**混合** | 两样在标准实践里分属不同文档 |
| `implementation-plan.md`（93 行） | 交付计划 | 结构正确，但**阶段一任务清单是空的**，写着「U1 未定，现在列的任何任务都会作废」 |

### 1.2 所有者要的是什么（**本轮的题面，不是待议题**）

所有者 2026-09-07 给出映射，**这是拍板，不是一方主张**：

```text
request-lifecycle  ≈ PRD
rounds             ≈ ADR
当前在做的          ≈ TLD
protocol           ≈ 实施计划的一部分
constraints        ≈ 开发纪律
```

所有者 2026-09-08 进一步明确了**两步的次序**：

> 「先提出一个规范的开发流程结构，然后把我们现在的 `dev-plan` 按现有的结构
> 融合进各自提出的规范开发流程。」

以及一条对参考材料的定性：

> 「这个 pipeline 现在有个参考，但是你一人写的，**大家还可以提出别的框架结构**。」

⚠ **第一版任务书把上述映射降级成了「不预设」的待议题（Q1/Q2/Q3/Q7），
又在 §6.4 F1 里把「直接套 PRD/ADR/TLD」写成扣分项。**那是本轮作废的直接原因。
本文撤销 Q7 与 F1，见 [`rulings.md`](rulings.md) R1 处置 2、3。

**现在的口径**：映射是所有者给的**起点**。候选可以论证某一处映射不成立，
但**举证责任在提出异议的一方**，且必须在自己提出的流程结构里给出替代落点——
不能只说「它不像 PRD」。

### 1.3 为什么必须走完整流程

所有者原话：**「鉴于工程巨大，意义重大」**。三条客观理由：

1. **规模**：260 节；
2. **权威层**：重构对象包含**内核** `working/request-lifecycle.md`——它被 40 份文档引用、
   有 71 个带行号的外部锚点；
3. **不可逆**：文档重排一旦落盘，历史引用与锚点全部要跟着动。

### 1.4 一条必须先说的边界

**这一轮不改任何结论，只改组织方式。**
凡涉及「某个设计对不对」的问题，一律不在本轮处理——那是另起工作单元的事。
候选若在重构中**顺手修正了某个结论**，该处按 §4.1 B3 处理。

## 2. 题目

**先提出一套规范的开发流程结构；再从它推导出文档架构；再把 `dev-plan/` 现有 260 节
逐节融合进去。**

三步，**次序不可颠倒**，缺一不可。

### 一、①a — 提出规范开发流程结构

**这是本轮的第一交付物，也是 ②互评主要比的东西。**

一条需求从提出到上线，该经过哪些阶段、哪些门、每阶段产出什么、凭什么算过关。
候选必须自己提出这套结构，**不是从 `inputs/` 里挑一份照抄**。

至少要回答：

| 必答 | 说明 |
| --- | --- |
| **阶段** | 有哪些阶段。合并到什么程度由你定，但每个阶段必须写清**产出什么、存在哪、凭什么算过关**。⚠ 缺第三件的阶段实际上不存在，它只是一段时间 |
| **门** | 「可以开工了」和「做完了」分别是什么条件。⚠ 这两句话每个人理解不一样，是多数混乱的真正来源 |
| **文档类型** | 每个阶段要哪几类文档。⚠ **文档类型必须从阶段推导，不得自己独立立一套**——见下方「为什么次序不能倒」 |
| **每类文档的生命周期** | 谁能改、怎么改、能不能被取代、旧版怎么办。⚠ 不同类规则不同：例如决定记录**只被取代不被修改**，而规格**随代码同步、改代码不改它就是 bug** |
| **判据由谁执行** | 每个门的判据是**机器执行**还是**靠纪律**。⚠ 把两者混在一张清单里是最常见的自欺 |
| **前提：开发由 AI 承担** | 本项目的开发工作全部由 AI 助手承担，人只提需求、拍板、验收。你的流程结构必须在这个前提下成立，不能照搬默认「人写代码」的实践 |
| **命名** | 你可以用 PRD / ADR / TLD / SDD 这些通行名，也可以自造。⚠ **用通行名不加分也不扣分**；自造名要说明为什么现有名装不下。判的是**这一格的规则说清楚了没有**，不是叫什么 |

**为什么次序不能倒（本轮作废的根因）：**

第一版让候选**直接立文档类别**。文档是为流程服务的——脱离流程去立类别，
只能立出自洽但悬空的东西。两份旧候选都是这个形状：一份按「变更规则」分六类，
一份把文档全文物理并进一个文件，**两份都答不出「一条需求怎么走完」**。

所以本轮：**先有流程，类别从流程推导。**候选若先给分类再倒推流程，按 §6.3 否决。

### 二、①b — 把现有 260 节逐节融合进你提出的结构

把 [`inventory.md`](inventory.md) 里的 **9 份文档 260 节**逐节安置到 ①a 的结构中。

**零丢弃是底线，不是目标。**每一节要有落点，或「故意不要 + 理由」。

### 三、有机融合：内容要长进架构，不是堆进架构

⚠ 能证明「一节不缺」只说明没丢东西，**不说明放对了地方**。
每一节落在哪里，都要有「**为什么在这里、为什么不在别处**」的判据；
重构后的每份文档要有**自己成立的内部组织逻辑**。

**为什么这一条要单列**：零丢弃是**机械可判**的，有落点表就能核；有机融合**不可机械判**，
只能靠论证。⚠ **一份机械判据全绿的稿子，组织方式可以是任意的**——这不是假设，
本仓有一个可复核的实测。

**实测（2026-09-07，起草者做的一次吸收）：**`agent-dev-guide.md` 吸收两份 lifecycle 时，
三级节由 39 增至 76，**而 10 个二级章的划分一次都没有被重新审视**：

| 章 | 原有小节 → 现在 |
| --- | --- |
| §2 一个运行时的结构 | 5 → **12** |
| §3 一次开发 Task 怎样执行 | 5 → **18** |
| §4 人介入、Interaction 与权力 | 4 → **11** |
| §5 可观测性、证据与等效 | 5 → **11** |

每处内容都塞进了**最近的那一章**；该文 §0.2「为什么分成这些章」仍停在二级章一层，
从未解释过 §3 凭什么装这 18 件事。**而这次吸收通过了全部零丢弃检查**——
落点齐全、正文级已验、50 处真缺已补，每一条机械判据都是绿的。

⚠ **这个实测的用途是给候选一把尺子，不是让本轮去评审那次吸收。**

**由此给候选三条可判要求：**

1. **归属判据先于归属结果。**先说清「什么样的内容属于这一类/这一节」，再放东西进去。
   ⚠ 只给「§X 装了这些」的清单、不给「凭什么装这些」的判据，按 §6.3 否决；
2. **每份文档的内部结构要被论证，不能继承。**沿用现有章节划分是**允许的**，
   但必须给理由；⚠ **不给理由的沿用等于没做这一部分**；
3. **拆与并都要给代价。**主张把某份拆开或某几份合并时，必须写明：
   谁的引用会断、锚点怎么保全（B2）、读者的检索路径怎么变。
   ⚠ **只说「这样更清楚」不算论证。**
