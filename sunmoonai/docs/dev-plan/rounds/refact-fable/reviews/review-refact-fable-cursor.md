## 阻断级

### C1：威胁模型只罩住 H1/H5，H2/H3/H4/H6 的回执在工作仓可伪造

**为什么错**：§3.13 要防的只有一件事——伪造一条肯定的人类回执。§3.13.3 自己写明：
`rulings.md` 在工作仓，agent 能写，所以 H5 的 `acceptance` 块必须进回执仓 tag。
同一份威胁模型下，权力表却把更危险的几行留在 `rulings.md`：

| 行 | 回执形态 | agent 能否独立做出来 |
| --- | --- | --- |
| H2 | 「同一签名 tag **或** `rulings.md` 一条」 | 能。写裁定行即可开工（T1/T2 的唯一意图对齐点） |
| H3 | `rulings.md` 一条，`人确认 = 是` | 能。这正是 P3 说必须由人确认的省事方向（降档、跳环节、免除某家） |
| H4 | `rulings.md` 一条 | 能。扩权（工具 / 网络 / 预算）在 H5 之前就生效 |
| H6 | `rulings.md` 追加 | 能。改判已冻结验收标准后，H5 内容门比对的是**被改过的**集合 |
| H7 | `rulings.md` 一条 | 能。取消是肯定动作，不是「伪造否定 = 不回执」 |

H1/H5 的签名边界因此被绕开：agent 先伪造 H6 把验收条改成策略白名单里最容易过的子集，
再等人在 H5 对这个空集合逐条写 `pass`。内容门比的是集合相等，不比「集合还覆盖原意图」。
H2 的「或」更直接——T1/T2 可以在无人签名的情况下被分发。

这不是边角：§3.3 规则 3 写「回执必须是产物且不可伪造」，紧接着只给 H1/H5 配了仓外锚。
规则写了全表，锚只打了两行。

**应当是什么**：`auto_policy = 无` 的行，回执形态与 H1/H5 同档——回执仓签名 tag，
`transition` 扩成 `H1 | H2 | H3 | H4 | H5 | H6`（H7 取消属失败安全，可保留 `rulings.md`，
但须在表上注明「例外：伪造取消只停工，不放行」）。H2 的「或 `rulings.md`」删掉；
T1 一签两用仍成立（同一 tag 的 `transition` 写 `H1+H2`）。
`round-status.py` / `round-dispatch.py` 对这几行的判据改为查回执仓，与 §8 第 6 条对齐。

**证据**：

- `refact-fable.md` §3.3 H2 行「同一签名 tag 或 `rulings.md` 一条」；H3/H4/H6/H7 回执列
- `refact-fable.md` §3.13.3：「它放在 tag 里而不放在 `rulings.md`，是因为 `rulings.md` 在工作仓，agent 能写」
- `refact-fable.md` §3.13 开篇：「要防的只有一件事：伪造一条肯定的人类回执」
- `refact-fable.md` §3.3 规则 3：「回执必须是产物且不可伪造」——主语是回执，不是「仅 H1/H5」

### C2：T0 的 H1「策略层一次完成」验的是门禁白名单，不是本票意图

**为什么错**：12:00 用「T0 验收条 ⊆ 已签策略的机械门禁列表」解开了 H1 无默认 × 开工前零触点
的矛盾，逻辑自洽，但验错了对象。策略签名证明的是「这些门禁允许被 T0 引用」，
不是「**这一票**选中的子集穷尽了这一票的意图」。

攻击形状（agent 不必恶意，顺手即可）：

1. 工单意图写「修登录失败」；`acceptance = [lint, doc-gate.py]`，二者都在策略列表里；
2. H1 已在策略签名时完成，H2 按 T0 + `decide` 自动放行并落 `RouteDecision`；
3. L1 acceptor 只对照冻结标准，lint 与 doc-gate 通过即过；
4. 本票的意图覆盖检查全部压到 H5 / L3。H5 内容门要求的是「编号集合相等 + 各写一个词」，
   人可以对 `lint` / `doc-gate` 各写 `pass` 而不看 diff 是否真的修了登录。

于是 T0「不能机械验收的东西不该全自动」只挡住了**新写一条验收条**，
挡不住**用合法门禁子集架空意图**。这比 11:30 的自相矛盾更隐蔽：脚本会绿，意图是空的。

**应当是什么**：策略文件不要做成扁平门禁列表 + 任意子集，改成**命名任务类包**：

```toml
[bundle.doc-typo]
gates = ["doc-gate.py", "link-check"]
covers = "仅改 docs/** 的笔误与链接，不改约束、协议、脚本行为"

[bundle.script-fix]
gates = ["unit:<named-suite>", "lint"]
covers = "仅改已有测试罩住的脚本，不新增行为"
```

T0 工单的 `acceptance` 必须引用**一个包名**，不得自拼子集；
包的 `covers` 与工单 `intent_restatement` 由脚本做字面包含检查（包外意图 → 拒认为 T0，升 T1）。
包本身的增删改按 T2（与现文「策略修改按 T2」一致）。
这样「H1 在策略层一次完成」才真正成立：人签的是「这类题目用这组门禁就够」，不是一张可被任意挑选的零件清单。

**证据**：

- `refact-fable.md` §3.6：「T0 工单的 `acceptance` 必须是该列表的子集」——子集关系，无意图覆盖
- `refact-fable.md` §3.6：「任何需要新写一条验收条的题目自动不是 T0」——只约束「新写」，不约束「选少」
- `refact-fable.md` §3.12 L1：「只能按冻结标准」——标准空，验收就空
- `refact-fable.md` §3.13.3 内容门：编号集合相等，不检查集合与意图的关系

### C3：S1 / R0 自称 T0，但 T0 新定义的前提正是它们要造出来的东西

**为什么错**：12:00 把 T0 收成「验收条 ⊆ 已签 `policies/tier-defaults.toml`」。
S1 的验收条是「回执仓建成、三次越权被拒、测试 tag schema 合法、凭据脚本零命中、断网 fail-closed」——
这些不在（也不可能在）尚不存在的策略文件里。R1 才产出策略首版并签 `policy/1`。
S1 前置还写「3.13 经 H1 冻结」：按新定义 T0 的 H1 就是策略 tag，循环依赖。

R0 旁注另有一笔「改协议补机器可读块，待所有者定」——本身承认这可能不是 T0，
却仍标在 T0 行。用新 T0 口径跑引导轮，脚本按 §8 第 5 条会拒绝分发。

**应当是什么**：§6 单立「引导轮」一行，明确 **R0 / S1 不适用新 T0 定义**。
它们的验收条就是本表「机械验收判据」列，效力来自本文被所有者冻结，不是来自 `policy/1`。
档位写法用 `bootstrap` 或「所有者手写验收的一次性轮」，不要写 T0。
R0 旁注「待所有者定」移入 §7 未决，冻结 §8 前给裁定。

**证据**：

- `refact-fable.md` §3.6 / §8 第 5 条：T0 验收条 ⊆ 已签策略，否则拒发
- `refact-fable.md` §6 S1 行：档 = T0，前置 = 「3.13 经 H1 冻结」，产物含回执仓与凭据脚本
- `refact-fable.md` §6 R1 行：产物才是 `policies/tier-defaults.toml` 首版与 `policy/1`
- `refact-fable.md` §6 R0 旁注：「待所有者定」

## 设计级

### D1：3.1.1 映射表隐含内核禁止的转换 `WAITING → SUCCEEDED`

**为什么错**：P0 的验收方式是「映射表里没有一个新词」，但合法**转换**也是内核的一部分。
`request-lifecycle.md` 合法转换只有 `WAITING → VALIDATING | QUEUED | FAILED | CANCELLED`，
没有 `WAITING → SUCCEEDED`，也没有「经 Side Effect 直达终态」。
3.1.1 写「⑥ 确认 = `WAITING(APPROVAL)`」「⑦ 清理与发布 = Side Effect → `SUCCEEDED`」，
中间缺了内核规定的恢复路径：执行阶段等待结束后先回 `QUEUED`，Attempt 获租约再进 `RUNNING`。

这不是用词问题。按这张表实现，开发 Profile 会走出内核禁止的边；
§8 第 4 条只 `rg` 状态词集合，抓不住非法边。产品 Profile 若真按同一张图做，审批通过后会跳过 `QUEUED`。

**应当是什么**：映射表改成显式路径，例如：

| 开发 Profile | 唯一状态机 |
| --- | --- |
| ⑥ 确认（人未回执） | Task `WAITING(APPROVAL)` |
| ⑥ 回执成立 | `WAITING → QUEUED`（内核规定的恢复） |
| ⑦ 清理与发布 | 一个 orchestrator Attempt：`CREATED → RUNNING → COMPLETED`；其 Side Effect 过 H5 门后，Task `RUNNING → SUCCEEDED` |

Side Effect 继续当对象，不当转换。§8 第 4 条加一条：映射表的每条边 ⊆ 内核合法转换集合（脚本可判）。

**证据**：

- `working/request-lifecycle.md` 合法转换表：`WAITING → VALIDATING | QUEUED | FAILED | CANCELLED`
- 同节：「执行阶段等待后先回 `QUEUED`，只有 Attempt 获得有效租约才重新进入 `RUNNING`」
- `refact-fable.md` §3.1.1：⑥ / ⑦ 两行；§8 第 4 条只比状态词、不比边

### D2：`RECEIVED` 与 Attempt `BUDGET_EXCEEDED` 未入映射表

**为什么错**：§8 第 4 条要求「脚本与三份新文档中出现的状态词，集合等于内核所列」。
3.1.1 是「P0 的验收方式」，却没有 `RECEIVED`、没有 `BUDGET_EXCEEDED`。
开发 Profile 里这两词要么空转（请求落盘的瞬间、观察窗用尽），要么根本不用。
不写清楚，实现者会补一个「开发专用入口态」，或让 §8 在「少一个词」时无法判定——
正文只写了「多一个词即失败」，与「集合等于」字面冲突。

**应当是什么**：映射表为内核每一个 Task / Attempt 状态各留一行，允许填
「空转：工单文件创建成功即离开 `RECEIVED`」或「观察窗用尽 → 该家 Attempt `BUDGET_EXCEEDED`，Task 不失败（I8）」；
不允许缺行。§8 第 4 条改成「多一个或少一个都失败」。

**证据**：

- `working/request-lifecycle.md` Task 状态含 `RECEIVED`；Attempt 终态含 `BUDGET_EXCEEDED`
- `refact-fable.md` §3.1.1 无这两行
- `refact-fable.md` §8 第 4 条：「集合等于」vs 括号里只禁多不禁少

### D3：Profile C 与 A 的差异只有「固定 T2」，不够单独成 Profile

**为什么错**：§3.1 画了三个 Profile。C（本协议自身的演化）持久层、执行者、通道、必需产物、状态判定
全部「同 A」，唯一差别是 guard = 固定 T2。那是 Profile A 上的档位钉死，不是第三套 Profile。
P0 禁的是按场景另造状态词；按场景另造一个与 A 同构的 Profile 名，是同一类膨胀，只是发生在上一层。

**应当是什么**：正文改成两个 Profile（开发 / 产品）。协议演化 = 开发 Profile + 工单 `tier = T2` 钉死
（命中「不可逆 / 权威层」四条中的两条，本就该 T2）。图里删 C，避免后文「两个 Profile 都过才算合并」
还得解释第三个。

**证据**：

- `refact-fable.md` §3.1 图：C 列五格写「同 A」，guard 写「固定 T2」
- `protocol-v2` `round-protocol.md`「流程档位」：改本协议命中不可逆 + 权威层，即 T2
- `refact-fable.md` §2 P0：场景差异只在 guard / 产物 / interrupt，不另造结构

### D4：P0 的正确强度是词表纪律，不是「git 上已经跑过产品运行时」

**为什么错**：qoder D1 要把「一个内核」降为共享词汇表，12:00 驳回并补了 commit 钉死与 3.11
「git 验不了事务 / 租约 / fencing」。驳回可以，但 §0 第 1 句和 §3.1 标题仍读作
「开发过程就是这套状态机在 git 上的运行」。3.11 已经承认三件内核性质验不了，
U3 的准确表述也改成了「跑通对象形状、状态转换与交互纪律」。
两处力度不一致。实现者若只读摘要，会以为产品侧的租约和 fencing 可以「先在这一层跑通」——
正是 3.11 禁止宣称的那句话。

**应当是什么**：不改 P0，不改映射表。§0 第 1 句加半句限定：
**P0 约束的是状态词与转换边，不宣称 git 载体具备内核的并发语义。**
U3 / 3.11 已有的那句移到摘要里，避免只读一页的人带错预期。

**证据**：

- `refact-fable.md` §0 第 1 句：「开发过程……是它在不同 Profile 下的运行」
- `refact-fable.md` §3.11：「不得宣称『已在开发层验过』」事务性 / 租约 / fencing
- `refact-fable.md` §3.1 末：「U3……要说准跑通的是什么」——与摘要力度不同

### D5：T0 收窄之后，H5 仍在；「零触点」只指开工前，日常并不便宜

**为什么错**：§8 第 5 条「T0 为零次」写的是开工前 `APPROVAL` 触点，字面成立。
但 T0 仍是「做 → 独立验收 → **确认**」，确认即 H5，A 档下每次都是 Windows + pinentry + push。
§7 风险 9 只登记「小题目落到 T1、H2 增多」，没登记「几乎每票仍要付一次 H5 签名」。
再叠加 C2（T0 安全压在 H5 上），触点疲劳的主战场其实是 H5，不是 H2。
3.4 的观察值（耗时、改动项数）能看见敷衍，但看不見「T0 名义上全自动、实际上每票仍要切 Windows」。

**应当是什么**：风险 9 补一行观察值：每票签名次数（H1/H2/H5 分别计）。
T0 的产品承诺改成「开工前零触点；发布仍要 H5」。若所有者不能接受「改一行文档也要签 tag」，
才需要另开「可逆、不写共享最终路径」的出口（例如只落 worktree、不走 ⑦）——那是新的权力表行，
不是把 H5 设默认。

**证据**：

- `refact-fable.md` §3.6：T0 = 「做 → 独立验收 → 确认」
- `refact-fable.md` §8 第 5 条：零次限定在「开工前」
- `refact-fable.md` §7 风险 9：只提 T1 / H2
- `refact-fable.md` §3.13.4：每次签名弹 pinentry

## 文字 / 可执行级

### T1：§0「四个词」与 §3.9 / §8「五个词」不一致

**为什么错**：修订记录与 §0 写 supervisor 解为 orchestrator / arbiter / acceptor / approver（四词）；
§3.9 表与 §8 第 1 条是 router + 上述四词（五词）。router 该留——它是确定性代码，不是第四个 supervisor。
摘要少写它，读一页的人会对不上验收条。

**应当是什么**：§0 与修订记录改成五词；强调 router / orchestrator 都是代码，后三词才是角色。

**证据**：`refact-fable.md` 修订记录第 11:45 条、§0 第 5 段、§3.9 表、§8 第 1 条。

### T2：正文引「七环节 / 流程档位」未钉 `protocol-v2`

**为什么错**：取证范围写了 `protocol-v2` 分支，但 §1.6、§3.1.1、§5.2 直接写
「round-protocol 七环节」「流程档位」。当前 `master` 上的 `round-protocol.md` 仍是
「六个环节」，无档位节，确认是 ⑤、清理是 ⑥。未合 R0 之前，只读 master 的人会对不上号。
这是本文自己立的规矩（「引用按标题，不按章节号」）的配套：标题在哪个 commit 上存在，要写明。

**应当是什么**：凡引用七环节或档位，写成 `round-protocol.md@protocol-v2`「七个环节（T2 专用）」/
「流程档位」；或把七环节清单抄进本文 3.1.1，避免读者去 master 对空。R0 合并后这条自动失效。

**证据**：

- `master` `round-protocol.md` §1 标题「六个环节」；确认 = ⑤，清理 = ⑥
- `protocol-v2` `round-protocol.md` §1「流程档位」、§4「七个环节」；确认 = ⑥，清理 = ⑦
- `refact-fable.md` 取证范围已列 protocol-v2，正文引用未钉

### T3：§8 第 4 条「多一个即失败」写窄了

与 D2 同因。改成「对称差非空即失败」一句即可，随 D2 修。
