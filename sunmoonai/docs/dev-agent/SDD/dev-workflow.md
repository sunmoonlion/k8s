# 开发任务的 workflow

开发这件事交给程序来驱动时，这条 workflow 是什么样。人怎么做见 [人版](../../dev-human/workflow.md)。

**本文是待开发的目标态，不是现行做法。**

人版与本版是**同一份「要什么」的两种实现**：人版用纪律实现，本版用机制实现。所以规矩**是两套**，
不是一套换个执行者——人版靠人当场把关的地方，这边必须落成执行者绕不过去的东西。
两边对同一件事各写一份是正常的；要防的是**一个版本内部**同一事实有两个权威写入面。

人版没有、这边必须有的那一块是**传递**：把用户消息送到执行者那里，并把结果取回来。
人版不需要它——人当面说，附件当面给。

## 一、传递：message 怎么到执行者

**这一整块人版没有**，是本版存在的全部理由。人当面说、当面给、当面批，所以不需要信封、
签名、租约和一次性令牌；一旦话要送出去，这些就全得有。

目标态走产品的那条链（见 [请求生命周期](../PRD/lifecycle.md)）：用户消息变成提交信封 →
后端受理与路由 → 带签名派发 → 本地 runtime 驱动 Codex → 结果本地检查、加密、回传。
开发任务在这条链上不是特例，它就是一类 Task。

**现状要说清楚，不能含糊：**

| 层 | 状态 |
| --- | --- |
| 手工投喂：人把话粘进助手窗口 | **现在唯一跑通的** |
| 脚本投喂：脚本把话投给**交互会话** | 可行且不破坏批准点——消息由脚本发出，审批照样浮到人面前 |
| 非交互一次性（`codex exec` / `agent -p` / `qoder -p`） | **不可用**：权限开关把审批预先答掉 |
| 走产品通道派发 | 待开发 |

**自动化的是传输，不是决定。**这条线把「投喂可以自动」和「批准不能自动」分开——
两者不冲突，见 [人的批准点](../../dev-human/approvals.md)。

## 二、驱动方由谁充当

| | 谁充当 | 批准点怎么落 |
| --- | --- | --- |
| 人版（现在） | **人自己兼**：出题、分发、审核、裁决、清理 | 人当场知道、当场说行 |
| 过渡 | **某个 AI 助手**充当驱动方，人退到批准点 | 必须落成它绕不过去的东西——它自己不能批自己 |
| 目标 | **后端程序** | 状态机上的一条边 + Interaction 原子消费 |

⚠ **别和产品的后端 supervisor 混**：那是程序，而且 v1 明确不调用生成式模型。
本文说的是「驱动开发流程的角色」，词汇表里叫**驱动方**。过渡期由 AI 助手充当时，
[自我批准禁令](../../dev-human/approvals.md) 一条都不放松——它不承担后果，所以不能自己批自己。

## 三、控制面与投影面各由谁写

| 面 | 装什么 | 谁写 | 人版里是什么 |
| --- | --- | --- | --- |
| **控制面** | 状态、批准、验收结论、预算与副作用账 | **后端，单一权威写入面** | 人的判断，记在提交说明与定稿里 |
| **投影面** | 目录、文件名、编号、给人看的进度视图 | **从控制面投影出来** | 目录本身就是真源（见 [turn 的投影](../../dev-human/turn-project.md)） |

这是两版最容易错位的一处：**人版里目录既是真源又是投影，本版里目录只是投影**。

- **不得直接编辑投影**：改目录不改记录，等于同一事实有两个权威写入面（P1）。
- 换成数据库、Issue、PR 或事件流承载都可以，但不能丢失原始请求、边界、验收、基线、证据和改判历史。

## 谁在驱动

驱动方按 workflow 决定下一个 turn 问什么、派给谁、怎么验收，人只在批准点介入。

| 步骤 | 驱动方做什么 | 人做什么 |
| --- | --- | --- |
| 开一个 thread | 按 workflow 选种类与 Profile，生成 `user-message.md` | 需要澄清时回答 |
| 派工 | 把用户消息派给执行者，记录派工与租约 | — |
| 收 response | 自动存 `response.md`、提交、写 `turn.md` | — |
| 验收 | 先做确定性验收（规则、schema、测试）；需要语义判断的另派一个验收 turn | 在批准点批准或打回 |
| 定稿 | 把通过验收的 response 整理进 `PRD/` 或 `SDD/`，提请人批准 | 批准即定稿 |
| 打回 | 生成新 turn 的用户消息，写清理由与改判三要素 | 达到上限时裁决 |

## worktree

- 执行者在 Attempt 的 worktree 里实现；验收在 worktree 的 `test/` 里。
- 驱动方审核以 **diff 为主**，不必为每次审核都另开 worktree；要跑测试或做最小修补时才开，开了就登记。
- 合并到 master 必须经人的批准点（不可逆动作）。
- **驱动方负责清理**：工作完成、合并之后清 worktree；清理前确认分支或标签已保留，并把清理这件事记下来。

## 与人手工做的差别

| 方面 | 人手工 | 交给程序 |
| --- | --- | --- |
| 谁发起 turn | 人 | 驱动方按 workflow |
| 谁写 `turn.md` | 人手写 | 运行时与后端自动写 |
| 审核 | 人读 response | 确定性验收 + 语义验收 turn，人只在批准点 |
| worktree 层数 | 助手、（supervisor）、人，逐层向上 | 助手一层；审核按需开 |
| 清理 | 人 | 驱动方 |
| 打回 | 人写理由 | 驱动方生成用户消息，改判入账 |

## 驱动方必须守的

- **不改已冻结的东西**：已发出的用户消息、已交回的 turn 一律不动，要改就开新 turn。
- **每一步都要留痕**：派工、交回、验收结论、打回理由、改判、清理，都进记录。
- **该停就停**：返工达到循环控制定的上限、遇到不可判、越出已授权的能力，停下来交给人。
- **人的批准点不能自动通过**：见 [人的批准点](../../dev-human/approvals.md)。

## 两条已知风险

**一、人不在场之后，「确认」会退化成盖章。**现在人能确认，是因为全程在旁边、知道每一步发生了什么。
自动化之后，人会在流程末尾看到一份一千多行的稿子和一句「请确认」——这时点通过几乎是必然。

已经挡住一半：不设逾期默认、人不确认就不发布、确认前必须有检视面。**挡不住的是「看了但没真看」**。
补法是让人的注意力有落点——验收结论必须点名最该看的三处，见
[UAT 把关](../../dev-human/uat/finalize.md)。

**二、难度地图和直觉是反的。**

| | 性质 | 状态 |
| --- | --- | --- |
| 怎么组织一群不确定的执行体 | **设计难**——没有现成答案，买不到抄不来，失败模式隐蔽 | 人版已跑通 |
| 怎么判断执行体做得对不对 | **工程难**——方法已知，费钱费时但路清楚 | 未做 |

所以不要按「先建判据与回路，再谈组织多个执行体」排期。**也不要把协作层跑通误读成执行内核已验证**：
那是另一条线，另有它自己的可证伪条件。
