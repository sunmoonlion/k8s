查证结论：**否，而且明令禁止。**`agent-dev-guide.md` §2.2 的 `arbiter` 行写着

## 2. 所有者的第二个判断：检视问题会自行消解

> 「这是我们下一轮就该做的，该轮做完后，比如人，它的检视问题应该迎刃而解：
> 它只是把要检视的 artifact 做一份投影而已」

与既有登记 **F-2**（投影的必要性由受众的展示环境决定）合起来是完整命题：

```
绑定 = 哪些 artifact 由谁产出、处于什么状态
投影 = 把某个集合按受众的展示环境铺开
⇒ 投影是绑定的**导出操作**，不是独立的设计问题
```

⚠ **反证在本轮已经发生**：2026-09-08 起草者在检视面上反复三次——
先开五棵完整 worktree，再加 `--flat` 平面对照面，随后撤掉、改为归档进轮目录。
**每次都在猜「该把什么摆给谁看」，因为没有判据可依。**

## 3. 所有者否掉「主体」这个提法

> 「主体这个词应该斟酌，我觉得不太恰当」

opus 查到这个直觉有出处——`agent-dev-guide.md` §0.0 第 2 条：

> 「supervisor」一个词同时指三套不同的东西……**每加一层就加一个名字，说明抽象层级选错了**。
> 稳定的概念不是「谁监督谁」，是「**这个状态转换由谁执行、需要什么权力、在哪里强制**」

**「主体」正是又一个总称名词，用它就是重犯 #2。**

⚠ 同节第 3 条还有一句，对任何「定义清楚再列表」的方案都是致命的：

> 那样的权力表是**第二份说明书，不是机制**——**它不驱动任何东西，只能靠人记得读**。

## 4. 所有者的第三步：定义应由 artifact 关系构成

> 「该主体的定义应该紧密结合 artifact，其他方artifact 状态，展示投影等等」

即：不是「先命名再绑 artifact」，而是**它与 artifact 的关系就是它的定义**。
这样不需要好名词，因为类别被**外延**定义；而且定义天然可机器判——
某件 artifact 是不是它产出的，从 git 里能查。

⚠ 这一步在讨论中被下一步取代，保留作为推演过程。

## 5. 所有者的最终立场：不要「谁」，要状态机

> 「我现在讨论不针对本轮。只是讨论未来方案。我觉得不定义主体啥的，
> 真正要做的事明确所有声明周期中的状态机和转换，artifact的完整定义
> 及其本身和投影的消费」

**三件事：**

1. 明确**所有生命周期**中的**状态机与转换**；
2. **artifact 的完整定义**；
3. artifact **本身**与**投影**的**消费**。

**「谁」不作为一等概念**——它退化成转换上的一个属性。
这正是 §0.0 #2 那句判语的彻底化：guide 说了「转换是主词」，
但随后仍造了 §2.1/§2.2 两张角色表，**半途而废**；此处走到底。

## 6. opus 就这三件事的取证与难点

### 6.1 「所有生命周期」——本仓现有几套，且性质不同

| 生命周期 | 在哪 | 状态是**存的**还是**推的** |
| --- | --- | --- |
| Task 状态机 | `working/request-lifecycle.md` §4.1 | 存（持久化主档） |
| Attempt / Run 状态机 | 同上 §4.5 | 存 |
| Interaction / `WAITING` | 同上 §4.2 | 存 |
| ingestion job（产品仓） | `knowledge-app`，8 个终态 | 存 |
| **轮次七环节** | `dev-plan/protocol/round-protocol.md` §4 | ⚠ **推**——`round-status.py`「从产物反推，不看声明」 |
| **文档 / artifact 生命周期** | 无 | ⚠ **不存在** |

⚠ **第一个真难点：存储态与导出态不是一回事。**
前四套是存储态，可能出现非法转换（要拦）；轮次那套是**产物的函数**，
不可能非法。把两者塞进同一个「状态机」框架会打架。
**这个区分本身可能就是下一轮该产出的东西之一。**

### 6.2 artifact 的完整定义——产品侧已有，开发侧没有

**产品侧**（`knowledge-app/contracts/artifact/v1/info-knowledge-artifact.schema.json`）
的 `ArtifactRef` 是一个完整定义：

```text
artifact_type · uri · storage_version · sha256 · size_bytes · content_type
```

且**四重机器校验**：下载后比对 `x-amz-version-id`、`Content-Length`、`content-type`，
并对字节重算 `sha256`，任一不符即拒绝。

**开发侧**（`dev-plan/`）：本轮候选也是 artifact，它的 digest 在哪？
`call-①.md` 写的是「把两份的 `sha256sum` **写进提交信息或候选首部**」——
**散文，不是字段**。`round-status.py` 不读它，任何门禁不校验它。
② 冻结表里那十份 sha256 是组织者手敲的。

⇒ **同一个仓：产品 artifact 有完整定义且机器可验；开发 artifact 连稳定的 digest 字段都没有。**

### 6.3 消费与投影——这一维现在完全没有

本仓已有四类消费方，各自要的形态不同：

| 消费方 | 怎么消费 | 要的形态 |
| --- | --- | --- |
| 人 | 通读、比对 | 摆在一起、可 diff |
| agent | `git show <分支>:<路径>` | 原件，不需要投影 |
| 判据脚本 | 只查存在性与 digest | 字段，不读正文 |
| 门禁 | 查链接 / 锚点 / 表格列数 | 全文，但只看结构 |

⚠ **第二个真难点：投影一旦落盘就会腐烂。**本轮实测结论是「**重复必然漂移**」。
候选规则（未定）：

```text
投影可随时重建 · 不得被引用为事实来源 · 不得写回
落盘的投影必须带「由什么重建」的命令
```

### 6.4 最难的一点：artifact 的粒度

一份文档是一件 artifact，还是它的每一节都是？

- **按文档**：`agent-dev-guide.md` 是一件，那「它内部 22.7% 是上一轮的轮次产物」
  （§8+§9+§10 = 698 / 3082 行）这件事就无法表达；
- **按节**：260 件各有状态与归属，表达力够，但状态机要跑在 260 个对象上。

⚠ 产品侧躲开了这个问题——它的 artifact 是**不可变的单个 S3 对象**，粒度天然确定。
开发侧的文档可变、有内部结构，**粒度是个真问题**。

## 9. 所有者的统一方案（2026-09-08 续）

> 「我觉得我们这样来统一：声明周期的每一个节点都有状态机，节点内部有输入和输出，
> 有中间态，可转换。状态都是真源，但必要时可以有投影」

拆成四条：

```text
① 递归    生命周期的每个节点都有状态机（不是只有顶层有）
② 结构    节点内部有输入、输出、中间态，可转换
③ 真源    状态都是真源 —— 不在别处存副本
④ 投影    必要时可以有投影 —— 派生，不是第二真源
```

### 9.1 ⚠ 这不是新造，是本仓已验证模式的推广

`working/request-lifecycle.md` §4 的标题就是**「两层状态机」**，§4.5 写着：

> **Task 层与 Attempt 层是目标实现中必须拆开的两层。**……跨层引用必须使用
> `task.state` 与 `attempt.status`；事件 schema 分字段携带两者，
> **日志和前端投影不得只写一个无层限定的 `status`**。

这句话里同时有 ①（分层各有状态机）、③（两个字段各自是真源）、
④（投影不得把层次压平）。**所有者的统一 = 把这个从两层推广到所有层级。**

### 9.2 它一次性化解了本文 §6 提的两个难点

| 原难点 | 在统一方案下 |
| --- | --- |
| §6.1 **存储态 vs 导出态打架**（Task 是存的、轮次是推的） | 消失。两者都是节点，各有状态机；`round-status.py` 输出的 ✅⬜ 表**是投影**，不是状态本身。真源是各节点（候选、评审……）自己的状态 |
| §6.4 **artifact 粒度**（文档 vs 260 节） | 由递归回答。文档是节点，节是它内部的节点。「`agent-dev-guide.md` 22.7% 是上一轮轮次产物」这件事**因此可表达**——父节点内含归属不同的子节点 |

### 9.3 用本轮四起事故回测

| 事故 | 在统一方案下是什么 |
| --- | --- |
| **F-6** 组织者 8 次重置参与方工作区 | 「重置」是把候选节点从「已提交」拉回「草稿」的**转换**。②要求每个转换写明可由谁执行——**该转换此前无执行者定义**，故谁都能做 |
| **R1** 所有者拍板被降级成待议题 | 拍板没有节点 ⇒ 无状态机 ⇒ 无状态 ⇒ 只能寄生在别人的文档里 |
| **F-14 后记** 登记簿两条编号线 | `findings.md` 是节点但**没有唯一的状态转换权**，两方各自 append，编号 `F-12` 撞车 |
| 检视面反复三次 | ④ 缺失 ⇒ 不知道什么该做投影、投影归谁 |

四条都能解释，且每条都指到一个**可机器判**的点。

## 10. opus 就统一方案提出的四个难点

⚠ 这四条不是反对，是「要做成必须先答」的。

### 10.1 递归的停止规则：节点细到哪一层为止

②的「节点内部有输入输出」允许无限细分：
Task → Attempt → ? ；文档 → 节 → 段 → 句 ？

**产品侧有天然停止规则**：artifact 是**不可变的单个 S3 对象**，不可再分。
**开发侧没有**：本轮 260 节的落点表说明「节」这一层是必要的，
但「节」之下要不要继续，没有判据。

候选停止规则（未定）：**能被独立引用、独立冻结、独立作废的最小单位**。
按此，「节」是节点（有稳定 ID `F-INTAKE-01` 可被引用），「段」不是。

### 10.2 ⚠ 中间态与「判据只认已提交」直接冲突

②说「有中间态」。但本仓的判据纪律是：

> `round-protocol.md` §8：结果**只依赖 git 提交**。
> `GO.md` §四.3：**交卷 = 可达 commit。**未提交的工作区文件**不算交卷**。

⇒ **「参赛方正在写候选但还没提交」这个中间态，在 git 里没有任何产物，不可观测。**

两条路，必须选一条：

| 选项 | 代价 |
| --- | --- |
| 承认部分中间态**不可观测**，判据不得依赖它 | 状态机不完整，某些转换的发生时刻无法确定 |
| 要求中间态也落产物（如 checkpoint） | 成本高；且「落了产物」本身又是一次提交，中间态会退化成一串终态 |

⚠ **这是四条里最硬的一条。**「状态都是真源」若成立，那不可观测的状态是不是状态？

### 10.3 「必要时可以有投影」——「必要」的判据

F-2 说「投影的必要性由受众的展示环境决定」，但那还不可操作。

候选判据（未定）：**当受众的展示环境无法直接消费真源时，才需要投影。**

| 受众 | 能否直接消费真源 | 结论 |
| --- | --- | --- |
| agent | 能（`git show <分支>:<路径>`） | **不需要**投影 |
| 人 | 不能（一个 checkout 一次只能在一个分支上） | **需要**投影 |
| 判据脚本 | 能（读 git 对象） | 不需要 |
| 门禁 | 能 | 不需要 |

⚠ 按此判据，本轮的**检视面是必要的**（人读不到别家分支），
而 `--flat` 平面对照面**不必要**（轮目录已是真源侧的组织，不是投影）——
这与实际处置一致，说明判据可用。

⚠ 但还缺一条：**投影的失效规则**。本轮实测「重复必然漂移」，
所以投影至少要带「由什么重建」，且**不得被引用为事实来源**。

### 10.4 节点之间的接缝 = 契约，而开发侧的接缝现在是散文

②说「节点内部有输入和输出」⇒ **节点之间的接缝就是契约**。

产品侧已经这么做了：`knowledge-app/contracts/` 有 schema、manifest、digest，
且**双端机器校验**。

开发侧的接缝现在是散文：
- ① 的输出 = ② 的输入 —— 靠 `call-②.md` 里手敲的一张冻结表；
- 候选的 digest —— 「写进提交信息或候选首部」，判据读不到。

⇒ **同一个仓，产品侧接缝有契约，开发侧接缝没有。**统一方案若成立，
这个差别应当消失——开发侧的每条接缝也要有可被机器校验的契约。

## 12. 所有者对 §10.2 的回答：本体与认识分开

> 「状客观存在但不一定可观察」

这一句把 §10.2 解开了，**而 opus 原来给的两条路前提就是错的**：

```
错的前提：不可观察 ⇒ 状态机不完整
正确的：  状态机描述**客观存在的状态**，不因不可观察而残缺；
          判据只能建在**可观察的状态**上。两者是两件事。
```

### 12.1 由此得到四条推论

| # | 推论 |
| --- | --- |
| 1 | **状态机可以是完整的。**「参赛方正在写候选」这个状态客观存在，写进状态机是对的 |
| 2 | **判据只能引用可观察的状态。**协议 §8「只依赖 git 提交」不是在说「只有可观察的才是状态」，是在说「判据只能用可观察的那部分」 |
| 3 | **差集必须被显式承认。**存在但不可观察的状态：判据不得引用、**任何人不得声称**。这给了 P2「状态从产物反推，不从声明读取」一个更硬的理由——声称之所以不可信，不是因为人会撒谎，而是**那个状态本来就不可观察，声称是唯一信息源，而唯一来源无法交叉验证** |
| 4 | **投影只能投影可观察的部分。**投影是真源的函数；不可观察的状态没有可读的真源。**任何显示了不可观察状态的投影，一定掺了声称** |

### 12.2 ⚠ 这不是新机制，本仓已经在这么做了——只是没这么表述过

`round-protocol.md` §14.1「参与方不可用：逾期、弃权与换人」：

| 判定 | 协议原文的判据 |
| --- | --- |
| **停滞** | 该家的产物连续一个观察窗内**字节数无变化且分支无新提交** → 视为停止 |
| **未启动** | 一个观察窗 `W`（不是随手挑的秒数）内，**CPU 时间无增长**（`ps -o etime,time` 采两次取差）**且**输出无增长 → 它挂着，不是在跑 |

**「正在写候选」看不见，所以协议不去看它**——它转而观察**别的可观察量**
（字节数、分支 HEAD、CPU 时间、输出增长），再用**观察窗**兜底。

⇒ 这正是「状客观存在但不一定可观察」的既有实现。
§2.4 还写着「宣布逾期一类的裁定，**依据必须是观测值**（字节数、时间戳、分支 HEAD），
不是『等太久了』」——**观测值 vs 感觉**，同一条区分。

### 12.3 由此可导出的设计规则（候选，未定）

```text
R-1  每个状态标注「可观察 / 不可观察」，判据只准引用前者
R-2  不可观察的状态不得被任何人声称 —— 声称即无效（P2 的加强版）
R-3  若某个不可观察状态对流程重要，二选一：
       a) 设法让它产生产物，把它变成可观察（代价：中间态退化成一串终态）
       b) 承认流程在那一段是盲的，并给出**替代观察量 + 观察窗**（协议 §14.1 的做法）
R-4  投影只投影可观察部分；投影里出现不可观察状态 = 掺了声称，视为缺陷
```

### 12.4 用这条重判 F-6

F-6 原记：「组织者在 ① 期间 8 次重置参与方工作区」，当时的归因是**纪律问题**
（§8c.1 说了不许，还是做了）。

**在本框架下归因不同**：

> 组织者需要知道「luna 是否正在工作」——**那是一个不可观察的状态**。
> 它没有按 R-3(b) 去找替代观察量（分支 HEAD、字节数），
> 而是**默认了一个假设**（「我没发通知，所以没人在干活」）。
>
> ⇒ 失败不在于疏忽，在于**用假设填补了不可观察的状态**，而假设不是观测值。

⚠ 这比「他忘了纪律」有用得多：纪律靠记，而 R-1/R-3 可以做成判据。

## 14. 所有者：状态与 pipeline 紧密相连

> 「刚才已经说过，状态与 pipeline 紧密相连」

⚠ **记录者此前把它们当成两个话题在谈**（§5 说「状态机」、本轮 ①a 说「阶段与门」），
所有者指出那是同一件事。回看 §5、§9 的原话，确实已经说过——
「**生命周期的每一个节点**都有状态机」，生命周期就是 pipeline。

### 14.1 一张对照表：两套词说的是同一个东西

| pipeline 的说法（本轮 ①a 的六项必答） | 状态机的说法 |
| --- | --- |
| **阶段** | **节点** |
| **门** | **转换 + 转换条件** |
| 产出什么 | 该节点的**输出 artifact** |
| 存在哪 | 该 artifact 的**真源位置** |
| 凭什么算过关 | **转换条件** |
| **判据归属**（机器 / 纪律） | 该转换**是否可观察**（机器可判＝可观察；靠纪律＝不可观察，须走 §12.3 的 R-3） |
| 生命周期规则 | 该 artifact 自己那层的状态机 |
| —— **本轮六项必答里没有的** —— | **返回边**（失败、回退、返工） |

⇒ **本轮任务书的六项必答，其实是状态机定义的一个子集，而且缺了返回边这一项。**
那是起草者（opus）的漏项，与 F-14 记的「主体」漏项是同一处失误的两面。

### 14.2 可验的推论：没有返回边的流水线不是状态机，是清单

对五份 ①a 实测（`grep -cE '回到|退回|往哪回|回 S[0-9]|返工|失败.*回|不通过.*回'`）：

| 家 | 返回边 | 判据归属（机器/纪律 提及） |
| --- | --- | --- |
| **luna** | **12 处** | 10 |
| kimi | 1 处 | 19 |
| **opus** | **0 处** | 20 |
| **cursor** | **0 处** | 28 |
| **qwen** | **0 处** | 33 |

```bash
cd ~/master/k8s
P=sunmoonai/docs/dev-plan/rounds/dev-plan-refact/candidates
for w in opus luna kimi cursor qwen; do
  printf '%-8s %s\n' "$w" "$(grep -cE '回到|退回|往哪回|回 S[0-9]|返工|失败.*回|不通过.*回' $P/${w}/pipeline.md)"
done
```

**五家里只有一家把流程写成了状态机；其余四家（含记录者自己）写的是清单**——
每个阶段都有产出、有判据、有归属，**但一旦不通过，没有边可走**。

⚠ 判据归属那一列反而五家都写得满（10–33 处）。
**说明大家都想清楚了「谁来判」，没想清楚「判不过怎么办」。**

### 14.3 这解释了 opus 在 ② 评审里给自己扣的那一分

`reviews/review-opus.md` §C.2 把「无失败回路」列为自己的四条缺口之一，
当时的理由是「luna 有、我没有」。

**在本框架下理由更硬**：不是「少了一个好特性」，是**它根本没构成状态机**——
一个只有前进箭头的东西，无法回答「现在处于哪个状态」，因为失败之后它不在任何状态里。

### 14.4 由此更新对下一轮题面的判断

§5 的三件事应当合成一句：

```text
不是「先定 pipeline，再补状态机」，
而是「pipeline 的每个节点就是一台状态机」——
  节点 = 阶段
  边   = 转换（含返回边）
  边的条件 = 门
  边的可观察性 = 判据归属（机器 / 纪律 / 替代观察量 + 观察窗）
  节点的输出 = artifact，其状态是真源
  展示 = 投影，只投可观察部分
```

⚠ 若这条成立，**本轮五份 ①a 都可以按状态机的完整性重判一次**：
节点齐不齐、边齐不齐（尤其返回边）、每条边的条件与可观察性写没写。
这是一把比 J1–J7 更统一的尺子——**但它是本轮结束后才出现的，不能用来追评本轮**。

### 16.3 这条规则直接解释了本轮 Q9 的病灶

Q9 的症状（任务书 §5）：**26 条裁定散在 3 个 `rulings.md`，`R1` 在三轮里指三件不同的事。**

## 18. 所有者：人的 review 也是投影，而它是「各分支的分支」

> 「而人的 review 也是投影，该投影其实是各个分支的分支」

检视面 `~/review/<轮次>-<家>/` 的实现就是 **`git worktree add --detach <该家分支>`**——
字面意义上的「分支的分支」。它是投影，真源是各家分支上的 commit。

### 18.1 由此看出：投影有**实现强度**之分

同一个真源，可以有不同强度的投影实现：

| 强度 | 实现 | 一致性由谁保证 | 会漂移吗 | 本轮实例 |
| --- | --- | --- | --- | --- |
| **强** | git 层（`worktree --detach` 到某 commit） | **git** | **不会**——它就是那个 commit | 检视面 `~/review/<轮次>-<家>/` |
| **中** | 字节复制进另一个 commit | 人 / 脚本 | **会**，须核 digest | `rounds/<轮次>/candidates/<家>/` |
| **弱** | 由源重新生成 | 重跑生成器 | **会过期** | `inventory.md`、`README.md` |

⇒ **操作规则（候选）：能用强的就不用弱的；用弱的必须带「由什么重建」。**

⚠ 本轮实测印证：检视面刷新时 git 直接 `checkout --detach --force` 到分支头，
不可能不一致；而 `candidates/` 的十份副本，opus 是**逐份 sha256 对拍**才敢说一致。

### 18.2 那么两份投影是否重复？——不是，因为分支会被回收

`candidates/` 与检视面投影同一批真源。按「重复必然漂移」，本该只留一份。
**但它们的存活期不同**，而这一点被协议假设错了。

`round-protocol.md` §16「⑦ 清理与发布」写：

> | 各提案方 worktree 的候选 | **删除。内容在各自分支的提交里，git 历史可取** |

**实测：这个假设不成立——分支被回收了。**

```bash
cd ~/master/k8s
for r in runtime runtime-refact refact; do
  printf '%-16s 分支 %s 条\n' "$r" "$(git branch --list "${r}/*" | wc -l)"
done
# runtime          分支 0 条
# runtime-refact   分支 5 条
# refact           分支 0 条
```

⚠ **同一条规则，两轮结局相反：**

| 轮次 | 分支 | 归档 | 候选今天取得到吗 |
| --- | --- | --- | --- |
| `runtime` | **已回收** | `rounds/runtime/reviews/candidate-<家>.md` **五份在** | ✅ 取得到 |
| `refact` | **已回收** | **无**（`rounds/refact/` 只剩一个 `round.md`） | ❌ **取不到了** |

⇒ **`refact` 轮的候选已经永久丢失。**协议说「git 历史可取」，
而 ⑦ 的实际做法回收了分支——**两条纪律互相拆台，谁也没发现，因为没有判据检查它。**

### 18.3 结论：两份投影都要，但职责必须写明

| 投影 | 存活期 | 职责 |
| --- | --- | --- |
| 检视面（强，git 层） | **临时**，`--close` 即消失 | 给人**现在**读；不可能漂移 |
| `candidates/`（中，字节复制） | **永久**，进 git | 分支回收后**唯一**的取件面 |

⚠ 这不是「留两份重复」，是**两个不同存活期的需求**。
但现状是：**这个区别从没被写下来**，所以 `refact` 轮才会丢。

由此得到一条候选规则：

```text
R-5  凡真源位于**会被回收的载体**上（分支、worktree、临时目录），
     必须在回收前建立一份**永久投影**，且回收动作与建立投影是同一次操作的两半。
```

⚠ 若 R-5 早已存在，`refact` 轮不会丢候选；而本轮 opus 提前归档 `candidates/`
（在 ⑦ 之前就做），恰好满足了它——**但那是运气，不是纪律**：
当时的理由是所有者说「artifact 应该放在该轮下面」，不是因为知道分支会被回收。

# 第二部分 · 综合

> 以下是记录者按所有者要求做的**全盘综合**。前面各节是讨论过程，本部分是把它收成一句话
> 再展开验。⚠ 仍不承担规范效力。

## 20. 所有者的最终抽象

> 「pipeline 里的各个节点的状态机是真源，状态有投影，
> 但**某一个投影可称为另一个状态**。这是高度抽象的表述，但我觉得它能指导全盘开发」

三小句，第三句是关键：

```text
① pipeline 的每个节点，其**状态机**（不只是当前值）是真源
② 状态有投影
③ ⚠ 某一个投影可称为另一个状态
```

**③ 说的是：状态与投影不是两个互斥的类，是相对于层级的关系。**

> 同一个东西，在**产生它的节点**是状态（真源）；
> 在**消费它的节点**是投影；
> 而那个投影，在消费层**就是该层的状态**。

### 20.1 一条贯穿本仓的实例链

```text
候选文件的状态（草稿 / 已提交冻结）
    真源：proposer 节点，载体是该家分支上的 commit
        ↓ 投影
「① 提案 opus✅ luna⬜ …」
    在轮次节点，这个投影**就是**轮次的状态
        ↓ 投影
「当前环节：② 互评　缺：luna」
    在人那里，这个投影**就是**「我现在该投喂谁」的状态
```

⇒ 三层，每层都有自己的状态；**上一层的状态就是下一层状态的投影**。

## 21. 它统摄了前面的哪些问题

| 前面的困惑 | 在 §20 下的解 |
| --- | --- |
| §16.4 **`round.md` 既不是真源也不是投影** | 困惑消失。它是轮次节点的**配置**真源；轮次的**状态**是下层产物的投影，而该投影在轮次层**就是**轮次的状态。`round-status.py` 输出的不是「投影而非状态」——它**是**轮次的状态 |
| §10.1 **递归的停止规则** | 有了判据：一个投影**升格为状态**的条件是——**该层有定义在它之上的转换**。`round-status` 的输出是状态，因为环节转换定义在它上面；一次随手 `grep` 的输出不是状态，因为没有任何转换以它为条件 |
| §18.2 **两份投影是否重复** | 重复的危险不在「有投影」，在于**把投影当成同层的第二个真源**。`candidates/` 与检视面之所以要靠「存活期不同」辩护，正因为它们**同层**、没有各自的层归属 |
| §6.1 **存储态 vs 导出态** | 不是两类。导出态就是上层的存储态，只不过它的真源在下层 |
| §6.4 · §10.1 **artifact 粒度** | 由「哪一层有转换定义在它上面」决定，不由主观分寸决定 |
| F-14 **「主体」该怎么定义** | **不需要定义**。「谁」＝「哪一层」；层由节点定，节点由 pipeline 定 |
| §18.1 **投影的实现强度** | 归位为：**层间映射由谁保证**。强＝机器（git）；中＝人核 digest；弱＝重跑生成器 |
| §16.3 **Q9 编号撞车** | 裁定是决定层的状态，被存进了轮次层的容器；**层错放** ⇒ 编号空间被上层切碎 |
| §18.2 **`refact` 轮候选丢失** | 丢的不是文件，是**上层的状态**：proposer 层被回收后，轮次层没有为它保留投影 |

**九处困惑，同一把钥匙。**

## 22. ⚠ 它预测出了本仓已知的一个洞——而且预测出了已有的解法

框架的一条推论：

> **上层状态必须是下层状态的确定性函数。**
> 若某个上层状态**不是**任何下层状态的函数（需要人当场判断），
> 那它就不是投影——它必须是**自己那一层的真源**，且必须落成产物。

拿这条去查本仓，命中 `agent-dev-guide.md` §0.0 第 4 条：

> | 4 | 有**一个环节命令判不了**（人的确认），只能靠人声明 |
> 与「状态从产物反推、不从声明读取」直接冲突，而**全自动化正好卡在这个洞上** |

而该文给出的解法（§0.0 末段）：

> **人的确认也落成可判的产物**（对 4）

⇒ **框架独立推出了这个洞的存在，也推出了本仓已经采用的解法。**
这是它值得当通则用的一个证据——它不是事后描述，它有预测力。

### 22.1 同一条推论还解释了「为什么声称不可信」

`round-protocol.md` §0 与 P2 都写「从产物反推，**不看任何人的声明**」。
在框架下这不是对人的不信任，是**类型错误**：

> 声称是一个**没有下层真源的上层状态**。它不是投影（无源可投），
> 也没有落成产物（无自己那层的真源）。**它什么都不是。**

## 23. 由 §20 导出的规则（候选，合并前面 R-1…R-5）

```text
L-1  每个节点声明：它的状态机（状态集 + 转换 + 每条转换的条件与执行者）
L-2  每个状态声明：它是**本层真源**，还是**下层某状态的投影**
       · 是投影 ⇒ 必须给出映射（谁 → 谁、由谁保证一致）
       · 是本层真源 ⇒ 必须落成产物，否则它不可观察（见 L-4）
L-3  投影升格为状态的唯一条件：**该层有定义在它之上的转换**
       ⇒ 没有转换以它为条件的派生物，只是显示，不是状态
L-4  状态客观存在，但不一定可观察。判据只准引用**可观察**的状态；
     不可观察的状态：任何人不得声称（声称即无效），
     要么让它产生产物，要么给替代观察量 + 观察窗
L-5  层间映射有强度：机器保证（如 git）＞ 人核 digest ＞ 重跑生成器。
     能用强的不用弱的；用弱的必须带「由什么重建」
L-6  凡真源位于**会被回收的载体**上，回收动作与建立永久投影必须是同一次操作的两半
```

⚠ L-1…L-6 **都能被机器检查**——这是它区别于「权力表是第二份说明书」（§0.0 第 3 条判语）
的地方：它们不是要人记得读的清单，是可以写成门禁的条件。

## 24. 记录者认为**尚不成立**的部分

⚠ 综合不等于背书。三处我认为还没被证明：

1. **L-3 的「转换」本身谁来定？**
   若某人给任意派生物补一条转换，它就升格成状态——**判据可被构造绕过**。
   缺一条「转换的合法性」判据，而那可能又要回到人的判断。

2. **「状态机是真源」与「状态机会变」的张力。**
   状态机本身也会演进（本仓的 Task 状态机改过、协议七环节加过异议轮）。
   那么**状态机自己的状态机**是什么？递归到哪一层为止？§20 没有说。

3. **本框架未在任何一次真实开发上跑过。**
   它解释了九处历史困惑（§21）、预测中一个已知洞（§22），
   但**全部是回溯性的**。回溯解释力强不等于前瞻可用——
   这正是本仓 F-12 记过的形状：**判据本身必须先被验证**。

⇒ 建议：下一轮**先拿一件小而可逆的真实工作**跑一遍 L-1…L-6，
再决定要不要写进 `constraints.md`。
