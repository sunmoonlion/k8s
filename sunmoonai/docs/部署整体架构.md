# 部署整体架构

## 一、核心思想

**镜像构建与 K8s 部署解耦。**

每个应用组件分为两个独立关注点：

1. **镜像从哪来** — 源码构建或从 Harbor 拉取
2. **镜像怎么跑** — K8s 资源生成与部署

两者通过镜像名称 + tag 衔接，互不干扰。

## 二、目录结构

```
k8s/sunmoonai/
├── app-platform/               # 各业务应用平台
│   ├── auth-app/
│   │   ├── auth-app-backend/   # 单个应用组件
│   │   └── auth-app-front/
│   ├── llmops-app/
│   │   └── celeryworker-llmops/
│   └── ...
└── docs/                       # 架构与规范文档
```

每个应用组件内部结构：

```
{app-component}/
├── resources/
│   ├── source/          # 可选：源码构建模式
│   └── k8s-resource/    # 必须：K8s 部署资源
└── deploy-{app}/        # 部署脚本（apply 到集群）
```

## 三、镜像来源：两种模式

### 模式 A：源码内置（小型组件）

源码体量小，直接放在 `resources/source/mybuild/` 中，在 k8s repo 内完成构建和推送。

```
resources/source/mybuild/
├── Dockerfile
├── build.conf          # 镜像名、tag 等配置
├── build-image.sh      # 构建镜像
├── push-image.sh       # 推送到 Harbor
└── <少量源文件>         # 启动脚本、预处理脚本等
```

**适用场景**：Celery Worker、轻量工具服务、启动脚本封装等。

**示例**：`app-platform/llmops-app/celeryworker-llmops/resources/source/`

---

### 模式 B：独立仓库（大型应用）

源码体量大（完整后端服务、前端应用），放在独立 git 仓库中单独维护和构建，推送镜像到 Harbor 后，k8s repo 直接引用镜像名部署。

```
Desktop/
├── auth-app-backend/    # 独立 git 仓库（NestJS 后端）
├── auth-app-frontend/   # 独立 git 仓库（Nuxt 前端）
├── toutiao-app-backend/ # 独立 git 仓库（Flask 后端）
└── toutiao-app-front/   # 独立 git 仓库（Nuxt 前端）
```

**适用场景**：完整后端服务、SSR 前端、有独立 CI/CD 需求的应用。

**示例**：`app-platform/auth-app/auth-app-backend/`（源码在 Gitee 独立仓库）

## 四、K8s 部署资源：统一结构

不管镜像从哪来，`resources/k8s-resource/` 的结构完全一致。

```
resources/k8s-resource/
├── generate.conf                    # 编排：声明要生成哪些资源
├── generate.sh                      # 编排脚本：按顺序调用各组件脚本
├── templates/                       # K8s YAML 模板（含占位符变量）
│   ├── app/{app}.yaml               # Deployment + Service
│   ├── configmap/{app}-config.yaml
│   ├── secret/{app}-secret.yaml
│   ├── secret/harbor-registry-secret.yaml
│   ├── ingress/ingress.yaml
│   ├── namespace/{app}-namespace.yaml
│   └── pvc/{app}-pvc.yaml
└── custom-values/                   # 每个组件的生成脚本和配置
    ├── app/generate-app/
    │   ├── generate-app.conf        # 镜像名、tag、PVC 挂载路径等
    │   └── generate-app.sh
    ├── configMap/{app}-config/generate-{app}-config/
    │   ├── generate-{app}-config.conf   # ConfigMap 各字段值
    │   └── generate-{app}-config.sh
    ├── secret/{app}-secret/generate-{app}-secret/
    │   ├── generate-{app}-secret.conf   # Secret 各字段值（⚠️ 敏感）
    │   └── generate-{app}-secret.sh
    ├── secret/harbor-registry-secret/generate-harbor-registry-secret/
    ├── ingress/{app}-ingress/generate-ingress/
    ├── namespace/{app}-namespace/generate-{app}-namespace/
    └── pvc/{app}-pvc/generate-{app}-pvc/
```

### 生成流程

```
generate-{component}.conf   →  提供变量值（默认值 + 覆盖机制）
        ↓
generate-{component}.sh     →  读取 conf，export 变量，envsubst 替换模板
        ↓
templates/{type}/{app}.yaml →  YAML 模板（${VAR} 占位符）
        ↓
*-generated.yaml            →  最终可 apply 的 YAML 文件
```

### 配置优先级（从高到低）

1. 环境变量（运行时注入）
2. `deploy-{app}/app/deploy-app/deploy-{app}.conf`（主部署配置）
3. `generate-{component}.conf` 中的默认值

### ConfigMap vs Secret 职责分离

| 类型 | 存储内容 | 示例 |
|------|----------|------|
| ConfigMap | 非敏感配置 | 服务地址、端口、功能开关、环境标识 |
| Secret | 敏感信息 | 密码、密钥、完整连接字符串（含密码）、Token |

Secret 生成脚本会从 ConfigMap conf 中读取非敏感部分（如 DB_HOST、DB_PORT），自动拼装完整连接字符串，避免重复维护。

## 五、部署脚本结构

```
deploy-{app}/
├── app/deploy-app/
│   ├── deploy-{app}.conf    # 主配置：NAMESPACE、镜像 tag、集群参数等
│   └── deploy-{app}.sh      # 主入口：分阶段 apply 各组件
├── configMap/{app}-config/deploy-{app}-config/
├── secret/{app}-secret/deploy-{app}-secret/
├── secret/harbor-registry-secret/deploy-harbor-registry-secret/
├── ingress/.../
├── namespace/.../
└── pvc/.../（按需）
```

**部署顺序**（固定）：

```
Namespace → Secret → ConfigMap → Middleware → Ingress → App(Deployment+Service)
```

卸载顺序反之。

## 六、新组件接入流程

1. **确定镜像来源**：源码小 → 创建 `resources/source/mybuild/`；源码大 → 建独立仓库
2. **构建并推送镜像**到 Harbor
3. **创建 `resources/k8s-resource/`** 按标准结构补齐所有组件
4. **填写各 `.conf` 文件**中的实际值（地址、端口、密钥等）
5. **创建 `deploy-{app}/`** 部署脚本
6. **运行生成脚本**产出 `*-generated.yaml`
7. **执行部署脚本** apply 到集群
8. **填写 `utils/app-config-checklist-template.md`**，归档配置完整性记录
