# 轮次协议（新版草案）

> **草案，未生效。**现行规范仍是同目录的 `round-protocol.md`。
> 本稿由所有者 2026-09-10 提出、与 opus 讨论形成。标「待定」的地方尚未拍板；其余条目已经所有者同意，但整份草案须所有者批准后才替换现行规范。

## 一、目的

多家 AI 助手就同一件事各自提案，经评优、建言、综合，形成一份定稿。
人始终是最后一道：每个角色的产物都要人审核同意才算数，人对一切决定有否决权，并可要求修改。

## 二、角色

| 角色 | 由谁担任 | 做什么 |
| --- | --- | --- |
| 人 | 所有者 | 指定 supervisor；批准判据、角色分派和每个角色的产物；否决、要求修改 |
| supervisor | 人指定，写在本轮 `task.md` 里 | 起草判据交人审批；分派其余角色交人审批；定时查进度并通知；人批准定稿后发布 |
| 竞选者 | supervisor 分派 | 独立提出方案 |
| 评优者 | supervisor 分派 | 从各家提案中确定基座 |
| 建言者 | supervisor 分派 | 提出基座该怎样吸收各家的长处 |
| 综合者 | supervisor 分派 | 评判各条建言，综合权衡后把采纳的建言正式吸纳进基座 |

一家 AI 助手可以担任一个或多个角色，具体担任哪些由 supervisor 分派。

## 三、分派角色的规矩

1. 同一家不得同时担任评优者和综合者。
2. supervisor 不得把自己分派为评优者。
3. 综合者是否可以同时是基座作者，由人处置。
4. 其余角色可以兼任。评优者可以选自己的提案作基座，综合者可以处置自己提的建言。

角色分派是 supervisor 的产物，同样须人审批。`round-status.py` 按以上规矩做机器检查，不合规矩即拒绝判定。

## 四、判据

- 判据由 supervisor 起草，写进本轮 `task.md`，交人审批。
- 产出开始前，人可以修改判据。
- **竞选开始即冻结**：之后评优者按它选基座，综合者按它权衡建言，不得再改。

## 五、四个环节

| 环节 | 角色 | 交什么 | 过关条件 |
| --- | --- | --- | --- |
| 竞选 | 竞选者 | 各自的方案 | 人审核同意 |
| 评优 | 评优者 | 选定的基座，以及对每份提案的比较理由；选自己的提案时标「（自选）」 | 人审核同意 |
| 建言 | 建言者 | 对基座的吸收建议，逐条写明出自哪份提案、吸收什么、为什么 | 人审核同意 |
| 综合 | 综合者 | 在基座上完成的综合稿，及处置记录 | 人审核同意 |

综合者的处置记录是纪律：对每条建言**原文引用**，写明采纳、部分采纳或驳回，并给出理由；处置自己提的建言时标「（自处置）」。综合之后不再由 agent 复查，人是最后一道。

综合稿经人同意后，由 supervisor 发布到 `master`。

## 六、先送人审核，同意后才正式提交

**各角色提交自己的产物之前，必须先交人审核；人审核同意后，才能正式提交。**supervisor 的产物（判据、角色分派、通知）同样如此。

⚠ **待定——审批要绑定确切的对象**（opus 的建议）：

- 送审：角色把产物提交到自己的分支，标明「送审」；
- 人同意：在人的分支上记下这一版产物的内容摘要（sha256）；
- 正式提交：机器看到人的同意，且摘要与送审那一版一致，才算正式提交；同意之后内容再变，须重新送审。

## 七、分支、工作区与目录

- **每个角色都有自己的分支和工作区，产物只写自己的分支。**人和 supervisor 也各有自己的分支和工作区，放各自的产物。
- **人的分支只收人本人署名的提交**（git 作者为所有者身份）。人的裁决、审批都是人的产物，记在人的分支上。
- **`master` 只放两样**：协议本身，以及人批准后发布的定稿。过程产物留在各自的分支上，不进 `master`。
- **`protocol/`**：规范、各环节的通知（一条通知对应一个环节，不再是某一轮的文件）、判定脚本。
- **`rounds/<轮次>/`**：主要是 `task.md`——目标、判据、supervisor 由谁担任，以及机器要读的配置（角色分派、最终路径、基线）。
  `task.md` **与人的审批同时生效**：人没有同意，其中的判据与配置都不算数。
- **人直接在各角色的工作区里读它们的产物**，不另做投影。两点须知：别人工作区里只有该角色自己的产物是新的，其中的协议等文件可能是旧的，协议一律读 `master`；工作区里可能有尚未提交的改动，看到的不一定是提交了的。

## 八、判定

结论只看 git 提交，不看工作区，不看任何人的说法。

- 一个环节完成 = 该环节各角色的产物已正式提交（见第六节），且人已同意；
- 人的同意只从人的分支读取，并核对提交作者是所有者身份；
- 分派角色的规矩（第三节）由机器检查。

## 九、通知

- 每个环节交什么、交到哪、按什么判，只在协议里写一处，不再每轮手写。
- supervisor 定时跑 `round-status.py`，查出谁还没交，按协议通知。
- **各家的交互会话跑在同一个 tmux 会话里**（每家一个窗口）。supervisor 用 `tmux send-keys` 把那一句敲进目标窗口，效果与人手动粘贴相同：会话仍是交互的，审批照样弹在该窗口里由人处理。
- **送之前必须先截屏确认该窗口空闲、停在输入框**；窗口停在菜单、审批或确认提示上时**一律不送**——敲进去的文字与回车会被当成对提示的回答。
- 送出后隔几秒再截屏，核对消息确已提交；截早了会误以为没送到。
- 不在 tmux 里的执行者，由 supervisor 告诉人「该给谁投喂」，由人去贴那一句。

## 十、三条底线

1. **判据先于产出冻结**（第四节）；
2. **产出方不等于批准方**：每个角色的产物都由人批准；
3. **不可逆动作由人确认**：发布到 `master` 须人同意。
