> 最后更新：2026-09-02
>

> 全部内核。**本文自足：不依赖任何其他开发生命周期文档才能执行。
>
> [`development-lifecycle-agent.md`](development-lifecycle-agent.md) 是同一件事的另一种

> 因此本文只可以**指出差异**，不得把共同内核留在那一份里——§1.1 说明为什么。
>
> **本文不是 [`request-lifecycle.md`](request-lifecycle.md) 的投影，也不复制产品状态机。**
> 那份是产品契约；实现它的是代码，不是本文。看到 Task、Attempt、Interaction、Delivery
> 这些词一律以那份为准，本文不重新定义，也不在正文使用产品状态名。
>
> 人可以向多名助手派活，此时人扮演**协调者（supervisor）**；隔离、评审与选优规则不因
> “人当协调者”而豁免，见 §11。
>
> 本文是目标流程与纪律，不是当前实现清单。能力现状只由代码、迁移、测试和运行证据证明。

## 1. 为什么要单独一份

人和 agent 做的是同一类事——领受、实施、验收、交付。**但有四处是真实差异**，
不是同一条规则的两种说法：

| | 人 | agent |
| --- | --- | --- |
| 批准权 | **有**——放行门禁、取消、预算追加、验收终审 | 无，且不得自我批准 |
| 跨会话续接 | 可依赖记忆、经验与组织背景 | 每次冷启动，只能靠落盘 |
| 裁量权 | 可判断“这件事不值得走全流程” | 不得自行降级流程 |
| 责任归属 | 人承担后果 | agent 不承担，因此不能是最终判定方 |

这四处决定了：**把人的规则写进 agent 那份，会给 agent 松绑；
把 agent 的规则写进人这份，会给人加不必要的枷锁。**

### 1.1 为什么本文必须自足

两份文档的存续期不同：Agent 那份描述的是产品运行时的开发路径（前端请求 → FastAPI
受理 → sandbox 物化 → Agent 执行），属于开发期产物，**开发结束后会删除**；本文描述
的是人怎样做开发，长期有效。

由此有两条硬要求：

1. **共同内核必须完整写在本文里**，不能用“其余见 agent 那份”省略。那一份消失时，
   被省略的部分会随之消失，而它们对人同样成立。
2. **凡能落实为代码、测试或门禁的纪律，必须落实为代码、测试或门禁。**只以文字存在于
   文档或提示词里的规则，会随文档一起消失。§10.1 的写入前门禁、§10.2 的范围门禁和
   §15 的完成判据都属于此类：文档描述意图，门禁产生效力。

本文引用 agent 那份的地方一律是**指出差异**，不是取用内容；那一份删除后本文仍然完整。

### 1.2 两条路径的差异总表

| 生命周期位置 | 人（本文） | Agent（另一份） | 共同不变量 |
| --- | --- | --- | --- |
| 请求入口 | 人直接提出或接收 | 前端用户提交 | 原始请求不覆写 |
| 受理整理 | 人写持久任务包（§8） | FastAPI 建立 Task | 边界、验收、权限、成本明确 |
| 根 Git 仓库 | **人初始化或检出** | 后端在 sandbox 物化 | 来源和 initial commit 可追溯 |
| 初始 worktree | **人建立** | sandbox 根工作区提供 | 目录、分支、HEAD 明确 |
| 后续 worktree | 协调者按工作单元建立 | supervisor 按 Work Unit 建立 | 一单元一可写面、同基线 |
| 协调者 | 人担任 | Agent 担任 | **地位与协调职责等同** |
| 批准权 | 人自己持有 | 前端用户或授权角色，经产品链路行使 | 执行者不得自我批准 |
| 候选产出 | owner 分支/worktree | owner 分支/worktree | 私有地产生，不写共享发布面 |
| 发布最终路径 | 唯一整合方 | 唯一整合方 | 单写者发布，最终 commit 验收 |
| 交付 | 人按协作/发布流程 | 后端持久化并返回前端 | 最终 commit、证据、风险固定 |

**地位等同是协调职责等同，不表示系统授权相同。**Agent 协调者不因角色升级获得人的
批准权；人当协调者也不因是人就能省略边界、证据或验收。

## 2. 人的三个角色

1. **请求提出者**：提出有边界的开发工作，提供原始意图、范围和验收期望；
2. **执行者**：亲自实施部分工作，与助手交替推进；
3. **有权主体**：批准、取消、追加成本和终审验收的最终权力。第三种助手不能替代。

助手不得自我批准；人也不得把终审责任外包给助手后不再复核。

## 3. 人独有的权力，及其义务

权力越大，留痕义务越重。下表左边是只有人能做的动作，右边是做了必须留下什么。

| 动作 | 必须留下 |
| --- | --- |
| **批准**一个需要放行的门禁 | 批准了什么、依据什么、承担什么风险 |
| **取消**一个进行中的工作 | 取消原因；已产生的副作用是否需要补偿 |
| **追加预算 / 提高资源上限** | 为什么值得、上限是多少、什么条件下停 |
| **验收终审** | 逐条对着验收标准的结论；未通过项是缺陷还是标准过期 |
| **降级流程**（判定不必走完整选优） | 判定依据：为什么这件事的风险不足以支付那个成本 |
| **推翻 agent 的判定** | 推翻的是哪一条、原判断错在哪、新判断的依据 |
| **推送、合并、发布、删除远端资产、执行不可逆迁移** | 批准范围、目标、版本、有效期 |

**“我看着行”不是依据。**依据要能被半年后的自己复核。

**授权不跨场景延续。**在 A 分支批准过推送，不等于 B 分支也可以；一次批准的破坏性动作
不构成下次的默许。批准绑定具体工作、动作、目标、版本和有效期。

派活给多名助手时：人冻结任务包、指定角色、收回最终选择；不在候选互投上“凑独立”。
无法保留候选人与裁判分离时，决策留在人，不交回候选方。

## 4. 跨会话续接：靠文档，不靠记忆

人可以隔一周回来接着做——但**别人接不上**，包括未来的自己。

判据就一句话：**把今天的记忆抹掉，另一个人只读持久载体能否接着做？**不能，就是没落盘。

- 当前推进哪件事、卡在哪、下一动作，落在
  [`handoff.md`](../handoff.md)，不落在脑子里；
- **“不能倒退的输入”必须写下来。**已经定过的事，下次不重新讨论——
  这是 `handoff.md` 最有价值的一节；
- 覆盖与缺口 → 实现矩阵；产品目标 → [`request-lifecycle.md`](request-lifecycle.md)；
  Git、远端、子模块与跨机操作 → 现行专门规范（若尚未建立，以本文 §12 为准）；
- 停下来之前，先让 `handoff.md` 能回答：“接手的人一分钟内要知道什么？”

交接投影不是第二真源，不得在 handoff 里复制整张覆盖矩阵。checkpoint 是恢复输入，
不是第二份代码真源，也不保存凭据。

**`handoff.md` 是单写者面。**多名执行者并行时，只有协调者 / 主驾驶写它；各执行者的进度
写在**自己的 worktree** 里，由协调者投影上去。判据不是“内容重不重要”，而是“同一事实只能
有一个权威写入者”（§12.1）——多人各自往同一份 handoff 追加，就是在共享路径上并发写。

同一判据对 agent 同样成立，只是理由不同：**agent 是记不住，人是记得但传不出去。**

## 5. 小请求的裁量权

人可以判断“这件事不值得走全流程”，agent 不可以。但裁量有底线——
下面五条不因规模而豁免：

1. **不篡改原始意图**；
2. **不越过权限与范围**；
3. **结论有与风险相称的证据**；
4. **“完成”可判定**；
5. **发生改判时，交代触发与变化**。

省略任何一步都必须**显式写出“不适用”及理由**。空着与“忘了”无法区分。

**什么时候不能简化**：涉及安全边界、数据迁移、跨 App 契约、不可逆外部动作、
生产发布——这几类无论多小都走完整流程（判据见 §11.1）。

## 6. 改判三要素

人比 agent 更容易改判——信息多、判断在变。改判本身不是问题，**装作没改过才是**。

每次改判必须写清三件事：

| | |
| --- | --- |
| **触发** | 什么新证据或什么情况变化 |
| **原判断错处** | 当初哪一句不再成立——不是“当时信息不全”，是具体哪一步推错了 |
| **新判断** | 现在以什么为准；能独立成立，不写“理由见上文” |

不得装作从未判过，也不得为了让检查变绿而静默删除旧标准。修改验收标准时保留原标准、
原始失败输出和改判理由。

把结论写进 project-guide 前回读代码或实物重新取证，不把目标态文字直接写成现状。
文字改对了、代码里还是旧的，比不改更糟。

## 7. 人与 agent 协作时，人的义务

不只是 agent 有纪律。人这边同样有，且被违反时后果更大——因为 agent 会照做。

| 人的义务 | 违反会怎样 |
| --- | --- |
| 请求写清**边界**：含什么、不含什么、不含的归谁 | agent 会自行扩大范围，或漏掉本该做的 |
| 给**可判定的验收标准**，不给倾向性结论 | agent 向你的结论收敛，等于白问 |
| 并行提案时**不泄露其他方案** | 独立信号退化成改写（§11.4） |
| 派活前先建好各自的 worktree 和命名分支 | 多个执行者写同一工作区，后写覆盖先写（§12） |
| 收到“我不确定”时**不追问到它给出确定答案** | 逼出的确定性是编的 |
| agent 说“没查过某处”时**当作真话对待** | 声明盲区的动力被消灭，下次它不说了 |

最后一条最容易被忽略：**盲区声明是自愿的，只要说了就受罚，很快就没人说了。**

## 8. 提出与委派一项开发工作

提出时至少给出：原始意图、边界（含什么 / 不含什么）、可判定验收、已知约束，以及需要
人工批准的动作。只有歧义会实质改变结果、权限、成本或不可逆风险时才必须先澄清；局部、
可撤销且惯例明确的细节可以作合理假设，但交付时必须说明影响结果的假设。

### 8.1 冻结工作单元

动手前把本单元写成不可覆写的任务包（PR、Issue、仓内持久记录或等价载体），至少包含：

```text
原始意图，一字不改
涉及的仓、子模块和基线 commit
包含什么、不包含什么、不包含部分归谁
硬门禁与质量偏好（两者分开）
时间、成本、工具与最大轮次
需要人工批准的动作
owner / 可写根 / 输出命名空间
最终发布目标 / 唯一整合方
```

硬门禁、质量偏好和待定项必须分开。原始意图只追加、不覆写。需求发生实质变化则结束本
单元，以新任务包重开，不在旧包上静默改口径。

### 8.2 工作区从哪来

人路径没有 FastAPI 代劳：**Git 仓库由人建立或选择，初始 worktree 也由人建立。**
进入并行执行后，后续 worktree 由当前协调者按工作单元建立。

| 对象 | 谁建立 |
| --- | --- |
| 仓库、initial commit | 人 |
| 初始 worktree | 人 |
| 后续 worktree、命名分支 | 协调者（人或其指定者）按工作单元建立 |

**建仓 ≠ 已派活、已验收、已交付。**建仓只是工作开始的前提。

### 8.3 委派

**委派转移的是执行，不是最终责任。**人向 agent 或其他人派活时必须给出范围、权限、预算、
停止条件和可验收输出；对超范围、追加成本、不可逆动作和规范修改及时批准或拒绝；亲自验收，
或指定未参与实施的验收方。

执行内核见 §10；需要并行候选时见 §11；产出物落点见 §12。

## 9. 终审与责任归属

终审针对最终固定版本，不针对计划、候选、作者总结或“所有 Agent 都返回”。人至少确认：
原始请求逐条满足；最终版本通过有效门禁；未验证项、副作用和残余风险已说明；多仓 commit
与 gitlink 可取得；必要的交接足以恢复。

| | 谁负责 |
| --- | --- |
| 决定做什么、不做什么 | **人** |
| 决定怎么做（在约束内） | 执行者 |
| 产出是否符合验收标准 | 未参与实施的一方判定；无人时由**人** |
| 上线后出问题 | **人**——agent 不承担后果，因此也不能是最终判定方 |

这张表解释了为什么 agent 不得自我批准：**不是不信任它的判断，是它不承担后果。**

# 共同内核

以下各节对人和 agent 同样成立。**写在本文，不是引自别处**——另一份会删除。

## 10. 执行内核

单路实施、亲自动手、当协调者，都必须先满足本节。§11 只增加并行候选时的额外步骤，
**不减免本节**。

### 10.1 动手前的核对与写入前门禁

每次开工先核对：

1. 当前目录、仓库根、分支、HEAD、子模块和工作树状态；
2. 原始意图、范围、验收、批准点和预期产物；
3. 基线 commit 与输入材料是否仍可取得；
4. 生效的 `AGENTS.md` 和目标代码附近的测试；
5. 依赖、权限和外部系统是否仍有效；
6. 哪些判断是事实、推断、假设、缺失或尚未验证。

**写入前门禁（一票否决）。**动手写任何文件之前逐条核对，任一不成立则**停，不写任何
文件**：

1. 当前目录就是派给自己的工作区；
2. 当前分支就是自己的命名分支；
3. 目标路径不在禁写清单内（他人 worktree、共享发布面、他人的单写者文件），且解析
   软链、`..` 和挂载别名后的规范路径仍在获准范围内；
4. 目标路径上没有他人产物；若有，**不覆盖**——先让对方的内容形成可达 commit 或备份；
5. 本次不是宽泛写入（批量生成、`>` 重定向、脚本 sweep、先 `rm -rf` 后重建）；确需
   宽泛写入时收窄到明确路径逐个执行。

这五条不是建议。**宽泛写入和“路径归属不明仍继续写”是覆盖事故的两个主因**，两者都
发生在写入前，事后恢复（§12.6）代价远高于停一次。

### 10.2 上下文路由与范围门禁

先读同一组入口，再按改动范围深入。上下文越多不等于信号越好，过量材料会把判断锚定在
既有结论上。

| 改动面 | 必须追加核对 |
| --- | --- |
| 项目总体边界 | 总览架构、[`../constraints.md`](../constraints.md) |
| 产品 Task/Attempt/Interaction/Delivery 语义 | [`request-lifecycle.md`](request-lifecycle.md)、生产代码与对应测试 |
| Agent 运行时、恢复、预算、事件、副作用 | 当前事实文档、生产链代码和测试 |
| 跨 App 契约 | provider schema、consumer lock 和双端契约测试 |
| Admin/Web/API | 目标目录 `AGENTS.md`、认证边界和端到端测试 |
| 数据模型或迁移 | 迁移链、数据库约束、前滚/回滚和数据不变量 |
| K8s 或发布 | bundle、release、部署引用与运行门禁 |
| Git、远端或子模块 | 现行专门规范、各仓 HEAD 和 gitlink |

历史 baseline、候选稿和聊天记录只作线索；**当前实现断言必须回到代码、测试或运行结果
取证。**

**本项目（Investment App）的范围门禁。**上表是通用路由。本文不复制项目实现，也不铺
项目清单——易变的当前事实只放
[`project-guide/repos/investment-app.md`](../../project-guide/repos/investment-app.md)。
只固定三条不随实现变动的路由：

1. **改动涉及 Investment App 时**，除上表外追加读取该仓的项目指南、生产链代码和相关
   测试；不得由历史设计稿或旧快照推断现状。
2. **陈述任何能力状态时只用四级词典**——`defined / wired / deployable / runtime-verified`
   （见 [`project-guide/overall-architecture.md`](../../project-guide/overall-architecture.md)
   §8.2）。类、DTO、迁移或测试夹具存在，都不等于生产链已经接线。
3. **涉及已知休眠能力时回跑 dormant 测试**——
   [`project-guide/repos/investment-app.md`](../../project-guide/repos/investment-app.md) §7
   指向的 `tests/test_dormant_capabilities.py`，同时确认锚点仍在且能力仍未接线。

### 10.3 共同纪律

无论单路还是协调者，每次都必须：

1. 不用自己的计划覆盖原始意图；
2. 只在范围、工具、数据、成本和副作用边界内行动；
3. 区分事实、推断、假设、缺失和未经运行验证的结论；
4. 对可中断工作持久化 checkpoint（§4）；
5. 无法满足完成契约时请求输入或明确失败，不伪造完整结果；
6. 在最终固定版本上运行与风险相称的验证，并报告原始输出位置；
7. 报告盲区、副作用和残余风险；
8. 未经授权不推送、合并、发布、删除远端资产或扩大外部影响。

### 10.4 单路实施与定向审核

解法明确、改动局部、可由测试充分判定时走单路：

```text
固定基线 commit → 实施 → 作者自检 → 固定候选 commit → 独立验收 → 处置 → 最终 commit 回归
```

**作者自检不能代替独立验收。**验收方不得是实施作者；没有第二名可运行验证的助手时，
由人验收，并保留门禁原始输出。**自我批准在任何轮次都不成立**——人当协调者时同样成立，
不得因为“人可以拍板”就给自己的实施做终审。

已有唯一产物、只需判断是否成立时走定向审核：冻结版本 → 两阶段审核 → 处置 → 在最终
commit 回归。

不要让所有工作都支付完整竞选成本。是否简化的裁量权在人（§5），但简化不降低硬门禁。

### 10.5 冻结、迟到与取消

候选、评审、改进、最终结果和验收绑定**不可变 commit**。冻结后替换必须产生新 commit
并登记，不得原地改写同一哈希。

主线采纳后的在途结果标为 stale：不得覆盖主线、执行副作用或推翻已交付结果。确需采用时
建立新的改进单元或新请求。

**迟到判定的对象是 commit 与候选状态，不是分支。**分支是可移动的运输通道（§12.3），
“commit 还在某分支上”既不必要（可达即可核对）也不充分（分支可被重置或强推）。整合前
必须显式核对四项：候选状态仍有效、commit 仍可达、提出方未撤回、基线未失效。

开发侧**没有租约或 fencing 这类运行时机制**——产品侧的对应机制见
[`request-lifecycle.md`](request-lifecycle.md)，那是目标合同，是否已接线由代码证明。
因此开发侧的取消必须**显式停止执行者**，不能只靠标状态。

## 11. 人作为协调者：fan-out

人向多名执行者派活、收集候选、选定主线时，就是协调者。这与 agent 当 supervisor
**是同一个角色**，规则不减。派活、隔离、评审、选优、整合是完成同一件工作的内部展开，
不是另一份生命周期。

### 11.1 展开条件

| 形态 | 适用条件 | 最少经过 |
| --- | --- | --- |
| 单路实施 | 解法明确、改动局部、可由测试充分判定 | §10 |
| 定向审核 | 已有唯一产物，只需判断是否成立 | §10.4 |
| 最小选优 | 需要独立候选，但风险不足以支付完整评审团成本 | 冻结任务包 → 隔离候选 → 一名未参赛决策方 → 处置 → 回归 |
| 完整选优 | 解法不明确、影响跨层或跨仓、错误代价较高 | §11 全流程 |
| 胜者改进 | 主线已选定，只吸收局部优点 | §11.7 |

最小选优只降低评审数量和留证规模，**不降低硬门禁或角色分离**。协调者可选执行形态，
不能降低硬门禁、扩大权限或增加总成本。

### 11.2 派工契约

每个工作单元至少固定：

```text
单元 ID、父请求、owner
目标、包含范围、排除范围
输入引用、基线 commit、允许的上下文
预期产出、验收、证据
权限、成本上限、期限、停止条件
依赖
工作区路径、独占分支、禁写路径
checkpoint 位置
输出命名空间、发布目标、整合方
结果状态
```

**工作区路径和独占分支必须在派工时写死，且对每个执行者唯一。**禁写路径至少包括：人的
主 checkout、其他执行者的 worktree、共享发布面、`handoff.md`。这三个字段是 §10.1 写入前
门禁的判定输入——派工时缺任一字段，执行者不得开始写。

派工只能**收窄**顶层请求的权限和成本。多个单元不得同时成为同一可变事实的权威写入者；
确需共同修改时，先划分所有权或改为串行。

**“已派工”“全部返回”“多数一致”都不等于顶层完成。**顶层验收满足后，其余在途执行必须
停止、取消，或明确降为不影响主线的只读参考。

### 11.3 建立 worktree

- 每个并行单元独立分支、独立可写 worktree；
- 候选从同一冻结 commit 开始；
- 同一分支不能被两个 worktree 同时检出（Git 会拒绝，这是保护，不要绕过）；
- worktree 只隔离**文件写入**，不阻止读取共享 Git 对象——因此“不读其他候选”是行为
  约束，不是机制保证，必须如实标注；
- 多仓单元固定每仓 commit 和父仓 gitlink；
- 建立、归属、基线和清理状态进入记录；
- 删除 worktree 不等于删除证据，commit 必须可达。

**一仓一个默认工作区不够多执行者用。**同一件工作出现第二名可写执行者时，协调者必须
先建好各自的 worktree 和命名分支再派活，不往默认工作区加写者。

### 11.4 候选隔离

候选冻结前只读同一任务包、基线和各自获准的上下文，**不得读其他候选、发起方倾向或预设
解法**。看到已有答案后产生的内容是改写，不再是独立候选。

候选提交时绑定不可变 commit，并声明：覆盖与未覆盖范围、各仓 commit/gitlink、执行过的
验证和原始输出位置、已知缺陷与假设、盲区、副作用，以及每项关键主张的证据。

需要脚本化产生候选时使用
[`../parallel-proposals.py`](../parallel-proposals.py)。**它的验证边界要如实标注**：已验证
的是独立进程、独立 `CODEX_HOME`、失败隔离与 manifest 写入；真实模型调用尚未在本项目
端到端验证。脚本存在不等于流程已经可用。

### 11.5 角色分离

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 协调者 | 冻结任务包、分配工作区、匿名随机排序、收集记录、停止其他执行 | 泄露候选、临时改规则 |
| 候选方 | 独立调查、实施、自检、固定 commit | 偷看候选、参与最终计票、决定自己胜出 |
| 验收方 | 在同一基线和环境上运行硬门禁 | 因身份或文案放宽标准 |
| 评审方 | 审查主张、证据、风险和偏好 | 交卷前读取其他评审 |
| 决策方 | 在合格候选中选定主线 | 参加本轮候选 |
| 整合方 | 从选定 commit 处置改进并形成最终版 | 默认接受优胜作者自评 |

同一执行者可在不同轮次换角色，但同一轮不得兼任有冲突的职责。**候选方不得兼任本轮
决策方，也不得作为自己基线的最终整合方。**无法保留这两项分离时，决策由人承担；
不得为了凑齐角色把裁判权交回候选方。

作者身份无法隐藏时必须声明。匿名化用于降低偏差，不得写成绝对保证——代码风格、目录
选择和提交习惯仍可能泄露身份。

### 11.6 评审、裁决和选优

评审分两阶段：**独立审**只读原始请求、匿名候选 commit 和统一验收标准；**对照审**在独立
审冻结后再读候选自评、盲区和验证记录。每份评审必须写明所审 commit、覆盖与未覆盖范围、
阻断与非阻断问题、证据，以及**哪些结论实际运行过、哪些只是静态判断**。

先裁决事实，再比较偏好：

| 主张 ID | 候选 commit | 证据/命令 | 结论 | 理由 |
| --- | --- | --- | --- | --- |
| `<ID>` | `<commit>` | `<位置/输出>` | 证实 / 证伪 / 未决 | `<可复核说明>` |

下列任一情况发生，候选**不进入偏好比较**：必须测试失败；违反
[`../constraints.md`](../constraints.md) 或明确范围边界；存在未解决的阻断级正确性、安全、
数据或迁移风险；commit、子模块对象或验证证据无法取得；提案隔离已被破坏且无法恢复公平
比较。

**能由证据裁决的主张不交给多数票。**投票只处理证据无法区分的偏好。**全体一致不是免检
理由**——多个相似模型可能共享盲区，对影响结论的全体一致主张至少额外抽查一次其共同证据
来源。

维度和权重在候选产生前冻结。有效票只来自未参赛评审方。结果称**“本轮选定”**，不称
“已证明正确”。

### 11.7 改进、整合和回归

选定 commit 冻结为只读基线。改进从它新建 worktree 和改进分支，**一条主张一个提交**，
提交说明写明依据、改动边界、验证结果和基线 commit。需要整体重写或依赖其他改进才能
成立的内容属于新候选，应开启下一轮。

整合方在独立的整合分支上逐项处置：

| 处置 | 必须记录 |
| --- | --- |
| 接受 | 合入的 commit、理由、验证结果 |
| 部分接受 | 接受到哪、停在哪里、最终 commit 与边界依据 |
| 拒绝 | 可独立复核的理由；能证伪时附命令或位置 |

选定候选的作者可以解释设计，**但不审批自己的基线**。冲突按原始请求、约束和证据解决，
不按票数、作者或提交时间覆盖。

**所有有效门禁必须在最终 commit 上重跑**，候选的绿色结果不能证明整合结果正确。验收标准
失败时区分实现错误与标准腐坏；修改标准必须保留原标准、原始失败输出和改判理由。

### 11.8 停止规则

- 默认 2—4 个候选；超过五个前先说明新增独立信号为何值得评审成本；
- 改进默认一轮，最多三轮；达到上限仍有结构性分歧时由人裁决或重开任务，不无限润色；
- 连续一轮没有关闭阻断问题或新增可验证价值时停止；
- 单元耗尽成本上限不得静默借用；
- 协调者退出前留下可恢复的 checkpoint。

## 12. 产出物与 commit 的落地纪律

### 12.1 根本原则：私有地产生，单写者发布

会话隔离、模型隔离和任务名称不同，都不等于文件系统隔离。**任何可能并行的执行者都不得
把共享路径当作自己的草稿纸。**所有产出先在执行者独占的分支/worktree 或 owner 命名空间
内产生；只有预先指定的整合方才能把选定结果写入共享发布面。

```text
private draft → owner candidate → frozen commit → 选定 → 整合工作区 → 最终 commit → 共享分支/发布
```

共享发布面包括 `master/main`、公共工作树、约定的最终文件路径、共享对象存储键、正式 PR、
release、部署环境和用户可见结果。**约定的最终文件名是发布目标，不是所有候选都可同时写的
路径。**

判定安全的精确条件：**多个候选各自在独立 worktree 中修改同一个相对路径，这是安全的；
若共用一个物理工作树，就必须使用 owner 命名空间**（如 `.work/<单元>/<owner>/...`），
共享最终路径保持只读，**不能靠“最后再改名”避免覆盖**。共享工作树只是降级方案，不能声称
具备 worktree 级隔离；连 owner 命名空间都无法保证时，任务必须串行。

**任何可写动作开始前先确定身份**：owner（谁可以写候选空间）与整合方（谁可以写发布目标）
必须显式指定，**不能因为某人先打开文件就获得所有权**。一个发布目标在同一轮只能有一个
写者。

### 12.2 本仓的具体落点

| | 路径 | 权限 |
| --- | --- | --- |
| 人的主 checkout | `~/master/<仓>` | **只读**。可以读、可以对照，**不是投稿箱**，也不因为“文档原件在这里”就该写这里 |
| 执行者工作区 | `~/worktrees/<助手>/<仓>` | 该执行者唯一的可写面；提交到自己的命名分支 |
| 整合面 | 整合方自己 worktree 上的整合分支 | 只有整合方写；源是**选定 commit**，不是任何人的工作区文件 |

- 每个执行者一条命名分支、一棵 worktree；长期约定是“一执行者一命名分支”；
- **未提交草稿不拿给别人比、不拷进主仓、不当作“已经交卷”。交卷 = 自己分支上的可达
  commit**；
- 未经授权不推送、不开 PR、不合并、不删远端分支；获准也只推自己的分支；
- 临时分支可在证据已落账且 commit 可达后清理；决策记录和 commit 哈希不得删除。

### 12.3 未提交文件、commit、分支与 worktree 的不同语义

隔离靠 **worktree + 命名分支，不靠文件名**。`-new`、时间戳、助手名写进文件名，都不能
阻止“同一工作区、同一相对路径”被后写覆盖。

| 对象 | 覆盖会怎样 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| **未提交工作区文件** | **后写直接覆盖先写：无冲突、无历史、无警告、无作者归属** | 磁盘此刻的内容 | 谁写的、谁先写完、被覆盖前是什么 |
| commit | 新 commit 不摧毁旧对象；旧对象需有 ref 才找得到 | 一组文件内容及父历史不可变 | 谁批准、测试是否通过、外部副作用状态 |
| branch | 指针可被快进、重置、强推 | 当前指向哪个 commit，便于运输和续接 | 稳定评审对象；分支头会移动 |
| worktree | 一分支只能被一棵 worktree 检出 | 某执行者当前可写目录和所检出分支 | 长期证据；目录可以删除 |
| tag/ref | 可被移动或删除，但所指对象仍在对象库 | 使对象可达并表达冻结点 | 自动构成验收或发布 |
| 共享发布面 | 未授权写入等于闯入他人工作区或发布面 | 只有整合后的最终 commit 算交付 | 任何未经整合的内容 |

候选和评审一律引用**完整 commit ID 与基线**，不能只给分支名。冻结候选后禁止 force-push
改写其可追溯历史；需要 rebase 时形成新的候选 commit 并保留旧→新映射。删除 branch、
worktree 前必须确认所需 commit 已由持久 ref 或 bundle 保持可达——**“对象暂时还在 reflog”
不是保留策略。**

### 12.4 产出物分类

| 类型 | 权威载体 | 处置 |
| --- | --- | --- |
| 源码和受控文档 | owner 分支的 Git commit | 候选冻结后由整合方选择性整合 |
| 未跟踪草稿 | owner 命名空间，尽快形成 commit | 不得放共享最终路径；未冻结不参与选优 |
| 可再生生成物（build、cache、coverage） | 构建系统，不作为真源 | 独占输出目录；通常不 commit |
| 需交付生成物（bundle、报告、安装包） | 内容寻址存储 + 摘要 + 来源 | Git 只记 manifest/摘要，不塞大文件 |
| 验证证据（日志、测试报告） | 不可变归档或 CI 记录 | 关联环境、命令、commit 和摘要 |
| 敏感临时物（token、私钥、隐私数据） | 受控 secret/data store | **禁止 commit**；最小暴露；到期销毁 |
| 外部副作用（数据库写入、发布、消息） | 副作用账和外部回执 | 幂等、可审计、必要时补偿；**Git 不是账本** |

### 12.5 各种场景的处置

每行四件事：场景、正确落点、禁止做法、**已发生时怎么收**。恢复列给的是入口动作，统一
规程见 §12.6。

| 场景 | 必须怎样做 | 禁止做法 | 已发生时 |
| --- | --- | --- | --- |
| 多执行者生成同名文档 | 各自在自己的分支/worktree 修改相同相对路径，分别 commit | 一起写共享目录的同一个文件 | 以 commit 认主，不以磁盘最后一版为准；共享路径上的未提交文件视为污染，移到各自命名空间后比对摘要，声明哪些候选已不独立 |
| 只能共享物理目录 | 用 owner 命名空间，最终路径只读，由整合方发布 | 用时间先后或“谁最后保存”决定结果 | 停写；把可识别的各版本分流进各自命名空间；由整合方裁决 |
| 单人单路任务 | 仍固定 owner、基线和候选 commit | 在脏的共享主仓上直接写未跟踪结果 | 把属于本任务的内容迁到自己的分支并 commit；共享工作区恢复为只读 |
| 人与助手混合 | 人和助手各有独占 worktree | 默认人的目录可被助手写 | 助手改动撤出人的工作区；**人的未提交改动优先保留** |
| 两个单元改同一文件 | 目标不同则各分支独立改、由整合方解冲突；共同写同一事实则先划所有权或串行 | 同时共享写，事后凭 mtime 猜作者 | 停写，重划所有权或改串行；已产生的双写内容各自成 commit，交整合方判定重复/互补/无关 |
| 多仓 / 子模块 | 每仓独立 owner 分支/commit；子仓对象先可达，父仓再更新 gitlink | 只交父仓 gitlink，不保证子仓 commit 可取得 | 补齐每仓 commit 映射；不可达的 gitlink 不进入整合 |
| 已交卷 commit 需要修改 | 新 commit；旧哈希仍报给评审并记 supersedes | `commit --amend` 改写已被他人读过的提交 | 原 commit 仍可达则继续作为评审对象；新哈希标为冻结后修订 |
| 两执行者提交到同一分支 | 不应发生——派工时分支互斥 | 共用 `tmp`/`new` 这类分支名却不拆所有者 | 停写；按作者和时间拆成两条分支，原分支冻结 |
| 从共享目录拷走他人未提交稿 | 不拷。交卷只经协调者收集的 commit | 把别人的草稿当自己的起点 | 该路不再计作独立候选；记录污染来源与时间窗口 |
| 整合时误拷工作区文件进主仓 | 整合方从**选定 commit** 取内容，写进自己的整合 worktree | 把任何人的未提交文件复制进共享主仓 | 从主仓撤出该文件，改从 commit cherry-pick / merge；撤出前先确认没有覆盖他人内容 |
| 用户工作树已有脏改动 | 视为其所有；另建 worktree/分支或避开，先记录基线 | stash、reset、checkout 或覆盖他人文件来“清理” | 不 stash、不 reset；先记录基线，另建工作区绕开 |
| 执行中发现共享路径又被改 | 立即停写并进入 §12.6 | 继续保存，期待自己的内容最后覆盖回去 | 从最新可确认版本建立新的整合轮次 |
| formatter/codegen 同时运行 | 只在 owner worktree 执行，固定工具版本 | 对共享目录启用后台自动写入 | 关掉共享目录上的自动写入；受影响文件从 owner commit 重新生成 |
| CI / 并行测试 | 每个 job 独立输出目录和产物名；聚合器只读 | 并行 job 写同一 coverage、报告或缓存真源 | 单槽文件作废，重跑到绑 commit 的位置 |
| 大文件 / 二进制 | 内容寻址存储，Git 记摘要、来源和位置 | 多人向同一路径覆盖上传 | 以摘要认主；无来源的降级为未验证参考 |
| 敏感产出 | 加密/受控存储，最短保留期，日志脱敏 | commit、PR 或聊天中保存凭据 | 按泄露处理：轮换凭据、清理副本与日志、记录暴露窗口。**不能靠删文件了事** |
| symlink / 路径别名 | 写前解析规范路径并确认仍在获准范围内 | 利用软链、`..` 或挂载别名写出自己的空间 | 核对实际写出的规范路径；越界写入按覆盖事故处理 |
| 外部发布 / 数据库写入 | 唯一副作用 owner + 幂等键 + 回执 | 因代码分支隔离就允许多候选同时写生产系统 | 查副作用账，按幂等键判定是否重复执行；需要时补偿 |
| 多执行者推远端 | 每人推自己的远端 ref；整合方独占发布 ref | 共推同名远端分支，遇 non-fast-forward 后强推 | **不要强推回滚**；报告有权主体，由其决定 revert 或冻结该 ref |
| PR 在评审后新增 commit | 原评审绑定旧 commit；新 HEAD 重新触发受影响门禁 | 沿用旧批准声明新 commit 已通过 | 原批准作废，重新触发门禁与评审 |
| 只读探索 | 不写；或只写一次性抛弃分支且不推送 | 探索性改动混进实施分支或共享主仓 | 探索提交不进选优，除非任务包事先允许 |
| 跨机 / 新会话接手 | 只凭分支 + commit 恢复；cwd 必须是自己的 worktree | 凭“上次写在共享目录里”接着写 | 先看 `worktree list` 和 `status`；共享工作区里的未跟踪文件先按覆盖事故处理 |
| 候选迟到 | 标 stale，只读保留 | 写入最终路径、覆盖已选 commit 或再次执行副作用 | 标 stale；需要采用则新开改进单元，源仍是 commit |
| 失败 / 取消 | 冻结失败现场和已产出对象，盘点副作用，再回收 | 先删 worktree 导致无法复盘 | 先冻结现场再回收；已删除的按证据缺口登记，不补造 |
| `master/main` 发布 | 仅整合方在最终验收后、获授权时更新 | 每个候选直接向 `master/main` 写文件或 commit | 未经整合的写入撤出发布面，从选定 commit 重走整合与最终门禁 |

### 12.6 覆盖或来源不明时的事故处理

**后到者赢在任何场景都不成立。**磁盘上的最后一版、时间戳最新的一份、最后推上去的那个
ref，都不因为“在后面”而获得正确性或所有权。覆盖发生后唯一有效的认主依据是 commit、
摘要和来源记录。

本节是唯一一套事故规程，分两档入口。

**四步前门（轻量场景）。**单个文件被覆盖、来源基本可判、无外部副作用、无发布竞争时：

1. **保全现场**：停止对该路径的一切写入，先记录，不删除、不 reset、不 checkout；
2. **恢复归属**：从 Git 对象、reflog、归档或备份取回可识别的各版本，各自恢复为归属者的
   独立分支或命名空间，交还归属者；
3. **判定关系**：由非当事方判定两份是重复、互补还是无关，据此决定取一、合并或都保留；
4. **留痕**：把覆盖窗口、受影响对象和恢复依据记入证据账。

任一条不成立——来源不明、涉及发布面或远端、已产生外部副作用、或同一路径反复被改——
立即升级为八步，不要在四步里硬撑。

**八步完整规程。**发现文件内容、大小、hash、mtime、branch/HEAD 或作者特征与预期不符时：

1. **停写**：暂停所有可能触及该路径的执行者和自动格式化/生成任务；
2. **保全**：不删除、不 reset、不 checkout；记录路径、stat、hash、`git status`、HEAD；
3. **分流**：把仍能识别的不同版本保存到各自命名空间或不可变归档；
4. **溯源**：依据 commit、checkpoint、记录和内容特征判断来源；**mtime 只作线索**；
5. **恢复**：优先从 owner commit、Git 对象、归档、备份或工具补丁记录恢复；
6. **裁决**：由整合方比较并决定选用、合并或全部拒绝，**不由最后写入者自动获胜**；
7. **回归**：在新的最终 commit 上重跑门禁；
8. **记录**：写清覆盖窗口、受影响对象、恢复依据和防复发控制。

来源无法确认时，文件不得进入最终版本；能恢复内容但不能恢复来源时，只能作为未验证参考。
**事故处理中不得为了“恢复干净”破坏他人或用户的未提交内容。**

### 12.7 最终路径的发布协议

当约定的产出是 `path/to/result.md` 时，必须区分：

```text
candidate path:   每个 owner worktree 内的 path/to/result.md
publication path: 整合方 worktree 内的 path/to/result.md
published ref:    最终 commit / PR / release
```

候选作者只提交自己的相对路径，**不直接把文件复制到共享主仓**。协调者选定后，由唯一
整合方从冻结 commit 取内容，在独占整合 worktree 写发布路径，运行最终门禁，再形成最终
commit。是否推到 `master/main`、开 PR 或发布仍受批准约束（§3）。

**发布动作必须带预期版本**：更新 Git ref 时校验目标仍指向整合方开始时记录的 commit；
文件或对象存储使用版本号、ETag 或等价的 compare-and-swap。目标已变化时**发布失败**，
创建新的整合轮次：读取新基线、重新解决冲突、重跑受影响门禁，再尝试发布。不得以强推、
无条件覆盖上传或先删后写绕过竞争。

若明确只要多个可比较草案，则发布目标是**候选集合及其清单**，而不是某个候选抢占正式
路径。只有作出选择后，才产生单一最终文件。

### 12.8 保留与清理

| 状态 | 默认保留 |
| --- | --- |
| 已选定 / 已整合 / 已发布 | 最终 commit、来源映射、验收、证据 |
| 已拒绝 | 候选 commit/摘要、拒绝理由和必要证据 |
| 已过期 / 被取代 | 血缘和摘要；是否留全文按审计与复用价值决定 |
| 失败 | 最小复盘证据、副作用状态和可恢复 checkpoint |
| 已取消 | 取消依据、已产生副作用、需补偿项 |
| 敏感临时物 | 达到最短业务/审计要求后尽快安全销毁 |

**清理是显式阶段，不是收工的副作用。**删除前验证：结果可重取；所需 commit 可达；摘要
可校验；副作用已收敛；没有活跃引用；保留期限已满足。清理记录至少包含操作者、时间、
对象、依据和失败项。

## 13. 证据账

证据按流程分级，不能只有“全套”与“零记录”两档。

| 流程 | 最小留证 |
| --- | --- |
| 单路实施 | 请求记录或 PR 中固定最终 commit、验收方、门禁命令及原始输出位置 |
| 定向审核 | 任务包链接、评审、处置、最终 commit 与验证结果 |
| 最小选优 | 任务包链接、参与者清单、候选 commit 映射、决策、处置与验证结果 |
| 完整选优 | 下列完整记录 |

```text
request          # 原始意图、边界、基线、门禁、资源上限
manifest         # 角色、参与者、耗时、状态、异常
candidates       # 匿名编号、commit、覆盖和验证声明
reviews          # 独立审、对照审、逐条主张裁决
decision         # 门禁、偏好评分、决胜与选定 commit
improvements     # 主张 ID、来源、commit、测试与冲突
dispositions     # 接受/部分接受/拒绝及证据
verification     # 最终 commit 上的回归结果
```

证据使用项目已有的请求记录、PR/Issue、CI 产物和 Git commit。载体可以分散，但必须由一个
稳定的主记录串起全部链接，并**能由第三方读取**。任何流程都不得只在聊天中宣称测试通过；
**另一个人不能恢复和复核的内容视为未持久化**。

候选 commit 必须来自该候选自己的分支。共享工作区里的未提交文件、从别人路径拷来的稿，
不得写入候选清单。

## 14. 成本与停止规则

- 资源上限、超时、外部副作用和人工批准点必须在启动前写入任务包；
- 完整交叉阅读是二次复杂度，候选较多时采用平衡分配，但每个候选获得相同评审覆盖；
- 无法运行命令的评审保留价值，但必须标注“未经事实验证”，且不能替代验收方的运行结果；
- 自动化必须保证单路失败、超时或缺席也进入记录，不能由成功路线覆盖；
- 其余停止条件见 §11.8。

## 15. 完成判据

只有同时满足以下条件，一件开发工作才算闭环：

- 原始意图、边界、验收、权限、成本和基线已冻结且可追溯；
- 工作区、分支和 owner 明确；每个产出有 owner、命名空间、状态、来源和唯一发布目标/
  整合方；
- 候选没有直接写共享路径或 `master/main`，发布只从独占整合面发生；
- 发布目标通过预期版本的条件更新，发布竞争没有变成静默覆盖；
- 并行结果绑定 commit；迟到、失败和取消已处置；
- 硬门禁和逐条证据裁决先于偏好评分；最终有效评审与候选作者分离；
- **全部门禁和验收在最终 commit 上逐条重跑通过**；
- 涉及的多仓提交和 gitlink 均可取得；
- 未覆盖范围、盲区、副作用和残余风险已公布；
- 证据账完整，且没有把“经过评审”夸大成“已经证明正确”；
- 没有任何执行者把未提交产出留在共享工作区；交卷清单里每一项都是可达 commit。

缺项时只能按实际阶段称为“候选完成”“评审完成”“本轮选定”“待验证整合”或“待发布”，
不能笼统宣称完成。

## 16. 反模式

| 反模式 | 失败方式 |
| --- | --- |
| 并行单元共用工作树 | 相互覆盖、无法归因 |
| 会话隔离当作文件隔离 | 多人仍写同一个物理文件，最后保存者覆盖前者 |
| **用 `-new` / 时间戳 / 助手名当隔离** | 文件名不是工作区。共享路径上照样后写覆盖先写，且制造虚假安全感 |
| 把人的主 checkout 当文档原件投放点 | 既覆盖人的未提交改动，也覆盖其他执行者的草稿 |
| 所有候选直接写约定的最终路径 | 路径成为竞态，选优在写入时被偷偷决定 |
| 发布时不校验目标版本 | 新结果静默覆盖别人的更新，或旧结果覆盖新结果 |
| non-fast-forward 后强推 | 用运输命令抹掉并发历史和已评审对象 |
| 用 mtime 判断作者或采用版本 | 时钟和后续复制会误导溯源，来源丢失 |
| 未跟踪文件作为唯一交付 | 无 commit/摘要，覆盖后难以恢复和归因 |
| 交卷报路径不报 commit | 路径会漂移、会被覆盖，评审对象丢失 |
| 未提交就让别人到“同一路径”接盘 | 拷走的是没有归属的污染源，接盘者不再独立 |
| 每个执行者都写共享 `handoff.md` | 单写者面被互相覆盖，交接游标失真 |
| 候选阶段偷看其他候选或发起方倾向 | 产出是改写不是独立信号，选优失效 |
| 自评自收、自我批准 | 验收失去独立性，缺陷被背书 |
| 候选人互投制造独立性 | 被审方兼任判定方，独立性是假的 |
| 多数票覆盖失败测试 | 偏好压过事实 |
| 只固定分支名 | 评审对象漂移 |
| 冻结后原地替换或把迟到 commit 算进本轮 | 比较对象漂移，无法复核 |
| 最终 commit 不回归 | 整合缺陷未被发现 |
| 把会话记忆或人脑当状态账 | 接手者无法恢复现场，决定无痕丢失 |
| 只靠自律执行纪律 | 换人或换会话后纪律蒸发 |
| Git 充当授权、成本或副作用账 | 恢复后越权或重复动作 |
| 删除分支/worktree 前不建立持久 ref | commit 变成不可达对象，可能被回收 |
| 复制文件代替整合记录 | 内容存在但来源、取舍和验证对象不明 |
| 把“已派工”或“全部返回”当作完成 | 内部动作冒充最终结果 |
| 静默扩大范围 | 越权副作用无人批准 |
| 伪造完整结果掩盖缺口 | 验收被污染，缺口被当成已完成 |
| 人当协调者就跳过隔离与角色分离 | 独立信号退化成改写 |

## 17. 常见失败方式与项目实例

上一节的反模式是机制描述。本节记录本项目实际遇到过的失败，并按**证据强度**分三级标注。
三级不是修辞差别，是能不能独立复核的差别：

- **已核对事实**：证据当前仍可独立取得并复核（commit、blob、文件存在性、可重跑命令）；
- **事故报告**：确实发生过，但现场已灭失，只能按当事方陈述记录，不能独立复核；
- **设计风险**：机制上成立，但本项目尚未实际踩到，或原始证据出处已不可取得。

三级不可互相升格。尤其**不得**把“机制上必然如此”当成“此处已核对”——这正是 §12.6
第 4 步要求的态度：能证明的和推断出来的分开写。

| 失败 | 证据性质 | 控制 |
| --- | --- | --- |
| **隔离来自 worktree + 命名分支，不来自文件名** | **已核对事实（2026-09-02）**：三方在各自 worktree 与命名分支上持有**同名且不带后缀**的文档，内容互不相同且**全部得以保留**；各自的 commit 与 blob 可独立复核。故后缀**非必要**；又因同一工作树内两方写同一带后缀的路径照样互相覆盖，后缀亦**非充分** | §12.1、§12.3、§16 |
| **未提交同路径写入没有任何保护** | **已核对事实**：Git 对未跟踪/未提交文件的同路径写入不提供冲突检测、不留历史、不留作者归属。这是 Git 的语义，可随时复现 | §10.1、§12.3、§12.5 |
| **多执行者写进共享 checkout 造成覆盖** | **事故报告（2026-09-02），现场已灭失**：当事方陈述有产出在共享 checkout 上被后写覆盖。共享路径上的文件事后已被清走，**具体发生过哪一次覆盖、写入顺序和责任人均不可独立复核** | §12.1、§10.1、§12.6 |
| 以工作区最后一版代替 commit 做交卷或比选 | **已核对事实**：磁盘上的“当前文件”不携带作者归属，也不能证明谁先写完 | §12.3、§12.5 |
| 评审给出的验收标准无人回跑 | **已核对事实（2026-08-27）**：当轮的 `disposition.md` 末节自记，一份“未回跑”、一份“待评审方执行”、一份仅第 3 条通过 | §11.7、§15 |
| 评审意见的处置边界由被审方单方划定 | **已核对事实（2026-08-27）**：当轮记录逐条由被审方判定采纳或拒绝，其中一条门禁因“三台机器分别报 0 / 4 / 95 条失败”被判误报并删除。**“优胜作者拒绝改进”这一更强的说法未获记录支持，不采用** | §11.5、§11.7 |
| 只写分支名，不固定 commit | **事故报告（2026-08-27）**：当事方记录评审曾引用旧提交而主方已前进；原始记录中**未找到**对应条目 | §12.3、§10.5 |
| 只测一端就宣布跨仓契约完成 | **现行硬规则**：[`../constraints.md`](../constraints.md) C4——单仓 CI 只跑自己那半，provider 改了、consumer 锁没跟，两边各自都绿 | §10.2 |
| 候选提前读取其他方案 | 设计风险。机理清楚，但本项目的原始记录出处已不可取得 | §11.4 |
| 把历史设计或目标态当成代码现状 | 设计风险（同上）。四级词典与 dormant 回跑是现行控制 | §10.2 |
| 多数票覆盖失败测试 / 全体一致的共同盲区 | 设计风险（同上） | §11.6 |
| 大补丁混合多条主张 | 设计风险，尚未在本项目实跑 | §11.7 |
| 整合时拷贝未提交文件进共享主仓 | 设计风险：绕过选定哈希，主仓变成公共投稿箱 | §12.7 |
| 完整选优流程本身 | **本项目尚未完整实跑**：独立裁判、匿名随机评审和停止规则目前是制度设计，不得写成既成能力 | §11 全节 |

**纪律的效力不依赖那次覆盖是否可复核**：上表的已核对事实足以支撑 §12.1、§10.1 和 §12.3
的全部要求。**用不可复核的叙述去加强一条本来就成立的规则，只会削弱整份文档的证据标准。**
